# Version 4

Version 4 expands Structure's compiler-visible PySpark transformation coverage. Its purpose is simple: when a developer
knows a PySpark transformation API, Structure should offer a clear typed equivalent or an immediate, documented answer
about why that operation remains outside the DSL.

## What V4 Covers

- Column methods and SQL functions that can remain typed and symbolic.
- Nested struct, array, and map transformations with exact result types.
- Schema-aware parsing transformations.
- DataFrame transformations, joins, aggregates, and windows whose schema and row-cardinality behavior is explicit.
- Row-expanding generators only if their schema-and-cardinality design proves safe and reviewable.

## What Stays Outside

V4 does not own data loading, storage or writes, table/catalog management, actions such as `collect()`, streaming
sources or sinks, triggers, checkpoints, output modes, or query lifecycle. Those are caller-owned PySpark concerns.
Raw SQL strings, raw Spark windows, and UDF/UDTF helpers remain explicit hook boundaries rather than compiler-visible
Structure APIs.

## Coverage Promise

The release creates a checked transformation coverage catalog for the supported PySpark 3.5.x and 4.0.x range. Each
relevant API is marked supported, scheduled, deferred, or unsupported, with its Structure spelling, compatibility
profile, semantic differences, and evidence. This means an unimplemented PySpark transformation is visible rather than
surprising.

See [PySpark Transformation API Coverage](dev/design/V4TransformationApiCoverage.md) for the design and
[the v4 ExecPlan](dev/planning/P07132601.V4-transformation-api-coverage.plan.md) for the delivery sequence.
