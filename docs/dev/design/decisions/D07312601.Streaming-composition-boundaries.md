# Streaming Composition Boundaries

Status: Accepted

Date: 2026-07-31

## Context

A transform can accept streaming input and produce an output that is consumed by another transform. Without an explicit
boundary rule, a downstream transform that omitted streaming declarations could accidentally be compiled as a batch-only
consumer. Class-level `@transform(streaming=True)` is also insufficient to establish lineage: it is a compatibility
marker, while `input(..., streaming=True)` identifies the relation that is actually streaming.

## Decision

- Streaming lineage is carried from declared streaming inputs through compiled step outputs. A class-level streaming
  marker alone does not make an output streaming.
- At pipeline and stage-graph composition boundaries, a streaming output must be consumed by an input declared
  `streaming=True`.
- The configuration key `allow_stream_to_batch` defaults to `false`. When enabled, it permits an otherwise undeclared
  stream-to-batch boundary for callers that intentionally own that transition.
- An explicit `input(..., streaming=False)` or `@transform(streaming=False)` is a hard rejection at a streaming
  boundary, regardless of `allow_stream_to_batch`. This declaration is reserved for transforms that deliberately do not
  support streaming, such as transforms using incompatible helpers.
- The check runs while resolving the output-to-input assignment, so the diagnostic identifies the producer output and
  downstream input before target code generation.

## Consequences

This fails unsafe or ambiguous composed boundaries early, while preserving an escape hatch for deliberate boundaries.
Users must declare streaming mode on the consuming input, not only on the transform class. Stream sources, sinks,
materialization, output modes, checkpoints, and query lifecycle remain caller-owned.
