# Decision: Platform Callbacks, Private Engine Replacement, and Messaging

## Status

Accepted for v5 planning on 2026-07-16.

## Context

Structure needs to support one target platform per transform without treating PySpark APIs as universal Structure APIs.
Core must remain responsible for workflow lifecycle and consistent public artifacts, diagnostics, storage, and CLI.
Some advanced platform vendors may nevertheless need to adjust an engine to give a callback information that the public
Platform API does not yet express.

## Decision

Platform plugins implement a public, versioned `PlatformAPI1` façade with small workflow service facets. Core discovers
one provider per platform id and does not separately register schema, compiler, execution, generation, serialization,
or capability providers. Core owns the default compiler, execution, generation, schema, serialization, capability,
diagnostic, and artifact workflows. Target APIs are imported from the selected platform package, not the `structure`
root.

Core and callback plugins negotiate the highest mutually supported Platform API version using each side's minimum and
maximum range. This negotiation is symmetric and permits either side to be newer.

A selected plugin may optionally supply private replacement classes for individual Core engines. Core discovers a
mapping automatically from that selected plugin's private manifest and constructs classes itself. The mapping is scoped
to the selected platform id and current workflow, never global state. This extension is deliberately undocumented and
private; the replacement must preserve all public output contracts, which Core validates.

Replacement engines do not downgrade. Their manifest declares a compatible Structure version range and an exact private
`core_engine_revision` for the complete engine suite. Core rejects target activation on either mismatch and never
silently falls back to the stock engine. The token changes only when a private engine contract changes.

`PlatformAPI1` may optionally implement synchronous duck-typed `send(message)`. A stock or replacement engine calls
the façade and receives its direct return value. Payloads and replies are arbitrary in-process Python objects owned by
the plugin vendor. Core provides failure diagnostics but no transport, persistence, message schemas, events, or
asynchronous bus.

## Consequences

External plugins have a stable public callback path and can negotiate Platform API versions. Advanced engine replacement
is possible but intentionally has a stricter upgrade burden, avoiding an unsafe mixture of old and new private engines.
The small `send` escape hatch prevents premature protocol expansion while keeping a normal feature request on the path
to a future typed Platform API method.

The v5 implementation must add engine-manifest validation, private engine-suite revisioning, output-boundary checks,
and diagnostics. It must exercise both public callback downgrade directions separately from strict replacement-engine
compatibility. Documentation must state the public callback policy while keeping private engine replacement out of the
external authoring guide.
