# Decision: Plugin API and Private Engine Replacement

## Status

Accepted for v5 planning on 2026-07-16.

## Context

Structure needs to support one target platform per transform without treating PySpark APIs as universal Structure APIs.
Core must remain responsible for workflow lifecycle and consistent public artifacts, diagnostics, storage, and CLI.
Some advanced plugin vendors may nevertheless need to adjust an engine beyond what the public Plugin API expresses.

## Decision

Plugin plugins implement a public, versioned `PluginAPI` façade with small workflow service facets. Core discovers
one plugin per plugin name and does not separately register schema, compiler, execution, generation, serialization,
or capability plugins. Core owns the default compiler, execution, generation, schema, serialization, capability,
diagnostic, and artifact workflows. Target APIs are imported from the selected plugin package, not the `structure`
root.

Core and Plugin API plugins negotiate the highest mutually supported Plugin API version using each side's minimum
and
maximum range. This negotiation is symmetric and permits either side to be newer.

A selected plugin may optionally supply private replacement classes for individual Core engines. Core discovers a
mapping automatically from that selected plugin's private manifest and constructs classes itself. The mapping is scoped
to the selected plugin name and current workflow, never global state. This extension is deliberately undocumented and
private; the replacement must preserve all public output contracts, which Core validates.

Replacement engines do not downgrade. Their manifest declares a compatible Structure version range and an exact private
`core_engine_revision` for the complete engine suite. Core rejects target activation on either mismatch and never
silently falls back to the stock engine. The token changes only when a private engine contract changes.

Class injection is disabled by default. Core constructs a replacement only when global Structure configuration sets
`plugin.plugin_options = "allow_injection"`. The setting applies to every plugin rather than a named plugin, so the
diagnostic for a blocked replacement tells the user to opt in only when the selected plugin is trusted.

## Consequences

External plugins have a stable public Plugin API path and can negotiate Plugin API versions. Advanced engine
replacement is possible but intentionally has a stricter upgrade burden, avoiding an unsafe mixture of old and new
private engines. A vendor replacement engine can call its vendor-owned Plugin API classes directly.

The v5 implementation must add injection-opt-in validation, engine-manifest validation, private engine-suite revisioning, output-boundary checks,
and diagnostics. It must exercise both public Plugin API downgrade directions separately from strict
replacement-engine
compatibility. Documentation must state the public Plugin API policy while keeping private engine replacement out of
the
external authoring guide.
