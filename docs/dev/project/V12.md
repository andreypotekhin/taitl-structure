# V12: PySpark 4.2 Adoption and Deeper Transformation Coverage

Status: active; Sprint 61 preparation complete on 2026-10-25. Runtime implementation remains pending.
V12 has twelve two-week sprints, 61 through 72. Calendar dates are unset.

V12 carries V11 pipelines onto PySpark 4.2, admits useful new transformation APIs, and extends the query, temporal,
spatial, sketch, Python, and ordinary streaming features that V11 implemented narrowly. Adoption and deeper coverage
share the same feature sprints. Spark Connect remains batch-only throughout V12.

## Goals and release boundaries

Users can select the exact `>=4.2,<4.3` target, run admitted transforms directly or as generated PySpark, and find
profile-specific guidance for unsupported shapes. Existing 3.5, 4.0, and 4.1 behavior remains covered by regression
lanes. The new target must carry forward V11 capabilities explicitly; the existing 4.2 capability entry does not
establish that continuity.

The feature commitments are temporal/Variant validation, native spatial extensions, Tuple sketches, richer queries,
ranked matching and available native vector operations, Arrow grouped iterators, ordinary state completion, selected
streaming compositions, and streaming observations. Each commitment includes its types, diagnostics, generated form,
examples, and live evidence. Exact API signatures and admitted streaming combinations are settled in the package's
design/specification before coding. A missing core deliverable requires an explicit scope revision; changing its
status to design-gated does not by itself satisfy that commitment.

Delta/Iceberg 4.2 admission, provider-specific CDC bindings, and managed spatial evidence depend on released compatible
providers and available sessions. Sprint 61 establishes feasibility; Sprint 71 collects the final provider evidence.
Record unavailable pairs and caller remedies without claiming support. Typed consumption of caller-created change
DataFrames remains useful independently of a provider-specific binding.

Sources, sinks, triggers, checkpoints, query start/stop, recovery, and external effects remain caller-owned.
Real-time triggers and stable source/sink names belong in caller-owned guidance. V12 does not admit Connect streaming,
automatic persisted-state migration, Dataset/Scala-only state APIs, implicit UDF fallback, general orchestration,
unrestricted callbacks, XML, cost-based join reordering, or Variant mutation absent a released upstream API.
Arrow UDTFs retain their separate caller-owned status.

## Target and compatibility policy

Ordinary PySpark 4.2 is the primary target. Spark Connect 4.2 batch claims require separate positive evidence.
Add `pyspark42` and `spark-connect42` to the existing ordinary/Connect 3.5, 4.0, and 4.1 matrix. These names and their
commands are planned interfaces until Sprint 61 implements them; no new lane has passed merely because it is listed.

Pin the Spark engine, PySpark client, Python, Arrow, pandas, Java, and optional provider packages in the runtime ledger.
Review public Python APIs separately from SQL/JVM release additions, including signatures and changed semantics.
Typed internal lowering to a public Spark function is a package design decision; exposing raw SQL or a generic
untyped call is not the fallback for an unavailable Python wrapper.

Keep the default profile at `>=3.5,<4.2` during development. Sprint 72 evaluates promotion to `>=3.5,<4.3` after the
eight-lane matrix and compatibility checks pass. Range promotion does not expose exact-target features in a profile
whose lower versions cannot implement them. Retaining the existing default is acceptable with a recorded rationale.

Preserve existing source behavior unless a package documents a necessary source change and migration before coding.
Checkpoint compatibility is separate from source compatibility; same-configuration restart evidence does not prove
cross-version Spark checkpoint upgrades or state-schema migration.

## Delivery and dependencies

Sprint 61 establishes the runtime and inventory foundation for every package. Existing V11 features may use those
lanes immediately; unresolved carry-forward differences stay visible until their feature sprint closes them.
Sprint 65 supplies query infrastructure for ranked matching. Sprint 68 supplies state evidence for Sprint 69.
Sprint 70 uses the streaming-stage metadata and admitted compositions from Sprint 69. Provider dependency resolution
starts in Sprint 61 rather than waiting for Sprint 71.

Every feature sprint starts with a source example and a design/specification that fixes the public behavior.
Create a focused ExecPlan under `docs/dev/planning/` when implementation needs multiple steps, following
[Plans](../auto/Plans.md). Existing specifications are inputs, not evidence that V12 extensions already exist.
The [Sprint 61 implementation plan](../planning/P10252601.V12-admission-and-runtime.plan.md) defines runtime pins,
runner selections, the API census, capability continuity, and provider feasibility for the initial sprint.
Add user stories and their tests when the package's API is specified; mark them complete only with implementation
and evidence. Keep public references, capability inventories, diagnostics, generated fixtures, and relevant annotated
source synchronized during delivery.

Each coding task runs `make build`; focused live integration checks are discretionary during development.
Every V12 sprint closes with `make build INTEGRATION=1 BACKEND=all` against its closing candidate, including all eight
configured backend selections and required isolated provider phases once Sprint 61 adds the new lanes. Record the
tested revision, commands, runtime versions, selection scope, passed/failed/skipped totals, reasons, outstanding gates,
and logs in the sprint review or ExecPlan. Resolve integration regressions before closure and rerun affected selections,
broadening reruns when shared changes invalidate other results. Follow the
[validation cadence](../Testing.md#validation-cadence); the full matrix is not a task completion requirement.

Each feature sprint supplies native/online/generated parity on each claimed target before support admission or marking
user stories complete. Implementation tasks may finish while this sprint evidence is pending.
Ordinary streaming evidence includes caller-owned same-checkpoint restart, required output/time modes, and relevant
late-data and eviction cases. Connect receives batch evidence only. Measure compilation and generated-plan behavior
when changing symbolic execution, query composition, or lowering. The final sprint verifies the integrated release
and admits no new feature family.

## V11 handoff

The six-lane V11 release matrix and integration-enabled build passed on 2026-10-23. Preserve that dated evidence.
The [V11 retrospective](V11Retrospective.md) and the separate runtime-validation follow-up are complete. All six
ordinary/Connect selections now have unfiltered passing evidence; the 2026-10-25 reruns are recorded in the archived
runtime-check plan and Sprint 60. These results do not change the dated 2026-10-23 V11 release matrix.

Carry forward the independent gates for managed Databricks sessions, legacy Pandas timeout/output behavior,
broader stateful chains, and streaming missing-column unions. Preserve the Apache/Sedona session-isolation rule
unless new provider-specific evidence establishes a safe replacement. Other historical milestone follow-ups are
not automatically adopted by V12.

## Risks and responses

| Risk | Response |
| --- | --- |
| 4.2 loses exact-4.1 capabilities | Inventory continuity and test both variants before feature expansion. |
| Provider artifacts are unavailable | Probe in Sprint 61; gate exact pairs and retain caller-created frames. |
| Query and state scope grows | Specify admitted shapes per package and record scope revisions explicitly. |
| Ranked matching is expensive or ties vary | Prove candidate bounds, disclose native ties, and compare plans. |
| Arrow changes conversion behavior | Exercise nulls, large integers, coercion, and declared return schemas. |
| Streaming timing and recovery vary | Use isolated fixtures with progress, eviction, and restart checks. |
| Final testing becomes a bottleneck | Collect evidence each sprint; reserve Sprint 72 for integration defects. |

## Exit criteria

- The reviewed 4.1-to-4.2 Python/API-semantic delta and carried V11 features each have one status, sprint owner,
  target/variant, streaming classification, diagnostic or remedy, and evidence location.
- Committed feature packages meet their sprint acceptance; any changed scope is recorded with its user impact.
  Conditional provider admissions retain exact dependency and availability records.
- Ordinary and Connect 4.2 batch features have native/online/generated schema and value parity. Ordinary streaming
  has mode, watermark/state, late-data/eviction where relevant, and same-configuration restart evidence.
- Eight configured runtime lanes pass their documented unfiltered selections; provider phases are isolated where
  required. Record selection coverage, failures, skips and reasons, unavailable providers, and exact versions.
  A skipped lane is not a pass, and passing a scoped selection is not a full-suite claim.
- `make build INTEGRATION=1 BACKEND=all` passes; generated artifacts and support ledgers agree with the release.
  Record compiler/plan performance comparisons for changed paths.
- The default-profile decision, migration guidance, troubleshooting, completed-plan moves, and retrospective are
  recorded. Unfinished work retains an owner and remedy; Connect streaming is excluded from release criteria.
