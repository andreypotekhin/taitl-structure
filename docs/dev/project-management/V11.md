# V11: PySpark 4.1 Adoption and API Parity

V11 follows the V10 closeout and adopts PySpark 4.1 as an explicit Structure target. It first inventories the upstream
4.1 Python API delta, then admits only typed, symbolic, explainable transformation contracts. Reader, writer, session,
catalog, declarative-pipeline, SQL-scripting, Python-data-source, arbitrary-UDF, and streaming-lifecycle APIs remain
caller-owned or design-gated unless a separate contract proves that they fit Structure.

## Goal

Make the PySpark 4.1 target profile reproducible and useful: users can select `>=4.1,<4.2`, use admitted 4.1
row-preserving and relational APIs through Structure's DSL, and see the same result in online and generated execution on
ordinary PySpark. Spark Connect receives the same claim only where 4.1 documentation and live evidence prove parity.

## Target policy

The primary V11 target is ordinary PySpark with `profile = ">=4.1,<4.2"` and `variant = "ordinary"`. The secondary
target is `variant = "spark-connect"` with the same profile for APIs that Spark Connect supports. PySpark 3.5 and 4.0
ordinary and Connect lanes remain regression lanes. The existing default profile stays `<4.1` until the final V11 gate;
promotion to a default range including 4.1 requires all retained 3.5/4.0 behavior, the 4.1 feature ledger, and both
claimed variants to pass.

## Feature families

V11 has six feature work packages plus one cross-cutting retained-V9 design package. Each package must produce an
implementation-ready design, a normative specification,
an API Catalog status and reference entry, capability requirements, diagnostics, focused tests, and live evidence or an
explicit gate.

The first package covers the 4.1 API inventory, `Column.transform`, deterministic and seeded scalar/string helpers, and
the other row-preserving built-in functions that can be given exact Structure types. The second covers relational query
operations: `DataFrame.exists`, IN-subquery behavior, and `DataFrame.lateralJoin`, including cardinality and alias
rules. The third covers complex-type observations and approximate-sketch aggregates, with an explicit decision about
whether their metric and binary-result semantics belong in Structure. The fourth covers Python-facing execution
families. Arrow-optimized UDF/UDTF APIs remain design-gated; row-based `transformWithState` is supported for ordinary
PySpark 4.1 under its admitted mode and lifecycle contract. The distinct `transformWithStateInPandas` interface has a
separate package and evidence gate for ordinary PySpark 4.0 and 4.1. The fifth
package extends the versioned integration infrastructure and evidence ledger so every admitted
feature runs across the selected target matrix.
The sixth package adds an optional PySpark Delta integration: schema-level `check(...)` and `delta_columns` declarations, caller-bound
`delta_table(...)` for same-schema reads and mutations, read-only `delta_input(...)`, and result-schema
`delta_output(...)` for explicit evolution. It includes compiled delete/update/merge/append and selective
`replaceWhere`, runtime transform variables, typed snapshot/CDF/history/detail reads, and explicit restore, optimize,
and vacuum effects. Ordinary PySpark checks generated, identity, and default metadata before insert omission. Spark
Connect Delta support remains outside this admission. Same-schema effects can be
inferred for typed `-> None` methods or returned directly from a typed merge with the target schema as the return
annotation. Compile-time evolution checks cover target, source, and result compatibility. Snapshot/CDF reads select the
step return schema; streaming CDF remains caller-created and caller-managed. Spark-free and build checks pass. Classic
PySpark / Delta live integration passes for classic 3.5.3 / 3.3.3, 4.0.0 / 4.0.1, and 4.1.0 / 4.1.0 in separate
Delta processes. The package does not claim general Delta table administration or
install native checks during transforms. Durable contracts live in the [Delta design](../design/DeltaTables.design.md),
[specification](../specifications/DeltaTables.spec.md), and [reference](../../reference/DeltaTables.ref.md).

The cross-cutting retained-V9 package carries forward only the design and evidence work that V9 intentionally left
gated: future-profile Variant mutation, PySpark 4.2 Variant evidence, broader chained stateful composition, streaming
side effects, and typed-state parity beyond the admitted row subset. V11 tracks four separate streaming families: row
`transform_with_state` on ordinary PySpark 4.1, Pandas `transform_with_state_in_pandas` on ordinary PySpark 4.0/4.1, legacy
`apply_in_pandas_with_state` on ordinary PySpark 3.5/4.0/4.1, and the remaining Dataset/Scala arbitrary-state APIs.
The row family is supported for its admitted 4.1 contract. Pandas and legacy Pandas remain independently gated until
their own contracts, live parity, and restart evidence pass; Dataset/Scala state remains outside the claim. Row
`foreach` and `foreach_batch` are caller-owned handoffs with
documented safety boundaries, not Structure-managed streaming lifecycles. See the [row state admission plan](../planning/past/P10062603.V11-transform-with-state-admission-and-typed-parity.plan.md),
[legacy Pandas state plan](../planning/P10062602.V11-apply-in-pandas-with-state.plan.md), and
[foreachBatch plan](../planning/past/P10052601.Schema-declared-foreach-batch-sinks.plan.md).
The exact watermarked dedupe-to-event-time-window pair is now supported on
ordinary PySpark 3.5.0 and 4.0.0 with per-operator budgets and caller-owned query recovery. It keeps XML helpers and
cost-based join reordering deferred and does not add either to the V11 implementation scope. The governing plan is
[V11 retained V9 design gates](../planning/P08042603.V11-retained-v9-design-gates.plan.md).

## Exit criteria

Every PySpark 4.1 API addition in the reviewed Structure boundary has exactly one status: supported, planned,
design-gated, caller-owned-guided, streaming-ineligible, or unsupported. The row, Pandas, and legacy state families
have separate status rows and evidence owners; no one state-family result promotes the others. Supported rows have typed contracts,
capability checks, diagnostics, online/generated parity, and live ordinary 4.1 evidence. A Spark Connect row is not
marked supported until its Connect-specific evidence passes. The six-version matrix is runnable by one documented
command, generated artifacts are fresh, the API Catalog and API Reference agree with the machine-readable ledgers, and
`make build` passes. The Delta package additionally proves that one `Schema` definition can validate a caller-supplied
Delta table's shape and native checks, execute compiled data mutations, and return the
same table handle. Schema changes are opt-in and checked against the method's declared result schema; constraints and
Delta column metadata remain caller-provisioned. Ordinary PySpark checks feature metadata at binding. Runtime variables,
inspection reads, maintenance effects, and selective overwrite are admitted on the tested classic profiles. Classic
Delta admission is independent of Delta Connect admission. The exact Connect 4.1 Delta package is documented
in the [completed Delta Connect plan](../planning/past/P10062601.V11-delta-connect-admission.plan.md); it does not widen
ordinary Delta claims to other Connect profiles. The broader V11 matrix remains separate work.
