# V11: PySpark 4.1 Adoption and API Parity

V11 follows the V10 closeout and adopts PySpark 4.1 as an explicit Structure target. It first inventories the upstream
4.1 Python API delta, then admits only typed, symbolic, explainable transformation contracts. Reader, writer, session,
catalog, declarative-pipeline, SQL-scripting, Python-data-source, arbitrary-UDF, and streaming-lifecycle APIs remain
caller-owned or design-gated unless a separate contract proves that they fit Structure.

## Goal

Make the PySpark 4.1 target profile reproducible and useful: users can select `>=4.1,<4.2`, use admitted 4.1
row-preserving and relational APIs through Structure's DSL, and see the same result in online and generated execution on
ordinary PySpark. Spark Connect receives the same claim only where 4.1 documentation and live evidence prove parity.

## Target policy

The primary V11 target is ordinary PySpark with `profile = ">=4.1,<4.2"` and `variant = "ordinary"`. The secondary
target is `variant = "spark-connect"` with the same profile for APIs that Spark Connect supports. PySpark 3.5 and 4.0
ordinary and Connect lanes remain regression lanes. The existing default profile stays `<4.1` until the final V11 gate;
promotion to a default range including 4.1 requires all retained 3.5/4.0 behavior, the 4.1 feature ledger, and both
claimed variants to pass.

## Feature families

V11 has six feature work packages plus one cross-cutting retained-V9 design package. Each package must produce an
implementation-ready design, a normative specification,
an API Catalog status and reference entry, capability requirements, diagnostics, focused tests, and live evidence or an
explicit gate.

The first package covers the 4.1 API inventory, `Column.transform`, deterministic and seeded scalar/string helpers, and
the other row-preserving built-in functions that can be given exact Structure types. The second covers relational query
operations: `DataFrame.exists`, IN-subquery behavior, and `DataFrame.lateralJoin`, including cardinality and alias
rules. The third covers complex-type observations and approximate-sketch aggregates, with an explicit decision about
whether their metric and binary-result semantics belong in Structure. The fourth covers Python-facing execution
families. Arrow-optimized UDF/UDTF APIs remain design-gated; row-based `transformWithState` has a separate
implementation package for ordinary PySpark 4.1, and remains gated until its contract and runtime evidence pass. The
distinct `transformWithStateInPandas` interface has a separate package for ordinary PySpark 4.0 and 4.1. The fifth
package extends the versioned integration infrastructure and evidence ledger so every admitted
feature runs across the selected target matrix.
The sixth package adds an optional PySpark Delta integration: schema-level `check(...)` declarations, caller-bound
`delta_input(...)` and `delta_output(...)`, compiled delete/update/merge/append operations, and return-typed,
operation-scoped schema evolution. Same-schema mutations preserve the table schema unless evolution is explicitly
enabled. The package does not claim general Delta table administration or install native checks during transforms.

The cross-cutting retained-V9 package carries forward only the design and evidence work that V9 intentionally left
gated: future-profile Variant mutation, PySpark 4.2 Variant evidence, broader chained stateful composition, row-level
streaming side effects, and arbitrary state. The exact watermarked dedupe-to-event-time-window pair is now supported on
ordinary PySpark 3.5.0 and 4.0.0 with per-operator budgets and caller-owned query recovery. It keeps XML helpers and
cost-based join reordering deferred and does not add either to the V11 implementation scope. The governing plan is
[V11 retained V9 design gates](../planning/P08042603.V11-retained-v9-design-gates.plan.md).

## Exit criteria

Every PySpark 4.1 API addition in the reviewed Structure boundary has exactly one status: supported, planned,
design-gated, caller-owned-guided, streaming-ineligible, or unsupported. Supported rows have typed contracts,
capability checks, diagnostics, online/generated parity, and live ordinary 4.1 evidence. A Spark Connect row is not
marked supported until its Connect-specific evidence passes. The six-version matrix is runnable by one documented
command, generated artifacts are fresh, the API Catalog and API Reference agree with the machine-readable ledgers, and
`make build` passes. The Delta package additionally proves that one `Schema` definition can validate a caller-supplied
Delta table's shape and native checks, execute compiled data mutations, and return the same table handle. Schema changes
are opt-in and checked against the method's declared result schema; constraint metadata remains caller-owned.
