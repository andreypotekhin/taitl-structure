## Purpose / Big Picture


After this work, a Structure transform can build an inner relation query with `where()` and `project()`, test whether
its rows exist, test membership with `.isin(...)`, and laterally join those rows to its driving lane. A lateral join
evaluates a relation query that can refer to the current driving row and produces zero, one, or multiple matching
rows. Users can prepare the query before joining or describe it inside `lateral_join()`. They do not need a public
`subquery()` wrapper or a new `select()` authoring API.

The visible proof is equal native PySpark, online Structure, and generated PySpark results and schemas on separately
verified ordinary and Connect 4.1 runtimes. Tests must demonstrate nulls, duplicates, missing matches, ordered limits,
and the difference between filtering the inner query and testing its rows in the join's `on=` condition. Existing
lane filtering and semi/anti joins must retain their behavior on earlier profiles.

## Surprises & Discoveries


The existing `exists(..., on=...)` is a filtering operation lowered to a semi join; `not_exists(..., on=...)` uses an
anti join. These preserve only driving rows and do not yet provide a general native EXISTS expression in a computed
output or Boolean combination. Evidence: `dsl/body.py:where` recognizes root `existence_join` expressions and turns
them into join operations; `dsl/InputScope.py:_existence_join` creates that expression.

`InputScope.where()` currently delegates to the active step's global `where()` helper. It does not build a query over
that secondary relation. Current-row `.where()` and joined-row chains are tested behavior, so query construction must
distinguish unjoined relation inputs from the driving and joined row scopes. Evidence: `dsl/InputScope.py`,
`dsl/RowScope.py`, and the row-filter/ordered-operation tests named below.

The older V11 specification groups EXISTS and IN under a correlated predicate contract. The approved first IN slice
is uncorrelated membership against projected relation columns; correlated EXISTS and lateral joins use explicit outer
references. `DataFrame.exists` and `DataFrame.lateralJoin` originated in PySpark 4.0; the DataFrame argument to
`Column.isin` is the 4.1 extension. API origin does not admit an untested Structure profile.

The first descriptor draft stored filters, projection, orderings, and limit separately. That cannot preserve
user-authored order when projection precedes a later filter or order. The descriptor now stores an immutable ordered
operation tuple and derives its schema and bound from that tuple. Evidence: the Spark-free query tests assert query
immutability and operation order; the renderer follows that sequence.

`InputScope.where()` is used in two contexts: an unjoined relation input starts a relation query, while a joined
`InputScope` continues the existing driving-step filter chain. Evidence: the multiple-schema and symbolic-execution
regression suite initially exposed a chain break; dispatch now preserves joined-row behavior, and 156 focused
regression cases pass.

The composite IN fixture exposed a PySpark lowering difference: Spark 4.1 treats `F.named_struct(...)` as one
unexpanded expression for `Column.isin(DataFrame)`, while `F.struct(...)` with aliased members participates in
composite-column IN semantics. The `named_struct(...)` Structure helper now evaluates and renders with `F.struct` and
member aliases; parity tests lock this generated shape. Evidence: ordinary and Connect 4.1.0 native/online/generated
query tests pass with the same composite input.

## Decision Log


Decision (2026-10-18, user): Use `.isin(relation_or_query)` for native-shaped membership and preserve Spark SQL null
semantics. Keep literal/list `isin(...)` unchanged. Rationale: IN can return unknown/null and must not be replaced by
ordinary semi-join or null-safe-key behavior.

Decision (2026-10-18, user): Build typed queries with equivalent `where()` and `filter()` methods, preferring `where()`
in examples. Project with `project()` or a `to=` schema parameter. Rationale: retain Structure's existing projection
vocabulary while following PySpark's relation-query composition style.

Decision (2026-10-18, user): Support a prepared query followed by `lateral_join(...)`, and an inferred
`lateral_join(where=..., to=..., ...)` form. Use the driving lane implicitly and bind joined fields back to the right
scope without requiring a result assignment. Rationale: match existing inferred join ergonomics and permit reusable
query expressions.

Decision (2026-10-18, user): Admit inner and left lateral joins, with optional `on=`. Default to inner. Rationale:
inner drops rows without matches; left retains them with nullable right fields. The join condition is evaluated after
the inner query, including its limit, and must not be pushed into that query by Structure.

Decision (2026-10-18, user): Require ordering before a query limit and explicit `allow_cartesian=True` for an
uncorrelated lateral product without a connecting join condition. Rationale: preserve Structure's established
ordered-selection and Cartesian-join contracts.

Decision (2026-10-18, agreed contract): Mark outer references with `.outer()`, retain a single named inner relation
per query, and initially admit only filtering, projection, ordering, and limits. Rationale: scope, schema, and
cardinality must be established without arbitrary DataFrame callbacks. New native operations are batch-only and
target exact ordinary and Connect `>=4.1,<4.2`, with admission based on each variant's own positive evidence.

Decision (2026-10-18, implementation): Store relation-query steps as an immutable ordered tuple and derive current
schema, ordering, and bound from it. Rationale: grouping operations by kind would change semantics when users project
or filter before later operations; an ordered sequence preserves the authored plan. Date/Author: 2026-10-18, Codex.

Decision (2026-10-18, implementation): Dispatch `.where()` on an unjoined `InputScope` to query construction and on a
joined scope to the existing step-filter chain. Rationale: adding relation queries must not change the established
fluent join/filter API. Date/Author: 2026-10-18, Codex.

Decision (2026-10-18, implementation): Lower `named_struct(...)` through aliased `F.struct(...)` in online and
generated execution. Rationale: native 4.1 `Column.isin(DataFrame)` expands a struct built with `F.struct` into its
member columns for composite membership; `F.named_struct` did not provide the required IN-subquery arity on ordinary
Spark. This preserves field names and typed member order. Date/Author: 2026-10-18, Codex.

## Context and Orientation


Run commands from `/Users/chaos/Files/Dev/Code/taitl-structure`. Structure captures typed Python methods into an
intermediate representation, or IR: data describing expressions and ordered relation operations. The compiler lowers
that description into shared recipes. Online execution evaluates recipes against Spark; code generation renders the
same recipes as readable PySpark. A recipe is the common semantic contract, not a separate Python callback per row.

The first schema parameter is the driving row scope. Additional schema parameters represent named, initially unjoined
relations. A relation scope identifies a particular input occurrence; two inputs with identical schema classes still
have different scopes. A projection establishes the output fields, their types, aliases, and nullability. Cardinality
describes how many result rows an operation can produce for each driving row.

Relevant code lives under `src/structure/plugin/pyspark/`. `api/AuthoringAPI.py:PySparkStepSession` binds driving and
secondary parameters. `dsl/RowScope.py`, `dsl/InputScope.py`, `dsl/body.py`, and `dsl/relation_sets.py` own row access,
joins, filtering/projection, and ordered limits. `dsl/Expression.py` owns literal/list IN and Boolean operators.
`symbolic_execution/model/PySparkSymbolicContext.py` records active scopes and operations;
`symbolic_execution/commands/ValidatePySparkJoins.py` validates existing join contracts.

Lowering belongs in `compiler/logic/maps/MapPySparkExpression.py` and the compiler's relation recipes and operation
maps. Evaluation belongs in `execution/logic/expressions/EvaluatePySparkExpression.py` and its relation delegates;
rendering belongs in `render/logic/expressions/RenderPySparkExpression.py` and `render/logic/steps/RenderPySparkStep.py`.
Extend the associated scope rewriting, requirement collection, fingerprint, explain, and traceability visitors so
query trees do not disappear from compilation, caching, or diagnostics.

`capabilities/model/PySparkCapabilities.py` decides which exact profile/variant admits an operation. Streaming
classification is separate from backend admission. Machine-readable inventories and evidence live in
`resources/pyspark-4.1-python-api-delta.json`, `resources/pyspark-transformation-inventory.json`, and
`resources/pyspark-transformation-coverage.json`.

The integration harness is `scripts/run_integration.py` with Compose services under `infra/compose/`. Use
`tests/integration/pyspark/support/backend_matrix.py` for profile selection, generated projects, and runtime sessions.
Use the existing row/parity helpers, preserving duplicate rows rather than comparing sets.

## Interfaces and Dependencies


Introduce an internal typed relation-query descriptor under `dsl/`, with immutable ordered operations, the named inner
input occurrence, current projected fields, source dependencies, explicit outer dependencies, and any known upper row
bound. It must not contain a live DataFrame, perform an action, or mutate the active driving lane when constructed.
Intermediate descriptors in a consumed chain count as consumed; constructing a descriptor and ignoring the whole
query raises an actionable compile diagnostic. Reusing a descriptor leaves its earlier operations unchanged.

Unjoined `InputScope` receivers expose `.where(*predicates)` and `.filter(*predicates)` as equivalent query builders.
Queries expose those methods plus `.project(target)`, `.order_by(*orderings)`, `.limit(count)`, and `.exists()`.
`project(target)` accepts the existing Schema-class and explicit field-subset forms. Schema projection uses declared
field types, aliases, and nullability; subset projection retains requested order. The first slice does not add a new
computed-column selection syntax. Current and joined row receivers preserve their existing `.where()` step effect;
their `.filter()` alias has that same effect. The global step-level `where(...)` keeps its current meaning.

`Expression.outer()` returns an expression with unchanged value type and nullability, marked as belonging to a visible
outer scope. Validate it when the query is consumed. Permit references to the driving row and already joined outer
scopes, requiring `.outer()` inside the inner query. Reject unmarked outer capture, markers containing inner fields,
markers outside an inner query, unrelated scopes, and nested correlation. Use existing `relation_alias(...)` to give
separate occurrences of the same source distinct names; never resolve a field by its name alone.

Implement this public join interface, using the project's normal overloads and option types:

    lateral_join(
        relation=None,
        *,
        where=None,
        on=None,
        to=None,
        order_by=(),
        limit=None,
        how="inner",
        allow_cartesian=False,
    )

`relation` is an unjoined input or prepared query. If omitted, infer exactly one inner relation from the predicates;
otherwise report the candidates and require an explicit argument. With a prepared query, inline options append
filtering, ordering, limit, and projection in that order; `on` remains the separate join condition. `to` performs the
same schema projection as `.project(to)`. Omitted projection retains the known source/query schema. Require a
non-negative integer literal excluding booleans for limits and a preceding valid ordering, including in inline form.

The join uses the active driving lane and exposes its projected right fields through the original right scope. It
returns the same joined row scope for optional assignment. `on` accepts a typed Boolean expression over the driving
or already joined outer scopes and the projected inner output. It uses normal field references, without `.outer()`.
Prepared-query field access such as `matching.quantity` refers to that query's projected output; inline references
such as `inventory.quantity` must refer to fields retained by `to`. Reject references to dropped fields. Normalize
`"left"`, `"leftouter"`, and `"left_outer"` to left; accept the corresponding `Join` enum values for inner and left.

Preserve duplicate right rows. With a query upper bound N, inner produces 0..N rows per driving row and left produces
1..max(1,N); without a limit the upper bound is unknown. These bounds are metadata, not singleton assertions. Left
makes all right fields nullable in the joined scope, even if the query schema requires them. Do not promise final
row order merely because the inner query is ordered.

Require `allow_cartesian=True` if the query has no outer dependency and `on` has no condition connecting the right and
outer scopes. This is a scope/dependency check, not proof that the predicate is selective. A prepared or explicit
relation is necessary when predicates cannot identify the inner input. No implicit dedupe or row-count action is
introduced.

New `.exists()` on a query or bare relation creates a non-null Boolean expression. Negation uses `~`; Boolean
composition uses the existing operators. Keep existing `exists(..., on=...)` and `not_exists(..., on=...)` filtering
paths, their streaming behavior, and earlier profile support. Do not route the new expression through the old
root-only semi/anti-join extraction in `where()`.

Extend `Expression.isin` to accept exactly one relation/query argument, without mixing it with literal/list arguments.
The first slice permits uncorrelated right queries. Scalars compare against one output column; struct expressions,
including existing `named_struct(...)`, compare against projected columns in order. Validate arity and member types
using the established scalar comparison rules and structural member compatibility, rather than schema class identity
or matching column names. Preserve native three-valued IN/NOT IN behavior and schema nullability, including nested
nullable members and empty right inputs. Keep the existing literal/list path unchanged.

Query-local joins, aggregates, windows, nested subqueries, correlated IN, and arbitrary Python DataFrame callbacks are
outside the first query slice. Existing typed scalar expressions and expression helpers remain available in query
predicates. Preserve their metadata and Spark's runtime errors; do not replace native failures with silent coercion or
session reconfiguration. All new native query consumers require exact ordinary/Connect `>=4.1,<4.2` capability and
batch input. Do not backport native admission solely because some upstream methods originated in 4.0.

are implemented; its presence in this plan is not a support claim:

    from structure import *
    from structure.plugin.pyspark import *

    class Store(Schema):
        store_id = string(nullable=False)

    class Inventory(Schema):
        inventory_id = long(nullable=False)
        store_id = string(nullable=False)
        status = string(nullable=False)
        item_name = string(nullable=False)
        quantity = long(nullable=False)

    class ClearanceItem(Schema):
        item_name = string(nullable=False)
        quantity = long(nullable=False)

    class StoreItem(Schema):
        store_id = string(nullable=False)
        item_name = string(nullable=True)

    @transform
    class ClearanceItems(Transform):
        stores = input(Store)
        inventory = input(Inventory)
        items = output(StoreItem)

        def find(self, store: Store, inventory: Inventory) -> StoreItem:
            lateral_join(
                where=(
                    (inventory.store_id == store.store_id.outer())
                    & (inventory.status == "Clearance")
                ),
                to=ClearanceItem,
                on=inventory.quantity > 50,
                how="left",
            )
            return StoreItem(store_id=store.store_id, item_name=inventory.item_name)
