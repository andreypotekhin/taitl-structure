# Close the PySpark temporal SQL baseline

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and

## Purpose / Big Picture

A Structure user should be able to migrate PySpark date, timestamp, epoch, and interval expressions without losing
compile-time types or silently crossing from a wall-clock timestamp to an instant. The user can verify the result in a
transform, its generated PySpark, and online execution. The default target is the common PySpark 3.5.x/4.0.x API, not a
4.1-only addition.

## Surprises & Discoveries

- Live PySpark 3.5 and 4.0 both confirmed that invalid `to_timestamp_ntz` input raises with ANSI enabled and returns
  null with ANSI disabled; `try_to_timestamp` returns null in either mode. The existing NTZ API description was
  corrected accordingly.
- `to_unix_timestamp` is not an alias: it requires an input and is deterministic. `unix_timestamp()` also has a
  query-time no-input form.
- `timestamp_seconds/millis/micros` always return LTZ even when `spark.sql.timestampType` selects NTZ. Spark's
  timestamp-to-epoch helpers accept LTZ and use floor division for negative instants.
- Structure already uses a fixed-name internal `F.call_function` lowering. Reuse it for typed generic timestamp
  patterns; the arbitrary scalar `call_function` API remains unsupported.
- Spark's migration guide confirms `date - date` and `timestamp - timestamp` return DayTimeIntervalType with legacy
  interval mode off and CalendarIntervalType with it on; date plus day-time interval returns Timestamp.
- Live arithmetic found that adding CalendarInterval to Date returns Date, not Timestamp. YearMonth/DayTime arithmetic
  and qualifiers matched generated execution on classic and Connect 3.5/4.0. DayTime values convert to Python
  `timedelta`; YearMonth conversion succeeded on classic 3.5 but failed on classic 4.0 and Connect Arrow; Calendar
  values failed conversion on classic and Connect 4.0. Keep interval values inside expressions and collect ordinary
  result columns.
- The focused v6 API-ledger plus plugin-boundary test selection passed (`170 passed`); new temporal unit coverage passed
  (`8 passed`). The final `make build` is green, including 2,078 main-suite passes and 78 follow-up-suite passes.
- Generated and online NTZ results matched on both Spark versions, including a row-dependent datetime pattern and a
  generic component constructor. The row yielded the expected wall-clock values `2026-10-02 00:00:00` and
  `2026-10-02 09:30:00`.

## Decision Log

- Decision: generic timestamp construction and parsing follow `spark.sql.timestampType`; explicit LTZ/NTZ helpers do
  not. A live session supplies that setting before compilation, while offline compilation uses an explicit Structure
  override or defaults to LTZ. Fingerprint the resolved setting and reject a mismatched runtime or output Schema.
  Rationale: a compiled expression must have one declared result type.
  Date/Author: 2026-10-02 / user and Codex.
- Decision: `Temporal` and `Interval` are `StrEnum` values. `Temporal.DAY_OF_YEAR` carries `"doy"`, and the literal
  `"dayofyear"` remains an accepted alias; do not add a second constant. Cover canonical extract/truncation/weekday
  choices and interval units/qualifiers, not arbitrary patterns or time-zone IDs.
  Rationale: constants improve discoverability while ordinary strings preserve migration ergonomics.
  Date/Author: 2026-10-02 / user and Codex.
- Decision: `make_timestamp*` accepts typed numeric seconds; Decimal is recommended for exact fractions. Generic and
  LTZ variants accept a typed String time zone. A zone passed to generic `make_timestamp` with an NTZ result emits a
  warning because it does not shift the wall clock.
  Rationale: mirror Spark's component conversion without hiding the NTZ distinction.
  Date/Author: 2026-10-02 / user and Codex.
- Decision: `to_timestamp`, `to_timestamp_ltz`, `to_timestamp_ntz`, and `try_to_timestamp` accept typed String format
  expressions. Explicit LTZ/NTZ parsers take String inputs; generic/try parsers admit String, Date, or LTZ. A format
  passed with an already typed Date/LTZ warns that Spark ignores it. Numeric epochs use the explicit epoch helpers.
  Rationale: allow per-row patterns while retaining Structure's focused typed conversions.
  Date/Author: 2026-10-02 / user and Codex.
- Decision: `to_unix_timestamp` requires an input and accepts typed String patterns. `unix_timestamp(value, ...)`
  also accepts typed patterns; its no-input form keeps a literal pattern and query-stable time. Warn when a typed
  Date/LTZ input renders the pattern ineffective.
  Rationale: keep both PySpark names and the query-clock distinction.
  Date/Author: 2026-10-02 / user and Codex.
- Decision: one `interval(...)` value constructor and one `types.interval(...)` factory require exactly one of `type=`
  or `unit=` and one component per selected field. Preserve `make_interval`, `make_ym_interval`, and
  `make_dt_interval`. No `_ym` or `_dt` convenience variants.
  Rationale: explicit type choices read clearly without duplicating APIs.
  Date/Author: 2026-10-02 / user and Codex.
- Decision: expose YearMonth and DayTime interval Schema types with exact qualifiers. Calendar is expression-only in
  PySpark 3.5; in 4.0 it is allowed in Schema, though classic Row conversion raises `NotImplementedError` and Connect
  Arrow conversion rejects Calendar values. YearMonth conversion is also target-sensitive; DayTime converts to
  `timedelta`. Date plus CalendarInterval is Date, while Date plus DayTimeInterval is Timestamp. Mirror
  `spark.sql.legacy.interval.enabled` for date/timestamp subtraction and fingerprint it as a compilation input.
  Rationale: preserve target behavior and make legacy-sensitive output types visible.
  Date/Author: 2026-10-02 / user and Codex.

## Context and Orientation

`src/structure/plugin/pyspark/dsl/expressions.py` constructs typed symbolic expressions; its helpers return an
`Expression` with a known type and nullability. `src/structure/plugin/pyspark/render/logic/expressions/RenderPySparkExpression.py`
turns those expressions into generated PySpark; `src/structure/plugin/pyspark/execution/logic/expressions/EvaluatePySparkExpression.py`
evaluates them online. The root package `src/structure/plugin/pyspark/__init__.py` exports public helpers. Schema types
and their Spark conversions live under `src/structure/plugin/pyspark/dsl/types/`. Configuration and fingerprints are
assembled in the plugin/compiler layers; inspect the current `StructureSession` and compiler configuration paths
before editing them.

LTZ is an instant measured relative to a time zone; NTZ is a wall-clock date and time without one. YearMonth and
DayTime intervals carry a fixed range of calendar fields. A mixed Calendar interval may combine both and is not
interchangeable with either. A qualifier such as `YEAR TO MONTH` determines the interval's fields and its Schema type.

## Plan of Work

First add `Temporal` and `Interval` string-valued enums and their public exports. Give context-specific validators
canonical spellings while retaining accepted literal aliases. Add `date_diff`, `dateadd`, and `day` wrappers with the
same argument order, typing, and target spelling as their established equivalents. Correct `localtimestamp()` to NTZ.

Next add the timestamp constructors and parsers. Require integral year/month/day/hour/minute components and numeric
seconds. Let Spark validate calendar ranges and microsecond coercion; nullable results reflect possible invalid
values. Keep the explicit constructors' fixed type and the generic constructor/parser's resolved type. Accept typed
String zones where Spark does. Add the NTZ-zone warning, ineffective-format warning, and fixed-name internal lowering
for `to_timestamp` with a typed format. Do not expose arbitrary `expr` or `call_function` to users.

Then add `to_unix_timestamp` and the six epoch functions. `timestamp_seconds` accepts numeric values, including
fractions, and returns LTZ; millis/micros accept integral values and return LTZ. `unix_seconds/millis/micros` accept
LTZ and return Long. Preserve Spark overflow and NaN/infinity behavior; do not silently cast NTZ into an epoch.

Finally add interval types, constructors, arithmetic, and `extract`/`date_part`/`datepart` fields. The field must be
compiler-visible (Python string, enum value, or typed String literal), not row-dependent. Normalize accepted aliases,
including `"doy"` and `"dayofyear"`, to Spark's supported spelling. Return Integer for integral parts and
`Decimal(8,6)` for seconds. Include date/timestamp subtraction and numeric interval multiplication/division, with
legacy mode affecting the subtraction result type. Enforce the 3.5 Calendar Schema restriction and document 4.0
Python Row conversion behavior.

After each slice, update generated and online lowering, public exports, capabilities, streaming classification,
documentation, and focused tests. Update `docs/dev/design/PySparkSQLBoundaryContracts.design.md`, the parent plan,
the function-level gap register, `docs/api/Expressions.api.md`, `docs/api/Schemas.api.md`, the matching public reference
pages, and `docs/QuickRef.md` in reader-appropriate locations. Keep the machine-readable inventory and coverage
ledgers in sync with actual exports. Follow `docs/dev/auto/Documenting.auto.md` for annotated source.

## Validation and Acceptance

One transform must be able to construct an interval, extract `Temporal.DAY_OF_YEAR`, parse a row-dependent timestamp
pattern, build a fixed LTZ epoch timestamp, and convert an LTZ timestamp back to epoch microseconds with declared
types. Generated PySpark and online execution must agree. A user who supplies an ineffective format or an NTZ
constructor time zone must receive an actionable compile warning. Incorrect types or unresolvable configuration must
fail before execution. `make build` must pass before the coding task is complete.
