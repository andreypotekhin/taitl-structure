# Reduce Search validation query plan growth

Completed 2026-09-27. Maintained according to `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

Implement the three approved follow-ups to the 92-step Search graph: measure validation growth and checkpoint
planning; reuse equivalent policy checks without weakening validation; test earlier materialization inside
`FuseDocuments`. Small inputs must not require repeatedly expanding large query plans.

## Surprises & Discoveries

- The original singleton check cross-joined the source with an aggregate of that same source. Each repeated
  `param_join` constructed this guard again. Whole-relation assertions also copy their source into a guard branch.
- Temporary views shorten submitted expressions but do not erase Spark's expanded query plan. Reliable checkpoints
  are still necessary before expensive branches are reused.
- The old empty-policy guard raises on classic Spark, despite its empty cross-join source, but can be pruned on
  Connect. The new guard consistently rejects zero rows, enforcing the existing documented cardinality contract.
- Reusing expanded policy attributes after a checkpoint triggers a Spark 3.5 conflicting-attributes error. Cache
  the nested guarded row and project fresh output attributes for each join instead.
- Connect's generated executor mislabeled duplicate-key failures from checkpoints as `CONNECT-E2601` because the
  server stack trace mentioned `RDD`. Classify the error message without the appended JVM stack trace so the real
  `REL-E0702` diagnostic reaches the caller. Focused classifier tests retain real classic-only boundary detection.

## Decision Log

- Keep `require_all` and `require_unique` as whole-relation assertions. Replacing them with ordinary row filters
  could hide failures after downstream filtering. Do not remove safety checks to improve benchmark numbers.
- Use a singleton-policy check over at most two rows: one is valid, zero or two is invalid. A bounded aggregate of
  row structs preserves null-valued rows and field nullability without a self-join. The initial bounded-window
  prototype emitted misleading Spark global-window warnings; the bounded aggregate avoids that mechanism.
  Explicit `exactly_one` remains unchanged. The failure expression must be inside the generated array so an empty
  array cannot bypass validation when exploded.
- Reuse only identical DataFrame objects and diagnostic scopes during one synchronous transform run. Never retain
  cached frames on the executor or across runs; never apply this guard to streaming steps.
- Keep checkpoint ownership inside `FuseDocuments`, controlled by its existing `materialize` parameter.

## Outcomes & Retrospective

The final bounded aggregate plus early checkpoints passes the isolated Spark 3.5 Search test in 85.49s versus
172.55s for the equally profiled baseline. Combined online/generated construction is 56.79s versus 140.63s (about
60% lower). These are single-run observations, not medians. Nine singleton checks are constructed per mode instead
of 52. Estimated expanded input references are cut from 672/236 to one before lexical/vector uniqueness validation.
All seven Search tests pass on ordinary 3.5, ordinary 4.0, and Connect 4.0. Policy/fusion safety checks pass on all
three backends after fixing the Connect error classifier; the streaming bypass case also passes on all three.
The final build passes: 1,947 tests passed / 195 skipped, secondary checks 78 passed / 7 skipped, mypy clean across
1,278 files, and both package artifacts built. `git diff --check` passes. Detailed commands, timings, and intermediate
failures are recorded in `docs/dev/issues/I09272601/SearchIntegrationPerformance.bench.md`.

The approved three-point scope is complete. This is not a fresh full-repository live integration certification,
and it does not promote Search streaming support or establish repeated cross-backend performance medians.

## Context and Orientation

Online execution lives in `RunOnlinePySparkTransform`; generated execution is emitted by `RenderPySparkStep` and
`RenderPySparkTransformModule`. Both now use the same `PolicyChecks` runtime helper. At the start of this work, Search
checkpointed only at the end of `examples/search/transforms/searching/search_docs/fuse.py`. Candidate uniqueness checks
earlier in that component expanded both lexical and vector input branches; each now has a preceding conditional
checkpoint, while the final checkpoint remains. Existing measurements are in
`docs/dev/issues/I09272601/SearchIntegrationPerformance.bench.md`.

## Plan of Work

Add optional profiling to integration support, with checkpoint planning measured separately through a public explain
request. Label the remaining checkpoint duration accurately: it can include additional planning, not just executor
work. Record guard construction counts/times and structural query plan growth where available. Run one isolated
reranking baseline before editing production behavior. Implement a run-scoped policy-check cache and bounded guard,
then compare the same case. Test checkpoint placement before candidate uniqueness checks as well as the existing
output checkpoint. Preserve rankings, schemas, UDF behavior, and malformed-input failures.

## Concrete Steps

Use `poetry run pytest` for focused tests and Docker Compose integration runners for live Spark. Run ordinary 3.5,
ordinary 4.0, and Connect 4.0 sequentially with stage outputs disabled and a 600-second runner deadline. Keep raw
logs under a task-specific `/tmp` directory; record commands and results in the benchmark report. Do not run heavy
host builds or another Spark driver during measurements. Finish with `make gold`, `make build`, and `git diff --check`.

## Validation and Acceptance

Tests must cover zero/one/multiple policy rows, null policy values, unchanged schemas, malformed rows hidden by
downstream filtering, equivalent checks reused within a run, separate/nested/concurrent run isolation, streaming
bypass, and online/generated parity. Search must preserve ranking assertions. Report unsuccessful runs honestly;
do not compare a profiled run to an unprofiled one as a speedup claim.

## Idempotence and Recovery

Preserve the existing dirty worktree. Profiling is opt-in and restores monkeypatches after each test. Cache ownership
ends even on exceptions. Checkpoints retain the established caller/session-owned checkpoint-directory lifecycle.
Do not delete Spark volumes or unrelated generated artifacts.

## Artifacts and Notes

describe the previously measured Search graph, not a permanent API contract.

## Interfaces and Dependencies

No new public Search class or configuration switch is required. Runtime reuse is internal and action-free; the only
eager work remains explicitly requested reliable checkpointing. Integration profiling is a development-only option.
