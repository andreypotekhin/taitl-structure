# Add tenant-safe personal recommendations to Store

This ExecPlan is a living implementation record for Store personal recommendations. It follows
`docs/dev/auto/Plans.md`; the progress, discoveries, decisions, and outcomes below must remain current until the work is
complete.

## Purpose / Big Picture

The Store example currently ranks eligible catalog products with transparent merchandising and behavior feedback
signals. This change adds a separate personalization workflow that uses catalog feature arrays, explicit customer
category preferences, browsing and purchase history, and a deterministic latent-factor baseline. The existing
`Recommender` remains the serving boundary and adds the personal contribution to its current score.

The design is tenant-safe. `tenant_id` identifies the organization/store, `customer_id` identifies a known shopper
within that tenant, `session_id` identifies a browsing session, and `request_id` identifies one recommendation request.
The serving key is `(tenant, request_id, product_id)`; persistent user state is keyed by `(tenant, customer_id)`.

## Surprises & Discoveries

- The existing Store schemas already carry nullable `customer_id` and `session_id` on `RecommendationRequest`,
  `RecommendationCandidate`, impressions, purchases, and session events. No new identity field is required for the
  first slice.
- Recommendation joins and ranking consistently use `(tenant, request_id)`; user profile joins must additionally use
  `customer_id` to avoid confusing request identity with shopper identity.
- The existing `Ranker` is an expression-special parameter that is replaced in tests by subclassing. The default
  personalization algorithm will follow the same replacement pattern rather than exposing an intermediate
  factorization-score relation.

## Decision Log

- Decision: Keep `customer_id` as the known shopper identity and do not introduce `user_id`.
  Rationale: Store orders and customer analytics already use `customer_id`; `tenant_id` is the organization scope, while
  `session_id` covers anonymous browsing. A separate `user_id` would only be justified by a distinct cross-tenant
  identity model.
  Date/Author: 2026-08-01 / user and Codex.

- Decision: Put normalized product features in a non-null `array<string>` on `CatalogProduct` instead of adding a
  `ProductFeatureSet` relation in the first slice.
  Rationale: The first preference model matches categories and the Search example already demonstrates label-like
  collected values. A relational source can be materialized into the same catalog array later.
  Date/Author: 2026-08-01 / user and Codex.

- Decision: Keep explicit preferences as include/exclude category arrays and keep inferred history separate.
  Rationale: User-specific weights are unnecessary in the first slice. History uses hard-coded global event weights and
  produces transient category affinity rather than mutating the explicit profile.
  Date/Author: 2026-08-01 / user and Codex.

- Decision: Place personalization under `examples/store/transforms/personalization/`; make `Recommender` consume only
  final personalized recommendations.
  Rationale: Personalization has a distinct dataflow and lifecycle. The serving recommender should not own raw profile,
  history, or algorithm details.
  Date/Author: 2026-08-01 / user and Codex.

- Decision: Use a Ranker-style replaceable personalization algorithm and do not expose a stable factorization-score
  schema.
  Rationale: The toy latent algorithm and a future replacement are complete algorithm swaps. The stable boundary is the
  final personal recommendation row consumed by `Recommender`.
  Date/Author: 2026-08-01 / user and Codex.

## Context and Orientation

`examples/store/schemas/catalog.py` defines the prepared catalog consumed by recommendation candidates. `Product` has
tenant, product, category, and audit facts; `PrepareCatalog` filters active and unblocked products and adds promotion
evidence. `RecommendationRequest` already contains optional `customer_id` and `session_id`. `Recommender` composes
signal building, candidate generation, ranking, diversification, publication, and run summarization. Its `Ranker`
parameter in `transforms/recommender/ranking/ranker.py` demonstrates the intended replaceable expression strategy.

Generated Store source is registered in `tests/helpers/example_projects.py` and checked against
`examples/structure_generated/store/`. Differential recommendation coverage lives in
`tests/differential/store/test_store_reference_contract.py`; generated-output coverage lives in
`tests/golden/test_examples_generated_output.py`.

## Interfaces and Dependencies

Add `features = array(string(), contains_null=False, nullable=False)` to `CatalogProduct`.

Add personalization schemas under `examples/store/schemas/personalization.py`:

- `UserFeaturePreference`: tenant, customer ID, included category array, excluded category array, and update time.
- `PersonalizationHistory`: tenant, nullable customer ID, nullable session ID, product ID, category, and aggregated
  history score. Browsing and purchase events are aggregated before serving joins.
- `PersonalizedRecommendation`: tenant, request ID, nullable customer ID, nullable session ID, product ID, personal
  score, matched-category flag, explicit-exclusion flag, algorithm ID, and algorithm version.

The result key is `(tenant.tenant_id, request_id, product_id)`. `customer_id` and `session_id` are provenance and lookup
context, not replacements for the request key.

Add `examples/store/transforms/personalization/` with focused transforms for catalog feature preparation, history
normalization, explicit preference matching, and final recommendation construction. The default algorithm uses global
constants for event weights and computes a deterministic hashed latent score from tenant/product/request context. Its
implementation is supplied through a Ranker-style `parameter` class so tests and future algorithms can replace it.

`Recommender` receives `personalized_recommendations` and left-joins by tenant/request/product. It adds the personal
score to the existing score, preserves suppression and deterministic tie-breakers, and carries personal explanation
fields into `RecommendedProduct`. Empty personal input leaves current behavior ranking unchanged.

## Plan of Work

First extend `CatalogProduct` and `PrepareCatalog` so the catalog carries normalized category/taxonomy feature tokens.
Carry the optional feature array through the raw `Product` contract and catalog normalization. Add preference and history
schemas with nullable identity fields matching the existing request/session model, and export them through Store package
initializers.

Implement the personalization workflow as independent stages. Explicit category exclusions are applied before scoring;
inclusions and history affinity contribute positive score. Customer history is keyed by tenant plus customer when
available, with session-only history used for anonymous requests. Do not persist anonymous activity as customer state.
The first slice uses hard-coded global weights: product views 1, other browsing events 2, add-to-cart 3, and purchases 5.

Implement the default algorithm as a `@special(type="expr")` strategy analogous to `Ranker`. It must publish the final
`PersonalizedRecommendation` fields and algorithm metadata; no factorization intermediate schema is public. Add a
constant replacement algorithm in tests to prove the swap boundary.

Wire the workflow into `Merchandising` and `Recommender`. Keep existing raw signal inputs and outputs available so
behavior evaluation remains compatible. Add personal score and explanation fields to ranked and published rows, update
run summaries if needed, and update Store documentation with the identity and fallback rules.

Register every new schema and transform in the Store example renderer, regenerate checked-in Store output, and update
focused differential references. Avoid touching unrelated dirty-worktree changes.

## Validation and Acceptance

The feature is accepted when:

- Two tenants with the same customer ID never share preferences or history scores.
- Two requests for one tenant/customer reuse the customer profile, while anonymous requests use session context only.
- Product category features match explicit includes and exclusions, with exclusions taking precedence.
- Personalization changes ranking only when a personal score exists; empty personal input reproduces behavior ranking.
- A replacement algorithm class changes the personal score without changing the `Recommender` serving interface.
- Generated Store source renders and imports successfully, and online/generated behavior matches the independent
  reference for focused scenarios.
- `make build` completes successfully.

## Idempotence and Recovery

## Outcomes & Retrospective

Implemented and validated on 2026-08-01:

- `Product.features` and `CatalogProduct.features` are label-like arrays; catalog normalization preserves them and the
  personalization feature stage adds the category token.
- `UserFeaturePreference` stores tenant-scoped customer include/exclude category arrays. `customer_id` is the known
  shopper identity; `session_id` supports anonymous browsing; `request_id` is only the serving join key.
- `BuildPersonalizationHistory` aggregates browsing and purchase facts in a separate personalization workflow.
- `PersonalizationAlgorithm` is a complete `@special(type="expr")` replacement boundary. The default is a deterministic
  hashed-latent baseline; no factorization intermediate contract is exposed.
- `Recommender` and `Merchandising` blend final personal rows by `(tenant, request_id, product_id)`, preserve the
  existing Ranker four-argument replacement contract, and suppress explicitly excluded products.
- Added Store registrations, generated PySpark/docs/traceability artifacts, generation-order coverage, focused
  tenant-aware and algorithm-swap tests, and README documentation.
- Validation: `make build` passed with 1,489 tests passed and 54 skipped; the rigidity subset passed with 68 passed and
  6 skipped; sdist and wheel packaging both succeeded.

The default factorization implementation is intentionally a deterministic first slice. A future offline-trained model
can replace the complete `PersonalizationAlgorithm` class without requiring a public score-relation compatibility layer.
