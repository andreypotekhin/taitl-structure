# Add assignable direct-row returns and same-class `Schema.base(...)`

This ExecPlan follows `docs/dev/auto/Plans.md`. It is a living plan; the implementation should update its Progress,
Surprises & Discoveries, Decision Log, and Outcomes & Retrospective sections as work proceeds.

## Purpose / Big Picture

Allow compiled transform methods to return an existing symbolic row directly when that row is legally assignable to the
declared output schema:

    def publish(self, shipment: ReadyShipment) -> Shipment:
        return shipment

The same rule must work independently for each result in a multi-output tuple:

    def split(self, shipment: ReadyShipment) -> tuple[Shipment, Shipment]:
        return shipment, shipment

The compiler will still create explicit target-schema projections. Direct returns are authoring shorthand, not permission
to carry arbitrary columns through the pipeline.

Also add public same-class base copying:

    return Shipment.base(shipment)

For an exact same-class source, this copies all effective fields and permits explicit overrides. It must not broaden
`.base(...)` to unrelated schemas that merely have matching field names.

## Surprises & Discoveries

- `Shipment.project(shipment)` does not create a `Shipment` row object. It creates a symbolic `Projection` consumed by the
  PySpark compiler.
- The current multi-output rejection is explicit in `ValidatePySparkResultReturn.py`; the downstream builder already
  lowers each result independently.
- The current `Projection` validator already verifies that an explicit projection target matches the output schema
  associated with its tuple position.
- The current schema IR requires explicit assignments for every output field. The new syntax must preserve that invariant.
- `.base(...)` currently copies fields from direct schema parents. An exact same-class source requires a deliberate special
  case because a root schema has no direct schema parent.
- A completed `Schema.base(...)` call is normally materialized immediately, but existing examples use the chained
  `Schema.base(source)(overrides...)` spelling even when the source is already complete. The first implementation exposed
  this compatibility gap: the full suite failed in the search example with `TypeError: 'DocumentSimilarityPair' object
  is not callable`.

## Decision Log

- Decision: A direct row may be returned only when the source schema is the target schema or a subclass of the target schema.
  Rationale: This follows ordinary assignability direction. A derived row can be returned as its parent schema, but a parent
  row cannot be returned as a more specific child schema. Normal field type and nullability checks still apply.
  Date/Author: 2026-09-17 / user and Codex.

- Decision: Unrelated schemas with matching field names remain invalid for bare-row returns.
  Rationale: Bare-row syntax represents nominal assignment, not structural conversion. Callers must use
  `TargetSchema.project(source)` for intentional same-name structural projection.
  Date/Author: 2026-09-17 / user and Codex.

- Decision: Multi-output direct rows are normalized independently by tuple position.
  Rationale: Each result already has a fixed declared output schema, so `return row, row` has an unambiguous target for each
  element.
  Date/Author: 2026-09-17 / user and Codex.

- Decision: Explicit symbolic projections become legal inside multi-output tuples.
  Rationale: The tuple position already identifies the result schema, and existing projection validation can detect target
  mismatches. The previous prohibition is an unnecessary authoring restriction.
  Date/Author: 2026-09-17 / user and Codex.

- Decision: Exact same-class `.base(source)` copies all effective fields and then applies keyword overrides.
  Rationale: This is simpler for end users and provides a natural copy-with-overrides form. It is restricted to exact schema
  identity and does not permit unrelated structurally compatible schemas.
  Date/Author: 2026-09-17 / user and Codex.

- Decision: For derived schemas, an exact same-class `.base(child)` also copies all effective fields, including local fields.
  Existing calls using a parent-schema source retain current inheritance-based behavior.
  Rationale: Same-class syntax should behave consistently regardless of whether the target has direct schema parents. A
  parent-schema source still uses the existing direct-parent mapping semantics.
  Date/Author: 2026-09-17 / user and Codex.

- Decision: Keep the existing explicit projection IR and Spark `select(...)` lowering.
  Rationale: This preserves field order, aliases, extra-column removal, online/generated parity, and schema validation. The
  feature is syntax sugar, not a new execution path.
  Date/Author: 2026-09-17 / user and Codex.

- Decision: Preserve immediate materialization for complete `.base(...)` calls, but retain the originating base builder on
  those values so they can still receive chained overrides.
  Rationale: This preserves the existing value-like behavior of `Schema.base(source)` while supporting the established
  `Schema.base(source)(...)` authoring form for complete same-class sources and existing derived-schema examples. Ordinary
  `Schema` instances remain non-callable.
  Date/Author: 2026-09-17 / Codex.

## Context and Orientation

`Schema` is the target-neutral row-schema base class in
`src/structure/core/dsl/model/schemas/Schema.py`. A schema class declares ordered fields and can construct symbolic output
values during transform compilation.

`RowScope` is the PySpark symbolic representation of a row parameter. It exposes field expressions such as
`shipment.order_id`, but it is not an instance of the schema class.

`Projection` is the PySpark symbolic record in `src/structure/plugin/pyspark/dsl/model/Projection.py`. It records source
rows and a target schema. `BuildPySparkResultBodies` converts it into explicit field assignments.

`ValidatePySparkResultReturn` validates whether a step returned the required number of result values. It currently rejects
`Projection` values in multi-output tuples.

The online executor and generated renderer already consume per-result projection assignments. No new execution
representation is required.

## Plan of Work

### 1. Extend same-class `.base(...)`

Modify `src/structure/core/dsl/model/schemas/Schema.py`.

Preserve the current behavior for ordinary base overlays:

- A target with a parent-schema source copies fields belonging to the target's direct schema bases.
- Multiple direct bases still require one source per direct base.
- Explicit overrides still replace copied values.
- Unrelated structurally compatible sources remain rejected where the current base rules reject them.

Add an exact-source special case before direct-base validation:

- If the target schema's source schema is exactly the target schema, copy all effective target fields by name.
- Permit this for both root schemas and derived schemas.
- If the source is incomplete, return the existing builder so callers can supply missing fields explicitly.
- Apply keyword overrides after copying, with overrides winning.
- Do not treat a subclass source as an exact same-class source for this special case.
- Do not change `Schema.project(...)`; it remains the structural same-name projection API.

The resulting behavior must include:

    Shipment.base(shipment)
    Shipment.base(shipment)(carrier="UNKNOWN")
    ReadyShipment.base(ready_shipment)

For a derived schema, an exact same-class base copies inherited and local effective fields. A parent-schema source
continues to use inherited-field mapping.

Update the `Schema.base` docstring and schema specifications to describe the exact same-class exception and its restriction
to exact schema identity.

### 2. Normalize direct symbolic rows in PySpark result capture

Modify:

- `src/structure/plugin/pyspark/symbolic_execution/logic/results/ValidatePySparkResultReturn.py`
- `src/structure/plugin/pyspark/symbolic_execution/logic/results/BuildPySparkResultBodies.py`

Allow result values to be:

- a concrete target `Schema` instance;
- a `Projection`;
- a `RowScope` or `InputScope` symbolic row.

For each result position, normalize a symbolic row using that position's declared output schema:

    RowScope(source_schema) + output_schema
      -> Projection(sources=(RowScope,), target=output_schema)

Before normalization, enforce nominal assignability:

    source_schema is output_schema
    or issubclass(source_schema, output_schema)

Then let the existing projection assignment logic perform normal field availability, type, alias, and nullability checks.

If nominal assignability fails, raise `DSL-E0402` with an actionable diagnostic explaining that direct-row returns require
the source schema to equal or derive from the declared output schema, and recommend `TargetSchema.project(source)` for
structural projection.

Do not apply this direct-row shorthand to aggregate results. Aggregated outputs must continue to return explicit schema
constructions containing grouping and aggregate expressions.

### 3. Enable explicit projections in multi-output tuples

Remove the special-case rejection of `Projection` values from `ValidatePySparkResultReturn`.

Retain strict validation that:

- the result is a tuple;
- its length equals the declared result count;
- each result is validated against the output schema at the same tuple position;
- a projection with an explicit target must target that position's declared schema;
- field-list projections must still select every required output field.

This enables:

    return (
        ReadyShipment.project(shipment),
        ReviewShipment.project(shipment),
    )

It also permits mixed forms:

    return (
        shipment,
        AuditedShipment(id=shipment.id, audit_status="checked"),
    )

Each result must independently satisfy the assignability or construction rules.

### 4. Preserve existing lowering

Do not add a separate renderer or executor path.

The normalized direct rows and tuple projections must become the same `ProjectAssignment` records currently used by
explicit projections. Existing code should continue to:

- render one `select(...)` per multi-output result;
- execute each result projection from the shared step input;
- apply result-specific hooks, validations, and post-operations;
- preserve target schema field order and aliases.

### 5. Update documentation

Update the canonical DSL and schema documentation:

- `docs/dev/specifications/DSL.spec.md`
- `docs/dev/specifications/SchemaDeclarationSyntax.spec.md`
- `docs/dev/specifications/SchemaInheritance.spec.md`
- `docs/reference/Transform.ref.md`
- `docs/reference/Schema.ref.md`

Document direct-row returns as assignable-schema shorthand, the source-to-target direction of assignability, direct-row
behavior in multi-output tuples, explicit projections in multi-output tuples, exact same-class `.base(source)` copying all
effective fields, the continued distinction between `.base(...)` and `.project(...)`, and rejection of unrelated
structurally compatible schemas for direct-row returns and same-class base syntax.

## Validation and Acceptance

The feature is accepted when all of the following are true:

- A step returning a symbolic subclass row into a parent-schema output compiles.
- A step returning a symbolic parent row into a child-schema output fails with `DSL-E0402`.
- A step returning a symbolic row into an unrelated same-field schema fails and directs the user to `.project(...)`.
- A same-class `Target.base(source)` copies all effective fields.
- Same-class `.base(source)(override=...)` applies the override after copying.
- Derived-schema same-class base copying includes both inherited and local fields.
- Existing parent-source `.base(...)` behavior remains unchanged.
- `return row, row` compiles when both tuple positions are assignable.
- A tuple with one invalid direct-row result fails for that result's declared output schema.
- Mixed direct-row, explicit schema-constructor, and explicit projection tuple elements work when each is legal.
- `return (TargetA.project(row), TargetB.project(row))` compiles.
- Explicit projection target mismatches still produce a targeted diagnostic.
- Aggregate steps do not accept direct rows as aggregate results.
- Generated PySpark contains explicit per-result `select(...)` projections.
- Online and generated execution retain the same output schemas and rows.
- `make build` completes without errors.

Add tests for aliases, extra source fields, field order, missing fields, nullability, and output schemas with different
subsets of the source fields.

## Artifacts and Notes

The intended new authoring forms are:

    def publish(self, shipment: ReadyShipment) -> Shipment:
        return shipment

    def split(self, shipment: ReadyShipment) -> tuple[Shipment, Shipment]:
        return shipment, shipment

    def split(self, shipment: ReadyShipment) -> tuple[Shipment, AuditedShipment]:
        return shipment, AuditedShipment(
            id=shipment.id,
            audit_status="checked",
        )

    def publish(self, shipment: ReadyShipment) -> Shipment:
        return Shipment.base(shipment)

    def publish(self, shipment: ReadyShipment) -> Shipment:
        return Shipment.base(shipment)(carrier="UNKNOWN")

The following must remain explicit:

    def publish(self, shipment: Shipment) -> ReadyShipment:
        return shipment  # invalid: Shipment is not assignable to ReadyShipment

    def publish(self, row: UnrelatedShipment) -> Shipment:
        return row  # invalid direct return; use Shipment.project(row) if intended

## Interfaces and Dependencies

No new third-party dependencies are required.

The core interface change is the documented behavior of:

    Schema.base(source)

when `source` is an instance or symbolic row whose schema is exactly the target schema. It copies all effective fields and
accepts explicit overrides.

The PySpark authoring interface changes result handling so that a single symbolic row or each symbolic row in a fixed
multi-output tuple can be returned directly when its schema is assignable to the declared result schema.

The existing `Projection`, `ProjectAssignment`, online executor, generated renderer, schema validation, and Spark
capability interfaces remain the implementation foundation.
