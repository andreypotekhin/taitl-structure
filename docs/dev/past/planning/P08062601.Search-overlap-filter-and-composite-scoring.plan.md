# Overlap filtering and multi-grain lexical scoring

This is a living execution plan. It follows `docs/dev/auto/Plans.md`; the progress, discoveries, decision log, and
outcomes are maintained as implementation proceeds.

## Purpose / Big Picture

Document search will use overlap twice for different purposes: an inexpensive early filter and a final lexical scoring
feature. The filter will retain at most 10,000 documents per query, fusion will retain at most 1,000, feedback
reranking will consider those 1,000, and the return stage will emit at most 100. BM25 and IDF-weighted overlap will be
combined independently for documents, sections, paragraphs, and sentences with caller-supplied grain-specific weights.

## Surprises & Discoveries

- The current `OverlapDocuments` stage runs after BM25 retrieval and caps candidates at 100; it cannot provide an early
  performance boundary without moving its inputs to the query/index side of the graph.
- `DocumentScore`, `SectionScore`, `ParagraphScore`, and `SentenceScore` currently carry only one selected scalar,
  while raw BM25 and overlap relations are separate reusable outputs.
- The working tree contains broad unrelated user changes, including the Search streaming migration. Implementation must
  preserve those edits and avoid reverting generated or documentation changes outside this task.
- Live PySpark integration tests are skipped in the current environment; compiler, generated-output, full unit, and
  rigidity suites still execute successfully.
- The first implementation placed query-term filtering directly inside a `FilterDocuments` wrapper; the final design
  composes `OnlineFiltering` directly and keeps target merging in `SelectFilterTargets`.

## Context and Orientation

Search schemas live under `examples/search/schemas/`; lexical score families are `DocumentBm25Score` and
`DocumentOverlapScore` (and their three smaller-grain equivalents), while unified `*Score` schemas carry the selected
score consumed by presentation transforms. Scoring composition is implemented by `ScoreOverlap`, `ScoreBm25`, and
`SelectScores`. Online query gaps are selected by `SelectGapQueries` and served by the document-search stages under
`examples/search/transforms/searching/search_docs/`.

The new pipeline is:

    OnlineFiltering -> SelectFilterTargets -> OnlineVectorization -> OnlineScoring -> RetrieveDocuments -> FuseDocuments -> RerankDocuments

`Filtering` and `OnlineFiltering` produce or resolve timestamped `DocumentFilterScore` rows. `SelectFilterTargets` merges
those rows and emits a typed `(query_id, document_id)` target set. `OnlineVectorization` fills missing query/document
embeddings for the selected targets. `RetrieveDocuments` materializes unranked lexical and raw-vector lanes.
`FuseDocuments` ranks both lexical and vector candidates, deduplicates document identities,
applies RRF, and caps the fused set at 1,000. `RerankDocuments` enriches, ranks, and caps the final results at 100.

IDF-weighted overlap is the sum of IDF values for matched distinct query terms divided by the sum of IDF values for all
distinct query terms. IDF uses the existing BM25 corpus formula and full-corpus document statistics, not statistics of
the filtered candidate set.

## Validation and Acceptance

Acceptance requires deterministic top-10,000 filtering, correct IDF math including missing vocabulary terms, all-grain
weighted scoring, effective-at cache invalidation, top-1,000 reranking followed by top-100 output, online/generated parity,
and unchanged unrelated search behavior. Run focused Search tests first, regenerate artifacts with the repository's gold
target, then run `make build` from the repository root.

## Idempotence and Recovery

All source changes are additive or explicit renames within the task. Generated artifacts are regenerated from source and
must not be hand-edited. Existing unrelated dirty files must remain unchanged. If validation fails, use the focused test
failure and the generated diff to revise only the affected task files.

## Outcomes & Retrospective

Implemented reusable offline/online filtering, target-scoped online vectorization, the document funnel, and the all-grain weighted lexical
scorer. `DocumentFilterScore` is the persisted bridge artifact; `SelectFilterTargets` merges it with online gap results,
and `RerankDocuments` owns the final top-100 cap. `QueryToken.expand()` contains the shared query parsing, while
`SearchDocuments` composes `OnlineFiltering`, `OnlineVectorization`, and `OnlineScoring` directly. The compiler and generated-output tests
verify the stage graph and schema boundaries. The remaining validation gap is live PySpark execution, which is
environment-skipped rather than a source failure.
