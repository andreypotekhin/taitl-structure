# Persist separate span-based Search structural relations

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date during implementation. It follows the repository guidance in
`docs/dev/auto/Plans.md`.

## Purpose / Big Picture

The Search example currently persists paragraph and sentence text in addition to the original document text. That
duplicates most corpus text and makes callers more likely to treat derived text as a durable artifact. After this work,
Search will persist three simple relational structural artifacts instead: `Section`, `Paragraph`, and
`Sentence`. Each row identifies its document and stores a source span; paragraph and sentence text will be
materialized privately only when a transform needs to display or tokenize it.

A caller will still be able to run the familiar pipeline:

    segments = Chunking(documents=documents).run(session)
    index = Indexing(documents=documents, sentences=segments.sentences).run(session)

The observable result is that `segments.sections`, `segments.paragraphs`, and `segments.sentences` contain no text
columns, while Search indexing, passage search, sentence search, and generated PySpark behavior continue to work.

## Surprises & Discoveries

- Observation: Current paragraph content is reconstructed rather than sliced directly from the document.
  Evidence: `examples/search/transforms/chunking/DocumentChunking.py` joins selected source lines with spaces after
  normalizing line endings and removing headings and blank lines.

- Observation: Current sentence content is returned by a Python sentence splitter as strings and then trimmed.
  Evidence: `examples/search/transforms/chunking/SentenceChunking.py` declares an array-of-string UDF and emits
  `Sentence.content` after `trim(...)`; it does not preserve source positions.

- Observation: The compiler already supports typed arrays of structs and typed struct expansion.
  Evidence: `src/structure/plugin/pyspark/dsl/field.py` provides `array(...)` and `struct(...)`, while
  `src/structure/plugin/pyspark/dsl/generators.py` provides `explode_struct(...)` and `posexplode_struct(...)`.

- Observation: Nested stage outputs cannot be rebound as parent step declarations, but this plan does not mix wrapper
  steps with stages. Stage outputs are passed to later stage constructors; local materialization steps remain inside
  their child transforms.
  Evidence: `Chunking`, `Indexing`, and `All` are stage-only compositions, while `SentenceChunking`, `LexIndex`, and
  the presentation/analytics consumers are local-step transforms. The compiler now rejects explicit wrapper-local
  `@step`/`@raw` members in a stage graph instead of silently ignoring them.

- Observation: The Word-to-term redesign is already present in the working tree, but the repository also contains
  unrelated active changes.
  Evidence: `git status --short --untracked-files=all` shows Search lexical changes alongside unrelated documentation,
  planning, security, store, and generated-output changes. Implementation must edit only files relevant to this plan.

## Decision Log

- Decision: Persist three independent boundary relations rather than a nested `DocumentStructure` relation.
  Rationale: Separate relations are simpler for joins, incremental updates, external consumers, and existing
  transformation boundaries. They repeat document identifiers, but avoid nested traversal and oversized document rows.
  Date/Author: 2026-08-07 / User and Codex.

- Decision: Use public schemas named `Section`, `Paragraph`, and `Sentence`, retaining the familiar `Chunking` output
  names `sections`, `paragraphs`, and `sentences`.
  Rationale: The relations are native structural outputs; their span-only fields and grain-specific names make the
  contract clear without a suffix that describes an implementation concern.
  Date/Author: 2026-08-07 / User and Codex.

- Decision: Store `span_start` and `span_end`, not offset-plus-length.
  Rationale: A half-open start/end interval makes containment, overlap, ordering, and range joins direct expressions.
  Both fields are 0-based code-point positions and `span_end` is exclusive.
  Date/Author: 2026-08-07 / User and Codex.

- Decision: Use Unicode code-point coordinates in canonical document text.
  Rationale: Search tokenization and the default sentence UDF operate on Python strings. UTF-8 byte offsets would add
  encoding work and UTF-16 code-unit offsets would be error-prone for non-BMP characters. Backend materializers may
  convert the code-point coordinates to their local substring convention.
  Date/Author: 2026-08-07 / User and Codex.

- Decision: Canonical document text normalizes CRLF and CR line endings to LF before offsets are calculated.
  Rationale: The current chunker already performs this normalization, so the span coordinate system must make that
  behavior explicit and deterministic.
  Date/Author: 2026-08-07 / User and Codex.

- Decision: Remove text fields from structural boundary relations without a compatibility bridge.
  Rationale: Keeping nullable content would preserve accidental persistence of duplicated text and would make it
  unclear whether a row is safe to persist. Text is a transient materialization concern.
  Date/Author: 2026-08-07 / User and Codex.

- Decision: Keep the existing replaceable sentence-chunking fallback, but require every supported sentence chunker to
  emit spans. Content-only custom sentence chunkers are outside the new Search contract.
  Rationale: The fallback remains useful for callers that replace the default sentence algorithm, while the persisted
  boundary contract remains enforceable and storage-safe.
  Date/Author: 2026-08-07 / User and Codex.

- Decision: Pass `documents` to transforms that need text and materialize text through private transient lanes.
  Rationale: This avoids introducing a new public content-bearing relation that callers could mistake for a persistence
  artifact. `Indexing` must have the source document to tokenize span-only sentences; named intermediate rows keep
  transient materialization intent and lineage visible without becoming public outputs.
  Date/Author: 2026-08-07 / User and Codex.

- Decision: Treat `document_id` as the immutable content-snapshot key.
  Rationale: Separate boundary relations can only be valid against the document text from which they were derived. A
  changed document must receive a new identifier or trigger a complete boundary rebuild; no additional fingerprint
  field is added in this first slice to keep the relations simple.
  Date/Author: 2026-08-07 / User and Codex.

## Context and Orientation

The repository compiles typed Python transformation classes into online execution plans and generated PySpark. Search
source schemas live under `examples/search/schemas/`, transformations under `examples/search/transforms/`, and Search
golden/generated registrations under `tests/helpers/example_projects.py` and
`tests/golden/test_examples_generated_output.py`. The same source must work in online mode and in generated PySpark.

`Document` remains the caller-owned source relation and keeps its full `content` string. `Section`, `Paragraph`, and
`Sentence` are derived structural relations. A structural span is a half-open interval
of Unicode code points in the canonical form of `Document.content`: a row with `span_start=10` and `span_end=25`
refers to code points 10 through 24. Empty spans are not emitted.

The current chunking pipeline is composed by `examples/search/transforms/chunking/Chunking.py`. It delegates paragraph
and section discovery to `DocumentChunking.py`, then sentence discovery to `SentenceChunking.py`. The current
paragraph and sentence schemas in `examples/search/schemas/text.py` contain `content`; those fields will be removed or
replaced by the boundary schemas. The current Search lexical index in `examples/search/transforms/indexing/lexical/LexIndex.py`
reads sentence content, so it will receive documents and use a private source-slice materialization lane before
normalization and aggregation.

The affected presentation consumers are sentence search and passage search, which currently read sentence or paragraph
content for result rows and neighboring context. They will receive documents and materialize source slices privately.
Document profiling and document-level similarity continue to use `Document.content` directly.

## Plan of Work

### Milestone 1: Establish span-only schemas and source-coordinate rules

Add `Section`, `Paragraph`, and `Sentence` schemas in the Search text schema module or its
dedicated boundary schema module, following the repository’s existing grain-specific identifier conventions. Section
boundaries include nullable heading span fields because explicit Markdown headings are derived text; implicit sections
materialize the existing synthetic `Document` heading. Paragraph and sentence boundaries contain only identifiers,
ordinals, and `span_start`/`span_end`.

Remove `content` and `heading` from the structural outputs. Materialize source text through private compiler-visible
lanes using the intermediate schemas in `schemas/chunking/intermediate.py`; do not expose those lanes as public
outputs.

Update the Search schema registries, source imports, generated-source registrations, and API documentation so the
public structural contract visibly contains spans and no content columns.

### Milestone 2: Preserve spans through document and sentence chunking

In `DocumentChunking.py`, retain line source positions while expanding canonicalized document lines. Compute paragraph
spans from the first selected body line’s start through the last selected body line’s end. Compute section body spans
from the first paragraph in the section through the last paragraph; compute explicit heading spans from the heading text
inside its source line. Keep section and paragraph ordinals and IDs unchanged unless a span-specific test proves an
existing identifier is inconsistent.

In `SentenceChunking.py`, change the default Python sentence supplier to return typed local spans for each sentence,
not only strings. The supplier must preserve the existing punctuation behavior and return trimmed non-empty sentence
intervals. Join each paragraph boundary to `Document`, slice the canonical paragraph source text privately, translate
local sentence positions by `paragraph.span_start`, and emit `Sentence` rows.

Preserve the replaceable-transform seam, but change its output contract to span-aware sentences. A custom chunker that
only returns strings must fail at schema/compile integration rather than silently producing a content-bearing boundary
relation. Add an explicit documentation note explaining how custom implementations provide spans.

### Milestone 3: Add private materialization and migrate consumers

Create a private utility helper that extracts the canonical source slice using `span_start` and `span_end`. Convert the
0-based, exclusive-end contract to the backend’s substring convention at this boundary. Apply existing
trim/whitespace presentation behavior only in the transient lane value; never write that value back into the boundary
relation.

Change the public compositions as follows:

    Chunking(documents=documents)
      -> sections: Section
      -> paragraphs: Paragraph
      -> sentences: Sentence

    Indexing(documents=documents, sentences=segments.sentences)

    SearchSentences(documents=documents, sentences=segments.sentences, ...)

    SearchPassages(documents=documents, paragraphs=segments.paragraphs, ...)

Update `LexIndex`, `AnalyzeText`, `All`, sentence search, passage search, and any other Search transform found by the
content-field search to use the private utility. Keep `DocumentTerm`, `SectionTerm`, `ParagraphTerm`, and
`SentenceTerm` unchanged except for their already-established aggregate contract. Preserve normalization, punctuation
handling, empty-token behavior, target frequencies, BM25, overlap, similarity, ranking, and existing result content.

### Milestone 4: Update documentation, fixtures, and generated artifacts

Update the Search README, Search design/background/specification documents, decision records, examples, and API
registries to explain that structural relations contain source spans and that text is transiently materialized from
`Document`. Document the canonical newline rule, code-point coordinate unit, half-open interval rule, and immutable
`document_id` requirement.

Update golden renderers, integration fixtures, schema registries, generated source inputs, and generated outputs. Ensure
no `DocumentStructure` relation is added, no structural boundary output contains content, and no old content-based
sentence/paragraph binding remains.

## Validation and Acceptance

The implementation is accepted when a caller can run `Chunking(documents=documents)` and observe section, paragraph,
and sentence rows containing identifiers, ordinals, and spans but no content or heading text. A caller can pass those
sentence boundaries plus the original documents to `Indexing`, and term aggregates match the pre-span implementation.

Sentence and passage search must return the same normalized result text, ranks, and scores as before, while deriving
their content transiently from document spans. Explicit headings must materialize correctly; implicit sections must
still display `Document`. Paragraph and sentence spans must be valid for multilingual text, including non-BMP emoji,
and must remain correct after CRLF-to-LF canonicalization.

Online execution and generated PySpark must produce equivalent boundary rows, materialized text, term aggregates, and
Search results. Tests must cover repeated terms, punctuation-only content, empty targets, adjacent half-open spans,
heading and blank-line boundaries, multilingual code-point indexing, custom span-aware sentence chunking, and failure
of content-only custom chunkers.

The final repository must pass `make gold`, the focused Search tests, `git diff --check`, and `make build` without
overwriting unrelated working-tree changes.

## Idempotence and Recovery

Schema and source edits are additive until the old content-bearing outputs are removed. Regeneration is idempotent and
must be run after source changes so checked-in generated files reflect the current Search source. Do not use destructive
Git commands to discard unrelated work. If generated output is wrong, correct the source or the registration and rerun
`make gold`; do not hand-edit generated files as the source of truth.

If a span calculation fails, retain the prior source file until the new boundary calculation has a focused test. A
document with invalid or empty spans must fail the boundary build with an actionable diagnostic rather than emitting a
row whose materialized text could silently refer to the wrong source characters.

## Artifacts and Notes

The canonical persisted artifacts after implementation are:

    Section(document_id, id, ordinal, span_start, span_end, heading_span_start, heading_span_end)
    Paragraph(document_id, id, section_id, ordinal, span_start, span_end)
    Sentence(document_id, id, section_id, paragraph_id, paragraph_ordinal, ordinal, span_start, span_end)

The original `Document` relation remains the required source for text materialization. No nested `DocumentStructure`
artifact and no public materialized paragraph/sentence persistence artifact are introduced.

## Interfaces and Dependencies

Use the existing `structure` schema, transform, join, string, window, UDF, and typed generator APIs. Use
`posexplode_struct` or `explode_struct` only for internal arrays returned by the span-aware sentence supplier; the
persisted public boundary relations themselves remain ordinary flat relations.

The generated PySpark target must use the same canonical newline and code-point contract as online execution. If Spark’s
substring indexing is 1-based or uses a backend-specific character convention, isolate the conversion in the private
materializer and prove it with multilingual tests rather than exposing backend units in the public schemas.

The implementation must preserve the existing Search aggregate-term redesign and must not reintroduce `Word`,
`WordChunking`, or a public occurrence relation.
