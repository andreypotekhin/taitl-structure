### I09272601 Search Integration Performance

Status: open
Scope: Search integration execution and PySpark query-plan construction
Versions: Structure 0.1.0, Python 3.11/3.12, PySpark 3.5/4.0, Spark Connect 4.0

Reproduction:

Run the focused Search integration test from the repository root, using the Compose backend runner:

    docker compose --env-file infra/compose/.env \
      -f infra/compose/docker-compose.yaml -p structure-integration run --rm \
      -e STRUCTURE_SEARCH_STAGE_OUTPUTS=0 -e STRUCTURE_INTEGRATION_TIMEOUT=600 \
      -e 'INTEGRATION_PYTEST_ARGS=-k test_document_search_reranks_bm25_candidates_for_multiple_queries \
        -vv -s --durations=20' \
      structure-integration-pyspark35 bash /workspace/infra/compose/images/pyspark/run-integration.sh pyspark35

For diagnostics, add `-e STRUCTURE_PROFILE_QUERY_PLANS=1`. The full module is
`tests/integration/pyspark/search/test_search.py`.

Observed output:

Small fixtures spend most of their runtime constructing and analyzing Spark query plans. The original isolated
Spark 3.5 reranking case took 172.55 seconds overall, including 140.63 seconds of combined online/generated
construction. The compiled Search graph contained 92 steps, 157 joins, 52 singleton-policy checks, six `require_all`
assertions, and two `require_unique` assertions. Repeated policy guards and assertion branches copied expensive
upstream query plans. Earlier runs also exhausted the Spark driver heap or failed while serializing a deep Spark
Connect checkpoint request.

Expected behavior:

Small Search fixtures should spend substantially less time constructing the query plan while preserving rankings,
schemas, sentence-splitting UDF behavior, online/generated parity, and strict validation failures for empty,
duplicate, or otherwise invalid policy/candidate inputs. Streaming DataFrames must not receive batch-only checks or
checkpoints.

Proposed fix (implemented; issue remains open):

The following resolution work is implemented and validated, but this issue remains open pending broader repeated
benchmarking and closure review:

- Use a bounded, Spark-side singleton policy check that examines at most two rows and reuses equivalent checks only
  within one transform run. It never collects policy data into Python and retains the existing exactly-one-row
  failure contract.
- Add conditional materialization inside `FuseDocuments` before candidate uniqueness checks, while retaining the
  final checkpoint before feedback branches. The existing `materialize=~streaming` policy remains the only public
  Search control.
- Keep `require_all`, `require_unique`, sentence-splitting UDFs, and generated/online semantics intact. Correct
  Spark Connect error classification so server stack traces mentioning RDDs do not mask real validation errors.
- Continue using the opt-in profiler to separate query-plan explanation time from checkpoint work and to report
  estimated query-plan expansion around joins, assertions, and checkpoints.
