### I09282601 SearchDocuments Repeat-Query Latency

Status: open; investigation and implementation planned, not resolved
Scope: different SearchDocuments requests against unchanged caller-owned corpus and policy snapshots in one session
Versions: Structure 0.1.0, v10 development; ordinary PySpark 3.5/4.0 and batch Spark Connect 4.0

Problem:

Reusing compiled Structure artifacts does not reuse the Spark work performed by each SearchDocuments invocation.
Each batch invocation constructs query plans and executes the three eager fusion checkpoints before returning its
lazy result. A small result collection time therefore does not establish fast subsequent requests. The user needs
new queries against the same corpus to become substantially faster, preferably a fraction of a second, without
changing rankings, validation, freshness, or scope isolation. Repeated retrieval of an identical cached answer is
not the target workload.

Reproduction:

The existing runnable proxy is the reranking integration case, not a same-mode repeat-query latency benchmark.
From the repository root, with the Compose environment prepared, run:

    docker compose --env-file infra/compose/.env -f infra/compose/docker-compose.yaml \
      -p structure-integration run --rm \
      -e STRUCTURE_PROFILE_QUERY_PLANS=timing -e STRUCTURE_PROFILE_COMPILATION=1 \
      -e STRUCTURE_COMPILED_ARTIFACT_REUSE=module -e STRUCTURE_PLAN_BOUNDARIES=auto \
      -e STRUCTURE_SEARCH_STAGE_OUTPUTS=0 -e STRUCTURE_INTEGRATION_TIMEOUT=600 \
      -e 'INTEGRATION_PYTEST_ARGS=-k test_document_search_reranks_bm25_candidates_for_multiple_queries -vv -s' \
      structure-integration-pyspark35 bash /workspace/infra/compose/images/pyspark/run-integration.sh pyspark35

Observed output:

The recorded timing-only Spark 3.5 observation reported:

    online construction: 27.80s
    online checkpoints: 16.502s, 5.495s, 0.222s
    generated construction: 25.60s
    generated checkpoints: 14.734s, 5.044s, 0.219s
    online/generated collection: 0.41s / 0.27s
    result: 1 passed in 110.77s

These are historical single-run measurements from [checkpoint evidence][checkpoint-evidence], not new measurements
or steady-state medians. Checkpoint times are included in construction. The separate [artifact-reuse matrix][matrix]
passed 54/54 runs and removed repeated runtime compilation misses, but did not measure sequential new requests in
one persistent Structure session. A new four-control cached-score sample measures one distinct query after the same
Structure sessions have run: online/generated construction was 42.91/46.08 seconds, while the narrow handwritten
reference took under a second to construct. The separately prepared handwritten request took 0.38 seconds after
0.50 seconds of preparation. See the [repeat-query benchmark record][repeat-benchmark]. This one cohort does not
measure score-cache misses or establish a stable latency distribution; repeated cohorts remain to be collected.
One warm Spark 4.0 parity cohort also passed: a distinct cached-score request took 45.54/45.19 seconds to construct
online/generated and 0.48 seconds to collect, while the narrow handwritten controls constructed in 0.86/0.77 seconds.
This remains a one-request smoke, not a median; see the [repeat-query benchmark record][repeat-benchmark].
The same harness passed on Spark Connect 4.0 with executor imports available: online/generated construction took
26.78/26.70 seconds and collection took 0.46/0.54 seconds. The handwritten controls constructed in 0.35/0.30
seconds. This is also a single warm cohort; it confirms the packaging fix, not a steady-state latency claim.
Three Spark 3.5 score-cache-miss requests per mode were also measured while explicitly dropping temporary plan-boundary
views after each result was collected. Online/generated construction medians remained 104.11/117.67 seconds, with
collection medians of 1.27/1.39 seconds; each request's 15 views were dropped and the registered count returned to
zero. An earlier no-cleanup run accumulated 15 views per request and one generated request reached 223.96 seconds.
These different-session runs are not a causal A/B test, but they show cleanup alone does not make repeated
construction fast. See the [boundary-lifecycle evidence][repeat-benchmark].
In a separate timing-only Spark 3.5 sample, one score-cache-miss request took 22.76/22.65 seconds to construct
online/generated. Eager checkpoints consumed 18.27/18.16 seconds, mostly the first two validation-boundary
checkpoints; collection took 0.38/0.35 seconds. This confirms repeated eager materialization is a major cost for this
batch request, but does not show that removing it is safe. See the [checkpoint breakdown][repeat-benchmark].

Expected behavior:

Construct a supported streaming Search graph once, let new requests enter that running graph, and return one final
ranked answer per accepted request using the same caller-owned snapshots. Prove whether this reduces full request
latency relative to repeated batch calls. Include queueing, completion-window waiting, and result delivery; do not
substitute throughput, checkpoint-free construction, or cached Python rows for latency. Subsecond latency is a goal,
not a currently demonstrated guarantee.

Proposed fix and rationale:

A long-running streaming transformation could amortize Python query-plan construction across requests and avoid
per-request batch fusion checkpoints. It does not automatically eliminate Spark planning, scoring, state, or sink
costs. `availableNow=True` drains available input and stops; it is a bounded test/restart mode, not the intended
interactive serving mechanism. `foreachBatch` calling ordinary batch Search rebuilds the batch graph per callback.

Execute [P09282601 Streaming Search repeat-query execution][execution-plan]: establish a fair repeated-query baseline
and handwritten PySpark controls, prove bounded ranking and completion in a small prototype, extend Structure's
streaming transformation support, then integrate the existing SearchDocuments component. The revised
[P08022605 streaming contract][contract-plan] records the current graph and migration requirements.

Storage, input reading, output writing, source/sink lifecycle, snapshots, checkpoint locations, and recovery remain
caller-owned. Do not introduce a Structure snapshot store, a parallel public Search component, or a cache of final
query answers. Preserve existing batch checkpoint protection until streaming correctness and performance are proven.

the dedicated repeat-query reproduction and proposed-fix PR are still missing. Keep it open while collecting them.

Resolution and closure:

No resolution yet. Require ranking/schema/UDF/validation parity, bounded state and reliable completion, restart
evidence on ordinary Spark 3.5/4.0, and measured improvement for sequential new requests. A functional streaming
implementation alone does not close a latency issue. If completion waiting defeats the latency goal, record the
result and retain the issue rather than reducing lateness tolerance or weakening safety without approval.
