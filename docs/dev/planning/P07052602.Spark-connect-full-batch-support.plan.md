# P07052602 Spark Connect Full Batch Support

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement Spark Connect
batch support from the current repository without prior conversation history.

## Purpose / Big Picture

Structure already has an experimental Spark Connect slice: configuration can select
`target_variant = "spark-connect"`, backend capabilities know that Spark Connect is a PySpark variant, and static parity
checks prevent obvious classic-only internals. That is not enough for a support claim. After this plan is complete,
developers can run completed v1/v2 compiler-visible batch transforms online and generated against a real Spark Connect
session, and unsupported classic-only behavior fails before execution or generation with useful diagnostics.

The user-visible behavior is simple: a project can set

    [tool.structure]
    target_backend = "pyspark"
    target_profile = ">=3.5,<4.1"
    target_variant = "spark-connect"

then run the same completed batch transform through `StructureSession(spark=connect_session)` or generated PySpark
classes. The generated class API, `run(...)` signature, Structure DSL, and schema contracts do not change.

- Observation: The completed batch surface expanded after this Spark Connect plan was created.
  Evidence: `P07052603.Full-pyspark-join-support.plan.md` records implemented `rowset_join(...)`, right/full/cross

- Observation: Spark Connect 3.5 reports conservative collection element nullability for `map_keys(...)`.
  Evidence: the live advanced-analytics generated path reported `ArrayType(StringType(), True)` where the Structure
  schema declared `Array(String(), contains_null=False)`.

- Observation: Spark Connect 4.0 runs with ANSI arithmetic behavior that can surface fixture-only divide-by-zero in
  correlation/covariance metrics.
  Evidence: the advanced-analytics fixture failed when one rollup group had nonzero quantity variance but zero price
  variance; changing fixture list prices preserved asserted totals while avoiding that undefined metric.

## Decision Log

- Decision: Promote only completed compiler-visible batch features in Sprint 09.
  Rationale: Spark Connect can share the PySpark DataFrame and Column target boundary for batch transforms, but
  Structure-owned streaming orchestration, storage writes, and arbitrary hook bodies require separate design and
  evidence.
  Date/Author: 2026-07-05 / Codex

- Decision: Keep Spark Connect as `target_backend = "pyspark"` plus `target_variant = "spark-connect"`.
  Rationale: Connect is a PySpark client/server runtime variant, not a peer alternative backend. Treating it as a
  variant avoids duplicating the DSL, generated class API, and target adapter.
  Date/Author: 2026-07-05 / Codex

- Decision: Require live runtime evidence before claiming support.
  Rationale: Generated-code shape checks catch classic-only strings and API drift, but they do not prove that a real
  Spark Connect session accepts the emitted plans.
  Date/Author: 2026-07-05 / Codex

- Decision: Leave historical completed plans and decision records intact.
  Rationale: Old documents should preserve why earlier work called Connect experimental. Current design,
  specification, public reference, roadmap, and sprint docs now define the active support target.
  Date/Author: 2026-07-05 / Codex

- Decision: Treat Spark collection element/value nullability metadata as compatible during runtime schema assertion
  when the physical element/value types match.
  Rationale: Spark can conservatively report collection nullability and Spark Connect 3.5 rejects nullability-only
  casts. Structure keeps declared schemas strict, but runtime validation must not fail on metadata Spark cannot
  reliably enforce.
  Date/Author: 2026-07-06 / Codex

- Decision: Keep advanced-analytics integration fixtures ANSI-clean across Spark 3.5 and 4.0.
  Rationale: Spark 4.0 correctly rejects divide-by-zero under ANSI mode. The Spark Connect support test should prove
  Structure lowering and execution parity, not depend on undefined statistical input.
  Date/Author: 2026-07-06 / Codex

## Context and Orientation

Structure is a Python library for schema-driven PySpark transforms. Users write transform classes with typed schema
methods. The compiler builds an intermediate representation, then the PySpark target either runs the transform online
through `StructureSession` or emits generated PySpark classes.

Spark Connect lets Python code submit PySpark DataFrame plans to a remote Spark server. In Structure, Spark Connect is
not a new backend id. It is selected with `target_backend = "pyspark"` and `target_variant = "spark-connect"`. The
caller creates the Spark Connect session and passes it as `spark`. Structure must not create the remote server, access
SparkContext, access RDDs, call direct JVM or Py4J objects, use `_jdf`, or rely on private classic PySpark fields.

The important files are:

- `docs/dev/design/SparkConnect.md`: design rationale and support boundary.
- `docs/dev/specifications/SparkConnect.md`: formal implementation requirements.
- `docs/reference/SparkConnect.md`: public user-facing reference.
- `docs/dev/project-management/sprints/done/Sprint09_OptimizationExplainDocsTooling.md`: sprint schedule and acceptance.
- `docs/dev/specifications/BackendCapabilities.md`: backend capability model and variant identity.
- `docs/dev/specifications/CompatibilityPolicy.md`: compatibility support policy.
- `src/structure/app/target/pyspark`: PySpark lowering, rendering, and recipe implementation.
- `src/structure/app/runtime/execution/online`: online PySpark execution.
- `tests/integration`: live runtime integration tests.
- `tests/specifications`: static compiler, capability, generated-code, and diagnostics tests.

Completed v1/v2 batch features include projection, filtering, v1 joins, analytical joins, full rowset joins,
aggregations, advanced grouping, advanced metrics, reusable explicit windows, selected-row helpers, dedupe helpers, and
compiler-visible array/map helpers. Streaming source/sink orchestration and storage writes are not part of this plan.
`grouping_sets(...)`, post-aggregate `having(...)`, same-name join-key shorthand, and unimplemented optimization
directives remain explicit capability boundaries until their owning specifications admit them.

## Plan of Work

Start by adding test fixtures that can run the same completed batch examples against ordinary PySpark and Spark
Connect. Prefer the existing v1/v2 testing model under `res/testing/model` and the current integration-test plugin
rather than creating a second fixture system. Include the advanced analytical fixture and rowset join fixture so
Connect evidence covers the recently implemented `rollup(...)`, `cube(...)`, additional metrics, reusable windows,
expanded HOFs, `rowset_join(...)`, right/full/cross joins, and non-equi/disjunctive predicates. The tests should
exercise online execution first because it proves `StructureSession(spark=connect_session)` works without changing the
public runtime contract.

Next add generated-code execution tests against Spark Connect. Generate or import the existing generated fixtures,
instantiate generated classes with the Connect session, and compare rows and schemas with ordinary PySpark expectations.
The generated code should not branch on Connect unless public PySpark APIs force a difference.

Then add static guardrails. Add a generated-source scan for forbidden classic-only tokens: `sparkContext`, `.rdd`,
`_jdf`, `_jvm`, `py4j`, and private classic fields. Add or extend backend capability requirements for
`backend.spark_context`, `backend.rdd_access`, `backend.jvm_access`, `backend.py4j_access`,
`backend.private_classic_fields`, `runtime.local_spark_context`, and `runtime.driver_only_jvm_gateway`. For
`target_variant = "spark-connect"`, each requirement must fail through `BACKEND-E2402` or a narrower diagnostic with a
link to `docs/reference/SparkConnect.md`.

After guardrails, implement setup verification. If CI can run Spark Connect, add a dedicated integration lane for
PySpark 3.5 and 4.0 Connect. If CI cannot run the full matrix, add a checked-in manual verification script and make the
Sprint 09 release checklist name it as blocking evidence. The script should start or connect to a Spark Connect server,
run a compact v1/v2 batch fixture online and generated, and print the commands and expected pass result.

Then handle hooks and StructureTools. Hooks remain opaque user-owned code, so Structure should validate signatures and
target scope but must not certify arbitrary hook internals. Add diagnostics or strict-report warnings for explicit
classic-only hook declarations and clear runtime wrapping where unsupported classic-only failures can be detected.
For StructureTools schema extraction, accept Connect sessions only for metadata paths that use public DataFrame or
SparkSession APIs. Unsupported live metadata paths should suggest passing an explicit schema object.

Finally, update docs and Sprint 09 evidence after implementation. Public docs should say Spark Connect is supported for
completed batch features only when the evidence is in place. They must keep streaming orchestration, storage writes,
and arbitrary hook internals outside the support claim.

## Validation and Acceptance

Acceptance is behavioral:

- With `target_variant = "spark-connect"`, completed v1/v2 batch fixtures, including full rowset joins and admitted
  advanced analytical operations, run online against a real Spark Connect session and produce the same rows and schemas
  as ordinary PySpark.
- Generated classes for the same fixtures run against a real Spark Connect session and produce the same rows and
  schemas as ordinary PySpark.
- `structure check` and `structure compile` remain Spark-free. Static tests should prove no PySpark import, Java
  startup, SparkSession creation, or remote connection occurs on compiler paths.
- Generated source for Spark Connect-compatible fixtures contains no `sparkContext`, `.rdd`, `_jdf`, `_jvm`, Py4J
  gateway access, or private classic PySpark fields.
- A transform or hook that explicitly asks for classic-only internals fails before Spark Connect execution or generated
  code with a diagnostic that links to `docs/reference/SparkConnect.md`.
- Public docs describe Spark Connect as supported for completed batch features only, and explicitly exclude streaming
  orchestration, storage writes, and arbitrary hook body certification.

## Idempotence and Recovery

The work is additive and test-driven. Re-running tests, generated-source scans, and documentation searches is safe.
Do not delete existing historical plans or completed decision records simply because they describe the older
experimental slice. If implementation reveals that a completed batch feature cannot run on Spark Connect without a
classic-only API, record the finding here, make the capability unsupported for `target_variant = "spark-connect"`, and
keep the public support claim narrower rather than adding a hidden fallback.

## Interfaces and Dependencies

Do not add a new public runtime wrapper for Spark Connect. Use the existing interfaces:

    StructureSession(spark=spark, ctx=ctx, config=config)
    GeneratedTransform(spark=spark, ctx=ctx).run(...)

Backend capability resolution remains static and Spark-free. Runtime integration tests may import PySpark and connect
to a Spark Connect server, but compiler and capability tests may not.
