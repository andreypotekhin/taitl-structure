## Surprises & Discoveries

- Observation: The repository has separate transformation and streaming coverage ledgers, so a catalog change can drift
  unless both are checked together.
  Evidence: `pyspark-transformation-coverage.json` and `pyspark-streaming-api-coverage.json`.
- Observation: `make build` is necessary but does not replace live streaming or generated-source evidence.
  Evidence: `docs/dev/project-management/SprintPlanningGuide.md`.
- Observation: Search integration exposed a second identity boundary after file/schema qualification: generated owner
  classes were still keyed by simple basenames. Distinct nested `SelectGapQueries` transforms therefore produced duplicate
  Python classes and bases in the composed module.
  Resolution: PySpark generated owner classes now qualify only colliding basenames with their source module; the generated
  Search module and no-Spark uniqueness regression verify both identities.

## Plan of Work

Create a matrix mapping each V10 row to its public contract, owner boundary, capability, diagnostic, test, target lane,
generated artifact, and documentation. Run no-Spark checks after every contract change, then run pinned PySpark 3.5/4.0
lanes for every Structure-supported streaming claim and optional Sedona lanes only when dependencies are pinned.

During Sprint 54, fix only release blockers: stale generated files, catalog drift, missing diagnostics, parity failures,
documentation contradictions, reproducibility failures, and performance regressions. Record every deferred item rather
than extending scope.

The collision-safe generated identities workstream is a Sprint 54 release blocker because source modules and schemas
are valid user-defined identities. Its acceptance evidence is maintained in
`docs/dev/planning/P08042601.Collision-safe-generated-identities.plan.md` and must include same-basename transforms,
same-name schemas, duplicate-path merge diagnostics, source-qualified schema documentation, and a passing `make build`.

The SearchDocuments row is release-blocking only when its streaming proving lane resumes. The future evidence matrix must
distinguish implemented lineage declarations from a startable end-to-end job and identify, for each state stage, the
event-time field, watermark delay, completion window, grouping keys, retained bound, output mode, generated-code form,
and restart result. It must separately record rejected global ranking, unbounded aggregate/deduplication, and unsupported
stream/stream joins, with a caller remedy or a linked V10 implementation task.
