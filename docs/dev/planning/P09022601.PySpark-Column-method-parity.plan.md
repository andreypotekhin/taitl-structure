# Add PySpark Column Method Parity to the Symbolic Expression API

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` sections as work advances. It follows `docs/dev/auto/Plans.md` and complements
`docs/dev/planning/P08222601.PySpark-SQL-function-coverage.plan.md`, which owns function-form SQL helper coverage.

## Purpose / Big Picture

Structure users should be able to use the PySpark `Column` methods that Structure supports directly on schema-field
expressions. The immediate user-visible example is `order.name.substr(1, 10)`, which should compile to the same
typed, optimizer-visible behavior as the existing `substr(order.name, start=1, length=10)` helper.

This plan targets strict PySpark 3.5.x/4.0.x `Column` parity. It does not turn every `functions.*` helper into a
method. In particular, `trim` and `lower` remain function helpers because they are PySpark SQL functions rather
than methods on the supported PySpark `Column` surface. The equivalent Structure expression remains:

    substr(lower(trim(order.name)), start=1, length=10)

The final result must work through symbolic compilation, online PySpark execution, generated PySpark rendering, and
online/generated parity tests. It must not introduce live PySpark `Column` objects into Structure's expression model.

## Surprises & Discoveries

- Observation: Structure already has the correct symbolic abstraction for a Column API.
  Evidence: `Expression` is immutable, carries Structure type and nullability, and is lowered later into
  `PySparkExpressionRecipe` values; it never contains a live PySpark Column.

- Observation: Function-form `substr(...)` is already implemented.
  Evidence: `src/structure/plugin/pyspark/dsl/expressions.py` defines `substr`, and the existing renderer/evaluator
  dispatches the `substr` call kind.

- Observation: Nested call rendering and evaluation already recurse through expression arguments.
  Consequence: method-form authoring can reuse the existing `call` expression kind and does not require a new IR node.

- Observation: PySpark's actual Column API includes `substr`, while `trim` and `lower` are function helpers in the
  project's supported baseline.
  Consequence: the exact `order.name.trim().lower().substr(...)` chain is deliberately outside this strict-parity
  plan.

- Observation: Adding public methods increases the set of names unavailable for attribute-based nested struct-field
  access.
  Consequence: colliding nested fields must continue to be accessed with `get_field(...)`, and the reference API must
  document the method-name reservation.

- Observation: The current development environment does not provide a local `pyspark` installation.
  Consequence: Spark-free symbolic and rendering tests can run locally; live PySpark evidence must come from the
  repository's integration environment and must not be reported as passed when unavailable.

- Observation: The existing renderer and online evaluator receive literal arguments as literal `Expression` nodes,
  while ordinary evaluation wraps literals for the backend call.
  Consequence: the substring lowering paths must preserve raw literal bounds for `Column.substr(start, length)` while
  still evaluating symbolic bounds as backend expressions.

## Decision Log

- Decision: Define parity as the intersection of the supported PySpark 3.5.x and 4.0.x public `Column` method
  surfaces, with Structure's existing naming conventions preserved.
  Rationale: the repository's compatibility range is 3.5.x/4.0.x, and using a newer PySpark surface would create an
  accidental API commitment.
  Date/Author: 2026-09-02 / Codex.

- Decision: Do not add `.trim()` or `.lower()` in this strict-parity slice.
  Rationale: these are PySpark function helpers, not baseline PySpark `Column` methods. Keeping them as functions
  avoids presenting a Structure-only convenience as PySpark parity.
  Date/Author: 2026-09-02 / Codex.

- Decision: Add explicit typed methods to `Expression`; do not implement a generic method dispatcher in
  `Expression.__getattr__`.
  Rationale: explicit methods preserve IDE completion, typo detection, readable signatures, and receiver-specific
  type validation. `__getattr__` must remain responsible for nested struct-field access.
  Date/Author: 2026-09-02 / Codex.

- Decision: Make `substr(startPos, length)` accept integer literals and integral symbolic expressions, and propagate
  nullability from all three operands.
  Rationale: this matches PySpark's Column method shape and makes dynamic substring bounds compiler-visible instead of
  restricting the method to the motivating literal-only example.
  Date/Author: 2026-09-02 / Codex.

- Decision: Keep generated code canonical rather than preserving the source spelling of the method call.
  Rationale: the semantic contract is the lowered PySpark expression; existing generated code uses function-form
  rendering for SQL helpers, and stable canonical output is preferable to source-syntax preservation.
  Date/Author: 2026-09-02 / Codex.

- Decision: Preserve the established function-form substring metadata for literal calls while adding explicit bound
  arguments to the shared call representation.
  Rationale: this admits symbolic bounds without changing existing function-form expression data or generated output
  contracts.
  Date/Author: 2026-09-02 / Codex.

## Context and Orientation

Schema field access is implemented by `RowScope` and returns `Expression` instances. `Expression` provides operators
and selected Column-like methods while `src/structure/plugin/pyspark/dsl/expressions.py` provides function-form
helpers. Symbolic expressions are mapped to `PySparkExpressionRecipe` values by the compiler, evaluated by
`EvaluatePySparkExpression`, and rendered as generated source by `RenderPySparkExpression`.

The existing SQL-function coverage plan owns function inventory and function-form APIs. This plan owns the method
surface on symbolic `Expression` values and its alignment with the supported PySpark `Column` surface. A method is
admitted only when its receiver type, argument types, result type, nullability, target capability, online behavior,
and generated behavior can all be stated and tested.

## Plan of Work

### 1. Build the parity register

Audit the PySpark 3.5.x/4.0.x `Column` method intersection against `Expression.py`, the current expression API
reference, and the target capability ledgers. For each method, record the Structure spelling, receiver and argument
types, result type, nullability, rendering form, execution form, and disposition. Do not include SQL functions such
as `trim` or `lower` in the Column-method register.

The audit must also identify method names that collide with nested struct fields and verify that `get_field(...)`
remains the documented escape hatch. Existing methods must not be renamed or silently changed as part of the audit.

### 2. Add explicit method authoring

Implement `Expression.substr(startPos, length)` with a public signature that accepts integer literals or integral
`Expression` values. Reuse the existing typed literal conversion and substring validation instead of creating a second
validation path. Extend the shared substring call representation so the receiver, start position, and length are
expression arguments; preserve the existing function-form `substr(...)` call as a backward-compatible API.

The resulting expression must be a normal `Expression(kind="call")` with function name `substr`, String result type,
and nullability equal to the disjunction of receiver, start, and length nullability. It must remain immutable and
compiler-visible.

### 3. Preserve both lowering paths

Update the PySpark renderer and online evaluator to consume the shared three-argument representation. Generated code
should use the repository's canonical function-form `F.substr(...)`; online execution should use the corresponding
public PySpark operation available in both supported profiles. The compiler mapper and capability requirement should
continue to classify the operation as an ordinary expression helper unless the audit proves a separate capability is
needed.

Do not add a new expression kind, live Column wrapper, Python string-method fallback, or dynamic method lookup.

### 4. Reconcile public evidence

Update `docs/api/Expressions.api.md`, `docs/QuickRef.md` where examples belong, and `docs/dev/Parity.md` with the
method-form contract and the function-versus-Column distinction. Add a short migration example showing the strict
parity form:

    order.name.substr(1, 10)

and the function composition needed for trim/lower:

    substr(lower(trim(order.name)), start=1, length=10)

Keep generated-output examples stable unless the new behavior changes an existing golden contract.

### 5. Extend tests by behavior

Add Spark-free symbolic tests covering method capture, nested method composition, dynamic integral bounds, result
type, nullability, and invalid receiver/argument types. Add renderer tests proving the canonical generated form and
online evaluator tests using the existing fake or semantic-contract infrastructure.

Add at least one online/generated parity scenario in the PySpark integration lane using nullable and non-nullable
string inputs. Add a regression test proving that function-form `substr(...)` remains compatible.

## Validation and Acceptance

The change is accepted when all of the following are true:

- A compiled step can author `order.name.substr(1, 10)` without a diagnostic.
- Dynamic integral expressions are accepted as `startPos` and `length`, and their nullability is represented in the
  resulting expression contract.
- Non-string receivers and non-integral bounds fail during symbolic authoring with actionable type errors.
- Generated PySpark contains a valid canonical substring call and imports without requiring Structure at runtime for
  the expression itself.
- Online and generated execution produce equal values, output schema, and null behavior on the same fixture.
- Function-form `substr(...)` continues to compile and behave identically.
- `.trim()` and `.lower()` are not presented as supported Column methods; documentation directs users to the existing
  function helpers.
- The focused suite and `make build` pass, with any environment-dependent integration limitation explicitly recorded.

## Idempotence and Recovery

The plan is additive. Re-running the audit, focused tests, and build is safe. Do not regenerate or overwrite checked-in
golden files during ordinary tests; update a golden only when the generated contract intentionally changes and the
diff has been reviewed. Preserve unrelated worktree changes and use file-scoped edits for this feature.

## Artifacts and Notes

The primary artifact is the method-parity register in `docs/dev/Parity.md`, accompanied by the public expression API

    order.name.substr(1, 10)
    # canonical generated form: F.substr(F.col("order.name"), 1, 10)

The exact generated qualification may vary with the active scope alias, but the operation must remain a standard
PySpark substring expression with the same receiver and bounds.

## Interfaces and Dependencies

The first public interface added by this plan is:

    Expression.substr(startPos: int | Expression, length: int | Expression) -> Expression

The method depends only on the existing Structure type classes, literal conversion, expression compiler mapper,
PySpark renderer, and online evaluator. It must not add a dependency on PySpark to compiler-only imports. Future
Column methods must follow the same explicit typed-method pattern and must be admitted only after their target-profile
capability and parity evidence are defined.
