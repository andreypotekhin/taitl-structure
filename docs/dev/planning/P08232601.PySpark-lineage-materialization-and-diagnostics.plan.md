It follows `docs/dev/auto/Plans.md`; the plan must remain self-contained for a contributor who has only this file and the current working tree.

The recorded memory evidence and implementation contract are in the developer [Memory specification](../specifications/Memory.spec.md); end-user symptoms and remedies are in the [memory gotcha](../../troubleshooting/memory/spark_driver_heap_oom.gotcha.md).

## Purpose / Big Picture

PySpark DataFrames are lazy descriptions of work. A Python variable, alias, cache, or persist call does not necessarily make the logical description smaller. When code repeatedly reuses a DataFrame that already contains a self-join, projection, or union, Spark can build an exponentially larger logical plan and exhaust the driver JVM heap while analyzing a tiny input. This plan turns the available remedy into a Structure-level, compiler-visible API and gives users an actionable warning before execution.

After implementation, a user can write `persist()`, `cache()`, `unpersist()`, `checkpoint()`, or `local_checkpoint()` in a compiler-visible transform body. The operation will be preserved in symbolic execution, generated PySpark, and online execution, subject to the configured PySpark capability profile. Structure will fuse an eligible same-source projection union into one typed row-expansion projection, and the compiler will warn by default when the remaining symbolic relation graph has the structural shape of repeated lazy-lineage reuse. The warning is advisory and points to the reproducible gotcha and the relevant helper.

The first implementation does not change Search reciprocal semantics, change Spark heap settings, or add automatic checkpoints. It supplies a semantics-preserving branch fusion, explicit user controls, and a conservative diagnostic so the user can choose a semantic materialization boundary when algebraic simplification is insufficient.

## Surprises & Discoveries

- Observation: The isolated reproducer fails during driver-side analysis even though its input has only two rows.
  Evidence: With a 1 GiB driver heap, six rounds complete and seven rounds reach `java.lang.OutOfMemoryError: Java heap space` during `count()`; the recorded unresolved logical-plan character counts are 1,211, 6,987, 35,617, 172,213, 806,405, 3,698,529, and 16,680,913 for rounds one through seven.
- Observation: The growth is finite exponential lineage duplication, not an infinite JVM allocator.
  Evidence: Each round reuses the current plan on both sides of a self-join, then reverses and unions the result. Spark's analyzer recursively walks the duplicated graph through operations such as `DeduplicateRelations`, `QueryPlan.references`, and attribute-set construction. More rounds or more reused branches make the required heap unbounded relative to the requested graph.
- Observation: A checkpoint boundary prevents the growth in the reproducer.
  Evidence: The checkpoint-every-round control keeps plan text between 46 and 48 characters through eight rounds and completes with `rows=0` under the same 1 GiB setting.
- Observation: `cache()` and `persist()` do not by themselves cut the logical lineage.
  Consequence: They are useful for reuse and recomputation cost, but they are not substitutes for `checkpoint()` or `localCheckpoint()` when the problem is driver-side logical-plan growth.
- Observation: Replacing the canonical/reverse union with one `explode(array(struct(...), struct(...)))` projection removes one independent multiplier without changing row multiplicity.
  Evidence: At 1 GiB, the fused shape settles near 2.2x growth, is about 74 times smaller at round seven, completes twelve rounds with an 11,525,294-character plan, and fails at round thirteen with a 24,772,674-character plan.
- Observation: A temporary view shortens only the visible unresolved plan in ordinary PySpark.
  Evidence: Applying a view after every round displays 59 characters but takes progressively longer and fails inside `createOrReplaceTempView()` at round eight. The nested Catalyst lineage remains behind the relation name.
- Observation: The previously tried reciprocal Search directional-aggregate rewrite was a diagnostic band-aid and is not to be reinstated by this plan.
  Consequence: Search restructuring remains end-user guidance and a separate semantic/design decision; this work provides explicit boundaries and a warning.
- Observation: Spark 4.0 still needs the documented writable working directory for live analysis.
  Evidence: Running the standalone proof from the read-only `/workspace` failed in Spark's `ArtifactManager`; rerunning from `/tmp` completed successfully with `rows=0`.
- Observation: A warning generated before lowering cannot truthfully report whether projection-union fusion was applied.
  Consequence: Runtime compilation now lowers and optimizes before building `PYSPARK-W2701`; documentation-only compilation retains the structural warning without claiming an optimization result.

## Decision Log

- Decision: Implement compiler-visible relation operations rather than only runtime wrappers.
  Rationale: A runtime-only helper cannot be captured, capability-checked, ordered with other symbolic operations, or kept in parity between generated and online execution. The existing `OperationPlan` and recipe/rendering pipeline already provides the appropriate vertical path.
  Date/Author: 2026-08-23 / Codex.
- Decision: Add `persist(storage_level=None)`, `cache()`, `unpersist(blocking=False)`, `checkpoint(*, eager=True)`, and `local_checkpoint(*, eager=True)` as explicit relation operations.
  Rationale: These are the smallest user-facing controls needed to express reuse, release, and logical-lineage boundaries. `cache()` is the readable default-storage-level alias for `persist()`; `@step(cache=...)` remains supported and unchanged.
  Date/Author: 2026-08-23 / Codex.
- Decision: Add only the lineage-growth warning, with code `PYSPARK-W2701`, enabled by default.
  Rationale: The warning addresses the reproduced driver-heap failure without pretending to prove runtime heap safety. It is independent of whether a user chose to cache first.
  Date/Author: 2026-08-23 / Codex.
- Decision: Do not implement `PYSPARK-W2702`, `warn_on_uncached_checkpoint`, or any cache-before-checkpoint state tracking.
  Rationale: The proposed hygiene warning was identified as relevant to RDD usage, not to this DataFrame logical-lineage problem. A DataFrame checkpoint is not invalid merely because `cache()` was not called first; adding that warning would encode the wrong contract and distract from the actual failure mode.
  Date/Author: 2026-08-23 / User correction recorded by Codex.
- Decision: Use separate boolean configuration for the warning, not a shared warning policy or heap threshold in the first version.
  Rationale: The only new diagnostic in scope is `warn_on_lineage_growth`; a threshold would imply a quantitative guarantee that the compiler cannot make without Spark's analyzed plan and version-specific optimizer behavior.
  Date/Author: 2026-08-23 / Codex.
- Decision: Do not expose `local_checkpoint(storage_level=...)` in the first version.
  Rationale: A uniform, portable local-checkpoint storage-level contract needs additional version and Connect evidence. The default Spark caching subsystem behavior is sufficient to establish the lineage boundary; the API can be extended later without weakening the initial contract.
  Date/Author: 2026-08-23 / Codex.
- Decision: Add a default-on compiler optimization for deterministic projection-only branches that are unioned back into their sole source relation.
  Rationale: The rewrite preserves bag semantics while emitting the source lineage once. The measured reproducer reduces from about 4.5x to 2.2x growth and moves the 1 GiB failure boundary from round seven to round thirteen. This is a material reduction, while the remaining self-join recurrence stays visible to the diagnostic.
  Date/Author: 2026-08-23 / Codex.
- Decision: Do not reuse the Spark Connect temporary-view boundary as an ordinary-PySpark heap remedy and do not insert automatic local checkpoints.
  Rationale: The temporary view failed to sever Catalyst lineage in the measured ordinary-PySpark run. Automatic local checkpoints alter evaluation, storage, recovery, and failure semantics; users must select that boundary explicitly.
  Date/Author: 2026-08-23 / Codex.
- Decision: End-user communication must distinguish reducing a lineage multiplier from bounding lineage growth.
  Rationale: Projection-union fusion changes the measured recurrence from about 4.5x to 2.2x but remains exponential. For the unchanged recursively reused self-join, only `checkpoint()` or `local_checkpoint()` creates the tested logical-lineage boundary. An algorithmic rewrite that stops feeding expanded lineage back into the next round can also remove the recurrence and should remain the preferred remedy when semantics permit it.
  Date/Author: 2026-08-23 / Codex.
- Decision: Build the final lineage warning after ordinary runtime lowering and optimization, while retaining a structural-only warning for documentation compilation.
  Rationale: The optimizer trace is the authoritative evidence that fusion was applied. Reporting fusion in a warning before lowering would overstate an optimization that might later be rejected by capability or eligibility checks.
  Date/Author: 2026-08-24 / Codex.

## Context and Orientation

The user-facing transformation DSL is captured without starting Spark. `src/structure/plugin/pyspark/dsl/operations/OperationPlan.py` is the structured intermediate representation for relation operations. `src/structure/plugin/pyspark/dsl/operations/CacheOperations.py` already models the `@step(cache=...)` optimization and storage-level serialization. `src/structure/plugin/pyspark/symbolic_execution/commands/CapturePySparkStep.py` and the surrounding symbolic-execution commands collect operation plans from transform bodies.

`src/structure/plugin/pyspark/compiler/logic/maps/MapPySparkStep.py` maps captured operations to execution recipes. `src/structure/plugin/pyspark/render/logic/steps/RenderPySparkStep.py` emits generated PySpark. `src/structure/plugin/pyspark/execution/logic/running/RunOnlinePySparkTransform.py` applies operations to a live DataFrame. Keep these three paths semantically identical and preserve operation order: a materialization boundary must occur at the source position where the user wrote it.

`src/structure/plugin/pyspark/capabilities/model/PySparkCapabilities.py` declares target-version and target-variant support. “Ordinary PySpark” means the driver owns a normal PySpark session. “Spark Connect” means the client submits DataFrame operations to a remote Spark server. A capability declaration is required because the same Python surface is not guaranteed on every supported version or variant.

Diagnostics are registered in `src/structure/lib/cross/errors/registry.py` and documented in `docs/Diagnostics.md`. Compiler options are represented by `src/structure/core/configuration/model/StructureConfig.py`, with transform-level options admitted by `src/structure/core/dsl/model/transforms/transform_api.py` and consumed by `src/structure/plugin/pyspark/api/CompilerAPI.py`. Follow the existing `warn_on_udfs` pattern for defaults and transform overrides.

The reproduced problem and its end-user guidance are in `docs/troubleshooting/memory/spark_driver_heap_oom.gotcha.md`; the developer evidence and decisions are in `docs/dev/specifications/Memory.spec.md`. The standalone example is deliberately Search-independent and uses only PySpark, two rows, a repeated self-join, a reverse projection, and `unionByName`. Its `--directions explode` control isolates projection-union fusion, `--checkpoint-every` proves a real lineage boundary, and `--view-every` proves that a short unresolved view reference is not such a boundary. It is the behavioral fixture for this plan.

## Plan of Work

### Milestone 1: Define the operation contract and capture it

Extend the relation operation model with distinct kinds for `persist`, `unpersist`, `checkpoint`, and `local_checkpoint`. Reuse the existing storage-level normalization for `persist`; represent `cache()` as the default-storage-level form rather than as an unrelated operation. Store `blocking` for `unpersist` and `eager` for the two checkpoint operations. Each operation must retain its source metadata so diagnostics and generated provenance can identify the user call.

Expose the helpers through the compiler-visible PySpark DSL module and its public exports. The intended signatures are:

    persist(storage_level=None)
    cache()
    unpersist(blocking=False)
    checkpoint(*, eager=True)
    local_checkpoint(*, eager=True)

The helpers return the current symbolic relation, allowing fluent use while still appending an operation in source order. Reject invalid values at authoring/compilation time where the existing DSL can do so; do not import or inspect private Spark objects merely to validate a symbolic call. Preserve the existing decorator-style/internal cache implementation under a non-conflicting name or split the public helper from it so `cache` has one unambiguous meaning in each API layer.

Add operation-family metadata. `persist`, `cache`, and `unpersist` are row-preserving optimization/lifecycle operations. `checkpoint` and `local_checkpoint` are row-preserving lineage-boundary operations and are batch-only unless existing streaming contracts prove otherwise. Do not silently allow them over streaming input; use the existing capability/streaming diagnostic path when the target does not support the shape.

### Milestone 2: Lower the operations through every execution path

Add recipe types and mapping branches in `MapPySparkStep.py`. Add generated rendering in `RenderPySparkStep.py` using public DataFrame methods and preserving the exact call arguments. Add online execution in `RunOnlinePySparkTransform.py` using `persist()` or `persist(StorageLevel(...))`, `unpersist(blocking=...)`, `checkpoint(eager=...)`, and `localCheckpoint(eager=...)` with the correct PySpark spelling. Keep the generated and online implementations aligned; do not use `_jdf` or another private Spark API.

Update the public API reference, DSL specification, and any operation coverage/catalog artifacts. Explain that `checkpoint()` writes to the configured Spark checkpoint directory and truncates the logical plan, while `local_checkpoint()` uses executor-local cached storage and is not a reliable recovery boundary. Explain separately that `persist()`/`cache()` retain reusable data but do not truncate logical lineage, and `unpersist()` releases persistence without truncating lineage. Existing `@step(cache=True)` and explicit `@step(cache=StorageLevel...)` must continue rendering and executing as before.

### Milestone 3: Declare target capabilities

Add capability entries for ordinary PySpark 3.5 and 4.0 based on the pinned integration images and for Spark Connect only where the target runtime exposes the public method. The initial expected matrix is all five helpers on ordinary 3.5/4.0, with Connect support determined by evidence rather than assumed. In particular, checkpoint and local-checkpoint support has changed across Spark Connect releases; do not claim Connect support merely because ordinary PySpark imports the method.

Use the existing capability diagnostic for an unsupported profile and include the operation name, target variant, and supported alternative. Do not add a compatibility promise for a version outside the repository's active `>=3.5,<4.1` baseline. Do not add a local-checkpoint storage-level argument in this milestone.

### Milestone 4: Fuse eligible projection unions

Add a whole-plan optimizer after `LowerPySparkPlan` has mapped source steps to `PySparkStepRecipe` values and before rendering or online execution. Name it `OptimizePySparkProjectionUnions` and keep it under `src/structure/plugin/pyspark/compiler/commands/`. It must build a consumer map from step input sources, join/relation-set sources, and final outputs, then recognize this exact graph: frame `B`; a projection-only step `R` that reads `B` and produces `P(B)`; and a merge step `M` that reads `B`, performs one `union_all(R)` or strict same-schema `union_by_name(R)`, and otherwise has only an identity projection. `R` must have no consumer other than `M`.

Apply the rewrite only when `R` is deterministic and row-preserving and neither `R` nor `M` has filters, joins, aggregates, windows, generators, hooks, assertions, validation side effects, cache/persist/checkpoint operations, or missing-column/default union behavior. Require identical Structure schemas and preserve field order for positional union. These rules make the transformation bag-semantics preserving: every `B` row emits the forward struct and the exact `P(B)` struct once, including duplicates and nulls.

Lower the fused step through the existing typed array/struct expression and `explode_struct` operation machinery, equivalent to `explode(array(struct(forward fields), struct(projected fields)))`. Do not add a second runtime implementation when the existing generator recipe can represent the result. Remove the now-dead projection step from runtime execution, but retain an optimization trace record mapping both source steps to the fused generated operation. Update explain/traceability output so a user can see `projection-union fusion: R + M` and the eliminated lineage fan-out.

The optimizer is an algebraic reduction, not a materialization boundary. Its acceptance evidence must state that measured growth falls from about 4.5x to 2.2x and that the remaining self-join is still exponential. Do not suppress `PYSPARK-W2701` merely because fusion applied; reduce the diagnostic's estimated fan-out and recommend checkpointing when the remaining graph still crosses its structural risk budget.

### Milestone 5: Add the lineage-growth warning

Register `PYSPARK-W2701` as a warning whose problem text explains that a relation is reused through a self-join or multi-branch operation after its lineage has already expanded. Its remedy must name `checkpoint()`/`local_checkpoint()` as logical-lineage boundaries, mention that `cache()`/`persist()` alone do not solve this specific driver-analysis failure, and link to `docs/troubleshooting/memory/spark_driver_heap_oom.gotcha.md` through the repository's diagnostics documentation convention.

Implement a Spark-free structural analysis over the captured relation graph. Track relation identity and parent edges, detect a non-leaf relation consumed more than once, detect a self-join or equivalent two-sided reuse, and raise the risk when a later union/projection/branch reuses a relation that already contains such a multiplication. Reset or reduce the risk at explicit checkpoint/local-checkpoint boundaries. Treat persistence as a reuse hint, not as a reset, because the gotcha evidence shows that caching does not cut the logical plan.

The analysis is deliberately conservative. It must not serialize a Spark logical plan, call `_jdf`, call `logical().toString()`, or claim an exact heap threshold. It should report the relation/operation path and deduplicate repeated findings for the same boundary. A simple self-join over a stable leaf should remain warning-free when no repeated expanded lineage exists. The standalone reproducer shape should produce one actionable warning before execution.

Add `warn_on_lineage_growth=True` to the configuration model/defaults, the transform option allow-list, and the compiler option resolution path. A project-level false value disables the warning; a transform-level false value overrides the project/default value. No second warning option is added. In particular, there is no `warn_on_uncached_checkpoint`, no cache-before-checkpoint check, and no RDD hygiene diagnostic in this plan.

### Milestone 6: Document restructuring and complete evidence

Extend `docs/Gotchas.md` and `docs/dev/Troubleshooting.md` only with links to the detailed memory gotcha, keeping the detailed reproducer and measurements in its dedicated file. Update the API and diagnostics documentation with examples for explicit helper use, projection-union fusion, and warning remediation. Include two restructuring patterns from the gotcha: keep each iteration connected to a small stable base relation, or checkpoint before reusing an expanded relation. For Search, fuse canonical and reverse rows through one typed array-of-struct expansion, separate grain-specific lanes, and use a directional aggregate only when its stronger uniqueness and reciprocal-semantics requirements are proven. The compiler optimization must preserve the current reciprocal self-join semantics; it does not introduce the previously rolled-back aggregate rewrite.

Make the end-user distinction impossible to miss in `docs/Diagnostics.md`, `docs/api/Relations.api.md`, `docs/api/Transforms.api.md`, and the dedicated memory gotcha. Use the same three-part vocabulary everywhere:

- **Diminish:** projection-union fusion emits the repeated projection once and lowers the measured multiplier, but growth remains exponential when an expanded relation is fed back into a self-join.
- **Bound:** `checkpoint()` or `local_checkpoint()` truncates the logical lineage at the selected boundary. For an otherwise unchanged recursive shape, this is the tested way to make each later round start from a bounded plan. Explain the reliable-storage versus executor-local recovery tradeoff.
- **Remove:** an algorithmic rewrite can remove the recurrence by making each round depend on a stable base relation or by replacing recursive reuse with an equivalent bounded reduction. State that this requires a semantics proof and is not always available.

Do not describe `cache()`, `persist()`, Python assignment, aliases, or temporary views as lineage boundaries. Explain that they may improve physical reuse or shorten a displayed unresolved plan while leaving the nested Catalyst lineage intact. Increasing the driver heap postpones a threshold and is not a structural fix.

Render `PYSPARK-W2701` in two parts when fusion applies. First report the optimization, for example, `Structure fused reverse projection union at document_pairs; estimated repeated-lineage multiplier reduced from about 4.5x to 2.2x.` Then report the residual risk, for example, `The self-join still reuses expanded lineage exponentially. Add checkpoint() or local_checkpoint() after document_candidates, or rewrite the recurrence to use a stable base relation.` The exact numeric estimate is evidence and guidance, not a heap-safety guarantee; omit numbers when the static graph cannot support them.

Extend `structure explain` and generated traceability with a concise boundary state for each risky path: optimization applied, residual repeated-lineage risk, and nearest actual checkpoint/local-checkpoint boundary. This lets a user verify whether the compiler merely diminished the plan or truly bounded it without inspecting Spark private plans. The explain output must never label a cache, persist call, alias, Python variable, or temporary view as a lineage cut.

Add Spark-free unit/specification tests for operation capture, argument validation, operation ordering, configuration defaults/overrides, warning enable/disable, warning deduplication, stable-leaf false positives, and diagnostic documentation links. Add generated-source tests and online integration tests for each supported capability. Add a focused Docker test using the standalone example or an equivalent transform: without a boundary, the diagnostic is present; with a checkpoint boundary between rounds, no lineage-growth warning is emitted for the downstream reuse and the job completes in the configured test budget.

## Validation and Acceptance

The operation feature is accepted when a compiler-visible transform can call each helper, the captured operation sequence preserves source order, generated PySpark contains the corresponding public DataFrame call, and online execution produces the same row values and side effects. `persist()` must preserve default and explicit storage levels; `cache()` must be equivalent to default `persist()`; `unpersist(blocking=True)` must preserve its blocking argument; and both checkpoint helpers must preserve their eager argument.

The capability feature is accepted when supported ordinary profiles execute and unsupported target/variant combinations fail with the existing structured capability diagnostic. The test suite must not claim Spark Connect support for an operation without live evidence from the relevant Connect image.

The optimizer is accepted when an eligible same-source projection union lowers to one typed array-of-struct generator in both generated and online plans, produces exactly the same rows including duplicates and nulls, and removes the dead projection branch from runtime execution while retaining source traceability. Near misses involving a filter, nondeterministic expression, extra consumer, hook, validation side effect, non-identity merge projection, missing-column union, or materialization operation must remain unfused. The standalone measured shape must retain the documented reduction from about 4.5x to 2.2x; no test may claim that fusion alone bounds recursive self-join lineage.

The warning feature is accepted when the standalone repeated self-join/reverse/union shape produces exactly one default-on `PYSPARK-W2701` with a useful relation path and gotcha link, a simple stable self-join does not produce a warning, an explicit checkpoint boundary suppresses the downstream repeated-lineage finding, and project/transform configuration disables the warning as documented. When fusion applies, tests must assert that the warning distinguishes the reduced multiplier from the residual exponential risk and recommends both a real checkpoint boundary and an algorithmic stable-base rewrite. Tests must also assert that cache, persist, alias, Python assignment, and temporary-view boundaries do not produce a `lineage bounded` explanation. No test or implementation may expect `PYSPARK-W2702` or inspect whether `cache()` preceded `checkpoint()`.

The overall work is accepted when API and troubleshooting documentation are linked, generated and online behavior agree, the focused tests pass, all available Docker evidence is recorded, and `make build` exits successfully. A larger driver heap may be used for diagnosis, but passing only after increasing `-Xmx` is not acceptance: the feature must demonstrate a bounded plan or an explicit user-selected boundary.

## Idempotence and Recovery

The implementation is additive. Before changing shared exports, capability ledgers, or diagnostic registries, inspect the current entry and preserve unrelated edits. If a target does not expose an operation, leave the operation in the DSL contract but route the compiled use through the existing capability error; do not silently omit it from generated output.

If the warning analysis produces too many false positives, narrow its structural trigger and add a regression fixture rather than disabling it globally. If it misses the standalone shape, add the smallest relation-graph fixture that reproduces the missed edge. Do not fix the warning by inspecting Spark private internals or by increasing heap defaults.

If online or generated execution diverges, keep the operation model and remove only the failing target claim until the renderer, runtime call, and capability evidence agree. If a Docker run exhausts resources, stop that run, preserve its logs, and retry with the documented bounded round count; do not delete unrelated containers, volumes, or user changes.
