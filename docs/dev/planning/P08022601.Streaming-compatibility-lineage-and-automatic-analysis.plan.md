# Make Streaming Compatibility Follow Concrete Data Lineage

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date. Maintain this document according to
`docs/dev/auto/Plans.md`.

## Purpose / Big Picture

Structure compiles typed transforms into a backend plan. `@transform(streaming=True)` is an explicit all-step
streaming-capability contract, while actual runtime streaming follows concrete data lineage. Streaming input
declarations and composed streaming outputs trigger compatibility analysis without implicitly changing transform
options. A batch-only operation with no streaming lineage remains batch-only, even in a transform that is analyzed.

After this change, the compiler records each concrete step input, follows streaming status through intermediate lanes,
automatically runs the PySpark streaming-compatibility analysis for compiled plans, and reports the result through the
normal compiler diagnostics. A user can therefore compile `BuildPersonalizedRecommendations` and see the real
streaming risks in its history aggregation and stream-stream join, while a batch-only step in a streaming-marked
transform remains compatible.

The change also distinguishes unsafe streaming operations from operations that PySpark permits but whose state may grow
without a watermark. Business-key and global streaming aggregates remain supported according to PySpark output-mode
rules, but emit `STREAM-W0802` as a warning describing their unbounded state.

## Surprises & Discoveries

- Observation: The original lowered step recipe retained the driving source but discarded the complete set of concrete
  step input bindings.
  Evidence: `PySparkStepRecipe` had `source` but no representation of the `StepPlan.inputs`; the classifier therefore
  could not distinguish a batch driving input from a streaming side input.

- Observation: A transform-level `streaming=True` marker had caused batch-only operations in otherwise batch-lineage
  steps to receive streaming findings.
  Evidence: explain-report tests for window projections, relation assertions, ordering, hierarchy, unions, and sampling
  expected `STREAM-E0801` even though their concrete inputs were not declared `streaming=True`. Those tests now report
  compatible status, while cases with concrete streaming inputs retain the findings.

- Observation: PySpark permits non-event-time grouped streaming aggregates in update or complete output mode, but the
  watermark does not evict business-key state.
  Evidence: Store personalization compilation now reports `STREAM-W0802` for the history aggregations rather than
  incorrectly classifying them as batch-only. The same behavior is covered by the streaming aggregate tests.

- Observation: Automatic analysis should not introduce a second lifecycle for mixed outputs.
  Evidence: the compiler now adds diagnostics to the existing `PluginCompilation` and `TransformPlan` objects; it does
  not add streaming sinks, queries, triggers, or output handling, and it does not change `allow_stream_to_batch`.

- Observation: A stream-stream join with both concrete inputs streaming remains a hard compatibility finding when it
  lacks the required event-time bounds, even if the enclosing transform is otherwise valid.
  Evidence: `StreamingOneSidedStreamJoin` receives `STREAM-E0801`, while the batch-input lookup regression remains
  compatible.

## Decision Log

- Decision: Determine whether a step is streaming from its concrete driving source and all concrete input bindings, then
  propagate that status to result lanes and later steps.
  Rationale: the operation’s state and lifecycle depend on the data it receives, not merely on the class-level intent.
  This allows batch-only methods to coexist with streaming methods in one transform when their lineages are separate.
  Date/Author: 2026-08-02 / user and Codex.

- Decision: Treat `@transform(streaming=True)` as an all-step capability contract, not as an inferred transform option.
  Streaming input declarations and composed streaming outputs independently trigger analysis, and output streaming
  status remains lineage-derived.
  Rationale: users should not have to remember two meanings of one class marker, while batch and streaming lineages can
  still coexist in one plan.
  Date/Author: 2026-08-02 / user and Codex.

- Decision: Use `stream_to_batch_policy = "default"` for safe automatic boundary relaxation and `"strict"` for
  explicit boundary discipline. Default accepts only compiler-visible compatible downstream code; unknown code remains
  `STREAM-E0802`. Strict requires downstream `streaming=True` or global/local `allow_stream_to_batch=True`.
  Rationale: the default is ergonomic for the closed DSL, while strict gives projects a conservative regime without
  weakening effective-mode checks.
  Date/Author: 2026-08-02 / user and Codex.

- Decision: `allow_stream_to_batch=True` never suppresses a known `STREAM-E0801`, and explicit `streaming=False` always
  rejects a streaming boundary.
  Rationale: an allowance can express deployment intent at a boundary but cannot make an incompatible operation safe.
  Date/Author: 2026-08-02 / user and Codex.

- Decision: Allow mixed batch and streaming outputs without adding a mixed-output opt-in.
  Rationale: output consumers already own their respective query or batch lifecycles. The compiler should prevent
  unauthorized stream-to-batch flow, but should not reject a plan merely because it has different output modes.
  Date/Author: 2026-08-02 / user and Codex.

- Decision: Treat non-event-time business-key and global streaming aggregates as compatible with warning `STREAM-W0802`.
  Rationale: this follows PySpark behavior for update or complete output modes. A watermark alone does not bound state
  that is grouped only by a business key, so the user needs an explicit advisory rather than a false compatibility error.
  Date/Author: 2026-08-02 / user and Codex.

- Decision: Run streaming analysis automatically at the frontend plugin-compilation boundary and preserve findings as
  normal diagnostics rather than adding a new exception path there.
  Rationale: the streaming classifier already produces a structured report and the compiler already carries diagnostic
  values through `PluginCompilation` and `TransformPlan`. Reusing that path makes inferred streaming plans observable
  without changing existing callers that explicitly consume compileability reports.
  Date/Author: 2026-08-02 / Codex.

- Decision: Do not change `BuildPersonalizedRecommendations` to add watermarks or event-time bounds in this slice.
  Rationale: the requested change is to analyze and report the existing workflow correctly. Changing the workflow’s
  business behavior would conflate compiler enforcement with a separate personalization design decision.
  Date/Author: 2026-08-02 / user and Codex.

## Outcomes & Retrospective

The implementation now separates the explicit all-step contract from actual streaming lineage. A streaming-marked
transform forces analysis of every concrete step, while batch-only steps are only rejected when the contract requires
streaming capability or their concrete lineage is streaming. Streaming inputs and composed outputs trigger analysis
without mutating transform options.

Composition now carries effective streaming mode through safe default-policy boundaries. Pending boundaries let the
backend distinguish compatible code, known incompatible operations (`STREAM-E0801`), and opaque code (`STREAM-E0802`).
Strict policy preserves an explicit opt-in requirement; global and local `allow_stream_to_batch=True` satisfy it, but do
not override operation compatibility. Structure still performs no batch materialization and owns no streaming query,
sink, checkpoint, or lifecycle.

The compiler automatically makes the analysis visible on compiled plugin results. The Store personalization workflow
therefore exposes warnings for unbounded history aggregates and errors for its unbounded stream-stream/stateful
composition through normal diagnostics. The workflow itself remains unchanged, as requested.

The main lesson is that compatibility must be computed after lowering has preserved enough lineage information. A
transform-level option is useful for declaring intent, but it is not sufficient evidence that every concrete method or
lane is streaming. Future changes to streaming operations should add tests for both sides of this boundary: a genuinely
streaming input must be checked, and the same operation with only batch inputs must not be rejected as streaming.

## Context and Orientation

The relevant compiler flow is:

1. `src/structure/core/compiler/frontend/commands/CompilePluginTransform.py` analyzes and authors a transform, invokes
   the selected backend compiler, and returns a `PluginCompilation` containing the lowered backend plan.
2. `src/structure/plugin/pyspark/compiler/logic/maps/MapPySparkStep.py` lowers authored step plans into
   `PySparkStepRecipe` objects.
3. `src/structure/plugin/pyspark/compiler/model/PySparkStepRecipe.py` is the backend-neutral recipe used by the
   PySpark streaming classifier and renderer. A recipe’s `source` is the current driving relation; `input_sources`
   lists every relation bound to the concrete step method.
4. `src/structure/plugin/pyspark/compiler/commands/ClassifyStreamingCompatibility.py` inspects lowered operations,
   joins, hooks, watermarks, aggregates, and propagated lanes without starting Spark.
5. `src/structure/lib/cross/errors/registry.py` defines the diagnostic metadata, and `docs/Diagnostics.md` documents
   the public diagnostic codes.

In this plan, “streaming lineage” means the path by which a streaming input reaches a concrete step or intermediate
 lane. A “batch-only operation” is an operation whose current compiler contract cannot safely run on an unbounded
 stream, such as an unbounded sort or an unbounded stateful lookup. A “watermark” is an event-time progress declaration
 that lets Spark discard state older than a configured delay. A “business-key aggregate” groups by ordinary fields such
 as customer or product identifiers rather than by event time; PySpark permits it in selected output modes, but the
 grouping state is not automatically evicted by an event-time watermark.

The Store workflow is under `examples/store/transforms/personalization/`. Its history aggregation and interaction
join are intentionally left unchanged by this plan. The compiler should report their current streaming risks rather
than silently accepting them or rewriting their business behavior.

## Plan of Work

First, preserve concrete input bindings in the lowered recipe. Add an immutable `input_sources` tuple to
`PySparkStepRecipe` and populate it from each authored step’s input bindings in `MapPySparkStep`. This is an internal
recipe change and does not alter the public transform API.

Next, update `ClassifyStreamingCompatibility`. For every step, compute whether the driving source or any concrete input
source is streaming. Use this result when checking projections, operations, joins, hooks, stateful composition, and
result lanes. Keep propagation through step names, lanes, and final outputs so a streaming intermediate remains
streaming for later steps. Add an early return to join classification when both the current and joined relations are
batch-only.

Then, refine aggregate classification. Event-time and session-window aggregates continue to require their existing
watermark rules. Non-event-time aggregates return a compatible `STREAM-W0802` warning explaining that Spark permits
the operation but its business-key or global state is unbounded. Compatible warnings must not suppress stateful
composition tracking for later operations.

Finally, invoke the backend’s optional `analysis.classify_streaming` API from
`CompilePluginTransform._compile` after backend lowering. Pass a `StreamingAnalysisRequest` containing the lowered
payload, whether analysis is required, and whether the explicit all-step contract is active. Convert findings to normal
diagnostics and attach them to both the `PluginCompilation` and its `TransformPlan` analysis object. Do not start Spark,
create streaming queries, materialize batches, or change output lifecycle ownership.

Update tests and documentation to make the concrete-lineage rule visible. Streaming fixtures whose purpose is to test
streaming restrictions must declare their relevant inputs with `streaming=True`; fixtures with only batch inputs must
assert compatible status even when the transform is marked streaming.

## Interfaces and Dependencies

The lowered recipe adds this internal field:

    input_sources: tuple[str, ...] = ()

The frontend uses the existing backend analysis interface when available:

    plugin.api.analysis.classify_streaming(
        StreamingAnalysisRequest(
            payload=lowered_plan,
            required=required_streaming,
            streaming_contract=explicit_transform_streaming,
        )
    ) -> StreamingReport

Composition plans also carry `stream_to_batch_policy` through resolved configuration and retain
`streaming_boundaries: tuple[StreamingBoundaryPlan, ...]` for undeclared boundaries deferred to backend analysis.
Those records describe compiler decisions only; Structure does not materialize batches or own streaming query
lifecycles.

The analysis remains backend-optional. A plugin without `analysis.classify_streaming` is skipped safely. The PySpark
implementation must remain independent of a running Spark session and must not import PySpark merely to classify the
plan. Diagnostic conversion uses each `StreamingFinding.to_diagnostic()` result and the existing cross-library
diagnostic registry.
