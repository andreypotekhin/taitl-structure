## Purpose / Big Picture

V9 deliberately retained a small set of design gates instead of making unsafe support claims. V11 will finish the
design work needed to make those gates actionable: users and maintainers will be able to see the exact target profile,
state or side-effect contract, evidence requirement, diagnostic boundary, and next action for every retained item.

This plan is design-first. It does not silently implement arbitrary state, row-level streaming side effects, or
future-profile Variant mutation. A successful plan run produces self-contained designs, normative specifications,
machine-checkable status/evidence rules, target-lane prototypes where available, and a V11 closeout report. A missing
PySpark 4.2 or 4.3 runtime remains unavailable evidence, not a support claim.

XML helpers and cost-based join reordering are explicitly excluded. Their current low-priority/design-gated statuses,
non-exported API boundaries, and caller remedies must remain unchanged throughout V11.

## Context and Orientation

Structure is a typed Python-to-PySpark compiler. A transform author declares input and output Schemas and writes
compiler-visible expressions and relation operations. The compiler captures those operations in an intermediate
representation (IR), which is a structured plan consumed by both online execution and generated PySpark rendering.
Streaming compatibility classifies operations that may run on a caller-supplied streaming DataFrame; Structure does not
start or recover a streaming query.

The retained V9 items are:

- Variant mutation helpers (`variant_array_append`, `variant_insert`, `variant_set`, and `variant_delete`) are
  reserved for released PySpark 4.3+ profiles.
- `is_valid_variant(...)` is target-gated to PySpark 4.2 and lacks positive live evidence in the current repository.
- Chained stateful operators beyond the exact admitted two-stage event-time window shape need a state-composition and
  state-budget contract.
- Row-level `DataStreamWriter.foreach` needs sink identity, idempotence, retry, security, and recovery semantics.
- Arbitrary state APIs such as `applyInPandasWithState` and `transformWithState` need typed state and restart rules.

The authoritative public and machine-readable surfaces are:

- `docs/APICatalog.md` and `docs/reference/API.ref.md` for public status and caller remedies;
- `docs/api/Streaming.api.md` and `docs/api/Expressions.api.md` for user-facing API contracts;
- `src/structure/plugin/pyspark/resources/pyspark-transformation-coverage.json` and
  `src/structure/plugin/pyspark/resources/pyspark-streaming-api-coverage.json` for checked statuses and evidence;
- `docs/dev/gated/Streaming.gates.md` and `docs/dev/specifications/V9StreamingDesignGatedFeatures.spec.md` for
  the current V9 state and side-effect boundaries;
- `docs/dev/project-management/V11.md` and `docs/dev/planning/P08042601.V11-pyspark-4.1-adoption.plan.md` for the
  V11 target, sprint dates, and evidence policy.

## Scope and Non-Goals

This plan covers design, specification, diagnostics, evidence, and catalog reconciliation for the retained V9 items.
It may add small no-Spark prototypes only when they answer a contract question. It does not admit a feature merely to
make a test pass.

XML remains low-priority design-gated and outside this plan. Do not add `from_xml`, `to_xml`, XML source support, XML
ledger rows beyond the existing classification, or XML runtime dependencies.

Join reordering remains design-gated and outside this plan. Do not add `join_order(...)`, optimizer-ordering directives,
cost-based plan selection, traceability changes, or a reordering prototype. Preserve source-authored join order and the
existing caller remedy.

This plan also does not create a Structure-owned streaming source, sink, query lifecycle, checkpoint manager, retry
executor, arbitrary-state runtime, or optional Spark 4.3 dependency. Those remain caller-owned or target-gated unless a
future approved plan changes the boundary.

## Plan of Work

### Milestone 1: Inventory and invariant lock

During Sprint 55, create a single retained-gates matrix in the V11 design and specification. For each item record its
public spelling, current status, owner boundary, target profile, generated-code boundary, diagnostics, evidence command,
and caller remedy. Add explicit negative assertions that XML and `join_order` remain unexported and that their catalog
rows retain their existing statuses.

Review the V9 closeout, V10 streaming plans, current ledgers, and V11 target policy together. Resolve vocabulary before
writing designs: `design-gated` means a contract exists but support is not claimed; `caller-owned-guided` means an
executable caller recipe exists but Structure does not own the API; `streaming-ineligible` means the shape must cross a
batch boundary; and target-gated evidence names the exact PySpark profile it needs.

Acceptance is a checked matrix with no generic `planned` or `deferred` status for an active retained item and with XML
and join reordering explicitly listed as excluded.

### Milestone 2: Variant profile and mutation contract

During Sprint 56, write the Variant mutation design and specification. Define literal path grammar, supported mutation
targets, value conversion rules, null and missing-path behavior, `create_if_missing` behavior, malformed-path
diagnostics, result nullability, array indexing, nested object behavior, and the generated PySpark function spelling.
The contract must distinguish safe and strict forms and must not imply support for dynamic path Columns unless a later
design admits them.

Define the capability matrix separately for PySpark 4.2 and released PySpark 4.3+ profiles. The current 4.2 profile must
continue rejecting mutation helpers before lowering. A 4.3+ design may remain a prototype or design-gated until a
released target is available; no unreleased runtime may be installed merely for this plan.

In the same milestone, document `is_valid_variant(...)` as a PySpark 4.2 target-gated row. Add a live evidence recipe
that records PySpark, Spark, Python, target profile, variant, command, and pass/skip result. If the lane is unavailable,
retain capability and negative-gate tests and record the missing runtime as unavailable evidence.

Acceptance is a profile-specific design with deterministic negative tests and no support claim that depends on a skipped
4.2 or unreleased 4.3+ lane.

### Milestone 3: Stateful composition and arbitrary state

During Sprint 57 and Sprint 58, define the state model needed to decide whether any second stateful operation can follow
an admitted first operation. A state stage is one operation that retains information across streaming micro-batches.
The model must record operation family, input mode, event-time source, watermark, grouping or partition keys, retention
bound, output mode, state budget, allowed next stages, diagnostics, and restart identity.

Keep the exact two-stage event-time window contract supported. For all other chained combinations, specify the rejection
diagnostic and the first unsupported operation. At minimum cover aggregate-to-dedupe, dedupe-to-aggregate,
stream-stream-join-to-aggregate, session-to-any-stateful, and arbitrary-state-to-any-stateful combinations.

Define the future arbitrary-state model for `applyInPandasWithState`, `transformWithState`, and related APIs. It must
declare input, key, state, and output Schemas; timeout clock and policy; initialization, update, removal, and error
behavior; target profile; Python worker and generated-code boundary; checkpoint identity; serialization/versioning;
and restart acceptance. The design must state which guarantees Structure verifies and which remain caller-owned.

Acceptance is an implementation-ready design and normative specification, even if the ledger remains `design-gated`.
No arbitrary state or second-stateful API may become supported solely because the design is complete.

### Milestone 4: Side effects and row-level foreach

During Sprint 58, define the caller-owned side-effect contract for row-level `foreach` and any future Structure-owned
side-effect proposal. Specify sink identity, idempotence key, retry policy, callback failure behavior, checkpoint and
query identity, security boundary, snapshot identity, and recovery behavior. Explain why `foreachBatch` remains the
caller-owned reference recipe and why the existing `ForeachBatchSafety` declaration is validation guidance rather than
an idempotence guarantee.

Add a safe adoption fixture only if it can run against an isolated test sink and checkpoint. The generated Structure
module must remain free of `foreach`, `foreachBatch`, `writeStream`, `start`, checkpoint, trigger, and sink calls. If
the live retry/restart lane is unavailable, retain the design-gated status and record the exact dependency.

Acceptance is an executable caller handoff or a precise design-gated classification with negative source-boundary tests;
there is no Structure-owned side-effect runtime in this plan.

### Milestone 5: Target evidence and V11 integration matrix

During Sprint 59, run every available target lane relevant to the designs. Preserve PySpark 3.5 and 4.0 regression lanes,
add PySpark 4.1 ordinary and Connect classification where the API is relevant, and use PySpark 4.2/4.3 lanes only when
the project has pinned, reproducible services or packages. Optional providers remain late-bound and must not become
bundled dependencies.

For each lane, record exact versions, target profile, variant, command, result, skipped tests, unavailable dependency,
and whether the result is positive support evidence, rejection evidence, or design evidence. Generated and online paths
must consume the same contract for any admitted prototype.

Acceptance is a complete evidence matrix with no skipped lane represented as a pass and no target-specific claim without
positive evidence.

### Milestone 6: Catalog reconciliation and V11 closeout

During Sprint 60, reconcile the V11 design/specification, API Catalog, API reference, API pages, ledgers, diagnostics,
examples, generated-source scans, and V11 project-management documents. Every retained item must have one status,
owner, evidence path, caller remedy, and follow-up owner. XML and join reordering must still be listed as deferred with
no new API export or implementation claim.

Record the final decision for each item in this plan and in the V11 release evidence report. If a target or live sink
lane remains unavailable, retain the gate and carry the exact blocker into the next plan rather than weakening the
status.

## Validation and Acceptance

The plan is accepted when a novice maintainer can open the V11 design/specification pair and answer, for every retained
V9 item, what the user may write, what Structure owns, what the caller owns, which target profile is required, how the
compiler rejects unsafe use, which evidence has run, and what remains blocked.

The acceptance behavior is:

- Variant mutation calls remain rejected before lowering on the current PySpark 4.2 profile and have a documented
  future-profile contract.
- `is_valid_variant(...)` has a positive 4.2 result only if a pinned live lane passes; otherwise the report says the
  lane is unavailable and preserves capability/rejection evidence.
- The exact two-stage event-time window remains supported, while unapproved stateful chains fail with a diagnostic that
  names the state stages and caller remedy.
- Row-level `foreach` and arbitrary state remain outside Structure-owned generated transforms and have explicit
  caller-owned or design-gated remedies.
- XML and join reordering retain their current deferred/design-gated status, are not exported, and have no V11 support
  claim.
- All catalog/reference/ledger links agree and `make build` passes.

## Idempotence and Recovery

This plan is additive and safe to rerun. Design and specification edits can be repeated without changing runtime
behavior. Never install an unpinned Spark or provider package to manufacture evidence. Use isolated temporary
checkpoints and sinks for live tests, remove only those isolated paths after a run, and record failures rather than
deleting broad workspace data.

If a target lane is unavailable, leave the last honest status unchanged and add the dependency and command to the
evidence report. If a prototype fails, preserve the smallest failing fixture and classify the API instead of weakening
the contract. If a design decision changes, update the Decision Log, Progress, catalog, ledger, and companion
specification together.
