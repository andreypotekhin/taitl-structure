# Reduce Search work before eager checkpoints


This ExecPlan follows `docs/dev/auto/Plans.md`. Keep Progress, Surprises & Discoveries, Decision Log, and
Outcomes & Retrospective current as implementation and measurements proceed.

## Purpose / Big Picture


Make `SearchDocuments` and `test_search.py` faster by simplifying the work that Spark must plan and execute before
its first eager checkpoints. A checkpoint executes the preceding operations and gives subsequent operations a
shorter starting point. Its elapsed time includes that preceding work, not just writing checkpoint files.

This is a separate resolution step for
[I09272601 Search Integration Performance](../issues/I09272601.Search-integration-performance.issue.md), alongside
[P09272601 compiled-artifact reuse](P09272601.Search-compiled-artifact-reuse.plan.md). That work reuses Structure's
compiled instructions; this work reduces the Spark operations those instructions build and execute. Hold artifact
reuse settings constant when measuring this plan. Do not modify or repeat the other plan's implementation.

Success means lower measured end-to-end Search time with the same rankings, schemas, validation failures, and
sentence-splitting UDF behavior. First add timing without explicit plan explanation, then test two query plan
simplifications independently. Investigate an earlier checkpoint only if measurements still justify it.

## Surprises & Discoveries


The historical isolated Spark 3.5 run measured 56.79 seconds of combined online/generated construction. Explicit
explanation and subsequent checkpoint calls accounted for 43.629 seconds. The checkpoint profiler itself calls
`frame.explain(mode="simple")`; this is opt-in diagnostic work, not an unconditional production Search operation.
Removing that call from a benchmark can move planning work into the following checkpoint, so its measured duration
must not be advertised as a production saving.

The recovered single-run breakdown, summed across online and generated execution, was:

    Ranked lexical candidates: explain 4.524s; checkpoint after explain 27.822s; combined 32.346s.
    Selected vector candidates: explain 2.051s; checkpoint after explain 8.674s; combined 10.725s.
    Final fused candidates: explain 0.116s; checkpoint after explain 0.442s; combined 0.558s.

These are historical observations, not medians or proof that storage is the bottleneck. The first lexical
checkpoint dominates this sample; the final checkpoint is cheap and protects the later reranking work.
See [the benchmark report](../issues/I09272601/SearchIntegrationPerformance.bench.md).

The first timing-only candidate run lost the Spark JVM during the first checkpoint, while an unprofiled control and a
retry on a healthy Spark 3.5 service passed. The retry measured 27.80s online and 25.60s generated construction with
checkpoint timings nested within those phases. This is evidence that the timing wrapper can report failures without
changing the original checkpoint, not a three-run performance result.

The current DSL requires `union_all` to operate on an input relation, so the four availability lanes need a small
merged lane before the final query-selection step. That adds one compiler-visible step but removes four outer joins
from the selection itself. Retrieval cannot currently share the stored/streamed enrichment chain without either
changing their exposed stage semantics or adding a compiler-level stage alias; the plan defers that candidate rather
than silently changing those contracts.

Inputs declared `streaming=True` can receive batch DataFrames. Those declarations alone cannot establish whether
a proposed rewrite is valid for streaming execution. In particular, moving a union before joins can introduce a
mixed batch/stream union, and changing outer joins into a semi join can alter streaming support and state handling.

## Decision Log


Decision (2026-09-27): Separate timing-only measurements from explicit explanations. Keep the old explanation
profiler available for diagnosis, but use timing-only runs for primary performance comparisons.

Decision (2026-09-27): Simplify gap selection before retrieval, measuring each independently. Both changes target
duplicated upstream work without weakening safety checks or assuming that faster compilation eliminates Spark work.

Decision (2026-09-27): Treat both rewrites as compatibility-gated prototypes before production promotion. Batch
relational equivalence is insufficient proof of streaming equivalence. If promotion requires a new compiler
specialization mechanism or a public execution-mode API, record that as a follow-up rather than silently expanding
this plan into a compiler redesign. A rejected prototype is a documented result, not an implemented speedup.

Decision (2026-09-27): Preserve `SearchDocuments` as one public component and retain
`FuseDocuments(materialize=~streaming)`. Keep its existing eager checkpoints throughout initial comparisons;
do not replace them with lazy checkpoints, caching, local checkpoints, or no-op boundaries.

Decision (2026-09-27): An additional upstream checkpoint is a measured experiment, not a default change. If accepted,
the component producing the reused data owns it through a materialization policy. Search orchestration must not
manage intermediate checkpoint artifacts. No new production profiler or process-global DataFrame cache is needed.

Decision (2026-09-27): Promote the gap-selection rewrite for the current batch Search path after the unprofiled
control and timing-only retry passed the focused parity test. Keep the first timing-mode JVM failure in evidence and
do not describe the single retry as a speedup.

Decision (2026-09-27): Defer shared retrieval enrichment. Preserving the existing stored and streamed stage views
requires either duplicate enrichment, which defeats the saving, or a new compiler/stage-alias capability outside this
plan. Record that capability as follow-up work instead of changing stage semantics.

## Context and Orientation


`tests/integration/pyspark/support/plan_profile.py` contains `profile_checkpoints`, `profile_guards`, and
`guard_expansions`. The last function estimates repeated input references in Structure's plan; it does not count
Spark optimizer nodes or prove repeated execution. `tests/integration/pyspark/conftest.py` enables this profiler
through `STRUCTURE_PROFILE_QUERY_PLANS=timing|explain`; `1` remains an explanation-mode alias.
`tests/app/test_integration_plan_profile.py` tests it without live Spark.

`examples/search/transforms/searching/search_docs/SearchDocuments.py` composes filtering, vectorization, scoring,
retrieval, fusion, and reranking. Its `streaming` parameter defaults to false. Fusion receives
`materialize=~streaming`, where `~` negates a Structure boolean parameter expression.

`examples/search/transforms/online/scoring/lexical/SelectGapQueries.py` identifies queries with missing or stale
scores. Four lanes produce `ScoreQueryAvailability` rows containing `query_id`: document, overlap, vector, and
paragraph-vector gaps. The original final `select_gap_queries` left-joined all four lanes to queries; the implemented
batch path now unions those lanes and uses one existence join. Each lane already removes duplicate query IDs. There
is a different class with the same name under `online/filtering/`; it is not the target of this rewrite.

`examples/search/transforms/searching/search_docs/retrieve.py` contains `RetrieveDocuments`. Its stored and
streamed document steps both call `_candidate`, repeating the same five joins against scores, queries, requests,
targets, and bands. It then combines the results with `union_all`. The vector retrieval branch deliberately uses
only stored documents and must remain separate. Step names and intermediate lanes can be visible when stage
outputs are enabled, so a rewrite must consider those outputs as well as the final rows.

`examples/search/transforms/searching/search_docs/fuse.py` contains `FuseDocuments`. It checkpoints ranked lexical
and selected vector candidates before uniqueness assertions, then checkpoints the selected fused candidates before
reranking. `tests/integration/pyspark/support/test_fusion_materialization.py` covers materialization parity and
duplicate rejection. `tests/integration/pyspark/search/test_search.py` supplies focused reranking, text-fixture,
and whole-module integration coverage.

`docs/api/Joins.api.md` documents `where(exists(on=...))`: a semi join retains a left-hand row when at least one
right-hand row matches, without adding right-hand columns or multiplying rows for multiple right-hand matches.
`union_all` combines rows without removing duplicates. These are the existing DSL operations for the prototypes;
do not introduce a new public relational operator.

## Plan of Work


### Milestone 1: Timing without explicit explanation


Extend the integration-only `STRUCTURE_PROFILE_QUERY_PLANS` switch to accept `off`, `timing`, and `explain`.
Unset and `0` mean off; retain `1` as an alias for explain so existing commands and the artifact-reuse plan keep
working. Reject other nonempty values with a message listing accepted values. Add an `explain: bool = True`
keyword to `profile_checkpoints`, preserving existing direct-call behavior. The fixture selects false in timing
mode and true in explain mode. Both active modes retain existing guard profiling.

Timing mode must call the original checkpoint once with the original `eager` value, return its result unchanged,
and propagate failures unchanged. It must never call explain, collect, count, inspect schema, or fetch the Spark
query plan to construct its log. Report elapsed time and success/failure even when checkpointing raises. Explain
mode reports explanation and subsequent checkpoint time separately; neither is labeled pure executor time.
Off mode must not patch methods or initialize Spark solely for profiling.

Include a per-test checkpoint sequence number and execution-mode context in evidence. Map sequence numbers to
compiled checkpoint steps for each measured invocation; do not assume the historical order applies to all tests.
Keep this attribution in test support, without adding runtime actions to obtain labels. Preserve method restoration
at pytest teardown and avoid retaining frames in collected records. Test aliases, invalid values, no-explain timing,
successful/failed calls, returned frame identity, eager forwarding, and restoration in the existing unit test file.

Establish a new baseline with artifact reuse fixed to `module`, plan boundaries fixed to `auto`, stage outputs off,
and the same driver memory, inputs, images, and Spark settings used for subsequent candidates. Record preparation,
construction, checkpoint calls, collection, cleanup, total time, and failures separately. Checkpoint timings are
nested within construction: do not add them again when computing totals. Run an unprofiled control to estimate
instrumentation overhead and a separate explain run for diagnosis.

### Milestone 2: Union gap IDs before matching queries


Prototype replacing only the final four-left-join selection in the lexical `SelectGapQueries` with a union of the
four `ScoreQueryAvailability` lanes followed by one semi join to `SearchQuery` on `query.id == gap.query_id`.
Keep the four gap-detection steps and their existing deduplication unchanged initially. Their freshness, scope,
model, dimension, policy, and optional-input logic is outside this optimization. Repeated IDs across the union must
not multiply queries; duplicate rows already present in the query input must retain their existing multiplicity.

Add a test-local reference for the former final selection and compare rows and schemas with the candidate on live
Spark in both execution modes. Cover no gaps, each individual gap kind, several kinds for the same query, repeated
IDs across lanes, unrelated IDs, and null keys wherever schemas admit them. Include fresh/stale scores, disabled
gap policy, and omitted paragraph-vector scores through the composed transform. Add a compiled-plan assertion that
the optimized selection has one existence join rather than four outer joins; avoid whole-graph exact join counts.

Before promotion, run existing streaming-contract compilation tests and exercise supported streaming combinations
with bounded file-source fixtures. Preserve watermarks, supported output behavior, and existing diagnostics for
unsupported combinations. If the rewrite changes streaming support, retain the existing production path and record
the tested batch prototype plus the precise missing specialization capability. Do not ship an unconditional semi
join merely because all benchmark fixtures are batch. Run the focused Search comparison before starting retrieval.

### Milestone 3: Share batch retrieval enrichment


Prototype combining stored and streamed document inputs with `union_all` before applying `_candidate` once.
This replaces two copies of the five-join enrichment chain with one for batch inputs. Keep the projection,
`retrieval_score`, null-safe experiment comparison, timestamp equality, time bounds, band behavior, and target
matching unchanged. Do not alter vector retrieval or deduplicate documents. A document in both sources must still
produce the duplicates that downstream candidate validation is expected to reject.

Compare the prototype with a test-local reference of the original two-branch retrieval. Cover empty sources,
stored-only, streamed-only, both sources, overlapping IDs, duplicate scores/targets, missing bands, multiple queries,
different experiments, and mismatched request times. Require equal schemas and row multisets, not incidental row
order. Compare fused rankings and validation errors in the composed Search tests as well.

The production-promotion gate includes stage-output and streaming compatibility. Verify the stored/streamed stage
views remain equivalent when requested; do not leave eagerly built duplicate enrichment paths just to preserve
their names in ordinary execution, since that defeats the intended saving. Test actual mixed batch/stream inputs,
not only input declaration flags. If the existing DSL/compiler cannot preserve these contracts while sharing batch
work, retain the original production implementation and document the smallest follow-up required. Do not add
`SearchDocumentsBatch`, silently rename exposed stages, or introduce a broad compiler optimizer in this milestone.

### Milestone 4: Decide whether earlier materialization is warranted


After measuring the two simplifications separately and together where promotable, inspect the remaining repeated
work feeding the lexical checkpoint. Test one candidate boundary at a time: the filtered target set produced by
`examples/search/transforms/online/filtering/OnlineFiltering.py`, or the selected gap queries produced by the lexical
`SelectGapQueries`. Select based on measured repeated consumption, not the largest-looking printed plan alone.

Prototype an eager batch checkpoint inside the producing component using its existing DSL checkpoint operation.
Use a constructor `materialize` policy defaulting to false for independent callers, with any composed opt-in derived
from `~streaming`. Forward that policy through the owning composition only as needed. Do not pass a streaming fact
into `FuseDocuments`, and do not add checkpoint management to `SearchDocuments` itself. Confirm that an actual
streaming frame never receives the proposed eager checkpoint, including an incorrectly configured caller.

Promote an upstream boundary only if it reduces median complete Search runtime, including its own checkpoint and
cleanup, without increasing failures or regressing another measured backend beyond observed run-to-run variation.
Keep the existing fusion checkpoints during this experiment. Otherwise remove the experimental boundary and retain
the negative result in evidence. Do not accumulate checkpoints simply because each individually shortens a plan.

## Validation and Acceptance


Timing mode makes no explain call, adds no Spark action beyond the original checkpoint, and preserves successful
returns and failures. Explain mode remains explicitly opt-in; `1` retains its former meaning. Profiler teardown
restores patched methods. Checkpoint labels in evidence distinguish the three fusion locations and execution modes.

The promoted gap rewrite produces identical row multisets and schemas in the focused online and generated batch
execution. Retrieval remains on the original path. Search rankings, sentence splitting, freshness/model/scope logic,
optional inputs, and strict singleton and candidate validation remain intact. Duplicates in either candidate lane still
fail with the existing `REL-E0702` contract.
Test materialization both on and off, including empty and nonempty lexical/vector lanes, without relaxing assertions.

Supported streaming cases retain their watermarks and behavior, and unsupported cases retain meaningful diagnostics.
No actual streaming DataFrame receives an eager checkpoint or compiler temp-view boundary. Stage-output-enabled
execution remains usable and correct. A rewrite failing these checks stays a prototype and is documented as deferred.

The accepted combined implementation must improve median complete Search time on the controlled matrix without
heap exhaustion or semantic regressions; report construction and checkpoint contributions separately. If structural
simplification does not improve runtime, report that outcome and the measured remaining bottleneck rather than
claiming a join-count reduction is sufficient. The full build and whitespace checks must pass before completion.

## Interfaces and Dependencies


Use the existing PySpark DSL `union_all`, `where(exists(...))`, and `checkpoint`, and the current integration helpers.
No new dependency, parallel public Search component, global result cache, or generalized optimizer is introduced.
The profiler interface becomes `profile_checkpoints(monkeypatch, frame_type, *, explain: bool = True) -> None`.
Its environment switch remains integration-only and is parsed before requesting Spark solely for profiling.

Any promoted earlier checkpoint belongs to its producing component with `materialize=parameter(False)` and a batch
runtime safety check. The existing `SearchDocuments.streaming` and `FuseDocuments.materialize` meanings do not change.
Before expanding public configuration or compiler specialization to support a deferred rewrite, record a separate
follow-up with the tested constraint and proposed interface for review.
