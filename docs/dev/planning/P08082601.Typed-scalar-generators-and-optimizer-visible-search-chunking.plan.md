# Add typed scalar-array generators and remove the Search line-chunking UDF

This ExecPlan is a living document. Maintain the `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections as work proceeds. ## Purpose / Big Picture

Search document chunking currently calls `DocumentChunking.canonical_document_lines`, a Python UDF that normalizes line endings, splits lines, identifies headings, and calculates line spans. The UDF is correct but opaque to Spark's optimizer and requires a large array-of-struct workaround because Structure currently exposes only typed generators for `array<struct>` values.

After this work, transform authors can expand primitive arrays and primitive maps through typed, compiler-visible generator APIs. Search will use the array API to split canonical document text, calculate Unicode line spans with native expressions and windows, and derive heading metadata without a Python UDF. Generated PySpark, online execution, traceability, streaming compatibility, and diagnostics will all describe the same typed row-expanding operations.

The existing `explode_struct` and `posexplode_struct` contracts remain unchanged. The new scalar-array operations are separate because their generated value is a scalar rather than a declared struct.

## Decision Log

- Decision: Add sibling typed scalar-array generators instead of widening `posexplode_struct` to accept scalar arrays.
  Rationale: The struct generator's schema validation is based on matching an array element struct. A separate scalar contract keeps input types, generated value naming, nullability, and explain output unambiguous.
  Date/Author: 2026-08-08 / Codex.
- Decision: Initially support primitive scalar array elements only: strings, booleans, numeric values, dates, timestamps, and binary values. Do not add scalar generators for nested arrays, maps, structs, or variants in this plan.
  Rationale: Primitive arrays cover Search line splitting and provide a small, testable API increment. Nested values have separate schema and nullability questions and should be admitted by a later plan with concrete use cases.
  Date/Author: 2026-08-08 / Codex.
- Decision: Name the new APIs `explode_array`, `explode_outer_array`, `posexplode_array`, and `posexplode_outer_array`.
  Rationale: The suffix distinguishes them from the existing struct generators and makes the accepted input shape visible at the call site. The names still map directly to Spark's `explode` and `posexplode` operations.
  Date/Author: 2026-08-08 / Codex.
- Decision: Require an explicit `as_` schema and `value_field` for scalar generators; `posexplode_array` also accepts an `ordinal` field name defaulting to `ordinal`.
  Rationale: The compiler must know the generated field name and type without inferring an arbitrary Spark column name. Explicit naming preserves typed row scopes and collision diagnostics.
  Date/Author: 2026-08-08 / Codex.
- Decision: Preserve the existing inner-generator contract that input arrays and their elements are non-null. Outer variants may receive nullable arrays and produce nullable generated fields, including a nullable ordinal.
  Rationale: This matches the current strictness of `posexplode_struct` and avoids silently introducing null-element behavior into the established generator family.
  Date/Author: 2026-08-08 / Codex.
- Decision: Do not add indexed `arr_transform` callbacks in this plan.
  Rationale: Search line offsets can be calculated after expansion with a native window over preceding line lengths. Indexed callbacks are a separate higher-order collection feature and are now specified as a follow-up that preserves the existing PySpark helper names rather than adding separate variants.
  Date/Author: 2026-08-08 / Codex.
- Decision: Add primitive map generators as a sibling collection slice with explicit `key_field` and `value_field` names.
  Rationale: Spark map generators emit two generated columns and map keys are non-null while map values may be nullable; a separate recipe keeps those semantics visible without overloading the scalar-array contract.
  Date/Author: 2026-08-08 / Codex.
- Decision: Treat null/empty conformance and backend parity/observability as follow-on hardening work in this plan.
  Rationale: The primitive map implementation is useful and compiler-visible now, while complete runtime semantics and
  cross-backend evidence require a broader fixture matrix than the initial API slice.
  Date/Author: 2026-08-08 / Codex.
- Decision: Keep `SentenceChunking.default_sentence_spans` as a UDF and move it to the end of the transform class, immediately before private methods.
  Rationale: It is a replaceable sentence-segmentation implementation whose Python regex behavior is part of the extension seam. This plan removes only the UDF that can be replaced by existing optimizer-visible operations.
  Date/Author: 2026-08-08 / Codex.
- Decision: Schedule this plan across V10 Sprints 49–54 as an explicitly admitted compiler/API proving slice.
  Rationale: The scalar generator contract belongs with V10 API Catalog work, while Search migration, streaming classification,

## Context and Orientation

Structure transform code is authored with symbolic expressions. The compiler captures those expressions into an intermediate plan, then either renders generated PySpark or evaluates the same plan through the online PySpark path. An optimizer-visible operation is one represented in that plan as a native DataFrame or Column operation rather than executed inside a Python UDF.

The current typed struct generator implementation is distributed across the PySpark DSL, compiler operation model, generated renderer, online evaluator, explain renderer, traceability, and streaming compatibility checks. The primary entry points are `src/structure/plugin/pyspark/dsl/generators.py`, `src/structure/plugin/pyspark/dsl/logic/CapturePySparkGenerator.py`, `src/structure/plugin/pyspark/compiler/model/PySparkOperationRecipe.py`, and the corresponding map/render/execution modules.

The Search example's live line chunking is `examples/search/transforms/chunking/DocumentChunking.py`. Its intermediate schemas are in `examples/search/schemas/chunking/intermediate.py`, and schema registries are maintained by the Search test helpers and the PySpark integration fixture. The current public boundary relations remain span-only; this plan changes only how transient line rows and line metadata are produced.

## Plan of Work

### Milestone 1: Add the scalar-array generator contract

Add four public DSL helpers in the same family as the struct generators: `explode_array`, `explode_outer_array`, `posexplode_array`, and `posexplode_outer_array`. Each accepts an array expression, `as_`, `value_field`, and optional `scope`; positional variants also accept `ordinal`.

The generated schema must contain the named scalar value field and, for positional variants, the named long ordinal field. The capture layer must validate that the source is an array of an admitted primitive type, that the value field type and nullability match the array element type, that positional schemas contain the ordinal field, and that no undeclared generated fields are present. Inner variants reject nullable arrays and nullable elements under the existing strict generator policy. Outer variants make generated fields nullable and preserve one null row for a null or empty source array according to Spark semantics.

Add distinct operation metadata for scalar generators rather than mutating the existing struct-generator recipe. Preserve the existing operation properties: row-multiplying cardinality, generated scope registration, source-column collision checks, and deterministic operation names.

### Milestone 2: Lower the contract through every execution path

Update the PySpark operation model, symbolic rewrite/map logic, generated renderer, online evaluator, explain renderer, traceability dependency builder, and streaming compatibility classifier. Generated code must lower scalar generators to Spark's native `explode` or `posexplode` call with explicit aliases for the value and ordinal fields. Online execution must produce the same rows and schema as generated execution.

Classify inner and outer scalar generators as stateless row-expanding operations with the same streaming support policy as the corresponding struct generators. Unsupported input shapes and invalid nullability must fail during symbolic compilation with actionable diagnostics before a Spark action.

Update `src/structure/plugin/pyspark/__init__.py`, the collection API reference, the API catalog, and the machine-readable transformation and streaming coverage inventories. Add direct operation tests beside the existing struct-generator tests, including accepted primitive arrays, generated field names, nullability, outer behavior, type rejection, source collisions, explain text, traceability, and streaming classification.

### Milestone 3: Rewrite Search line chunking with native operations

In `examples/search/transforms/chunking/DocumentChunking.py`, remove `canonical_document_lines` and call `posexplode_array` directly from `mark_lines` over:

    split(regexp_replace(document.content, pattern=r"\r\n?", replacement="\n"), pattern="\n")

Redefine `ExpandedDocumentLine` in `examples/search/schemas/chunking/intermediate.py` as the transient generated row containing the ordinal and line value. Remove `DocumentLine`, which only existed as the UDF's array element schema, from the public Search schema surface and all registries.

Derive `span_start` with a document-partitioned window over preceding line lengths plus one canonical newline character. Derive `span_end` from `span_start + length(line)`. Detect headings using native regular-expression extraction, `trim`, and `nullif`; compute heading start from the matched prefix length and heading end from the heading length. Preserve the current fallback and blank-line behavior, including the empty document and trailing newline cases.

Move `SentenceChunking.default_sentence_spans` to the end of the transform class after all public step methods and before any private methods. Apply the same ordering rule to any other transform-local `@special(type="udf")` methods discovered during implementation. Shared utility methods such as `Text.span` remain in their utility module and are not transform members.

Update Search traceability expectations so `mark_lines` has no opaque UDF boundary and records the scalar generator and native expressions. Update span tests to validate the compiled operation and generated/online results for ASCII, CRLF, emoji, Arabic, headings with surrounding whitespace, blank lines, punctuation-only lines, empty documents, and trailing newlines.

### Milestone 4: Regenerate and document the resulting contract

Regenerate Search PySpark artifacts with `make gold`. Update collected and annotated Search documentation so it shows the optimizer-visible scalar generator and native span derivation, and remove stale references to `canonical_document_lines` and `DocumentLine` from active documentation and registries. Preserve unrelated working-tree changes.

Record any new API limitations or deferred collection operations in the relevant coverage ledgers and in this plan's `Surprises & Discoveries` section. Do not implement indexed higher-order callbacks, nested-value generators, or compatibility aliases in this plan; the approved indexed callback follow-up is tracked separately.

### Milestone 5: Null and empty collection conformance

For inner and outer forms, assert the generated and online paths agree on null input, empty input, nullable array
elements, nullable map values, generated-field nullability, ordinal nullability, and preserved source-row behavior.
Keep the established strict inner contracts explicit: inner scalar arrays reject nullable elements, inner maps preserve
`value_contains_null`, and outer variants emit one nullable generated row for null or empty collections according to
Spark semantics. Add live Spark assertions when the integration backend is available; otherwise retain the symbolic
and fake-online evidence with an explicit skip reason.

### Milestone 6: Backend parity and observability

Build a parity matrix covering generated PySpark, online execution, ordinary PySpark, and Spark Connect for every
admitted generator variant. Compare output rows and schemas, native function lowering, operation cardinality and
streaming classification, explain text, static dependency reads, provenance, and source-collision diagnostics. Record
backend/profile limitations in the capability and streaming ledgers, and ensure generated and online failures use the
same actionable contract diagnostics before a Spark action.

## Interfaces and Dependencies

The new public helpers are typed PySpark DSL operations:

    explode_array(value, *, as_, value_field, scope=None)
    explode_outer_array(value, *, as_, value_field, scope=None)
    posexplode_array(value, *, as_, value_field, ordinal="ordinal", scope=None)
    posexplode_outer_array(value, *, as_, value_field, ordinal="ordinal", scope=None)

`as_` is a `structure.Schema` class. For non-positional forms it must declare the scalar `value_field`; for positional forms it must additionally declare the long ordinal field. The value field type must match the array element type. These helpers are compiler-visible only and do not accept arbitrary Python callbacks or raw PySpark columns.

The implementation depends on the existing Structure schema/type system, operation-plan model, generated PySpark renderer, online PySpark evaluator, traceability model, and streaming capability classifier. Search depends on the existing `regexp_replace`, `split`, `regexp_extract`, `trim`, `nullif`, `length`, `window`, `rows_between`, `preceding`, `coalesce`, and `window_sum` helpers.

### Map-generator extension

This plan is extended with a second typed collection-generator slice. Add four public helpers:
`explode_map`, `explode_outer_map`, `posexplode_map`, and `posexplode_outer_map`.

The map contract uses explicit `key_field` and `value_field` names because Spark emits two generated columns and map
keys have different nullability semantics from map values. Positional forms additionally declare a long `ordinal`
field. The first implementation admits primitive scalar key and value types, requires non-null map expressions for
inner forms, preserves the source map's `value_contains_null` contract for inner values, and makes key, value, and
ordinal fields nullable for outer forms. It does not admit nested map keys/values, variant values, or compatibility
aliases. Map generators remain stateless row-expanding operations across generated, online, symbolic, explain,
traceability, and streaming paths.

The map slice is accepted when the generated and online paths lower to native Spark `explode`/`posexplode` map
generators, validate field names/types/nullability before execution, preserve deterministic source collision checks,
and expose the operation in the API and capability ledgers. Focused tests must cover primitive map types, nullable map
values, outer rows, ordinal fields, invalid nested/non-primitive shapes, schema mismatches, collisions, explain text,
traceability, and streaming classification.
