## Purpose / Big Picture

Structure must support a future non-PySpark plugin without weakening Structure semantics.
Core continues to own transform declarations, inheritance, source order, step invocation,
parent-step restrictions, lane routing, outputs, decorators, and hook placement. PySpark owns
the symbolic language evaluated during those Core-controlled invocations: concrete field types,
expressions, joins, projections, aggregates, operations, schema validation, and runtime-hook
rules.

`Compiler.frontend.analyze()` will return a structural plan without invoking user methods.
`Compiler.frontend.compile()` will select PySpark, author each step once through PySpark symbolic
arguments, attach opaque PySpark bodies, and compile once. PySpark remains bundled and remains
central to Structure documentation and examples.

  Evidence: `StepPlan`, `StepResultPlan`, and `OutputPlan` expose filters, projections, joins,
  aggregates, or operations despite already having `plugin_body`.
- Observation: Core's frontend invokes methods and reads symbolic state.
  Evidence: `CompileTransform` creates a fallback context, constructs symbolic scopes, validates
  expressions and joins, and writes target values into structural plans.
- Observation: documentation is intentionally integrated with bundled PySpark.
  Evidence: generated Structure documentation includes PySpark types, joins, generated artifacts,
  and traceability; that product composition remains supported.
- Observation: PySpark authoring can already freeze context-local filters, joins, operations, and aggregate state
  without Core reading the context.
  Evidence: `CapturePySparkStep` now creates `PySparkStepBody` through the PySpark symbolic-execution endpoint.
- Observation: lowering can consume the opaque body before public-plan fields are deleted.
  Evidence: the PySpark step mapper now maps filters, joins, operations, projections, aggregates, and
  per-result target values exclusively from `PySparkStepBody`; its compatibility branch exists solely for the
  temporary Core legacy authorer.
- Observation: PySpark authoring can initialize its own symbolic scope from the public request.
  Evidence: `PySparkStepSession.__enter__()` now installs its default source and relation scopes, and capture
  applies PySpark reserved operations. Core only retains its legacy fallback setup while body validation moves.
- Observation: a plan can already be structurally clean at the compiler dispatch boundary while the legacy
  authorer remains behind that boundary.
  Evidence: `AuthorTransform` overlays only `plugin_body` on the plan returned by `analyze()`; the plugin
  contract test verifies the Core target slots are empty when `plugin.compiler.compile()` receives it.
- Observation: integrated documentation can keep PySpark-rich join material without allowing the Core docs data
  mapper to inspect a PySpark step body.
  Evidence: `DescribePySparkDocumentation` provides the displayed join/dependency facts through the PySpark render
  app endpoint; existing generated-doc and CLI snapshots remain unchanged.
- Observation: final output target slots were dead data rather than authored values.
  Evidence: output construction always supplied empty filters, projections, joins, and operations; removing them
  leaves PySpark output lowering as final Core routing and schema validation only.
- Observation: public step/result target slots can be removed before removing the deprecated compiler helper.
  Evidence: `LegacyStepPlan` and `LegacyStepResultPlan` preserve its temporary payload while normal compiler dispatch
  receives the structural plugin records with `PySparkStepBody` payloads.
- Observation: Core's field records need only a neutral marker for annotation-derived declarations, not a concrete
  target type.
  Evidence: `AnnotationType("__annotation__")` lets the selected schema facet infer Python hints without restoring a
  Core import of the PySpark type hierarchy.
- Observation: pipeline composition must distinguish structural analysis from captured-body rewriting.
  Evidence: `AnalyzeTransform` composes before any body exists, while authored pipelines must rewrite join source
  frames inside the opaque selected-plugin body. An optional identity rewrite preserves the former; the selected
  `AuthoringAPI` owns the latter.
- Observation: relation-read ordering is a target-body rule even though Core owns input declaration order.
  Evidence: the plugin can validate it from `StepAuthoringRequest.inputs` plus its own captured operations and
  projections, preserving `JOIN-E0601` without exposing symbolic context to Core.
- Observation: target validation may need to run between invocation and Core result routing.
  Evidence: invalid RIGHT/FULL temporal and as-of joins must raise `JOIN-E0601` before structural assignment
  validation observes their nullable result shape. `StepAuthoringSession.validate()` provides that lifecycle point
  without exposing the plugin context to Core.
- Observation: moving target validators must preserve parameterized-type and purpose-specific behavior, not merely
  their broad type categories.
  Evidence: migration review found that decimal join keys with incompatible scale/precision had become accepted and
  documentation-purpose compilation had bypassed PySpark hook validation. PySpark now restores exact type matching
  and validates hooks before both documentation and runtime compilation.
- Observation: aggregate lowering has two distinct concerns: recording aggregate intent during a step and constructing
  a reusable aggregate expression value outside a step.
  Evidence: recording intent unconditionally made `count()` fail public DSL/API inspection, while treating Core's
  implicit grouped representative value as the user-facing ordered `first_value(...)` rejected valid struct fields.
  Intent is now conditional on an active context; implicit `first` remains a PySpark body-level aggregate with its
  established broad type support.

## Context and Orientation

A structural plan contains plugin-independent facts: names, declaration origins, schemas,
parameter-to-lane bindings, source order, output routing, options, and hook placement. A
plugin body is the target language evaluated by a step. For PySpark it contains expressions,
joins, projections, aggregations, operations, concrete types, and target diagnostics. Core may
retain and route a plugin body but never inspect it.

Current work begins in `src/structure/core/compiler/frontend/commands/CompileTransform.py`.
It combines structural analysis with PySpark behavior. Public authoring contracts and plans live
under `src/structure/plugin/api/v1/model/`; PySpark capture and lowering live under
`src/structure/plugin/pyspark/`.

## Interfaces and Dependencies

Add the public frozen value `StepAuthoringCapture`:

    body: object
    diagnostics: tuple[object, ...] = ()

Change `StepAuthoringSession` to expose only `arguments()` and
`capture(value) -> StepAuthoringCapture`. Remove `context()` so Core cannot read or mutate
plugin symbolic state.

`StepPlan` retains step identity, structural schemas, source/lane routing, bindings, results,
options, origins, hook placement, and `plugin_body`. `StepResultPlan` retains schema, lane,
frame, ordinal, and hook placement. `OutputPlan` retains final structural routing and aliases.
Remove their filters, projection, joins, aggregate, and operation fields.

Create PySpark-owned `PySparkStepBody` and `PySparkResultBody` values. They contain all
PySpark expression, join, projection, aggregate, and operation records currently kept in Core.
Their values remain opaque to Core.

## Concrete Steps

### Validator-Migration Safety Rule

When moving a validator from Core to a plugin, preserve behavior before deleting the
Core implementation. The migration must identify every semantic branch of the old validator
and add or retain a regression for each target-specific edge: parameterized types (for example
Decimal precision/scale and Struct schema identity), nullability, operation ordering, and generated
as well as online execution behavior.

Run each affected contract through every compilation purpose. In particular, `RUNTIME` and
`DOCUMENTATION` must both perform target validation even when documentation intentionally omits a
runtime payload. A validator may move to a plugin lifecycle point only if that point is reached by
all applicable purposes. Do not infer PySpark behavior from broad type names or from a successful
happy-path generated artifact; use exact type and diagnostic assertions.

## Validation and Acceptance

`analyze()` returns the same structural declaration order, bindings, lanes, outputs, origins, and
hook placement without calling a step or importing PySpark. `compile()` validates schemas before
execution, authors every step once through the selected plugin, preserves Core lifecycle rules,
and calls the compiler once with complete opaque bodies.

Every existing invalid PySpark expression, join, aggregate, relation read, UDF, nested type, and
runtime-hook case fails with equivalent diagnostics after migration. Patching former Core target
validators to fail must not affect PySpark compilation. A fake non-PySpark plugin compiles a
simple structural transform without loading PySpark. Integrated generated documentation continues
to include PySpark content. `make build` passes.

## Idempotence and Recovery

Keep each migration additive until its focused suite passes. If an import cycle appears, move the
disputed target helper into PySpark rather than restoring a Core PySpark import. Do not update a
generated snapshot until the completed PySpark body and lowered recipe show that a difference is
intentional.
