# Scalable PySpark Integration Test Layout

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can reorganize the live PySpark
integration tests without relying on prior conversation.

## Purpose / Big Picture

Structure's live PySpark integration tests prove that online execution and generated PySpark execution agree on real
PySpark and Spark Connect backends. The test behavior is already valuable, but the previous layout grouped multiple
versions and scenarios into a few broad files. After this change, each integration scenario lives in a versioned,
domain-oriented directory that mirrors `res/testing/model/v1` and `res/testing/model/v2`, making future backend and
fixture growth easier to review.

The visible result is that `make integration` still runs the same live parity checks, while collection paths now show
small scenario modules such as `tests/integration/pyspark/v2/analytics/test_order_analytics.py`.

## Surprises & Discoveries

- Observation: The integration runner already invokes pytest on the whole `tests/integration` tree.
  Evidence: `infra/compose/images/pyspark/run-integration.sh` runs `python -m pytest /workspace/tests/integration`, so
  no runner change is needed when test files move deeper under that root.

- Observation: Some unrelated documentation files were untracked before this work started.
  Evidence: `git status --short` listed unrelated files under `docs/` and `docs/dev/`; this plan leaves them untouched.

- Observation: A first `make build` attempt failed on the public API snapshot while unrelated public API work was still
  changing in the dirty tree, and a later pre-collapse build was green.
  Evidence: a later `make build` passed lint, mypy, 522 default pytest tests with seven integration skips, rigidity
  checks, and package build.

- Observation: After collapsing versioned support under `v1/support` and `v2/support`, `make build` is again blocked by
  unrelated public API snapshot drift.
  Evidence: the only snapshot deltas are `StreamingMode` enum members changing from `STREAM`, `STATIC`, `EITHER` to
  `YES`, `NO`, and `input(..., streaming=...)` defaulting from `StreamingMode.EITHER` to `StreamingMode.NO`.

- Observation: The current dirty generator/compiler state emits invalid generated code for Spark Connect order
  enrichment scenarios.
  Evidence: both Spark Connect lanes fail v.1 and v.2 order enrichment in generated execution with
  `UnboundLocalError: cannot access local variable 'orders'` at generated calls shaped as
  `self._impl.use_current_orders(orders=orders, inputs=inputs, ...)`. The moved support modules only build input
  DataFrames and call the same render/session APIs; they do not render step bodies.

## Context and Orientation

Live backend integration tests live under `tests/integration`. They are opt-in tests marked with
`pytest.mark.integration`; without `--run-integration`, the pytest plugin in `tests/integration/pytest_plugin.py`
skips them so ordinary `poetry run pytest` and `make build` stay Spark-free.

The old PySpark layout used a few broad files:

- `tests/integration/pyspark/test_v1_backend_matrix.py`
- `tests/integration/pyspark/test_v2_backend_matrix.py`
- `tests/integration/pyspark/test_v2_adv_analytics_backend_matrix.py`
- `tests/integration/pyspark/matrix_support.py`

The new layout separates backend mechanics, reusable support, and scenario assertions:

    tests/integration/pyspark/
      backend/test_runtime_versions.py
      support/backend_matrix.py
      support/rows.py
      v1/support/orders.py
      v1/support/multi_lookup.py
      v1/orders/test_enrichment.py
      v1/multiple_schema_parameters/test_lookup_product.py
      v2/support/orders.py
      v2/support/analytics.py
      v2/support/rowset_joins.py
      v2/support/advanced_analytics.py
      v2/orders/test_enrichment.py
      v2/analytics/test_order_analytics.py
      v2/rowset_joins/test_rowset_join.py
      v2/advanced_analytics/test_advanced_order_analytics.py

## Plan of Work

Move the generic Spark session fixture, backend selection helpers, generated-project writer, and generated Spark
Connect safety scan into `tests/integration/pyspark/support/backend_matrix.py`. Update `tests/integration/pyspark/conftest.py`
to re-export `spark` from that new module.

Move repeated DataFrame row collection helpers into `tests/integration/pyspark/support/rows.py`. Keep these helpers
small and independent of fixture versions.

Move version-specific fixture setup into version-local support modules. The v.1 modules own CSV-backed orders setup and
the multi-schema lookup fixture. The v.2 modules own orders enrichment rows, analytics rows, rowset join rows, and
advanced analytics CSV parsing. Do not create a second `support/v1` or `support/v2` hierarchy under the top-level
support directory.

Create one test module per live scenario. Each test module must set `pytestmark = pytest.mark.integration`, render the
generated project with the same source transform and generated package name as before, run online and generated
execution against the same inputs, and keep the same expected row assertions.

Update `docs/dev/Testing.md` so future contributors place new integration tests under the versioned scenario hierarchy,
put shared live-backend support under `tests/integration/pyspark/support`, and put fixture-version support under the
matching version directory.

## Concrete Steps

From the repository root, inspect collection and default skip behavior:

    poetry run pytest tests/integration --collect-only -q
    poetry run pytest tests/integration -q

Run the standard Spark-free project gate:

    make build

When Docker and the integration stack are available, run each focused backend lane:

    make integration BACKEND=pyspark35
    make integration BACKEND=pyspark40
    make integration BACKEND=spark-connect35
    make integration BACKEND=spark-connect40

## Validation and Acceptance

Acceptance is met when pytest collects the same seven live integration scenarios under the new paths, default
integration pytest runs skip them without importing PySpark at module import time, and `make build` passes without
starting Docker or Spark.

Full live acceptance is met when all four focused backend lanes pass with the same online/generated parity assertions
and generated Spark Connect safety scans as before.

## Idempotence and Recovery

The reorganization is ordinary file movement and helper extraction. Re-running pytest or `make build` is safe. If
collection fails, first check stale imports from `integration.pyspark.matrix_support`; all imports should now point to
`integration.pyspark.support.backend_matrix`. If live integration fails in one backend lane, rerun the focused
`make integration BACKEND=...` command and record the exact backend and traceback in this plan before changing
behavior.

## Artifacts and Notes

The implementation intentionally does not move checked-in fixture data from `res/testing/data` and does not change the
Compose runner, pytest plugin, or public Structure APIs.

## Interfaces and Dependencies

No public library interfaces change. The only import path change is internal to tests:
`integration.pyspark.matrix_support` is replaced by `integration.pyspark.support.backend_matrix`.
