# Add ordinal-aware higher-order array callbacks

This ExecPlan is a living document. Maintain the `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections as work proceeds. Follow [`docs/dev/auto/Plans.md`](/Users/chaos/Files/Dev/Code/taitl-structure/docs/dev/auto/Plans.md) when revising or implementing this plan.

## Purpose / Big Picture

Extend the existing `arr_transform` and `arr_filter` helpers so callbacks may receive a typed zero-based element index, matching PySpark's binary callback forms:

    arr_transform(values, lambda item: lower(item))
    arr_transform(values, lambda item, index: item + index)
    arr_filter(values, lambda item, index: index % 2 == 0)

The unary forms remain unchanged. The compiler, generated PySpark renderer, online evaluator, explain output, traceability, diagnostics, and backend compatibility model must all represent the same callback arity and typed index. The feature also enables ordinal-aware array outputs by returning a declared typed struct from `arr_transform`.

This plan follows PySpark's existing helper names. It does not add `arr_transform_indexed` or `arr_filter_indexed` aliases.

## Surprises & Discoveries

- Observation: PySpark exposes indexed callbacks as binary forms of `transform` and `filter`, not separate functions.
  Evidence: The supported PySpark 3.5 API documents `(element, index)` callbacks with a zero-based index.
- Observation: Structure currently captures callback bodies by invoking the Python callback once with symbolic `lambda_arg` expressions, while the renderer and online evaluator infer bindings from the captured expression.
  Evidence: `arr_transform` and `arr_filter` currently pass one `_lambda_arg`; generated and online paths each bind one lambda value.
- Risk: Callback parameter names alone are insufficient for nested callbacks if inner and outer callbacks reuse names such as `item` or `index`.
  Required response: Preserve explicit callback argument identity/role in the captured IR and add a nested-binding regression test.
- Constraint: An index supplies position, not a cumulative prefix value. Search's variable-length line offsets should not be migrated from explode-plus-window logic unless a separate benchmark proves the composed array expression is preferable.

## Decision Log

- Decision: Extend `arr_transform` and `arr_filter` to accept either unary or binary callbacks.
  Rationale: This follows the public PySpark API and avoids redundant indexed helper names.
  Date/Author: 2026-08-08 / Codex.
- Decision: Use a zero-based, non-null `LongType` index for both helpers.
  Rationale: This matches PySpark and the existing `posexplode_*` ordinal type/semantics.
  Date/Author: 2026-08-08 / Codex.
- Decision: For `arr_filter`, the index refers to the original input-array position, not the compacted output position.
  Rationale: Filtering evaluates the predicate against the source array before elements are removed.
  Date/Author: 2026-08-08 / Codex.
- Decision: Keep `arr_exists`, `arr_forall`, map callbacks, `arr_sort_by`, and `arr_aggregate` unchanged.
  Rationale: They either lack a native indexed PySpark callback contract or have callback semantics that are not position-preserving. An accumulator struct or `sequence`/`arr_zip_with` composition remains available when a caller needs an explicit derived position.
  Date/Author: 2026-08-08 / Codex.
- Decision: Do not add a dedicated `arr_enumerate`/`arr_with_ordinal` helper in this plan.
  Rationale: An ordinal-aware `arr_transform` returning a declared struct already provides the capability; a convenience helper should wait for repeated use cases that justify schema and field-name policy.
  Date/Author: 2026-08-08 / Codex.
- Decision: Preserve existing unary lowering and generated source shape wherever possible.
  Rationale: Existing users and golden tests should not observe a gratuitous IR or generated-code change when they use unary callbacks.
  Date/Author: 2026-08-08 / Codex.
- Decision: Determine callback arity during symbolic compilation using an inspectable callable signature, accepting exactly one or exactly two required positional parameters. Reject ambiguous varargs, keyword-only, zero-argument, and greater-than-two-argument callbacks with an actionable diagnostic.
  Rationale: The compiler must choose the Spark unary or binary form before invoking the symbolic callback; implicit trial calls would conflate callback-arity errors with errors raised by callback bodies.
  Date/Author: 2026-08-08 / Codex.

## Context and Orientation

Structure transform authors write symbolic expressions. Higher-order helpers invoke the callback once during authoring with symbolic expressions, then capture the resulting body. Generated PySpark renders the body as a native Spark higher-order lambda; online execution evaluates the same captured body against runtime `Column` objects.

The primary DSL entry points are in `src/structure/plugin/pyspark/dsl/operations_api.py`. Generated expression rendering is in `src/structure/plugin/pyspark/render/logic/expressions/RenderPySparkExpression.py`; online expression evaluation is in `src/structure/plugin/pyspark/execution/logic/expressions/EvaluatePySparkExpression.py`. Existing higher-order API documentation is in `docs/api/Collections.api.md`, with contract tests under `tests/specifications/`.

## Plan of Work

### Milestone 1: Capture typed callback arity

Update `arr_transform` and `arr_filter` type annotations with overloads for unary and binary callbacks. Add a shared callback-signature validator that classifies only exact one- or two-required-positional-parameter callables and produces helper-specific diagnostics for unsupported signatures.

For binary callbacks, construct two explicit symbolic arguments: the existing typed array element and a non-null `LongType` index. Preserve the source array nullability and element nullability rules. Capture callback arity, argument roles, and lexical binding identity in the expression metadata so nested callbacks cannot rebind an outer index accidentally.

For `arr_transform`, retain the callback result type and nullability as the resulting array element contract. For `arr_filter`, require a Boolean callback result and preserve the input array element type and nullability.

### Milestone 2: Lower generated and online execution

Add binary rendering for the existing reserved operations:

    F.transform(array, lambda item, index: body)
    F.filter(array, lambda item, index: body)

The unary forms must continue rendering as one-parameter lambdas. Update the online evaluator to pass both runtime lambda columns and bind the captured body using the same argument identity as generated rendering.

Add nested callback coverage where an outer indexed transform contains an inner indexed transform and both callbacks use the same source-level parameter names. The result must demonstrate that each body observes its own index and that an explicitly captured outer index remains the outer index.

### Milestone 3: Compiler surfaces and compatibility

Update explain rendering, traceability/dependency walking, streaming compatibility classification, backend capability tests, public exports if needed, and Spark Connect compatibility evidence. Indexed forms reuse the existing `array_transform` and `array_filter` capability names; callback arity is operation metadata, not a new backend function.

Diagnostics must occur before a Spark action and identify the helper, expected callback shape, received shape, and the supported unary/binary alternatives. Existing unsupported-Python callback diagnostics must remain actionable.

### Milestone 4: Documentation and ordinal-aware outputs

Document unary and binary forms in `docs/api/Collections.api.md` and the relevant higher-order collection reference. Document that filter indexes are source positions and that indexes are zero-based `long` expressions.

Show the typed output pattern using a declared schema instance returned by `arr_transform`, for example an array of `{value, ordinal}` structs. Explain that this preserves nested array shape; callers needing rows should use the existing typed struct generator afterward.

Do not migrate Search line-span windows as part of this plan. Add a note that indexed callbacks may annotate positions but do not inherently compute variable-length prefix offsets.

## Validation and Acceptance

The feature is accepted when:

- `arr_transform(values, lambda item: ...)` and `arr_filter(values, lambda item: ...)` retain existing behavior and generated source.
- `arr_transform(values, lambda item, index: index + item)` captures an index typed as non-null `long`, renders a native binary Spark lambda, and matches online execution.
- An indexed transform can return a declared typed struct containing the source value and zero-based ordinal.
- `arr_filter(values, lambda item, index: index % 2 == 0)` retains elements at original positions 0, 2, 4, and so on.
- Null and empty arrays preserve existing higher-order nullability and cardinality behavior.
- Nested indexed callbacks bind inner and outer indexes correctly.
- Invalid callback arity, untyped results, non-Boolean filter results, and unsupported Python callback code fail during compilation with deterministic diagnostics.
- Explain output, traceability, streaming classification, ordinary PySpark, Spark Connect, generated execution, and online execution agree on the same operation contract.
- `make gold` is stable on repeat runs and `make build` completes successfully.

## Interfaces and Dependencies

The public signatures become overloadable forms equivalent to:

    arr_transform(value, function: Callable[[Expression], object] | Callable[[Expression, Expression], object]) -> Expression
    arr_filter(value, function: Callable[[Expression], object] | Callable[[Expression, Expression], object]) -> Expression

The second callback argument is a compiler-created `Expression` with `LongType` and `nullable=False`. The implementation depends on the existing `Expression`/`lambda_arg` model, PySpark expression recipe conversion, generated renderer, online evaluator, capability registry, explain/traceability walkers, and higher-order documentation/tests.
