## Purpose / Big Picture

After this plan is complete, large Structure projects can run `structure compile --changed-only` and avoid recompiling
unaffected transforms while preserving deterministic generated output and fail-fast correctness. The work is
deliberately scheduled after v3's PySpark parity and streaming orchestration surfaces so cache keys can include the
final v3 operation and lifecycle-policy shapes.

Users can see the result by running a cold compile, then a no-change incremental compile, then a one-transform source
edit. The first incremental run should reuse all unchanged transforms; the source edit should recompile only the changed
transform and affected dependents. Diagnostics must explain every reuse and invalidation decision.

## Context and Orientation

Structure already requires deterministic IR, generated output, source discovery, and generated-file freshness checks.
Those are prerequisites for incremental compile, but they are not enough for production caching. A correct cache must
know when a source, schema, dependency, configuration, target profile, or generated-artifact policy change affects a
transform.

## Plan of Work

Milestone 1 defines cache identity. Cache keys must include Structure version, effective configuration, source roots,
source fingerprints, schema fingerprints, transform dependency fingerprints, target backend/profile/variant, generated
package, generated-doc configuration, and v3 streaming lifecycle policy where applicable.

Milestone 2 implements `compile --changed-only`. The command must detect changed transforms and affected dependents,
reuse unchanged outputs, and preserve existing `compile --fail-on-diff` behavior. It must not skip validation merely
because generated files exist.

Milestone 3 adds diagnostics. Every transform should be reported as reused, recompiled, invalidated, skipped, or failed
with the reason. Diagnostics should be compact by default and expandable through profile or explain output.

Milestone 4 adds tests and performance fixtures. Cover no-change, one-transform change, schema change, config change,
target-profile change, dependency change, generated-doc config change, cache deletion, stale generated output, and
corrupt cache cases. Add synthetic 10-transform and 100-transform projects for cold and warm timing checks.

Milestone 5 updates public docs and troubleshooting. Explain how to use `compile --changed-only`, how to interpret cache
diagnostics, and how to recover by deleting cache artifacts.

## Validation and Acceptance

The plan is accepted when `compile --changed-only` is implemented, cache diagnostics are documented and tested, and
`make build` passes.

Behavioral acceptance:

- No-change incremental compile reuses unchanged transform artifacts.
- One-transform edits recompile only the changed transform and affected dependents.
- Schema, config, target, generated-doc, and dependency changes invalidate affected transforms.
- Deleting cache artifacts does not break correctness.
- Corrupt or stale cache artifacts fail closed or rebuild with diagnostics.
- Compiler commands remain Spark-free.

## Idempotence and Recovery

Incremental compile must be safe to rerun. Cache artifacts are derived state and must be safe to delete. If cache
diagnostics become ambiguous, prefer full recompilation with an explanation over trusting stale generated artifacts.

## Interfaces and Dependencies

Use existing compiler discovery, IR determinism, generated artifact comparison, diagnostics, and profile infrastructure.
Do not add a runtime dependency that makes compiler commands import PySpark, start Java, or create a SparkSession.
