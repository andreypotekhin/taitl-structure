## Purpose / Big Picture


Let users declare native Geometry and Geography fields, call Apache Spark or Databricks spatial helpers explicitly,
and use Sedona alongside them without application settings that choose one spatial provider. A namespace identifies
the helper implementation. A spatial type identifies the representation of its values. Those are separate facts:
Spark and Databricks helpers may produce the same native SQL type, while Sedona uses a distinct user-defined type.

After implementation, users can write `geometry(srid=4326)` for a native field, `sedona.geometry(srid=4326)` for a
Sedona field, and choose between `st_geomfromwkb(...)`, `databricks.st_geomfromwkb(...)`, and
`sedona.st_geomfromwkb(...)` at each call. An explicit Binary encoder and decoder may bridge representations within
one step. Tests will compare native execution, Structure's online execution, and generated Python code for every
claimed runtime and execution mode.

The project default profile remains `>=3.5,<4.1`. State processors and foreachBatch remain with their existing owners.
This plan does not add spatial joins, coordinate transformations, measurements, arbitrary SQL calls, reader/writer
ownership, or additional providers. Streaming support requires its own evidence and is not admitted by batch tests.

## Surprises & Discoveries


The existing experimental implementation chooses a single installed provider, falling back to Sedona when no entry
point is present. Its generic Geometry schema materializer therefore cannot describe native and Sedona fields in the
same schema reliably. Evidence: `src/structure/plugin/pyspark/geo/runtime.py`,
`src/structure/plugin/pyspark/schema/commands/MaterializePySparkSchema.py`, and
`src/structure/plugin/pyspark/schema/commands/RenderPySparkSchemaModule.py`.

Pinned Apache PySpark 4.1.0 exposes `st_geomfromwkb(wkb)` with one argument. The prior design's optional SRID argument
matches the Databricks API, but not this Apache wrapper. Inspection of the installed
`structure-integration-pyspark41` image confirmed the five Apache signatures listed below. Assign a native SRID with
`st_setsrid(...)` rather than extending the Apache constructor signature.

The same image provides `pyspark.sql.types.GeometryType(srid: int | str)` and `GeographyType(srid: int | str)`.
Both accept `"ANY"` for mixed SRID. Inspection of `structure-integration-pyspark40` reported PySpark 4.0.0 and neither
constructor. These are API-inspection findings, not live value, schema round-trip, or online/generated parity results.

Databricks documents spatial helpers under `pyspark.databricks.sql.functions` on Runtime 17.1 and above; Runtime
17.1 is based on Spark 4.0.0. Its current type reference links to the standard PySpark native spatial types. This
supports testing a shared native declaration, but does not establish older managed-runtime constructor compatibility.
No Databricks runtime has been exercised for this plan. Do not choose an obsolete runtime merely because it is the
first documented version; record the actual supported deployment used for evidence.

The installed Sedona Python API exposes the eleven helpers listed below. Its Geometry type is a user-defined type
(UDT), meaning a Spark type supplied by the extension with its own serializer and JVM implementation. A matching
Geometry name does not make that representation interchangeable with native Geometry.

The Compose images install Sedona 1.9.0, but the current 4.1 lanes do not configure its server packages or extension.
The existing geometry integration test skips 4.1 for that reason. Configuring a coexistence test requires explicit
server setup; finding the Python package is insufficient. Treat registration collisions as testable behavior.

Project-management records now live in `docs/dev/project/`, including the current V11 sprints. Use those paths when
updating progress; preserve unrelated work already present in the shared checkout.

## Decision Log


Decision (2026-10-19, user and Codex): Namespace every provider-specific helper. Root names target Apache PySpark;
`databricks.*` targets Databricks' Python API; `sedona.*` targets Sedona. Remove `geo_provider`, scope precedence,
automatic runtime-distribution switching, and selection based on which providers happen to be installed.
Rationale: the source already identifies the implementation, so ambient selection adds ambiguity and configuration.

Decision (2026-10-19, user and Codex): Share native Geometry/Geography declarations between Apache Spark and
Databricks where their physical type compatibility is verified. Keep Sedona Geometry distinct. Do not invent
`databricks.geometry(...)` solely because the function import differs.
Rationale: function origin and SQL value representation need not have the same identity.

Decision (2026-10-19, user): Allow explicit Binary encode/decode bridges within a single step. A declared Binary
field and a later step are optional.
Rationale: the encoder and decoder already make the conversion visible; a step boundary adds no compatibility proof.

Decision (2026-10-19, user and Codex): Replace the experimental API directly, without deprecated aliases.
Rationale: backward compatibility is not required. Retain ordinary string `contains(...)` while moving spatial
containment to `sedona.st_contains(...)`.

Decision (2026-10-19, user and Codex): Separate helper admission from native schema-constructor availability.
Apache root helpers keep their exact 4.1 gate. Databricks helpers have independent requirements that allow supported
4.0 deployments. Shared native schema declarations are conditional on actual constructor availability on admitted
4.0 and 4.1 profiles. Rationale: an Apache-version-only gate would reject valid managed-runtime capabilities, while
globally enabling Apache helpers on 4.0 would make an incorrect upstream support claim.

Decision (2026-10-19, user and Codex): Preserve native parsing, conversion, and runtime errors. Admit each provider,
operation, and execution mode only after positive evidence. Rationale: SQL convergence and Python importability do
not establish parity, persistence, or collision-free execution.

## Interfaces and Dependencies


The public native declarations and aliases are:

    geometry(srid=None, **field_options)
    geography(srid=None, **field_options)
    Geometry / GeometryType
    Geography / GeographyType

An explicit integer declares a fixed SRID. `None` declares mixed or unknown SRIDs. Reject booleans and noninteger
non-None declarations; let the selected runtime validate its supported integer SRIDs without copying its entire CRS
catalog into Structure. A CRS, or coordinate reference system, defines how coordinates are interpreted. Assigning an
SRID labels coordinates and does not transform them.

Map native fixed types to `T.GeometryType(srid)` or `T.GeographyType(srid)` and mixed types to the corresponding
constructor with `"ANY"`. Use the installed `pyspark.sql.types` module. On a managed runtime, verify that these
constructors produce the actual native schemas expected by the documented helpers. If they do not, retain that target
gate and return the concrete incompatibility for design; do not silently substitute Sedona or invent another logical
type during implementation.

The Apache helper contract is:

    st_geomfromwkb(value)
    st_geogfromwkb(value)
    st_asbinary(value)
    st_srid(value)
    st_setsrid(value, srid)

Constructors consume typed Binary expressions. Geometry construction produces native SRID 0; Geography construction
produces native SRID 4326. Consumers accept native Geometry or Geography. `st_asbinary` returns Binary, `st_srid`
returns Integer, and `st_setsrid` preserves representation and kind. A literal SRID produces a fixed result; a typed
integral SRID expression produces a mixed result. Do not infer values by evaluating symbolic expressions.

The Databricks module exposes the corresponding five `databricks.st_*` helpers. Its WKB Geometry constructor accepts
`databricks.st_geomfromwkb(value, srid=None)`, matching the additional upstream argument. Emit imports from
`pyspark.databricks.sql.functions`. Its spatial outputs use the shared native types, with the same fixed-versus-mixed
reasoning. Databricks helper requirements must not implicitly request Apache root helper capabilities.

The initial Sedona module exposes:

    sedona.geometry(srid=None, **field_options)
    sedona.Geometry / sedona.GeometryType
    sedona.st_geomfromwkt(value, srid=None)
    sedona.st_geomfromwkb(value)
    sedona.st_geomfromewkb(value)
    sedona.st_astext(value)
    sedona.st_asbinary(value)
    sedona.st_asewkb(value)
    sedona.st_srid(value)
    sedona.st_setsrid(value, srid)
    sedona.st_intersects(left, right)
    sedona.st_contains(left, right)
    sedona.st_within(left, right)

Use Sedona's public constructor, function, and predicate modules and their `ST_*` functions. WKT consumes String;
WKB/EWKB consume Binary. Encoders return String or Binary as their names specify. Predicates return Boolean.
An explicit literal SRID establishes a fixed result. Omitted constructor SRIDs, encoded EWKB SRIDs, and symbolic
SRIDs remain mixed or unknown unless a separately typed operation establishes a fixed value. Do not inspect payloads
at compilation time. This slice does not add Sedona Geography or the rest of its spatial catalog.

Representations are `native` and `sedona`, independently of helper namespace. Apache and Databricks helpers may consume
each other's native outputs where the same physical type is verified; they reject Sedona UDT operands. Sedona helpers
reject native operands. Spatial predicates require the same representation, kind, and fixed SRID. General spatial
arithmetic, implicit conversions, and unsupported SQL comparisons must not fall through generic scalar handling.
Nullability and malformed-input behavior must follow the selected upstream operation and be checked by parity tests.

An explicit bridge may be authored in one expression:

    st_setsrid(st_geomfromwkb(sedona.st_asbinary(row.shape)), 4326)

This deliberately removes the Sedona type at the Binary encoder and constructs a native type at the decoder. WKB is
Well-Known Binary; standard WKB does not preserve SRID. EWKB is an extended encoding which can carry SRID, but Binary
alone does not prove that another decoder supports it. Compare geometry meaning, dimensions, and SRID as well as
bytes when establishing a particular bridge's contract.

## Validation and Acceptance


A user can declare a native and a Sedona field in one schema, choose a helper through its namespace, and obtain the
expected physical types and scalar results through native, online, and generated execution. Native Spark and
Databricks helper provenance does not by itself make their verified native values incompatible. Sedona values remain
distinct and require an explicit encoder/decoder when crossing to native values.

Stock Apache 4.0 still rejects unavailable root helpers. A supported Databricks Spark 4.0 deployment can use its
namespaced helpers and shared native declarations without a new distribution setting. Missing native constructors or
vendor functions fail with the operation/type, missing requirement, and Geospatial reference link. Earlier profile
and dependency failures are not hidden by generic SQL calls or selection of another installed provider.

The implementation is accepted only when its physical schemas, SRID/null/error behavior, generated imports, and
coexistence behavior pass the claimed runtime modes; compatibility records match those results; and `make build`
succeeds. A constructor inspection, a query that never executes, a mocked module, or an optional managed test skip is
not positive runtime evidence.
