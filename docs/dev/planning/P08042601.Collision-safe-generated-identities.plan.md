# Make Generated Identities Collision-Safe Across Plugins, Schemas, and Documentation

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It follows the execution-plan rules in `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

Structure must preserve the identity of user source code whenever it creates a generated Python module, schema symbol, documentation artifact, or file path. A user should be able to have two valid source modules with the same basename, or two valid schema classes with the same class name in different modules, without one generated result replacing or silently shadowing the other.

After this work, the following examples must remain distinct from end to end:

    catalog.prepare       -> its own generated module and traceability artifacts
    fulfillment.prepare   -> its own generated module and traceability artifacts
    catalog.Customer      -> its own generated schema symbol and documentation
    fulfillment.Customer  -> its own generated schema symbol and documentation

The behavior is demonstrated by no-Spark regression tests, by generated file maps containing both identities, and by a complete `make build` run. The existing PySpark full-source transform mapping remains the reference behavior; this plan extends the same principle to the Iterable plugin, schema symbols, schema documentation, and the file-writing boundaries.

## Surprises & Discoveries

- Observation: The PySpark transform collision has already been addressed structurally.
  Evidence: `src/structure/plugin/pyspark/GeneratedPySparkTransformModule.py` maps the complete source module below `pyspark.transforms`, and `RenderPySparkProject` creates nested package markers.

- Observation: The same source-basename mistake remained in the example Iterable plugin and was confirmed by the audit.
  Resolution: Iterable now uses the validated full source module and emits nested package markers; the core renderer rejects conflicting paths instead of silently overwriting them.

- Observation: Distinct generated schema module files do not by themselves prevent schema identity collisions.
  Evidence: `RenderPySparkSchema.constant_name()` derives `CUSTOMER_SCHEMA` from only `schema.__name__`, and generated transform imports are emitted without aliases.

- Observation: Documentation had a separate collision path from generated code.
  Resolution: Schema Markdown and JSON now live below `docs/schemas/<source-module-path>/`, and the index links use the same source-qualified identity.

- Observation: A green default build does not prove the old path assumptions are gone.
  Evidence: the prior full build passed while Spark integration lanes were skipped, and several integration tests still index generated files by the former flat path.
  Resolution: Current generation, normative documentation, and active generated-output assertions now use the canonical nested layout. Versioned V3 fixture checks and online `MemoryStorage` cases retain flat paths deliberately as compatibility coverage for historical artifacts.

- Observation: Moving schema mapping behind public plugin endpoints introduced an import-cycle risk through legacy module-level renderer singletons.
  Resolution: The compatibility function entry points now construct their renderers lazily, preserving their call shape while allowing the public PySpark API to initialize cleanly.

- Observation: The isolated Iterable wheel cannot import `structure.core`.
  Resolution: Shared identity and safe-path helpers live under `structure.plugin.api.v1.logic`, which keeps external plugins on the public contract and passes the isolated-wheel test.

## Decision Log

- Decision: Preserve full source-module identity in every generated backend module instead of inventing a global basename-disambiguation registry.
  Rationale: The source module is already a stable identity supplied by discovery and grouping. Mirroring its parts is deterministic, easy to inspect, and does not require cross-run state.
  Date/Author: 2026-08-04 / Codex.

- Decision: Add a defensive merge check at the core project-rendering boundary, even after individual generators become collision-safe.
  Rationale: A plugin can still return duplicate file paths. Identical repeated package markers are harmless; different content at one path must fail explicitly rather than be silently overwritten.
  Date/Author: 2026-08-04 / Codex.

- Decision: Keep the existing PySpark legacy basename import fallback during this increment.
  Rationale: Existing generated projects may still contain the old layout. New generation must always emit and prefer the canonical full-source path, while old artifacts remain readable where they are unambiguous.
  Date/Author: 2026-08-04 / Codex.

- Decision: Make schema documentation paths source-qualified for every schema, not only when a duplicate is detected.
  Rationale: A uniform path is easier to explain and cannot change depending on which other modules happen to be present in a project. The resulting generated-artifact migration is intentional and can be handled by the golden regeneration step.
  Date/Author: 2026-08-04 / Codex.

- Decision: Keep standalone schema-renderer defaults readable, but pass a project-wide collision-safe schema-symbol map through project generation.
  Rationale: Direct users of the low-level renderer should not receive an unnecessary breaking change, while project generation needs one consistent symbol for every schema reference, import, inheritance expression, validation expression, and traceability record.
  Date/Author: 2026-08-04 / Codex.

- Decision: Schedule this work as V10 Sprint 54 hardening rather than a new V10 API feature.
  Rationale: The changes protect generated artifacts, compatibility, documentation, and release reproducibility without expanding the user-facing transformation API.
  Date/Author: 2026-08-04 / Codex.

- Decision: Preserve legacy function-shaped PySpark renderer entry points as lazy wrappers.
  Rationale: Existing callers can continue importing and calling them, while renderer instances receive project-wide schema maps through the public API without import-time cycles.
  Date/Author: 2026-08-04 / Codex.

## Context and Orientation

Structure discovers Python source modules and groups transforms by their `__module__` value. A plugin generator receives one group through `GenerationRequest.source_module` and returns a `GenerationResult` containing generated file paths, the generated importable module name, and generated class names. The core project renderer currently combines results from all source groups.

The important current paths are:

- `src/structure/core/cli/commands/RenderConfiguredPluginProject.py` groups transforms and combines plugin-generated file maps.
- `src/structure/plugin/pyspark/render/commands/RenderPySparkProject.py` renders PySpark runtime, schema, transform, and traceability files.
- `src/structure/plugin/pyspark/GeneratedPySparkTransformModule.py` is the canonical PySpark source-module-to-generated-module mapping.
- `examples/plugins/iterable/src/structure_iterable/generation/Generation.py` is the example Iterable backend generator.
- `src/structure/plugin/pyspark/schema/commands/RenderPySparkSchema.py` creates Python schema constant names.
- `src/structure/plugin/pyspark/render/logic/modules/RenderPySparkTransformModule.py` imports schema constants into generated transform modules.
- `src/structure/core/docs/commands/RenderStructureDocsProject.py` writes generated Markdown and JSON documentation.
- `src/structure/core/compiler/artifacts/commands/WriteGeneratedFiles.py` and `src/structure/plugin/pyspark/files/commands/WriteGeneratedFiles.py` write returned paths to disk.

In this plan, “source identity” means the complete dotted Python module name plus the class name when a class is involved. “Flattening” means discarding part of that identity, usually by taking only the final dotted component. “Collision” means two different source identities resolve to the same generated key or path. “Shadowing” means both artifacts exist conceptually, but one Python import or symbol silently hides the other.

The normal source-discovery path already rejects malformed source file names through `StructureSources`. The generation API is also callable directly, so generation boundaries must validate their own module and path inputs rather than relying exclusively on discovery.

## Plan of Work

### Milestone 1: Establish shared identity validation and fail-fast file merging

Create the target-neutral `SourceModulePath` utility in `src/structure/plugin/api/v1/logic/SourceModulePath.py`, creating the `logic` directory and package marker if needed. It must accept a canonical dotted Python module name, expose its validated parts and slash-separated relative path, and reject empty parts, absolute/path-traversal components, and non-identifier parts. It must produce actionable errors naming the invalid module. Place it under the versioned plugin API because external plugins, including the isolated Iterable wheel, may depend on the API but must not import `structure.core`. Reuse the existing source-path rules from `StructureSources` rather than creating a second incompatible definition.

Use the utility in the canonical PySpark mapper and the Iterable mapper. Validate the generated package separately with the existing dotted-package rules, and reject a generated path that is absolute or escapes its generated root.

Replace the unconditional `files.update(...)` in `RenderConfiguredPluginProject` with a merge helper. The helper must preserve identical repeated files, such as package markers, and raise a structured or clearly actionable error when the same path is returned with different content. The error must include the path, the first source unit, the second source unit, and the remedy: use a collision-safe source-module mapping in the plugin generator.

Create `src/structure/plugin/api/v1/logic/GeneratedFilePath.py` as the shared safe-relative-path helper and call it from both generated-file writers. It belongs under the versioned plugin API for the same reason as `SourceModulePath`: external plugins must be able to use the contract without importing `structure.core`. The check must run before filesystem access and must reject absolute paths and any path whose normalized form is outside the requested root.

### Milestone 2: Remove the Iterable basename collision

Change `examples/plugins/iterable/src/structure_iterable/generation/Generation.py` so the generated module is formed from the full validated `request.source_module`, analogous to the PySpark mapping:

    <generated_package>.iterable.transforms.<full source module>

The returned file map must contain nested `__init__.py` markers for every generated package directory. The returned `GenerationResult.module_name` must be exactly the importable full module name, and all recipes from one source module must remain in that module.

Update the existing Iterable fixture test to expect the full source path. Add a regression using two source units whose final component is the same, such as `demo.catalog.prepare` and `demo.fulfillment.prepare`, with distinct generated classes. Exercise the configured project renderer so the test proves that both outputs survive the cross-source merge, not merely that each isolated generator call produces a file.

Retain no basename compatibility fallback for Iterable unless an existing public runtime path requires it. The plugin is an example implementation and has no need to preserve an ambiguous old layout silently; if compatibility is required by an existing test or documented API, add an explicit legacy adapter with a diagnostic rather than allowing overwrite.

### Milestone 3: Give duplicate schema classes distinct generated symbols

Build one project-wide mapping from each schema class object to its generated Python constant name in `RenderPySparkProject`. The mapping must start with the current readable class-based name, such as `CUSTOMER_SCHEMA`, and qualify duplicates with the generated schema module identity and class name. The final candidate set must be checked for exact uniqueness after normalization; if normalization creates an accidental underscore collision, extend the qualification deterministically until unique.

Thread this mapping through every PySpark generation component that emits or references a schema:

- `RenderPySparkSchema` for schema declarations, bases, and nested schema expressions.
- `RenderPySparkSchemaModule` for dependency imports.
- `RenderPySparkTransformModule` and `RenderPySparkStep` for transform imports, validation, projection, output metadata, and generated expressions.
- `PySparkTraceabilityReport` wherever it records a generated schema constant.

Keep the low-level renderer’s current default when no project mapping is supplied. Project generation must always supply the map, so a schema has one name everywhere in the generated project.

Add a no-Spark regression with two schema classes named `Customer` from different source modules. The test must render both schema modules and a transform that references both. It must assert that the generated module imports two distinct constants and uses each expected constant in the corresponding generated code. It must also verify that schema inheritance and nested schema dependencies use the mapped names rather than reverting to `CUSTOMER_SCHEMA`.

### Milestone 4: Make schema documentation source-qualified and reconcile path contracts

Change `RenderStructureDocsProject` to write schema documents below a source-qualified path, for example:

    docs/schemas/<source-module-path>/<SchemaName>.md
    docs/schemas/<source-module-path>/<SchemaName>.json

Use the source module already carried in `StructureDocsData.schema`; do not infer identity from the class name. Update generated documentation links, index rendering, and documentation tests so the links point to the new paths.

Audit all references to flat generated transform paths and classify each match as normative documentation, active test contract, generated output, or historical/archive material. Update normative documentation and active tests to the canonical full-source layout. Regenerate checked-in outputs through the repository’s supported `make gold` command; never hand-edit generated artifacts. Historical companion documents may retain old examples only when they are clearly marked as historical and cannot be mistaken for the current contract.

The audit must include `docs/GettingStarted.md`, `docs/dev/specifications/PySparkCodeGeneration.md`, related background/specification documents, `tests/specifications/cli/test_v1_cli_commands.py`, `tests/specifications/online-execution/test_v1_structure_session.py`, the Iterable fixture test, and Spark integration tests that index generated files by path.

### Milestone 5: Prove the behavior and close the migration

Run focused tests for source identity validation, generated-file merging, Iterable generation, PySpark project rendering, schema modules, generated documentation, CLI generation, and runtime generated-module imports. Then run golden-output tests and regenerate goldens if the focused tests demonstrate the intended path changes.

Run the full build. If Spark integration tests remain unavailable, record the exact skipped count and run every available no-Spark/generated-source gate. Do not treat skipped live Spark tests as proof that runtime imports work; retain the canonical generated-source and module-import assertions as the no-Spark evidence.

## Validation and Acceptance

The implementation is accepted only when all of the following are true:

- A configured Iterable project containing `catalog.prepare` and `fulfillment.prepare` produces two importable generated modules, two distinct file paths, and both generated classes. Neither class disappears from the combined file map.
- A PySpark project containing same-basename transform modules continues to produce the existing full-source nested paths, and the canonical runtime import selects the correct module. The legacy fallback remains available only for old unambiguous generated layouts.
- Two schemas with the same class name in different source modules produce distinct generated constants. Generated transforms import and use the correct constant for each schema; no later import silently shadows an earlier one.
- Schema Markdown and JSON documentation remains available for both duplicate-named schemas at source-qualified paths, and the generated index or links identify the source module.
- Duplicate generated file paths with different content fail at the core merge boundary with an actionable diagnostic instead of silently overwriting data.
- Direct generation requests with invalid module identities or generated paths fail before writing files. Valid discovered source modules continue to generate unchanged except for the intentional collision-safe paths.
- Normative documentation and active tests no longer require the old flattened transform path. Historical material is explicitly identified if retained.
- `make build` succeeds, `git diff --check` succeeds, and focused collision regressions pass.

## Idempotence and Recovery

All code and test changes are additive until the migration step. The generated-output migration is repeatable because `make gold` derives files from the current source and uses deterministic ordering. If regeneration produces unexpected deletions or broad unrelated changes, do not restore the whole worktree; inspect the generator and revert only the newly generated files that are demonstrably outside this task, preserving pre-existing user changes.

The legacy PySpark import fallback provides a compatibility recovery path for already-generated flat projects. New projects must not rely on that fallback, because it cannot distinguish two old artifacts that collided under the basename layout.

## Artifacts and Notes

The expected architectural invariant after implementation is:

    distinct source identities
        -> distinct generated module/file identities
        -> distinct importable classes and schema symbols
        -> distinct documentation and traceability artifacts

Any exception must be intentional, documented, and protected by a collision test. In particular, repeated package-marker files may have identical content and may be merged; different content at one path is always an error.

## Interfaces and Dependencies

The source-module and generated-path helpers are target-neutral and must not import PySpark or Iterable code. PySpark and Iterable generators may depend on them through `structure.plugin.api.v1.logic`; external plugins must not need `structure.core`. The helpers expose validated dotted-module and relative-filesystem representations, with clear `ValueError` diagnostics for invalid input.

The project renderer continues to consume `GenerationRequest` and `GenerationResult`; no plugin API version bump is required. The `GenerationResult.module_name` contract becomes stricter: it must identify the canonical full generated module returned in the file map.

The schema-symbol map is internal to the PySpark project-rendering call graph. Standalone schema rendering remains backward-compatible when no map is passed, but all project generation, generated documentation, traceability, and generated execution paths must use the project map.

The only external build dependencies are the repository’s existing Poetry environment, pytest, mypy, flake8, and the Makefile targets. Live Spark dependencies are optional for the no-Spark tests; unavailable live lanes must be recorded rather than treated as passing evidence.
