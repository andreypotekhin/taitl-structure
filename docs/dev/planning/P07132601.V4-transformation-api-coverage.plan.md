# Implement V4 PySpark Transformation API Coverage

This ExecPlan is a living document. Its `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` sections must be updated as work proceeds.

## Purpose / Big Picture

After this plan is complete, a Structure user can look up any relevant PySpark 3.5.x/4.0.x transformation API and see
an honest answer: the typed Structure equivalent, a scheduled delivery slice, a deliberate deferral with a reason, or
an unsupported boundary and the appropriate `@raw` or caller-owned alternative. The plan then delivers the scheduled
features in dependency order, so common transformations no longer force users to leave compiler-visible code merely
because a familiar PySpark function is absent.

The visible proof starts with the public coverage catalog and ends with a v4 fixture whose Structure transform uses the
new helper families and whose generated PySpark remains readable. `make build` must pass, and supported helpers must
produce identical results online and through generated code on every claimed target.

## Surprises & Discoveries

- Observation: v3 closed its scheduled parity work but `docs/dev/Gaps.md` still contains planned Column, function,
  join, aggregation, and collection work.
  Evidence: the remaining entries include bitwise and struct mutation; hashes, encodings, and parsers; nearest as-of
  and reordering; exact percentiles and statistics; and array variants and generators.
- Observation: Structure already has one shared PySpark recipe path for online and generated execution.
  Evidence: `src/structure/app/target/pyspark/model/PySparkExpressionRecipe.py` and the PySpark expression mapper
  render symbolic expression recipes rather than maintaining separate public implementations.
- Observation: the supported type model is intentionally smaller than Spark SQL's type system.
  Evidence: `src/structure/app/dsl/model/types/` provides scalar, array, map, and struct types but not binary,
  interval, timestamp-without-time-zone, variant, or geospatial types.

## Decision Log

- Decision: Measure coverage against the PySpark 3.5.x and 4.0.x target intersection, not the newest Spark release.
  Rationale: Structure promises `>=3.5,<4.1`; newer functions would create accidental version assumptions.
  Date/Author: 2026-07-13 / Codex and project owner.
- Decision: Make catalog completeness, rather than a raw percentage, the release guard.
  Rationale: a percentage can conceal a missing high-frequency method; every relevant API needs an explicit user-facing
  status and rationale.
  Date/Author: 2026-07-13 / Codex and project owner.
- Decision: Keep loading, storing, orchestration, actions, and backend expansion outside v4.
  Rationale: they are not data transformations over caller-supplied DataFrames and would dilute the stated outcome.
  Date/Author: 2026-07-13 / Codex and project owner.
- Decision: Admit generators only after a schema-and-cardinality design gate.
  Rationale: generator functions change row counts and often output column shape; rendering them without an explicit
  IR contract would undermine validation and traceability.
  Date/Author: 2026-07-13 / Codex and project owner.

## Context and Orientation

Structure is a schema-first Python DSL that symbolically captures transforms, creates an intermediate representation,
and either runs a shared PySpark recipe online or emits readable PySpark source. `@raw` hooks are intentional opaque
boundaries for arbitrary user-owned PySpark. Compiler commands must remain Spark-free.

The current public DSL is exported through `src/structure/app/dsl/api/__init__.py`. Row-local expressions live in
`src/structure/app/dsl/model/expr/`, analytical helpers and rowset operations in
`src/structure/app/dsl/model/transforms/`, symbolic compilation in
`src/structure/app/compiler/symbolic_execution/`, and PySpark recipes/lowering in
`src/structure/app/target/pyspark/`. Capability profiles are in `src/structure/app/target/capabilities/`.

`docs/dev/Gaps.md` records current parity gaps and `docs/APIRef.md` is the public summary. V4 adds the detailed catalog
described in `docs/dev/design/V4TransformationApiCoverage.md`; it must be understandable without inspecting source.

For this plan, a transformation means a logical operation on caller-supplied DataFrames that returns another DataFrame
or a symbolic expression used to construct one. An action, such as `collect()` or `count()`, evaluates a DataFrame and
is not a transformation. Cardinality describes how an operation changes rows: it may preserve, filter, aggregate,
multiply, or expand them.

## Plan of Work

### Milestone 1: Build the coverage contract and inventory

Create a maintained local inventory of relevant public PySpark 3.5.x and 4.0.x Column methods, SQL functions, and
DataFrame transformation methods. Exclude readers, writers, sessions, catalog APIs, actions, UDF/UDTF APIs, and
streaming lifecycle methods, but list them as excluded categories in the public catalog so users do not mistake their
absence for an oversight.

Add `docs/reference/PySparkTransformationCoverage.md` as the human-readable catalog and a local structured source used
by tests. Every entry must identify PySpark names and aliases, Structure spelling or alternative, status, profile,
variant, type/nullability/cardinality contract, semantic notes, and evidence links. Add tests that verify the catalog
has one classification for every inventory item; verify supported entries map to a public helper or operation and link
to capability and parity evidence; verify no feature claims a target outside its capability profile.

Update `docs/dev/Gaps.md`, `docs/APIRef.md`, `docs/dev/specifications/UserStories.md`, and
`docs/reference/UserStories.md` to use the same vocabulary. Create a compact v4 source fixture and generated fixture
location under `res/testing/model/v4/` before admitting the first helper.

Run from the repository root:

    poetry run pytest -q tests/app/test_public_api_snapshot.py tests/specifications/compatibility

The milestone is complete when the catalog exposes every in-scope API's status without consulting source code and its
integrity tests fail when an inventory item is unclassified.

### Milestone 2: Close scalar and conditional-expression gaps

Add the remaining compiler-visible Column methods and high-value SQL function families in small, independently
releasable groups: bitwise operations; null-control and conditional functions; practical string predicates and
transformations; deterministic numeric functions; temporal extraction/conversion; hashes; and encoding. The exact
member list comes from the catalog and must be split further where type or version semantics differ.

For each group, add a typed constructor in `src/structure/app/dsl/model/expr/`, validate argument types and literal-only
parameters, record result type and nullability, and lower through the existing shared PySpark recipe mechanism. Add
capabilities for PySpark-4-only functions rather than using a generated code fallback. Do not expose aliases merely for
PySpark familiarity if one unambiguous Structure spelling already exists; list those aliases in the catalog.

For each group, add symbolic diagnostics, generated-code assertions, online/generated Spark parity rows including null
and invalid-input cases, Spark Connect evidence where claimed, API snapshot changes, and an example in the v4 fixture.

### Milestone 3: Close nested-value and declared-parser gaps

Implement struct mutation only through declared Structure schemas: `with_field` and `drop_fields` must produce an exact
struct result type, respect physical aliases, and reject an unknown result shape. Extend array and map coverage with
typed construction, append/prepend/insert/remove, compact, slicing, sorting, reversing, and map construction only when
element/key/value type and nullability can be represented.

Admit JSON and CSV conversions only where callers give a Structure `Schema` or another exact Structure type contract.
Use stable literal options rather than arbitrary dictionaries until option normalization has its own design. Do not add
Variant, XML, geospatial, binary, interval, or timestamp-without-time-zone behavior without first extending the public
type model and catalog; record them as deferred rather than type-erasing them.

The milestone is complete when nested helper outputs validate against their declared schema and examples prove both
online and generated PySpark use the same visible operation.

### Milestone 4: Close relational and analytical transformation gaps

Add rowset operations only where the schema and cardinality contract is explicit. Evaluate schema-compatible union,
intersection, subtraction, distinct/deduplication variants, ordering, limits, offsets, and sampling. Deterministic
operations may be admitted directly; operations whose result depends on unspecified partition order or random state
must require an explicit order/seed or be catalogued as deferred.

Finish advanced transformation work that builds on the existing analytical model: nearest as-of matching with a stated
tie/tolerance policy; exact percentile and stable approximate percentile forms; skewness, kurtosis, and mode only with
clear null and tie behavior; and corresponding window forms where Spark permits them. Do not add cost-based join
reordering: it changes source-visible execution choices and belongs to a separate optimizer design.

Update explain and traceability with each operation family and classify streaming legality without assuming ownership of
streaming sources or sinks. The milestone is complete when every admitted relational operation has a recorded
cardinality, output-schema proof, and parity evidence.

### Milestone 5: Run the generator cardinality design gate

Before coding `explode`, `posexplode`, `inline`, or outer variants, write a short design decision that specifies the
source selector, output-schema declaration, generated field names, null behavior, position/key/value shapes,
traceability, and streaming classification. Build a small prototype against arrays, maps, and arrays of structs.

Promote generators only if a transform step can declare its resulting Structure schema without dynamic aliases or hidden
columns and if generated/online behavior stays equivalent. Otherwise mark all generator variants deferred in the catalog
with a diagnostic that names `@raw` as the current escape hatch. Do not ship a half-typed `explode` API.

### Milestone 6: Close the release

Update the end-user Quick Reference and API reference, compatibility matrix, Gaps page, v4 fixture, generated output,
diagnostics, and troubleshooting guidance. Ensure each deferred or unsupported catalog item gives an actionable next
step. Update the release roadmap and move completed v4 implementation plans to `docs/dev/planning/done/`.

Run focused tests throughout, then from the repository root run:

    make build

The release is complete when no in-scope baseline API is unclassified, all supported catalog entries have current
evidence, and the full build passes.

## Concrete Steps

Work from the repository root.

1. Inspect `docs/dev/Gaps.md`, `docs/APIRef.md`, public exports, expression constructors, transform helpers, capability
   profiles, recipes, generated rendering tests, and integration target matrices.
2. Populate the local source inventory from the official PySpark 3.5.x and 4.0.x reference intersection. Preserve the
   source URL and version in catalog metadata, but do not fetch it during tests or builds.
3. Add catalog integrity tests before changing a status to supported.
4. For each scheduled family, write failing user-story/specification tests, then add typed symbolic capture, IR/recipe
   lowering, capability checks, diagnostics, rendering, online/generated parity, fixture examples, and public docs.
5. Run the focused family tests after every change and `make build` before closing a slice.

## Validation and Acceptance

Catalog acceptance:

- Every relevant PySpark 3.5.x/4.0.x transformation API appears exactly once or belongs to a documented excluded
  category.
- Every catalog entry has a visible status, PySpark spelling, and an actionable Structure alternative or rationale.
- Tests reject unclassified inventory APIs and unsupported target claims.

Feature acceptance:

- Supported APIs remain typed, symbolic, backend-capability checked, explainable, and readable in generated PySpark.
- Online and generated execution have equal schemas and rows for representative and null/edge-case inputs.
- A capability diagnostic fires before execution for profile or Spark Connect exclusions.
- Each relational operation records honest cardinality and output schema behavior.
- Sources, sinks, stores, orchestration, and actions remain caller-owned and out of scope.
- `make build` passes.

## Idempotence and Recovery

Catalog generation and validation are read-only with respect to external systems and safe to rerun. Every feature slice
is additive; if an API proves ambiguous, restore its catalog status to `deferred`, retain its rationale, and remove any
public export or generated snapshot rather than preserving partial behavior. If target evidence differs between 3.5.x
and 4.0.x, add a capability gate or keep the feature deferred; do not silently use the newer API.

## Interfaces and Dependencies

Use the existing public export layer, expression model, operation plans, capability provider, diagnostics registry,
shared PySpark recipe/lowering, explain/traceability, and test harness. Do not introduce a dependency that imports
PySpark during compiler-only commands, starts a SparkSession during catalog validation, or downloads documentation
during a build. The v4 catalog may use official Spark documentation as its maintained source, but it must remain a
checked-in repository artifact.
