# SearchDocuments Structured Streaming


Maintain this living ExecPlan according to `docs/dev/auto/Plans.md`. It records the Search streaming contract and
current migration gaps. [P09282601][execution-plan] owns the resumed feasibility, Structure extensions, integration,
and latency experiments for [I09282601 Search repeat-query latency][issue]. These are complementary plans, not
parallel implementation tracks: update this contract as the execution plan proves or rejects each requirement.

## Purpose / Big Picture


Allow callers to build one SearchDocuments transformation over incoming requests and fixed, caller-owned corpus,
index, score, feedback, and policy snapshots. The caller starts and manages the streaming query. Search should emit
one final ranked result set per accepted request, without rebuilding the entire Python transformation for every
request. Lower repeat-query latency is a hypothesis to measure, not a consequence of declaring streaming inputs.

## Surprises & Discoveries


V10 added useful support without admitting every stateful shape. Watermarks, event-time aggregates, bounded dedupe,
selected stream/static and bounded stream/stream joins, exact-schema streaming unions, and ordered state reporting
exist. The general composition rule still allows one stateful operation followed by stateless work, apart from a
narrow two-window aggregate sequence. Search needs more than that exception.

`StreamingStateStage.completion_window` is observational metadata, not an executable finalization mechanism.
`examples/streams/adoption.py:ArbitraryStateContract` validates declarations, not state execution. No named bounded
top-K runtime was found. Finite selected values implemented with `min_by`/`max_by` are not a top-K collection.

Search has changed since the original plan: `admit.py` and `overlap.py` no longer exist in `search_docs`.
`FilterOverlap.maximum_candidates` is 10,000; fusion uses `VectorIndexPolicy.maximum_candidates`; reranking uses
1,000 candidates and 100 results. The historical 1,000/100 candidate/overlap design is not the current scoring
contract. Do not restore those old limits as part of streaming migration.

The 185 compiler findings include propagated intermediate-output findings, not 185 independent defects. Categories
include 20 window-projection findings, 22 subset-duplicate findings, 16 unbounded aggregates, four `require_all`, two
`require_unique`, and stateful composition, joins, union, and selected-row restrictions. These counts describe the
reviewed checkout and default stage visibility, not a stable public contract.

## Context and Orientation


The public composition is `examples/search/transforms/searching/search_docs/SearchDocuments.py`: filtering,
vectorization, scoring, retrieval, fusion, and reranking. `retrieve.py` contains query/request timestamp matching and
some paired ten-minute watermarks; a matching timestamp is not proof that all candidates for that query have arrived.
`fuse.py` contains lexical/vector ranking, uniqueness checks, reciprocal-rank fusion, and three conditional eager
checkpoints. `rerank.py` contains feedback selection, per-query maximum normalization, and final ranking.

`examples/search/transforms/filtering/FilterOverlap.py` has another query-dependent ranking boundary. Inspect the
online filtering, lexical scoring, and vectorization dependencies too; fixing the final ranker alone is insufficient.

Streaming admission lives in
`src/structure/plugin/pyspark/compiler/commands/ClassifyStreamingCompatibility.py`. State metadata lives in
`src/structure/core/compiler/compileability/streaming_compatibility/model/StreamingStateStage.py`. The current support
ledger is `src/structure/plugin/pyspark/resources/pyspark-streaming-api-coverage.json`. V10 release evidence records
ordinary-PySpark restart tests; those tests skip Connect and do not prove Search streaming support.

## Plan of Work


### 1. Preserve and make the request contract explicit


Keep `SearchQuery.requested_at` and matching `SearchRequest.requested_at` consistent through query-dependent stages.
Retain query identity, experiment, user-band, and all other scope keys used by the current ranking/cache contract.
Treat fixed corpus/index/cache/feedback/policy inputs as caller-owned snapshots for the whole run. Policy changes
are independent of corpus changes; any effective snapshot change requires a new run and checkpoint identity.

The caller selects lateness tolerance and a finite completion contract; do not silently reuse hard-coded ten-minute
watermarks as an interactive latency guarantee. Define completion for missing query/request pairs and zero-candidate
queries as well as successful queries. An empty result set must not be confused with a request still being processed.
Completion observability must preserve the existing `results` schema and be explicit in the caller handoff.

### 2. Prove finite ranking and validation before migration


Top-K means retaining at most K candidate records per grouping/window, with deterministic ordering and explicit
additional validation metadata. It does not mean collecting every candidate and slicing the output. Prove limits for
score-aggregation and duplicate-validation state separately; bounded top-K does not make the entire graph bounded.

Use only finalized scores when dropping candidates unless an equivalence proof covers changing scores. Preserve
fusion ranks, late contributions, per-query normalization, deterministic ties, null handling, and duplicate errors.
Do not replace `require_unique` with silent deduplication. Snapshot-only checks can move to caller-controlled
preparation; request-specific checks need equivalent bounded execution before final output.

### 3. Extend Structure's transformation contracts


Implement typed bounded ranking and completion only after P09282601's prototype passes. Capture event time,
watermark source, scope/grouping, completion rule, candidate bounds, ordering, validation-state bounds, output mode,
and permitted following stages. Add precise compiler admission instead of broadly allowing analytic windows or all
chained state. Preserve source traceability, generated/online parity, and corrective diagnostics with remedies.

### 4. Refactor the current Search graph


Separate fixed-input transformations from request-dependent ones. Convert cached/online score branches to compatible
streaming shapes before exact-schema unions. Replace analytic ranking and business-key aggregates only with proven
bounded equivalents. Every stream/stream join must retain compatible watermarks and finite event-time bounds.
Precompute only feedback work independent of the request; query-text-dependent feedback remains request-dependent.

Keep one public SearchDocuments and current declared stage outputs/aliases. Preserve `streaming=False` by default
and `FuseDocuments(materialize=~streaming)`. Batch checkpoint behavior remains unchanged. The streaming branch must
contain neither eager batch checkpoints nor compiler temp-view boundaries. `streaming=True` remains a migration
selection, not evidence that unsupported streaming code may bypass admission.

### 5. Prove completion, recovery, and latency


Use caller-owned isolated sources, sinks, and recovery checkpoints. Test online/generated results on ordinary Spark
3.5/4.0, including duplicate/late events, interleaved queries, empty answers, failure and replay, and snapshot mismatch.
Test an idle stream without artificially advancing time in the measured latency. Event-time watermarks can stop when
input stops; a trigger interval alone does not establish a wall-clock completion deadline.

Treat batch execution inside `foreachBatch` as a comparison, not native streaming implementation. Use available-now
runs for backlog/restart evidence and a long-running query for repeat-request latency. Caller-owned lifecycle and
storage are required in both. Leave Connect gated until its specific execution and recovery lane passes.

## Validation and Acceptance


Promotion requires a compiler-compatible Search streaming graph and live proof, not just streaming-shaped inputs.
No unsafe ranking, unbounded dedupe, unsupported assertion, or unproven stateful chain may be hidden by a switch.
Generated transformations must not own reading, writing, query lifecycle, or snapshot materialization.

An accepted request yields one final answer with batch-equivalent ranks, schema, UDF behavior, and validation under
the declared finite-input/lateness contract. Demonstrate completion, bounded resources, no revised final results, and
recovery with the same snapshots. Quantify per-request latency independently from throughput; keep I09282601 open
if the implementation is correct but does not improve repeat-query latency.

## Idempotence and Recovery


Use unique test-owned paths and query names. Stop only test-owned queries and clean only their resources. Reuse a
checkpoint deliberately only in restart tests with unchanged state schema and snapshots. Failed prototypes remain
gated; never replace reliable batch protection with an unproven streaming path.
