# Admit a bounded chained stateful streaming shape

This ExecPlan is a living document maintained according to `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as work proceeds. This file is the implementation handoff; the plan's creation does not implement or promote the feature.

## Purpose / Big Picture

After implementation, a Structure user can express a streaming transform that removes duplicate events within a watermark and then counts the remaining events in event-time windows. They can see the two stateful operations, their separate row and state-size limits, and the transform's memory policy in compileability and explain output. On an admitted ordinary PySpark target, the online transform and generated module produce the same result, and a caller-managed query resumes from its checkpoint. A runnable example and live tests must demonstrate these outcomes before documentation claims support.

The first new shape is exactly watermarked `drop_duplicates_within_watermark(...)` followed by one watermarked `group_by(...window(...))` aggregate in Append output mode. The existing exact two-stage event-time window aggregation remains supported. These are two specifically admitted pairs, not a general claim that arbitrary stateful operators can be chained. Row-based `transform_with_state` and Pandas-based `transform_with_state_in_pandas` are separate work in `docs/dev/planning/P10042603.V11-transform-with-state.plan.md` and `docs/dev/planning/P10042604.V11-transform-with-state-in-pandas.plan.md`; completing either does not make processor chains part of this plan. Joins, processor chains, reversed dedupe/window order, a third stateful operation, and other pairs remain design-gated.

The caller supplies the streaming input, output sink, query, trigger, checkpoint, and recovery policy. Structure compiles a transformed streaming DataFrame and exposes a caller-attached budget guard; it does not start or own the query.

## Surprises & Discoveries

- Observation: `group_by(...)` records grouping intent during a step method, but the aggregate operation is finalized after the method returns. A `budget(...)` call immediately after `group_by(...)` therefore needs an explicit pending-aggregate attachment; looking only at the last completed operation would attach it to the wrong operator. Evidence: `src/structure/plugin/pyspark/dsl/operations_api.py` and `src/structure/plugin/pyspark/symbolic_execution/commands/CapturePySparkStep.py`.
- Observation: The current classifier already tracks stateful operations and emits `STREAM-E0801` for additional operations, except for the exact two-window exception. The rejected `StreamingDedupeThenAggregate` fixture gives a before/after compiler example. Evidence: `src/structure/plugin/pyspark/compiler/commands/ClassifyStreamingCompatibility.py` and `tests/specifications/streaming-compatibility/test_v1_streaming_compatibility.py`.
- Observation: A configured RocksDB memory value is not necessarily an active limit. The Spark bounded-memory switch must be enabled, and its limit is a soft, executor-wide pool rather than a per-operator cap. Spark's `stateOperators[*].numRowsTotal` can be zero when row tracking is disabled. Runtime logic must check these conditions rather than treating a configuration value or zero count as enforcement. Evidence to retain in implementation notes: pinned target documentation and live progress/configuration output for each claimed profile.
- Observation: The repository currently has ordinary PySpark 3.5 and 4.0 integration paths but no ready 4.1 lane. A 4.1 support claim requires its own runnable lane and evidence; a skipped test is not evidence. Evidence: `infra/compose/`, `Makefile`, and `docs/dev/planning/P10042603.V11-transform-with-state.plan.md`.
- Observation: PySpark 3.5 exposes `StreamingQueryProgress.json` as a string property, not a method; the listener wraps it in a Python progress object. The guard must accept both method and property forms. Evidence: the PySpark 3.5 worker source and successful integration run.
- Observation: The existing worker could run tests only after Python and JVM temporary directories were redirected to the writable integration mount. PySpark 4.0 also required running from that mount because its artifact directory is relative to the current directory. No Docker data was pruned or removed.
- Observation: Append-mode event-time windows require another input batch after Spark advances the watermark to emit a closed window. The restart fixture replays the same event ID across the checkpoint boundary and confirms one deduplicated count in online and generated modes.

## Decision Log

- Decision: Admit only the new watermarked dedupe then event-time window aggregate pair, alongside the existing exact two-window pair. Require Append mode and positive evidence per ordinary PySpark profile. Rationale: one validated pair is a useful feature without implying that all Spark stateful combinations, modes, or versions work. Date/Author: 2026-10-04 / User and Codex.
- Decision: Name the checking option `state_budget_checking`, with `off`, `compile_time_check`, `require_declaration`, and `declaration_and_runtime`; default to `compile_time_check`. Rationale: the names describe four different commitments without changing behavior according to detected data volume. `off` disables only budget checks; it never disables composition, type, watermark, output-mode, or target checks. Date/Author: 2026-10-04 / User and Codex.
- Decision: Use one public `budget(...)` helper in two contexts. `memory_budget = budget(memory_source=..., fallback_mb=...)` is a transform-class declaration that overrides a project memory default; `budget(max_rows=..., max_state_bytes=...)` immediately follows the stateful helper inside a step method and applies to that specific operation. Rationale: `budget` reads clearly beside the operation it limits, while memory policy has a distinct transform-wide scope. Do not use `stage_budget`, `dedupe_state`, or `window_state` declarations. Date/Author: 2026-10-04 / User and Codex.
- Decision: Project memory defaults apply first, then the transform's `memory_budget` overrides them. `memory_source="spark"` is a declaration even if it later cannot resolve; unresolved active Spark memory is a runtime preflight error. `memory_source="prefer_spark"` uses an active Spark RocksDB pool first and an explicit `fallback_mb` only when no active pool exists. Rationale: author intent and the source of a memory figure must remain visible. Date/Author: 2026-10-04 / User and Codex.
- Decision: `require_declaration` accepts a complete chain memory declaration or complete per-operator limits for every stateful operation; partial per-operator limits without chain memory are insufficient. Missing declarations fail compilation. Rationale: a declaration mode must not silently leave one operator unbounded. Date/Author: 2026-10-04 / User and Codex.
- Decision: In `declaration_and_runtime`, the caller attaches a guard to its query for declared per-operator limits; an active Spark bounded RocksDB pool can provide the memory control. If `prefer_spark` falls back because no active pool exists, continue with an explicit warning that runtime memory enforcement is absent. Rationale: Spark's pool is soft and node-wide, while the fallback is a planning limit, not a Spark setting. Date/Author: 2026-10-04 / User and Codex.
- Decision: Runtime progress can detect a limit only after Spark reports a completed micro-batch. The guard must stop the caller's query on an observed breach and expose a typed failure, but must not promise a hard within-batch cap. Rationale: progress metrics are observations, not admission controls. Date/Author: 2026-10-04 / Codex, implementing the agreed caller-attached guard boundary.

## Context and Orientation

Structure's typed `@transform(streaming=True)` method is executed symbolically to record PySpark operations. The PySpark plugin compiles one recipe used both by online execution and generated code. `src/structure/plugin/pyspark/dsl/operations_api.py` contains `watermark`, `drop_duplicates_within_watermark`, and `group_by`. `src/structure/plugin/pyspark/symbolic_execution/commands/CapturePySparkStep.py` completes an aggregate after the method returns. `src/structure/plugin/pyspark/compiler/commands/ClassifyStreamingCompatibility.py` checks whether streaming operations may be composed and reports findings through `StreamingReport` and `StreamingStateStage`. `src/structure/plugin/pyspark/resources/runtime.py.template` supplies the generated runtime's `TransformResult`; the online result must expose the same caller-facing metadata.

A watermark tells Spark how late an event may arrive before event-time state can be retired. Watermarked duplicate removal retains seen keys for that interval. A window aggregate retains counts by time bucket until its watermark allows final output. Both operations keep state, so chaining them needs an explicit rule for event time, retention, output, memory, and restart. The current exception is one watermarked event-time window aggregate followed by stateless operations and one second window aggregate over `window_time` from the first window. See `docs/dev/specifications/V9StreamingDesignGatedFeatures.spec.md` and the retained V11 gate in `docs/dev/design/V11RetainedV9DesignGates.design.md`.

A state budget is a declared upper expectation and optional observed-progress limit; it is not proof that Spark will never use more memory. `max_rows` is the number of state rows for one Spark state operator. `max_state_bytes` is that operator's reported memory bytes. `memory_budget` is the transform's expected memory policy for the chain. `fallback_mb` uses 1,048,576 bytes per unit for planning when no active bounded Spark RocksDB memory pool is available; use that conversion consistently in code and documentation. A Spark memory pool is shared across operators on an executor and is not interchangeable with `max_state_bytes`.

Configuration lives in `src/structure/core/configuration/model/StructureConfig.py`, `src/structure/core/configuration/logic/StructureConfigDefaults.py`, `StructureConfigBuilder.py`, and `StructureConfigValidator.py` in the same directory. Runtime configuration can be read through `src/structure/core/runtime/session/model/StructureSession.py`. Keep the PySpark-specific resolution in the PySpark plugin or a narrow adapter so Core has no PySpark import. The compiler options fingerprint must include budget configuration so cached plans cannot reuse a different policy.

The user reference and gate ledgers are `docs/api/Streaming.api.md`, `docs/reference/Streaming.ref.md`, `docs/dev/gated/Streaming.gates.md`, `docs/dev/specifications/V11RetainedV9DesignGates.spec.md`, `docs/dev/design/V11RetainedV9DesignGates.design.md`, `src/structure/plugin/pyspark/resources/pyspark-streaming-api-coverage.json`, and `pyspark-structured-streaming-coverage.json` in the same resources directory. `docs/dev/Testing.md` describes unit and live PySpark testing. Integration services are under `infra/compose/`.

Separate budget-mode checks from composition checks. `compile_time_check` validates any declared limits and reports an honest missing-budget warning, with an additional bounded-memory warning only when the runtime configuration is known and lacks an active bounded pool. An active Spark pool supplies runtime memory control; the caller attaches a guard for any declared per-operator limits. The explicit exception is `prefer_spark` without an active pool: use its fallback and allow the query with a warning that memory is not runtime-enforced. Define “complete per-operator limits” as both `max_rows` and `max_state_bytes` for each operator when no chain memory declaration exists. If a chain memory declaration exists, any operator limits are optional but an attached guard observes those supplied. Do not weaken this rule without an updated Decision Log entry and tests.

## Validation and Acceptance

On each claimed target, a caller starts an Append query from a fresh file stream, sends two records with the same event ID and one distinct ID in the same window, advances the watermark, and receives a single final window with count two. The caller stops the query, resumes from its checkpoint, supplies further records, and gets counts consistent with dedupe state and watermark retirement. Online and generated transforms produce the same schema and results; input ordering must not be assumed. A late event must follow the documented watermark policy. The query and checkpoint remain caller-owned throughout.

The compiler identifies both stateful operations by step and operation, shows each budget beside its operation, and reports the effective memory policy. The four modes have distinct verified behavior: `off` skips budget-specific requirements; `compile_time_check` validates declarations without requiring them; `require_declaration` fails for missing coverage; `declaration_and_runtime` requires the declaration and observes declared per-operator limits through a caller-attached guard while recognizing an active Spark pool as memory control. All modes still reject illegal chains, invalid output modes, and unsupported targets. An unresolved `spark` memory source fails session preflight. A `prefer_spark` fallback emits the agreed warning and is permitted even though memory has no runtime enforcement. A guard breach stops the attached query and yields a typed, actionable error after progress reports the breach; disabled row tracking cannot produce a false pass.

The public support statement lists only profiles with successful live chain execution, online/generated parity, and same-checkpoint restart. It names the exact dedupe-to-window shape and preserves the previously admitted two-window shape. The broad gate and processor-chain exclusions remain visible. `make build` passes at completion. ## Idempotence and Recovery

Compiler and code-generation operations must be deterministic on repeated runs; budget metadata cannot mutate the user's SparkSession or source DataFrame. A caller may attach one guard to its own query once; repeated attachment returns the same attachment or a clear duplicate-attachment error without registering two observers. `close()` may be called repeatedly. Tests use fresh temporary input and checkpoint paths, except for the deliberate same-checkpoint restart within one test. Stop queries in `finally` and clean up only test-owned resources.

If a live target fails the Spark proof, retain its gate, record the exact failure and runtime version, and continue implementing only the proven profile subset. If operator-to-progress mapping cannot be verified, leave runtime operator enforcement unavailable for that target and do not claim `declaration_and_runtime` support there. Do not rewrite or delete a caller's checkpoint when a query fails; Spark state schema, watermark, state-store provider, and partition settings may constrain restart compatibility. Expose the failing setting and require the caller to choose a compatible restart or a new checkpoint.

    @transform(streaming=True)
    class EventSummary(Transform):
        events = input(RawEvent, streaming=True)
        summary = output(WindowSummary)
        memory_budget = budget(memory_source="prefer_spark", fallback_mb=768)

        @step(input=events, output=summary)
        def summarize(self, row: RawEvent) -> WindowSummary:
            watermark(row.event_time, delay="10 minutes")
            drop_duplicates_within_watermark(row.event_id)

## Interfaces and Dependencies

The public `budget(...)` helper has two accepted keyword sets: `budget(*, memory_source: str, fallback_mb: int | None = None)` for a transform-class `memory_budget` declaration, and `budget(*, max_rows: int | None = None, max_state_bytes: int | None = None)` within a step method. An operator call must supply at least one limit; the mode's completeness rule decides whether more is required. Do not expose separate `dedupe_state`, `window_state`, or `stage_budget` interfaces. Preserve a stable step/operation identifier across captured plan, explain, online result, generated result, and Spark progress mapping. Keep public declarations immutable and serializable.

Add `state_budget_checking: Literal["off", "compile_time_check", "require_declaration", "declaration_and_runtime"]` to Structure configuration with `compile_time_check` default. Add an optional project memory default with the same source semantics as class `memory_budget`. Compile-time diagnostics must name the relevant step, operation, missing field or invalid value, and a remedy. Session preflight resolves Spark configuration but does not mutate it. The caller-facing guard API is `session.state_budget_guard(result).attach(query)` returning a closeable handle; the handle reports `StateBudgetExceeded` for a breached observed limit. If the existing session/result API requires a nearby name, preserve these ownership and behavior requirements and record the exact final signature in this plan before documentation promotion.

Use the repository's existing PySpark plugin recipe, classifier, online executor, generated renderer, and `TransformResult`; do not add an external dependency or require PySpark at compile time. Live tests use Docker Compose backends described in `docs/dev/Testing.md`; the 4.1 lane may be supplied by the ongoing V11 adoption work. This plan does not depend on completion of the row or Pandas state processor plans, and neither processor becomes chainable through this work.
