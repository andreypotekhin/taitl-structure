# Search integration lineage and runtime


## Purpose


Keep the tiny Search integration fixtures from producing enormous Spark logical plans, and remove repeated
generation and collection work. Preserve sentence-splitting UDFs, online/generated parity, and public boundary
validation. Provide reusable test infrastructure and an explicit, constructor-controlled fusion boundary without
changing the meaning of cache, persist, or checkpoint.

## Context and Orientation


`tests/integration/pyspark/search/test_search.py` recompiles 54 transforms in five tests. A fresh source-only pass
rendered 135 files (4.38 million characters) in 21.49 seconds. The shared runtime fixtures and helpers live under
`tests/integration/pyspark/`. Existing `cache_frames` persists frames but does not truncate their logical plans.
`docs/dev/issues/I09272602/Memory-evidence.md` reproduces exponential plan expansion on two rows in plain Spark;
checkpointing truncates lineage whereas cache/persist does not.

Current SearchDocuments has 91 steps and 77 exposed stage outputs. Runtime output validation analyzes these
outputs even when the test requests only public results. Stage access remains enabled by default in the library;
Search parity tests may explicitly disable it in both compilation and execution. Dedicated stage-access tests
must retain coverage. The current release evidence still records heap exhaustion in the text-fixture and
multi-query reranking tests on Spark 3.5. SearchDocuments does not contain ReduceSimilarityScores.

## Plan of Work


First add test-scoped snapshot infrastructure with eager, explicit boundaries and deterministic cleanup.
Use a shared-volume Parquet round trip across backend variants so Connect 3.5 does not require unsupported
checkpoint APIs. Snapshots are test orchestration, not a new production DSL contract. Preserve column types
and values; Parquet may widen nullability, which must not be used to assert nullability contracts.

Reuse generated source maps within a module, keyed by the complete explicit compilation request and backend
options. Continue isolating imports per test. Reuse already collected ordered rows for unordered assertions,
without replacing explicit Spark ordering with Python ordering. Add non-live tests for cache isolation and reuse.

Then place snapshots at offline preparation boundaries in Search: chunking, indexing, analytics, and scoring
results reused by later transforms. Disable unneeded stage exposure explicitly for this test module in both
online configuration and generated artifacts. Keep the full SearchDocuments invocation and all expected results.

The second milestone adds `FuseDocuments.materialize=parameter(False)` and a final identity-return step that calls
`checkpoint(eager=True)` when enabled. `SearchDocuments.streaming=parameter(False)` forwards `materialize=~streaming`.
`ParameterDeclaration` represents the deferred inverse; `ComposeTransformGraph` resolves it using the enclosing
invocation's bound values. Session compilation and artifact keys preserve constructor scalar parameters. Test this
with direct, nested, default, overridden, and negated bindings, distinct specialization fingerprints, and streaming
frame rejection. Keep runtime frames out of compiler cache keys.

Finally run individually bounded live reproductions. If an internal Search graph still expands, use the last
completed phase to locate it and record evidence before choosing a semantic rewrite. Do not disguise a failing
end-to-end transform by replacing it with disconnected component assertions or by only increasing driver heap.

## Surprises and Discoveries


Earlier Connect UDF schema and closure fixes are present. Connect intermediate validation already defaults off.
Streaming tests already skip unsupported Connect variants at collection. These are not missing fixes to repeat.
The current slowdown includes newly exposed intermediate stage schemas as well as growing upstream lineage.

The first snapshot-enabled reranking run still failed on Spark 3.5 with the default 1 GiB driver after 131.85 seconds
(113.12 seconds in the test body). All chunking/index snapshots completed in 0.27–2.18 seconds each. The first logged
OOM was in `SparkListenerSQLExecutionStart.toString`, building diagnostic strings on the app-status listener thread.
This exposes a second memory amplifier: Spark permits nearly 2 GiB of plan text by default, even with the UI disabled.
Spark's configuration documentation recommends lowering `spark.sql.maxPlanStringLength` to about 8k for this failure.

The capped 1 GiB retry still failed in closure serialization after 163.04 seconds; the cap is diagnostic hygiene,
not a lineage remedy. An uncapped 3 GiB comparison lost its driver after 173.60 seconds. Input snapshots alone
are insufficient: the internal fused-candidate relation must be materialized before reranking fans out.

Connect exposed an optimizer regression: projection-union fusion emitted `call` for `array`, which now belongs to
`transform_expression`. Corrected the recipe and added render/evaluation coverage. Its subsequent run reached the
sentence UDF and exposed an older image's missing `/workspace` Python path. The checked-in runner now supplies it.
The next Connect run completed all preparation and scoring snapshots, then exposed stale relation qualifiers in the
optimizer's final projection: exploded fields no longer belong to the original `document_similarity_pair` alias.
Retarget both the step and result projections to the generator's scope; regression tests cover online evaluation and
rendered field references. This keeps the optimization enabled rather than restoring costly intermediate validation.

Constructor parameters were discarded by StructureSession's class-only compilation and by nested composed-graph
authoring. Preserve invocations through authoring, propagate bound scalar values recursively, and distinguish
non-default parameter bindings in artifact keys and fingerprints. Runtime DataFrames must never enter cache keys.

The isolated checkpointed Spark 3.5 reranking run completed both execution modes with a 1 GiB driver: online
construction 74.63 seconds, generated construction 67.46 seconds, collections 0.91 and 0.36 seconds. Parity passed,
then the expected-three-results assertion found only two. The cached-score fixture named `all-scoring-targets-v1`
without supplying matching targets; current scope validation correctly rejected that cache. Supply the corresponding
targets explicitly rather than weaken the three-result assertion.
The scoped verification passed on classic Spark 3.5 in 181.41 seconds (162.90-second body) and Connect 4.0 in
83.59 seconds (71.50-second body). Connect construction took 33.24 and 27.93 seconds; collection took 0.61 and 0.26
seconds. The original three-result assertion and top-ranked document IDs remain unchanged.

After the optimizer repair, the text-fixture test reached generated vector similarity and exposed a missing
`ParagraphVectorCandidate` entry in its schema fixture catalog. The generated ranker imports that schema even when
only document candidates are consumed. Restore the catalog entry; do not replace the generated assertion with online
execution or suppress the missing-module error. Declare it after `ParagraphVectorScore`, its parent. A Spark-free
regression compiles the ranker and imports all its generated schema dependencies with test types (0.22 seconds).
The repaired Connect 4.0 text-fixture test passes in 47.13 seconds, with a 36.34-second body.
The same complete text-fixture case passes on classic Spark 3.5 in 61.74 seconds, with a 42.70-second body.
The combined Connect 4.0 Search module passes all seven tests in 139.34 seconds. Initial shared-source fixture setup
takes 7.15 seconds; later tests using that fixture need only 0.05–0.06 seconds of setup. This verifies reuse across
tests without retaining Spark sessions, generated imports, or temporary snapshots across their fixture boundaries.

The final native Connect 4.0 checkpoint probe passed in 21.42 seconds (19.77-second setup, 0.57-second body), using
runner-owned server-startup checkpoint storage. It proves schema/row preservation, a `LogicalRDD` plan without the
parent `Range`, and readability after the source view is dropped.

## Decision Log


2026-09-25: Keep library stage-output defaults and materialization capabilities unchanged. Use explicit test
configuration and eager offline snapshots first; do not remove user-required sentence UDFs.

2026-09-25: Do not touch the user's existing edits to release evidence, stage-output implementation, or All.

2026-09-25: Bound diagnostic plan text to 8192 characters and use simple UI explain output in shared integration
sessions (and Connect server startup). This limits diagnostics, not validation or relational semantics. Measure it
separately from the already-running 3 GiB comparison; increasing heap alone is not the remedy.

2026-09-25 (user): Keep one SearchDocuments component. Put a dedicated materialization step inside FuseDocuments,
selected by a constructor argument. Do not expose an additional materialized stage on SearchDocuments. Use the
supported identity return `return candidate`.

2026-09-25 (user refinement): FuseDocuments has only `materialize=False`; it does not receive a streaming flag.
SearchDocuments declares `streaming=parameter(False)` and supplies `materialize=~streaming`. Python has no `!`
operator, and `not streaming` would eagerly coerce the declaration, so Boolean parameter negation must be deferred
until composed invocation binding. Reject eager truth testing of declarations and non-Boolean negation values.
The dedicated FuseDocuments step records an eager reliable checkpoint only when materialize resolves to true.
Existing input streaming declarations and compatibility diagnostics remain authoritative;
the scalar switch does not reclassify a relation or make the full Search graph stream-compatible. This avoids
introducing a separate parameterized-input-declaration API. Actual streaming DataFrames cannot be checkpointed.

2026-09-25: Retain caller-owned checkpoint storage. Configure classic test sessions with unique shared-volume
directories. Spark Connect requires `spark.checkpoint.dir` at server startup, not session configuration. Admit
only the reliable-checkpoint capability for Connect 4.0 after its public API probe passes; Connect 3.5 stays gated.

2026-09-25: Exclude only the checkpoint-dependent full document-search case on Connect 3.5. Its shared source fixture
omits SearchDocuments, its experimental subclass, and SearchFields (which delegates to SearchDocuments); other
Search cases remain eligible. Do not falsely claim Spark 3.5 supports the new reliable boundary.
