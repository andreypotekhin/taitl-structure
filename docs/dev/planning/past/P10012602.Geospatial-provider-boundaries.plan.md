# Establish Geospatial Provider Boundaries

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` sections as work proceeds. It follows `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

Give a PySpark user one honest path for native Spark spatial values and equally explicit paths for external spatial
providers. Native PySpark `st_*` helpers will be a future PySpark 4.1+ target slice. Sedona, Mosaic, and other
Geometry providers will use their own namespaces and explicitly selected provider scope. This plan delivers the
design, public guidance, and target gates needed before either runtime slice is promoted.

## Surprises & Discoveries

- Observation: standard WKB does not retain SRID. Spark accepts a separate SRID when decoding a native Geometry, while
  Sedona also exposes EWKB-specific functions.
  Evidence: Spark and Sedona public ST documentation reviewed on 2026-10-01.

- Observation: the existing Geometry runtime chooses one installed provider late and labels Sedona expressions as
  provider-neutral. That cannot safely model a native-plus-provider application.
  Evidence: `src/structure/plugin/pyspark/geo/runtime.py` and `dsl/geo.py`.

## Decision Log

- Decision: reserve no-prefix `st_*` helpers for native PySpark Geometry/Geography, beginning with the 4.1 target.
  Rationale: native PySpark users retain the names they already know and no `native_*` namespace is needed.
  Date/Author: 2026-10-01 / user and Codex.

- Decision: expose every external provider through a namespace with its documented function names, such as
  `sedona.st_geomfromwkt` and `sedona.st_asewkb`.
  Rationale: a provider-specific API is easy to search and gives Sedona, Mosaic, H3, and S2 equal status.
  Date/Author: 2026-10-01 / user and Codex.

- Decision: resolve `geo_provider` by step, then transform, then application configuration; infer native only on a
  qualifying target. A provider namespace must match the effective scope.
  Rationale: physical schema, dependency setup, and renderer selection must agree even when the function name already
  identifies a provider.
  Date/Author: 2026-10-01 / user and Codex.

- Decision: direct Geometry/Geography values never cross dialects. An ordinary declared `binary()` field is the only
  handoff boundary. Extended binary codecs remain caller-owned and are not portable claims.
  Rationale: Binary permits deliberate integration without pretending arbitrary WKB or EWKB is universally compatible.
  Date/Author: 2026-10-01 / user and Codex.

- Decision: P093 delivers documentation and target gates only. Native 4.1 and external-provider runtime support need
  their own capability, generated/online parity, and live target evidence.
  Rationale: P093's supported baseline is PySpark `>=3.5,<4.1`.
  Date/Author: 2026-10-01 / user and Codex.

## Outcomes & Retrospective

The target-gated contract is documented and cross-linked from the relevant API and public indexes. Focused checks and
`make build` pass. Runtime adoption remains intentionally unstarted until its profile/provider evidence is available.

## Context and Orientation

`docs/dev/planning/past/P09302601.PySpark-SQL-baseline-gap-closeout.plan.md` owns default-baseline closeout. Its Milestone 5
delegates geospatial target and provider boundaries to this plan. `docs/dev/design/PySparkSQLBoundaryContracts.design.md`
records why raw scalar SQL and other non-symbolic behavior remain outside the DSL.

The current PySpark Geometry implementation is experimental. It resolves a single runtime provider and exposes WKT
and predicate helpers as though they were provider-neutral. This plan replaces that public story; it does not ship the
future runtime API. The specification names the future API so later implementation work does not need to reopen the
design.

## Plan of Work

Create a developer-facing geospatial design and specification. Define native root helpers, provider namespaces,
Geometry/Geography dialect and SRID facts, scope precedence, capability evidence, collision-free provider rendering,
and Binary handoff limits. The specification must state that external provider functions preserve their provider's
signature only after a typed capability entry and evidence prove it.

Create a concise background page and a public Geospatial reference. The reference must distinguish current support from
planned native 4.1 and provider adoption, explain `geo_provider` placement, and link users to native PySpark or a raw
boundary when no certified provider is available. Add one recipe that shows a Sedona EWKB value moving through an
ordinary Binary field and warns that the receiving codec is application-owned.

Replace the obsolete provider-neutral Geometry language in the Schema and Expressions APIs with short, local status
tables and links to the new reference. Add narrow cross-links from Configuration, Transform, API, Reference, Quick
Reference, and Recipes indexes. Update the catalog, gap register, function gates, and 4.1 adoption statements so
geospatial work cannot be mistaken for default-baseline support.

## Milestones

### Milestone 1: Contract and documentation lane

Add the five geospatial documents and their indexes. A reader must be able to determine whether a native `st_*`, a
provider namespace call, a declared spatial field, or a Binary handoff is supported without reading source code.

### Milestone 2: Baseline and target reconciliation

Update P093, its boundary design, the gap register, catalog, and capability references. The default `>=3.5,<4.1`
profile must make no native-geospatial support claim; native Geometry/Geography belongs to the 4.1 adoption record.

### Milestone 3: Documentation verification

Add or extend focused checks for links and status consistency. Run the documentation/ledger checks and `make build`.
Record any unavailable runtime evidence rather than upgrading a status.

## Validation and Acceptance

Acceptance requires a reader to find the Geospatial reference from both the public Reference index and API reference;
find the Binary bridge recipe from Recipes; and find the target-gated status from P093 and the gap register. The docs
must state that native `st_*` is 4.1+ only, external functions are namespaced and scope-matched, and Binary codecs are
not portability guarantees. Documentation checks and `make build` must pass.

## Idempotence and Recovery

This work changes documentation and ledgers only. Repeat edits by reconciling status wording before changing a row. If
a provider fact is not evidenced, keep it target- or design-gated and direct users to an explicit native boundary.

## Interfaces and Dependencies

Later runtime work will add `geo_provider` to `[tool.structure.plugin.pyspark]`, `@transform`, and `@step`, and will
provide native root helpers plus provider namespace modules. This plan does not add those executable interfaces. H3 and
S2 remain provider-specific cell-index extensions rather than `geo_provider` Geometry/Geography backends.
