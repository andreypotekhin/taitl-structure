# Admit row `transform_with_state` and design typed state parity

This ExecPlan is a living document maintained according to `docs/dev/auto/Plans.md`. Keep `Progress`,
`Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as work proceeds. This document is
self-contained: it records the present implementation, the remaining admission evidence, the compatibility-ledger
split, the documentation reconciliation, and the accepted direction for the next typed state contract.

## Purpose / Big Picture

Structure already compiles and runs row-based `transform_with_state(...)` on ordinary PySpark 4.1, but public and
development documentation still groups it with unfinished arbitrary-state APIs and calls the whole family
design-gated. After this plan, a user can rely on a precise support claim for the row API, including every admitted
output and time mode, without implying support for the separately developed Pandas APIs or Scala-only Dataset APIs.
The machine-readable compatibility ledger, public documentation, design, specification, tests, and live evidence will
all describe the same boundary.

The plan also saves the accepted design for full typed processor parity. A Structure processor will declare named
state handles as annotated class attributes, closely matching how native PySpark examples keep handles on `self`.
That later API is intentionally a breaking replacement for the current single-`ValueState` callback contract. It will
not interpret old generic positions polymorphically and will not duplicate typed state declarations at the
`transform_with_state(...)` call. Users who need native Python constructs or PySpark features outside the typed model
will continue to bind an external stateful processor; Structure will treat its body and state topology as opaque.

The visible proof is fourfold. Online and generated execution produce the same rows for admitted modes on the pinned
ordinary PySpark 4.1 lane. An event-time timer fires after a watermark advances. The compatibility ledger has separate
rows for the row, Pandas, legacy Pandas, and unavailable Dataset families. A new typed-parity design document contains
the attribute API, lifecycle, checkpoint, migration, and implementation order needed for a later coding plan.

## Decision Log

- Decision: Use processor attributes, previously discussed as option 2, for the future typed state API.
  Rationale: It is concise, resembles native PySpark processors, makes migration mechanical, and gives callbacks
  direct `self.<state>` access without a growing list of state parameters.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Replace `StateProcessor[Input, Key, State, Output]` with
  `StateProcessor[Input, Key, Output]` when typed parity is implemented.
  Rationale: Persisted state belongs in named class annotations. Retaining a state generic would create two competing
  sources of truth and would preserve a narrow one-state abstraction the new design is intended to remove.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Do not add a `StateModel` alternative, interpret the third generic position based on its type, or support
  both callback shapes.
  Rationale: Backward compatibility is not required. One strict API is easier to understand, validate, render, and
  document than a transitional polymorphic contract.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Keep `@state_processor` parameterless and keep typed state schema declarations off
  `transform_with_state(...)`.
  Rationale: Class annotations are the single source of truth for Structure-authored processors. Operation-level
  arguments continue to describe relation-specific configuration: grouping keys, output mode, time mode, output
  event-time column, and optional initial-state relation.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Keep `external_state_processor(...)` as a separate call-site binding with explicit input, key, output, and
  informational state schemas.
  Rationale: Native processor classes have no dependable Structure generic metadata. Their Python code, state names,
  state kinds, TTL policy, and other internals remain opaque, while explicit boundary schemas let Structure compile,
  render, explain, and type-check the surrounding relation.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Admit `Append` and `Update` for the row API and reject `Complete` during capture.
  Rationale: These are the processor modes with defined PySpark examples and useful incremental output semantics.
  Structure must not pass an unproved mode to Spark and allow a query-start failure. A future plan may add `Complete`
  only after pinned runtime evidence and a clear snapshot-output contract exist.
  Date/Author: 2026-10-06 / Codex.
- Decision: Prove every admitted output mode and every time mode, but do not require a Cartesian product of all mode
  combinations.
  Rationale: A compact matrix can isolate each semantic branch: ordinary no-timer processing, processing-time timers,
  and watermarked event-time timers, while exercising both incremental output modes.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Replace the combined arbitrary-state ledger row with four API-specific rows.
  Rationale: Row `transformWithState`, Pandas `transformWithStateInPandas`, legacy `applyInPandasWithState`, and
  Scala Dataset state methods have separate availability and evidence. One row causes unrelated work to block or
  accidentally promote another family.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: This plan may promote only the row family. The two Pandas statuses remain owned by their existing plans.
  Rationale: `P10042604` and `P10062602` are active in another chat and have their own runtime matrices. This plan must
  preserve their edits and report their observed status without substituting row evidence.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Produce a design document for typed parity in this plan; defer the breaking implementation to a dedicated
  follow-on ExecPlan.
  Rationale: Row admission fixes a stale claim and missing mode evidence. The attribute model changes the public API,
  runtime adapter, recipes, generated source, fingerprints, tests, and migration guidance and deserves an independent
  implementation sequence after the design is reviewed.
  Date/Author: 2026-10-06 / User and Codex.

execution pass for both output modes and all time modes, including a composite key, processing-time and event-time
timers, and same-checkpoint restart. The live run used PySpark 4.1.0: the Delta V11 proof phase passed 31 tests with 3

ExecPlan. The Pandas gates remain with their separate plans.

## Context and Orientation

Structure is a schema-first compiler. A transform step is captured symbolically, lowered into an immutable PySpark
recipe, interpreted for online execution, and rendered into a generated Python module. A supported stateful operation
therefore needs the same behavior in both execution paths, an explainable recipe, target capability checks, and live
evidence on every claimed runtime profile.

The row state public API lives in `src/structure/plugin/pyspark/dsl/Stateful.py` and is exported from
`src/structure/plugin/pyspark/__init__.py`. A typed processor currently inherits
`StateProcessor[InputSchema, KeySchema, StateSchema, OutputSchema]`. Its `on_rows(...)` callback receives one
`ValueState[StateSchema]` argument, and its optional `on_timer(...)` callback receives the same handle. The operation
captures through `_capture_stateful_transform(...)`, lowers into the stateful recipe under
`src/structure/plugin/pyspark/compiler/model/`, executes through
`src/structure/plugin/pyspark/execution/stateful.py`, and renders through the PySpark render package. Ordinary PySpark
4.1 is the only row target. PySpark 4.0 has no row Python entry point, and Spark Connect is unclaimed.

`tests/specifications/streaming-transform-with-state/test_stateful_api.py` owns Spark-free typed row behavior.
`tests/integration/pyspark/v11/test_transform_with_state.py` owns the pinned runtime proof. The predecessor plan at
`docs/dev/planning/past/P10042603.V11-transform-with-state.plan.md` records passing online/generated accumulation,
same-checkpoint restart, processing-time timer, and native multiple-state/initial-state/timer behavior. The missing row
proof is an admitted-mode matrix, especially `time_mode="None"`, `output_mode="Append"`, a watermarked
`time_mode="EventTime"` timer, and a live composite key.

The initial PySpark 4.1 Compose lane is intentionally narrow. `make integration BACKEND=pyspark41` runs the backend
version check and `tests/integration/pyspark/v11`; it does not run the older 3.5/4.0 integration trees. This plan must
not expand that lane or run non-4.1 integration suites as evidence for row `transform_with_state(...)`.

The machine-readable ledger is
`src/structure/plugin/pyspark/resources/pyspark-streaming-api-coverage.json`. Its tests are in
`tests/specifications/compatibility/test_pyspark_streaming_api_coverage.py`. Public status appears in
`docs/compatibility/Streaming.compat.md`, `docs/compatibility/APICompatibility.md`,
`docs/compatibility/APITracker.md`, `docs/api/Streaming.api.md`, and `docs/reference/Streaming.ref.md`. Development
status appears in the V11 Python/streaming and retained-V9 design and specification documents, streaming gates, V11
project and sprint documents, milestones, user stories, and the predecessor plan. A repository-wide search is still
required because a status claim duplicated outside this list must be reconciled too.

The two other active plans are
`docs/dev/planning/P10042604.V11-transform-with-state-in-pandas.plan.md` and
`docs/dev/planning/P10062602.V11-apply-in-pandas-with-state.plan.md`. Their implementations share `Stateful.py`, recipe,
render, execution, compatibility, and documentation files with this work. Before editing a shared file, re-read its
current contents and `git diff -- <file>`. Preserve all concurrent Pandas work. Never use `git checkout`, `git reset`,
or a whole-file replacement to recover a shared file.

In this plan, an admitted mode is a value Structure accepts at compile time, documents as supported, and proves in
online and generated execution on the claimed runtime. An opaque processor is a native PySpark `StatefulProcessor`
whose body Structure neither compiles nor analyzes. Structure knows enough schemas to connect it to the transform, but
the processor owns native state-handle creation and advanced behavior.

### Milestone 5: Save the typed parity design

Create `docs/dev/design/V11TransformWithStateTypedParity.design.md`. Begin with the current limitation: the typed row
adapter owns one unnamed `ValueState`, passes it into callbacks, rejects typed initial state, and cannot express native
named `ValueState`, `ListState`, `MapState`, per-state TTL, or typed state evolution. Record composite grouping keys as
already compiler-supported and require live evidence from Milestone 2 rather than listing them as future API work.

The accepted public shape is:

    @state_processor
    class AccountProcessor(StateProcessor[Event, AccountKey, AccountOutput]):
        total: ValueState[Total]
        recent_events: ListState[Event]
        summaries: MapState[SummaryKey, Summary] = map_state(
            name="summaries",
            ttl=timedelta(hours=24),
        )

        def on_rows(
            self,
            key: AccountKey,
            rows: Iterator[Event],
            timers: TimerContext,
        ) -> Iterator[AccountOutput]:
            current = self.total.get()
            ...

`StateProcessor` has exactly three Schema generic arguments: input, grouping key, and output. Annotation-only state
attributes use their Python attribute name as the persisted Spark state name. `value_state(...)`, `list_state(...)`,
and `map_state(...)` are optional declaration factories used only when metadata such as an explicit persisted name or
TTL is needed. A factory creates immutable declaration metadata at class-definition time; the adapter replaces or
resolves it to a live typed handle on each processor instance during Spark `init`.

`@state_processor` takes no schema arguments. It resolves all annotations, rejects unparameterized or non-Schema state
types, duplicate persisted names, reserved callback names, and declarations inherited with conflicting metadata.
State handles are unavailable in user `__init__`; they become valid before `on_initial_state`, `on_rows`, or
`on_timer`. Users must not define the Spark `init` method because the Structure adapter owns handle creation. Handles
are callback-scoped to the current key and must not be cached outside the processor instance or used from other
threads.

`ValueState[ValueSchema]`, `ListState[ValueSchema]`, and
`MapState[UserKeySchema, ValueSchema]` expose typed wrappers over the matching PySpark 4.1 handles. The design document
must specify reads, writes, iteration, clearing, map-key removal, and absent-value behavior without inventing semantics
that Spark does not provide. Use `datetime.timedelta` for TTL. Reject non-positive durations, sub-millisecond values,
and values that cannot be represented as Spark integer milliseconds. `None` means no TTL. Persisted names must be
nonempty and unique.

Keep grouping-key declarations at the operation call because they bind a processor to the current relation. One-field
keys accept one field expression. Composite keys accept a tuple ordered exactly like the Key Schema. Do not accept a
mapping because it would create a second field-naming and ordering source. Validate arity, duplicate fields, relation
scope, and Structure types before lowering.

Typed initial state remains a relation-specific `initial_state=` argument. A processor opts in by defining
`on_initial_state(self, key: Key, initial: Initial, timers: TimerContext) -> None`, where `Initial` is a concrete
Structure Schema annotation. Compilation rejects an initial relation without the callback, a callback without a bound
initial relation when the contract requires initialization, mismatched key fields, and an initial-row schema that does
not match `Initial`. The adapter injects all state handles before invoking this callback. Do not add an initial-state
generic to `StateProcessor`.

The design must define state identity and checkpoint compatibility. Persisted identity is the explicit `name=` value
or, by default, the Python attribute name. Generated recipes fingerprint each state kind, persisted name, key/value
schemas, and TTL for traceability. Renaming only the Python attribute can preserve Spark identity by retaining the old
explicit name. Changing a persisted name, state kind, key/value schema, or TTL is checkpoint-sensitive. Structure does
not own checkpoint locations and therefore does not promise an automatic migration or write manifests beside
checkpoints. Spark remains responsible for runtime state-schema compatibility. The public reference must tell users to
use a new checkpoint unless pinned Spark evidence and a later migration specification admit a particular evolution.

Keep native processors available through `external_state_processor(...)`. Their binding continues to carry explicit
relation-bound schemas, but Structure does not inspect Python control flow, native handle declarations, timers, TTL,
cleanup, state deletion, or schema evolution. This is the escape hatch for Python constructs the Structure compiler
does not model and for PySpark features not yet exposed by typed handles. Explain output and generated artifacts must
label this boundary opaque.

Do not preserve the old typed shape. The follow-on implementation removes the fourth `State` generic and removes the
`state` argument from `on_rows(...)` and `on_timer(...)` in one change. Migration guidance must show current Structure
users moving `State` to `state: ValueState[State]` and replacing local callback access with `self.state`. Native PySpark
users move `self.foo = handle.getValueState(...)` declarations to annotations or factories and keep ordinary callback
logic on `self.foo`. No compatibility decorator arguments, generic-position dispatch, deprecation phase, or dual
renderer are required.

The design must give a staged implementation order for the follow-on plan: first the breaking three-generic processor
and named `ValueState` foundation; then typed `ListState` and `MapState`; then TTL; then typed initial state; then
checkpoint/evolution diagnostics supported by pinned Spark evidence. Composite grouping keys stay in the existing
foundation and receive regression coverage. Event-time timers belong to the admitted row contract and are completed by
Milestone 2. Native `close`, state-variable deletion, and any state evolution not proved by Spark remain explicit
follow-on gates rather than implied parity.

The milestone is complete when the design contains examples, invariants, validation failures, lowering/runtime
ownership, generated-code implications, external-processor escape hatch, checkpoint rules, migration examples, test
strategy, documentation impact, and the staged implementation order. It must not claim that the attribute API is
already implemented.

## Validation and Acceptance

The row operation is admitted when a user can compile and run it on ordinary PySpark `>=4.1,<4.2` with `Append` or
`Update` and with each of `None`, `ProcessingTime`, and `EventTime`, subject to the documented valid combinations.
Online and generated execution must emit equivalent values and schemas. `Complete` must fail before query startup with
an actionable message naming the two admitted alternatives.

The no-time scenario must resume accumulated state from the same caller-provided checkpoint. The processing-time
scenario must observe a timer callback. The event-time scenario must advance a real input watermark and observe a
timer-produced row without depending on wall-clock passage. A two-field grouping key must keep state isolated by the
ordered composite key in both execution modes.

The ledger is accepted when it contains the four specified API-family rows and no combined arbitrary-state row. The
row family is `structure-supported`; the two Pandas families retain their independently proven current statuses; the
Dataset family is `out-of-scope`. Focused tests must prevent row evidence from changing either Pandas status.

Documentation is accepted when public API, reference, compatibility, and tracking pages describe the row support
claim and limitations consistently, development design/specification/gate pages no longer call row evidence pending,
and every future attribute-API example is labeled as design rather than current behavior. Repository-wide search must
find no contradictory live claim.

The typed-parity design is accepted when a future implementer can derive one public API without making unresolved
choices about generics, decorator parameters, state declarations, naming, TTL units, key order, initial state,
checkpoint compatibility, migration, external processors, or implementation sequence. The design must explicitly
state that backward compatibility with the old typed processor is not required.

Final acceptance requires the focused test suites, ordinary PySpark 4.1 V11 lane, `make build`, JSON validation, and
`git diff --check` to pass. Skipped local live tests are not evidence; the Compose lane is required.

## Idempotence and Recovery

All tests use unique temporary source and checkpoint directories and can be rerun. A failed streaming query must be
stopped in `finally`, after which the same test can start with a fresh temporary root. Keep the event-time fixture
small so recovery does not require manual Docker cleanup.

This is a shared dirty worktree. Before each edit to `Stateful.py`, state recipes, render/execution code, the ledger,
or shared documentation, inspect the latest file and its diff. Apply narrow patches. If concurrent Pandas work changes
a nearby hunk, rebase the intended row edit mentally onto the latest content and rerun both the row-focused and
affected Pandas-focused Spark-free tests. Never discard, reset, or restore another task's changes.

If the 4.1 Compose lane fails because the Docker VM is full, follow the documented Docker storage recovery in
`docs/dev/Troubleshooting.md`, preserve useful versioned images and caches where possible, and rerun the same command.
Record the incident and remedy in the plan and update troubleshooting only when the existing entry does not cover the
observed failure. Do not substitute a different PySpark version.

If an event-time timer test stalls, inspect query progress and watermark values before increasing timeouts. Correct the
fixture so a later input deterministically advances the watermark beyond the registered timer. If Spark requires a
no-data micro-batch, use the pinned runtime's supported trigger and record that behavior in `Surprises & Discoveries`.

## Interfaces and Dependencies

Milestones 1 through 4 retain the current typed public interface, apart from narrowing its unproved `Complete` mode:

    @state_processor
    class CurrentProcessor(StateProcessor[Input, Key, State, Output]):
        def on_rows(
            self,
            key: Key,
            rows: Iterator[Input],
            state: ValueState[State],
            timers: TimerContext,
        ) -> Iterator[Output]:
            ...

    transform_with_state(
        *,
        key: Expression | tuple[Expression, ...],
        processor: type[StateProcessor] | ExternalStateProcessor,
        output_mode: Literal["Append", "Update"],
        time_mode: Literal["None", "ProcessingTime", "EventTime"],
        event_time_column: str | None = None,
        initial_state: InputScope | None = None,
    ) -> StatefulResult

Typed `initial_state` remains rejected in current code. `initial_state` is available only with
`external_state_processor(...)` until the follow-on typed-parity implementation.

The accepted future interface, documented but not implemented by this plan, is:

    @state_processor
    class FutureProcessor(StateProcessor[Input, Key, Output]):
        value: ValueState[Value]
        items: ListState[Item] = list_state(ttl=timedelta(minutes=30))
        index: MapState[IndexKey, IndexValue] = map_state(name="stable-index")

        def on_rows(
            self,
            key: Key,
            rows: Iterator[Input],
            timers: TimerContext,
        ) -> Iterator[Output]:
            ...

        def on_timer(
            self,
            key: Key,
            timer: Timer,
            timers: TimerContext,
        ) -> Iterator[Output]:
            ...

        def on_initial_state(
            self,
            key: Key,
            initial: Initial,
            timers: TimerContext,
        ) -> None:
            ...

No `StateModel`, decorator schema parameters, duplicate call-site state schemas, generic-position dispatch, or old
callback overload will exist on the typed path. `ExternalStateProcessor` remains the explicit opaque boundary.

Use only the project's existing Python standard library, Structure Schema/DSL/compiler layers, and pinned PySpark 4.1
runtime. `datetime.timedelta` is the future typed TTL surface. Do not add a third-party dependency. PySpark imports
remain late-bound so importing Structure and compiling Spark-free tests do not load PySpark.
