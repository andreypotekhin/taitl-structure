# Add schema-declared foreachBatch sinks and sink-only steps

This ExecPlan is a living document. Maintain it according to `docs/dev/auto/Plans.md`; update `Progress`,
`Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` as work proceeds. This plan extends the
implemented row `foreach` contract described in `docs/dev/planning/P10042602.Row-level-foreach-sinks.plan.md`.

## Purpose / Big Picture

A streaming transform author should be able to declare `sink(AlertMessage)` and associate its final `Alert` output
with a caller-owned `foreachBatch` query. For each Spark micro-batch, the caller can run a second Structure transform
that prepares `AlertMessage` rows, then send those rows to an external destination. Structure compiles the association
and prepares the batch; the caller starts the query, chooses the destination, writes, and handles retries.

Authors may use a sink parameter in the step that returns the final row, or use a separate sink-only step whose return
annotation names the sink schema. Neither style needs `self.send_alerts` in the step body. The same sink-only form
should also work for the existing row `foreach` API. A live test must show alerts arriving through the batch path and
replaying a batch without an unintended duplicate external effect when the caller supplies idempotent writing.

## Surprises & Discoveries

- Observation: `SinkDeclaration` currently accepts only concrete `Sink` subclasses, and `SinkPlan` stores an
  importable writer class. A schema sink is a new declaration role; treating its schema as a writer would misdescribe
  the handoff. Evidence: `src/structure/core/dsl/model/transforms/SinkDeclaration.py` and
  `src/structure/plugin/api/v1/model/SinkPlan.py`.
- Observation: `CompileTransform._return_schemas` treats every `Schema` annotation as a DataFrame result, while
  `_step_parameters` treats every schema parameter as a relation. The new public syntax requires role-aware binding.
  Evidence: `src/structure/core/compiler/frontend/commands/CompileTransform.py`.
- Observation: row sink capture currently expects the captured row to be returned by that same step. A sink-only
  `publish(alert: Alert)` instead consumes a row produced by the preceding step. Evidence:
  `src/structure/plugin/pyspark/symbolic_execution/commands/CapturePySparkStep.py` and
  `CompileTransform._sink_plans`.
- Observation: `StructureSession.close()` currently drops every plan-boundary temporary view for its Spark object.
  A child session sharing that Spark object could therefore drop views needed by its parent. Evidence:
  `src/structure/core/runtime/session/model/StructureSession.py` and
  `src/structure/plugin/pyspark/execution/logic/PlanBoundary.py`.
- Observation: a batch DataFrame supplied inside `foreachBatch` may use a SparkSession wrapper different from the
  session that ran the streaming transform. A temporary view created on the DataFrame's SparkSession must be looked up
  there, and session cleanup must release views across all wrappers used by that owner. Evidence: the first live 3.5
  run failed with `TABLE_OR_VIEW_NOT_FOUND` until plan boundaries used `frame.sparkSession` and owner cleanup visited
  each tracker.
- Observation: the sink handoff needs two different schema identities. Its `input_schema` is the Structure `Schema`
  class for the streaming output (used to match the batch transform input); its `schema` is the declared batch output
  `Schema` class. Spark `StructType` values are used only to compare live callback DataFrame shape. Evidence: the live
  test first failed input matching and then output matching when either side used materialized Spark schemas.
- Observation: `foreach_batch_alerts` passed one finite micro-batch through both online and generated execution on
  classic PySpark 3.5 and 4.0. Each lane reported `1 passed, 265 deselected`.

## Decision Log

- Decision: Keep a class-level sink declaration in every form. For batch sinks, declare `sink(AlertMessage)`, where
  `AlertMessage` is a `Schema`. Retain `sink(AlertWriter)` for row sinks, where `AlertWriter` is a `Sink` subclass.
  Rationale: Declarations give both forms a named result handoff and a compile-time binding target.
  Date/Author: 2026-10-05 / user and Codex.
- Decision: Steps may access a sink through an annotated parameter or through a sink-typed return. Do not support
  `self.send_alerts` in a step body; relation and sink dependencies follow the same method boundary rule.
  Rationale: The method signature should expose the step's inputs and effects.
  Date/Author: 2026-10-05 / user and Codex.
- Decision: Require the explicit sink as the second argument in every `foreach(row, sink)` and
  `foreach_batch(row, sink)` call. The preferred step form returns its ordinary relation and calls the helper as a
  side effect. Also allow an effect step to return the sink's nominal type, provided it still has the explicit sink
  parameter and returns `foreach_batch(row, sink)` or `foreach(row, sink)`. These helpers return symbolic markers;
  they never construct a `Schema` row, writer, or DataFrame.
  Rationale: The parameter declares the dependency consistently with relation inputs. A sink-typed return can remain a
  secondary way to mark a sink-only step without inferring a sink from an omitted helper argument.
  Date/Author: 2026-10-05 / user and Codex.
- Decision: Classify each step parameter and return position by role: relation or sink effect. Keep public annotations
  as `Schema` and `Sink` classes; do not expose `SinkEffect[T]`. Defer mixed tuples such as
  `tuple[Alert, AlertMessage]` until a separate concrete use case requires them.
  Rationale: The declaration and method contract already identify the role; a public wrapper would diverge from
  relation-style authoring.
  Date/Author: 2026-10-05 / user and Codex.
- Decision: `StructureSession.run_batch(handoff, invocation)` runs a fully constructed batch transform invocation and
  returns its normal `TransformResult`. The caller validates or writes `result.messages`; no transform starts a query
  or calls `.write`. The handoff supplies the source DataFrame and expected output schema, not a processor class.
  Rationale: The caller chooses the batch processor and owns the external write.
  Date/Author: 2026-10-05 / user and Codex.
- Decision: Expose the batch operation in caller code as
  `PrepareAlertBatch(alerts=batch_df).run_batch(batch_session, handoff)`. Implement that invocation method as a thin
  forwarder to `batch_session.run_batch(handoff, invocation)`, where session owns validation and execution.
  Rationale: Existing transforms use `invocation.run(session)`. Putting the processor invocation first makes the
  responsible transform visible at the call site, while keeping runtime work in the session API.
  Date/Author: 2026-10-05 / user and Codex.
- Decision: Add both `StructureSession(parent_session)` and `parent_session.spawn()`. Show `spawn()` in examples.
  A parent may instead call `run_batch` itself if it stays open and repeated batches leave no accumulating resources.
  Rationale: The short context manager improves resource hygiene; copy construction remains useful when child setup
  needs to be explicit.
  Date/Author: 2026-10-05 / user and Codex.
- Decision: Use `batch_id` at the caller-owned write boundary. A durable destination must deduplicate by a stable
  stream identity plus batch ID, atomically with the write, to make retry effects idempotent.
  Rationale: Spark may invoke the batch callback again after a failure; Structure cannot promise exactly-once effects
  for an arbitrary external destination.
  Date/Author: 2026-10-05 / user and Codex.

## Context and Orientation

A `Schema` class describes row fields for Structure compilation. A `Transform` declares inputs and outputs and has
methods called once during symbolic compilation, rather than once per data row. A `sink(...)` declaration names an
external effect. A handoff is a read-only value on `TransformResult` that tells caller code which final DataFrame and
sink contract to use. Spark `foreachBatch` invokes a Python callback for each micro-batch, passing a batch DataFrame
and integer batch ID. The callback runs on the driver and can execute batch DataFrame actions.

`src/structure/core/dsl/model/transforms/transform_api.py` exports declarations and `@step`.
`src/structure/core/dsl/model/transforms/Transform.py` collects declarations.
`src/structure/core/compiler/frontend/commands/CompileTransform.py` binds method signatures and final outputs.
`src/structure/plugin/pyspark/dsl/body.py` contains the existing `foreach` helper; its symbolic calls are captured in
`src/structure/plugin/pyspark/symbolic_execution/commands/CapturePySparkStep.py`. Plugin-neutral step and sink facts
live in `src/structure/plugin/api/v1/model/`, and Spark execution consumes the lowered plan. The online and generated
paths both return `TransformResult` through `StructureSession.run` in
`src/structure/core/runtime/session/model/StructureSession.py`. `SinkResult.py` represents the current row handoff.

The existing row implementation in `docs/dev/planning/P10042602.Row-level-foreach-sinks.plan.md` is a prerequisite:
it adds `sink(AlertWriter)`, a typed writer parameter, symbolic `foreach(row, sink)`, and a named handoff containing
the final DataFrame plus writer class. It restricts sinks to direct transforms and final outputs. Preserve that
boundary for this first batch version. `docs/reference/Streaming.ref.md` and `examples/streams/Readme.md` currently
describe caller-owned `foreachBatch` without a Structure sink declaration; extend those pages when the code works.

## Proposed Public Behavior

The schema sink names the *output of the batch processor*, while its handoff DataFrame is the streaming `Alert`
output. This distinction is essential: the main transform does not produce an `AlertMessage` DataFrame.

    from structure import *
    from structure.plugin.pyspark import foreach_batch

    class Event(Schema):
        event_id = string(nullable=False)
        message = string(nullable=False)

    class Alert(Schema):
        event_id = string(nullable=False)
        message = string(nullable=False)

    class AlertMessage(Schema):
        event_id = string(nullable=False)
        payload = string(nullable=False)

    class PrepareAlertBatch(Transform):
        alerts = input(Alert)
        messages = output(AlertMessage)

        def prepare(self, alert: Alert) -> AlertMessage:
            return AlertMessage(event_id=alert.event_id, payload=alert.message)

The one-step form keeps the row-returning method and supplies the declared sink through a method parameter. With a
unique `sink(AlertMessage)` declaration, the compiler binds `sink: AlertMessage` as a sink role, not a relation.

    class PublishAlerts(Transform):
        events = input(Event, streaming=True)
        alerts = output(Alert)
        send_alerts = sink(AlertMessage)

        def publish(self, event: Event, sink: AlertMessage) -> Alert:
            alert = Alert(event_id=event.event_id, message=event.message)
            foreach_batch(alert, sink)
            return alert

If authors prefer a separate sink-effect step, keep the sink explicit there too. The `AlertMessage` return annotation
marks the step's effect role, while the parameter selects `send_alerts`; the method does not create a second relation
or change `result.alerts`. This style is supported, but the ordinary relation return in `PublishAlerts` is the main
example.

    def publish_batch(self, alert: Alert, sink: AlertMessage) -> AlertMessage:
        return foreach_batch(alert, sink)

When multiple sink declarations match a parameter or return annotation, `@step(sink=send_alerts)` selects one. A
`Schema` used both as a readable relation and sink type must also be disambiguated by explicit `@step` metadata; the
compiler must not guess from declaration order. A sink-only step must consume the exact final output lane, and its
helper call must use that same symbolic row. Reject intermediate lanes, duplicate sink attachment, missing helper
calls, wrong helper families (`foreach` versus `foreach_batch`), and mixed relation/effect tuple returns with
diagnostics that name a valid form. Preserve ordinary relation-only `Schema` steps.

The callback below runs the main transform through the traditional invocation method, then supplies Spark's callback
`batch_df` to a fully constructed batch transform. `PrepareAlertBatch` is selected by caller code, not by `sink(...)`.
The invocation-owned `run_batch` method delegates validation and execution to `batch_session`; it validates that
`messages` has the schema expected by `send_alerts`.
`run_batch` can validate the declared input schema and batch execution mode, but it cannot prove that the DataFrame
passed into the constructed invocation is the same Python object that Spark passed to the callback. Caller code must
pass `batch_df` explicitly, as shown below.

    with StructureSession(spark=spark, config=config) as session:
        result = PublishAlerts(events=events_stream).run(session)
        handoff = result.send_alerts

        def send_batch(batch_df, batch_id: int) -> None:
            with session.spawn() as batch_session:
                prepared = PrepareAlertBatch(alerts=batch_df).run_batch(batch_session, handoff)
                messages = prepared.messages
                alert_writer.write(messages, stream_id="alerts-v1", batch_id=batch_id)

        query = (
            handoff.dataframe.writeStream.foreachBatch(send_batch)
            .option("checkpointLocation", checkpoint_dir)
            .start()
        )
        query.awaitTermination()

Here `alert_writer` is application code that sends a batch and commits a stable `(stream_id, batch_id)` key with its
destination write. Its concrete API and storage transaction are outside Structure. The writer must arrange atomic
deduplication if retries cannot produce duplicate alerts. The caller should stop the query before leaving the parent
session's context. A main session can execute `run_batch` directly while it remains open, but every callback then
shares its temporary resources; use `spawn()` unless the application has proven that repeated callbacks clean up
fully. Do not close the main session inside the callback.

The row form follows the same method boundary. The existing parameter-based form remains valid; an optional
sink-effect step includes the sink parameter and returns the declared row writer's nominal type. The helper always
receives both row and sink; it never infers the sink from a return annotation.

    class PublishRowAlerts(Transform):
        events = input(Event, streaming=True)
        alerts = output(Alert)
        send_alerts = sink(AlertWriter)

        def alert(self, event: Event) -> Alert:
            return Alert(event_id=event.event_id, message=event.message)

        def publish(self, alert: Alert, sink: AlertWriter) -> AlertWriter:
            return foreach(alert, sink)

Define `AlertWriter` as a module-level concrete `Sink` subclass with `process(row)` as in the row plan. The caller
still receives `result.send_alerts.writer` and starts the separate row query; this plan does not change that lifecycle.

## Validation and Acceptance

`send_alerts` handoff whose

## Idempotence and Recovery

All compilation and test steps can be repeated. Use test-specific checkpoints and destination paths; remove only
paths created by the test fixture. Stop active queries in `finally` or context cleanup before closing the parent
session. On failed live tests, inspect query exception and checkpoint before retrying with a fresh test path. To test
replay, deliberately reuse the same checkpoint or invoke the same batch key in a controlled fixture; never assume
Spark makes arbitrary writes exactly once. Preserve existing uncommitted worktree changes. Do not stop the shared
Spark session when closing a Structure child session.

## Interfaces and Dependencies

The public target interfaces are `sink(AlertMessage)`, `foreach_batch(row, sink)`, and `foreach(row, sink)`, each
requiring both arguments. The preferred step returns its ordinary relation after calling the helper. An optional
sink-effect step returns the nominal sink type while still taking the sink as a parameter. Add
`Transform.run_batch(session, handoff)` forwarding to
`StructureSession.run_batch(handoff, invocation: Transform) -> TransformResult`, plus
`StructureSession(parent_session)` and `StructureSession.spawn() -> StructureSession`. The nominal return types exist
for step signature resolution; at compile time the helpers return internal symbolic markers. Batch handoffs expose
`dataframe` and the expected output schema; row handoffs expose `dataframe` and `.writer`. The compiler must represent
roles explicitly in internal metadata rather than infer sink effects from a `Schema` annotation alone.

Use the repository's existing Core DSL, PySpark plugin, classic PySpark integration profiles, and `pytest`/`make`
toolchain. Do not add a mandatory external alert service dependency. The application controls alert transport,
checkpoint location, write configuration, and idempotent commit. Support claims for additional Spark runtimes require
separate live evidence.
