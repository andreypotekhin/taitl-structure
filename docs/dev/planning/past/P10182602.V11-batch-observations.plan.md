## Purpose / Big Picture


After implementation, a Structure transform can declare a named observation, attach typed aggregate metrics at a
particular point in its relation operations, and expose a handle beside its normal results. An observation measures
rows processed at that point while a Spark action executes. An action is a caller operation such as `collect()`,
`count()`, or a write that causes Spark to execute its otherwise lazy DataFrame plan.

The caller executes an output action and retrieves an instance of the declared metric Schema through
`result.quality.get()`. Observation expressions leave the relation's rows and schema intact. Structure adds no action
to collect these metrics. Scalar and complex metric values follow Spark semantics, including empty-input nullability
and the documented differences between ordinary Spark and Spark Connect handles.

The visible proof is native/online/generated agreement on each claimed exact `>=4.1,<4.2` variant. Online execution
runs the compiled Structure plan directly; generated execution runs the emitted PySpark. The ordinary and Connect
claims require separate evidence. The default profile remains `>=3.5,<4.1`. Streaming observations and KLL/Theta
sketch development are separate work packages.

## Surprises & Discoveries


Native 4.1 handles differ across variants. With a ten-row single-partition range, an observed frame first read with
`limit(2).collect()` reported two rows on both variants. A later full `collect()` left ordinary metrics at two rows
but updated Connect metrics to ten rows. Connect also returned an empty dictionary before execution, whereas the
ordinary public getter waits for metrics. These are native-runtime probes, not evidence of implemented Structure
support. Preserve these differences explicitly rather than inventing a common first-action guarantee.

An empty non-null Long input produced count zero, sum null, and coalesced sum zero. The corresponding ordinary Spark
aggregate result fields were non-null, nullable, and non-null respectively. An observation returned the same values.
Input-field nullability therefore cannot determine aggregate metric nullability by itself.

Native ordinary 4.1 probes accepted an aggregate composition (`sum(id) + max(id)`), a struct containing aggregates,
`collect_set`, an array containing aggregates, and a map containing an aggregate. Native analysis rejected distinct
aggregates, unaggregated row references, and window expressions. Typed validation preserves this eligibility.

Spark Connect exposed two composition requirements. An automatic plan boundary in a downstream stage detached the
native Observation handle, so plan boundaries are disabled for observation-bearing batch plans through the
caller-visible output. The generated composed-class renderer also needed to initialize its observation registry and
pass stage handles into `TransformResult`; direct transform generation did not exercise that renderer branch.

`dsl/operations_api.py:_aggregate` currently sets `context.aggregate_requested` as soon as an aggregate expression is
constructed. Python constructs arguments before calling `observe`, so an observation payload initially sets this
flag too. `symbolic_execution/logic/results/BuildPySparkResultBodies.py` uses the flag to select aggregate result
lowering. Observation consumption must be tracked so those expressions cannot accidentally aggregate the row output;
simply resetting the flag would also hide genuine aggregates used elsewhere in that step.

`TransformResult` and `StageResult` already provide attribute-based result access and preserve output-only mapping
behavior. Sink handles establish a precedent for a separate named result value. Child stage results are governed by
`allow_stage_outputs`. Extend these mechanisms rather than adding a second observation namespace.

Generated schema modules currently emit Spark `StructType` constants, not Python Structure Schema value classes.
Those constants cannot construct an `OrderMetrics` value. Generated observation handles must import the declared
metric Schema classes through explicit source dependencies, as existing generated provider integrations do, and
include observation schemas in dependency discovery. The original metric schema package must be importable at
generated runtime; an anonymous replacement or native dictionary would violate the selected result API.

## Decision Log


Decision (2026-10-18, user): Start with typed batch metrics declared inside transforms. Rationale: this fits the
existing lazy output model while leaving streaming progress and listener design separate.

Decision (2026-10-18, user): Require `quality = observation(OrderMetrics)` and accept a schema-valued payload in
`observe`. Support `observe(self.quality, OrderMetrics(...))` and `observe(OrderMetrics(...))`. Rationale: the schema
is visible at the call site and the named declaration supports reuse, inheritance, and composition. The initially
discussed keyword-only metric form was removed from the first version at the user's request.

Decision (2026-10-18, agreed inference rule): Infer from exact Schema class identity among all visible observation
declarations. Require an explicit reference when multiple declarations use that schema. Rationale: resolution must
not depend on which declaration has already been bound.

Decision (2026-10-18, user): Expose `result.quality.get()` returning an instance of the declared metric Schema.
Rationale: direct access follows the established result style and provides ordinary schema field access. Complex
values are reconstructed and copied recursively into detached snapshots.

Decision (2026-10-18, user): Preserve native ordinary/Connect action semantics. Rationale: public Spark handles differ
on subsequent actions; Structure will not wrap actions or use private runtime state to manufacture uniform behavior.

Decision (2026-10-18, user): Permit unused declarations and omit their handles. Require bound observations to lie on
a returned output path. Rationale: compile-time parameters can disable metrics, while disconnected measured branches
would otherwise have no caller action that can execute them.

Decision (2026-10-18, user): Include scalar and complex values and follow `allow_stage_outputs` for child handles.
Rationale: complex metrics are the reviewed 4.1 extension, and child metric visibility should follow existing stage
result visibility.

Decision (2026-10-18, implementation plan): Bind a declaration at most once per specialization; allocate fresh native
handles per execution and stage occurrence. Rationale: a native Observation cannot be attached to multiple independent
plans. Public declaration names remain stable, while internal native names distinguish invocations and stage paths.

Decision (2026-10-18, user): First request a design-only plan; a later user instruction authorized implementation.
The later instruction superseded the initial deferral. Implementation did not change the agreed public contract.

## Outcomes & Retrospective


Typed batch observations are implemented for ordinary and Spark Connect `>=4.1,<4.2`. The public API exposes named
metric Schema declarations and detached typed snapshots. Online and generated execution preserve native Spark action
semantics; empty-input values retain aggregate nullability, collection metrics are recursively reconstructed, and
composed stage handles follow stage-output visibility. Unused declarations have no handle, used declarations must
reach a returned output, and streaming or unsupported profiles remain rejected.

The ordinary and Connect live cases passed on Python 3.11.17 and PySpark/Spark 4.1.0, including native comparisons,
online/generated values and schemas, conditional counts, `collect_set`, empty input, and composed stage access. Exact
commands and the build result are recorded in the completion evidence below. The default profile remains `>=3.5,<4.1`;
the implementation makes no streaming claim.

## Context and Orientation


Work from the repository root. A transform's Python declarations describe inputs, lanes, outputs, sinks, parameters,
and composed stages. Symbolic execution evaluates a step with typed placeholder fields and records its expressions
and ordered operations. The compiler converts those records into immutable recipes: data shared by online execution
and source generation. Runtime DataFrames and native observation handles must never enter those compiled records.

Core declaration and result plumbing lives under `src/structure/core/`. The starting points are
`dsl/model/transforms/Transform.py`, `dsl/model/transforms/SinkDeclaration.py`,
`runtime/session/model/TransformResult.py`, and `runtime/session/model/StageResult.py`. Shared plugin-facing plan
models and exports live under `src/structure/plugin/api/v1/`. Add target-neutral declaration and result metadata here;
keep PySpark imports and native metric interpretation in the PySpark plugin.

Under `src/structure/plugin/pyspark/`, public relation/aggregate functions are in `dsl/operations_api.py`. Capture state
is in `symbolic_execution/model/PySparkSymbolicContext.py`; result aggregation and schema assignment rules are in
`symbolic_execution/logic/results/BuildPySparkResultBodies.py`. Ordered operations and lowered records are represented
by `dsl/operations/OperationPlan.py`, `compiler/model/PySparkOperationRecipe.py`, and the execution-plan models.

Lower observation operations and expressions through `compiler/logic/maps/MapPySparkStep.py` and
`compiler/logic/maps/MapPySparkExpression.py`. Online execution starts in
`execution/logic/running/RunOnlinePySparkTransform.py`. Expression and step rendering live under `render/logic/`;
`render/logic/modules/RenderPySparkTransformModule.py` assembles the generated execution layouts and result objects.
Use focused delegates for new observation logic rather than extending these large orchestration classes with all
validation and conversion details.

`compiler/commands/DescribePySparkOptimization.py` and `compiler/logic/RemovalSafety.py` describe unused-step removal.
`compiler/commands/ClassifyStreamingCompatibility.py` supplies streaming findings. Explain and traceability delegates
must visit metric expressions just as they visit normal projections. Update composition rewriting, schema dependency
discovery, capability collection, and semantic fingerprints together with the new recipe.

The pinned runtime harness uses `infra/compose/docker-compose.yaml`, its repository-mounted
`images/pyspark/run-integration.sh`, and `tests/integration/pyspark/support/backend_matrix.py`. Ordinary 4.1 uses Spark
services; Connect 4.1 starts a gateway inside its runner and cleans it up on exit. The launcher runs isolated Iceberg
and Delta phases before the general selection. Preserve their caches, extensions, and cleanup behavior.

## Interfaces and Dependencies


Export `observation(schema)` from the core public DSL. It accepts a Schema class and returns an immutable named
declaration whose attribute name supplies its public name. Export `observe` from `structure.plugin.pyspark` with
the equivalent signatures below, where `T` is a Schema subclass and `RowScope` is the current symbolic relation:

    observation(schema: type[T]) -> ObservationDeclaration[T]
    observe(metrics: T) -> RowScope
    observe(reference: ObservationDeclaration[T], metrics: T) -> RowScope
    ObservationResult[T].get() -> T
    ObservationResult[T].schema -> type[T]

Require the payload's Schema class to match the declaration exactly. Supply every metric field through normal schema
assignment validation, preserving aliases and supported type widening. Reject missing/extra assignments, mixed
payload styles, string targets, undeclared references, and references belonging to another transform occurrence.
Inference searches all visible declarations by exact Schema class; it does not infer from field-name coincidence.
Zero matches explains how to declare the observation. Multiple matches lists the candidates and requests an explicit
declared reference.

Track bindings per compiled specialization. Two calls binding the same declaration are a compile error even when
their expressions match. A parameter-disabled call leaves its declaration unused and produces no runtime handle or
observation capability requirement. Access to an unused declared result raises an explanatory `AttributeError`.
Reject collisions with public outputs and aliases, sinks, stages, and reserved result attributes. Follow established
inheritance override rules and retain declaration provenance in composed stages.

Attach the observation to the current relation at the operation's source position. Validate metric fields against the
scopes visible there; an unrelated unjoined input cannot silently become the measured relation. Require a returned
output path, including a stage output when stage outputs are enabled. Validate this before unused-step removal can
erase an invalid binding. Do not preserve a disconnected observation by running a separate action.

Keep the operation row-preserving and batch-only. A call after pending grouped-result construction must request a
separate step: observe the input before grouping, or finish that grouped result and observe the resulting lane in a
following step with admissible aggregate expressions. Ordinary row output aggregates remain independently tracked.

An observed metric is a literal or an expression whose row references occur inside admissible aggregates. Support
existing scalar/complex types and existing expressions that lower to one native metric Column without an extra
relation or guard action. Reject known Spark-invalid forms such as distinct aggregates, nested aggregates, windows,
and bare row fields. Preserve existing per-metric `where=` semantics using conditional aggregate inputs. A helper
requiring relation reshaping or a separate guard must produce a diagnostic explaining the ordinary typed-step
alternative; do not weaken that helper's semantics. Other native analysis/runtime errors retain Spark's errors.

Compute metric nullability in a global, possibly empty input context, recursively through composed expressions and
complex fields. `count()` is non-null Long; `sum`, `min`, `max`, and similar empty-sensitive aggregates can be null
even when their arguments are required. Explicit fallbacks such as `coalesce(sum(value), 0)` retain ordinary
non-null inference. Reuse aggregate type widening; do not silently fill metric values from schema defaults.

Expose root handles through `result.quality` and child handles through `result.stages.clean.quality`. Use existing
stage visibility rules, including the disabled-stage-access diagnostic. Output iteration, `as_dict()`, output schema
mappings, and composition output matching remain DataFrame-output interfaces. Each observation handle's `schema`
contains its metric Schema class. Observation values are not inputs to expressions inside a lazy transform.

Use the public native `Observation` constructor, `DataFrame.observe`, and `Observation.get`. Introduce no background
listener, readiness polling thread, timeout getter, action wrapper, or native private-member access. Ordinary
`get()` can block until the observed part of a plan executes; Connect's empty pre-execution metrics must raise an
actionable unavailable-metrics error instead of constructing a schema with absent fields. A completed action on an
unrelated output does not make a handle ready. After an action failure, do not attempt an automatic metric read.

Every `get()` returns a fresh detached Schema snapshot. Recursively reconstruct declared nested Schema values and
copy arrays/maps so a later Connect action or mutation of a previously returned container cannot alter another
snapshot. Preserve native values and validate required fields; do not replace native nulls or coerce invalid values
into superficially compatible results. Ordinary handles retain first-action values; Connect handles expose their
current native values. Existing configured eager actions can populate metrics before `run()` returns.

Allocate fresh native objects per execution, including repeated or concurrent executions of one compiled artifact
and repeated child stages. Generate native names that distinguish invocation and full stage path while preserving
the public declaration name in diagnostics and result access. Generated modules import the original declared metric
Schema classes explicitly and construct the same Schema value types as online execution. Include nested schema
dependencies and document that these application schema modules are generated-runtime dependencies.

Introduce the capability key `observation.batch`. Initially admit exact ordinary and Connect `>=4.1,<4.2` separately
after their own parity passes. Used observations reject earlier/later profiles and streaming input; unused declarations
alone do not widen or restrict a runtime profile. No new third-party runtime dependency is required beyond the pinned
PySpark environment and normal Structure runtime.

## Idempotence and Recovery


Keep runtime state in newly allocated invocation/stage handles, never in class declarations or compiled artifacts.
Repeating compilation or rendering is deterministic. Repeating execution produces independent handles. Failure
during a native action must not cause a hidden retry, read, or cross-invocation reuse. Spark and the caller retain
action/recovery ownership.

Preserve shared services, image pins, dependency caches, and other chats' changes. Do not use Compose teardown or
delete shared checkpoint directories. The existing gateway runner performs its own success/failure/timeout cleanup.
If a focused diagnostic needs a temporary server, clean up that process and its own temporary resources on every exit.
Generated fixtures must be regenerated through repository helpers; do not hand-edit emitted PySpark to hide a failure.
Retain operation/variant gates whenever evidence is incomplete.

## Artifacts and Notes


The planned public example below becomes executable after implementation. Keep the metric Schema visible in the
call and demonstrate reference inference; replacing that call with
`observe(self.quality, OrderMetrics(rows=count(), total_quantity=sum(order.quantity)))` demonstrates the explicit
equivalent. These are alternative bindings, not two calls to the same declaration in one step.

    from structure import *
    from structure.plugin.pyspark import *

    class Order(Schema):
        order_id = string(nullable=False)
        quantity = long(nullable=False)

    class OrderMetrics(Schema):
        rows = long(nullable=False)
        total_quantity = long(nullable=True)

    @transform
    class MeasureAcceptedOrders(Transform):
        orders = input(Order)
        accepted = output(Order)
        quality = observation(OrderMetrics)

        def accept(self, order: Order) -> Order:
            where(order.quantity >= 0)
            observe(OrderMetrics(
                rows=count(),
                total_quantity=sum(order.quantity),
            ))
            return Order.project(order)

With a matching input frame containing quantities -1, 2, and 3 and a session configured for an exact 4.1 profile,
the caller's workflow is:

    result = MeasureAcceptedOrders(orders=frame).run(session)
    result.accepted.collect()
    metrics = result.quality.get()
    assert isinstance(metrics, OrderMetrics)
    assert metrics.rows == 2
    assert metrics.total_quantity == 5
