# Add a typed, migration-friendly `json_tuple` generator

This ExecPlan is a living document. Maintain it under `docs/dev/auto/Plans.md` while the feature is implemented.

## Purpose / Big Picture

Structure users migrating PySpark code will be able to extract several top-level JSON values in one
compiler-visible operation, preserving PySpark `json_tuple`'s nullable-string output while retaining Structure
schemas, generated code, online execution, and streaming/Connect classification.

The feature closes the existing `json_tuple` multi-column-schema gate without introducing a generic multi-output
expression system.

## Decision Log

- Decision: Model `json_tuple` as a narrow row-preserving generator, not a scalar expression or a general multi-output framework.
  Rationale: Spark emits sibling columns, while Structure's existing generator mechanism already represents declared multi-column scopes safely.
  Date/Author: 2026-09-30 / Codex and user.

- Decision: Use a declared nullable-string schema plus optional output-to-JSON-member mapping.
  Rationale: The schema makes every generated output visible to the compiler; mapping preserves common PySpark alias migrations.
  Date/Author: 2026-09-30 / Codex and user.

## Context and Contract

Add this public helper:

    json_tuple(value, *, to: type[Schema], fields: Mapping[str, str] | None = None, scope: str | None = None) -> RowScope

`value` must be a declared String expression. `to` must declare one or more nullable String fields. The returned
`RowScope` exposes those fields for ordinary output-schema construction.

`fields` maps a logical Structure field name to its literal top-level JSON member name. Unmapped fields use their
logical field name. Mapping keys must be declared schema fields; values must be strings. Schema declaration order
determines PySpark argument and output order; mapping order has no meaning.

The helper delegates to `F.json_tuple`, preserving Spark behavior for null input, malformed JSON, missing members,
scalar serialization, and duplicate member requests. It does not admit JSONPath syntax, dynamic member expressions,
nested extraction, inferred schemas, type conversion, or the PySpark 4-only table-valued-function form.

The operation is row-preserving: every input row produces exactly one generated tuple. Generated physical columns must
not collide with existing input columns. It is supported for ordinary PySpark `>=3.5,<4.1`, Spark Connect, and
stateless streaming once live evidence passes.

## Plan of Work

Add immutable `JsonTuplePlan` and `PySparkJsonTupleRecipe` records carrying the source expression, scope, schema, and
schema-ordered `(output_field, json_member)` pairs. Extend `OperationPlan` and `PySparkOperationRecipe` with a
`json_tuple` member and an operation constructor whose capability is `generator/json_tuple`, cardinality is
`ROW_PRESERVING`, and streaming support is `COMPATIBLE`.

Add `json_tuple(...)` beside the public generator helpers and capture it through the existing generator capture service.
Validate input type, schema shape, mapping, scope, and physical-column collisions before compilation. Generalize the
collision diagnostic currently named for `posexplode_struct` so it names the failing helper.

Extend symbolic rewriting, relation-read validation, UDF diagnostics, traceability, streaming classification, lowering,
and generated-module imports to recognize the operation. Traceability records the source expression, scope, schema, and
resolved member mapping.

Add generated and online executors using the same schema-ordered names:

    frame.select("*", F.json_tuple(payload, "customerId", "tier").alias("customer_id", "tier"))

Use declared physical schema aliases for output columns. Do not add casts or temporary parsing columns.

Document the helper in the expressions and API catalogs, remove its multi-column-schema gate from the active JSON/CSV
descriptions, and update batch and streaming coverage ledgers. Retain the dynamic-schema gate.

## Surprises & Discoveries

- Observation: The multi-column output-schema gate is genuine, but does not require a new generic abstraction.
  Evidence: Existing typed generators already represent declared multi-column scopes with schemas, aliases, recipes,
  renderers, online execution, traceability, and streaming classification. `json_tuple` needs its own row-preserving
  contract.

## Outcomes & Retrospective

Focused compiler and compatibility checks pass (41 tests, plus the generator parity matrix). Static lint, typing, and
the final repository-wide `make build` pass. The focused parity scenario passed on PySpark 3.5.0, PySpark 4.0.0,
Spark Connect 3.5.0, and Spark Connect 4.0.0; each run exercised native Spark behavior for present, missing, null,
malformed, numeric, Boolean, and nested-object JSON values through both generated and online execution. The active
multi-column-schema gate was removed for declared-schema `json_tuple`; dynamic schema inference remains gated.

## Idempotence and Recovery

The feature is additive. If implementation stops midway, keep the catalog status design-gated and do not export the
public helper until symbolic capture, rendering, execution, and parity tests agree. Re-run focused tests after each
milestone; preserve existing `from_json` and `get_json_object` behavior.
