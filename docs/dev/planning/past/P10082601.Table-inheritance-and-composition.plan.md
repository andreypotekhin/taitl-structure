# Preserve Delta and Iceberg tables through inheritance and composition

This ExecPlan follows [Plans.md](../../auto/Plans.md). It records the implementation, evidence, decisions, and retrospective
for table-transform inheritance and composition.

## Purpose / Big Picture


A developer should be able to inherit a table transform, replace an inherited method, or extend it with `super()`,
using the same scheduling rules as DataFrame transforms. Independent transforms should also pass an existing Delta
or Iceberg table from one composed stage to another, preserving its identity and validating the schema expected by
each consumer. Both online execution and generated PySpark must perform the same native operations in the same order.

Success is visible in a small pipeline: a parent cleans a caller-owned table, a child extends that cleanup, and a
second composed stage reads or mutates the resulting table. The returned Delta object is the caller's original
handle; the returned Iceberg value is the original catalog identifier. A declared schema transition becomes usable
by a later stage after the transition commits.

This work does not adapt DataFrame inputs or outputs to table storage through inheritance. It does not persist
intermediate DataFrames, create tables, change provider versions, add streaming table effects, or add transactions
across steps. The caller continues to provide tables, storage, catalogs, credentials, and provider configuration.

## Surprises & Discoveries


The starting compiler already handled ordinary effect method ordering for both providers. A child override without a
parent call replaced the inherited step; an override with `super()` produced two separate effect steps. The probe printed:

    delta_table Replace [('clean', True, [('delete', 'orders')])]
    delta_table Extend [('Base.clean', True, [('delete', 'orders')]), ('clean', True, [('delete', 'orders')])]
    iceberg_table Replace [('clean', True, [('iceberg_delete', 'orders')])]
    iceberg_table Extend [('Base.clean', True, [('iceberg_delete', 'orders')]), ('clean', True, [('iceberg_delete', 'orders')])]

These initial observations were compile-only; dedicated table tests and live evidence were subsequently added.

`ComposeTransformGraph._inputs` and `ComposeTransformPlans._inputs` construct new `InputPlan` objects without copying
`binding`. `ComposeTransformGraph._outputs` similarly constructs outputs without copying that field. The probe showed:

    TableReader inputs [('rows', 'delta')] outputs [('selected', 'dataframe')]
    Graph inputs [('rows', 'dataframe')] outputs [('selected', 'dataframe')]

`RewritePySparkStepBody` does not rewrite `delta_mutations`, which holds both Delta and Iceberg operations. Fixing input
flags alone therefore cannot fix composed mutations. Table targets, row sources, and evolving output slots must also
be rewritten.

Online final table outputs are currently looked up by their public name. Nested stage outputs always take the ordinary
DataFrame output path. Generated outputs likewise index table dictionaries by the output name, including synthetic
stage output names. Renaming an output or exposing nested outputs therefore needs explicit table identity routing.

A child that replaces an ordinary `output(Order)` with `delta_output(Order)` currently compiles without creating a
write. This plan rejects that inherited declaration change; it does not add automatic persistence.

Generated inherited/composed classes use a separate renderer path from standalone classes. That path initialized Delta
table bindings but omitted the equivalent Iceberg registry setup, so generated steps received the catalog identifier
where they expected the validated DataFrame relation. Adding the missing registry initialization and schema validation
made generated Iceberg inheritance and handoff match online execution. Generated Iceberg integration also exposed an
existing runtime contract: the renderer passes materialized `StructType` schemas to the Iceberg validator, so the
validator now accepts both serialized Structure schemas and already-materialized Spark schemas.

## Decision Log


Decision: Preserve inherited declaration kinds and table schemas. Rationale: inheritance customizes a pipeline's
methods without silently changing storage or performing schema evolution. An inherited declaration cannot switch
between DataFrame, Delta, and Iceberg, or between a provider's input, output, and mutable-table roles. An overridden
table declaration must retain exact schema identity. Existing DataFrame-to-DataFrame declaration behavior stays as it
is. A separately named table declaration is allowed. Date/Author: 2026-10-08 / User and Codex.

Decision: Use existing method scheduling for tables. Rationale: users should have one inheritance model. An inherited
method runs at its parent position; an override replaces it there; a supported parent call schedules the selected
parent implementation immediately before the child step. Parent-first ordering, direct-base order, diamond
deduplication, and sibling-name ambiguity rules remain unchanged. Date/Author: 2026-10-08 / User and Codex.

Decision: Compose existing table references, with no implicit conversion. Rationale: the selected use case is handing
off the same caller-owned table after mutation or evolution. A table output may satisfy a same-provider `*_input` or
`*_table` consumer with the exact declared schema. The consumer declaration explicitly selects its read or mutation
role. DataFrame/table and Delta/Iceberg connections fail at compilation, even when schemas match. Date/Author:
2026-10-08 / User and Codex.

Decision: Treat wrapper declarations as roles too. Rationale: a wrapper `*_input` may supply a matching stage
`*_input`, including its already-supported explicit evolution operation, but cannot supply a stage `*_table`. A wrapper
`*_table` may supply either input role for that provider. Wrapper outputs must preserve the selected stage output's
provider, role, and schema; they may rename it. Date/Author: 2026-10-08 / Codex.

Decision: Represent table identity separately from row-relation sources. Rationale: stage names, output aliases, and
schema transitions must not change the table registry key or turn a handle into a DataFrame. Use additive provenance
fields described below rather than embedding provider objects in compiler plans. Date/Author: 2026-10-08 / Codex.

Decision: Refresh and validate table consumers when their steps execute. Rationale: a consumer of an evolved schema
must validate after its producer commits, and another alias must not retain a stale relation after a mutation. Table
outputs refer to the live table, not a saved stage snapshot. Historical reads remain explicit provider operations.
Date/Author: 2026-10-08 / Codex.

Decision: Retain native commit and failure semantics. Rationale: steps may commit separately. Do not retry uncertain
commits, roll back earlier effects, or promise that a fresh read excludes concurrent commits. If a later step fails,
earlier commits remain and the native exception retains transform/step context. Date/Author: 2026-10-08 / Codex.

caller-owned table identity through both composition APIs. Spark-free contracts cover declaration rejection, parent

## Context and Orientation


All paths below are relative to the repository root. Use the existing Poetry environment and run commands from that
root. A transform invocation is a deferred binding of runtime values to declared inputs. A step is a compiled method.
A stage is one complete transform inside either a class-body composition graph or an invocation `.to(...)` pipeline.
An effect is a retained operation that changes a table during execution, even if no later row result uses it.

Declarations live in `src/structure/core/dsl/model/transforms/Transform.py` and the provider `bindings.py` modules
under `src/structure/plugin/pyspark/delta/` and `src/structure/plugin/pyspark/iceberg/`. Provider inputs use the internal
binding strings `delta` and `iceberg`; mutable declarations use `delta_table` and `iceberg_table`. Provider output
declarations also use `delta` or `iceberg`, with the declaration position distinguishing their role. These strings are
compiler metadata, not native table values. Delta runtime values are native handles; Iceberg values are identifiers.

`src/structure/core/compiler/frontend/commands/CompileTransform.py` collects declarations, compiles methods, and
constructs the target-neutral plan. `CompilerTransformMemberCollector.py` and `PatchParentStepCalls.py` in the adjacent
`logic/` directory implement effective methods and separate parent-call scheduling. `_invoke_parent_step` currently
requests symbolic result arguments without preserving provider binding; `AuthoringAPI.result_arguments` in the PySpark
plugin currently returns ordinary `RowScope` values for all results. Table-returning parent calls need typed provenance.

`ComposeTransformPlans.py` handles `.to(...)`; `ComposeTransformGraph.py` handles class-body stage assignments. Both
flatten ordered stages into one plan, rewrite relation names, and retain named stage outputs. Their shared provider
body rewrite is `src/structure/plugin/pyspark/symbolic_execution/commands/RewritePySparkStepBody.py`.

The immutable plan types are in `src/structure/plugin/api/v1/model/`. PySpark lowering is under
`src/structure/plugin/pyspark/compiler/`, online execution is in
`execution/logic/running/RunOnlinePySparkTransform.py`, and generated code is produced by
`render/logic/modules/RenderPySparkTransformModule.py` and `render/logic/steps/RenderPySparkStep.py` within that plugin.
Online execution keeps separate table registries and DataFrame maps. A canonical table source means the external
input name identifying one caller-supplied table in those registries; it is stable across internal relation names.

The working tree contains unrelated ongoing changes. Preserve them, including partially staged documentation and
PySpark work. Inspect the current diff before each implementation milestone; never reset the workspace or stage it all.

## Interfaces and Dependencies


Keep the six public provider declaration functions and existing composition syntax. Add no provider dependencies or
new runtime profiles. Preserve the separation between target-neutral compiler structure and provider-native behavior.

Add `table_source: str | None = None` to `StepInputPlan`, `StepResultPlan`, `StepAuthoringResult`, and `OutputPlan`.
Add `binding: str = "dataframe"` to `StepResultPlan`. The provenance field identifies the canonical table source;
`source`, `lane`, and `frame` continue to identify row relations. DataFrame entries leave provenance unset.

Add `table_sources: tuple[tuple[str, str], ...] = ()` to `StepAuthoringCapture`. Each pair maps a table result lane to
the target relation source reported by the provider capture. Core resolves that relation through input or preceding
result provenance to the canonical table source. Ambiguous or missing provenance for a table result is an error, not
a fallback to its public output name. This lets Core route tables without inspecting opaque mutation payloads.

Carry provenance into `PySparkOutputRecipe` and `PySparkStepResultRecipe`. Add a default-empty `table_inputs` tuple of
`StepInputPlan` values to `PySparkStepRecipe`, populated with the step's table inputs. Keep metadata serializable,
include it in fingerprints, and preserve it through optimizer rewrites. Update plugin API snapshots and compatibility
tests for additive defaulted fields; old DataFrame plans must continue to construct and run with their defaults.

### Milestone 2: Preserve inherited declarations and override semantics

Update `AuthoringAPI.result_arguments` to return provider table scopes for parent table results, with their schema,

merge result can be used by a compatible child mutation. An evolving parent result can be forwarded as its declared
output; it cannot become a mutable declaration implicitly. Additional mutation of that evolved output belongs in a
later explicitly declared table-consuming stage.

Handle pure parent delegation too: `super().clean(order)` with no local mutations, or `return super().apply(...)`,
retains the parent operation once and forwards its table reference without inventing another mutation. Record parent
table results in the active symbolic context when parent result arguments are created. Classify the child's body as
table forwarding only when a scheduled parent establishes the matching table result and the child records no local
operations. Represent it with a default-false `table_forward` flag on `PySparkStepBody` and `PySparkStepRecipe`; retain
its step identity and applicable validation while executing no native write. An empty mutation method with no parent
delegation remains invalid. Reject forwarding a read-only table into an undeclared table output.

Preserve existing `super()`, explicit base-call, and two-argument `super` resolution. Schedule a selected parent once
under the existing parent-call rules. A parent call schedules the whole parent step before the child step, matching
DataFrame behavior; it does not splice a commit into the middle of a captured child body. Tests must cover secondary
table inputs as well as the driving input, so refresh is not accidentally limited to the first parameter.

This milestone is complete when replacement, extension, delegation, schema-returning results, multiple inheritance,
and prohibited declaration changes all compile as specified without regressing DataFrame inheritance.

### Milestone 3: Preserve references through composition


Introduce a small shared `ValidateTransformBinding` helper in frontend logic for provider/kind/role checks. Use it in
both composition paths, including explicit wrapper bindings, automatic `.to(...)` matching, and public output selection.
Filter automatic candidates by provider and exact schema before applying the existing alias/name preference. When a
same-schema candidate has the wrong provider or relation kind, report that mismatch rather than a misleading missing
input. Deduplicated external inputs must also agree on provider and role; do not let a later binding overwrite either.

Preserve complete `InputPlan` metadata with `dataclasses.replace` where possible. A wrapper `*_table` is an
`OutputDeclaration` with a synthesized input entry, so resolve it by declared identity/role rather than accepting only
`InputDeclaration`. Keep the outer wrapper role on its external plan input and the consumer role on each step input.
Continue rejecting ordinary output declarations as external inputs.

Rewrite table provenance independently of relation frame names in both composers. Each table output carries the
canonical external source from its producer; a consuming step keeps its own mapped row source and takes that table
source. Forward it through nested stages, repeated stage classes, aliases, wrapper output renaming, and multiple
table outputs. Distinct tables with identical schemas remain distinct references. Existing forward-reference/cycle
checks and explicit binding disambiguation continue to apply.

In `RewritePySparkStepBody`, rewrite every provider mutation's `target`, optional row `source`, and optional `output`
using the complete stage name map, including current step result names. Preserve provider expressions, lexical scope
names, clauses, selectors, schema-evolution flags, and declared result schemas. Apply the same rewriting to captured
mutation results retained inside the body so capture metadata and payload do not disagree. In typed SQL relation
metadata, rewrite table references through the same mapping; keep SQL placeholder names and text unchanged.

Do not infer a table output from a row projection. Every `*_output` needs captured provenance from its supported
transition or an explicit forwarded stage result. Table-only stage connections remain batch operations. This milestone
is complete when both graph and `.to(...)` plans preserve bindings and unambiguous identities without starting Spark.

### Milestone 4: Execute and render the same table flow


In online execution, initialize native registries from canonical external inputs, with existing preflight validation.
Before each step, use `table_inputs` to resolve all table parameters, bind their local registry aliases, refresh their
row sources, and validate the step's expected table schemas and applicable provider checks. This happens after earlier
steps commit. Do not preflight an evolved consumer schema against the producer's original table. Preserve the existing
Delta expression/name/off CHECK precedence and Iceberg evolved-schema validation behavior.

After mutation, keep registry aliases tied to the same native reference and refresh row sources at subsequent table
consumption. Do not reinterpret an already produced ordinary DataFrame as a live table or replace explicitly
historical relations with latest-state reads. An alias whose old schema no longer matches fails before it is next used;
returning a table reference does not freeze its data or schema at the earlier stage.

Handle `table_forward` before ordinary mutation/projection execution: forward the already established handle and row
source without a second write. Resolve every final and nested table output through `output.table_source`; preserve its
public name, aliases, declared schema metadata, and stage path. DataFrame outputs keep their existing projection path.
Earlier stage table results remain references to the live table, including after a later stage changes its schema.

Mirror the same binding, refresh, validation, forwarding, and result routing in generated execution. Update
`MapPySparkStep`, `MapPySparkOutput`, and the renderer components named above. Generated temporary output names must
not become table registry keys. Preserve existing native error context and retain effects during optimization even
when their row results are unused. Do not add DataFrame raw hooks to mutation steps; retain existing supported hooks
on inherited read/DataFrame steps and their ordering.

This milestone is complete when online and generated tests agree on table identity, final rows, commit order,

## Validation and Acceptance


Specification tests must prove both providers inherit declarations and parent steps, replace overridden methods in
place, extend them through all currently supported parent-call forms, delegate without duplicate writes, and preserve
returned table provenance. Cover a mutable target as a secondary parameter, schema-returning merge overrides, and
evolution-method replacement/forwarding. A mismatched schema, provider, role, or table-field shadowing must produce a
corrective compile-time diagnostic. Diamond parents execute once and sibling method ambiguity still requires a child
override. Ordinary DataFrame inheritance and composition remain covered by the existing suites.

Composition tests must cover graph and `.to(...)` handoff from mutable-table and explicit-transition outputs to matching
read-only and mutable consumers. Exercise external wrapper inputs, mutable wrapper declarations, public renamed outputs,
nested stage paths, aliases, multiple same-schema tables, repeated stage classes, and effects with unused row results.
Reject cross-provider and DataFrame/table links, wrapper role escalation, missing provenance, ambiguous selection, and
undeclared evolution. Assert provider operation references use mapped relation names while output identity remains the
canonical caller binding.

For live inheritance evidence, start with rows A/open, B/legacy, and C/archived. The parent deletes legacy rows; a
replacement child deletes archived rows instead, leaving A and B. An extending child calls the parent then deletes
archived rows, leaving A. Use fresh disposable tables for each execution mode and case. Verify a pure delegation
executes the parent's operation once using provider history/snapshot evidence where the operation creates a commit.

For live composition evidence, stage A updates A/open to A/cleaned and stage B selects or updates rows matching
cleaned. Inspect collected results and final table data to prove B sees A's commit. A second case evolves a V1 table
to V2 with a nullable note field, then consumes V2 in the next stage. Use each provider's already-supported evolution
helper. Assert final and nested table results preserve the native handle or identifier, including renamed outputs.

For failure evidence, let stage A make a successful update and make stage B fail through a deterministic invalid native
write or schema check. Assert the A update remains, B's exception identifies the failing step, and execution did not
retry A. For alias freshness, update through one declared alias and consume the same table through another; the second
consumer must see refreshed rows or a clear schema mismatch after evolution. A historical read remains historical.

Compilation/generation tests do not import Spark or start sessions. Generated source parses and executes through
the existing generated-project harness. Test declared result data and commit effects, not just text patterns. All
targeted tests, the required live cases, and `make build` must pass before marking implementation complete.

## Idempotence and Recovery


The implementation introduces no storage migration. Live tests create unique disposable paths or catalog names and
clean them up using the existing fixture patterns, so reruns do not target application tables. Native operations are
not globally idempotent: never rerun a partially failed application pipeline automatically. A test rerun starts with a
new fixture and observes the documented partial-commit behavior.

If Docker, provider packages, or a required runtime lane are unavailable, retain the implementation and record the
exact failing command and missing evidence; do not substitute a skipped test or mark the plan complete. Resolve
environment failures through the repository's integration troubleshooting guidance before collecting admission evidence.

Keep unrelated local/staged work intact. Do not regenerate example artifacts wholesale or run workspace reset commands.
If an added plan field changes fingerprints or snapshots, update the relevant expectations and test default-field
compatibility explicitly. No public declaration migration is needed; previously accepted inherited storage-role changes
will now fail early with guidance to use explicit declarations or composition.
