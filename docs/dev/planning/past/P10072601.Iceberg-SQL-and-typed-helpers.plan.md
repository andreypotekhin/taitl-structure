## Purpose / Big Picture


Allow Structure transforms to read, update, append to, inspect, and maintain existing Apache Iceberg tables. First
prove that the existing typed `sql(...)` helper supports Iceberg's Spark SQL operations. Then provide Python-friendly
`iceberg_` declarations and helpers for the common operations, with roughly the breadth of Structure's Delta API.
Both stages belong to this delivery, but SQL evidence must precede helper admission.

The caller configures Spark and its Iceberg catalog and passes a table name when invoking a transform. A catalog is
Spark's configured service for resolving table names and committing table metadata. A binding connects a transform
declaration to that caller-supplied table. Structure compiles typed operations and executes them through Spark;
it does not provision catalogs or own the lifecycle of the caller's tables.

Success is observable in three executions of the same example: a Structure transform, its generated PySpark class,
and independent native Spark SQL produce the same rows, schemas, and table effects. Snapshot reads recover earlier
data, append can explicitly evolve a schema, and maintenance uses Iceberg's native operations. A snapshot is an
Iceberg table state identified by an opaque integer ID, not a sequential Delta commit version.

## Surprises & Discoveries


The SQL foundation already exists. `src/structure/plugin/pyspark/dsl/sql_api.py` captures SQL text, literal arguments,
relation scopes, result schemas, and optional command labels. `ExecutePySparkSql.py` delegates to `spark.sql` and
adds a transform-context note to immediate backend exceptions. The typed SQL design already mentions caller-owned
Iceberg configuration, but that statement is not live Iceberg evidence.

SQL currently substitutes string relations during compilation and treats row scopes as DataFrame bindings. An
Iceberg mutation target needs a runtime table identifier instead. Extending relation bindings must preserve that
distinction without specializing the compiled artifact to one caller's table name.

The runtime SQL operation currently obtains Spark from `df.sparkSession`. SQL operations without a DataFrame source
therefore need an explicit execution path using the session's Spark object. Confirm source-free frontend discovery
as well as execution; changing this one runtime expression alone is not sufficient.

The first native integration experiment passed its three Iceberg tests on Spark 3.5.3 with Iceberg 1.12.0. The
existing Delta tests also passed after restoring the Docker image's exact PySpark pin after installing `delta-spark`.
The repository's ignored local Compose environment had requested PySpark 3.5.0, which caused pip to select 3.5.9
through Delta's broad dependency and made its exact-runtime integration test fail. The run used a one-command 3.5.3
override and the Dockerfile now reinstalls the requested Spark version after Delta installation.

Iceberg creates its first snapshot on the first data commit; creating an empty table did not create a snapshot in
the pinned run. A no-op `rewrite_data_files` procedure preserved the table and left history/snapshot metadata at one
row. Tests assert the native minimum rather than assuming DDL or no-op maintenance creates a commit.

`NormalizePySparkSqlCommandResult.py` builds a lazy result using a join against the returned command DataFrame. It
does not by itself prove command completion or prevent repeated execution on every backend. Discarded results,
repeated collection, and Connect analysis must be checked with observable native commits before making guarantees.

Delta's table declarations are not isolated entirely within its plugin package: the core frontend recognizes Delta
binding kinds and evolution results. Iceberg requires deliberate frontend integration, not merely new prefix aliases.

The Compose runner launches Delta tests in a separate Python process. Connect 4.1 also installs Delta-specific
server extensions and a catalog. Iceberg needs its own startup configuration and evidence process so that tests do
not accidentally inherit an incompatible session. Keep existing Delta evidence intact.

The first full 3.5 run invoked the dedicated Iceberg suite and then rediscovered it under the broad integration test
root without the Iceberg jars/catalog. The dedicated suite had already passed; the repeated tests failed from missing
Iceberg setup. The runner now excludes that directory from the general process after its dedicated lane, ensuring
each selected backend runs the suite once under the correct isolated configuration.

The corrected runtime initially collected only the three native cases from the Iceberg test directory. The runner now
passes the native, typed-SQL, and typed-helper test modules as explicit paths so live SQL and generated-helper parity
cannot be silently omitted by directory selection.

The first typed SQL receipt exposed an ambiguous Spark reference because default and native command metric columns had
the same names after a join. Normalization now aliases the native metric columns before selecting the public schema;
command execution is eagerly detached so repeated receipt reads cannot resubmit the command.

Iceberg's Spark schema reports can be looser about field nullability than the table's DDL, so binding validation checks
column names and data types while preserving Structure's declaration checks for helper assignments and append
evolution. Generated helper code now initializes runtime variable state for provider operations, emits quoted update
columns without nested f-strings, and imports temporal literals used by maintenance procedure arguments.

The Spark 4.0 direct-test container must run from `/tmp`: otherwise Spark writes relative artifacts beneath the read-only
`/workspace` mount before the Iceberg test fixture is ready. The integration runner already uses `/tmp`; direct evidence
used the same working directory.

Upstream Iceberg schema merging uses DataFrameWriterV2, a native writer addressed by table name. It requires both
the table property `write.spark.accept-any-schema=true` and the per-write option `mergeSchema=true`. The selected
evolution design consequently needs one native writer operation alongside SQL-based helpers.

Iceberg's incremental append reader does not include deletes or overwrites and is not exposed by Spark SQL syntax.
Do not label that reader as a Delta-compatible change feed. Changelog helpers are deferred; supported native SQL
procedures remain accessible through `sql(...)`.

## Context and Orientation


Structure compiles Python transform methods into an execution recipe: immutable data describing ordered operations,
bindings, schemas, and expressions. The PySpark plugin either runs that recipe directly or renders generated Python
that runs equivalent operations. Changes need both paths; a generated string assertion alone is not execution proof.

The existing public Delta pattern is documented in `docs/api/DeltaIceberg.api.md`. Its implementation lives under
`src/structure/plugin/pyspark/delta/`: `bindings.py` declares tables, `operations.py` captures typed operations,
`model.py` contains their immutable payloads, and `runtime.py` performs native work. Delta accepts a native DeltaTable
object. Iceberg will instead accept a fully qualified name, such as `warehouse.sales.orders`.

The SQL design is in `docs/dev/design/TypedSqlExecution.design.md`. Capture is in
`src/structure/plugin/pyspark/dsl/sql_api.py` and `dsl/operations/SqlPlan.py`. Lowered SQL data is represented by
`src/structure/plugin/pyspark/compiler/model/PySparkSqlRecipe.py`. The plugin's
`compiler/logic/maps/MapPySparkStep.py` maps captured operations to executable recipes. Execution and code generation
are orchestrated by `execution/logic/running/RunOnlinePySparkTransform.py` and
`render/logic/steps/RenderPySparkStep.py`, respectively, under the same plugin directory.

`src/structure/plugin/pyspark/api/AuthoringAPI.py` constructs symbolic row and Delta table scopes. The core frontend
in `src/structure/core/compiler/frontend/commands/CompileTransform.py` discovers step inputs, effect steps, and
table-result lanes; `frontend/logic/DeltaEvolution.py` helps identify schema transitions. A lane is a named relation
that passes between transform steps. Review these binding-sensitive sites together so an Iceberg output is never
mistaken for a DataFrame or required as an invocation argument.

Capability admission lives in `src/structure/plugin/pyspark/capabilities/model/PySparkCapabilities.py` and is checked
during lowering. Admission means Structure has tested that operation for the selected Spark profile and variant.
Spark Connect is a remote Spark session: extensions and catalogs must exist on its server, and client JVM access is
not available. Use public Spark SQL and DataFrame APIs in both variants.

The existing live Delta example is `tests/integration/pyspark/v11/test_delta_transform_live.py`. Docker configuration
is under `infra/compose/`; its tracked environment template is `.env_example`, not `.env.example`. The runner script
is `infra/compose/images/pyspark/run-integration.sh`, dispatched by `scripts/run_integration.py`. Spark 4.1 presently
selects only runtime-version tests and the V11 directory. New Iceberg tests must be included explicitly rather than
relying on broad test discovery.

### Milestone 3: Table bindings, data operations, and SQL interoperability


Create `src/structure/plugin/pyspark/iceberg/` with focused declaration, operation, model, runtime, and SQL-rendering
modules. Export the public names through `src/structure/plugin/pyspark/__init__.py`. Follow Delta's authoring pattern
for symbolic table scopes, effect results, typed merge clauses, and output assignment, but use distinct Iceberg
payloads and capability names. Factor shared table-binding frontend logic only where it removes duplication; do not
make this a general plugin redesign or rename public Delta APIs.

Integrate Iceberg declarations through the core frontend and PySpark authoring API. Preserve the runtime table name
separately from its current DataFrame. Resolve and validate the name as an Iceberg table in the session, validate its
declared schema under the existing validation policy, and refresh relation state after table effects. Use public
Spark catalog/SQL metadata for provider checks, including Connect; do not inspect client JVM internals or infer that
every table in a mixed catalog is Iceberg. Reject DataFrame, DeltaTable, and PyIceberg table objects as Iceberg
bindings.

Extend SQL binding recipes to distinguish runtime table identity from ordinary relation DataFrames. A table scope in
`relations={"target": order}` inserts the quoted runtime identifier; it must not become a temporary view used as a
write target. A projected ordinary row scope continues to be a DataFrame binding. Preserve existing caller-owned raw
SQL string relation substitutions for compatibility. A runtime binding string is an identifier, not arbitrary SQL:
parse multipart names respecting backtick quoting and quote each component, including embedded backticks. Require an
explicit catalog and at least a table component; do not split blindly on dots inside quoted components.

Implement ordinary reads, snapshots, update/delete, append, and merge. Lower helper expressions to generated SQL from
the typed expression tree, with target/source aliases and separate value encoding. Reuse existing expression metadata
and function admission; never turn Python `repr` into SQL or use private JVM expression strings. Unsupported expression
forms must fail compilation with an actionable reference to the SQL alternative. Validate expressions and field
assignments before running a mutation. Parameterize values where native Spark supports the statement position; for
positions that do not accept parameter markers, use one tested literal encoder, including UTC timestamps and nulls.

Record ordered Iceberg effects in the same executable operation sequence as SQL. Do not maintain separate batches
that move helper mutations across handwritten SQL or reads. Track affected table identity so later bindings reload
after helper writes. Because arbitrary SQL is opaque, invalidate invocation-local Iceberg read frames after explicit
SQL calls before any later table read; do not pretend to infer affected tables. Historical result frames retain their
chosen snapshot. No helper performs Spark work during symbolic compilation.

Add `tests/specifications/iceberg-transform/`, `tests/user_stories/iceberg_tables/`, and
`tests/integration/pyspark/iceberg/test_iceberg_transform.py`. Prove same-schema table results, read-only input rules,
multiple tables with the same schema, `@step` disambiguation, source-free reads, and compiled artifact reuse with
different table names. Mix SQL and helpers in a single transform and assert observed order. The milestone passes
when direct, generated, and native executions agree and existing Delta tests remain unchanged in behavior.

### Milestone 4: Evolution, inspection, rollback, and maintenance


Implement evolving append as a single native DataFrameWriterV2 append using `mergeSchema=true`. Require the caller's
table to have `write.spark.accept-any-schema=true`; diagnose a missing prerequisite with the exact remedy, without
altering the property or session. Connect the old `iceberg_input` schema to a distinct `iceberg_output` schema through
the returned operation result. Check compatibility before the append and the resulting schema after the commit.

Initially admit additive nullable fields, including nested fields where the native evidence proves them; preserve
existing column types and nullability. Match source columns by declared physical names, not positions. Require the
source projection to supply the intended new output shape. Reject inferred renames, drops, type changes, and implicit
evolution on ordinary writes. Do not expose merge-time evolution merely because Delta has it. SQL remains the route
for other schema changes. A post-commit schema mismatch must say that the write may already have committed.

Add history/snapshot inspection and generic typed metadata reads. Implement rollback using the native snapshot or
timestamp procedure; do not turn it into a Delta-style restoring data commit or promise schema restoration. Reload
and validate the current schema after rollback. Add data-file and manifest rewriting, snapshot expiration, and orphan
cleanup as separate helpers with native procedure semantics. Quote the procedure catalog as an identifier and pass
the namespace/table name as a procedure string argument. Do not pass a fully qualified name to a procedure that
expects a name within its own catalog.

Maintenance helpers are explicit effects finalized by `.execute()`, retaining the bound table result. Detailed native
metrics remain available through `sql(..., to=UserSchema)` without being reduced to normalized affected-row counts.
Keep native retention checks and option meanings. Omitted optional procedure arguments are omitted from SQL so the
pinned native default applies. Do not combine expiration with orphan deletion or automatically perform either after
rewriting files. Test destructive maintenance only against disposable tables and owned test warehouses.

This milestone passes when evolving append produces the declared output shape, historical reads return the earlier
shape, rollback follows native ancestry rules, rewriting preserves rows, and retention cleanup matches direct native
procedures. Include empty tables and zero-work maintenance. For snapshot IDs and timestamps, compare behavior within
each independently created table rather than expecting generated IDs to match across reference executions.

## Idempotence and Recovery


Each integration run uses unique test namespaces, table names, and warehouse directories within the shared disposable
test root. Cleanup is scoped to those names; never target a caller's configured production catalog or storage path.
Retain existing dependency caches and unrelated warm services. Stop only the extra gateway process created by this
suite. Tests should clean up in a finalizer, while failed-run evidence identifies any owned resources left behind.

There is no repository data migration and no automatic modification of caller table properties. An individual native
write follows Iceberg's commit behavior. Several transform operations are not one transaction, and a transport error
or post-write validation error may leave a committed result. Structure does not automatically replay such operations.
Reproduce ambiguous outcomes on a fresh disposable table, inspect history, and record the result before retrying.

If a lane cannot validate a promised capability, retain the failing reproduction and leave that capability unadmitted.
Continue independent work without claiming the requested delivery complete. Any change to the selected public scope

## Interfaces and Dependencies


### Declarations and outputs


Expose `iceberg_input(schema: type[Schema])`, `iceberg_table(schema: type[Schema])`, and
`iceberg_output(schema: type[Schema])`. The first two accept invocation strings naming an existing table in an explicit
catalog. `iceberg_input` is read-only except as the source binding of an explicit evolving append. `iceberg_table`
supports reads and same-schema effects. `iceberg_output` is a schema-transition result and never an invocation input.
Schema transitions use a distinct output declaration. Same-schema methods can return `None` or their mutation result
with the bound schema annotation, following existing Delta lane resolution.

Table outputs expose the supplied identifier string. Ordinary `output(Schema)` exposes a DataFrame. In recipes, retain
logical binding names and runtime selector expressions rather than concrete invocation values. No public
`IcebergTableRef`, PyIceberg dependency, or new standalone session API is introduced.

A complete representative authoring example, after implementation, is:

    from structure import *
    from structure.plugin.pyspark import *

    class Order(Schema):
        id = string(nullable=False)
        status = string(nullable=False)

    class ApplyOrders(Transform):
        incoming = input(Order)
        orders = iceberg_table(Order)

        def apply(self, incoming: Order, order: Order) -> None:
            iceberg_update(order, where=order.id == "A", set=Order(status="paid"))
            iceberg_append(order, incoming).execute()

    result = ApplyOrders(incoming=incoming_df, orders="warehouse.sales.orders").run(session)
    assert result.orders == "warehouse.sales.orders"

Here `incoming_df` and `session` are caller-created runtime values. If schema-based inference is ambiguous, use
`@step` to bind the method parameters explicitly, exactly as with existing Delta transforms.

### Reads and mutations


Expose `iceberg_snapshot(target, *, snapshot_id=None, timestamp=None)` with exactly one selector; the direct step
return annotation declares the selected snapshot's schema. Snapshot IDs are integer scalars. Timestamp selectors use
timezone-aware datetime scalars normalized to UTC. Both allow compatible runtime `variable(...)` values. Current
reads use the bound table directly. Branch/tag selectors and incremental/changelog readers are outside helper scope.

Expose `iceberg_update(target, *, where, set)` and `iceberg_delete(target, *, where)` as immediate symbolic effects,
and `iceberg_append(target, source)` / `iceberg_merge(target, source, *, on)` as builders ending in `.execute()`.
Predicates are Boolean Structure expressions; explicit `where=True` affects all rows. Assignments use schema objects,
with partial updates and complete required insert fields. Append aligns source fields by physical name. Bind source
DataFrames natively where supported; any required private temporary view must have collision-safe naming and survive
until its lazy native plan resolves, with cleanup after command completion.

The merge builder exposes `when_matched_update(set=..., condition=None)`, `when_matched_delete(condition=None)`,
`when_matched_update_all(condition=None)`, `when_not_matched_insert(values=..., condition=None)`, and
`when_not_matched_insert_all(condition=None)`. Also expose `when_not_matched_by_source_update(set=..., condition=None)`
and `when_not_matched_by_source_delete(condition=None)`, with separate capability checks where the tested native
runtime restricts these clauses. Preserve clause order and native multiple-match errors; do not deduplicate sources.
Unfinished builders must fail compilation instead of silently doing nothing.

Append adds `.with_schema_evolution(to=NewSchema)`. Require that `to` matches the destination `iceberg_output` and that
the evolving append is the returned table effect of its transition step. Use native writer schema merging, not an
ALTER-then-INSERT sequence. Initial helper evolution is additive nullable fields as specified in milestone 4.

### Inspection and maintenance


Expose `iceberg_history(target, *, limit=None)` and `iceberg_snapshots(target, *, limit=None)` as typed relation reads.
The direct return schema declares the requested fields; project those fields from native metadata and validate their
types. If a limit is supplied, order newest-first by `made_current_at` for history or `committed_at` for snapshots,
using snapshot ID as a deterministic tie-breaker. Without a limit, make no result-row-order promise.

Expose `iceberg_metadata(target, *, kind, to)` with native metadata kinds `history`, `snapshots`, `files`, `manifests`,
`partitions`, and `refs`. `to` is a Structure schema; it permits selecting a typed subset without freezing every
provider metadata column as a public Structure class. Other metadata relations remain accessible through SQL.

Maintenance builders use these signatures:

    iceberg_rollback(target, *, snapshot_id=None, timestamp=None)
    iceberg_rewrite_data_files(target, *, strategy=None, sort_order=None, where=None, options=None)
    iceberg_rewrite_manifests(target, *, use_caching=None, spec_id=None)
    iceberg_expire_snapshots(target, *, older_than=None, retain_last=None)
    iceberg_remove_orphan_files(target, *, older_than=None, dry_run=False)

Each ends in `.execute()` and is valid as an effect on `iceberg_table`. Rollback requires exactly one selector and
preserves the bound schema. Use Iceberg's native rollback-to-snapshot or rollback-to-timestamp procedure; ancestor
restrictions remain native. Data-file `where` accepts a typed predicate. `strategy`, `sort_order`, and `options` are
native procedure settings: validate their structure and supported combinations, and encode string values as literals,
not executable SQL fragments. `options` is a mapping of string keys to string values. Omitted arguments use the native
defaults; do not invent Delta retention defaults. Selectors and retention scalars can use compatible runtime variables;
procedure strategy, metadata kind, and mapping shape are compile-time choices.

Detailed procedure outputs are available through the existing typed SQL API. For example, a user schema declaring
native rewrite counts can be supplied as `to` for `CALL`, without renaming those counts to affected-row metrics.
Arbitrary supported procedure arguments and catalog administration remain available through SQL rather than expanding
every convenience signature. Do not add `iceberg_optimize` or `iceberg_vacuum` aliases in this delivery.

### Runtime dependencies and compatibility


Iceberg requires optional server-side Spark runtime jars and configured extensions/catalogs. Structure's base Python
installation must not gain an eager PySpark or PyIceberg import. Classic execution uses the caller's SparkSession;
Connect uses the existing remote session with server-installed jars. No new table service or client metadata bridge
is introduced. Preserve all existing Delta public signatures, core target selection, and generic SQL behavior.
