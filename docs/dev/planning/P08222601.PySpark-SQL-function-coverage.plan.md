# Complete the PySpark SQL Function Coverage Register and Implementation

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections as work advances. It follows `docs/dev/auto/Plans.md` and is written so a contributor can implement the work from this file and the named repository files alone.

## Purpose / Big Picture

Structure users should be able to choose a typed, compiler-visible helper for every PySpark 3.5.x/4.0.x SQL function that fits Structure's contract. Today the catalog groups a small supported subset together and leaves the rest difficult to discover. This plan turns the remaining surface into an auditable register, then implements the admissible deterministic row-local functions in family-sized slices.

The first visible result is documentation: a user can look up a function family, see the exact functions already covered, understand whether a missing function is planned, design-gated, caller-owned, or unsupported, and find the owning work item. The final implementation result is stronger: supported helpers produce typed expressions, checked diagnostics, generated PySpark, online results, and documented streaming/Connect boundaries.

The default baseline is `profile = ">=3.5,<4.1"` with ordinary PySpark. PySpark 4.1 adoption is a separate ledger and must not be silently included in this work. “Full coverage” means every function in the baseline has one explicit disposition; it does not mean accepting arbitrary SQL strings or exposing APIs whose semantics cannot be made typed and testable.

## Decision Log

- Decision: Use the intersection of PySpark 3.5.x and 4.0.x public `pyspark.sql.functions` APIs as the active inventory.
  Rationale: That is the default compatibility range in `docs/Compatibility.md`; using the newest Spark reference would turn future APIs into accidental current commitments.
  Date/Author: 2026-08-22 / Codex.
- Decision: Treat a family as `partial` until every in-scope function has either implementation evidence or an explicit non-implementation status.
  Rationale: A family row that lists only its supported examples currently hides important gaps such as `lpad`, `add_months`, and `next_day`.
  Date/Author: 2026-08-22 / Codex.
- Decision: Admit deterministic row-local functions before nondeterministic, cardinality-changing, sketch, provider, and runtime-metadata functions.
  Rationale: Deterministic scalar expressions have the smallest contract surface; the other groups need additional seed, cardinality, dependency, or ownership decisions and should not be made green by weak tests.
  Date/Author: 2026-08-22 / Codex.
- Decision: Preserve typed equivalents where they provide a stronger contract than a direct PySpark wrapper.
  Rationale: `arr_transform`, schema-carrying parsers, and typed generators make result types, aliases, nullability, and cardinality explicit. Exact-name aliases are optional and must not weaken those guarantees.
  Date/Author: 2026-08-22 / Codex.
- Decision: Admit `lpad`/`rpad` with non-negative literal lengths and non-empty literal pads, and admit `next_day` only for recognized weekday literals.
  Rationale: These constraints make generated code deterministic and keep invalid configuration errors at authoring time instead of deferring them to Spark.
  Date/Author: 2026-08-22 / Codex.
- Decision: Admit `rand()` with `reproducible=True` by default, requiring an integer seed; permit an omitted seed only with `reproducible=False`.
  Rationale: A seed makes use auditable, while the explicit opt-in preserves PySpark's unseeded form without claiming exact value reproducibility across retries, repartitioning, versions, or query restarts.
  Date/Author: 2026-08-22 / Codex.
- Decision: Classify `rand()` as stateless streaming work only on profiles and variants with passing PySpark evidence.
  Rationale: The function preserves row cardinality, but nondeterminism and backend analyzer behavior must remain visible in streaming support rather than being inferred from batch support.
  Date/Author: 2026-08-22 / Codex.
- Decision: Admit the common `asin`/`atan`/`atan2`/`cos`/`degrees`/`ln`/`log10`/`radians`/`sin`/`tan` functions as
  typed Double-returning scalar helpers.
  Rationale: Their arguments and outputs are numeric, row-local, and expressible through the existing public Spark
  function calls; Spark remains the authority for mathematical domain behavior.
  Date/Author: 2026-08-27 / Codex.
- Decision: Admit `e()` and `pi()` as non-null Double constants, `factorial(...)` as an Integer/Long-to-Long helper,
  `greatest(...)` and `least(...)` as two-or-more compatible common-type helpers, and `pmod(...)` as a common-numeric-
  type binary helper.
  Rationale: each contract is row-local, deterministic, and expressible through public PySpark functions without an
  untyped escape hatch; Spark remains authoritative for overflow and numeric domain behavior.
  Date/Author: 2026-08-27 / Codex.

## Context and Orientation

`src/structure/plugin/pyspark/dsl/expressions.py` contains row-local expression constructors and their type/nullability validation. `src/structure/plugin/pyspark/dsl/operations_api.py` contains grouped, window, and relation-level helpers. `src/structure/plugin/pyspark/dsl/generators.py` contains cardinality-changing collection helpers. `RenderPySparkExpression.py` lowers expressions to generated PySpark, while `EvaluatePySparkExpression.py` executes the supported subset directly.

`src/structure/plugin/pyspark/resources/pyspark-transformation-inventory.json` is the reviewed upstream inventory. `pyspark-transformation-coverage.json` is the machine-readable support ledger; the streaming ledgers classify whether admitted operations may receive streaming input. `docs/APICatalog.md` is the user-facing decision catalog. `docs/dev/Parity.md` is the durable parity and boundary register; `docs/dev/gated/Functions.gates.md` indexes function gates. API details belong in `docs/api/Expressions.api.md`, `Collections.api.md`, `Aggregations.api.md`, and `Windows.api.md`.

An expression is a symbolic description of a computation. A typed contract states its accepted Structure types, result type, nullability, literal-only arguments, and target-profile requirements before Spark runs it. A capability check is the compiler diagnostic that rejects a helper when the configured PySpark version or variant cannot support it. A generated test checks rendered PySpark source; an online test executes the same transform through PySpark. “Streaming classification” records whether the operation is safe and supported when the input relation is a streaming DataFrame.

## Validation and Acceptance

The inventory is accepted when every baseline PySpark SQL function has exactly one row in the machine-readable ledger and
one matching family-level explanation in `docs/dev/Parity.md` and `docs/APICatalog.md`. The eight
audited examples must be visibly correct: `hour` and `exp` remain implemented; `add_months`, `next_day`, `acos`,
`hypot`, `rand`, and `lpad` have explicit implementation or boundary status.

An admitted deterministic function is accepted only when a typed transform using it compiles without Spark, renders the expected `pyspark.sql.functions` call, executes online with expected values and null behavior, and matches generated execution on every claimed ordinary/Connect profile. `rand()` additionally requires seed-policy diagnostics, nondeterministic trace metadata, value-range tests without exact-sequence assertions, and target-specific streaming evidence. Unsupported profiles must fail with the repository's structured backend capability diagnostic and a caller remedy. A function with row multiplication, nondeterminism, provider dependency, or aggregate state must additionally pass its cardinality, seed, provider, mergeability, or streaming tests before status changes to implemented.

The overall work is accepted when `make build` exits successfully, focused tests pass, available PySpark 3.5/4.0 lanes pass, generated artifacts are fresh, and no catalog row says “supported” without a capability, diagnostic, API reference, test, and evidence path. Remaining design-gated and caller-owned families are acceptable only when their reason and remedy are explicit.

## Idempotence and Recovery

Inventory and documentation updates are additive and safe to repeat. Before editing a shared ledger, inspect its current row and preserve unrelated changes. If a function cannot be admitted without weakening the typed contract, keep or move it to `design-gated`, `caller-owned-guided`, or `unsupported` and record the decision; do not add an untyped `expr` fallback.

If live PySpark is unavailable, complete no-Spark validation and record the missing evidence without claiming runtime support. If a generated artifact changes, regenerate it through the project command and review the diff; never hand-edit generated output. If an implementation slice fails, retain the catalog row as planned and leave the focused test or diagnostic in a reproducible state for the next contributor.
