# Complete the PySpark SQL Function Coverage Register and Implementation

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections as work advances. It follows `docs/dev/auto/Plans.md` and is written so a contributor can implement the work from this file and the named repository files alone.

## Purpose / Big Picture

Structure users should be able to choose a typed, compiler-visible helper for every PySpark 3.5.x/4.0.x SQL function that fits Structure's contract. Today the catalog groups a small supported subset together and leaves the rest difficult to discover. This plan turns the remaining surface into an auditable register, then implements the admissible deterministic row-local functions in family-sized slices.

The first visible result is documentation: a user can look up a function family, see the exact functions already covered, understand whether a missing function is planned, design-gated, caller-owned, or unsupported, and find the owning work item. The final implementation result is stronger: supported helpers produce typed expressions, checked diagnostics, generated PySpark, online results, and documented streaming/Connect boundaries.

The default baseline is `profile = ">=3.5,<4.1"` with ordinary PySpark. PySpark 4.1 adoption is a separate ledger and must not be silently included in this work. “Full coverage” means every function in the baseline has one explicit disposition; it does not mean accepting arbitrary SQL strings or exposing APIs whose semantics cannot be made typed and testable.

## Decision Log

- Decision: Use the intersection of PySpark 3.5.x and 4.0.x public `pyspark.sql.functions` APIs as the active inventory.
  Rationale: That is the default compatibility range in `docs/Compatibility.md`; using the newest Spark reference would turn future APIs into accidental current commitments.
  Date/Author: 2026-08-22 / Codex.
- Decision: Treat a family as `partial` until every in-scope function has either implementation evidence or an explicit non-implementation status.
  Rationale: A family row that lists only its supported examples currently hides important gaps such as `lpad`, `add_months`, and `next_day`.
  Date/Author: 2026-08-22 / Codex.
- Decision: Admit deterministic row-local functions before nondeterministic, cardinality-changing, sketch, provider, and runtime-metadata functions.
  Rationale: Deterministic scalar expressions have the smallest contract surface; the other groups need additional seed, cardinality, dependency, or ownership decisions and should not be made green by weak tests.
  Date/Author: 2026-08-22 / Codex.
- Decision: Preserve typed equivalents where they provide a stronger contract than a direct PySpark wrapper.
  Rationale: `arr_transform`, schema-carrying parsers, and typed generators make result types, aliases, nullability, and cardinality explicit. Exact-name aliases are optional and must not weaken those guarantees.
  Date/Author: 2026-08-22 / Codex.
- Decision: Admit `lpad`/`rpad` with non-negative literal lengths and non-empty literal pads, and admit `next_day` only for recognized weekday literals.
  Rationale: These constraints make generated code deterministic and keep invalid configuration errors at authoring time instead of deferring them to Spark.
  Date/Author: 2026-08-22 / Codex.

## Context and Orientation

`src/structure/plugin/pyspark/dsl/expressions.py` contains row-local expression constructors and their type/nullability validation. `src/structure/plugin/pyspark/dsl/operations_api.py` contains grouped, window, and relation-level helpers. `src/structure/plugin/pyspark/dsl/generators.py` contains cardinality-changing collection helpers. `RenderPySparkExpression.py` lowers expressions to generated PySpark, while `EvaluatePySparkExpression.py` executes the supported subset directly.

`src/structure/plugin/pyspark/resources/pyspark-transformation-inventory.json` is the reviewed upstream inventory. `pyspark-transformation-coverage.json` is the machine-readable support ledger; the streaming ledgers classify whether admitted operations may receive streaming input. `docs/APICatalog.md` is the user-facing decision catalog. `docs/dev/Gaps.md` is the durable gap and boundary register. API details belong in `docs/api/Expressions.api.md`, `Collections.api.md`, `Aggregations.api.md`, and `Windows.api.md`.

An expression is a symbolic description of a computation. A typed contract states its accepted Structure types, result type, nullability, literal-only arguments, and target-profile requirements before Spark runs it. A capability check is the compiler diagnostic that rejects a helper when the configured PySpark version or variant cannot support it. A generated test checks rendered PySpark source; an online test executes the same transform through PySpark. “Streaming classification” records whether the operation is safe and supported when the input relation is a streaming DataFrame.

## Plan of Work

First, produce a canonical inventory diff. Start from the PySpark 4.0.1 functions reference and verify each candidate against the PySpark 3.5.x reference or pinned runtime. Exclude readers, writers, session/catalog APIs, actions, lifecycle APIs, and arbitrary UDF/UDTF registration as already defined by the inventory policy. Add missing family members to `pyspark-transformation-inventory.json`, including normal, predicate, sort, mathematical, string, bitwise, temporal, hash, collection, array, struct, map, aggregate, window, generator, partition, CSV, JSON, Variant, XML, URL, and miscellaneous families. For every entry, choose exactly one Structure disposition and record the owning contract or caller remedy.

Next, reconcile current implementation evidence before adding code. Search the public exports in `src/structure/plugin/pyspark/__init__.py`, definitions in the DSL modules, renderer/evaluator dispatch, API reference, and focused tests. Keep `hour`, `exp`, and all other already supported helpers as implemented. Mark a function as implemented only when type/nullability behavior, generated spelling, diagnostics, and the claimed target profile have evidence. A renamed typed equivalent must list both the PySpark names and Structure names.

Implement the deterministic scalar slices in this order. Add missing mathematical functions such as `acos` and `hypot` through the shared numeric argument and result-type helpers, then add the remaining safe unary/binary math functions. Add string padding and related literal-argument functions such as `lpad` and `rpad`. Add calendar operations such as `add_months` and `next_day`, preserving Spark's date semantics and validating weekday/unit/format literals. Add predicates, sort descriptors, bitwise/binary helpers, and JSON/CSV inspection functions only when their result schema and nullability can be stated without an untyped escape hatch.

For each scalar slice, update the same vertical path: public export, DSL constructor, type validation, symbolic execution, generated renderer, capability requirement if profile-specific, API reference, catalog row, and tests. Reuse the existing `Expression` call representation and helper functions rather than adding one-off renderer branches. Test null input, invalid domain input, decimal/integer/double widening, literal validation, and boundary values. Verify generated calls use `pyspark.sql.functions` and do not introduce private Spark internals.

Implement collections, maps, structs, and generators as a separate cardinality milestone. Decide whether each PySpark spelling should receive a thin alias or remain represented by a stronger typed Structure helper. For `reduce`, `arrays_zip`, `array_join`, `shuffle`, and generator/partition functions, explicitly document callback scope, null behavior, output schema, row multiplication, ordering, seed behavior, and streaming classification. Do not mark a generator covered merely because a happy-path array expands; include empty, null, outer, nested, and alias cases.

Implement aggregate and window gaps only after their contracts are written. For ordinary aggregates, specify empty-input behavior, null skipping, numeric widening, order sensitivity, and whether the result is mergeable. Keep sketch, bitmap, regression, and approximate functions design-gated until binary result, accuracy, mergeability, dependency, and determinism are specified. For window functions, use the existing typed `WindowSpec`; raw `Column.over` remains outside the compiler-visible contract.

Close the boundary families explicitly. XML and URL functions need provider/dependency and schema decisions. Runtime metadata, reflection, encryption, partition identifiers, and arbitrary callbacks need security, portability, or ownership decisions. Keep them `design-gated`, `caller-owned-guided`, or `unsupported` with an actionable remedy rather than placing them in a vague “not implemented” bucket.

Finish with evidence reconciliation. Update `docs/APICatalog.md`, `docs/dev/Gaps.md`, `docs/api/*.api.md`, and both transformation coverage ledgers whenever a status changes. Add a family-level test that fails if a reviewed inventory entry lacks a coverage disposition, public symbol/equivalent, boundary, or evidence path. Re-run the documentation and generated-artifact checks so the catalog cannot drift back to a v6 snapshot.

## Validation and Acceptance

The inventory is accepted when every baseline PySpark SQL function has exactly one row in the machine-readable ledger and one matching family-level explanation in `docs/dev/Gaps.md` and `docs/APICatalog.md`. The eight audited examples must be visibly correct: `hour` and `exp` remain implemented; `add_months`, `next_day`, `acos`, `hypot`, `rand`, and `lpad` have explicit implementation or boundary status.

An admitted deterministic function is accepted only when a typed transform using it compiles without Spark, renders the expected `pyspark.sql.functions` call, executes online with expected values and null behavior, and matches generated execution on every claimed ordinary/Connect profile. Unsupported profiles must fail with the repository's structured backend capability diagnostic and a caller remedy. A function with row multiplication, nondeterminism, provider dependency, or aggregate state must additionally pass its cardinality, seed, provider, mergeability, or streaming tests before status changes to implemented.

The overall work is accepted when `make build` exits successfully, focused tests pass, available PySpark 3.5/4.0 lanes pass, generated artifacts are fresh, and no catalog row says “supported” without a capability, diagnostic, API reference, test, and evidence path. Remaining design-gated and caller-owned families are acceptable only when their reason and remedy are explicit.

## Idempotence and Recovery

Inventory and documentation updates are additive and safe to repeat. Before editing a shared ledger, inspect its current row and preserve unrelated changes. If a function cannot be admitted without weakening the typed contract, keep or move it to `design-gated`, `caller-owned-guided`, or `unsupported` and record the decision; do not add an untyped `expr` fallback.

If live PySpark is unavailable, complete no-Spark validation and record the missing evidence without claiming runtime support. If a generated artifact changes, regenerate it through the project command and review the diff; never hand-edit generated output. If an implementation slice fails, retain the catalog row as planned and leave the focused test or diagnostic in a reproducible state for the next contributor.

## Interfaces and Dependencies

Use the existing `Expression` model, Structure type classes, backend capability registry, symbolic executor, PySpark renderer, and integration runners. Do not introduce a new expression representation for an individual function. New public helpers belong in the relevant DSL module and must be re-exported through `src/structure/plugin/pyspark/__init__.py` with a stable `__all__` entry.

Use the default profile `>=3.5,<4.1` for baseline claims. Gate newer functions with the resolved profile rather than importing them optimistically. Use ordinary PySpark as the primary runtime evidence and Spark Connect only where generated and live evidence demonstrate parity. Keep streaming claims separate from batch claims and update both streaming coverage ledgers when a function receives streaming input.
