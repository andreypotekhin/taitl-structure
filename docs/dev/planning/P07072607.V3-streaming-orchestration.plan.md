## Purpose / Big Picture

After this plan is complete, Structure can own the first real Spark Structured Streaming lifecycle contract instead of
only accepting caller-owned streaming DataFrames. Users can declare streaming sources and sinks, generate reviewable
`readStream` and `writeStream` PySpark code, configure triggers, checkpoints, output modes, watermarks, and admitted
state policies, and still rely on v.1/v.2 streaming compatibility diagnostics for transform bodies.

Users can see the result by compiling a small streaming job that reads orders from a configured streaming source,
applies a compatible Structure transform, writes to a configured streaming sink with checkpointing and trigger policy,
and starts through generated code or an online lifecycle runner in a bounded integration test.

## Context and Orientation

Spark Structured Streaming represents an unbounded table as a DataFrame. A streaming query normally has a source
created through `spark.readStream`, transformations, and a sink created through `DataFrame.writeStream`. A checkpoint
directory stores progress so the query can recover. A trigger controls when Spark processes new data. An output mode
controls what rows Spark writes for each micro-batch. A watermark tells Spark how late event-time data may arrive
before state can be cleaned up.

Structure v.1/v.2 can classify whether transform bodies are compatible with caller-owned streaming DataFrames. This plan
adds Structure-owned lifecycle declarations and generated lifecycle code.

## Plan of Work

Milestone 1 defines streaming lifecycle declarations. Add typed source and sink declaration objects that can describe
format, options, schema expectations, checkpoint location, trigger, output mode, and whether the declaration is allowed
in generated code, online execution, or both. Keep configuration explicit; do not infer production checkpoint paths.

Milestone 2 implements generated `readStream`. Render reviewable source setup for admitted formats. Validate schema,
source options, and target backend before generation. Generated code must keep source creation separate from transform
logic so users can review operational policy.

Milestone 3 implements generated `writeStream` and lifecycle runner. Render sink setup, output mode, trigger, query
name where applicable, checkpoint option, and query startup. Decide whether online execution starts queries directly or
returns a query builder; record the decision in this plan before implementation. Tests must prove retry-safe behavior
for deterministic generated output and configuration validation.

Milestone 4 implements watermarks and state policies. Add source or transform-level event-time watermark declarations,
state policy objects for admitted streaming aggregations or dedupe, and compatibility diagnostics that explain when an
operation needs a watermark, output mode, or state policy. Do not admit broad stream-stream joins unless bounded,
watermarked semantics are fully specified.

Milestone 5 adds live integration evidence, docs, explain, compatibility tables, and troubleshooting. Integration
tests should use a small local streaming source and a sink that can be bounded or inspected deterministically. Public
docs must explain the difference between caller-owned streaming transforms and Structure-owned streaming jobs.

## Validation and Acceptance

The plan is accepted when Structure can generate and run a minimal streaming job with explicit lifecycle policy, public
docs and compatibility tables are updated, and the default `make build` passes.

Behavioral acceptance:

- Users can declare streaming sources and sinks explicitly.
- Generated PySpark includes reviewable `readStream` and `writeStream` code only when lifecycle declarations exist.
- Triggers, checkpoints, output modes, watermarks, and admitted state policies are validated before runtime.
- Missing checkpoint, invalid output mode, missing watermark for stateful behavior, unsupported stream-stream joins, and
  custom side-effect sinks fail with diagnostic links.
- Existing caller-owned streaming compatibility behavior remains valid.
- A live integration test or release-blocking manual script proves at least one generated streaming job starts and
  processes bounded input.

## Idempotence and Recovery

Lifecycle generation must be deterministic. Re-running compile and generated snapshots is safe. Streaming integration
tests must use isolated checkpoint directories and clean them through the test harness. If a query starts and fails
halfway, rerun with a fresh checkpoint unless the test is specifically verifying recovery.

## Interfaces and Dependencies

Use existing Structure configuration, runtime session, backend capability, generated rendering, diagnostics,
compatibility classification, and integration-test infrastructure. Do not hide streaming lifecycle work inside hooks.
Do not support custom side-effect sinks in this plan. Do not require Spark for compiler-only commands.
