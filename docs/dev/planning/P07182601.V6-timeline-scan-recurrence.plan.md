# Deliver v6 Ordered Timeline Scans

This ExecPlan is a living document. Maintain it according to `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` accurate whenever work stops or a design fact changes.

## Purpose / Big Picture

After v6, a developer can supply an ordinary, finite timeline DataFrame and derive one typed output row per timeline row from an explicitly carried state. This covers ordered recurrences such as Fibonacci without pretending that `lag(...)` is recursive. The developer owns the timeline's rows; Structure owns the typed recurrence, deterministic ordering contract, schema validation, and equivalent online/generated PySpark plans.

The feature is visible through a new PySpark-plugin `scan(...)` expression. A scan starts each partition from a declared `Schema` state, exposes the state before the current timeline row, and invokes a symbolic callback that returns the next state. The first delivery is bounded batch PySpark only. It does not create DataFrames, retain state between transform invocations, or start streaming queries.

The observable acceptance example is a caller-created `Tick(series, index)` DataFrame whose rows 0 through 9 produce `Fibonacci(series, index, value)` values 0, 1, 1, 2, 3, 5, 8, 13, 21, and 34 through both `StructureSession` execution and generated PySpark execution.

## Decision Log

- Decision: v6 accepts a caller-supplied timeline input and does not include input-less transforms, synthetic seed frames, or constructor parameters.
  Rationale: The timeline makes output cardinality and partitioning explicit and isolates recurrence semantics from source creation.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: Introduce a PySpark-plugin `scan(...)` expression instead of extending `lag(...)`.
  Rationale: `lag(...)` is a read from the input relation; scan has an explicit initial state and feedback transition. Combining them would make a non-recursive API appear recursive.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: Scan state is a `Schema` instance and the callback returns the same state schema.
  Rationale: Existing Schema constructors already provide a typed, named collection of fields. Reusing them avoids untyped tuples, maps, and target-specific state records.
  Date/Author: 2026-07-18 / Codex.
- Decision: The initial release is bounded batch PySpark only and requires a positive literal `max_rows` per partition.
  Rationale: The public PySpark lowering materializes each logical partition as an ordered array in order to remain DataFrame/Column-plan-visible. A declared bound makes its memory cost explicit and prevents accidental use as unbounded or streaming state.
  Date/Author: 2026-07-18 / Codex.
- Decision: Every scan requires `partition_by`, one or more `order_by` expressions, and `ties=TiePolicy.ERROR` by default.
  Rationale: A distributed DataFrame has no intrinsic row order. The contract must name the recurrence partitions and order, and must fail rather than silently choose an arbitrary order for tied keys.
  Date/Author: 2026-07-18 / Codex.

## Context and Orientation

Structure source is compiled from schema-returning methods into backend-neutral planning records and then into a target plan. Current transform methods consume declared `input(...)` DataFrames. Their row expressions are symbolic: they describe a Spark plan and are not run one Python row at a time. `lag(...)` is an analytic window expression that can inspect a value in an earlier input row, but it cannot make a new output value become the next row's input.

An ordered scan is a recurrence over a finite, ordered set of input rows. For each partition, it begins with an initial state, exposes that state for the current row's output, applies a state-transition callback, and carries the returned state to the next row. A partition is the subset selected by equal `partition_by` values. The order is the lexicographic order of `order_by` expressions. A tie is two rows in one partition with equal order keys.

The relevant current locations are `src/structure/plugin/pyspark/dsl/operations_api.py` and its focused delegates for
public symbolic helpers, `src/structure/plugin/pyspark/symbolic_execution/` for body capture, `src/structure/plugin/pyspark/compiler/`
for PySpark recipe lowering and capability checks, `src/structure/plugin/pyspark/execution/` for online execution, and
`src/structure/plugin/pyspark/render/` for generated source rendering. Core retains transform declarations and routing
only; it must not gain target-specific scan semantics. Documentation contracts belong in `docs/dev/specifications/`,
while feature tests belong in `tests/specifications/` and live PySpark evidence in `tests/integration/pyspark/`.

## Public Contract

Add the following PySpark-plugin expression form and re-export it from the PySpark plugin DSL, not from the Core `structure` root:

    scan(
        *,
        initial: StateSchema,
        partition_by: Expression | tuple[Expression, ...],
        order_by: Expression | tuple[Expression, ...],
        max_rows: int,
        step: Callable[[StateSchema, TimelineRow], StateSchema],
        ties: TiePolicy = TiePolicy.ERROR,
    ) -> StateSchema

`initial` must be a fully populated instance of a `Schema` subclass. `step` receives a symbolic scope with that schema and a symbolic scope for the driving timeline row, and must return an instance of exactly the same state schema. The result is a symbolic state scope representing the state before the transition for the current row. A developer uses its fields in the normal schema-returning step method.

The canonical Fibonacci source is:

    class Tick(Schema):
        series = string(nullable=False)
        index = long(nullable=False)

    class FibonacciState(Schema):
        previous = long(nullable=False)
        current = long(nullable=False)

    class Fibonacci(Schema):
        series = string(nullable=False)
        index = long(nullable=False)
        value = long(nullable=False)

    class FibonacciFromTimeline(Transform):
        ticks = input(Tick)
        values = output(Fibonacci)

        def calculate(self, tick: Tick) -> Fibonacci:
            state = scan(
                initial=FibonacciState(previous=0, current=1),
                partition_by=tick.series,
                order_by=tick.index,
                max_rows=10_000,
                step=lambda state, _: FibonacciState(
                    previous=state.current,
                    current=state.previous + state.current,
                ),
            )
            return Fibonacci(series=tick.series, index=tick.index, value=state.previous)

For `index` values 0, 1, and 2, `value` is 0, 1, and 1. The step callback receives the current input row so that state transitions may depend on timeline data. It must be pure symbolic Structure source: no Spark session, DataFrame, Python collection mutation, action, or arbitrary loop is permitted.

The scan result does not persist between `run(...)` calls. It is not a streaming state store. `max_rows` is a positive integer literal, applies independently to each partition, and is verified in the target plan before state folding. Empty partitions produce no rows. A nonempty partition begins from the same `initial` state. `partition_by`, `order_by`, and `max_rows` are required; global scans, inferred order, null order keys, descending order, and all streaming inputs are rejected in the first release. A later release may add them only with a new explicit semantic contract.

When two rows have equal ordering keys in one partition, `ties=TiePolicy.ERROR` causes the DataFrame plan to fail at execution with a diagnostic naming the partition/order contract and recommending an additional tie-breaker. No arbitrary Spark row order is accepted. The first release accepts only this tie policy.

The scan capability is named `pyspark.ordered_timeline_scan`. Explain and traceability output identify the scan, its state schema, partition keys, order keys, `max_rows`, and its `row_preserving` cardinality. The transform remains batch-only; streaming compatibility emits a precise unsupported-operation finding before execution or generated rendering.

Do not encode a Python callback or a live state object in the compiled artifact. Capture the callback once during symbolic execution using a typed state scope and current-row scope, convert the returned state schema fields to immutable expressions, and reject missing, extra, wrong-type, or nullable-incompatible state fields with the same quality of diagnostic used for ordinary Schema projections.

Extend validation so a scan can appear in a normal output projection but only once per step in v6. Every output expression that reads it must refer to that one plan record. Reject scan expressions in filters, joins, aggregate keys, raw hooks, nested scan callbacks, and multiple different scans in a single step; these shapes obscure execution order or require multiple independent materializations. Reject a scan when its driving relation is joined, streaming, or already aggregated. Allow it only over a direct declared input or lane with row-preserving prior operations.

Lower the record in the PySpark plugin into an optimizer-visible DataFrame plan. Preserve each input row as a payload
struct, group by partition fields, sort payloads by the declared order fields, and fail with `raise_error` when
duplicate order keys occur or the group contains more than `max_rows` items. Use Spark higher-order `aggregate` over
the ordered payload array. Its accumulator contains the current typed state and an array of output
payload-plus-before-state records. The merge expression calculates the current output state, appends the payload/state
record, and returns the next state. Expand that result array through the public row-expansion path admitted in Sprint
25, project the preserved row fields plus output state fields, and continue through the existing output projection and
schema-validation path. The plan must use no Python UDF, Pandas UDF, RDD, action, local collection, or driver loop.

Keep the PySpark recipe, online runner, and generated renderer structurally identical: they consume the same lowered scan recipe. Generated code should show named intermediate variables for the grouped, folded, and expanded frames and use public `pyspark.sql.functions` APIs. It must not hide the recurrence in a source-transform method or re-evaluate the user callback at runtime. Materialize initial literals and state schema fields through the existing schema/type rendering mechanisms.

Include an input value in the state transition to prove the callback receives the timeline row. Cover empty input, a one-row partition, missing index gaps (allowed; ordering rather than contiguity defines recurrence), duplicate keys, null order keys, partition overrun, integer overflow behavior inherited from normal PySpark arithmetic, and a scan followed by an ordinary projection. Verify online/generated output and schema parity as well as generated-source guard scans. Add live PySpark tests against all supported batch target versions; the expected Fibonacci rows must be compared after deterministic sorting in the test only.

Update performance and user documentation honestly. The first lowering groups each logical partition into an array, so memory grows with the configured partition bound and it is unsuitable for unbounded state. Explain that a developer should partition timelines meaningfully, choose the lowest safe `max_rows`, and use a normal window helper such as `lag(...)` when predecessor values already exist. ## Validation and Acceptance

Acceptance is behavioral, not merely structural. Given a DataFrame with one `series` value and indices 0 through 9, the Fibonacci transform returns exactly the ordered values 0, 1, 1, 2, 3, 5, 8, 13, 21, and 34, with the declared `Fibonacci` schema. Given two series, the second series restarts at 0 rather than continuing the first. Given an empty timeline, it returns an empty DataFrame with the declared schema.

The same source must compile without Spark, execute through online PySpark, render readable generated PySpark, and execute generated code with identical rows and schema. Generated-source tests must prove the emitted implementation calls public DataFrame/Column APIs and contains no UDF, RDD, Pandas conversion, collection action, or Python recurrence loop. A duplicate order key, null order key, or partition larger than `max_rows` must fail with the documented diagnostic when Spark evaluates the plan. A streaming timeline must fail compilation/capability checking rather than silently claiming stateful-stream support.

## Idempotence and Recovery

All source, specification, and test edits are additive. Re-running the focused tests, integration lanes, or `make build` is safe; they may recreate ignored build artifacts only. ## Artifacts and Notes

The desired generated shape is intentionally recognisable:

    ordered = timeline.groupBy(...).agg(F.sort_array(F.collect_list(F.struct(...))).alias("_timeline"))
    folded = ordered.select(F.aggregate(F.col("_timeline"), initial_state, merge, finish).alias("_scan"))
    values = folded.select(F.posexplode(F.col("_scan.rows")).alias("_position", "_row"))

The exact field aliases and struct construction belong to the PySpark renderer, but the generated source must preserve this three-stage story: order, fold, expand. It must not use `lag(...)` to emulate feedback.

## Interfaces and Dependencies

The feature depends on the current PySpark plugin package and its compiler, capability, executor, and generator facets.
Core must not import PySpark or add target-specific scan semantics to `structure`. The PySpark plugin owns the
`scan(...)` helper, scan IR-to-recipe lowering, capability declaration, online execution, and generated source.
Core-owned Schema classes remain the type language for timeline rows, scan state, and output rows.

The first implementation uses only public PySpark DataFrame, Column, window-free aggregation, higher-order array, struct, sorting, error, and `posexplode` APIs available across the supported batch target range. It must not add dependencies. The existing `TiePolicy` type supplies the public tie vocabulary, but only `TiePolicy.ERROR` is accepted by this feature until a future specification defines another deterministic policy.
