This ExecPlan is a living document. Maintain it according to `docs/dev/auto/Plans.md`, including the required progress,

## Purpose / Big Picture

V10 will make additional streaming state assumptions visible instead of treating every multi-stage plan as equivalent.
Users will receive precise diagnostics and explain output for state stages, watermarks, retention, join bounds, and
output modes. Only shapes proven by public Spark APIs and live restart evidence can become Structure-supported.

## Surprises & Discoveries

- Observation: V9 already records stateful operations internally but rejects general second-stateful composition.
  Evidence: `ClassifyStreamingCompatibility.py` and the `streaming.chained-stateful-operators` ledger row.
- Observation: Global selected-row and broad analytic-window helpers are already explicit batch boundaries.
  Evidence: `docs/dev/specifications/V9StreamingDesignGatedFeatures.spec.md` and the streaming ledger.
- Observation: SearchDocuments reaches the selected-row boundary in multiple stages, not one isolated helper. Candidate
  admission and overlap narrowing use global `row_number(...)`; reranking uses `row_number(...)` and
  `select_first_qualified(...)`; these operations do not expose finite retention or append-finalization semantics.
  Evidence: `examples/search/transforms/searching/search_docs/admit.py`, `overlap.py`, and `rerank.py`.
- Observation: Search's declared streaming lineage still contains business-key aggregates and ordinary duplicate
  removal. A watermark on `requested_at` does not by itself bound `group_by(query_id=...)` or arbitrary
  `drop_duplicates(...)` state.
  Evidence: `examples/search/transforms/scoring/ScoreBase.py`, `SelectGapQueries.py`, and the Search compiler report.
- Observation: A stream/stream join is safe only when both inputs have compatible watermarks and a finite event-time
  predicate. Search currently has joins whose bound and retention are not represented as one end-to-end query window.
  Evidence: `examples/search/transforms/searching/search_docs/admit.py`, `RetrieveDocuments.py`, and the streaming
  join findings for SearchDocuments.
- Observation: Existing aggregate, dedupe, and bounded stream-stream join recipes already contain enough symbolic
  information to expose an initial state-stage record without changing generated execution. The record can preserve
  ordered steps, watermark delays, aggregate windows, duplicate keys, join event-time bounds, and output modes while
  leaving unsupported shapes rejected.
  Evidence: `ClassifyStreamingCompatibility.py`, `PySparkOperationRecipe.py`, and the V10 streaming compatibility
  tests.
- Observation: Cross and anti stream-stream candidates need different corrective remedies. Cross joins have Cartesian
  state with no event-time pair, while anti joins can revise a prior negative result when a late right-side match
  arrives. Both now fail before query start with candidate-specific guidance.
  Evidence: `ClassifyStreamingCompatibility.py` and the V10 cross/anti rejection tests.
- Observation: The finite selected-value alternative already carries an explicit aggregate `order_by` expression.
  Exposing it in the state-stage record distinguishes deterministic in-window selection from global ranking, without
  changing the supported shape.
  Evidence: `PySparkAggregateAssignment.order_by`, `StreamingFiniteSelection`, and the V10 compatibility tests.
- Observation: The current SearchDocuments graph contains repeated join-bound, duplicate-removal, broad-rowset,
  global-ranking, analytic-window, and business-key-aggregate blockers before any top-K migration. The proving lane is
  deferred while integration delivery remains batch-focused.
- Observation: Search candidate admission already captures matching `query.requested_at` and
  `request.requested_at` as both an equality and a zero-width `event_time_between(...)` predicate, with ten-minute
  watermarks on both fields. This is timestamp consistency, not yet a finite query-completion contract.
  Evidence: `RetrieveDocuments.select_stored_candidates`, `select_streamed_candidates`, and the V10 proving tests.
- Observation: State-stage explain output now renders `completion_window: none` when no caller-owned finite completion
  contract has been captured. Existing V9 support is unchanged; Search remains design-gated until that field is supplied
  alongside bounded state and append-final semantics.
  Evidence: `StreamingStateStage`, `RenderPySparkExplainReport`, and the SearchDocuments proving lane.
- Observation: SearchDocuments still lowers candidate and overlap stages through global analytic windows. The intended
  bounded top-K shape remains recorded in the SearchDocuments plan without an active adoption API.

## Decision Log

- Decision: A state stage records operation family, event-time source, watermark source, grouping/partition keys,
  retention or bound, required output mode, and whether a later stateful stage is allowed.
  Rationale: A single boolean cannot explain why a composition is unsafe.
  Date/Author: 2026-08-02 / Codex.
- Decision: No new stateful shape is supported without positive PySpark 3.5/4.0 online/generated parity and restart
  evidence; rejection is the accepted outcome when Spark or the Structure contract cannot bound state.
  Rationale: Live streaming semantics and recovery behavior are part of the support claim.
  Date/Author: 2026-08-02 / Codex.
- Decision: Cross and anti stream-stream joins are prototype candidates, not assumed supported APIs.
  Rationale: Join direction, watermark behavior, and state retention differ by Spark version and must be proven.
  Date/Author: 2026-08-02 / Codex.
- Decision: SearchDocuments will eventually need a named finite-window top-K operation rather than an exception to the
  existing `row_number(...)` rule; the API and adoption work are deferred.
  Rationale: Candidate admission, overlap narrowing, and final ranking need bounded state, deterministic ties, and one
  append-final result per query. Reusing a batch analytic window would hide unbounded state and revision behavior.
  Date/Author: 2026-08-02 / Codex.
- Decision: Query/request completion is a separate contract from Spark's watermark declaration. The compiler must see
  the event-time field, watermark delay, finite completion window, grouping key, and append requirement together.
  Rationale: A watermark can discard late data, but it does not by itself say when a query is complete or whether a
  result may be revised.
  Date/Author: 2026-08-02 / Codex.
- Decision: The first state-stage contract is observational metadata only. It does not promote new streaming shapes or
  generate lifecycle calls; existing compatibility findings remain the source of support decisions.
  Rationale: State visibility is useful immediately, while promotion still requires online/generated parity and restart
  evidence on both supported PySpark profiles.
  Date/Author: 2026-08-02 / Codex.

## Outcomes & Retrospective

The completed plan will state which join and finite-window shapes are supported, caller-owned, streaming-ineligible, or
design-gated, with exact target evidence and deferred owners. It will record state-retention findings and any Spark
version differences.

## Context and Orientation

Structure transforms caller-supplied DataFrames; callers own streaming sources, sinks, checkpoints, triggers, output
modes, and query lifecycle. Streaming classification is performed before query start by the PySpark compiler. The key
implementation is `src/structure/plugin/pyspark/compiler/commands/ClassifyStreamingCompatibility.py`; the current
stateful and join contracts are described in `docs/dev/design/SparkStreaming.design.md`,
`docs/dev/gated/Streaming.gates.md`, and `docs/dev/specifications/V9StreamingDesignGatedFeatures.spec.md`.

## Plan of Work

Introduce an immutable state-stage metadata record in the existing IR/compatibility path. Every admitted aggregate,
dedupe, session window, and bounded stream-stream join contributes one record. Explain output renders the ordered stage
list and the caller-required output mode.

Add a SearchDocuments proving lane to this same IR. The lane must represent the following state stages explicitly:

1. query/request correlation, keyed by unique query/request identity and bounded by matching `requested_at` plus the
   configured completion interval;
2. candidate admission, retaining no more than 1,000 rows per query window;
3. overlap narrowing, retaining no more than 100 rows per query window;
4. final deterministic ranking, retaining only the configured result bound until the query window closes.

Each stage must name its event-time expression, watermark source and delay, query grouping keys, deterministic order
keys, retained bound, and required `append` mode. The state record must distinguish a static lookup from a stateful
stream/stream join and must list any rejected unbounded operation that prevented admission.

The Search proving lane must also make the boundary transformations explicit. Cached and online score branches must be
streaming before an exact-schema stream/stream union; feedback fallback, popularity, and policy selection must be
resolved into an immutable static snapshot; and every remaining stream/stream join must have a finite event-time
predicate that uses the same run completion contract. Ordinary business-key aggregates and global duplicate removal
must be removed from the streaming lineage or replaced with row-local uniqueness or the named bounded state stage.

Prototype each candidate using only public DataFrame and Column APIs. The first candidates are bounded stream-stream
anti/cross forms and finite event-time selected-value alternatives. The prototype must use watermarks, explicit
event-time predicates, literal or declared bounds, and deterministic ties. It must not use actions, collection, RDDs,
Pandas conversion, raw SQL, private JVM state, or lifecycle calls.

Promote only the exact shape that passes symbolic capture, capability checks, generated rendering, online/generated
parity, and restart evidence on both supported profiles. All broader or unsupported shapes receive diagnostics that
name the missing watermark, bound, retention rule, output mode, or target capability.

## Validation and Acceptance

Acceptance requires the existing two-stage event-time window shape to remain green; state-stage explain output to name
each stage; aggregate/dedupe/join compositions to fail before query start when unsafe; and every promoted join or finite
selected-row shape to pass online/generated parity and restart tests on both target profiles.

SearchDocuments additionally requires all of the following before it can be called ready-to-start:

- no global `row_number`, `rank`, `select_first_qualified`, or equivalent selected-row operation in the streaming path;
- no ordinary `drop_duplicates` or business-key/global aggregate whose state is not bounded by the query event-time
  window;
- every stream/stream join has declared inputs, compatible watermarks, a finite event-time predicate, and a compiler-
  visible retention interval;
- cached/online branches use exact-schema stream/stream union only after both branches are streaming;
- top-K state reports its grouping keys, order/tie keys, retention bound, and append mode;
- live tests prove one result set per query, no post-emission revisions, deterministic ties, late/duplicate handling,
  checkpoint restart, and immutable snapshots on PySpark 3.5 and 4.0.

Global selected-row helpers, ranking, lag/lead, rolling projections, and any shape without a finite state contract must
remain `streaming-ineligible` or `design-gated` with a useful caller remedy.

## Idempotence and Recovery

Streaming fixtures use isolated temporary input, output, and checkpoint paths. Failed live runs are retried from clean
paths. A failed prototype is preserved as a regression fixture and does not weaken the support claim.

## Artifacts and Notes

SearchDocuments blocker fixtures, top-K parity/restart transcripts, and updated `docs/APICatalog.md`, streaming ledgers,
