# Transform Boundary Aliases

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement optional transform
input and output aliases from this file alone.

## Purpose / Big Picture

Structure already composes complete transform invocations with `.to(...)`. Composition wires a downstream
`input(...)` from an upstream `output(...)` by schema, preferring an exact boundary name match when multiple upstream
outputs have the same schema. That is useful, but it forces reusable transforms to expose implementation-oriented
output field names such as `normalized` when downstream transforms want a stable domain name such as `orders`.

After this change, a transform declaration may publish an optional boundary alias:

    class NormalizeOrders(Transform):
        orders = input(OrderRaw)
        normalized = output(OrderNormalized).alias("orders")

    class AddProduct(Transform):
        orders = input(OrderNormalized)
        products = input(Product)
        enriched = output(OrderEnriched)

    result = NormalizeOrders(orders=raw_df).to(AddProduct(products=products_df)).run(session)

The pipeline above should compile without explicit constructor remapping because `NormalizeOrders.normalized` exposes
the alias `orders`. The alias is a synonym, not a replacement: the declaration name `normalized` remains the canonical
source-code and plan name, while the alias is available for composition matching and result access.

## Surprises & Discoveries

- Observation: Composition already exists and matches unbound downstream inputs by schema, preferring an exact upstream
  output name before falling back to a single schema match.
  Evidence: `ComposeTransformPlans._matching_outputs(...)` compares `output.schema is input_plan.schema`, then filters
  by `output.name == input_plan.name`.

- Observation: Runtime results and schemas expose output names through mapping and attribute access.
  Evidence: `TransformResult.__getitem__`, `TransformResult.__getattr__`, and `ResultSchemas.__getitem__` use the
  output mapping keys directly.

- Observation: Generated and online execution both use lowered plan output names as the public result keys.
  Evidence: `RunOnlinePySparkTransform._run(...)` builds `outputs[output.name]`, and
  `RenderPySparkTransformModule` emits `TransformResult({"<name>": <frame>}, schema={"<name>": <schema>})`.

- Observation: Declaration descriptors are small frozen dataclasses, so a fluent `.alias("orders")` method can return
  a copied declaration without adding mutable descriptor state.
  Evidence: `InputDeclaration`, `LaneDeclaration`, and `OutputDeclaration` are `@dataclass(frozen=True)` descriptors.

## Decision Log

- Decision: Aliases are optional boundary synonyms, not canonical replacements.
  Rationale: Aliases are expected to be rare and used to work around transform name-match differences. Keeping the
  Python field name canonical preserves existing source references, generated variable names, traceability labels, and
  iteration over result mappings.
  Date/Author: 2026-07-08 / Codex and project owner

- Decision: Implement `.alias("name")` on transform declarations.
  Rationale: The requested spelling is compact and matches user intent. Documentation must distinguish transform
  boundary aliases from schema field `alias=` and Spark DataFrame `.alias(...)`.
  Date/Author: 2026-07-08 / Codex and project owner

- Decision: Output aliases participate in `.to(...)` matching before declaration names.
  Rationale: The purpose of the feature is to let a stable alias such as `orders` satisfy a downstream input named
  `orders` even when the upstream declaration is named `normalized`.
  Date/Author: 2026-07-08 / Codex and project owner

- Decision: Result access accepts output aliases, while mapping iteration and `as_dict()` stay canonical.
  Rationale: Alias access should be convenient (`result.orders`, `result["orders"]`, `result.schema["orders"]`) without
  duplicating keys, changing `len(result)`, or surprising callers that serialize result mappings.
  Date/Author: 2026-07-08 / Codex and project owner

- Decision: Do not add `transform.output(["orders"])` in this slice.
  Rationale: The existing public shape already has mapping and attribute access. Adding a second accessor API would
  widen the surface area without solving a separate composition problem.
  Date/Author: 2026-07-08 / Codex and project owner

- Decision: Add `.rename(normalized="orders")` as invocation-level output aliasing.
  Rationale: This lets users compose third-party or already-stable transform classes without editing their declarations.
  It contributes aliases to the specific invocation only; it does not rename the transform class's canonical output
  declaration.
  Date/Author: 2026-07-08 / Codex and project owner

## Context and Orientation

A Structure transform is a Python class inheriting from `Transform`. It declares runtime inputs with `input(Schema)`,
internal lanes with `lane(Schema)`, final outputs with `output(Schema)`, and public schema-returning methods as
subtransforms. A transform declaration's Python field name is currently its only boundary name.

The relevant files are:

- `src/structure/app/dsl/model/transforms/InputDeclaration.py` and `OutputDeclaration.py`, which define declaration
  descriptors;
- `src/structure/app/dsl/model/transforms/LaneDeclaration.py`, which should receive the same fluent alias API for
  consistency even though lane aliases remain internal;
- `src/structure/app/dsl/model/transforms/Transform.py`, which validates constructor input names;
- `src/structure/app/compiler/ir/model/InputPlan.py` and `OutputPlan.py`, which carry compiler-visible boundary
  contracts;
- `src/structure/app/compiler/frontend/logic/ComposeTransformPlans.py`, which composes stage plans and matches upstream
  outputs to downstream inputs;
- `src/structure/app/runtime/session/model/TransformResult.py` and
  `src/structure/app/runtime/schemas/model/TransformSchemas.py`, which expose result and schema mappings;
- `src/structure/app/target/pyspark/resources/runtime.py.template`, which must mirror runtime result behavior in
  generated code;
- `src/structure/app/target/pyspark/commands/RenderPySparkTransformModule.py`, which renders generated
  `TransformResult(...)` calls.

In this plan, a boundary alias is an alternate name for matching and reading a transform boundary. It is not a Spark SQL
relation alias, a Spark column alias, or a schema field alias.

## Plan of Work

Milestone 1 adds declaration alias metadata. Extend `InputDeclaration`, `LaneDeclaration`, and `OutputDeclaration` with
an `aliases: tuple[str, ...] = ()` field and a fluent `alias(*names: str)` method. The method returns a copied
declaration with the new alias names appended, preserving frozen descriptor behavior. Validate every alias when the
method is called: it must be a non-empty valid Python identifier, must not start with `_`, and must not duplicate the
declaration's own Python field name or another alias on the same declaration. Use a small shared helper in the transform
DSL package instead of copying validation logic into all three descriptor classes.

Milestone 2 validates aliases at transform class construction and constructor binding. In `Transform.__init_subclass__`,
after collecting inherited and local declarations, validate aliases by role. Input aliases must be unique across input
declarations and must not collide with canonical input names on another input. Output aliases must be unique across
output declarations and must not collide with canonical output names on another output. The same alias as an input name
and output alias in one transform is allowed because it is the motivating use case. If a constructor receives an input
alias, normalize it to the canonical input name in `_structure_bound_inputs`; if both canonical name and alias are
provided, raise `TypeError` with a message that tells the user to pass only one.

Milestone 3 carries aliases through plans. Add `aliases: tuple[str, ...] = ()` to `InputPlan`, `OutputPlan`, and the
corresponding PySpark input and output recipe dataclasses. Update `CompilerInputCollector`, `CompileTransform._outputs`
and `_lane_output`, `PySparkInputMapper` if present, `PySparkOutputMapper`, schema building, traceability, online
execution, generated execution, and generated rendering to preserve aliases. Canonical plan names remain unchanged and
continue to drive generated local variable names.

Milestone 4 updates composition matching. In `ComposeTransformPlans._matching_outputs(...)`, match by schema first as
today. Among schema matches, choose outputs whose alias contains the downstream input's canonical name before
considering outputs whose canonical name equals the downstream input name. If exactly one alias match exists, use it.
If more than one alias match exists, fail with a diagnostic listing the matching output declarations and aliases. If no
alias match exists, keep the existing canonical-name and single-schema fallback behavior. Update error text to mention
aliases when they are present, so users know whether adding `.alias("...")` or using explicit constructor binding would
fix the pipeline.

Milestone 5 updates result and schema access. `TransformResult` should store canonical outputs plus a read-only alias
index. `__getitem__` and `__getattr__` should resolve canonical names first and aliases second. `__iter__`, `__len__`,
and `as_dict()` must continue to expose canonical output names only. `ResultSchemas` should mirror the same lookup
rules for output schemas. Generated runtime support in `runtime.py.template` must accept the alias index so generated
execution and online execution behave the same. When the online runner wraps an injected executor result, preserve
aliases on the wrapper `TransformResult`.

Milestone 6 updates generated rendering and docs. Render `TransformResult` with an alias mapping such as
`aliases={"normalized": ("orders",)}` only when at least one output has aliases, so existing generated output stays
stable for ordinary transforms. Update `docs/reference/TransformComposition.md`, `docs/reference/OnlineExecution.md`,
`docs/QuickRef.md`, and the README transform composition section to show output aliases as a rare boundary-name escape
hatch. The docs must explicitly say that schema field `alias=`, transform declaration `.alias(...)`, and Spark
DataFrame `.alias(...)` solve different problems.

## Validation and Acceptance

The feature is accepted when this source compiles and runs:

    @transform
    class NormalizeOrders(Transform):
        orders = input(Raw)
        normalized = output(Normalized).alias("orders")

        def normalize(self, order: Raw) -> Normalized:
            return Normalized(id=order.id)

    @transform
    class PublishOrders(Transform):
        orders = input(Normalized)
        published = output(Published)

        def publish(self, order: Normalized) -> Published:
            return Published(id=order.id)

    result = NormalizeOrders(orders=raw_df).to(PublishOrders()).run(session)

A human should observe that the downstream `orders` input is supplied by the upstream aliased output without explicit
binding. If running only with the fake online executor used by existing composition tests, the compiled plan should show
the two expected stage steps and the final output should remain `published`.

For a single transform with `normalized = output(Normalized).alias("orders")`, a human should observe:

    result.normalized is result.orders
    result["normalized"] is result["orders"]
    result.schema.normalized == result.schema.orders
    list(result) == ["normalized"]

The generated PySpark source for transforms without aliases should remain byte-stable except where tests intentionally
cover the generated runtime template. The generated source for transforms with aliases should return a canonical result
mapping plus alias metadata.

## Artifacts and Notes

The key behavior should be visible in a focused composition test. A concise expected assertion shape is:

    plan = compile_transform(NormalizeOrders(orders=object()).to(PublishOrders()))

    assert [input.name for input in plan.inputs] == ["orders"]
    assert [step.name for step in plan.steps] == [
        "normalize_orders.normalize",
        "publish_orders.publish",
    ]
    assert [output.name for output in plan.outputs] == ["published"]

For alias result access, use a fake frame object so the test proves mapping behavior without requiring Spark:

    frame = object()
    result = TransformResult(
        {"normalized": frame},
        single=True,
        aliases={"normalized": ("orders",)},
    )

    assert result.normalized is frame
    assert result.orders is frame
    assert result["orders"] is frame
    assert result.as_dict() == {"normalized": frame}

## Interfaces and Dependencies

The public interfaces at completion are:

- `input(Schema).alias("name")`, `lane(Schema).alias("name")`, and `output(Schema).alias("name")`;
- transform constructors accept input aliases as alternate keyword names and normalize them to canonical input names;
- `TransformResult(..., aliases={canonical: ("alias",)})` and generated-runtime `TransformResult` support alias lookup;
- `ResultSchemas(..., aliases={canonical: ("alias",)})` supports alias lookup for output schemas;
- compiler `InputPlan` and `OutputPlan` expose `aliases` for lowering, composition, diagnostics, and schema building.

No new third-party dependency is required.
