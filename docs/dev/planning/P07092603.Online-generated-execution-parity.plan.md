# Close Online and Generated PySpark Execution Parity Gaps

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can restore the required semantic
parity between online PySpark execution and generated PySpark execution without relying on earlier discussion.

## Purpose / Big Picture

Structure supports two ways to run one compiled transform. In online mode, `StructureSession` gives the checked
PySpark execution plan to an interpreter that calls the PySpark DataFrame API with caller-supplied frames. In generated
mode, the generator renders Python from that same plan and the session imports the generated class. Users must get the
same DataFrame semantics from either choice; generated execution must not be a more complete implementation.

At present, a compiled `watermark(...)` operation is rendered as `DataFrame.withWatermark(...)` in generated source,
but online execution ignores it. This is observably wrong for streaming state retention, late-data handling, and the
legality of watermarked stateful operations. After this work, both modes apply watermarks at the same plan position,
including a watermark on a joined input before that join. The repository will also contain executable runtime parity
proof for owner-qualified inherited hooks, plus a documented opt-in live-Spark command for broad batch and streaming
parity evidence.

An end user will be able to choose either of these without changing the transform's output plan:

    online = Orders(events=events_stream, customers=customers).run(
        StructureSession(spark=spark, execution_mode="online")
    )
    generated = Orders(events=events_stream, customers=customers).run(
        StructureSession(spark=spark, execution_mode="generated", generated_package="my_generated")
    )

Both resulting DataFrames will carry the expected watermark and have equivalent schemas and rows for bounded test
fixtures. The caller still owns streaming sources, sinks, triggers, checkpoints, and query lifecycle; this plan changes
only transform-body execution.

## Decision Log

- Decision: Treat online/generated parity as a contract of each admitted `PySparkOperationRecipe`.
  Rationale: Both consumers receive the same lowered plan. If either consumer cannot implement an admitted operation,
  compilation must reject that execution mode or the operation must be implemented before it is considered supported.
  Silently omitting a recipe is never acceptable.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: Implement watermark handling in the online interpreter rather than routing online streaming execution
  through generated source.
  Rationale: Online mode must remain a direct interpreter of the compiled artifact; importing generated code would
  create a second runtime path, require generated files, and defeat the distinction between the modes.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: Preserve the renderer's existing placement rules exactly: watermark the current source at its ordered
  operation position, and prepare a watermarked joined frame before applying its join.
  Rationale: Position affects streaming state semantics. Applying all watermarks at step start or after a join would
  not be equivalent.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: Add fake-PySpark tests for operation sequence and live PySpark tests for observable behavior.
  Rationale: Fake frames make placement deterministic and fast in the default test suite. Real Spark is required to
  prove metadata and streaming behavior that cannot be faithfully modeled by a fake frame.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: Make the shared live-test renderer compile an artifact rather than lower a standalone frontend plan.
  Rationale: Generated execution must verify the artifact fingerprint selected by its session. A test helper that omits
  that metadata only tests an obsolete generated-mode contract.
  Date/Author: 2026-07-09 / project owner and Codex.

## Context and Orientation

A `Transform` is a Python class that declares input DataFrames, intermediate lanes, outputs, and schema-returning step
methods. Compilation symbolically evaluates those step methods and lowers them into a data-only
`PySparkExecutionPlan`. A recipe is one immutable record in that plan describing an operation such as a join, filter,
projection, validation, hook, aggregate, or watermark.

`StructureSession` selects the plan from a compiled artifact before choosing an execution mode. In online mode,
`RunOnlinePySparkTransform` interprets recipes on live DataFrames. In generated mode,
`RenderPySparkTransformModule` renders recipes to a generated class and `RunGeneratedPySparkTransform` imports it. A
semantic fingerprint verifies that the imported generated module was rendered from the same artifact selected by the
session. Fingerprint equality establishes provenance, but it does not prove that both consumers implement every recipe;
the tests in this plan do that.

A watermark is Spark Structured Streaming metadata attached by `DataFrame.withWatermark(event_time, delay)`. It lets
Spark bound state and decide late-data handling. It is not a source, sink, trigger, or lifecycle action. Structure's
v1/v2 streaming contract therefore permits it inside a caller-owned transform body.

The relevant code is:

- `src/structure/app/target/pyspark/logic/mapping/PySparkStepMapper.py`, which creates watermark recipes.
- `src/structure/app/target/pyspark/model/PySparkWatermarkRecipe.py`, which stores the field expression and delay.
- `src/structure/app/target/pyspark/commands/RenderPySparkStep.py`, which renders watermarks for generated execution.
- `src/structure/app/runtime/execution/online/commands/RunOnlinePySparkTransform.py`, which must interpret every
  admitted operation.
- `src/structure/app/runtime/execution/online/logic/PySparkHookInvoker.py`, which calls the exact hook owner selected
  by the plan on the concrete transform invocation.
- `tests/user_stories/10_generated_code/shared_pyspark_semantic_contract/test_online_recipe_runtime.py`, the fake
  PySpark runtime fixture suite.
- `tests/specifications/transform-inheritance/test_transform_inheritance.py`, compiler and rendering tests for owner
  identity and parent hook dispatch.
- `tests/integration/pyspark`, opt-in live PySpark parity tests. Their shared fixture calls
  `pytest.importorskip("pyspark")`, so they require the optional PySpark dependency.

## Plan of Work

### Milestone 1: Interpret every lowered watermark recipe online

Extend `RunOnlinePySparkTransform._operations(...)` so an operation whose kind is `watermark` cannot be ignored. Add a
small helper such as `_watermark(recipe, frame)` that calls:

    frame.withWatermark(recipe.column, recipe.delay)

The helper must be called only when the recipe scope is the current step or output source scope. This matches
`RenderPySparkStep._operations(...)`. A watermark whose scope names a joined input must be applied to the prepared
right-hand frame before `_join(...)` aliases, hints, deduplicates, or joins it. Refactor the online join preparation
minimally so it receives the applicable watermarks from the ordered operations, mirroring the renderer's
`_right_watermarks(...)` behavior. Do not apply a watermark twice when the same scope appears in multiple operations;
the plan order remains authoritative and each recipe corresponds to one PySpark call.

Keep batch behavior unchanged: PySpark allows `withWatermark` only for suitable streaming DataFrames, so a batch
transform that reaches a watermark operation should receive PySpark's normal failure or an existing compiler
compatibility diagnostic rather than silently losing the operation. Do not add mode-specific fallback behavior.

Add tests beside the fake runtime fixture. Give `FakeFrame` a `withWatermark(...)` method that records the field and
delay. Build one plan with a current-source watermark before a stateful operation and assert that online operations show
the watermark at the exact recipe position. Build another plan with a joined-input watermark and assert the recorded
right frame is watermarked before its alias and join. Render the same plans and compare the normalized operation order
or explicit expected operations. These tests must fail against the current interpreter.

Run:

    poetry run pytest tests/user_stories/10_generated_code/shared_pyspark_semantic_contract/test_online_recipe_runtime.py \
      tests/specifications/streaming-compatibility -q

### Milestone 2: Prove runtime parity at inheritance and hook boundaries

Add an executable parity fixture for a parent step with a parent raw hook and a child transform that shadows the
same hook name. The parent hook must add an unambiguous column or otherwise leave an observable frame marker; the child
hook must add a different marker so incorrect late name lookup is visible. Compile and render the child transform,
then execute both modes from the same compiled artifact.

Use the existing `assert_online_generated_parity(...)` helper from `structure.lib.testing.parity` to compare output
columns, schema, and rows. The generated module must carry the artifact semantic fingerprint. The test must demonstrate
that the parent hook selected by `PySparkHookRecipe.origin` runs in both modes even though the concrete child instance
has a same-named hook. This is a runtime test, not merely an assertion on generated Python text.

Place the live test under `tests/integration/pyspark` following the existing generated-project context-manager pattern.
If a Spark-free fake test can exercise generated code faithfully, add it under `tests/specifications/transform-inheritance`
as a fast guard, but do not substitute it for the live test. Keep the fixture bounded and use static batch DataFrames;
it needs no streaming query lifecycle.

Run when PySpark is installed:

    poetry run pytest --run-integration tests/integration/pyspark -q

### Milestone 3: Add bounded streaming parity evidence and make its prerequisite explicit

Add one opt-in integration test for a caller-supplied streaming DataFrame and a static lookup input. Use the repository's
existing local Spark integration fixture and a bounded source suitable for test execution. The test must run the same
transform in online and generated modes, assert both returned DataFrames are streaming, assert the expected watermark
metadata or analyzed plan contains the declared event-time field and delay, and compare a bounded sink result only when
the fixture explicitly owns and cleans up its query. Do not add `readStream`, `writeStream`, trigger, checkpoint, or
sink behavior to `StructureSession`; those remain test-harness responsibilities.

If maintaining a bounded streaming query is too unstable for the normal integration suite, retain a live plan-analysis
test that does not start a query, document the manual bounded-query command in `docs/dev/Testing.md`, and mark that
command release-blocking. The plan must record the chosen approach and why.

Update `docs/dev/specifications/ExecutionSemanticContract.md`, `docs/dev/specifications/OnlineExecution.md`, and
`docs/dev/specifications/SparkStreaming.md` to state that every lowered operation, specifically watermark placement,
is consumed by both modes. Update the public streaming reference if it promises the same behavior. Update
`docs/dev/Troubleshooting.md` with the environment prerequisite and the remedy when live parity tests skip because
PySpark is not installed.

## Validation and Acceptance

The work is complete only when all of the following are true:

- A source-scope watermark recipe results in exactly one online `DataFrame.withWatermark(field, delay)` call at the
  same ordered position as generated code.
- A joined-input watermark reaches the online right DataFrame before aliasing and joining, matching generated source.
- Online and generated modes produce equivalent schema and rows for the inherited parent-hook fixture, and the fixture
  proves the parent body—not a child method with the same name—ran.
- An opt-in real-PySpark streaming fixture proves both modes retain the declared watermark on a caller-supplied
  streaming input, or a documented release-blocking manual test does so.
- Generated fingerprint validation remains enabled; no test bypasses it by directly importing stale code.
- `make build` passes. When PySpark is installed, `poetry run pytest --run-integration tests/integration/pyspark -q`
  passes with no skipped selected parity tests.

## Idempotence and Recovery

The changes are additive and safe to rerun. Fake-frame tests do not create files or Spark sessions. Generated projects
in integration tests must use each test's temporary directory and existing cleanup context manager. If a streaming
test leaves a query running, stop it in a `finally` block and delete only its test-owned temporary checkpoint path.
If local PySpark is unavailable, run the compiler and fake-frame suites, retain the explicit skipped integration output
in the plan, and run the live command in CI or a PySpark-equipped environment before accepting the work.

## Artifacts and Notes

The intended consumer relationship is:

    Transform source
        -> compiler and PySpark lowerer
        -> one PySparkExecutionPlan
           -> online interpreter: calls DataFrame APIs
           -> generator: renders the same APIs
        -> equivalent observable DataFrame plan and result

For the present defect, the required symmetry is:

    PySparkOperationRecipe(kind="watermark", scope="events", delay="10 minutes")
        -> online: events.withWatermark("event_time", "10 minutes")
        -> generated: events.withWatermark("event_time", "10 minutes")

No execution mode may drop, relocate, or invent that operation.

## Interfaces and Dependencies

No production third-party dependency is added. Use the existing PySpark DataFrame API, compiled recipe models,
renderer, online executor, parity helper, and integration harness. `pyspark` remains an optional test dependency
required only for live integration verification. Do not use generated source as an online-execution fallback, do not
introduce Spark lifecycle ownership, and do not create a parallel watermark model outside `PySparkWatermarkRecipe`.
