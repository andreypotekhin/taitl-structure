# Deferred: Replace Schema Type Constructors with `field.*()` Factories

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows [Plans.md](../../auto/Plans.md). It is intentionally stored in `docs/dev/planning/postponed/`: the API redesign is agreed in principle but must not be started until the active v3 work and its current compatibility changes are stable. When promoted, move this file to `docs/dev/planning/` before implementation and update the progress entries rather than creating a second plan.

## Purpose / Big Picture

Structure schemas currently use a broad top-level type-class surface:

    total = field(Decimal(12, 2), nullable=False)
    promo_code = field(String(), nullable=True, alias="promo-code")

That is explicit, but it forces users to import names such as `String`, `Map`, and `Decimal` into application modules. It also makes a schema member look like a generic function call wrapped around a separate type object.

After this change, schema declarations use a small, namespaced factory surface:

    total = field.decimal(12, 2, nullable=False)
    promo_code = field.string(alias="promo-code")

The observable outcome is that users write only `field.*()` to declare schema members, while standalone type values needed by casts and UDF contracts use `types.*()`. The schema still preserves all existing Spark-visible type, nullability, alias, metadata, description, inheritance, and collection-shape behavior. Comments remain prose only: they never affect schema discovery or compilation.

## Surprises & Discoveries

- Observation: `Schema.__init_subclass__` currently obtains a field's name from the mutable `FieldDeclaration`
  descriptor after Python invokes `__set_name__`.
  Evidence: `src/structure/app/dsl/model/schemas/Schema.py` iterates class-dictionary values and calls
  `value.definition()`, while `FieldDeclaration.__set_name__` writes `self.name`.

- Observation: Reusable scalar field factories require immutable declarations, because one object such as
  `field.string()` may appear in more than one class body.
  Evidence: mutating one declaration's `name` during `__set_name__` would leak the last bound name into every earlier
  use of that object.

- Observation: Structure types are used outside schema declaration.
  Evidence: expression casts accept `StructureType` values, and DSL documentation describes calls such as
  `expr.cast(Integer())`; compiler recipes and tests construct the same values directly.

- Observation: PySpark's schema model has no primary-key or uniqueness constraint.
  Evidence: Structure's current `FieldDefinition.primary_key` is not a Spark `StructField` feature. The compiler uses
  it only as a user assertion when deciding whether to issue `JOIN-W0601` for a lookup join.

- Observation: the checked-out worktree is dirty in schema, compiler, documentation, and test areas unrelated to this
  postponed plan.
  Evidence: `git status --short` on 2026-07-13 reported pre-existing modifications and untracked v3 tests. Promotion
  must begin with a fresh overlap check rather than assuming those changes belong to this redesign.

## Decision Log

- Decision: Use lowercase methods on a `field` namespace: `field.string()`, `field.decimal(precision, scale)`, and
  `field.array(...)`.
  Rationale: The namespace avoids exporting common type class names into user modules and makes a schema declaration
  visibly different from an ordinary Python value.
  Date/Author: 2026-07-13 / User and Codex

- Decision: Preserve `nullable=True` as the default for a declared field.
  Rationale: Existing schemas, generator output, and documentation rely on nullable-by-default behavior. Required
  fields remain explicit through `nullable=False`.
  Date/Author: 2026-07-13 / User and Codex

- Decision: Keep nullability of array elements and map values on their container factories:
  `contains_null=` and `value_contains_null=`.
  Rationale: A nested field declaration supplies the nested type only. Letting child `nullable=` also control a
  container would create two conflicting ways to specify the same fact.
  Date/Author: 2026-07-13 / User and Codex

- Decision: Add a parallel `types` namespace for standalone `StructureType` values.
  Rationale: Schema declarations need field metadata, whereas casts, UDF return types, expression recipes, and compiler
  APIs need a type value alone. `types.integer()` makes that distinction explicit without retaining top-level `Integer`.
  Date/Author: 2026-07-13 / User and Codex

- Decision: Do not use source comments as an executable schema language.
  Rationale: Python discards comments during import, while Structure discovers schemas from runtime objects. Parsing
  comments would make dynamically created schemas and imported schemas behave differently and would make aliases,
  precision, and nullability harder to validate.
  Date/Author: 2026-07-13 / User and Codex

- Decision: Remove `primary_key` rather than replace it with another field modifier in this change.
  Rationale: PySpark does not enforce primary keys; the current flag is an unchecked single-field uniqueness assertion.
  A future design for declared unique keys must be schema-level so it can model composite keys and define validation
  semantics deliberately.
  Date/Author: 2026-07-13 / User and Codex

- Decision: This is a breaking public API replacement, not a long-lived dual syntax.
  Rationale: Maintaining both declarations would leave two canonical examples, duplicate generators and diagnostics,
  and defeat the goal of removing broad top-level type names. A temporary migration error for `field(...)` is allowed
  only to explain the replacement; it must not execute the old API.
  Date/Author: 2026-07-13 / User and Codex

## Context and Orientation

Structure is a Python library rooted at `src/structure`. Users subclass `Schema`; each declared class attribute becomes
a row field used by compiler checks, generated PySpark schemas, runtime schema validation, documentation, and expression
access. A `FieldDefinition` is the immutable effective field contract. It records the Python attribute name, Spark type,
field nullability, physical Spark-column alias, metadata, and description.

The current public declaration function is in
`src/structure/app/dsl/model/schemas/schema_api.py`. It accepts a `StructureType` object and creates a mutable
`FieldDeclaration`. Scalar and collection type wrappers live in `src/structure/app/dsl/model/types/`; they wrap
immutable `StructureType` value classes. `Schema` in `src/structure/app/dsl/model/schemas/Schema.py` captures local
declarations and combines inherited fields. The public DSL API is re-exported by
`src/structure/app/dsl/api/__init__.py` and top-level `src/structure/__init__.py`.

Use these terms consistently during implementation:

- Field declaration: an object assigned in a `Schema` class body. It carries a Spark type and field-only options until
  the schema binds it to an attribute name.
- Type value: an immutable `StructureType` value. It represents only a Spark type and is valid for casts, UDF type
  contracts, compiler recipes, and nested type construction.
- Root field: the class-body declaration that becomes a `FieldDefinition`. Its `nullable` option defaults to `True`.
- Nested field: a declaration passed to `field.array(...)` or `field.map(...)` to identify a child type. It is not a
  column, so it must not carry column-only metadata or field nullability.
- Container nullability: `contains_null` for array elements and `value_contains_null` for map values. Map keys are
  non-null by Spark definition.

The target syntax is:

    from structure import Schema, field, types


    class Customer(Schema):
        id = field.string(nullable=False)
        name = field.string()
        email = field.string(alias="email-address")


    class Order(Schema):
        total = field.decimal(12, 2, nullable=False)
        discount = field.decimal(12, 2)
        tags = field.array(field.string(), contains_null=False)
        attributes = field.map(
            field.string(),
            field.string(),
            value_contains_null=False,
        )


    def normalize(raw):
        return raw.total.cast(types.decimal(12, 2))

In this example, `name`, `email`, `discount`, `tags`, and `attributes` are nullable fields because their root
declarations omit `nullable=False`. A present `tags` array cannot contain null elements; a present `attributes` map
cannot contain null values. `field.string()` inside a collection is a bare nested declaration: it describes a type,
not the nullability of the outer field.

## Plan of Work

### Milestone 1: Establish immutable declaration and type boundaries

At the end of this milestone, `field.*()` and `types.*()` exist as internal/public API candidates, field declarations
can safely be reused, and every pre-existing `StructureType` still renders to the same Spark type.

Refactor `FieldDeclaration` so it no longer owns a mutable `name`. Make it immutable and make materialization accept the
class attribute name explicitly, for example `definition(name)`. Preserve the immutable copy of supplied metadata and
all existing validation. `Schema.__init_subclass__` must iterate `cls.__dict__.items()` so it knows the attribute name
and must call `value.definition(attribute_name)` for each declaration. Inherited-field ordering and duplicate physical
column validation must remain unchanged.

Field factories must distinguish an omitted root option from an explicitly supplied option. Use a private `UNSET`
sentinel or an equivalent immutable option record. Public signatures should still present `nullable=True`, `alias=None`,
`metadata=None`, and `description=None` as normal user-facing defaults through overloads or documentation. This record
lets nested validation reject `field.string(nullable=True)` even though the root default is also nullable.

Replace the `field(type_, ...)` function in `schema_api.py` with a typed `field` namespace object. It has factories for
the current supported schema types: `string`, `integer`, `long`, `float`, `double`, `boolean`, `date`, `timestamp`,
`decimal`, `array`, `map`, and `struct`. Every factory returns a `FieldDeclaration` based on the same type value the
current class constructor would produce. Scalar factories accept only root field options. Decimal validates precision
and scale exactly as current `Decimal` does. Collection factories retain their current element/key/value checks.

Create a typed `types` namespace object alongside the schema API. It exposes the same factory names but returns
`StructureType` values, not field declarations. Its `array`, `map`, and `struct` factories accept type values. This is
the only public way to create a standalone Structure type after the migration. Internally it may delegate to existing
wrapper classes or directly construct their immutable base type objects; behavior and equality must stay structural.

`field.array(child, ...)` and `field.map(key, value, ...)` accept field declarations for child arguments, then obtain a
type through a dedicated `nested_type()` operation. That operation must reject a child that explicitly supplied
`nullable`, `alias`, `metadata`, or `description`, with an error explaining the correct container option. For example,
`field.array(field.string(nullable=False))` must fail with text directing the user to `contains_null=False`.

Nested collections must work recursively. `field.array(field.map(field.string(), field.decimal(12, 2)))` is valid
because the inner map declaration has type-specific options only and no root field options. Nested structs must work
with `field.struct(Address)` and in any collection position. Continue rejecting invalid `Struct` targets and recursive
schema graphs at schema declaration time.

Make the `field` namespace callable only to raise a focused `TypeError`, not to run the old API. The error must show a
direct rewrite such as `field(String(), nullable=False) -> field.string(nullable=False)` and link users to the schema
reference. Do not leave an executable legacy overload.

Add focused unit tests close to `tests/user_stories/05_schemas/fields_with_types_and_nullability/` that prove every
new factory produces the existing effective type and field defaults. Add a regression test that assigns one factory
result to two schemas and verifies both definitions keep their own names. Do not migrate the full test suite in this
milestone; it would hide API-boundary defects.

### Milestone 2: Replace public imports and non-schema type consumers

At the end of this milestone, top-level users can import `Schema`, `field`, and `types`, and every public DSL consumer
that needs only a type uses `types.*()`.

Export `field` and `types` from `src/structure/app/dsl/api/__init__.py` and `src/structure/__init__.py`. Remove
`String`, `Integer`, `Long`, `Float`, `Double`, `Boolean`, `Date`, `Timestamp`, `Decimal`, `Array`, `Map`, and `Struct`
from the documented and `__all__` public surface. The underlying classes may remain importable by internal modules but
must not be presented as user-facing DSL constructors.

Update expression casts and aliases, special-function return-type handling, compiler recipe construction, and any
other public API that validates a `StructureType` to accept values returned by `types.*()` without any adapter-visible
change. Replace internal tests that construct public wrappers merely to create a type value with `types.*()` where they
test public behavior; retain internal base type construction only when a test specifically covers implementation logic.

Update the public API snapshot test so it proves `field` and `types` are present and all legacy constructor names are
absent. Add tests for `expr.cast(types.integer())`, `expr.astype(types.string())`, and UDF/special return type values.

### Milestone 3: Remove primary-key claims and revise join diagnostics

At the end of this milestone, schema fields no longer advertise a primary key, and lookup-join diagnostics do not treat
an unchecked field flag as proof of uniqueness.

Remove `primary_key` from `FieldDeclaration`, `FieldDefinition`, field factory signatures, documentation data, schema
generation output, and serialization/traceability data that exposes fields. Remove its implicit `nullable=False`
normalization because callers now declare required fields directly with `nullable=False`.

In compiler frontend join analysis, remove the method or branch that recognizes a right-hand field as a primary key.
An ordinary `lookup_join(...)` without an explicit deterministic deduplication policy must retain or emit `JOIN-W0601`
when its right-side uniqueness cannot otherwise be proven. Rewrite its `use` text so it recommends a deterministic
`JoinDedupe`, or a join form whose row multiplication is explicit; it must not suggest `primary_key=True` or generic
uniqueness metadata.

Update compiler-diagnostic tests that previously expected a primary-key join to suppress the warning. Ensure a required
field alone has no special uniqueness meaning. Remove the user story that promises primary keys or uniqueness hints, or
rewrite it to describe the current explicit-deduplication behavior. Do not introduce a replacement unique-key API in
this plan; that requires a separate schema-level design with composite-key and validation semantics.

Update all examples under `examples/` and all testing source models under `res/testing/model/` from the old form to the

    field(String(), nullable=False)       -> field.string(nullable=False)

Move root options unchanged onto the outer factory. For example,

Update `RenderStructureSchemaSource` and its mapping helpers so generated source imports `Schema` and `field`, emits

## Validation and Acceptance

The redesign is accepted only when all of the following behaviors are true:

- A user can define a nullable field with `name = field.string()` and a required field with
  `id = field.string(nullable=False)`.
- `field.decimal(12, 2, nullable=False)` creates the same decimal precision, scale, and field nullability as the
  previous `field(Decimal(12, 2), nullable=False)` declaration.
- `field.array(field.string(), contains_null=False)` distinguishes a nullable array column from non-null array
  elements, and maps to Spark's `ArrayType(StringType(), containsNull=False)`.
- `field.map(field.string(), field.string(), value_contains_null=False)` maps to a Spark map with non-null values.
- `field.array(field.string(nullable=False))` fails immediately with a message that names `contains_null=False`.
- `raw.cast(types.integer())` works wherever the old `raw.cast(Integer())` worked.
- Reusing a declaration object cannot cause one schema's field name, alias, metadata, or description to appear in
  another schema.
- `from structure import String` and equivalent broad constructor imports are no longer part of the public API;
  canonical imports use `field` and `types`.
- A lookup join is not silently considered unique because a field is non-null. It emits the documented warning unless
  its cardinality is made explicit through the supported join/deduplication mechanism.
- No checked-in public schema documentation or generated schema source presents `field(String(), ...)`,
  `primary_key=True`, or comment text as executable schema metadata.
- `make build` passes.

## Interfaces and Dependencies

The feature adds two public namespace objects:

    field.string(*, nullable: bool = True, alias: str | None = None,
                 metadata: Mapping[str, object] | None = None,
                 description: str | None = None) -> FieldDeclaration

    field.decimal(precision: int, scale: int, *, nullable: bool = True,
                  alias: str | None = None, metadata: Mapping[str, object] | None = None,
                  description: str | None = None) -> FieldDeclaration

    field.array(element: FieldDeclaration, *, contains_null: bool = True,
                nullable: bool = True, alias: str | None = None,
                metadata: Mapping[str, object] | None = None,
                description: str | None = None) -> FieldDeclaration

    field.map(key: FieldDeclaration, value: FieldDeclaration, *, value_contains_null: bool = True,
              nullable: bool = True, alias: str | None = None,
              metadata: Mapping[str, object] | None = None,
              description: str | None = None) -> FieldDeclaration

    field.struct(schema: type[Schema], *, nullable: bool = True, alias: str | None = None,
                 metadata: Mapping[str, object] | None = None,
                 description: str | None = None) -> FieldDeclaration

`field.integer`, `field.long`, `field.float`, `field.double`, `field.boolean`, `field.date`, and `field.timestamp`
have the same field-option signature as `field.string`. There is deliberately no `primary_key` parameter.

`types` exposes the analogous factory names but returns `StructureType`; its type factories accept only parameters that
describe the type itself. For example:

    types.string() -> StructureType
    types.decimal(precision, scale) -> StructureType
    types.array(element: StructureType, *, contains_null=True) -> StructureType
    types.map(key: StructureType, value: StructureType, *, value_contains_null=True) -> StructureType
    types.struct(schema: type[Schema]) -> StructureType

No new third-party dependency is required. The change relies only on existing Python typing facilities, existing
immutable Structure type values, and the project test/build commands.
