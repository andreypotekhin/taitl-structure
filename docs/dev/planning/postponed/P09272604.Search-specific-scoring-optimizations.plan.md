## Context and Orientation


`examples/search/transforms/scoring/lexical/ScoreBase.py` expands tokens and declares query-term counting; overlap
and BM25 scoring inherit that preparation separately. `examples/search/transforms/online/scoring/lexical/OnlineScoring.py`
uses combined gap queries for scoring and vector-cache invalidation. `ScoreOverlap.py` derives vocabulary relations
from index terms at request time. These are application opportunities, not evidence of measured speedups.

## Decision Log

Decision (2026-09-27): Keep Search as one public component, preserve strict validation and sentence-splitting UDFs,
and do not introduce implicit global caches or change ranking formulas.

## Plan of Work


### Workstream 1: Shared lexical preparation


Prepare query tokens/counts once for overlap and BM25. First specify token normalization, multiplicity, scope, and
watermark equivalence. Compare shared preparation with current independent branches on empty, duplicate-token,
multi-query, and mixed-scope fixtures. Investigate shared document-term matches only after this smaller change is
proven; aggregation semantics must remain identical. Reuse compiler optimization if it already eliminates duplication.

### Workstream 2: Score-family-specific refresh


Separate lexical and vector refresh/invalidation sets. Specify authoritative cached versus newly calculated scores,
freshness boundaries, models, experiments, scope, and consistency across a query group before editing composition.
Test lexical-stale/vector-fresh and the inverse, mixed misses, empty caches, and complete warm caches. Finer
query/document/scope refresh is a separate later extension, not assumed equivalent to whole-query recomputation.

### Workstream 3: Prepared corpus statistics


Specify reusable vocabulary/statistics artifacts associated with index revisions. Define creation, persistence,
invalidation, ownership, concurrent readers, and cleanup before implementation. Compare cold preparation and warm
request costs, including all setup and invalidation costs. Do not silently cache across changing corpus revisions.

## Validation and Acceptance


Promotion requires unchanged rows, schemas, rankings, supported streaming contracts, strict validation errors,
online/generated parity, and measured end-to-end improvement. Include cold/warm caches, partial freshness, duplicate
keys, optional inputs, and revision changes. Reject prototypes without measured benefit; retain negative evidence.
