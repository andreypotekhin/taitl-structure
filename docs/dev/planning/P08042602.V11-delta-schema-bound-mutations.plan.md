# Add schema-bound Delta mutations to the PySpark plugin

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept current as work proceeds.

This plan follows `docs/dev/auto/Plans.md` and is scheduled as a V11 cross-cutting feature package under
`docs/dev/project-management/V11.md`. It defines the first Structure-owned Delta integration slice; it does not claim
general Delta Lake API parity.

## Purpose / Big Picture

After this work, a user can define Delta CHECK constraints once on a Structure `Schema`, bind that schema to an
existing Delta table, and use typed predicates for supported table mutations without repeating field names or SQL
constraint strings. The vendor class remains visible as the vendor class; Structure exposes a clearly named
`DeltaTableWrapper` around it.

The first observable workflow is:

    class Order(Schema):
        status = string()
        refund_amount = double()

        constraints = (
            check(
                (status != "refunded")
                | (refund_amount.is_not_null() & (refund_amount > 0)),
            ),
        )

    table = DeltaTableWrapper.for_path(spark, path).set_schema(Order)
    table.delete(lambda order: order.status == "refunded")

`set_schema(Order)` is the one source of truth. It validates the existing table shape and installs or verifies the
native Delta checks. A supported mutation can only run through a schema-bound wrapper. The first mutation is
`delete`; future `update` and `merge` work must use the same bound-handle contract after their typed assignment
semantics are specified.

## Surprises & Discoveries

- Observation: Ordinary `Transform.run()` is a row-producing contract and should not own Delta mutations.
  Evidence: Structure keeps storage, writes, actions, and orchestration caller-owned; Delta `delete`, `update`, and
  `merge` change an external table and have transaction/retry consequences.
- Observation: A schema declaration by itself cannot enforce a Delta CHECK constraint on an external table.
  Evidence: Native enforcement belongs to Delta table metadata. The explicit `set_schema()` operation is required to
  bind the Structure schema and install or verify those native checks.
- Observation: A manifest without a binding operation would create a second deployment workflow and could leave the
  table unenforced.
  Evidence: The agreed user workflow requires the `Schema` declaration to remain the only authored constraint source.
- Observation: PySpark field declarations already exist as class-body objects, but they are currently field metadata,
  not a complete standalone expression namespace.
  Evidence: `src/structure/core/dsl/model/schemas/FieldDeclaration.py` produces finalized field definitions during
  `Schema.__init_subclass__`; the implementation must preserve symbolic field tokens until that finalization step.

## Decision Log

- Decision: Implement Delta support inside `structure.plugin.pyspark`.
  Rationale: DeltaTable consumes PySpark sessions, DataFrames, and predicates; it is a PySpark runtime integration,
  not an alternate Structure transformation target.
  Date/Author: 2026-08-04 / Codex.
- Decision: Name the public adapter `DeltaTableWrapper`.
  Rationale: The public name must not shadow the vendor's `delta.tables.DeltaTable` and should make the ownership
  boundary obvious.
  Date/Author: 2026-08-04 / Codex.
- Decision: Use `Schema.constraints` and `check(...)` as the public constraint vocabulary.
  Rationale: `CHECK` is Delta terminology, while `constraints` makes the schema-level collection clear. The field
  references remain symbolic Python objects rather than strings.
  Date/Author: 2026-08-04 / Codex.
- Decision: Make check names optional.
  Rationale: Most users should not repeat a name that can be derived deterministically. Explicit names remain available
  for interoperability and migration control.
  Date/Author: 2026-08-04 / Codex.
- Decision: Derive anonymous names from schema name, referenced field name when exactly one field is used, and source
  declaration sequence.
  Rationale: Delta requires unique names, and this gives stable, readable names such as
  `Order__refund_amount__check_001` and `Order__check_002` without field-name strings in predicates.
  Date/Author: 2026-08-04 / Codex.
- Decision: Require `set_schema(schema)` before every supported mutation.
  Rationale: The bound schema supplies the field vocabulary, expected shape, and native CHECK contract. Requiring it
  up front prevents untyped mutations and makes the enforcement boundary explicit.
  Date/Author: 2026-08-04 / Codex.
- Decision: Make `set_schema()` explicit and idempotent; do not install checks automatically from `delete`, `update`,
  or `merge`.
  Rationale: Installing a native check changes table metadata and can upgrade the Delta writer protocol. Users must see
  and control that deployment step, while still maintaining the definition in only one Schema class.
  Date/Author: 2026-08-04 / Codex.
- Decision: Keep Delta mutations outside ordinary `Transform.run()`.
  Rationale: A standalone Delta command may consume a Structure schema without requiring a Transform. This preserves
  caller-owned table lifecycle and avoids mixing external side effects with row-transform execution.
  Date/Author: 2026-08-04 / Codex.
- Decision: Admit `delete` in the first mutation slice; defer `update` and `merge` until typed assignment semantics are
  specified.
  Rationale: `delete` needs only a schema-bound predicate. `update` and `merge` also need a string-free, typed assignment
  DSL and stronger transaction/evidence coverage.
  Date/Author: 2026-08-04 / Codex.

## Context and Orientation

Structure is a schema-first Python library. A `Schema` class declares fields used by transforms and by the PySpark
plugin. A transform's `run()` method produces DataFrames or named outputs; it does not own storage writes or external
table mutations. Delta Lake is an optional PySpark runtime integration. Its vendor `DeltaTable` class represents a
Delta table and performs operations such as delete, update, and merge.

The implementation belongs under `src/structure/plugin/pyspark`. The existing symbolic expression model is
`src/structure/plugin/pyspark/dsl/Expression.py`; field factories and declarations are under
`src/structure/plugin/pyspark/dsl/field.py` and `src/structure/core/dsl/model/schemas/FieldDeclaration.py`. Static
backend capabilities live under `src/structure/plugin/pyspark/capabilities`. Late runtime provider resolution is
already demonstrated by `src/structure/plugin/pyspark/geo/runtime.py`. The public plugin facade is assembled through
`src/structure/plugin/pyspark/api/PluginAPI.py`.

The first slice must remain Spark- and Delta-free during compiler-only commands. Importing the Delta wrapper or
executing a Delta command may load the optional `delta` package late. The project must not make `delta-spark` a core
dependency for ordinary PySpark transforms.

## Plan of Work

### Milestone 1: Normative design and admission

Create the paired V11 Delta design and specification documents. Define the user-visible contract for `Schema.checks`,
`check(predicate, *, name=None)`, anonymous-name derivation, field-token binding, `DeltaTableWrapper`,
`set_schema`, schema-bound mutation requirements, and the explicit boundary around Transform execution.

Add API Catalog and API Reference rows with separate statuses for `check` declarations, `set_schema`, `delete`, and
future `update`/`merge`. Mark update and merge as planned or design-gated until their assignment contract exists. Add
capability keys and diagnostics before any row is marked supported.

The milestone is complete when a reader can tell which code runs during compiler-only work, which code requires Delta,
which operation changes table metadata, and which operation performs a table mutation.

### Milestone 2: Symbolic checks and names

Extend field declaration handling so a schema class can write symbolic expressions without string field references:

    class Order(Schema):
        status = string()
        refund_amount = double()
        country_code = string()

        constraints = (
            check(status != "refunded"),
            check(country_code.length() == 2),
        )

`check()` returns an immutable declaration. The schema finalization path collects only the reserved `constraints`
attribute, validates that every referenced symbol belongs to the schema, resolves logical names and physical aliases,
and rejects unsupported expression types. Field-local `.constraint(...)` is not part of this milestone.

Anonymous names are assigned in source declaration order. A single-field expression uses the logical Structure field
name; a multi-field expression uses only the schema name. Names are normalized to a safe Delta identifier. Explicit
names are preserved after validation. Duplicate names and conflicting explicit names fail at compile time.

The resulting internal record must contain the check name, schema identity, referenced fields, typed expression, rendered
Delta predicate when available, source location, and a deterministic sequence number. It is separate from the shape-only
generated `StructType` schema.

### Milestone 3: Capability and runtime integration boundary

Add static PySpark capability requirements for Delta check rendering, Delta schema binding, and Delta delete. Add a
plugin-owned runtime integration report with availability, version, supported features, and actionable diagnostics.
Use `optional`, `required`, and `disabled` integration modes under the PySpark plugin's Delta options. Do not create a
generic Core `enable()` method or modify a caller-owned Spark session.

The renderer must produce deterministic Delta SQL predicates from Structure expressions. It must handle identifiers,
aliases, numeric/string/date literals, boolean precedence, null predicates, `LIKE`, and supported standard functions.
It must reject unsupported expressions rather than falling back to arbitrary SQL strings or serializing a live PySpark
`Column` through private JVM representation.

### Milestone 4: DeltaTableWrapper and schema binding

Add `DeltaTableWrapper` with late vendor imports and factories such as `for_path` and `for_name`. The wrapper delegates
table loading to `delta.tables.DeltaTable` but never exposes a public API that shadows the vendor class.

Implement:

    table = DeltaTableWrapper.for_path(spark, path)
    bound = table.set_schema(Order)

`set_schema()` returns a schema-bound wrapper. It validates the existing table shape, derives the expected native Delta
checks, installs missing checks through the vendor API, and no-ops when the exact check already exists. It must fail on
an incompatible table schema, duplicate/conflicting check names, or existing rows that violate a newly installed check.
It must not create tables, evolve columns, silently drop checks, or run implicitly from a mutation.

The wrapper should retain the vendor object only as an internal delegate. If a `.native` escape hatch is exposed, its
documentation must state that native mutations bypass Structure's schema and check guarantees.

### Milestone 5: Schema-bound delete

Implement the first supported mutation:

    bound.delete(lambda order: order.status == "refunded")

The lambda runs in a dedicated symbolic row scope backed by `Order`. It must not execute arbitrary Python or require
field-name strings. The compiler validates field access and types, then renders the predicate using the same expression
renderer used for checks. Calling `delete` on an unbound wrapper fails with a diagnostic that instructs the user to call
`set_schema(Order)` first.

Because delete removes rows, it does not evaluate row checks. The table's native checks remain installed for future
write-like operations. Add an explicit boundary test proving that delete is still unavailable without schema binding,
even though its predicate alone could be rendered.

### Milestone 6: Future mutation contract and V11 evidence

Document the shared contract for future `update` and `merge`: they must require a schema-bound wrapper and must rely on
native Delta checks for transactional enforcement. Do not mark them supported until a typed assignment DSL, concurrency
behavior, online/runtime evidence, and diagnostics are specified.

Run the Delta ordinary-runtime evidence lane with a pinned Delta version compatible with the claimed PySpark profile.
Keep Delta tests optional when the dependency is absent, but ensure missing, disabled, and incompatible integration
states have deterministic negative tests. Reconcile V11 API Catalog, reference, compatibility, troubleshooting,
capability, and evidence documents.

## Validation and Acceptance

The package is accepted when a novice can define an anonymous `check(...)` using only symbolic field references, bind
the schema once with `DeltaTableWrapper.set_schema(Order)`, and perform a supported `delete` without any duplicate SQL
or field-name definitions.

Compiler-only `structure check` and `structure compile` must not import `delta`, start Spark, create a Spark session, or
inspect a table. A missing Delta runtime must produce a named integration diagnostic at runtime. A disabled integration
must fail even if the package is installed. An unbound mutation must fail before the vendor operation is invoked.

`set_schema(Order)` must be idempotent for matching table shape and checks, must install missing checks, and must fail
when existing data violates a newly installed check. An existing check with a conflicting predicate must not be
silently replaced. A bound delete must render the predicate with physical aliases and delegate to the vendor Delta
operation. A schema class reused by a Transform and by a standalone Delta command must retain identical field and check
semantics.

The first slice must not claim support for table creation, schema evolution, vacuum, optimize, history, restore, generic
table properties, merge builders, or untyped raw SQL predicates. Those rows remain caller-owned, planned, or design-gated.

## Idempotence and Recovery

`set_schema()` is intentionally idempotent for an unchanged schema. Re-running it should not add duplicate checks or
change existing table metadata. If a check expression changes, preserve the old table check and fail with a migration
diagnostic; do not drop or replace it automatically. If a table schema is incompatible, stop before mutation and report
the expected and actual shape.

Delta integration tests must use isolated temporary tables or disposable test paths. Never run installation tests
against a user table. If optional Delta dependencies are unavailable, run all Spark-free and negative integration tests
and record the missing positive evidence rather than weakening the feature status.

## Interfaces and Dependencies

The public wrapper is `structure.plugin.pyspark.delta.DeltaTableWrapper`. It exposes `for_path`, `for_name`,
`set_schema`, and the first supported mutation `delete`. `set_schema` returns a schema-bound wrapper; mutation methods
must reject an unbound wrapper. The vendor `delta.tables.DeltaTable` remains the implementation delegate and is imported
only at runtime.

The public schema DSL adds `check(predicate, *, name=None)` and the reserved `Schema.constraints` collection. Check
predicates use the existing Structure expression semantics, including `&` and `|` for symbolic boolean composition.
Anonymous names are deterministic and are part of the generated Delta check specification, not the predicate source.

The capability surface adds requirements for Delta integration availability, check rendering, schema binding, and
delete. The runtime integration report must distinguish unavailable, disabled, incompatible, and available states.
The compiler must remain independent of both PySpark and Delta imports.
