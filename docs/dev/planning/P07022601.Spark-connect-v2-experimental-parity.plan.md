# P07022601 Spark Connect V2 Experimental Parity

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and

This document follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can update Structure's design,

## Purpose / Big Picture

Structure currently describes Spark Connect as v4 backend-expansion work. That is too late for planning if the v2
analytical feature set can stay inside the same PySpark DataFrame and Column contract. After this plan is complete,
the documentation will state a more precise path: ordinary PySpark remains the v1 and primary v2 target, while the end
of v2 adds an experimental Spark Connect parity lane for v1 and completed v2 batch features. Spark Connect remains a
PySpark target variant, not a separate alternative backend and not a SQL target.

The visible result is a consistent documentation set that teaches this configuration shape:

    [tool.structure]
    target_backend = "pyspark"
    target_profile = ">=3.5,<4.1"
    target_variant = "spark-connect"

The same docs must also replace canonical use of `target_pyspark` with `target_profile`. Existing compatibility notes
must not preserve `target_pyspark` as a compatibility alias because Structure has no release or deployment compatibility
burden yet. The implementation should rename the active field now.

## Decision Log

- Decision: Keep other SQL targets out of scope for this plan.
  Rationale: Spark Connect is a PySpark client/server execution variant. It should not be bundled with Spark SQL,
  DuckDB SQL, generic SQL rendering, or other SQL-family target decisions.
  Date/Author: 2026-07-02 / Codex

- Decision: Model Spark Connect as `target_variant = "spark-connect"` under `target_backend = "pyspark"`.
  Rationale: Spark Connect uses the PySpark DataFrame API over a remote session. It should reuse the PySpark target
  adapter where semantics match, while capability checks reject classic-only assumptions such as SparkContext, RDD,
  direct JVM/Py4J access, `_jdf`, and private implementation fields.
  Date/Author: 2026-07-02 / Codex

- Decision: Make `target_profile` the canonical version/profile key and retire canonical docs use of `target_pyspark`.
  Rationale: `target_profile` works for PySpark and later backends. Keeping a PySpark-specific version key as the
  primary spelling makes the future backend contract harder to explain.
  Date/Author: 2026-07-02 / Codex

- Decision: Replace `target_pyspark` immediately instead of keeping it as a legacy alias.
  Rationale: Structure has no releases or deployments yet, so compatibility migration cost is effectively zero. Carrying
  both keys would create avoidable resolver precedence, documentation, tests, and diagnostics complexity.
  Date/Author: 2026-07-02 / Codex

- Decision: Place experimental Spark Connect parity at the end of v2, after the mainstream v2 analytical feature work
  and adoption tooling are stable.
  Rationale: Moving it earlier than v4 is reasonable because it is PySpark-family, but adding it before v2 analytical
  semantics are settled would double the parity matrix while the operation contract is still moving.
  Date/Author: 2026-07-02 / Codex

- Decision: Keep full Spark Connect support as a later promotion, not as a v2 guarantee.
  Rationale: V2 should prove parity for completed v1/v2 batch features under an experimental label. Promotion requires
  capability diagnostics, online/generated contract evidence, documentation, and CI coverage.
  Date/Author: 2026-07-02 / Codex

## Context and Orientation

Structure is a Python library whose users write typed transform classes. The compiler builds backend-neutral
intermediate representation, often shortened to IR, which is an internal data model describing the transform semantics.
The PySpark target then lowers that IR to live PySpark DataFrame execution for online mode or generated PySpark source
for generated mode.

The active backend is configured through `[tool.structure]`. Today the only executable backend is PySpark. Existing
docs commonly show:

    target_backend = "pyspark"
    target_pyspark = ">=3.5,<4.1"

This plan changes the documented canonical spelling to:

    target_backend = "pyspark"
    target_profile = ">=3.5,<4.1"
    target_variant = "ordinary"

`target_backend` names the implementation backend family. `target_profile` names the version or capability profile for
that backend. `target_variant` selects a runtime variant inside the backend family. For PySpark, the documented values
are `ordinary` and `spark-connect`. `ordinary` means the normal in-process PySpark `SparkSession`, `DataFrame`, and
`Column` contract. `spark-connect` means the caller supplies a Spark Connect session and Structure must avoid
classic-only PySpark internals.

This plan intentionally removes `target_pyspark` from current implementation and current docs. Because there is no
released compatibility contract, the resolver should reject `target_pyspark` as an unknown key after this work. Do not
add aliasing or precedence rules.

The main documentation files to update are:

- `docs/specifications/ConfigSchema.md` for the formal configuration contract.
- `docs/specifications/CompatibilityPolicy.md` for PySpark profile and Spark Connect scope.
- `docs/specifications/BackendCapabilities.md` for capability identity and unsupported-feature diagnostics.
- `docs/specifications/AlternativeBackends.md` and `docs/dev/design/AlternativeBackends.md` to say Spark Connect is a
  PySpark variant, not a generic alternative backend or SQL target.
- `docs/dev/project-management/Roadmap.md`, `docs/dev/project-management/Milestones.md`, and v2 sprint docs to place
  experimental Spark Connect parity at the end of v2.
- Public docs such as `Readme.md`, `docs/Overview.md`, `docs/QuickRef.md`, `docs/Configuration.md`, and
  `docs/Compatibility.md` so users see one consistent story.
