# Generated Transform Inheritance Boundaries

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement owner-aware
transform inheritance execution and generated transform class boundaries from this file alone.

## Purpose / Big Picture

Structure already lets a child transform inherit parent step methods and explicitly call a parent implementation from
an override. Today the compiler flattens that inheritance into one ordered plan. That works, but generated PySpark code
still appears as one concrete generated class, and hook execution identifies hooks mostly by method name. This makes
parent-class hook execution fragile when subclasses override or shadow names, and it hides useful source inheritance
boundaries from generated code review.

After this change, Structure keeps compiler IR as the semantic source of truth, but records the declaring owner of each
compiled step and hook. Online execution uses that owner metadata to call the exact parent or child hook body intended
by the compiled plan. Generated PySpark may then organize inherited transform fragments into separate generated Python
classes, letting subclass overrides call parent generated methods with normal Python `super()` style calls while still
running Spark-visible DataFrame operations.

The observable behavior is a transform like this:

    class NormalizeBase(Transform):
        rows = input(Raw)
        normalized = lane(Normalized)

        @transform(output=normalized)
        def normalize(self, row: Raw) -> Normalized:
            return Normalized(id=row.id)

        @after(normalize, lane=normalized)
        def audit_parent(self, *, normalized, spark, ctx):
            return normalized.withColumn("parent_hook", F.lit(True))

    @transform
    class PublishOrders(NormalizeBase):
        published = output(Published)

        @transform(output=NormalizeBase.normalized)
        def normalize(self, row: Raw) -> Normalized:
            parent = super().normalize(row)
            return Normalized(id=parent.id)

        def publish(self, row: Normalized) -> Published:
            return Published(id=row.id)

After implementation, online and generated execution both run the parent `NormalizeBase.audit_parent` hook for the
parent scheduled step even if `PublishOrders` later declares a hook with the same Python method name. The generated
module should make the boundary reviewable by rendering a parent generated class method for the parent step and a child
generated class method for the child override.

## Surprises & Discoveries

- Observation: Transform inheritance is already implemented by flattening effective members into `TransformPlan.steps`.
  Explicit parent calls are compiled by temporarily patching overridden parent methods during symbolic execution.
  Evidence: `src/structure/app/compiler/frontend/commands/CompileTransform.py` uses
  `_parent_call_patches(...)`, and existing tests assert generated order for `DirectNormalize.normalize`, `normalize`,
  and `publish`.

- Observation: Generated PySpark currently renders one generated class per concrete source transform.
  Evidence: `src/structure/app/target/pyspark/commands/RenderPySparkTransformModule.py` emits
  `class {Transform}Generated:` and renders all steps inside `run(...)`.

- Observation: Hook recipes currently carry hook `name` but not hook declaring owner.
  Evidence: `HookPlan` and `PySparkHookRecipe` contain `name`, `phase`, `target`, lanes, outputs, and metadata, while
  `PySparkHookInvoker` calls `getattr(invocation, hook.name)(**kwargs)`.

- Observation: Overridden parent hook members are still available through `CompilerTransformMember.overridden`.
  Evidence: `CompilerHookCollector` can collect overridden hook members and attach them to the overridden parent target
  key, so an explicitly scheduled parent step can run its parent hooks without changing flattened plan semantics.

## Decision Log

- Decision: Keep flattened compiler IR as the semantic source of truth.
  Rationale: Online execution, generated execution, validation, traceability, and backend lowering already agree through
  ordered plans. Preserving that contract avoids creating a second semantic interpretation of Python inheritance inside
  generated code.
  Date/Author: 2026-07-07 / Codex and project owner

- Decision: Add owner metadata before changing generated class shape.
  Rationale: Owner-aware hook and step metadata fixes the correctness boundary first. Separate generated classes can
  then be a rendering organization over known semantics rather than a risky semantic migration.
  Date/Author: 2026-07-07 / Codex and project owner

- Decision: Owner-qualified hook execution should call the declaring function with the concrete invocation instance.
  Rationale: This runs the exact parent or child hook body selected by the plan while preserving ordinary Python `self`
  behavior, so parent hooks can still use subclass-provided helpers or state if that is intentional.
  Date/Author: 2026-07-07 / Codex and project owner

- Decision: Generated classes may inherit from other generated classes, but must not inherit from source transform
  classes.
  Rationale: Source transform classes are authoring surfaces; generated classes are compiler-owned runtime artifacts.
  Keeping that separation preserves the existing generated-code rule while still making generated inheritance
  boundaries reviewable.
  Date/Author: 2026-07-07 / Codex and project owner

## Context and Orientation

A Structure transform is a Python class inheriting from `Transform`. It declares input DataFrames with `input(Schema)`,
intermediate lanes with `lane(Schema)`, final outputs with `output(Schema)`, and public schema-returning methods as
step methods. A hook is a Python method decorated with `@before(...)` or `@after(...)`; hooks are explicit PySpark
escape hatches and remain opaque to compiler expression analysis.

The current compiler path is:

1. `src/structure/app/dsl/api.py` exposes `compile_transform(...)`.
2. `src/structure/app/compiler/frontend/commands/CompileTransform.py` builds a backend-neutral `TransformPlan`.
3. `src/structure/app/target/pyspark/commands/LowerPySparkPlan.py` maps that plan to a `PySparkExecutionPlan`.
4. `src/structure/app/runtime/execution/online/commands/RunOnlinePySparkTransform.py` executes the PySpark plan online,
   or `src/structure/app/target/pyspark/commands/RenderPySparkTransformModule.py` renders generated PySpark source.

The current inheritance path is:

- `CompilerTransformMemberCollector` gathers inherited step method and hook methods in parent-first order.
- `CompilerTransformMember` records the method owner, name, callable, order position, and overridden parent members.
- `CompileTransform._parent_call_patches(...)` turns explicit calls such as `super().normalize(row)` into separate
  compiled parent steps.
- `StepPlan.name` may already be qualified for a parent-call step, for example `DirectNormalize.normalize`.

The current gap is that owner identity is not carried far enough. `StepPlan` and `HookPlan` do not expose stable owner
metadata to lowerers and runtimes. Once a hook becomes a `PySparkHookRecipe`, execution only knows the method name. If a
parent and child use the same hook method name or a subclass shadows a parent hook, `getattr(invocation, hook.name)` may
resolve the child attribute even when the compiled boundary was declared by the parent.

## Plan of Work

Milestone 1 records origin metadata in compiler IR. Extend `StepPlan` with step owner information and extend
`HookPlan` with hook owner information. The owner should be represented in a deterministic, generated-code-friendly way:
store at least the owner module and owner class name, and keep the owner class object where the in-memory compiler and
online runtime can use it safely. A small frozen model such as `TransformMemberOrigin` is preferable to scattering
strings. It should identify `module`, `class_name`, `member_name`, and optionally the owner type object.

In `CompileTransform._compile_step(...)`, use `CompilerTransformMember.owner` and `CompilerTransformMember.name` to set
the step origin. In `CompilerHookCollector.collect(...)`, use the effective hook member's owner and name to set the hook
origin. Preserve the existing hook target behavior: hook target lookup still binds hooks to the target step method
member, including overridden parent members known through `CompilerTransformMember.overridden`.

Milestone 2 carries the metadata into PySpark recipes. Extend `PySparkStepRecipe`, `PySparkStepResultRecipe` only if
needed, and `PySparkHookRecipe` with origin fields mapped from `StepPlan` and `HookPlan`. Update
`PySparkStepMapper` and `PySparkHookMapper` to copy those fields. This should be a mechanical lowering change and
should not change rendered code yet, except for tests that inspect recipe metadata.

Milestone 3 fixes online hook dispatch. Update `PySparkHookInvoker.apply(...)` so that when a hook recipe includes an
owner type object, it retrieves the raw function from that owner class dictionary and calls it with the concrete
invocation as the first argument:

    function = hook.owner_type.__dict__[hook.member_name]
    result = function(invocation, **kwargs)

If the owner type object is absent, fall back to the old `getattr(invocation, hook.name)(**kwargs)` path so injected or
serialized execution plans fail gracefully during migration. Keep Spark Connect error wrapping behavior around the new
call path. Add tests where a parent hook and child hook use the same name, and assert the parent scheduled step calls
the parent body.

Milestone 4 factors generated rendering into generated methods while preserving existing output. Before introducing
generated inheritance, move step rendering out of the `run(...)` body into protected methods on the generated concrete
class. For example, render `_step_normalize(...)`, `_step_publish(...)`, or another deterministic private/protected name
that includes the step ordinal when needed to avoid collisions. `run(...)` should validate inputs, build `HookInputs`,
store raw inputs as it does today, then call these generated methods in plan order. This milestone should keep one
generated class and preserve all existing generated behavior.

Milestone 5 introduces generated parent classes for inherited transform owners. The renderer should group step recipes
by step owner. For each non-concrete owner that contributes compiled steps, emit a generated parent class before the
concrete generated class. The concrete generated class should inherit from generated parent classes using the same
effective order as the compiled plan. Parent generated classes should not own a separate source implementation; they
receive and use the concrete `_impl` instance created by the final generated class. Parent generated methods may call
owner-qualified hooks using the hook owner metadata, for example:

    rows = NormalizeBase.audit_parent(self._impl, normalized=rows, spark=self.spark, ctx=self.ctx)

When a subclass override explicitly called a parent step method, the generated child method may call the parent
generated method directly, for example:

    rows = super()._step_normalize_base(rows, inputs=inputs)

If reconstructing direct `super()` call structure from the flattened plan is too large for the first generated-class
slice, keep `run(...)` calling methods in flattened plan order while still rendering those methods on the generated
owner classes. That fallback still gives reviewable class boundaries and can be promoted later to intra-method parent
calls.

Milestone 6 updates specifications and examples. Update `docs/dev/specifications/DSL.md` and
`docs/dev/specifications/PySparkCodeGeneration.md` to say that transform inheritance semantics are defined by compiler
IR, that generated classes may preserve source transform ownership through generated parent classes, and that generated
classes still must not inherit from source transform classes. Add a short note that hooks execute according to their
declaring transform owner, not by late name lookup alone.

## Validation and Acceptance

Acceptance is met when all of these are true:

- Online execution calls the hook body owned by the compiled hook boundary, even when the concrete subclass has an
  attribute with the same hook name.
- Lowered PySpark recipes carry deterministic owner metadata for steps and hooks.
- Existing transform inheritance behavior remains unchanged: parent steps run before child steps, explicit parent calls
  produce separate scheduled parent steps, and generated output preserves plan order.
- Generated PySpark can render inherited transform boundaries as separate generated classes without inheriting from
  source transform classes.
- Generated hook calls are owner-qualified when needed for inherited parent hooks.
- Generated and online execution remain semantically equivalent for inherited transforms, hooks, validation, and
  explicit parent calls.

The strongest manual inspection signal is generated text shaped like this:

    class NormalizeBaseGenerated:
        ...
        def _step_normalize(...):
            ...
            rows = NormalizeBase.audit_parent(self._impl, normalized=rows, spark=self.spark, ctx=self.ctx)
            return rows

    class PublishOrdersGenerated(NormalizeBaseGenerated):
        ...
        def run(...):
            rows = self._step_normalize(...)
            rows = self._step_publish(...)
            return TransformResult(...)

The exact generated method names may differ, but they must be deterministic, collision-free, and readable.

## Idempotence and Recovery

All work should be additive until tests pass. Re-running tests and regeneration is safe. If generated rendering changes
large snapshots, inspect the corresponding `PySparkExecutionPlan` first to distinguish semantic recipe changes from
formatting-only changes.

If generated parent-class rendering proves too large, stop after Milestone 4 with owner-aware hooks and protected
per-step methods. Record that fallback in `Outcomes & Retrospective`; do not merge partial generated inheritance that
changes generated class shape without owner-qualified hook correctness.

Do not remove the existing flattened plan path. The flattened plan remains the compatibility layer for online execution,
traceability, streaming compatibility checks, and future non-PySpark backends.

## Interfaces and Dependencies

New or extended internal interfaces:

- `TransformMemberOrigin` or equivalent frozen model under `src/structure/app/compiler/ir/model/`, carrying owner
  module, owner class name, member name, and optionally the owner type object for in-process execution.
- `StepPlan.origin` and `HookPlan.origin`.
- `PySparkStepRecipe.origin` and `PySparkHookRecipe.origin`.
- `PySparkHookInvoker` owner-qualified dispatch helper.
- Generated renderer support for protected per-step methods and generated owner classes in
  `RenderPySparkTransformModule` and `RenderPySparkStep`.

No new third-party dependency is required. The feature uses existing Python class objects, dataclasses, compiler IR,
and PySpark rendering infrastructure.
