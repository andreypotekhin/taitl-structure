## Purpose / Big Picture

v7 makes Structure useful across a deliberately broad, checked portion of the PySpark DataFrame transformation surface while taking the next safe step in caller-owned streaming adoption. A developer will be able to choose a supported typed operation from one catalog, receive a corrective diagnostic for an excluded operation, and use the admitted operations in both batch and caller-managed streaming transforms with matching online and generated behavior.

## Context and Orientation

Structure's bundled PySpark plugin is under `src/structure/plugin/pyspark`. A typed operation is an operation captured in Structure's symbolic model, lowered through public PySpark DataFrame and Column APIs, represented in explain and traceability output, and rendered identically in online and generated execution. Caller-owned streaming means the caller still constructs sources and owns sinks, checkpoints, triggers, output modes, and query lifecycle; Structure only returns a transformed streaming DataFrame.

The authoritative current gap inventory is `docs/dev/Gaps.md` and the v6 ledger is `docs/dev/specifications/V6PySparkApiLedger.md`. The completed v6 release plan is `docs/dev/planning/done/P07242604.V6-pyspark-api-and-example-hook-retirement.plan.md`. Do not revive a prior plan's scope without first recording its selected disposition here.

## Plan of Work

First, publish a v7 catalog derived from the PySpark 3.5.x/4.0.x intersection. Every candidate must state its user value, dependency family, schema and cardinality effect, batch and streaming eligibility, generated representation, diagnostics, traceability, and explicit disposition. Prioritize high-use relational and projection transforms, scalar/conditional/date-time/string functions, nested and collection transformations, joins, aggregation/windows, and remaining relation operations. Reject actions, I/O, raw SQL, arbitrary callbacks, RDD/Pandas APIs, untyped UDTFs, and physical-plan controls until a separate contract admits them.

Before adding a family, extract the focused delegate needed at its seam from the oversized operation, expression, scope, result, evaluation, execution, rendering, or traceability component. Characterize existing behavior first; preserve public façade imports and generated snapshots. Each delegate must have one responsibility and direct tests. The extraction is complete only when every named v6 module has either a focused delegate or a documented, measured reason it is already cohesive.

For each admitted batch slice, write a concise specification and then add symbolic capture, immutable plugin-body records, capability checks, lowering, online evaluation, rendering, explain, traceability, diagnostics, examples, and focused online/generated parity tests. Run live PySpark 3.5 and 4.0 evidence for each family before calling it supported. Keep Spark Connect status separate from classic PySpark status.

For streaming, deliver three independently verified stages: stream-static inner/left-semi enrichment; left-outer lookup;
and one existing stateful operation followed only by stateless transforms. The design must classify each operation as
stateless, stateful with a declared bound, or unsupported; reject two-stateful chains, unbounded state, sources, sinks,
and query management. Add file-stream restart and state evidence before claiming support.

Reconcile historical deferred work as follows. v4 incremental compilation/cache diagnostics remains retained backlog because it is compiler performance rather than transformation or streaming behavior. v4 caller-owned streaming is complete; its next adoption stage belongs to this plan. v5 plugin-owned DSL-body residuals become a boundary audit only where v7 extracts or extends PySpark behavior; the finite-iterable generator plan remains retained backlog. v6's unfinished delegate extraction is in scope. V6 Spark Connect schema/plan-boundary work is an optional v7 enabling spike, not a release requirement, unless a selected feature needs it. Data-quality constraints, cross-library restructuring, persistent artifact bundles, and Search-only evaluation live evidence remain retained backlog unless separately scheduled.

## Validation and Acceptance

The v7 catalog has no unclassified relevant transformation candidate. Every supported operation has a typed authoring example, visible generated PySpark, capability decision, explain/traceability record, diagnostic tests, online/generated parity test, and recorded classic-PySpark 3.5/4.0 result. Unsupported operations fail before execution with a supported alternative or an explicit raw-boundary explanation.

Streaming acceptance requires live file-stream evidence for each admitted family on both classic target versions. Generated transform code must contain no source, sink, trigger, checkpoint, output-mode, action, or query-lifecycle call. The caller can retain ownership of these calls while receiving a transformed streaming DataFrame. `make build` must pass at release close.

## Idempotence and Recovery

Catalog and documentation changes are additive. Keep an old implementation beside a delegate only until characterization and parity tests prove equivalence, then remove it in the same change. Do not update generated fixtures unless a specification change explains the difference. If a live target disagrees, mark the operation unsupported for that target and return to the design gate rather than weakening the declared contract.
