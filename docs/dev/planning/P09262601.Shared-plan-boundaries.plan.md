# Generalize batch plan boundaries and measure Search


This ExecPlan follows `docs/dev/auto/Plans.md`. Keep Progress, Surprises & Discoveries, Decision Log, and
Outcomes & Retrospective current.

## Purpose / Big Picture


Make compiler-selected temporary-view references available on all PySpark backends, reducing repeated transmission
and construction of shared plans where Spark benefits. A fan-out is a frame consumed by multiple steps or outputs.
Named views do not sever Spark logical lineage or guarantee shared physical execution; retain the reliable fusion
checkpoint in Search. Measure the change instead of claiming that a small fixture implies inexpensive planning.

## Context and Orientation


`src/structure/plugin/pyspark/api/CompilerAPI.py` resolves plugin options. `LowerPySparkPlan` counts consumers and
`MapPySparkStep` attaches boundaries to validation recipes. `RunOnlinePySparkTransform` and `RenderPySparkStep`
execute or render these recipes. `PlanBoundaryTracker` owns unique session-scoped views and drops them on close.
`tests/integration/pyspark/support/backend_matrix.py` configures both generated and online paths. The existing
Search timing helper measures construction including its eager fusion checkpoint, so that phase is not pure planning.

## Plan of Work


First replace `connect_plan_boundaries` with `plan_boundaries`, rejecting the removed name with a migration error.
Resolve auto by default on every backend, except an explicit transform streaming contract defaults to off.
Keep explicit off/auto/strict values; streaming-capable inputs alone do not alter the default. Auto selects frames
with multiple distinct downstream step/output consumers, including exposed stage outputs; remove the eighth-step
cadence. Strict selects every non-final step. Guard each online/generated boundary with the frame's actual
`isStreaming` state. Keep current view ownership/cleanup and Search fusion checkpoint behavior.

The approved follow-up stages the input of an explicit Connect checkpoint step through an owned view before
executing that step's operations. Restore the input alias immediately, before joins can introduce additional
qualifiers. This avoids the protobuf nesting failure without adding an eager action, changing operation order,
or replacing Search's final fusion checkpoint. Mark this in `PySparkCheckpointRecipe.stage_input` during Connect
lowering, independently of the off/auto/strict policy; ordinary checkpoints stay unchanged. Both runners must
skip staging for streaming inputs, which retain the existing checkpoint rejection. Test a 60-projection input,
qualified output expressions, online/generated parity and owned-view cleanup with the compiler policy off.

Next test configuration, fan-out selection, linear graphs, exposed outputs, streaming guards, cleanup and parity.
Update current configuration references and integration override to `STRUCTURE_PLAN_BOUNDARIES`; historical plans
remain historical. Regenerate affected golden examples through the repository generator. Update Search docs and
troubleshooting without promising that named views truncate Catalyst lineage.

Finally run sequential fresh runners with policy off/auto, alternating order over three repetitions for each of
ordinary Spark 3.5/4.0 and Connect 4.0. Run the reranking and text-fixture selectors separately, then the full Search
module. Keep stage outputs off, existing heaps, partitions, fixtures, and checkpoint settings fixed. Record phase
times, totals, exit codes and medians in `docs/dev/issues/I09272601/SearchIntegrationPerformance.bench.md`. A repeatable bounded
failure should be diagnosed once and recorded; do not run hours of identical failing repetitions.
`scripts/benchmark_search_boundaries.py` automates this sequence and writes raw logs, results, and median phase times
to a caller-selected output directory. It refuses to overwrite logs and stops repeating a configuration after two
failures. Use `--cases module boundaries --repetitions 1` for the final regression runs.

## Surprises & Discoveries


The old boundary policy is forced off on ordinary Spark and inserts every eighth step on Connect. Existing timings
include eager checkpoint execution, and named views do not themselves sever Spark's logical lineage.

2026-09-26: The current final-output-only Search plan has 92 steps, 15 selected view boundaries, and one explicit
checkpoint inside `fused.materialize_candidates`. The first auto pilot on ordinary 3.5 passed in 184.91 seconds:
online construction 76.42s, generated construction 77.69s, collections 0.85/0.43s. This is not a controlled median.
The full build initially found stale generated goldens after the final-output boundary fix. Regenerated examples
then passed all 17 golden tests and the full build. A final build after additional regression cases is running.

2026-09-26: Connect reranking fails with both policies at the fusion checkpoint with protobuf
`Exceeded upb_DecodeOptions_MaxDepth`. Fan-out reuse does not limit long linear request depth. A diagnostic-only
pytest plugin is testing a view immediately before the explicit checkpoint; production behavior remains unchanged.
The view bypasses serialization failure, but must preserve the compiler's qualifier. With qualifier restoration,
online construction completed (43.21s, checkpoint 34.88s); the server JVM exited during generated execution while
another Spark runner was active. Repeat in isolation before drawing conclusions. The user approved production
checkpoint-input staging, including under policy off. Stage at step entry rather than after joins, so aliases
introduced inside the step retain their meaning.

## Decision Log


2026-09-26: User approved production compiler work, global batch auto, and removal of the old option without an alias.
Retain explicit checkpoint semantics and add no automatic eager materialization. Count distinct step consumers and
exposed outputs so unused stage outputs do not introduce boundaries. Runtime streaming checks are necessary because
Search declares streaming-capable inputs while accepting batch frames.

2026-09-26: User approved a separate Connect checkpoint-execution fix. Its input-staging view is part of explicit
materialization, not an additional fan-out policy rule. `off` disables compiler reuse boundaries but no longer
disables checkpoint request compaction. The Search component graph and eager action count remain unchanged.

For root-cause follow-up, the current 92-step Search graph contains 157 declared joins, 52 singleton-policy checks,
six `require_all` assertions and two `require_unique` assertions. The assertion implementation derives a guard
from the input and cross-joins that guard back to the input. That duplicates upstream lineage within an operation,
which step-level fan-out counting cannot see. Profile growth at these operations, then investigate equivalent
guard reuse and assertion lowering before adding more materialization. Preserve lazy validation failure semantics,
including nulls, empty inputs, downstream filtering and duplicate keys. Earlier materialization inside
FuseDocuments is a separate candidate if intrinsic graph duplication cannot be eliminated.

2026-09-27: Those three follow-ups are now implemented and verified in
[Search guard reuse](past/P09262602.Search-guard-reuse.plan.md). Bounded policy checks reuse nine guard constructions
instead of 52; early checkpoints precede both fusion uniqueness checks. All seven Search tests pass on ordinary
3.5/4.0 and Connect 4.0. The isolated profiled 3.5 comparison reduced combined construction from 140.63s to 56.79s.
This is separate evidence from the earlier off/auto medians and does not turn single observations into medians.

passes: 1,905 tests passed / 180 skipped in the primary suite and 73 passed / 7 skipped in the regression suite.
Ordinary 3.5 reranking medians are 170.35s off and 174.09s auto, showing no demonstrated gain; all six runs passed.

change less than 2% on each backend. No measured focused run reports heap exhaustion. Live streaming/cleanup
tests pass on ordinary 3.5. Full-module regressions, remaining live boundary lanes, and a checkpoint diagnostic
remain in progress. The Connect serialization failure prevents declaring the plan complete.
