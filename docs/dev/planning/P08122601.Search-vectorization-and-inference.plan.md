# Add provider-backed inference and cache-aware Search vectorization

This ExecPlan is a living document. It follows `docs/dev/auto/Plans.md`; the `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections must remain current throughout implementation.

## Purpose / Big Picture

Search currently accepts provider-produced query embeddings and document-vector index rows, but it cannot infer a vector for a newly encountered query or an uncached document during request serving. After this change, `SearchDocuments` will resolve vector gaps after filter-target selection, invoke a configured inference adapter for those gaps, use successful embeddings immediately, and emit them for caller-owned persistence and cache warming. Offline preparation will use the same inference contract to build reusable document and query embeddings.

The model provider remains replaceable and caller-configured. Structure owns typed request/response contracts, cache and gap orchestration, validation, fallback behavior, and a deterministic default adapter for development and tests. It does not own a model service, credentials, storage, or hidden mutable cache.

## Surprises & Discoveries

- Observation: `Vectorization` should be the provider-neutral inference stage, while cache-gap resolution and cache merging are facet/pipeline concerns.
  Evidence: `Vectorization` now accepts only the relations to infer and `InferencePolicy`; `OnlineFiltering` selects targets, `OnlineVectorization` selects gaps and merges vectors, and `SearchDocuments` passes ready-to-score relations between facets.
- Observation: the repository already has a replaceable compiler-visible strategy pattern.
  Evidence: `examples/store/transforms/personalization/score.py` passes `PersonalizationAlgorithm()` through `parameter(...)`, while Search transforms are ordinary Structure compositions.
- Observation: arbitrary runtime model calls cannot be represented as ordinary compiler-visible row expressions.
  Evidence: `docs/dev/specifications/HookSemantics.spec.md` and `docs/dev/specifications/ExplicitScalarUdfs.spec.md` require explicit runtime boundaries; this plan therefore keeps adapter execution behind the inference boundary while the default adapter remains deterministic and compiler-compatible.
- Observation: provider selection cannot be dynamically dispatched from a row-level `provider_id` inside a compiler-visible Structure step.
  Evidence: compiling a registry method that indexed a Python adapter map with `policy.provider_id` produced `DSL-E0401` because the policy field is symbolic at authoring time. The registry therefore resolves a concrete compiler-visible adapter at application configuration time; `Inference` and Search transforms still receive only policy data.
- Observation: `All` contains a pre-existing user working-tree change increasing `maximum_offline_queries` from 1,000 to 100,000.
  Evidence: `git diff -- examples/search/transforms/all/all.py`; preserve this change.

## Decision Log

- Decision: Put adapter configuration under top-level `examples/search/inference/`, and the executable `Inference` stage under `examples/search/transforms/inference/`.
  Rationale: model execution configuration and Search workflow orchestration are separate responsibilities; callers can replace adapters without confusing configuration objects with Structure stages.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: Use relation-level query and document inference operations rather than row-level hooks.
  Rationale: providers can batch model requests and support streaming micro-batches without exposing provider-specific calls in `SearchDocuments`.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: Select a concrete compiler-visible adapter through an application/process registry keyed by `InferencePolicy.provider_id`; calling Search transforms receive only `InferencePolicy`.
  Rationale: Structure cannot dynamically dispatch a Python adapter map from a symbolic policy field. Resolving the adapter when configuring the inference boundary preserves the no-hooks Search funnel and still allows provider-specific adapters with Spark-compatible expressions.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: Use `streaming=True` for online vectorization and `streaming=False` for offline cache creation.
  Rationale: the same adapter contract supports provider-specific execution optimization while preserving one semantic boundary.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: Inference failures produce status rows; failed query inference preserves lexical-only search, and failed document inference removes only that document from the vector lane.
  Rationale: vector inference is optional enrichment and must not make lexical Search unavailable.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: Successful embeddings are outputs of offline/online vectorization for caller persistence and cache warming.
  Rationale: Structure must not own hidden mutable state; the caller owns persistence and later cache inputs.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: The default adapter creates stable normalized token-hash vectors with dimension 100; custom adapters may use any policy dimension.
  Rationale: tests need deterministic local inference while production models must not be constrained to the default dimension.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: `RetrieveDocuments` uses the single `OnlineScoring.document_scores` relation for both stored and streamed score merges.
  Rationale: `online_streamed_document_scores` was a duplicate alias of the same scoring output and added a redundant public/input contract.
  Date/Author: 2026-08-12 / user and Codex.

## Outcomes & Retrospective

Implemented the provider-backed inference and cache-aware vectorization path. `SearchDocuments` now runs
`OnlineVectorization` after `OnlineFiltering`; it fills query and selected-document gaps, merges successful vectors,
feeds them into online scoring, and exposes embedding/status outputs. `All` runs `OfflineVectorization` with `streaming=False` and
feeds the resulting query vectors and document index into offline scoring. The shared workflow preserves compatible
cache rows, supports arbitrary policy dimensions, and uses a normalized stable token-hash adapter by default.

Compiler and generated-output parity are covered by the Search golden suite and focused vectorization tests. Final
validation: `make build` passed with 1,636 tests passed and 66 skipped; the rigidity suite passed 73 tests and skipped 6.
Spark-backed integration tests remain skipped because this environment has no integration backend. Provider-specific
runtime adapters remain an application configuration boundary: Structure requires a concrete compiler-visible adapter
to be selected before graph compilation, while `InferencePolicy` carries the provider/model identity through the typed
workflow.

## Context and Orientation

The Search example lives under `examples/search`. Lexical index artifacts are produced by `Indexing`; `Filtering` and `OnlineFiltering` create and resolve document admission artifacts; `Scoring` produces lexical and vector score rows; `Ranking` bounds vector scores; and `SearchDocuments` retrieves, fuses, and reranks results. The current vector package normalizes provider-produced query embeddings through `VectorizeSearchQueries`, while `VectorIndex` validates caller-supplied document embeddings into `DocumentVectorIndex` rows.

`SearchDocuments` must preserve its current funnel and insert vectorization only after `OnlineFiltering`, because document inference must be limited to the bounded selected target set. `OnlineScoring` owns request-valid merging of stored, streamed, and newly calculated document scores before retrieval. `All` is the offline pre-serving composition and must invoke offline vectorization separately from scoring. `DocumentVectorIndex` remains the validated, caller-persisted document vector artifact.

## Plan of Work

First add `InferencePolicy`, inference request/status contracts, and the adapter protocol/registry. The protocol exposes separate query and document methods receiving a typed request relation, policy, and `streaming` flag, and returning typed embeddings plus statuses. Register the deterministic token-hash adapter as the default provider. Validate adapter output through the existing `Vectors.valid_embedding` contract and fail invalid output rather than silently dropping it.

Next add vectorization compositions. The shared `Vectorization` workflow only calls the `Inference` stage for the
relations supplied by its caller and publishes inferred embeddings/statuses; it does not resolve cache gaps or merge
cached rows. The `OfflineVectorization` facet owns all-document target generation, invokes inference for the complete
document/query population with `streaming=False`, and owns offline cache merging. `OnlineVectorization` owns
query/document gap selection and runs after `OnlineFiltering` with `streaming=True`; it uses query identity for
query gaps and selected document identity/content for document gaps. It must not infer vectors for unselected
documents. `SearchDocuments` consumes the ready vector relations from `OnlineVectorization` and the ready score
relation from `OnlineScoring`; `RetrieveDocuments` only materializes document candidate lanes.

Move `VectorizeSearchQueries` into the lowercase `vectorization/queries/vectorize_queries.py` stage module and retain it as
an independently compilable leaf. Fold request query vectorization into `OnlineVectorization` so SearchDocuments has
one serving vectorization boundary.

Update `SearchDocuments` to consume query/document embedding inputs and policy inputs, invoke `OnlineVectorization` after `OnlineFiltering`, and feed its merged vectors to `OnlineScoring`. Let `OnlineScoring` merge stored, streamed, and newly calculated document scores before `RetrieveDocuments`. Publish online embeddings and inference status/gap relations where the public transform contract permits. Update `All` to invoke `OfflineVectorization` with `streaming=False`, publish offline embeddings/statuses, and feed normalized query vectors and the document index into offline scoring. Update SearchFields and experiment wrappers to forward the new inputs.

Finally update package exports, schema/example registries, docs, annotated sources, compiler tests, live/generated parity fixtures, and golden generated output. Do not edit generated files directly; regenerate them from source.

## Validation and Acceptance

Acceptance requires that a query without a supplied embedding can receive a deterministic or provider-produced vector and proceed through hybrid Search; a selected document without a cached vector can be inferred and participate in the vector lane; an unselected document is never inferred by the SearchDocuments serving path; successful inference rows are available for caller persistence; query failures retain lexical results; document failures do not remove lexical candidates; and online and generated execution agree on all deterministic adapter scenarios.

Tests must cover valid and invalid policy identity, arbitrary dimensions, deterministic default vectors, duplicate requests, cache hits, missing query vectors, missing selected-document vectors, inference statuses, lexical fallback, document omission from vector scoring, offline/online mode flags, generated/online parity, and existing RRF/feedback behavior. Final validation is `make build` with no unresolved failures.

## Idempotence and Recovery

Source changes are ordinary version-controlled edits. Generated output is derived and must be recreated with `make gold`; never hand-edit generated files. The inference registry is process/application configuration only and performs no persistence. If a provider call fails, status rows and lexical fallback preserve the request; if validation fails because an adapter returned an incompatible vector, fail at the declared validation boundary with the model identity and target key.

## Interfaces and Dependencies

The new public contracts are `InferencePolicy`, query/document inference request and status schemas, the inference adapter protocol/registry, the `transforms/inference/Inference` stage, `Vectorization`, `OfflineVectorization`, and `OnlineVectorization`. `Vectorization` and its callers depend on `InferencePolicy` and the existing vector index policy; they do not accept an adapter argument. The default adapter is deterministic and dependency-free. External adapters may use provider-supported Spark-compatible execution, including streaming-aware behavior, but must return the declared typed embedding/status relations and preserve online/generated semantics.
