# Typed Spark SQL Execution

## Purpose

This work adds a typed SQL relation operation to PySpark Transform methods. A Transform author can reuse reviewed Spark SQL while declaring the row schema Structure should expose to the rest of the method. Data-changing statements produce explicitly typed command-result rows with an optional label so a caller can retain, route, and inspect command outcomes as ordinary Transform relations.

The public helper is `structure.plugin.pyspark.sql`. It records a symbolic operation during compilation; the compiler stores it as a `PySparkSqlRecipe`, online execution evaluates it in `RunOnlinePySparkTransform`, and generated code emits the corresponding Spark calls from `RenderPySparkStep`. Both paths must behave alike.

## User-visible behavior

Inside a Transform method, `sql(statement, relations=..., args=..., as_=...)` requires a concrete Structure `Schema`. A SQL query uses its result schema as `as_`. A standard mutation uses `as_=SqlCommandResult` (or a subclass); its `label=` is optional. `relations` maps `{name}` placeholders either to a Structure row scope, which becomes a Spark DataFrame parameter, or to a string table expression, which is inserted as caller-owned SQL text. `args` is reserved for Spark's literal parameter binding.

`SqlResult` is an empty marker subclass of `Schema`. `SqlCommandResult` is a concrete `SqlResult` subclass with a nullable `label` and nullable Long fields `num_affected_rows`, `num_updated_rows`, `num_inserted_rows`, and `num_deleted_rows`. Structure fills the label when supplied and a metric when the backend result provides its matching column; unavailable values are null, never an implied zero. Other concrete direct subclasses represent provider-owned result contracts and require an adapter before they can execute. Standard command results can be returned from step methods, then included in command-result lanes or outputs. Repeated writes to these typed destinations accumulate rows; ordinary outputs retain their existing assignment behavior. The final `TransformResult` continues to expose outputs by their existing names.

SQL execution stays within Transform methods to match Structure's compiled execution model. Query and mutation legality in streaming contexts belongs to Spark and the configured provider. Structure does not parse dialect SQL, create catalogs, manage provider transactions, or retry mutations.

## Repository orientation

`src/structure/core/dsl/model/schemas/Schema.py` defines the target-neutral row-shape base. `src/structure/plugin/pyspark/dsl/` contains public helpers and captured operation plans. `src/structure/plugin/pyspark/compiler/logic/maps/MapPySparkStep.py` lowers plans to immutable runtime recipes. `src/structure/plugin/pyspark/execution/logic/running/RunOnlinePySparkTransform.py` executes recipes directly, while `src/structure/plugin/pyspark/render/logic/steps/RenderPySparkStep.py` renders generated code. Tests under `tests/specifications/` verify public contracts, compilation, online semantics, and generated-code parity.

## Milestones

### 1. Public schema and capture contract

Add `SqlResult`, `SqlCommandResult`, and the `sql()` helper. Capture SQL text, relation kinds, literal arguments, declared schema, optional label, and generated result scope in immutable plan objects. Validate required `as_` and exact relation-placeholder coverage at capture time. Prove that a compiled method exposes query fields as typed expressions.

### 2. Runtime and generated execution

Map the operation into `PySparkSqlRecipe`. Online execution binds relation scopes to DataFrames and delegates SQL to `SparkSession.sql`. String relation values are already substituted by the helper. Standard commands return one result row with the optional label and available backend metrics; absent values are null. Generated code must render the same calls. Keep native Spark/provider exceptions intact.

### 3. Result routing and verification

Allow `SqlCommandResult` subclasses as step result schemas and output/lane-compatible schemas. Repeated command-result writes to the same destination union in execution order, with schema assignability checked during compilation. Add focused tests for capture, errors, SQL query execution, labeled mutation results, and generated-code parity. Run the full `make build` gate.

## Acceptance

The public PySpark API exports `sql`, `SqlResult`, and `SqlCommandResult`. A Transform can bind an input relation, run a typed SQL query, and use its fields in the method's returned projection. A standard command produces a result row that can be returned through a command-result output; repeated writes accumulate. Missing `as_`, mismatched placeholders, invalid supplied labels, or unsupported provider-specific result contracts fail early with clear messages. Online and generated paths follow the same SQL and result-shape rules. The repository passes `make build`.

## Surprises & Discoveries

- `Schema` already computes inherited field definitions, so the command contract can naturally extend `SqlResult` without changes to the core schema model.
- Online execution and code generation are separate implementations. Both require explicit SQL operation dispatch; implementing only one would create observable semantic drift.
- The PySpark plugin currently has no provider SQL-result adapter registry. Direct custom `SqlResult` subclasses are therefore captured as an extension point but rejected for execution until an adapter is available.
- PySpark is not installed in the local development environment, so a live Spark execution was not available. Backend behavior still requires the project's integration environment.

## Decision Log

- The common base is `SqlResult(Schema)` and carries no fields. This allows future result contracts without making them claim command semantics.
- `SqlCommandResult(SqlResult)` is the standard normalized command contract. Structure owns its optional nullable label and four common nullable Long metrics; providers that omit metric columns yield null values.
- Every SQL operation requires `as_`. Query results use ordinary schemas; standard commands use `SqlCommandResult` or a subtype.
- One Transform-only `sql()` helper handles both query and command statements. No direct session-level SQL API is included.
- `relations` accepts either row scopes or caller-owned string relation text. There is no separate `tables=` or identifier model.
- Structure does not retry mutations because a transport error can leave the provider commit outcome unknown.

## Outcomes & Retrospective

The feature is implemented across the public DSL, compiler recipe, online runner, and generated runner. The standard command contract contains an optional nullable label and four nullable Long metrics (`num_affected_rows`, `num_updated_rows`, `num_inserted_rows`, and `num_deleted_rows`); absent provider columns normalize to null. Typed query and command rows flow through Transform methods and command outputs; command-result destinations accumulate rows, and provider subclasses can flow to a base command output while retaining only the declared base fields. Direct custom `SqlResult` contracts still need a provider adapter. Verification passed on 2026-10-01: `make build` completed formatting, lint, and mypy; the main suite passed 2,058 tests with 216 skipped, the rigidity suite passed 78 with 7 skipped, and package sdist/wheel builds succeeded. Live PySpark integration tests were skipped because PySpark is not installed locally. The optional-label update also passes the focused SQL tests and the full build.
