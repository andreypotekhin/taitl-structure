## Purpose / Big Picture

After this plan is complete, Structure users can express the remaining planned PySpark join conveniences without
falling back to hooks: using-key joins, sharper right/full diagnostics, explicit cross join safety, broader join
strategy directives, and forward as-of joins. The work closes the `planned` rows in the `Joins` section of
`docs/dev/Gaps.md` while keeping raw SQL predicates, stream-stream joins, and automatic cost-based reordering out of
the public contract.

Users can see the result by compiling v3 orders-style transforms that use `on="key"` and `on=["k1", "k2"]` join
forms, full/right joins with clear nullable-side output rules, explicit cross joins guarded by
`allow_cartesian=True`, strategy directives that render or fail through capability diagnostics, and forward as-of joins
with deterministic tolerance behavior.

  Rationale: Symbolic predicates are more explicit and preserve Structure's typed expression contract. Using-key joins
  are admitted for readable equality joins and PySpark parity, not as a replacement for symbolic predicates.
  Date/Author: 2026-07-07 / Codex.
- Decision: Do not include automatic join reordering or nearest as-of joins in this hardening slice.
  Rationale: `docs/dev/Gaps.md` marks reordering and nearest as-of joins as `future`; both need separate cost, tie, and
  correctness contracts.

## Context and Orientation

Structure already supports v1 lookup joins, v2 analytical joins, and broad rowset joins. Join source capture builds
intermediate representation that is lowered through shared PySpark recipes for online and generated execution.

Relevant files and documents:

- `docs/dev/Gaps.md`: source gap list for this plan.
- `docs/reference/FullPySparkJoinSupport.md`: public rowset join behavior already admitted.
- `docs/reference/AnalyticalJoinCoverage.md`: analytical join behavior such as as-of joins.
- `src/structure/app/dsl`: public join helpers.
- `src/structure/app/compiler/ir`: join operation records.
- `src/structure/app/target/pyspark`: PySpark join recipe lowering and generated rendering.
- `src/structure/app/compiler/traceability`: join cardinality and dependency reporting.
- `src/structure/app/compiler/compileability/streaming_compatibility`: streaming classification for join forms.
- `tests/specifications` and `tests/user_stories`: behavioral tests.

Terms used in this plan:

- A using-key join is a join where the same field name is used on both sides, such as PySpark's `on="customer_id"`.
- A nullable side is the join side whose fields can be null in outer join output.
- A Cartesian join pairs every left row with every right row. Structure requires explicit acknowledgement through
  `allow_cartesian=True`.
- A strategy directive is a user request for a physical join strategy, such as broadcast, shuffle hash, or sort merge.
  It is not a guarantee that Spark will choose that strategy.

## Plan of Work

Milestone 1 adds using-key joins. Extend the source DSL so equality joins can be written with one key string or a list
of key strings when both inputs expose the same field names. Validate that every key exists on both sides, that key
types are compatible, and that ambiguous duplicate output names are handled by existing projection rules.

Milestone 2 hardens right and full join diagnostics. Audit existing right/full behavior and add diagnostics that name
the nullable side, the field that needs nullable output type, and the source method that constructed the invalid
schema. Keep projection rules strict after row-admitting joins.

Milestone 3 completes cross join safety. Ensure every Cartesian join path requires explicit acknowledgement, explain
output labels the cardinality as row-multiplying Cartesian, and generated code renders reviewable PySpark such as
`crossJoin(...)` or an equivalent explicit `how="cross"` form only after safety checks pass.

Milestone 4 expands strategy directives. Admit shuffle hash, sort merge, merge, and lookup projection directives only
where configured backends support them. Unsupported directives must fail through backend capability diagnostics before
runtime. Explain output should show that directives are requests and may be ignored by Spark.

Milestone 5 adds forward as-of joins. Reuse the existing as-of join orientation where possible, but add direction
semantics for selecting the first right row at or after the left timestamp. Validate tolerance, tie policy, order keys,
and nullable unmatched output. Keep nearest as-of out of scope unless this plan is revised.

## Validation and Acceptance

The plan is accepted when all `planned` join gaps in `docs/dev/Gaps.md` are implemented or explicitly narrowed with
rationale, and when `make build` passes.

Behavioral acceptance:

- Using-key joins compile and run for one key and multiple keys.
- Missing keys, incompatible key types, and ambiguous projections fail with actionable diagnostics.
- Right/full join diagnostics name nullable sides and invalid output fields.
- Cross joins require explicit Cartesian acknowledgement.
- Strategy directives are visible in source, IR, generated code, traceability, and explain output or fail through
  backend capability diagnostics.
- Forward as-of joins have online/generated parity coverage for matched, unmatched, tolerance, and tie scenarios.

## Idempotence and Recovery

The work is additive and test-driven. If a strategy directive cannot be proven portable across the configured PySpark
target range, leave the directive capability-gated and document the target-specific reason. If a generated fixture
drifts unexpectedly, inspect the diff and update only intended join output.

## Interfaces and Dependencies

Use the existing join DSL, IR, capability, recipe, traceability, and explain infrastructure. Do not render raw SQL join
predicates. Do not add hidden join reordering. Do not make compiler commands depend on PySpark runtime startup.
