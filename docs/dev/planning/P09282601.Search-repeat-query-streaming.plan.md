# Reduce Search Repeat-Query Latency with Streaming Execution


Maintain this living ExecPlan according to `docs/dev/auto/Plans.md`. It executes
[I09282601 SearchDocuments repeat-query latency][issue] and the revised
[P08022605 Search streaming contract][search-contract]. Keep the issue open until correctness and measured latency
both justify closure. This document plans implementation; its creation does not implement streaming Search.

## Purpose / Big Picture


A caller should construct SearchDocuments once against immutable, caller-owned snapshots and submit new requests
through a running streaming query. Subsequent requests should avoid rebuilding the full Python query plan and
repeating the batch-only fusion checkpoints. Prove that this yields lower request-to-final-result latency than
repeated batch invocations. The desired fraction-of-a-second response is an experimental target, not a promise.

Structure continues to return transformations of supplied DataFrames. Applications own sources, snapshots, reading,
writing, persistence, recovery checkpoints, triggers, query start/stop, and result delivery. Do not implement a
snapshot store, streaming service, or final-answer cache. Keep the existing public SearchDocuments and batch behavior.

## Surprises & Discoveries


Existing evidence measures costly construction, not a dedicated same-mode sequence of new queries. A historical
Spark 3.5 timing-only observation reported online/generated construction of 27.80/25.60 seconds, including three
checkpoints each, followed by collection of 0.41/0.27 seconds. The completed artifact-reuse matrix passed 54/54
samples, but each sample had a fresh runner. Neither establishes steady-state request latency.

`tests/integration/pyspark/support/rows.py` caches collected rows by DataFrame identity. Repeating that helper call
can return Python data without running Spark. The new benchmark must collect new request results directly.
The existing Search case submits two queries together, then compares online and generated execution; it is not a
series of different queries through one same-mode Structure session.

V10 supports important streaming primitives, but not bounded top-K or a general chain of stateful transformations.
The arbitrary-state example validates metadata only. A `completion_window` field exists in the report but has no
Search execution contract. Do not equate a green metadata test with executable streaming support.

Current bounds differ from the old plan: filtering admits 10,000 candidates, fusion uses a policy-supplied bound,
and reranking considers at most 1,000 candidates and emits at most 100 results. Fusion ranks lexical and vector
branches, validates uniqueness, merges them, computes reciprocal-rank scores, and ranks again. Feedback normalization
depends on a whole query group. Keeping only K provisional rows too early can change the final answer.

## Decision Log


Decision (2026-09-28): Start with a handwritten feasibility prototype and semantic baseline, not a full Search rewrite.
Rationale: missing execution primitives and completion delays may defeat the proposed performance improvement.

Decision (2026-09-28): Keep all storage and streaming lifecycle caller-owned. A session-bound prepared handle, if
needed for fixed transformation reuse, binds caller-owned immutable inputs only and performs no hidden materialization.
Rationale: optimization must preserve Structure's transformation-only responsibility.

Decision (2026-09-28): Preserve one public SearchDocuments, its current batch default, declared stage interface, and
`FuseDocuments(materialize=~streaming)`. Rationale: downstream examples and source-related documentation depend on
component identity; streaming is an additional proved execution path, not a competing public component.

Decision (2026-09-28): Require ordinary Spark 3.5 and 4.0 as the first streaming support targets. Retain Connect 4.0
batch comparisons; promote Connect streaming only after separate positive execution/restart evidence. Rationale:
existing state/restart tests skip Connect, so classic results cannot establish its support.

Decision (2026-09-28): Treat event-time completion and interactive latency as separate acceptance conditions.
Rationale: watermarks describe late-data handling and may stop advancing when input is idle. Shortening tolerated
lateness, injecting artificial future timestamps, or changing to processing-time expiry cannot silently manufacture
a latency win. If the agreed semantics cannot meet the goal, record the failure and seek a contract revision.

## Context and Orientation


`StructureSession.run` in `src/structure/core/runtime/session/model/StructureSession.py` reuses compiled artifacts,
then invokes the backend executor. Artifact reuse does not preserve the request's constructed Spark DataFrames.
`examples/search/transforms/searching/search_docs/SearchDocuments.py` composes filtering, vectorization, scoring,
retrieval, fusion, and feedback reranking. In the same directory, inspect `retrieve.py`, `fuse.py`, and `rerank.py`.
Also inspect `examples/search/transforms/filtering/FilterOverlap.py` and the online scoring/vectorization dependencies.

The PySpark plugin owns symbolic operations, lowering into executable operation recipes, online execution, and code
rendering. Its streaming classifier is
`src/structure/plugin/pyspark/compiler/commands/ClassifyStreamingCompatibility.py`. It currently rejects most
multiple-stateful-operation sequences. Core's `StreamingStateStage` records the facts used by explain output;
metadata extensions must remain backend-neutral. The optional optimizer facet supplies dependency/safety facts for
unused-branch pruning, but removal safety is not a proof of safe reuse or safe streaming execution.

An event-time window groups events using their timestamps. A watermark estimates which older events the application
will no longer accept. A final answer is emitted only when the chosen completion rule establishes that accepted
future events cannot revise it. A state bound limits records or bytes kept while waiting; bounded output alone is
not bounded state. Streaming recovery checkpoints store progress/state, unlike batch DataFrame checkpoints used to
shorten expensive query plans. Both remain under caller-controlled storage and lifecycle.

## Plan of Work


### M1. Establish the baseline and handwritten controls


Create `tests/integration/pyspark/search/test_search_repeat_queries.py` and a test-support handwritten reference in
`tests/integration/pyspark/search/support/handwritten_search.py`. Add a runner at
`scripts/benchmark_search_repeat_queries.py`. These are proving tools, not a second public Search implementation.
Extract reusable inputs from the existing reranking/text fixtures without altering their assertions or the ongoing
checkpoint implementation. Record commit identity and dirty-file hashes before every comparison cohort.

Measure different query texts and IDs against the same caller-owned corpus/policy snapshots in one Spark session
and one Structure session per execution mode. Start with sequential requests; measure concurrent throughput
separately. Use one cold request and 20 distinct subsequent requests in each of three independent session cohorts.
Alternate variant order between cohorts. Keep query-scoped cache misses separate from a deliberate cache-hit scenario;
do not count a final-answer cache hit as a new-query result. Missing/empty optional inputs remain explicit fixtures.

Use four initial controls: Structure online, Structure generated, handwritten equivalent batch PySpark, and handwritten
prepared batch PySpark. The equivalent reference preserves operations, validation, boundaries, inputs, and output
semantics; it must not call generated Structure code. The prepared reference moves only demonstrably fixed work
outside the request, using caller-controlled preparation/materialization. Record every changed operation so reuse
is not confused with weaker validation or a different ranking algorithm. Keep `.transform()` as optional syntax:
it invokes a function again and does not itself provide prepared computation.

Map each Search dependency as fixed, request-dependent, or effectful. Include request time, model/index revisions,
experiment, band membership, feedback, and cache freshness. A policy revision can change independently of a corpus
revision. Python DataFrame identity is not evidence that an external source is immutable. Prototype a session-bound
prepared binding only where needed; no cross-session cache, storage ownership, automatic refresh, or new production
API is required to establish this control.

Acceptance: references match batch Search ranks and schemas on valid inputs and preserve failure behavior on invalid
inputs. Report preparation and per-request work separately, with direct Spark collection and no Python row cache.
Write the semantic dependency map and baseline under `docs/dev/issues/I09282601/` before starting migration.

### M2. Prove the minimal streaming mechanism


Create `tests/integration/pyspark/search/test_search_streaming_prototype.py`. Begin with one request stream joined to
caller-owned static candidates whose scores are final. Retain K candidates per query/scope with a total, deterministic
ordering; test K=1, 3, and a production-sized bound. Increase candidates per key far beyond K and independently
increase active query count. Observe stored candidate records and all auxiliary state, not merely output cardinality.
Do not implement collect-all/sort/slice and describe it as bounded top-K.

Prove completion on out-of-order arrivals, ties, nulls, duplicate events, interleaved requests, missing pairs, and
zero matches. Keep request/experiment/band isolation. Test the last request followed by no more input, using a bounded
wall-clock deadline; record stalled finalization rather than sending future-dated events to make a timing pass.
The event-time baseline must publish its lateness/window settings. Synthetic watermark-advancement fixtures are useful
for correctness but must be labeled and excluded from interactive-latency claims.

Prove finalization observability for empty answers and missing inputs without changing the public `results` schema.
Record the proposed typed completion signal or caller correlation protocol in the prototype contract before public
integration. It must distinguish success-with-no-rows, rejected/expired input, and still-pending work. It must neither
turn polling an empty sink into completion nor add a hidden Structure-owned result service.

Then add a preceding score aggregation with contributions arriving across batches, the lexical/vector merge, and
following normalization/ranking. Verify equality against a batch oracle over the same accepted finite event set.
Final candidate scores and ranks may change before completion: do not evict a candidate based on a provisional score
without proving it cannot re-enter the result. Test full-scope uniqueness, including duplicates outside retained top-K;
silent deduplication or checking only returned candidates would weaken current `require_unique` behavior.

Account separately for validation, dedupe, score-aggregation, and active-query state. Strict duplicate detection may
require more than K identifiers; document finite retention and cardinality limits rather than hiding that state.
If preserving the current contract requires unbounded history or unsafe early eviction, reject the prototype.

Prefer public DataFrame/Column operations. If those cannot express the proved bounded algorithm, prototype a narrow
typed stateful transformation using public version-supported PySpark APIs. Verify ordinary 3.5 and 4.0 separately,
including any optional dependencies and generated execution. Do not use private JVM APIs, RDD conversion, driver
collection, or an opaque hook to bypass compiler admission. This is not permission for a generic arbitrary-state API.

Use caller-owned file sources/sinks and recovery checkpoints to prove normal restart, failed-batch replay, late-event
handling, and no revised final answer. Distinguish logical final emission from physical sink exactly-once delivery;
the caller's sink must handle replay with stable request/snapshot keys. Test changed snapshots/state schema against
checkpoint reuse and reject incompatible restarts before processing.

Promotion gate: record the exact operator signatures, schemas, ordering, completion, error, memory, replay, and
version contracts in `docs/dev/issues/I09282601/StreamingFeasibility.design.md`. Both ordinary profiles must pass
before extending production Search. If only a subset succeeds, leave broader support gated; if completion conflicts
with interactive latency, report that limitation and keep the issue open. Do not silently substitute a different
search or lateness contract. The selected lowering and its dependencies become fixed inputs to M3.

### M3. Add reusable Structure streaming extensions


Add the proved typed operation recipes and DSL entrypoints in the PySpark plugin. A bounded ranking operation must
represent input/output schema, grouping and scope keys, event time, completion rule, total ordering, K, and duplicate
handling. Its state metadata must distinguish retained candidates from validation/aggregation state, expose retention,
state-schema version, output mode, and supported successor stages. Parameters affecting state semantics participate
in compiler/artifact fingerprints and the caller's restart compatibility declaration.

Extend classification to admit only the proved dependency shapes, including completion propagation across stages.
Do not globally allow `row_number`, relation assertions, arbitrary state, or all multiple-stateful-operation chains.
Preserve current rejection tests and add a separate non-Search conformance transform to demonstrate reusable benefit.
Unsupported profiles fail before query start with a plain-language explanation, remedy, and troubleshooting link.

Implement equivalent online and generated lowering. Generated transforms return DataFrames and never read inputs,
write results, choose checkpoint paths, start queries, or create snapshots. A proved stateful transformation may let
Spark manage its state using the caller's query checkpoint; Structure must not add its own state-storage service.
Keep plugin-specific execution out of Core and preserve compatibility for plugins without these extensions.

If the prototype proves that fixed transformation preparation must be public, use a session-bound explicit binding
of caller-owned immutable inputs; changing a binding creates a new handle/run rather than mutating active state.
Specify this interface at the M2 gate, separately from `.compile()`. It must not persist/read/write snapshots, must
reject session mismatch/closed-handle use, and must not unpersist caller-owned frames. No generic preparation API is
added merely to wrap native streaming graph construction that already occurs once.

Acceptance: compiler, schema, fingerprint, serialization, explain, negative-profile, generated-source, and
online/generated parity tests pass for the narrow operations and their composition. Preserve existing streaming and
batch behavior, and update the streaming support ledgers only for positively proved shapes.

### M4. Integrate the existing SearchDocuments


Refactor internal stages without adding a parallel public Search class. Preserve the `streaming=False` batch default,
current declared outputs, aliases, stage visibility rules, rankings, and schema. Bind fixed snapshots outside the
request flow; split cache/online branches so every streaming union has compatible exact schemas. Keep every remaining
stream/stream join explicitly time-bounded and scoped. Do not mislabel a fixed relation as streaming to satisfy a gate.

Replace ranking in FilterOverlap, lexical/vector fusion, fused candidate selection, normalization, and reranking with
the M2-proved sequence. Preserve current limits and null/tie ordering, including the policy-supplied vector/fusion
bound. Preserve reciprocal-rank fusion and query-dependent feedback; precompute only feedback independent of request
text and scope. Preserve freshness and authoritative-cache semantics in gap selection and vectorization.

Move snapshot-only validation to explicit preparation where equivalence is proved. Preserve all request-specific
required-match, uniqueness, timestamp, scope, and policy failures before final publication. Keep sentence-splitting
and other required UDFs; a speedup obtained by dropping them is not valid. Preserve rejection of invalid authored
code even when a branch can be pruned. Do not disable stage access or intermediate validation solely to pass timing.

Retain `FuseDocuments(materialize=~streaming)` and existing reliable batch checkpoints. The new streaming path uses
proved bounded state, not those checkpoints, cache substitutions, or compiler temporary views. Compile actual
streaming inputs with strict admission and prove the graph compatible before exposing a ready-to-start example.

Add a caller-owned recipe in `examples/search` that supplies immutable snapshot identities, reads requests, obtains
the transformed DataFrame, and owns the sink, completion observation, checkpoint, trigger, and recovery. This recipe
is application code outside generated transforms. Snapshot/policy changes require a new effective run; no automatic
cross-revision mixing. Document lazy-result/handle lifetime and cleanup without taking over caller storage.

Acceptance: `tests/integration/pyspark/search/test_search_streaming.py` proves complete results and failure behavior
against the unchanged batch oracle, including lexical-only, vector fusion, personalization, fallback, and text UDF
cases. Re-run the full existing Search module to detect batch and downstream component regressions.

### M5. Prove latency and publish the outcome


Extend the M1 runner with handwritten native streaming and Structure streaming online/generated variants. Construct
the streaming graph once per cohort, then feed the same cold-plus-20-new-request sequence. Include an idle-last-query
case and measure sequential requests before a separate concurrent-throughput experiment. A `foreachBatch` comparison
may explain batching effects, but is not a substitute for native graph reuse. Available-now is for finite backlog and
restart tests; use a long-running query for the main latency experiment.

Record preparation, compilation, graph construction, batch checkpoint time, request submission, queue/wait time,
processing, caller-observed final delivery, cleanup, total duration, state size, and heap/errors. Compiler/checkpoint
times are nested in their enclosing phases, not added twice. Use a monotonic clock at the caller for end-to-end time;
cross-machine timestamps must not be subtracted without a clock-synchronization contract. Include source/sink/polling
cost and report it separately where observable. Missing final answers are failures, not excluded samples.

Run three cohorts on ordinary Spark 3.5 and 4.0. Keep the settled code, corpus, queries, validation, stage visibility,
artifact reuse, heap, partitions, and adaptive/broadcast settings identical across variants. Use timing-only profiling;
collect expensive explain/state diagnostics in separate untimed runs. First preserve integration settings; test tuned
settings as a separate uniformly applied experiment. Never run competing Docker benchmarks or builds concurrently.

Report warm median, p95, range, failures, cold/setup cost, and amortized break-even request count. Record raw
per-request values and settings in `docs/dev/issues/I09282601/SearchRepeatQueries.bench.md` and adjacent JSON/logs.
Use warm median below 0.5 seconds and p95 below 1 second as explicit exploratory goals for the small fixture, not a
universal service-level guarantee. At minimum, issue closure requires repeatable improvement over batch on both
required ordinary profiles without semantic compromise; report clearly whether the subsecond goal was achieved.

Run batch controls on Connect 4.0. Attempt streaming execution only when the selected operations are capability-
supported, and separately prove replay/restart there before adding any support claim. A rejected or skipped Connect
lane is missing support/evidence, never a pass. Do not generalize ordinary-profile results to Connect.

## Interfaces and Dependencies


The retained public entrypoint is SearchDocuments with its existing streaming selection and supplied DataFrames.
New reusable bounded-ranking/completion interfaces belong to the PySpark transformation DSL; backend-neutral report
fields belong to the existing plugin/Core contract. M2 must freeze exact signatures and version adapters before M3
implementation, because supported execution cannot be inferred from metadata. Operation identity, parameters,
schemas, completion rules, and state versions must survive artifact round trips and generated execution.

No new public Search variant, final-result cache, global prepared-data cache, storage provider, source connector,
sink runtime, or generic arbitrary-state service is in scope. Any required optional execution dependency must be
profile-gated, documented, and proved on the pinned ordinary backends. Existing required UDFs remain supported.
