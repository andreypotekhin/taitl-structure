# Implement row-based `transformWithState` for PySpark 4.1

This ExecPlan is a living document maintained according to `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as work proceeds. This document is self-contained: it records the intended behavior, repository entry points, public interface, implementation sequence, and evidence required for a support claim.

## Purpose / Big Picture

After this work, a Structure user can put keyed, row-based stateful processing inside a typed transform on ordinary PySpark 4.1 and obtain the same semantics from online and generated execution. The normal path uses a typed Structure processor declaration; users who need the broader native Spark processor interface can pass an explicitly opaque PySpark processor. In both cases the caller still creates and manages the streaming query and its checkpoint. PySpark 4.0 support belongs to the separate `transformWithStateInPandas` plan at `docs/dev/planning/P10042604.V11-transform-with-state-in-pandas.plan.md`.

The visible proof is a transform that accumulates state per key, emits rows, registers and handles a timer, survives a restart from the same checkpoint, and produces equivalent results online and from generated code. The native processor path additionally proves that a top-level importable PySpark processor class is available in generated execution and can use native state features, including initial state where the target profile supports it.

The row-based support claim is ordinary PySpark `>=4.1,<4.2`. The row API is not present in PySpark 4.0's Python interface; the separate Pandas plan provides 4.0 support through `transformWithStateInPandas`. This operation does not silently switch callback shapes by target. Spark Connect and `applyInPandasWithState` remain outside this feature's support claim. The feature does not start or manage a streaming query, sink, trigger, checkpoint, retry loop, or deployment.

## Surprises & Discoveries

- Observation: Spark introduced TransformWithState in 4.0, but PySpark 4.0's Python entry point is the Pandas interface; PySpark 4.1 adds the row interface.
  Evidence: The 4.0 Python guide names `transformWithStateInPandas`; the 4.1 guide distinguishes the `python_Pandas` and `python_Row` processor interfaces. The separate Pandas plan owns the former; this plan implements the latter.
- Observation: The repository currently treats arbitrary state, including `transformWithState`, as design-gated and has only a metadata completeness helper for caller-owned state declarations.
  Evidence: `examples/streams/adoption.py`, `docs/api/Streaming.api.md`, `docs/dev/gated/Streaming.gates.md`, and `src/structure/plugin/pyspark/resources/pyspark-streaming-api-coverage.json`.
- Observation: The PySpark plugin captures typed operations into a shared recipe used by online execution and generated rendering; Core carries plugin operation payloads opaquely.
  Evidence: `src/structure/plugin/pyspark/symbolic_execution/commands/CapturePySparkStep.py`, `src/structure/plugin/pyspark/compiler/commands/LowerPySparkPlan.py`, and the PySpark execution and render subpackages.
- Observation: The repository has a PySpark 4.0 integration lane. The V11 plan calls for adding 4.1 ordinary and Connect lanes; this feature requires ordinary 4.1 evidence but does not claim Connect.
  Evidence: the checked-in backend matrix and compose configuration contain no 4.1 service; PySpark is not installed in the project Poetry environment. The V11 adoption plan owns adding the 4.1 lane.

## Decision Log

- Decision: Support the row-based Python API on ordinary PySpark 4.1 only; keep the PySpark 4.0 Pandas interface in its separate plan.
  Rationale: The methods pass different callback containers. Routing the row contract through an implicit conversion would blur the public API distinction and duplicate the separate Pandas plan.
  Date/Author: 2026-10-04 / User and Codex.
- Decision: Provide two explicit processor modes: typed Structure callbacks and an opaque native PySpark processor.
  Rationale: Typed callbacks give Structure a stable schema and operation boundary while allowing normal Python control flow. The explicit native mode gives users access to Spark processor features that the typed callback contract does not model.
  Date/Author: 2026-10-04 / User and Codex.
- Decision: Declare schemas for Structure-authored processors through class type hints; require schema bindings at the operation call for native processors.
  Rationale: One source of truth avoids conflicting duplicated declarations. Native Spark classes do not expose a reliable generic Structure schema contract, so their boundary must be declared where the processor is bound to a relation.
  Date/Author: 2026-10-04 / User and Codex.
- Decision: Treat processor method bodies as ordinary Python executed by Spark workers, not as statements translated by the relational compiler.
  Rationale: Users need normal Python loops, conditionals, and helper calls. Structure can validate the typed boundary and preserve the processor as an explicit Python execution boundary without pretending to optimize its body.
  Date/Author: 2026-10-04 / User and Codex.
- Decision: The typed path supports one `ValueState` and timer registration/handling. The opaque native path may use the full `transformWithState` features exposed by each supported profile, including multiple state variables and initial state.
  Rationale: This keeps the Structure-managed state model small while allowing users who need broader state facilities to opt into an explicitly opaque contract.
  Date/Author: 2026-10-04 / User and Codex.
- Decision: Do not claim Spark Connect support in this plan.
  Rationale: This plan targets the ordinary PySpark 4.1 row API. Connect support requires separate API and restart evidence.
  Date/Author: 2026-10-04 / User and Codex.
- Decision: Preserve the common processor metadata and recipe boundary for the separate Pandas plan, while retaining distinct public operations and runtime calls.
  Rationale: The plans share schema bindings, processor modes, state placement, output/time modes, and native opacity. An explicit interface discriminator can be added by the Pandas plan without changing row callback behavior.
  Date/Author: 2026-10-04 / User and Codex.

## Context and Orientation

Structure is a schema-first Python compiler. A user declares input and output `Schema` classes and writes step methods using a plugin DSL. The Core compiler discovers step methods and asks the selected plugin to symbolically capture their bodies. The PySpark plugin lowers captured operations into a target recipe. Online execution interprets that recipe; generated execution renders the same recipe as Python source. Both paths must use the same state operation contract.

The public transform and step declarations live under `src/structure/core/dsl/model/transforms/`. Core discovery, step authoring, and operation capture run through `src/structure/core/compiler/frontend/commands/CompileTransform.py`, `src/structure/plugin/api/v1/model/StepAuthoringRequest.py`, and the PySpark symbolic execution code under `src/structure/plugin/pyspark/symbolic_execution/`. The PySpark operation model and compiler recipes live under `src/structure/plugin/pyspark/dsl/operations/` and `src/structure/plugin/pyspark/compiler/model/`. Online execution lives under `src/structure/plugin/pyspark/execution/`; generated module rendering lives under `src/structure/plugin/pyspark/render/`.

Streaming compatibility is classified from the lowered execution plan by `src/structure/plugin/pyspark/compiler/commands/ClassifyStreamingCompatibility.py`. It currently admits a narrow set of streaming state shapes and reports additional stateful operations with `STREAM-E0801`. A stateful processor must be represented in this plan so diagnostics, explain output, capability checks, online execution, and generated source agree about its position and contract.

PySpark's `transformWithState` groups an input DataFrame by key and calls a user `StatefulProcessor`. The processor initializes its state handles, receives input rows for one key, can emit zero or more output rows, and may receive timer callbacks. The operation returns a streaming DataFrame; the caller still chooses its source, sink, output writer, checkpoint, trigger, and query lifecycle. The row-based Python method is available in PySpark 4.1; PySpark 4.0 uses the separate Pandas callback API covered by `P10042604`. Spark Connect is a separate variant and is not covered by this plan.

The present gate is described in `docs/dev/design/V11RetainedV9DesignGates.design.md`, `docs/dev/specifications/V11RetainedV9DesignGates.spec.md`, `docs/dev/design/V11PySpark41PythonAndStreaming.design.md`, `docs/dev/specifications/V11PySpark41Parity.spec.md`, `docs/dev/gated/Streaming.gates.md`, and `docs/api/Streaming.api.md`. Update those surfaces and the machine-readable streaming coverage resource as part of implementation. The existing `ArbitraryStateContract` in `examples/streams/adoption.py` remains a caller-owned metadata helper unless implementation proves it should be narrowed or retired; do not silently present it as a runtime.

## Scope and Non-Goals

The feature adds a stable `transform_with_state` Structure operation to compiler-visible PySpark transforms. Its typed mode declares processor schemas with class annotations, exposes one typed `ValueState`, and supports processing input rows plus timers. On PySpark 4.1 it uses row-based `GroupedData.transformWithState`. Its native mode accepts a PySpark `StatefulProcessor` class and explicit Structure schema bindings, passes the native processor to Spark unchanged, and marks its body opaque. Both processor classes must be top-level importable Python classes so generated modules can reference them consistently.

The operation accepts call-site `output_mode` and `time_mode` settings. The native mode accepts the optional initial-state relation when available in the selected Spark profile. The row adapter targets PySpark `>=4.1,<4.2`; Spark imports remain late-bound, so compilation is Spark-free. The separate Pandas plan owns the PySpark 4.0 API and its runtime dependencies.

Do not add `transformWithStateInPandas`, `applyInPandasWithState`, Spark Connect support, a query/source/sink API, checkpoint management, automatic retries, automatic state-schema migration, or support for chaining multiple stateful operations. PySpark 4.0's Pandas operator has its own public operation and ExecPlan. Preserve the existing rule that the admitted state operation may be followed only by stateless operations. No extra third-party dependency may be required for importing Structure or compiling a transform.

### Milestone 2: Specify the typed processor and operation boundary

Define a PySpark-plugin public `StateProcessor[InputSchema, KeySchema, StateSchema, OutputSchema]` protocol and `@state_processor` marker. The protocol's type parameters declare the four Structure `Schema` classes; annotated processor methods are the schema source of truth. Its required `on_rows(key, rows, state, timers)` callback receives a typed input-row iterator and yields typed output rows. Its optional `on_timer(key, timer, state, timers)` callback handles expiration. `ValueState[StateSchema]` provides typed existence, read, update, and clear operations; `TimerContext` provides timer registration, deletion, and listing. Callback code is ordinary Python; it is serialized and run by Spark workers and remains opaque to expression optimization.

Define `transform_with_state(key=..., processor=..., output_mode=..., time_mode=..., event_time_column=None)` as an explicit operation recorded in the active symbolic context. `key` refers to fields available from the step's current streaming relation and must match the declared key Schema. The call requires `output_mode` and `time_mode`, and may specify the output event-time column when the target API supports it. Validate processor annotations, Schema types, output Schema, mode values, and target capability before lowering. Do not repeat typed-processor Schemas in the call.

Define a separate explicit native binding such as `external_state_processor(NativeProcessor, input=..., key=..., states=..., output=...)`. The `states` binding is an informational tuple of Structure Schema classes for traceability; state variable names, native state kinds, timers, time-to-live, initialization logic, side effects, and recovery compatibility remain opaque and caller-owned. Both typed and native processor classes must be top-level importable; generated code uses their qualified module paths, and callers deploy the modules and dependencies to workers.

Add a normative V11 specification and design update before promoting the capability. Define stable diagnostics for unsupported profile/variant, invalid schemas or grouping keys, invalid modes, unimportable native processors, incompatible state-stage composition, and worker/runtime failures that occur after query start. Keep errors actionable and link them to the user streaming reference.

## Validation and Acceptance

The row feature is ready for support only when typed callbacks accept their annotated input, key, state, and output Schemas, update one value state per key, and return a streaming DataFrame with the declared output Schema on ordinary PySpark 4.1. Timer registration and timer callbacks must produce expected rows for supported `time_mode` values. The row operation must fail compilation for PySpark 4.0 with an actionable target diagnostic.

Typed and opaque native processor classes must execute through online and generated transforms. Generated code must import the top-level class through its qualified module path and preserve the declared output shape. Native initial state must pass through the target API and produce matching results online and in generated execution. Restarting from the same caller-owned checkpoint must continue state according to Spark's documented semantics.

The compiler must reject missing or mismatched schema declarations, unavailable profiles, unimportable processor classes, and disallowed stateful combinations before query execution. Generated source must contain the intended `transformWithState` call and processor adapter/import, while avoiding source or sink creation, writer chains, query start/stop, checkpoint configuration, local collection, and hidden UDF fallback. Spark-free compilation and the complete `make build` must pass without importing PySpark.

Keep output mode and time mode visible in plans and diagnostics. Do not claim deterministic ordering among rows delivered for the same key unless proven by the selected Spark API. Do not claim automatic recovery for application side effects or automatic state-schema migration. Spark Connect remains unclaimed until its own API compatibility and restart evidence pass.

## Idempotence and Recovery

Compiler and generation steps must be deterministic and safe to rerun. Live tests must create fresh source/checkpoint directories per test, stop all queries in `finally` blocks, and remove only their own temporary data. The same-checkpoint restart test intentionally reuses one checkpoint within that test to prove Spark state recovery. Do not write to user or shared checkpoints.

The caller owns checkpoint identity and lifecycle. A processor code or state schema change may be incompatible with an existing checkpoint; Structure must not delete, rewrite, or migrate it. Document the Spark/runtime diagnostic and require users to choose an explicit checkpoint migration or a new checkpoint. If a test fails after query start, stop the query and preserve logs before retrying with a fresh temporary checkpoint.

## Artifacts and Notes

The typed authoring shape is:

    @state_processor
    class AccountTotal(StateProcessor[Event, AccountKey, TotalState, TotalOutput]):
        def on_rows(self, key: AccountKey, rows: Iterator[Event], state: ValueState[TotalState], timers: TimerContext) -> Iterator[TotalOutput]:
            ...

        def on_timer(self, key: AccountKey, timer: Timer, state: ValueState[TotalState], timers: TimerContext) -> Iterator[TotalOutput]:
            ...

    @transform(streaming=True)
    class Totals(Transform):
        events = input(Event, streaming=True)
        totals = output(TotalOutput)

        @step(input=events, output=totals)
        def calculate(event: Event) -> TotalOutput:
            return transform_with_state(
                key=event.account_id,
                processor=AccountTotal,
                output_mode="Update",
                time_mode="ProcessingTime",
            )

The native binding shape is:

    return transform_with_state(
        key=event.account_id,
        processor=external_state_processor(
            CustomSparkProcessor,
            input=Event,
            key=AccountKey,
            states=(TotalState,),
            output=TotalOutput,
        ),
        output_mode="Update",
        time_mode="ProcessingTime",
        initial_state=initial_totals,
        event_time_column="event_time",
    )

These examples describe the intended interface; the symbols are new PySpark-plugin API names. Keep the two schema-declaration rules above unchanged.
