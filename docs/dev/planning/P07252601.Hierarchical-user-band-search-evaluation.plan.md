# Add Hierarchical User-Band Search Relevance and Evaluation

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections as implementation proceeds. It follows `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

The Search example currently learns one global feedback signal and evaluates either all queries, query-label slices, or active experiments. After this work, it will also understand caller-owned user profiles and demographic cohorts. A logged-in search request will map its single user to a reusable band, receive relevance feedback appropriate to that band, and fall back through less-specific bands when the most-specific band has too little evidence. A caller will be able to evaluate relevance and served behavior for labels, user bands, their combined slice, and active experiments over that combined slice.

The observable outcome is that two users with the same matching bands reuse one `(query_id, band_id, experiment_id)` ranking, while users with a sparse context transparently receive the closest sufficiently evidenced fallback. Per-query judged-quality output identifies the reusable context, not an individual request. The existing global behavior remains available for anonymous or unmapped users.

  Evidence: `examples/search/transforms/evaluation/with_labels/` and `examples/search/transforms/experiments/` contain both judged-quality and behavior subclasses, while their schemas and public exports are registered in the Search integration test.

- Observation: Current experiment evaluators subclass the ordinary evaluator directly, and no `with_all` composition package exists.
  Evidence: `examples/search/transforms/experiments/evaluation/search_docs/*` imports the transforms from `evaluation/search_docs/`; the only slice package is `evaluation/with_labels/`.

- Observation: A request cannot truthfully carry one `cohort_id` because one user can match several overlapping bands.
  Evidence: The requested hierarchy allows independent dimensions such as locale, country, gender, and geo tag; a single request must nevertheless produce one result list.

## Decision Log

- Decision: Keep `SearchRequest` single-user through nullable `user_id`; derive bands from the persisted user profile instead of storing one band ID on the request.
  Rationale: A user may match several bands, while a request is one serving event. Persisting one selected band would either discard valid dimensions or require caller-side arbitrary selection.
  Date/Author: 2026-07-25 / user and Codex.

- Decision: Name the contracts `Cohort`, `CohortMembership`, `UserBand`, `Band`, and `BandFallback`, and use `band_id` for the reusable band key.
  Rationale: `cohort_id` is ambiguous. `Cohort` and `cohort_id` mean one persisted cohort; `UserBand` maps a user to the reusable `Band` used to rank that profile.
  Date/Author: 2026-07-25 / user and Codex.

- Decision: Represent one user band with one optional half-open age interval and optional lists for the other demographic dimensions.
  Rationale: The caller supplies a set of `Cohort` rows. Multiple age ranges are separate bands, so no age-only nested band type is needed.
  Date/Author: 2026-07-25 / user and Codex.

- Decision: Compute an exact context plus a linear fallback chain that weakens the least-important band first; do not blend scores from unrelated bands.
  Rationale: A caller-defined band priority gives a deterministic sequence such as locale, country, gender, then geo tag. This preserves one context-specific result list and avoids both a powerset explosion and opaque score blending.
  Date/Author: 2026-07-25 / user and Codex.

- Decision: Use a narrow raw Spark hook only to resolve recursive parent links and materialize deterministic context/fallback relations.
  Rationale: the current typed DSL has no recursive relation operator. Metric, feedback, ranking, and evaluation logic remain ordinary typed steps. The hook is a tracked capability gap to remove when recursive relations are supported.
  Date/Author: 2026-07-25 / user and Codex.

- Decision: Keep the ordinary evaluator as the unsliced base. `with_all` combines the label and user slices; experiment evaluators inherit from `with_all`.
  Rationale: This preserves the current unsliced public API, gives combined filters one explicit home, and ensures experiments cannot bypass the agreed label-and-user population selection.
  Date/Author: 2026-07-25 / user and Codex.

## Context and Orientation

The Search example is under `examples/search/`. Schemas declare DataFrame row shapes and transforms declare typed PySpark-compatible relations. `BuildRelevanceSignals` reads persisted daily impression and click aggregates, produces query-document and document-popularity feedback, and `SearchDocuments` uses that feedback to rerank lexical candidates. `SearchRequest`, `Impression`, and `Click` represent serving events; `EvaluateDocumentRankingQuality` measures caller-supplied relevance judgments, while `EvaluateDocumentSearchBehavior` measures the request/impression/click funnel.

The dirty worktree already adds query-label contracts (`Label`, `QueryLabel`, and `EvaluationParams`), `MergeQueryLabels`, label-sliced evaluators, experiment metadata and score selection, and experiment-aware evaluators. This plan incorporates those changes. Do not discard, reset, or hand-copy generated output. Reconcile the in-tree sources, register their final modules, and regenerate through the existing test path.

A `Cohort` is a small caller-persisted configuration catalog of cohort predicates. `country` and `geo_tag` are distinct opaque strings: country is typically a broader and more important relevance dimension, while geo tags can represent arbitrary caller-defined regions or markets. A `CohortMembership` relates one user to one most-specific matching cohort. A `Band` is a canonical, priority-ordered set of those cohort IDs; identical sets have identical `band_id` values, so results and signals are reusable across users. A null `band_id` represents existing global feedback.

## Interfaces and Dependencies

Add a public user-band schema module and re-export the public types from the Search schema surface:

- `User`: required `id`; nullable `age`, `gender`, `locale`, `country`, `geo_tag`, `device_type`, and `time_zone`.
- `Cohort`: required `id` and `priority`; nullable `name`, `parent_cohort_id`, `age_start`, and `age_end`; non-null, possibly empty lists named `genders`, `locales`, `countries`, `geo_tags`, `device_types`, and `time_zones`.
- `age_start` is inclusive and `age_end` is exclusive. Empty constraints impose no restriction. A missing user value fails a constrained dimension. All constrained dimensions are ANDed; values within one list are ORed. `country` and `geo_tag` are opaque caller-owned strings.

Add compiler-visible internal schemas for `CohortMembership`, `UserBand`, `Band`, and `BandFallback`. `Band` contains `band_id` and the ordered cohort IDs; `UserBand` maps one user to that key. A fallback row identifies one band, one candidate fallback band (nullable for global), and its ordinal. Keep these types internal to the Search example unless an external caller needs to persist them.

Extend `SearchRequest`, `Impression`, and `Click` with nullable `user_id`. Logged-in callers must populate all applicable event rows; the transforms use the request identity to select a context and the impression identity for feedback attribution. Preserve nullable `user_id` in `DailyImpressions` and `DailyClicks`, including it in their aggregation keys.

Extend `QueryDocumentSignals` and `DocumentPopularity` with nullable `band_id`, and `RelevancePolicy` with required `minimum_band_impressions`. Extend document candidates, document results, and judged-evaluation intermediate/final query facts with nullable `band_id`. Partition ranking identity in this exact order: `(query_id, band_id, experiment_id)`.

Extend `EvaluationParams` with nullable `user_band: struct(Cohort)`. Label-only transforms retain this field unchanged. `with_users` and `with_all` require it to be non-null and select its authoritative persisted `Cohort` row by ID.

## Plan of Work

### 1. Establish user bands and canonical contexts

Create the user/band schemas and exports, then implement a focused band resolver. It receives persisted `User` and `Cohort` rows and returns the memberships, deduplicated shared bands, and fallback rows needed downstream. A user matches every applicable cohort predicate, but only cohorts with no matching child in the same parent chain become direct memberships. This prevents a band from redundantly containing both a specific cohort and its ancestor.

Sort direct memberships by descending `Cohort.priority`, then stable cohort ID. Construct `band_id` deterministically from that ordered sequence using an unambiguous serialization or hash plus collision-safe equality checks. A user with no membership has the null/global band.

For a non-global band, construct one ordered fallback chain. Repeatedly replace the lowest-priority remaining cohort with its parent, or remove it when the parent is null; normalize duplicate IDs, preserve the remaining order, and continue until global. This means a band like locale/country/gender/geo tag weakens geo tag before gender, country, and locale. Detect missing parents and cycles before traversal and fail with an error that names the invalid cohort IDs and directs callers to the cohort hierarchy contract.

Keep recursion and context-row expansion inside the approved raw Spark hook only. Give the resolver transform and hook-adjacent methods docstrings explaining why the hook exists, its input/output grain, hierarchy validation, and its planned retirement. Do not move ordinary matching, aggregations, fallback eligibility, or ranking calculations into raw code.

### 2. Produce global and context feedback

Add `user_id` to the event and daily-fact contracts, update `Impressions` and `Clicks` grouping keys, and update their documentation and fixtures. Add users, bands, memberships, contexts, and fallback relations as inputs or derived lanes of `BuildRelevanceSignals`.

Emit the existing global feedback rows with `band_id = null`. For each logged-in event, also emit one contribution for the exact context and every fallback context. Aggregate and normalize query-document and document-popularity signals independently for every context key. Global rows must not be affected by duplicate memberships or fallback expansion.

Use `minimum_band_impressions` only to decide whether a non-global context has sufficient evidence for a feedback lookup. Retain `minimum_ctr_impressions` solely for CTR normalization. Add docstrings to every relevance transform and step that state whether its rows are global, context-scoped, or fallback-expanded.

### 3. Rerank one user request through its reusable context

Make `SearchDocuments` accept `SearchRequest` and the context mapping in addition to reusable `SearchQuery` definitions and lexical scores. Resolve each request to its user’s exact context, join the request to candidates through its query ID, and deduplicate requested work by `(query_id, band_id, experiment_id)`.

For every candidate, walk the ordered fallback relation in typed joins and select the first query-document signal with an impression count at least `minimum_band_impressions`; use global when no non-global row qualifies. Apply the same independent lookup to document-popularity feedback. Do not blend signals from siblings or unrelated contexts. Preserve the existing lexical candidate limit, score normalization, and deterministic rank tie-breakers, but partition every rank/window operation by `(search_query_id, band_id, experiment_id)`.

Expose `band_id` in `DocumentSearchCandidate` and `DocumentSearchResult`. It is null only for the global path. Add transform and step docstrings explaining that this is a reusable user-profile context, not a request ID or one user-band ID.

### 4. Normalize label, user, combined, and experiment evaluation

Keep `evaluation/search_docs/` as the unsliced base. Retain the already-present `with_labels` package, but correct and test its selection predicate: different label names are ANDed, repeated requested values for one name are alternatives, and an empty label list selects all queries. `MergeQueryLabels` remains the source that materializes latest timestamped labels onto `SearchQuery`.

Add `evaluation/with_users/` judged-quality and behavior subclasses. They join request/user/membership data to select all bands containing the requested persisted cohort, including descendant leaf cohorts. User-aware judged quality joins only result rows with the selected query and band ID; it publishes per-query-band facts and aggregates daily summaries across bands for the requested cohort. Behavior evaluation selects matching requests before the inherited impression/click funnel, preserving zero-result requests.

Add `evaluation/with_all/` as the explicit composition of the existing label and user selectors. It requires both label criteria and a non-null user band. If multiple inheritance cannot safely combine the two overridden selection steps, implement one focused combined selection class that invokes the same base lanes and applies both predicates in one typed step; do not duplicate the downstream metric or behavior funnels.

Rebase only `experiments/evaluation/search_docs/judged_quality` and `experiments/evaluation/search_docs/behavior` on the `with_all` transforms. Preserve `Experiment` filtering and `SelectExperimentScores`: production score rows have a null experiment ID, named rows require an active matching `Experiment`, and experiment evaluators select only active named experiments. Their query/result/request selection must also apply the label and user-band filters and retain `EvaluationParams` in outputs.

Document every transform class and non-obvious selection step with concise Python docstrings. The docstrings must name the selected population, state whether the transform is unsliced, label-sliced, user-band-sliced, combined, or experiment-aware, and identify the output grain. This is required because inheritance and context fallback make the behavior non-obvious to a code reader.

### 5. Publish, generate, and verify

Update `examples/search/transforms/evaluate.py` to export the unsliced, label, user, combined, and experiment evaluator entry points with names that distinguish their population. Preserve existing ordinary and already-introduced label/experiment public aliases where feasible; document any new required inputs for experiment evaluation.

Update `examples/search/Readme.md` and `docs/dev/design/Search.design.md` (and the Search evaluation decision if its contract changes) with the profile ownership boundary, opaque country/geo-tag values, hierarchy integrity requirements, membership/context construction, priority-tail fallback, minimum evidence rule, all evaluation slices, and the raw-hook limitation. Explain that user-band behavior remains observed satisfaction, not relevance truth.

Register every new source schema and transform in `tests/integration/pyspark/search/test_search.py` and `tests/helpers/example_projects.py`. Regenerate `examples/structure_generated/search/` through the existing rendering and golden-test workflow; do not edit generated artifacts manually.

## Validation and Acceptance

The feature is accepted when all of the following are observable in both online and generated PySpark execution:

- A logged-in user maps to all matching leaf bands, then to one deterministic reusable `Band`; an anonymous or unmatched user uses the null/global context.
- Two users with the same ordered matching-band IDs produce and reuse the same context-specific result rows.
- Context fallback weakens the lowest-priority band first, handles parent generalization, stops at global, and rejects missing-parent or cyclic hierarchies with actionable errors.
- A sufficiently evidenced exact or fallback context is preferred; sparse context feedback falls through to the first qualifying ancestor, then global, without sibling blending.
- Global relevance signals retain their existing values when bands are added; context expansion does not duplicate global event contribution.
- Label evaluation implements AND-across-label-names and OR-within-values; user evaluation selects membership-matching contexts; `with_all` applies both; experiment evaluation applies all three constraints plus active experiment selection.
- Per-query judged-quality rows use `band_id`, never a request ID; behavior rows retain request IDs because they describe served events.
- Public transform and significant step docstrings make the population, inheritance/composition role, context semantics, and output grain understandable without reading parent classes.
- Generated Search documentation, traceability, source, tests, and `make build` are current and pass.

## Idempotence and Recovery

Band contexts and fallback rows are deterministic for identical user and band inputs. Re-running the resolver or feedback build replaces the same context-keyed results. If hierarchy validation fails, correct the caller-owned `Cohort` data and rerun; do not silently truncate a cycle or invent a missing parent. If generated output differs, change source registrations or renderer inputs and regenerate rather than editing `examples/structure_generated/search/` manually. If multi-inheritance cannot compose the two selector steps safely, use the explicit `with_all` selector described above and keep metric logic inherited from the unsliced base.

## Artifacts and Notes

The expected concept flow is:

    User + Cohort hierarchy
      -> CohortMembership (most-specific matching bands)
      -> Band (ordered reusable band set)
      -> ordered fallback contexts
      -> context-scoped relevance signals
      -> SearchRequest context lookup
      -> one ranked result list per query/context/experiment
      -> label, user, combined, and experiment evaluation slices

For a user whose direct memberships are ordered as `locale=en`, `country=us`, `gender=male`, and `geo_tag=bay-area`, a fallback chain first weakens the geo-tag branch, then gender, country, and locale according to each band’s parent link. The exact parent sequence is caller-owned; the resolver’s responsibility is to follow it deterministically and detect invalid links.

## Interfaces and Dependencies

This work adds public Search example contracts for `User` and `Cohort`, and extends existing event, feedback, result, policy, and evaluation schemas as listed above. It adds internal context contracts and a localized raw Spark resolver because the current Structure DSL has no recursive hierarchy operation. It depends only on the existing Structure/PySpark stack and current Search registries; no new third-party dependency is required.
