# Add field-aware boolean and phrase search

This ExecPlan is a living document. It follows `docs/dev/auto/Plans.md`; the `Progress`, `Surprises & Discoveries`,
`Decision Log`, and `Outcomes & Retrospective` sections must be updated as implementation proceeds.

The design authority for this work is `docs/dev/design/FieldSearch.design.md`. Keep that document and this plan aligned
when interfaces or behavior change.

## Purpose / Big Picture

After this change, a caller can search structured document metadata with boolean terms and positional phrases while
retaining the existing full-text content search unchanged. An unqualified query searches document metadata by default;
`content:` explicitly delegates that part of the query to the existing lexical content index. For example,
`title:"release notes" and content:upgrade` will require a title phrase match and rank the surviving documents using
the existing full-text score for `upgrade`.

The change introduces a caller-owned `Document.fields` map as the authoritative source for string metadata and a
separate `FieldIndex` for those fields. It does not create a positional index for full document content, does not add
`content_summary`, and does not change `LexIndex`, BM25, overlap scoring, similarity, or the existing full-text search
contract.

## Surprises & Discoveries

- Observation: `LexIndex` currently receives `Document` and sentence boundaries, materializes only `Document.content`,
  and emits four-grain term statistics. Its transient token expansion has a position, but the public lexical outputs do
  not retain positions.
  Evidence: `examples/search/transforms/indexing/lexical/LexIndex.py` uses `posexplode_struct` and then returns
  `LexicalOccurrence` without the position field.

- Observation: the current `Document` schema mixes caller-owned source metadata with search-result-related fields, while
  `DocumentFeatures` is a derived feature relation.
  Evidence: `examples/search/schemas/text.py` declares title, source, content type, language, and score fields directly
  on `Document`; `examples/search/schemas/features/__init__.py` declares derived normalized fields.

- Observation: a content positional index is unnecessary when `content:` delegates to the current full-text search
  path. Only metadata fields need positional postings for the first boolean/phrase implementation.
  Evidence: existing `LexIndex.document_terms` already supports document-level lexical term lookup and scoring, while
  the requested content clause is explicitly full-text rather than a phrase clause.

- Observation: arbitrary field names require a field-policy default rather than a hardcoded list of every possible
  custom key.
  Evidence: `Document.fields` is a dynamic map, so field extraction must preserve field identity while policy resolution
  supplies a default analyzer for unlisted keys.

- Observation: aggregate expressions cannot be used directly in generated filter predicates.
  Evidence: `SearchFields` materializes aggregate match counts in intermediate schemas and applies equality filters in
  later steps; keeping the filter in the grouping step failed generated rendering with an unsupported aggregate recipe.

- Observation: stop-word removal must preserve original positions for phrase behavior.
  Evidence: the parser keeps the original token ordinal (`release`, `the`, `notes` becomes positions `0` and `2`),
  while `FieldIndex` drops the stop-word posting without renumbering later terms.

- Observation: the moved worktree temporarily contained two identities for the same field schemas and index transform.
  Evidence: the compiler reported `expects DocumentField, but ... provides DocumentField` because the class names matched
  while their Python class identities came from different modules. Keeping one active source module per schema/transform,
  with generated output regenerated from that layout, restored deterministic composition.

## Decision Log

- Decision: retain `LexIndex` and create `FieldIndex`.
  Rationale: `LexIndex` is the stable full-text content index and should not acquire field identity, metadata semantics,
  or positional output. Shared tokenization helpers may be reused, but the public index contracts remain separate.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: make `Document.fields` the source of truth for string metadata while preserving every existing plain
  `Document` field.
  Rationale: callers and presentations continue to receive the established named fields, but
  `ExtractDocumentFields` assigns those values from the authoritative map, which wins when a typed copy is also present.
  The map is the source; named columns are the typed view.
  Date/Author: 2026-08-09 / User and Codex.

- Decision: add `ExtractDocumentFields` as a distinct transform after `Chunking`; it enriches the same `Document` relation
  and emits the flattened field relation without a separate normalized-document relation.
  Rationale: flattening and validating metadata is not document chunking. Keeping the transform separate lets
  `Chunking` remain responsible only for content structure and lets field extraction evolve independently.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: use `metadata` as the default query scope.
  Rationale: unqualified boolean/phrase search should remain cheap and predictable and should not silently search the
  full body.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: reserve `content:` for full-text body search.
  Rationale: this reuses `LexIndex` and existing scoring without creating expensive content-position postings. A query
  such as `title:"release notes" and content:upgrade` is a metadata phrase constraint joined with a full-text content
  clause.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: do not retry metadata search against content when metadata produces no rows.
  Rationale: implicit fallback changes query meaning and makes latency and ranking unpredictable. Content participation is
  explicit in the query.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: omit `content_summary` from this slice.
  Rationale: it is not needed when body content can be explicitly searched through the existing full-text path, and its
  synthesis would introduce a separate content-generation concern.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: make all fields in `Document.fields` positional-searchable by default; route body content outside
  `FieldIndex`.
  Rationale: metadata values are small enough for positional postings, and this makes phrase behavior uniform for
  reserved and arbitrary fields. The field policy can still select exact or text normalization per field.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: separate `FieldProfile` from `AnalyzerPolicy`.
  Rationale: a field definition describes what a field is and whether it is searchable; an analyzer policy describes how
  its text is transformed. `FieldPolicy` conflates those concerns and makes custom fields harder to reason about.
  Date/Author: 2026-08-09 / User and Codex.

- Decision: use field-qualified syntax such as `title:"release notes"`, `source:github`, and `content:upgrade`, with
  lowercase `and` and `or` operators.
  Rationale: explicit qualifiers make the search scope inspectable and let the parser route metadata and body clauses
  to different indexes.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: support mixed metadata/content conjunctions first; reject mixed `or` expressions with an actionable
  diagnostic until their union and score semantics are specified.
  Rationale: conjunction is a direct intersection of document IDs and preserves existing content ranking. Mixed `or`
  requires a new policy for documents that match only metadata, only content, or both.
  Date/Author: 2026-08-08 / User and Codex.

- Decision: expose parsing as a pure-Python `parse_field_search_query` helper that materializes typed query and term
  rows consumed by `SearchFields`.
  Rationale: query text is a caller/request boundary, while the execution transform remains schema-driven and parity
  safe. The helper makes normalization and syntax diagnostics directly testable without embedding an opaque UDF in
  the indexed DataFrame path.
  Date/Author: 2026-08-09 / Codex.

- Decision: require lowercase `and` and `or`, with whitespace between unqualified terms treated as implicit `and`.
  Rationale: this matches the agreed query convention while preserving natural simple-query behavior. Uppercase
  operators are rejected with a remedy rather than silently changing query meaning.
  Date/Author: 2026-08-09 / Codex.

## Context and Orientation

The repository is a schema-driven transformation compiler. Search source schemas live under `examples/search/schemas/`,
transform compositions live under `examples/search/transforms/`, and checked-in generated PySpark output lives under
`examples/structure_generated/search/`. The same transform source must work in online Structure execution and generated
PySpark execution.

The field-search design is documented in `docs/dev/design/FieldSearch.design.md`. It defines the separation between
`FieldProfile`, which describes searchable field behavior, and `AnalyzerPolicy`, which describes text analysis
behavior.

The existing content path is:

    Document.content -> Chunking -> sentences -> LexIndex -> document/section/paragraph/sentence lexical artifacts
                         -> Scoring/SearchDocuments -> full-text results

`LexIndex` builds compact term-frequency and target-statistic relations. It does not expose token positions. Its content
index and the formulas that consume it are already documented in `docs/dev/design/Search.design.md`,
`docs/dev/specifications/Search.spec.md`, and `docs/reference/Search.ref.md`. This plan must preserve those contracts.

The new metadata path is:

    Document -> Chunking + ExtractDocumentFields -> Indexing(fields=FieldIndex) -> metadata boolean/phrase matches

`Document.fields` is a non-null map from string field names to non-null string values. Body `content` is not duplicated
into that map and is not an input to `FieldIndex`. Existing string metadata keys become reserved map keys:
`title`, `url`, `source`, `content_type`, `encoding`, `language`, `document_type`, `category_id`, and
`file_type`. `content_summary` is deliberately not part of this plan. Identity and lifecycle values remain typed
source fields rather than arbitrary string metadata.

`ExtractDocumentFields` flattens the map into one relation row per document field. That relation carries field identity,
value, field kind, and the analyzer-policy reference. `FieldIndex` analyzes those rows and emits positional postings. A
position is the original token ordinal within a field value; preserving positions allows `title:"release notes"` to
mean adjacent analyzed terms rather than two independent matches.

The default analyzer is metadata-oriented. It performs deterministic tokenization, case normalization, punctuation
handling, configured stop-word removal, and position preservation. Field-specific policies may use exact normalized
keyword behavior instead. Caller-supplied spelling, morphology, and synonym rule tables remain versioned policy inputs;
arbitrary opaque NLP UDFs are outside this plan.

## Interfaces and Dependencies

The following interfaces are the required end state. Names may be adjusted only if the replacement remains equally
explicit and the decision log is updated.

`Document` retains every existing plain field, adds authoritative `fields: map(string(), string(),
value_contains_null=False, nullable=False)`, and keeps top-level body `content`. `ExtractDocumentFields` assigns the
preserved named string fields from the map and copies the remaining typed identity/lifecycle values. Downstream
consumers use the enriched `Document` and `DocumentField` outputs; no independent top-level/map source of truth is
permitted.

`DocumentField` is a flattened relation with `document_id`, `field_name`, `field_value`, `field_kind`,
`analyzer_policy`, and a deterministic `ordinal` for the source field row. `field_kind` distinguishes text analysis
from exact/keyword normalization. All field rows are eligible for positions; keyword fields normally produce one
logical token.

`FieldProfile` identifies a reserved field or dynamic-field default and carries `analyzer_policy`, `field_kind`,
`phrase_enabled`, `searchable`, and `default_scope`. The default scope is `metadata`. Body `content` has no
`DocumentField` row and is routed to the existing lexical path. `AnalyzerPolicy` separately identifies the
versioned tokenization, normalization, stop-word, and rewrite behavior referenced by a field definition.

Initial analyzer policy identifiers are stable names such as `metadata_text_v1`, `keyword_lowercase_v1`, and
`keyword_exact_v1`. The identifier and version are persisted with index artifacts. A policy definition may reference
stop-word rows and caller-owned versioned term rewrite rows without embedding those rule sets in every posting.

`FieldTerm` is a positional posting with `document_id`, `field_name`, `term`, `position`, and `analyzer_policy`.
Duplicate terms at different positions remain separate postings. A separate compact field vocabulary or summary relation
may be added if execution needs it, but it must not replace position-bearing postings required for phrase matching.

`FieldSearchQuery` carries query identity, raw query text, queryset, immutable requested time, and language/query
metadata needed by the existing Search contract. Its raw text accepts field-qualified terms and phrases. The parser emits
metadata clauses and at most one full-text `content` clause for the first implementation.

`SearchFields` is the new serving composition. It accepts field search queries, extracted document fields,
`FieldTerm` postings, and optional existing lexical index artifacts. It returns deterministic document results. A
metadata-only result is ordered by stable document identity; a result with a content clause preserves the existing
full-text score and ranks by that score with stable document-ID tie-breaking.

The content clause is converted to the existing `SearchQuery`/scoring pathway. For a mixed `and`, metadata candidates
are intersected with content-scored document IDs. Full-corpus index statistics remain the source of BM25 values even
when candidate IDs are restricted for efficiency. No new content-position index is permitted.

## Plan of Work

### Milestone 1: Add the authoritative field map without dropping named Document fields

Update the Search text source schema and source fixtures so `Document.fields` contains the reserved string keys and any
custom string keys while every existing plain `Document` field remains declared. Keep document identity, body content,
and lifecycle timestamps typed. `ExtractDocumentFields` must populate the preserved named string fields from the map,
copy non-string source values, and let map values win over duplicate typed copies. Update chunking,
presentation, statistics, labeling, and other current consumers to use the extracted outputs.

Add `DocumentField`, `FieldProfile`, and `AnalyzerPolicy` schemas and register them in the Search schema exports
and generated-schema workflow. `ExtractDocumentFields` should flatten `Document.fields`, skip empty field names,
preserve stable field identity, apply the dynamic metadata definition to unlisted custom keys, assign the preserved
named `Document` fields, and let map values win over typed copies. It must not generate `content_summary` or
tokenize body content.

At the end of this milestone, existing chunking and full-text indexing still operate on the same body content, while a
caller can inspect one field row per metadata entry.

### Milestone 2: Implement `FieldIndex`

Add the field indexing package and make its transform a child of `Indexing`. Reuse shared text-normalization helpers
where possible, but keep `LexIndex` unchanged. Tokenize each field value with the selected policy, preserve the original position before
stop-word removal, and emit one `FieldTerm` posting per analyzed occurrence. Use deterministic policy/version identity in
every output artifact.

Support the initial policies as follows. Text policy performs canonical tokenization, case normalization, punctuation
handling, stop-word removal, and positions. Keyword policies normalize the complete value as one logical token. Rule
tables for spelling, morphology, and synonyms are optional and must be applied consistently to field values and query
clauses under the same policy version. Multi-token rule behavior must preserve positions or fail with an actionable
diagnostic; it must never silently collapse phrase boundaries.

All fields from `Document.fields` are phrase-enabled by default. A field policy may disable searching, but body `content`
is excluded by the source boundary rather than represented as a disabled field posting.

Add deterministic field vocabulary/statistics only where needed by boolean lookup, and avoid computing BM25 statistics
for the field lane. Field search is a constraint operation; content scoring remains the ranking operation when a
`content:` clause is present.

### Milestone 3: Parse and execute field-aware queries

Add a parser for the following first-version grammar. A field name is an identifier followed by `:`. A value is one
term or a quoted phrase. Unqualified terms and phrases target the `metadata` default scope. Field-qualified metadata
clauses target the named map key. `content:` is reserved and delegates its value to ordinary full-text search.

Support `and` and `or` for metadata-only expressions. Support mixed metadata/content `and` expressions, including
`title:"release notes" and content:upgrade`. Recognized operators are normalized to lowercase in the parsed query.
Reject mixed `or` with a diagnostic that explains that only conjunction
currently combines metadata constraints with content ranking. Do not treat quotes on a `content:` value as a new phrase
operator; pass the contained text to the existing full-text query semantics.

The executor should first derive metadata document targets from `FieldIndex`, then either return those targets in
deterministic document-ID order or intersect them with existing content scores. A content-only query should delegate to
the existing full-text path without changing its results. A mixed query should retain the content score, query identity,
requested time, and existing freshness/evidence rules.

Unknown or absent dynamic field keys must produce no matching field rows rather than being interpreted as content. Field
names must be treated as literal data keys, not executable expressions. Invalid syntax, malformed quoting, empty field
names, and unsupported mixed operators must produce diagnostics naming the query and remedy.

### Milestone 4: Documentation, generated artifacts, and evidence

Update `docs/dev/design/FieldSearch.design.md` together with the Search specification, design, reference, README,
focused indexing/searching background documents, and user stories. Document that metadata is the default scope, body
search requires `content:`, body content has no positional FieldIndex, and `content_summary` is not part of the feature.

Update public exports, transform registries, generated source, schema snapshots, fixture rows, and annotated source
documents required by the repository. Generated PySpark files must be regenerated through the repository command and
must not be hand-edited.

Keep the existing Search streaming boundary unchanged. This plan adds batch field extraction and batch field-aware
document retrieval; it does not introduce streaming field-index refresh or query serving lifecycle ownership.

## Validation and Acceptance

Acceptance is behavioral. A caller must be able to supply a document with `fields` containing `title`, `source`,
`category_id`, `file_type`, and a custom key, run `ExtractDocumentFields`, and observe one deterministic field row
per value. No duplicate top-level metadata source is accepted.

A metadata query such as `title:"release notes"` must match only documents whose analyzed title contains the phrase at
the preserved positions. Stop-word removal must not make separated terms appear adjacent. A query for an arbitrary
custom key must search that key through the same field index and default analyzer policy.

An unqualified query must search metadata only. A body term absent from all metadata must not match unless the query
uses `content:`. `content:upgrade` must produce the same document score and ordering as the existing full-text query
`upgrade` over the same corpus. `title:"release notes" and content:upgrade` must return only the intersection and must
rank by the existing content score.

The implementation must prove that no content-position artifact is created. Content terms may be reused from
`LexIndex`; metadata postings may carry positions; body phrase matching is explicitly out of scope.

Tests must cover empty fields, missing field keys, duplicate field-map impossibility, custom fields, exact keyword
fields, stop words, preserved phrase gaps, repeated terms, malformed field syntax, unknown/absent fields, metadata-only
queries, content-only delegation, mixed conjunction, rejected mixed `or`, deterministic ties, and content-score
preservation.

Every new transform and schema must have online/generated parity evidence. Generated-output golden tests must verify
the field extraction, analyzer, parser, and mixed-query source shape. `make build` must pass before the plan is marked
complete.

## Idempotence and Recovery

The plan is additive at the transform level and preserves the existing plain `Document` schema fields. Add the
authoritative map and perform its fixture updates as one reviewed change. `ExtractDocumentFields` must assign the
preserved named fields from the map and diagnose disagreement; do not create an independently authoritative shadow map
or column set.

Generated artifacts are reproducible from source. If `make gold` produces unrelated changes, stop and inspect the diff;
do not hand-edit generated output or revert unrelated user work. If a milestone fails, keep the new schemas and focused
tests, correct only the failing transform or contract, and rerun the focused command before continuing.

Analyzer policy changes require a new policy version and regenerated field-index artifacts. Historical artifacts must not
be silently reused under a different analyzer policy.

## Artifacts and Notes

The central observable example should include these query/result cases:

    title:"release notes"
    content:upgrade
    title:"release notes" and content:upgrade
    custom_field:"blue sky"

The expected behavior is that the first and fourth cases use `FieldIndex`, the second uses existing full-text scoring,
and the third intersects the two result sets while retaining the second case's content score.

The initial analyzer-policy examples are:

    metadata_text_v1       deterministic tokenization, normalization, stop words, and positions
    keyword_lowercase_v1   one normalized case-insensitive value token
    keyword_exact_v1       one exact normalized value token

The implementation may add policy rows for language-specific stop-word or rewrite tables, but every such addition must
carry an immutable version and be documented in the decision log.

## Deferred Work

The following are intentionally outside this plan:

- full-content phrase search;
- a positional index for `Document.content`;
- automatic metadata-to-content fallback;
- `content_summary` synthesis;
- mixed `or` expressions that combine metadata and content;
- answer generation or prompt assembly;
- streaming field-index maintenance;
- external NLP services or opaque analyzer UDFs; and
- replacing the existing BM25/full-text scoring formulas.
