This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept current as work proceeds.

This plan follows `docs/dev/auto/Plans.md`. It is the governing implementation plan for V11, whose release charter is `docs/dev/project-management/V11.md`. The paired design and specification documents are `docs/dev/design/V11PySpark41Adoption.design.md`, `docs/dev/specifications/V11PySpark41Parity.spec.md`, the four feature designs linked from the V11 charter, and the Delta integration plan at `docs/dev/planning/P08042602.V11-delta-schema-bound-mutations.plan.md`.

## Purpose / Big Picture

After this work, a Structure user can select a tested PySpark 4.1 target profile, use every admitted 4.1 transformation feature through a typed Structure contract, bind a Structure schema to an optional Delta table for schema-bound mutations, and run the same transform online and as generated PySpark. A maintainer can see exactly which PySpark 4.1 API additions and Delta integration rows are supported, gated, caller-owned, streaming-ineligible, or unsupported; can reproduce the result on ordinary PySpark and the claimed Spark Connect subset; and can run the six-lane integration matrix with one command.

The visible proof is a passing `make build`, a passing `make integration` matrix for PySpark 3.5, 4.0, and 4.1 plus their Connect lanes, and synchronized 4.1 sections in `docs/APICatalog.md` and `docs/reference/API.ref.md`. A feature is not complete because a name appears in a table: its tests must demonstrate output values, output schemas, diagnostics, and generated-source behavior.

## Surprises & Discoveries

- Observation: The current capability resolver supports `>=3.5,<4.1`, its narrower 3.5 and 4.0 ranges, and `>=4.2,<4.3`, but not `>=4.1,<4.2`.
  Evidence: `src/structure/plugin/pyspark/capabilities/model/PySparkCapabilities.py` defines `SUPPORTED_PROFILES` without a 4.1 range and adds Spark 4 capabilities only for the 4.0 range.
- Observation: The current integration matrix is hard-coded to four backends and two Spark image versions.
  Evidence: `scripts/run_integration.py`, `infra/compose/docker-compose.yaml`, `infra/compose/.env_example`, and `tests/integration/pyspark/support/backend_matrix.py` name only 35 and 40 lanes.
- Observation: PySpark 4.1 is broader than Structure's transformation boundary.
  Evidence: Apache Spark 4.1 release notes include Declarative Pipelines, SQL Scripting, Python Data Sources, Arrow UDF/UDTF APIs, and row-based state APIs in addition to query functions. The plan therefore classifies boundary APIs instead of claiming blanket parity.

## Decision Log

- Decision: Use ordinary PySpark 4.1 as the primary target variant and Spark Connect 4.1 as a separately evidenced secondary variant.
  Rationale: ordinary PySpark exercises the full classic DataFrame runtime, while Connect support must be proven per API and generated source must remain free of classic-only access.
  Date/Author: 2026-08-04 / Codex.
- Decision: Add an exact `>=4.1,<4.2` profile before considering promotion of the broad default profile.
  Rationale: exact capability matching prevents a 4.1-only function from being silently accepted for 3.5 or 4.0 and preserves the current default while evidence is incomplete.
  Date/Author: 2026-08-04 / Codex.
- Decision: Treat 4.1 API parity as a reviewed inventory with explicit statuses, not as a promise to wrap every upstream API.
  Rationale: Structure owns typed transformations and deliberately excludes readers, writers, sessions, arbitrary Python callbacks, and streaming lifecycle/state ownership.
  Date/Author: 2026-08-04 / Codex.
- Decision: Preserve the 3.5 and 4.0 ordinary and Connect lanes throughout V11.
  Rationale: 4.1 adoption must detect regressions in the existing target intersection rather than replacing evidence with a newer runtime.
  Date/Author: 2026-08-04 / Codex.
- Decision: Treat the Delta integration as an optional PySpark-plugin package, not as a separate Structure target.
  Rationale: DeltaTable is a PySpark runtime integration, while Structure's ordinary Transform contract remains focused on row-producing transformations.
  Date/Author: 2026-08-04 / Codex.
- Decision: Require an explicit `DeltaTableWrapper.set_schema(schema)` binding before supported Delta mutations.
  Rationale: The schema is the single authored source for field references, expected shape, and native Delta CHECK constraints; automatic installation during mutation would hide a table-metadata change.
  Date/Author: 2026-08-04 / Codex.

## Context and Orientation

Structure is a schema-first Python library. A transform declares typed schemas and compiler-visible operations. The compiler captures those operations in an intermediate representation (IR), a structured description of the computation, and the PySpark plugin can execute the same semantics online or render them as generated PySpark. A capability profile is the exact target version range and variant used to decide whether an operation is legal. The ordinary variant uses classic PySpark DataFrames; the Spark Connect variant uses the remote DataFrame API and must avoid classic-only internals.

The current documented baseline is ordinary and Connect PySpark `>=3.5,<4.1`. The relevant capability resolver is `src/structure/plugin/pyspark/capabilities/model/PySparkCapabilities.py`. Integration support is split between `scripts/run_integration.py`, `infra/compose/docker-compose.yaml`, `infra/compose/.env_example`, `infra/compose/images/pyspark/Dockerfile`, `infra/compose/images/pyspark/run-integration.sh`, and the fixtures under `tests/integration/pyspark`. The API decisions are documented in `docs/APICatalog.md`, `docs/reference/API.ref.md`, and the machine-readable inventories under `src/structure/plugin/pyspark/resources/`.

PySpark 4.1 adds many SQL functions and query APIs, plus Python execution and streaming-state APIs. The upstream release notes identify, among other items, Column transformation, IN-subquery support, lateral query APIs, new functions such as `chr`, `random`, and `uuid`, complex observation values, Arrow UDF/UDTF support, and Python row-based state. This plan admits only APIs whose Structure contract can define types, nullability, cardinality, determinism, streaming behavior, target variant, generated spelling, and diagnostics.

## Plan of Work

### Milestone 1: Admission and upstream inventory

Create a versioned inventory of the PySpark 4.0-to-4.1 Python API delta. Compare the 4.1 SQL/DataFrame/Column/function reference and release notes against the current `pyspark-transformation-inventory.json`, `pyspark-transformation-coverage.json`, and streaming coverage inventory. For each addition, record the upstream symbol, family, whether it is a transformation, whether it supports Spark Connect, Structure status, intended Structure spelling, owner boundary, design/spec link, capability key, diagnostic, test location, and evidence command. Do not mark an API supported during inventory merely because PySpark imports it.

Update `docs/dev/design/V11PySpark41Adoption.design.md`, `docs/dev/specifications/V11PySpark41Parity.spec.md`, and the four feature design files whenever the inventory resolves an ambiguity. Add a decision log entry for every scope change. The milestone is complete when every reviewed 4.1 addition has one status and no row points to an undefined owner or missing contract.

### Milestone 2: Target profile and capability boundary

Add `>=4.1,<4.2` to the capability profile resolver and make 4.1-specific capability keys distinct from common 3.5/4.0 keys. Preserve the existing default profile until release promotion. Ensure unsupported profile/variant diagnostics state the configured range, required range, target variant, and caller remedy. Update capability snapshots and unit tests for ordinary and Connect variants.

Add the target profile to configuration and compatibility documentation wherever the supported range is currently written. Do not widen an existing feature's claim without a passing 4.1 regression test. Keep profile resolution spark-free.

### Milestone 3: Expression parity

Implement only the expression rows approved by `V11PySpark41ExpressionParity.md`. Extend the DSL model, symbolic evaluator, capability mapping, generated renderer, imports, and type/nullability inference in the same vertical slice. Reuse existing expression nodes where semantics match instead of adding duplicate helpers. For `Column.transform`, use a typed symbolic element callback and reject callbacks that execute arbitrary Python. For random functions, require the chosen seed/nondeterminism policy and classify streaming use explicitly.

Add specification tests for successful compilation, wrong types, nullability, profile rejection, variant rejection, generated spelling, and diagnostics. Add integration fixtures that compare online and generated output on ordinary 4.1 and Connect 4.1 where claimed. Run the unchanged 3.5/4.0 lanes to prove regression safety.

### Milestone 4: Query operations

Implement the approved `exists`/IN-subquery and lateral relation slice from `V11PySpark41QueryOperations.md`. Extend relation IR, alias and scope validation, cardinality metadata, renderer/evaluator delegates, explain output, and static traceability together. Keep raw DataFrame-returning Python callbacks caller-owned. Add positive and negative tests for correlation, duplicates, empty inputs, nulls, alias collisions, lateral zero/one/many output, and streaming eligibility.

The query milestone is complete only when generated source is readable, online/generated results match, explain output identifies relation and field dependencies, and Connect evidence exists for every row labeled Connect-supported.

### Milestone 5: Observations, sketches, and Python/state boundaries

Implement the decision from `V11PySpark41ObservationsAndSketches.md`: either a typed metric channel with tests or an explicit caller-owned/design-gated classification. Do the same for KLL and Theta sketch aggregates; a binary result without a documented merge and dependency contract is not supported.

Add stable diagnostics and docs for Arrow UDF/UDTF and `transformWithState` gates. Add generated-source scans proving that gated APIs and lifecycle/state ownership are never emitted by compiler-visible transforms. If a narrow positive slice is approved, create a separate specification and require failure/recovery and Connect evidence before support status changes.

### Milestone 6: Integration infrastructure and matrix

Extend the Compose image arguments and environment template with a pinned PySpark 4.1 version, Spark 4.1 master/worker services, ordinary runner, and Connect runner. Extend `scripts/run_integration.py` and `tests/integration/pyspark/support/backend_matrix.py` with `pyspark41` and `spark-connect41`, including profile and variant selection. Keep service selection lazy so running one lane does not start all versions.

Update runtime-version assertions, Spark Connect dependency cache naming, Sedona or other optional package coordinates if needed, integration README commands, and CI/build entry points. Add a matrix test that enumerates all six backend names and verifies that each maps to exactly one profile, variant, expected PySpark version, and Spark service. Pin exact versions or image digests and record them in the evidence report.

## Validation and Acceptance

The release is accepted when the following behavior is observable. A project configured with `profile = ">=4.1,<4.2"` and `variant = "ordinary"` can compile and execute each supported 4.1 fixture online and through generated PySpark with equal rows and schemas. A supported Connect fixture executes through the Connect runner without classic-only tokens. A 3.5 or 4.0 profile using a 4.1-only operation receives a structured capability diagnostic naming the required profile. A gated Arrow UDTF or stateful API receives an actionable boundary diagnostic. `make integration` runs six named lanes, and `make build` passes without Spark.

The evidence report must record the exact PySpark version, Spark version, Python version, target profile, variant, Compose image or package pin, command, pass/skip/fail counts, and any unavailable optional provider. A skipped live lane is unavailable evidence, not a positive support claim.

## Idempotence and Recovery

Inventory, documentation, and configuration edits are additive and safe to repeat. Compose `.env` creation must continue to use `scripts/ensure_compose_env.py`, which does not overwrite an existing file. If a 4.1 image or optional dependency cannot build, retain the existing 3.5/4.0 lanes, record the unavailable 4.1 evidence, and fix the image or pin before release; do not weaken a support status to make the matrix green. If implementation work conflicts with unrelated dirty files, stop at the overlapping file and preserve the user’s changes.

Generated files must be regenerated from source and reviewed with `structure compile --fail-on-diff`; never hand-edit generated output. If a feature is removed from scope, leave its catalog row as a design gate with the reason and caller remedy, and update the decision log before deleting implementation work.

## Interfaces and Dependencies

The new capability identity is `BackendId(name="pyspark", target=">=4.1,<4.2", family="ordinary_pyspark", variant="ordinary")` for the primary lane and the same target with family `spark_connect_dataframe` and variant `spark-connect` for the secondary lane. The profile resolver must recognize both exact ranges and the capability mapper must reject 4.1-only keys for earlier ranges.

The integration interface adds backend names `pyspark41` and `spark-connect41` to the runner choices, maps them to Spark 4.1 services, and exposes `STRUCTURE_EXPECTED_PYSPARK`, `STRUCTURE_EXPECTED_SPARK`, `STRUCTURE_INTEGRATION_BACKEND`, and the matching master/remote settings exactly as existing lanes do. The test helper’s `_target_profile()` must return `>=4.1,<4.2` for names ending in `41`.

The feature interfaces are the existing typed Structure DSL, expression/relation IR, capability requirements, online evaluator, generated renderer, explain/traceability model, and public API docs. No new public API may bypass those interfaces with raw SQL text or an untyped Python callback.
