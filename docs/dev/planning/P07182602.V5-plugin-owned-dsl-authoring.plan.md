# Move PySpark DSL Authoring and Type Semantics into the PySpark Plugin

This ExecPlan is a living document. Maintain it according to
`docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`,
and `Outcomes & Retrospective` accurate whenever work stops or a design fact changes.

## Purpose / Big Picture

After this change, a PySpark transform author imports every PySpark-specific concept from
`structure.plugin.pyspark`: field factories, field types, expressions, joins, aggregation,
streaming helpers, and all other symbolic operations. Core continues to own the Python
declaration model: `Schema` inheritance, `Transform` inheritance, input/output/lane
declarations, decorators, source order, step invocation, override rules, and hook placement.
PySpark owns the meaning and validation of a step body, including concrete and nested field
types. This makes it possible for a future plugin to use different field definitions and
symbolic operations without putting its model in Core.

The observable result is a transform such as the following, which compiles and runs with the
same PySpark behavior as today while Core contains no join, expression, concrete field-type,
or PySpark operation plan.

    from structure import *
    from structure.plugin.pyspark import *

    class Order(Schema):
        id = long(nullable=False)
        customer_id = long(nullable=False)

    class Customer(Schema):
        id = long(nullable=False)
        name = string(nullable=False)

    class EnrichedOrder(Schema):
        id = long(nullable=False)
        customer_name = string(nullable=False)

    class Enrich(Transform):
        orders = input(Order)
        customers = input(Customer)
        result = output(EnrichedOrder)

        def enrich(self, order: Order, customer: Customer) -> EnrichedOrder:
            return EnrichedOrder(
                id=order.id,
                customer_name=inner_join(customer, on=order.customer_id == customer.id).name,
            )

The implementation preserves Core's existing ownership of the method call: Core determines
that `enrich` is a step, resolves its inherited declarations and lane bindings, invokes it once
with plugin-supplied symbolic arguments, and records the result's structural placement.
PySpark captures the symbolic operation body and validates it. Core then dispatches the already
captured body to the selected PySpark compiler exactly once.

## Decision Log

- Decision: Core owns transform structure and invokes every step method; the selected plugin supplies symbolic
  arguments and captures the returned body.
  Rationale: Source ordering, inherited overrides, decorators, lane bindings, and hook placement are Structure
  semantics. Letting a plugin invoke methods would duplicate or weaken those guarantees.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: Extend Plugin API v1 now with a required authoring facet rather than introduce v2.
  Rationale: v1 is still under active internal development. One explicit, complete v1 contract is preferable to
  preserving a temporary façade that cannot express plugin-owned authoring.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: PySpark owns concrete-type and nested-type validation after its types move to the plugin.
  Rationale: Recursive structs, arrays, maps, nullability, aliases, and type compatibility are meaningful only under
  a plugin's field model. Removing validation would regress schema safety; moving it preserves the current behavior
  and lets other plugins define their own rules.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: Remove `structure.field` and all root PySpark DSL aliases in this change.
  Rationale: A forwarding alias hides which plugin owns the declaration and prevents a second plugin from defining
  its own field vocabulary. The migration is intentionally breaking and is completed atomically across examples,
  fixtures, tests, and public documentation.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: Core treats every captured plugin step body and lowered payload as opaque.
  Rationale: Core may route a value through its workflow, attach the Core structural plan to an artifact, and ask a
  plugin to serialize its payload, but it must not inspect target operations to render explain output, decide
  capabilities, or validate a target rule.
  Date/Author: 2026-07-18 / project owner and Codex.

## Outcomes & Retrospective

Core owns structural compilation and dispatch while PySpark owns the concrete DSL that has already moved: joins,
operations, expressions, field types, schema validation, symbolic capture, and lowering. The public PySpark authoring
import is now `structure.plugin.pyspark`; schema factories are exclusively `*`, and no Plugin API or PySpark
source imports a private Core module. Plugin API v1 is structurally organized into `api/` and `model/`, with
`PluginAPIV1` as the façade name and `PySparkPlugin.py` as the plugin entry module.

The structural-plan extraction remains open: Core's legacy plan records still retain target-shaped compatibility
fields while the legacy source import shims are removed. The public-import and plugin/Core dependency boundaries are
now independently verified.

Latest verification on 2026-07-19: `make build` passed with 1,119 tests passing and 22 skipped; the rigidity suite
passed with 26 tests passing and 6 skipped; the source and wheel distributions built successfully. Live PySpark
integration remains skipped where Spark is unavailable, as before.

## Context and Orientation

Core compilation begins at `Compiler.frontend.analyze()` and `Compiler.frontend.compile()`. `analyze()` currently uses
`CompileTransform` to create a `TransformPlan`; `compile()` selects a plugin and sends that plan as
`CompileRequest.analysis` to `plugin.compiler.compile()`. `BuildCompiledTransform` then creates the standard Core
artifact envelope. This workflow ownership remains unchanged.

The problem is the shape of the current plan. The Core compiler's `CompileTransform` imports PySpark-shaped expression
and transform models, symbolically executes methods with Core `RowScope` and `InputScope` objects, and stores the
result in Core `JoinPlan`, `OperationPlan`, aggregate, projection, and expression records. The bundled PySpark
compiler in `src/structure/plugin/pyspark/api/Compiler.py` only lowers that Core-owned target model. Moving
only `JoinDedupe` or `JoinPlan` would leave expressions, aggregation, schema type checks, and method capture in Core.

A structural plan describes facts that are true regardless of data plugin: a transform and step name, declaration
origin, input and output schemas, method parameter-to-lane bindings, output lanes, source order, declared options, and
raw-hook placement. A plugin step body describes the target language evaluated by the method: for PySpark it is the
expression graph, join sequence, projection, aggregation, streaming operation, and target diagnostics. Core owns the
former and never interprets the latter.

The relevant Core declaration classes are `Schema`, `Transform`, `InputDeclaration`, `OutputDeclaration`,
`LaneDeclaration`, and decorators in `src/structure/core/dsl/model/`. They retain their behavior. Create the public
`structure.dsl` contract package and export `Schema`, `Transform`, the declaration classes, `FieldDeclaration`, and
`FieldDefinition` from it. `Schema` needs those common field containers to merge inherited Python attributes, but their
`type` value is opaque to Core. Only the selected schema facet interprets it. A plugin imports this shared declaration
contract from `structure.dsl`, never from a `structure.core` path.

`structure.plugin.api.v1` is the public contract between Core and a selected plugin. A public contract here means
that an independently packaged plugin can import the types without importing Core implementation modules. Requests and
results are frozen data classes or protocols. An opaque value is a value whose shape is owned by the plugin: Core may
retain and pass it to the same plugin but may not branch on its fields or type.

## Interfaces and Dependencies

Extend the v1 façade with a required `authoring` field in `PluginAPI`. Keep the existing optional `analysis` facet
for post-compilation streaming and traceability reports; do not overload it with symbolic authoring. Add the following
public v1 models and protocols under `src/structure/plugin/api/v1/` and export them from that package.

`StepAuthoringRequest` is a frozen request containing the selected plugin name, plugin configuration mapping, a
stable step identity, the step name and declaration origin, ordered structural input bindings, ordered structural
result bindings, and the step's declared options. Its input and result bindings are public frozen API models containing
only parameter/lane/source names, schema objects, ordinals, and driving/result flags. They replace plugin imports of
Core `StepInputPlan`, `StepResultPlan`, and `TransformMemberOrigin`.

`AuthoringAPI` defines `open_step(request: StepAuthoringRequest) -> StepAuthoringSession`.
`StepAuthoringSession` is a context-manager protocol with these operations:

    arguments() -> tuple[object, ...]
    capture(value: object) -> object

`arguments()` returns exactly one plugin symbolic scope for every ordered input binding. Core enters the session,
passes those scopes to the user method, and calls `capture()` exactly once with the returned value. `capture()` returns
one opaque plugin body or raises a normal Structure diagnostic for invalid target DSL. The session is responsible for
installing and clearing only plugin-local symbolic state. It must not call Core compiler, frontend, capability,
traceability, schema, or plugin-registry services.

Move the structural `TransformPlan`, `StepPlan`, input/output/binding, result, hook, and declaration-origin models to
`src/structure/plugin/api/v1/` and export them from that package. Their schema fields are typed as `object` at this
public boundary so the API itself imports no Core implementation module. Core remains their sole constructor.
`Compiler.frontend.analyze()` returns this target-neutral structural plan without evaluating any plugin DSL. A
`StepPlan` has a `plugin_body: object | None` slot, initially empty. `Compiler.frontend.compile()` selects the
target, asks its schema facet to validate the reachable schemas, then has the Core authoring runner attach one opaque
body to every schema-returning step. The compiler facet receives that completed plan in `CompileRequest.analysis` and
may read only the body values it owns. `PluginCompilation.analysis` is the same Core-owned completed plan, attached
by Core after a successful compiler return. The compiler must not replace the structural plan.

Make `SchemaAPI.validate(schema: object, configuration: Mapping[str, object]) -> None` a required v1 operation. Core
calls it after target selection and before opening the first authoring session for every input, lane, and output schema
reachable from a transform. PySpark validates that every field declaration was created by the PySpark DSL, that nested
PySpark types are well formed and acyclic, and that aliases, nullability, metadata, and type compatibility satisfy
PySpark's existing rules. A foreign or mixed field definition fails before a user step method executes.

Move the Core concrete models to `src/structure/plugin/pyspark/dsl/`, organized by responsibility rather than as one
large compatibility module. This package contains PySpark field factories and field types; expressions and symbolic
row/input scopes; projections; joins and their policy/value classes such as `JoinDedupe`; aggregates, windows,
selection, streaming, and optimization operations; PySpark plan/body records; and their validators. The PySpark
authoring facet owns the replacement for `CompileContext` and captures those records. The PySpark compiler facet
lowers only its own body records with its own capability rules.

Public imports are fixed as follows. `structure.dsl` exports the common declaration contract for plugin authors.
`structure` re-exports only its user-facing target-neutral declarations: `Schema`, `Transform`, `input`, `output`,
`lane`, `transform`, `step`, `raw`, and `special`. It exports neither `field` nor a PySpark expression, join, type,
streaming, or operation name. `structure.plugin.pyspark` re-exports the supported PySpark DSL from its internal
`dsl` package, including `field`, expressions, joins, policies, and type helpers. The plugin package may import
`structure.dsl` and `structure.plugin.api.v1`, but no plugin module may import a `structure.core` compiler,
capability, traceability, frontend, registry, or implementation model module.

## Plan of Work

### Milestone 1: Establish a public structural-authoring boundary

First add the public v1 models and `AuthoringAPI` protocol. Update `PluginAPI` validation, test fakes, the PySpark
plugin façade, and the iterable/conformance fixture so that a façade without `authoring` is rejected before a workflow
starts. Since the project intentionally extends v1, update `docs/dev/specifications/PluginAPI.spec.md` and
`docs/dev/design/PluginArchitecture.design.md` in the same commit to state that authoring is required and that Core
invokes user methods.

Move the structural plan records from Core IR to the public v1 API package and update Core to import them there. Keep
only structural fields in the records: no expression, join, projection, aggregate, operation, concrete type, or
streaming enum may remain in the Core-owned plan. Add `plugin_body` as an opaque field on a completed step. The body
is absent only for a non-symbolic structural step; a schema-returning step must have one before `compile()` calls the
compiler facet.

Refactor `CompileTransform` into two focused collaborators. The structural collector discovers members, inheritance,
declarations, lane bindings, output schemas, options, and raw hooks. The Core authoring runner owns ordered method
invocation, current-step guards, permitted overridden-parent calls, result cardinality checks, lane updates, and hook
attachment. It calls `SchemaAPI.validate()` first, opens exactly one authoring session per schema-returning step, and
uses its arguments/capture operations. Delete Core's symbolic context creation and all Core validation that reads a
target body. Preserve existing diagnostic source context around the Core call so user errors still identify the method.

Keep `Compiler.frontend.analyze()` as the target-neutral structural API. It validates declarations, inheritance,
bindings, output schemas, decorators, and hooks, but it neither selects a plugin nor invokes a schema-returning user
method. `Compiler.frontend.compile()` calls it once, resolves the target/configuration, validates every reachable schema
through that plugin, and has the Core authoring runner enrich a copy of the structural plan with opaque bodies. It
then calls the selected `compiler.compile()` once with the completed plan in `CompileRequest.analysis`, rejects a
missing/invalid plugin result, and attaches that exact completed plan to `PluginCompilation.analysis`.
`BuildCompiledTransform` continues to own artifact identity, validation, and fingerprints. It stores the completed
structural plan; plugin payload serialization remains delegated to the plugin serializer.

Add unit contracts before moving PySpark behavior. A recording fake authoring facet must prove that Core supplies the
expected bindings, enters/exits one session, invokes each method exactly once, sends the captured body to the compiler
once, and preserves Core-owned inherited and raw-hook behavior. A failing fake schema validator must prove that no
step method runs after ownership validation fails.

### Milestone 2: Move PySpark authoring, plans, and validation

Create `src/structure/plugin/pyspark/dsl/` and move the complete target DSL there. Do not leave forwarding modules
under `src/structure/core/dsl/model/expr`, `.../types`, or target operation/plan modules. Move each consumer with its
owner: PySpark lowering, generated rendering, online execution, explain, streaming classification, traceability, and
diagnostics import PySpark DSL/body records only from the plugin subtree.

Implement `PySparkAuthoringAPI`. Its session creates PySpark symbolic row and relation scopes from the structural
bindings, records joins/filters/projection/aggregate/window/streaming operations in plugin-local state, and validates
the captured return value against the declared result schemas. It returns an immutable `PySparkStepBody`. The body
