# Introduce a vector index and Reciprocal Rank Fusion to Search

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date during implementation. It follows the repository guidance in
`docs/dev/auto/Plans.md`.

## Purpose / Big Picture

The Search example currently finds similar documents and passages only through normalized token overlap and BM25.
That works for shared vocabulary, but it misses semantically related text that uses different words. After this work,
a caller can provide precomputed embeddings, build a typed exact vector index, and retrieve semantically similar
documents and paragraphs through the same Search application.

The first user-visible result is hybrid similarity: lexical and vector retrieval each produce a ranked candidate list,
and Reciprocal Rank Fusion (RRF) combines those ranks without pretending that BM25 and cosine scores share a numeric
scale. The second result is hybrid document search: lexical and vector candidates are fused before the existing
feedback-aware reranking stage, so semantic candidates can recover documents that lexical search missed.

Embedding model execution, credentials, vector persistence, refresh scheduling, and production ANN services remain
caller- or plugin-owned. This plan introduces a typed exact Spark implementation suitable for the Search example and
its generated artifacts; it does not turn Structure into a model-serving or hosted vector-database product.

## Surprises & Discoveries

- Observation: Similarity now has a bounded hybrid path while the broader Search application still defers hosted vector operations.
  Evidence: `SearchSimilarity` consumes provider-neutral candidates and `SimilarityFusionPolicy`; the exact index is a reference producer and ANN operation remains caller-owned.

- Observation: The Search example already has independent same-grain lexical pipelines and a shared reduction boundary.
  Evidence: `examples/search/transforms/similarities/CreateSimilarityQueries.py` creates document, section, paragraph, and sentence queries; `ReduceSimilarityScores.py` canonicalizes reciprocal pairs and ranks each source target.

- Observation: Document search has a natural candidate-generation boundary before feedback reranking.
  Evidence: `RetrieveDocuments`, `FuseDocumentCandidates`, and `RerankDocuments` under `examples/search/transforms/searching/search_docs/` separate lane admission, RRF fusion, feedback enrichment, and final ranking.

- Observation: The vector document lane can bypass lexical filter targets safely because it is still bounded by the
  provider rank and matching request/policy identity; the existing filter target remains the lexical admission boundary.
  Evidence: `RetrieveDocuments.select_vector_candidates` joins only the request, query, document, and user-band
  context, then `FuseDocumentCandidates` applies the policy cap before feedback.

- Observation: Structure schemas support arrays, including non-null array elements; the Search vector contract now uses that
  typed representation without adding a provider dependency.
  Evidence: `docs/reference/Schema.ref.md`, `examples/search/schemas/indexing/vector.py`, and the exact reference index.

- Observation: Exact vector retrieval will require a distributed pair comparison and bounded ranking rather than driver-side collection.
  Evidence: The existing Search design forbids driver-side corpus collection and keeps similarity reduction in DataFrame transformations; the first implementation must preserve that boundary.

## Decision Log

- Decision: Use the term Reciprocal Rank Fusion (RRF), not “early fusion.”
  Rationale: The intended behavior combines independently ranked lexical and vector result lists by rank contribution. RRF is the precise name for that operation.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Treat RRF as `sum(1 / (rrf_k + rank))` over the available retrieval lanes, with equal lane weight and `rrf_k=60` by default.
  Rationale: BM25 and cosine similarity have different scales and should not be numerically blended without calibration. Equal-weight RRF is transparent, deterministic, and gives a useful baseline for later experiments. The policy may expose a positive `rrf_k`, but the first example uses the standard default of 60.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Keep lexical and vector candidate generation separate and fuse ranked candidates rather than concatenate sparse and dense representations.
  Rationale: Separate lanes preserve each evidence source, allow lexical-only and vector-only candidates, fit the existing Search stages, and avoid inventing a new combined index representation.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Make embedding production caller- or plugin-owned.
  Rationale: Search should not own model execution, credentials, batching, model deployment, or provider-specific dependencies. It consumes validated embedding rows and exposes the provider/model identity needed for compatibility checks.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Implement a typed exact vector index first; defer approximate-nearest-neighbor (ANN) backends.
  Rationale: Exact retrieval is portable across the existing PySpark and generated execution paths and proves the schema, identity, scoring, ranking, and parity contracts before introducing an external service or backend-specific library.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Vectorize documents and paragraphs first; leave section and sentence vector retrieval lexical-only in the first slice.
  Rationale: Documents are the first document-search consumer and paragraphs are the existing passage grain. This limits the first vector contract while covering the most useful Search surfaces.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Every embedding carries model identity, dimension, source-content revision, and `experiment_id`.
  Rationale: Vectors from different models, dimensions, corpus revisions, or experiments must not be mixed silently. These fields make compatibility and evaluation boundaries explicit.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Use cosine similarity and reject zero-norm vectors.
  Rationale: Cosine is the natural first metric for normalized text embeddings, and a zero vector has no defined direction. Failing the vector-index build with an actionable diagnostic is safer than producing arbitrary similarity values.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Keep similarity policy and document-retrieval policy separate.
  Rationale: Corpus-neighbor exploration and request-serving retrieval have different candidate limits, freshness, query inputs, and operational constraints. Sharing one policy would couple two product behaviors unnecessarily.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Preserve the lexical-only Search path as the compatibility baseline.
  Rationale: Callers that do not supply a vector policy or query embeddings must retain current lexical similarity and document-search behavior. Vector-enabled behavior is an explicit opt-in.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Schedule this plan for v10 Sprints 49–54 as an explicit Search application exception to the general rule that application futures remain outside v10.
  Rationale: The user requested v10 scheduling for this focused vector-index/RRF slice, while the future documents must continue to preserve broader deferred Search work. The exception is limited to this plan’s caller-owned exact implementation and its evidence.
  Date/Author: 2026-08-05 / User and Codex.

## Context and Orientation

The repository is a typed transformation compiler. Search schemas under `examples/search/schemas/` describe DataFrame
relations, and transforms under `examples/search/transforms/` declare inputs, intermediate lanes, and outputs. The same
transform source is executed online and rendered into generated PySpark, so every new ordinary operation must remain
compiler-visible and must have generated-output evidence.

The lexical index is built by `examples/search/transforms/indexing/Indexing.py` from normalized words. Its public term and
summary schemas are in `examples/search/schemas/indexing/lexical/index.py`. Lexical scores are produced by the scoring
transforms and exposed as overlap and BM25 relations. Similarity currently creates a query from each indexed target,
scores that query against the same-grain index, and reduces reciprocal directed scores in
`examples/search/transforms/similarities/ReduceSimilarityScores.py`.

RRF is a rank-list combination rule. If a candidate has rank `r` in a retrieval lane, that lane contributes
`1 / (rrf_k + r)`. A candidate present in both lexical and vector lists receives both contributions; a candidate present
in only one list receives only that lane’s contribution. The fused rank is determined by the sum, followed by stable
component-score and identifier tie-breakers. RRF does not compare or normalize the raw BM25 and cosine values.

Document search currently admits lexical candidates in `RetrieveDocuments`, narrows them in `OverlapDocuments`, and
passes the survivors to `RerankDocuments`, which adds query-document and document-popularity feedback. The hybrid path
must add vector candidates before feedback and must not require a semantic-only candidate to have a lexical overlap row.

The current Search design is documented in `docs/dev/design/Search.design.md`, `docs/background/Search.back.md`, and
`examples/search/Readme.md`. Those documents now describe the bounded caller-owned exact vector and document-search
fusion paths while preserving the deferred model, ANN, and streaming boundaries.

## Plan of Work

### Milestone 1: Define and validate embedding and vector-index contracts

Add `examples/search/schemas/indexing/vector.py` with typed document and paragraph embedding/index relations. Each row
must contain its target identifiers, a non-null `array(double(), contains_null=False)` vector, `model_id`, positive
`dimension`, `content_revision`, and non-null `experiment_id`. The declared dimension must equal the vector length.

Add a vector-index policy with the expected model ID, dimension, content revision, experiment ID, positive candidate
bound, and positive `rrf_k` defaulting to 60. The index-building transform must validate that the policy contains exactly
one row, that all embedding rows match the policy identity, that vectors are non-empty and finite, and that their norm
is nonzero. It must emit validated document and paragraph index relations plus summaries containing the identity and
target count. The transform may preserve the vector rows rather than materializing a separate physical index; the
typed relation is the persisted artifact and exact retrieval scans it through DataFrame operations.

Keep the provider boundary explicit in names and documentation. The Search example accepts a caller-produced embedding
relation; it does not add a model SDK, model call, network client, secret lookup, or driver-side batching. A provider
may implement the embedding relation outside Structure or in a separate plugin-owned transform.

Add vector scoring relations for directed document and paragraph queries. The scorer must compute cosine similarity
using typed expressions or a narrowly documented compiler-supported boundary, never collect vectors to the driver. It
must reject mismatched query/index identity and must rank deterministically by descending cosine and target identifiers.
The scorer must support self-similarity by excluding a target from its own candidate list.

Add Spark-free schema, compiler, and generated-source tests for array shape, identity fields, validation diagnostics,
and deterministic relation shapes. Add a small live-PySpark test with hand-authored vectors so cosine values can be
checked exactly enough to distinguish identical, orthogonal, and tied vectors.

### Milestone 2: Refactor document and paragraph similarity around RRF

Keep the existing lexical similarity query creation and scoring for all four grains. Factor the common candidate and
reduction responsibilities so document and paragraph similarity can consume two ranked lanes: lexical candidates from
the existing reducer inputs and vector candidates from the new scorer. Section and sentence outputs remain on the
existing lexical path for this milestone.

For document and paragraph similarity, retain at most the configured lexical and vector candidate bound per source
target. Union the lanes by the complete same-grain pair key and deduplicate a pair that appears in both lanes while
preserving both ranks and component scores. Exclude self-pairs. Compute:

    rrf_score = (1 / (rrf_k + lexical_rank), when lexical_rank exists)
                + (1 / (rrf_k + vector_rank), when vector_rank exists)

Use `rrf_k=60` by default and equal lane contribution. Rank the final output by descending `rrf_score`, then vector
similarity, then the existing lexical evidence, then stable target identifiers. Keep the existing overlap and directed
BM25 fields for inspection; add vector score, lexical rank, vector rank, RRF score, and `experiment_id` rather than
discarding evidence needed to explain why a pair ranked where it did.

Update `SearchSimilarity`, `Similarities`, `SimilarParagraphs`, and `SimilarDocuments`-equivalent presentation paths
to accept the new vector artifacts and policy only when vector behavior is requested. A lexical-only invocation must
continue to produce the current result shape and ordering. A vector-enabled invocation must require exactly one
matching embedding per source query and must fail with a remedy if a query embedding is absent or incompatible.

Add tests for lexical-only regression, vector-only candidates, candidates appearing in both lanes, self-exclusion,
missing-lane RRF contributions, deterministic ties, candidate bounds, model/revision mismatch, and document-versus-
paragraph isolation. Add judged similarity fixtures or a focused ranking assertion that proves RRF can promote a
candidate that is strong in one lane without requiring BM25 and cosine to be numerically comparable.

Regenerate Search generated artifacts with `make gold` after source and schema changes. Add generated-source scans and
online/generated parity tests for both the lexical-only and vector-enabled branches.

### Milestone 3: Add vector candidates to document search

Add a separate document-retrieval vector policy and a query-embedding input. The policy must identify the vector model,
dimension, content revision, experiment ID, per-lane candidate bound, and RRF `rrf_k`. The query embedding must carry the
same request/query key as `SearchQuery` and the same model, dimension, revision, and experiment identity as the document
vector index. When the vector policy is enabled, missing or duplicate query embeddings are errors; when it is disabled,
the existing lexical path remains unchanged.

Refactor the document-search admission stages so hybrid retrieval has two independent ranked inputs:

1. lexical candidates ranked by the current BM25 score and existing deterministic tie-breakers;
2. vector candidates ranked by cosine similarity and deterministic document-ID tie-breakers.

Fuse those ranked lists by document ID and the request’s query/band/experiment key. A candidate present in either list
survives the union. Calculate its RRF score from the ranks that exist, retain lexical and vector component values, and
admit the configured fused top-K. Semantic-only candidates must not be discarded merely because they have no overlap
score. Preserve the old overlap narrowing behavior for lexical-only mode; the hybrid mode’s candidate gate is RRF, not
the lexical overlap relation.

Pass fused candidates to feedback selection and reranking. Feedback remains an enrichment of admitted candidates and
must not create new documents. Extend candidate/result schemas with explicit lexical, vector, RRF, and final ranking
evidence rather than overloading an existing BM25 field. Preserve the current experiment and band partition keys,
deterministic final ranks, freshness handling for lexical score caches, and streaming lineage. Query embeddings and the
vector index are static caller-owned side inputs for the current streaming boundary; this plan does not introduce
streaming vector-index refresh or query lifecycle ownership.

Add document-search tests that compare lexical-only, vector-only, and hybrid results. Include a case where a semantic-only
document outranks a lexical candidate through RRF, a duplicate candidate appears in both lanes, feedback reranks only
after fusion, and a missing vector query fails only when vector mode is explicitly enabled. Run the existing judged
document-ranking evaluator with separate `experiment_id` values for the lexical baseline and hybrid run; do not claim
semantic quality from click feedback alone.

## Validation and Acceptance

The vector-index milestone is accepted when a caller can provide two documents and two paragraphs with hand-authored
vectors, build a validated index, and retrieve exact same-grain neighbors with correct cosine ordering. The run must
reject mismatched dimension, model ID, content revision, experiment ID, empty vectors, and zero-norm vectors with an
actionable diagnostic.

The similarity milestone is accepted when lexical-only output remains unchanged and vector-enabled output combines
lexical and vector ranked lists with the documented RRF formula. A pair found only by lexical retrieval, only by vector
retrieval, and by both must each receive the correct contribution. Ranks must restart per source target and ties must be
deterministic.

The document-search milestone is accepted when hybrid search can return a semantic-only candidate, deduplicate a
candidate found by both retrieval lanes, fuse before feedback reranking, and preserve the current feedback and band
semantics. Lexical-only search must retain its current candidate and result behavior.

Generated PySpark and online execution must agree on rows, schemas, ranks, and diagnostics for the focused fixtures.
The final Search documentation must no longer describe vector search as wholly deferred, while explicitly preserving
the caller-owned and ANN boundaries. `make build` must pass, apart from any pre-existing environment-gated skips
recorded in this plan.

    lexical_rank = 3
    vector_rank = 8
    rrf_k = 60

A lexical-only candidate has only the first term. A vector-only candidate has only the second term. The implementation

## Interfaces and Dependencies

The embedding contract must provide typed document and paragraph rows with target identifiers, `vector`, `model_id`,
`dimension`, `content_revision`, and `experiment_id`. The vector index builder must output validated relations using the
same identity fields and must expose target counts for sanity checks.

The vector scorer must accept source/query embeddings and same-grain index rows and output directed candidate rows with
query identity, target identity, cosine similarity, deterministic vector rank, and experiment identity. It must use
Structure expressions or a deliberately narrow compiler-supported operation; arbitrary DataFrame actions, driver
collection, RDD conversion, and hidden persistence are prohibited.

The similarity reducer must accept lexical and vector ranked candidate lanes and output existing same-grain similarity
relations extended with vector score, source ranks, RRF score, and experiment identity. It must support document and
paragraph vector lanes while leaving section and sentence lexical behavior intact in the first slice.

The document-search hybrid admission boundary must accept lexical candidates, vector candidates, query embeddings,
document vector index rows, and a separate document retrieval policy. It must output candidates carrying lexical score,
vector score, lexical rank, vector rank, RRF score, and the existing feedback/ranking fields. Feedback inputs remain
static enrichment relations, and streaming query/request lineage remains caller-owned and compiler-visible.

No new external runtime dependency is required for the exact implementation. Model providers and future ANN adapters may
be implemented outside the Search example or behind explicitly documented plugin boundaries.
