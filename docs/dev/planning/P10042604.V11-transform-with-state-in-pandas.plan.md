# Implement `transformWithStateInPandas` for PySpark 4.0 and 4.1

This ExecPlan is a living document maintained according to `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as work proceeds. This document is self-contained: it records the user-visible behavior, prerequisite contract, implementation sequence, public interfaces, and evidence required for a support claim.

## Purpose / Big Picture

After this work, a Structure user can process each streaming key as one or more Pandas DataFrames while using Spark's arbitrary state API. The user can declare typed input, key, value-state, and output schemas; update one persisted value state; register and handle timers; and emit zero or more Pandas DataFrames. Users who need Spark's complete native processor interface can bind an opaque PySpark `StatefulProcessor` instead. Online execution and generated code produce the same result on ordinary PySpark 4.0 and 4.1.

The visible proof is a streaming transform that accumulates state per key from multiple Pandas batches, emits typed output, fires a timer, stops, and resumes from the same caller-owned checkpoint. The same fixture must pass through online and generated execution. A native processor fixture must additionally prove optional initial state and more than one native state variable. The feature does not create a source, sink, writer, trigger, checkpoint, or query.

This plan starts from the completed row-based state contract in `docs/dev/planning/past/P10042603.V11-transform-with-state.plan.md`. That prerequisite provides `StateProcessor`, `ValueState`, `Timer`, `TimerContext`, `@state_processor`, `external_state_processor(...)`, `transform_with_state(...)`, and the shared compiler-visible state recipe. If those names or semantics change before this plan begins, first revise this document so that its descriptions and examples match the merged row feature. Do not implement this plan against a partial copy of the row work.

  Evidence: The versioned PySpark 4.0.3 and 4.1.0 API references both list that signature and mark the operator as introduced in 4.0.
- Observation: Row and Pandas state processing use the same object-oriented `StatefulProcessor`, state variables, timers, output modes, time modes, and initial-state lifecycle; their input and output containers differ.
  Evidence: The Spark 4.1 Structured Streaming guide shows `handleInputRows` yielding `pandas.DataFrame` values for the Pandas operator and `Row` values for the row operator.

  Rationale: The typed path keeps schemas and the supported state slice visible to Structure. The native path preserves access to Spark features that Structure does not model.
  Date/Author: 2026-10-04 / User and Codex.

  Date/Author: 2026-10-04 / User and Codex.

  Date/Author: 2026-10-04 / Codex.

## Context and Orientation

Structure is a schema-first compiler. Users declare `Schema` classes and write transform steps with the Structure DSL. The Core compiler discovers steps and asks the PySpark plugin to capture their operations. The plugin lowers captured operations into an immutable recipe. Online execution interprets that recipe, while generated execution renders equivalent Python source. A feature is supported only when both paths share the same contract and live runtime tests prove equal behavior.

The row-state prerequisite adds authoring declarations under `src/structure/plugin/pyspark/dsl/Stateful.py`, an immutable captured state operation under `src/structure/plugin/pyspark/dsl/operations/`, and a lowered recipe under `src/structure/plugin/pyspark/compiler/model/`. Capture and lowering flow through `src/structure/plugin/pyspark/symbolic_execution/commands/CapturePySparkStep.py` and `src/structure/plugin/pyspark/compiler/logic/maps/MapPySparkStep.py`. Execution and generated rendering consume the lowered recipe from their respective PySpark-plugin packages. Streaming compatibility is classified from the lowered plan, so the classifier can report state placement, modes, and composition without inspecting callback bodies.

In Spark, `transformWithStateInPandas` performs a full grouping shuffle. For each grouping key, Spark invokes a `StatefulProcessor`. Its `handleInputRows` callback receives an iterator of Pandas DataFrames and may yield any number of Pandas DataFrames of arbitrary sizes. State variables and timers persist in Spark's checkpointed state store. The output schema is declared when calling the operator. Optional initial state is a grouped batch DataFrame processed once before streaming input. Structure owns the typed transformation boundary; the caller owns sources, sinks, checkpoints, query start/stop, worker dependency deployment, and checkpoint migration decisions.

The typed callback body is ordinary Python executed by Spark workers. Structure does not symbolically interpret, optimize, or translate that body. The typed contract means that four Structure schemas declare the input rows, grouping key, single persisted value, and output rows, and that Structure adapts key/state values and checks emitted DataFrame shape. It does not make `pandas.DataFrame` statically generic.

This feature is distinct from `applyInPandasWithState`, which is Spark's older arbitrary-state API, and from `toPandas`, `mapInPandas`, and implicit Pandas UDF fallback. Supporting this explicit compiler-visible operator must not admit those other boundaries into streaming transforms.

## Scope and Non-Goals

Add a typed Pandas processor declaration and a compiler-visible `transform_with_state_in_pandas(...)` operation. Support one declared `ValueState`, processing-time and event-time timers consistent with the row contract, zero or more emitted Pandas DataFrames, and ordinary PySpark 4.0/4.1 execution. Retain the opaque native binding for users who need multiple state variables, `ValueState`, `ListState`, `MapState`, time-to-live settings, native initialization behavior, or other features exposed by the selected Spark profile.

Do not add `applyInPandasWithState`, Spark Connect support, automatic batching or concatenation, automatic vectorization, a query/source/sink API, checkpoint management, checkpoint conversion between row and Pandas operators, automatic state-schema migration, external side-effect recovery, or support for chaining arbitrary stateful stages. Do not claim stable input-row ordering within a key. Do not claim that Pandas execution is faster than row execution for every workload.

## Validation and Acceptance

The typed API is accepted when a user can declare `PandasStateProcessor[Event, AccountKey, TotalState, TotalOutput]`, receive an iterator of Pandas DataFrames, update a typed value state, register and handle a timer, and emit DataFrames that become a streaming DataFrame with the declared `TotalOutput` Spark schema. The same transform must produce equal logical output online and from generated code on ordinary PySpark 4.0 and 4.1.

The adapter must preserve streaming behavior with arbitrary input and output batch sizes, zero output, null values allowed by the Structure schema, and multiple batches for one key. It must reject a non-DataFrame yield, wrong output columns, incompatible processor decorator, typed initial state, unsupported target, missing runtime packages, and disallowed stateful composition with actionable messages before or at the narrowest possible boundary.

The native path is accepted when a top-level importable PySpark `StatefulProcessor` executes unchanged through online and generated transforms, uses multiple state variables and initial state, and resumes from a caller-owned checkpoint. Generated modules contain the intended `transformWithStateInPandas` call and processor import while containing no reader, writer, trigger, checkpoint path, query start/stop, `collect`, `toPandas`, RDD conversion, or fallback to the legacy state API.

The support claim is complete only after `make build`, the full ordinary 4.0 lane, and the full ordinary 4.1 lane pass. Spark Connect and `applyInPandasWithState` remain unclaimed. No test may claim deterministic order among input rows or equivalence of physical batch boundaries.

## Idempotence and Recovery

Compiler and generation changes must be deterministic and safe to rerun. Integration tests create unique source, output, and checkpoint directories under pytest temporary storage and stop every query in `finally` blocks. Restart tests deliberately reuse one checkpoint only within one test and one operator interface. Differential row/Pandas tests always use separate checkpoints.

The caller owns checkpoint identity and migration. Changing the processor implementation, state schema, interface, or Spark profile may make an existing checkpoint incompatible. Structure must not delete, rewrite, inspect private state-store files, or automatically migrate it. Document the original Spark error and direct the user to an explicit application migration or a new checkpoint.

If a live test fails after starting a query, stop the query, preserve the relevant Spark logs and dependency versions, and retry with a fresh temporary directory. If implementation overlaps unrelated dirty files, preserve those changes and adapt or stop at the overlapping edit rather than resetting the worktree.

    class AccountTotalBatches(PandasStateProcessor[Event, AccountKey, TotalState, TotalOutput]):
        def on_batches(self, key, batches, state: ValueState[TotalState], timers: TimerContext):
            import pandas as pd

            total = state.get() or TotalState(total=0)
            for batch in batches:
                total = TotalState(total=total.total + int(batch["amount"].sum()))
            state.update(total)
            yield pd.DataFrame({"account_id": [key.account_id], "total": [total.total]})

            total = state.get()
            if total is not None:

    return transform_with_state_in_pandas(
        key=event.account_id,
