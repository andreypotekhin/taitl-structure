# Implement Advanced Analytical Operations

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement the remaining
aggregation, window, and higher-order function work from this file and the current working tree.

## Purpose / Big Picture

After this plan is complete, Structure users can express mainstream analytical batch pipelines without dropping into
hooks for multi-level aggregations, filtered metrics, explicit window frames, ranking distribution metrics, value
windows, window aggregates, and richer array/map higher-order helpers. The behavior is visible in source, IR,
generated PySpark, online execution, traceability, and `structure explain`.

Users can see the result by compiling and running v2 orders-style transforms that contain rollups, grouping sets,
filtered aggregates, reusable windows, and nested collection helpers, then comparing online and generated outputs.

  Evidence: `Sprint08_AggregationsWindowsHigherOrderFunctions.md` records grouped aggregates, projection windows,

- Observation: PySpark exposes `rollup(...)` and `cube(...)` directly on DataFrames, but does not provide an equally
  stable DataFrame API surface for arbitrary grouping-set levels.
  Evidence: `grouping_sets(...)` remains exported only as a reserved helper that fails through backend capability
  checks.
- Observation: Post-aggregate `having(...)` needs a distinct aggregate-output predicate scope.
  Evidence: Metric-local filters lower cleanly as `F.when(...)` inside aggregates, while `having(...)` would otherwise
  blur pre-aggregate and post-aggregate expression scopes.

## Decision Log

- Decision: Keep the first Sprint 08 analytical surface stable and add advanced features as a second Sprint 09 lane.
  Rationale: The first slice has implementation, tests, docs, and generated fixtures. Reopening those semantics would
  risk regressions; broader support can extend the IR and recipes additively.
  Date/Author: 2026-07-05 / Codex.
- Decision: Require explicit window frames for broad aggregate window helpers.
  Rationale: Spark defaults can be subtle, especially with range frames and ordered aggregates. Explicit frames keep
  generated code reviewable and explain output meaningful.
  Date/Author: 2026-07-05 / Codex.
- Decision: Treat advanced grouping and broad windows as batch-only in v2.
  Rationale: Streaming requires watermark, state, late-data, and output-mode contracts that belong to v3 streaming
  orchestration.
  Date/Author: 2026-07-05 / Codex.
- Decision: Reject arbitrary Python in HOF callbacks rather than generating UDFs or row-wise functions.
  Rationale: Structure's core promise is Spark-plan-visible compiled transforms. HOF callbacks must remain symbolic.
  Date/Author: 2026-07-05 / Codex.
- Decision: Ship `grouping_sets(...)` and `having(...)` as deferred capability boundaries rather than partial
  semantics.
  Rationale: Both features need contracts that are more specific than the rest of the advanced analytical surface:
  grouping sets need explicit level lowering, and having needs aggregate-output predicate binding. Capability-gating is
  safer than accepting source that renders misleading Spark code.
  Date/Author: 2026-07-05 / Codex.

## Outcomes & Retrospective

The admitted Sprint 09 advanced analytical lane now compiles through IR, backend capabilities, shared PySpark recipes,
online execution, generated PySpark rendering, traceability, and the public API snapshot. The implemented surface
includes rollup/cube grouping, grouping metadata helpers, Boolean/statistical/approximate/collection aggregates,
metric-local filters, deterministic ordered first/last aggregates, reusable explicit windows, broad ranking/value/window
aggregate helpers, and additional symbolic array/map HOF helpers.

Two features from the original design remain intentionally deferred: arbitrary `grouping_sets(...)` lowering and
post-aggregate `having(...)`. Both are documented as capability boundaries rather than silent partial behavior.

## Context and Orientation

Structure is a Python-to-PySpark runtime compiler. Users write `Structure` schema classes and `Transform` classes.
Compiled subtransform methods are symbolically executed into an intermediate representation, then lowered to online
PySpark execution or generated PySpark source.

The first analytical slice is already implemented. Relevant files include:

- `src/structure/app/dsl/model/transforms/reserved_v2.py`: public helper constructors such as `group_by(...)`,
  selected-row helpers, rolling helpers, duplicate-removal helpers, and HOF helpers.
- `src/structure/app/compiler/ir/model`: IR models for operations and expressions.
- `src/structure/app/target/pyspark`: shared PySpark lowering, generated rendering, and online recipes.
- `src/structure/app/compiler/traceability`: static dataflow and provenance reporting.
- `src/structure/app/compiler/compileability/streaming_compatibility`: streaming compatibility classification.
- `res/testing/model/v2/orders`: v2 source and generated fixture examples.
- `docs/dev/specifications/AdvancedAnalyticalOperations.md`: implementation contract for this plan.
- `docs/reference/AdvancedAnalyticalOperations.md`: public behavior reference.
- `docs/dev/project-management/sprints/done/Sprint09_OptimizationExplainDocsTooling.md`: sprint charter carrying this work.

Terms used in this plan:

- A grouping operation changes many input rows into fewer summary rows.
- A window expression calculates a value over a partition of rows while preserving the original row count.
- A higher-order function, or HOF, is a collection helper that accepts a symbolic callback over array or map elements.
- Online execution means Structure directly applies PySpark operations at runtime.
- Generated execution means Structure writes PySpark source that a project can import and run.

## Plan of Work

Milestone 1 adds advanced grouping. Extend the DSL with `rollup(...)`, `cube(...)`, `grouping_sets(...)`,
`grouping_id()`, and `is_grouped(...)`. Add IR nodes for grouping kind and levels. Lower supported PySpark profiles
through shared recipes. Add diagnostics for unnamed expression keys and non-nullable subtotal output fields. At the
end of the milestone, v2 fixtures should compile to visible `rollup`, `cube`, or grouping-set PySpark operations.

Milestone 2 adds advanced metrics. Implement Boolean, statistical, approximate, collection, deterministic first/last,
filtered aggregate, and `having(...)` semantics from the specification. Start with the smallest PySpark-supported
subset that still proves every contract shape, then expand helper by helper. Each helper needs type/nullability checks,
backend capabilities, generated rendering, online execution, traceability, explain output, and negative diagnostics.

Milestone 3 adds reusable windows and broad window expressions. Implement immutable `window(...)` specs, row/range
frame builders, explicit order descriptors if needed, ranking distribution helpers, value helpers, and window aggregate
helpers. Add batch-only streaming classification and diagnostics for invalid range frames, missing frames, and
ambiguous tied ordering.

Milestone 4 adds advanced HOF helpers. Implement additional array and map helpers with symbolic callback capture.
Reject unsupported Python callback behavior before lowering. Add target capability checks for helpers that are not
available in every configured PySpark profile or Spark Connect variant.

Milestone 5 integrates explain, traceability, docs, and examples. Compact explain must stay readable; expanded explain
must show grouping levels, metric filters, window partition/order/frame dependencies, and HOF callback lineage. Update
QuickRef, public reference docs, diagnostics links, user stories, v2 fixtures, and generated snapshots.

## Validation and Acceptance

Advanced grouping is accepted when an orders fixture can produce detail rows, subtotal rows, and grand totals with
schema-correct nullable subtotal fields and explain output that names grouping levels.

Advanced metrics are accepted when exact, statistical, approximate, filtered, collection, and deterministic first/last
metrics either compile and run online/generated with parity or fail early with capability diagnostics for unsupported
targets.

Broad windows are accepted when reusable `window(...)` specs and explicit frames render as Spark-visible window
expressions and online/generated execution produce equal row sets and schemas.

Advanced HOFs are accepted when symbolic callbacks compile to Spark-visible higher-order functions, and unsupported
Python callback behavior produces actionable diagnostics before runtime.

The full plan is accepted when `make build` passes and Sprint 09 records advanced analytical support as complete or
explicitly narrows the admitted helper list with rationale.

## Idempotence and Recovery

The plan is additive. Re-running tests and builds is safe. If API snapshot changes include unexpected exports, remove
the accidental exports instead of accepting the snapshot. If generated fixtures drift, inspect the diff and update only
intended generated output.

If a helper proves unsupported on a configured backend, keep the DSL helper only if it can fail with a clear backend
capability diagnostic. Otherwise leave the helper unexported and update this plan, the specification, and Sprint 09
notes with the reason.

## Interfaces and Dependencies

Use the existing DSL and recipe architecture. Do not import PySpark at module import time for public helper
constructors. Do not add a second execution path for online versus generated behavior. Each implemented operation must
share PySpark recipe lowering for online and generated modes.

New public helpers belong behind `structure` exports only after tests and documentation are in place. Internal class
names may differ from the names in this plan, but the behavior and public helper names must match the specification
unless the plan is updated first.
