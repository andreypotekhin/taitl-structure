# Unify lexical and vector scoring across Search

This ExecPlan is a living document. It follows `docs/dev/auto/Plans.md`; its `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections must be updated as implementation proceeds.

## Purpose / Big Picture

Search treats lexical scores as reusable scoring artifacts and request-search vector results as a scored lane. One shared
`Scoring` composition owns lexical and vector scoring, while `OfflineScoring` and `OnlineScoring` resolve both families.
`SearchDocuments` consumes ordinary `Document` rows plus score evidence. `SearchSimilarity` deliberately keeps a
separate provider-neutral ranked-candidate boundary so caller-owned exact or ANN producers can be swapped without
changing hybrid fusion or presentation.

The user-visible result is a consistent hybrid path: request search still performs lexical/vector RRF fusion and feedback reranking, and similarity search remains document-to-document while obtaining its query document embedding through the same vectorization boundary. The result is demonstrated by generated/online parity tests and `make build`.

## Surprises & Discoveries

- Observation: `DocumentVectorCandidate` was initially consumed directly by both `SearchDocuments` and `SearchSimilarity`, while `ScoreVectors` and `RankVectors` were separate from `Scoring`.
  Evidence: `examples/search/transforms/searching/search_docs/SearchDocuments.py` and `examples/search/transforms/searching/search_similarity/SearchSimilarity.py` declare `DocumentVectorCandidate`; `examples/search/transforms/scoring/lexical/Scoring.py` does not invoke vector scoring.
- Observation: `SearchSimilarity` initially had a corpus `Document` input but used it only during final reranking; vector admission bypassed that document relation.
  Evidence: the earlier `SearchSimilarity.py` passed `document_vector_candidates` to `AdoptVectorSimilarity`, while `RerankSimilarity` received `documents` later.
- Observation: the current vector score schema has no scoring timestamp, so it cannot participate in the same freshness contract as lexical score caches.
  Evidence: `DocumentVectorScore` and `ParagraphVectorScore` contain model/index identity but no `scored_at`.
- Observation: generated Search output is source-derived and must be regenerated after source changes.
  Evidence: generated files begin with `Generated by Structure. Do not edit by hand.` and the repository build exposes `make gold`.
- Observation: the compiler requires composed inputs to use the exact declared relation schema, so provider-specific query relations are normalized to the shared `DocumentVectorQuery` relation at the vectorization boundary rather than relying on subclass covariance.
  Evidence: `VectorizeSearchQueries` and `VectorizeSimilarityQueries` emit the common normalized relation consumed by vector scoring.
- Observation: request-search vector retrieval should use the same document-candidate boundary as lexical retrieval; ranking and capping both lanes belongs in hybrid fusion.
  Evidence: `RetrieveDocuments` now joins raw `DocumentVectorScore` rows to `Document`, while `FuseDocuments` ranks/caps both candidate lanes before RRF.
- Observation: adding vector scoring to the shared scorer makes the complete `All` facade require explicit vector-query, vector-index, and vector-policy inputs.
  Evidence: `examples/search/transforms/all/all.py` now forwards those five inputs to `OfflineScoring`.
- Observation: ranking must happen after cached and online vector scores are reconciled.
  Evidence: independently ranked cache and online subsets cannot preserve one query-wide rank order; `OnlineScoring` now invalidates cached vector groups selected for online recomputation.
- Observation: the same candidate bound governs offline artifact generation and online hybrid serving, but the boundaries differ.
  Evidence: `All` retains standalone `RankVectors` for offline candidate artifacts, while online `FuseDocuments` applies `VectorIndexPolicy.maximum_candidates` to the vector lane and fused result.

- Observation: “similarity vector embedding” described the source query rather than the corpus/index side of the
  operation.
  Evidence: `SearchSimilarity` joins the provider row to `SimilaritySearchQuery` before scoring it against
  `DocumentVectorIndex`; the corrected names are `SimilarityQueryEmbedding` and the provider-neutral
  `DocumentVectorCandidate` boundary.

- Observation: the broad v7 source-label rename was incorrect because it changed expectations without changing transform
  declarations.
  Evidence: the parity test expected `similarity.values`/`similarity.attributes`, while lowering correctly reported
  `documents.values`/`documents.attributes`; restoring the declarations made all eight cases pass.

## Decision Log

- Decision: Move `Scoring` one level up and make it the shared lexical/vector composition.
  Rationale: vector scoring must participate in the same offline and online orchestration instead of being a bolted retrieval input.
  Date/Author: 2026-08-11 / user and Codex.
- Decision: Keep request-search and document-similarity vector query schemas separate.
  Rationale: request queries have a `SearchQuery` identity; similarity queries must preserve a source document identity for self-exclusion. One nullable overloaded schema would obscure that invariant.
  Date/Author: 2026-08-11 / user and Codex.
- Decision: Keep `SearchSimilarity` document-to-document.
  Rationale: similarity search has a distinct use case and must not collapse into request-time document search. Its query remains a source `Document`, and its corpus remains `Document` rows.
  Date/Author: 2026-08-11 / user and Codex.
- Decision: Remove legacy imports and caller interfaces rather than retaining compatibility shims.
  Rationale: the user explicitly authorized the interface migration, so stale lexical paths and direct vector-candidate inputs should be removed instead of preserved.
  Date/Author: 2026-08-11 / user.
- Decision: Keep model inference caller/provider-owned.
  Rationale: the Search example has no model runtime or network ownership. The new vectorization transform validates and normalizes provider-produced embeddings; persistent query-vector caching is a later stage.
  Date/Author: 2026-08-11 / user and Codex.
- Decision: Normalize both typed provider query relations into `DocumentVectorQuery` before scoring.
  Rationale: separate public/provider contracts preserve use-case invariants, while the compiler's exact relation typing keeps the vector scorer's implementation uniform and composable.
  Date/Author: 2026-08-11 / Codex.
- Decision: Rank raw vector scores in the dedicated `Ranking` composition before document retrieval, while similarity adoption continues to rank its raw scores at the document join.
  Rationale: `SearchDocuments` can use one explicit ranking stage and still join ranked evidence to `Document` rows; neither public presentation requires a caller-supplied candidate relation.
  Date/Author: 2026-08-11 / user and Codex.
- Decision: Keep raw `DocumentVectorScore` rows as the cache boundary and invalidate an entire query group when online vector scoring runs.
  Rationale: rank is global within a query; merging independently ranked cache and online rows can create duplicate or stale ranks. Re-ranking one authoritative merged score relation preserves contiguous deterministic ordering.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: Remove `RankVectors` from the online document-search workflow and rename `FuseDocumentCandidates` to `FuseDocuments`.
  Rationale: online vector scores should enter `RetrieveDocuments` as ordinary document candidates; `FuseDocuments` then owns lexical/vector ranking, lane bounds, deduplication, and RRF. Standalone `RankVectors` remains for offline candidate artifacts until those outputs are retired.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: Use query-oriented names for the similarity embedding and vectorization stage.
  Rationale: the embedding belongs to the source similarity query and is scored against the corpus vector index. The name
  must not imply that it is a document-index embedding or a separate search mode.
  Date/Author: 2026-08-12 / user and Codex.
- Decision: Use a parameterized, caller-replaceable similarity candidate-provider adapter modeled after Store's
  `Ranker`; the provider-neutral ranked candidate relation is the stable downstream contract.
  Rationale: example-app callers may freely subclass or replace the default exact provider, while Structure retains
  ownership of typed fusion, validation, and presentation rather than an ANN implementation.
  Date/Author: 2026-08-13 / user and Codex.
- Decision: Refactor `Inference` into a composed stage with separate provider-invocation and publication subtransforms.
  Rationale: it keeps adapter execution, embedding publication, and status publication focused and independently
  inspectable without moving persistence or cache ownership into Structure.
  Date/Author: 2026-08-13 / user and Codex.

## Context and Orientation

The Search example is under `examples/search`. Lexical index relations are produced under `transforms/indexing` and scored by `ScoreOverlap`, `ScoreBm25`, and `SelectScores`. The current composition is `transforms/scoring/Scoring.py`. Exact vector indexing, cosine scoring, and ranking are under `transforms/indexing/vector`, `transforms/scoring/vector`, and `transforms/ranking/vector`.

`OfflineScoring` selects a bounded query snapshot and calculates reusable scores. `OnlineScoring` detects missing or stale score groups and calculates only the gaps. `SearchDocuments` then retrieves documents from batch and streamed document/score lanes, fuses lexical and vector candidates with reciprocal-rank fusion (RRF), and applies feedback. `SearchSimilarity` accepts a source `SimilaritySearchQuery`, corpus `Document` rows, lexical similarity relations, provider-neutral ranked candidates, and a separate fusion policy. `ExactSimilarityCandidates` is the bundled exact reference producer; caller-owned ANN producers can replace it.

RRF is the existing rank-list fusion rule: a candidate contributes `1 / (rrf_k + rank)` for every lane in which it appears. Raw cosine and BM25 values must remain inspectable and must not be added as if they had the same scale.

## Plan of Work

### Milestone 1: Define query inference and vector-score contracts

Add separate typed relations for request-search vector queries and document-to-document similarity vector queries. Request queries are keyed by `SearchQuery.id`; similarity queries retain `query_id` plus `query_document_id`. Add the missing `scored_at` field to vector score relations so cached vector evidence can be validated against `ScorePolicy`.

Add pure `VectorizeSearchQueries` and `VectorizeSimilarityQueries` boundaries under `transforms/vectorization`. They accept text-bearing query rows and provider-produced embedding rows, validate one row per query and model/dimension/revision/experiment identity, and emit the appropriate typed vector-query relation. Do not add model SDK calls, network access, driver collection, or persistent cache behavior.

Update vector scoring so the common cosine/ranking implementation can serve both typed query contracts. Self-exclusion is required only for similarity queries and uses `query_document_id`; request search has no self target.

### Milestone 2: Make shared `Scoring` own both families

Move `Scoring.py` to `examples/search/transforms/scoring/Scoring.py`. Remove the old lexical `Scoring` module and update every source import. The new composition invokes lexical overlap/BM25 selection and vector scoring, exposing raw lexical scores, selected lexical scores, and raw vector scores as typed outputs. Keep standalone vector ranking for offline candidate artifacts; online document ranking belongs to `FuseDocuments`.

Move the orchestration modules out of lexical-only namespaces where needed so their names and exports describe both score families. Update `OfflineScoring` to run vectorization and shared scoring for the bounded offline query set. Update `OnlineScoring` and gap selection to resolve both lexical and vector freshness, then expose both batch and streamed score outputs to callers.

### Milestone 3: Migrate `SearchDocuments`

Remove `DocumentVectorCandidate` from the public `SearchDocuments` inputs. Supply request vector queries, vector index relations, and policy to the online scoring boundary. `RetrieveDocuments` joins raw `DocumentVectorScore` rows to ordinary `Document` rows, and `FuseDocuments` ranks/caps vector candidates alongside lexical candidates.

Retain the existing lexical-only and hybrid semantics: vector-only documents may survive admission, RRF is computed before feedback, candidate bounds remain explicit, and final ties remain deterministic. Update `SearchFields` and experiment wrappers to pass the new score/inference inputs.

### Milestone 4: Migrate `SearchSimilarity` without changing its use case

Keep `SimilaritySearchQuery` as a source document and keep corpus `Document` input. Expose ranked
`DocumentVectorCandidate`/`ParagraphVectorCandidate` relations as the provider-neutral retrieval boundary. The bundled
`ExactSimilarityCandidates` composition performs similarity-query vectorization, exact scoring, and deterministic
ranking; `AdoptVectorSimilarity` normalizes those candidates into the internal fusion relation.

Apply the same document-plus-score shape to paragraph similarity where applicable. Add the future-compatible streamed-document inputs now if the transform contract permits it, but retain the repository’s existing batch-only execution gate until bounded streaming state is proven.

### Milestone 5: Regenerate, document, annotate, and validate

Update Search reference/background documents, scoring and similarity docs, schema registries, example-project registrations, tests, and annotated transform sources. Run `make gold` to regenerate PySpark output; never edit generated files directly. Run focused compiler and live Search tests followed by `make build`.

- lexical and vector score artifacts from the same `Scoring` composition;

- SearchSimilarity results that remain document-to-document, exclude the source document, preserve corpus `Document` metadata, and consume replaceable provider-neutral candidates;
- generated PySpark and online execution with equal rows, schemas, vector ranks, RRF scores, and deterministic ties.

All source edits are reversible through normal version control. Generated output must be regenerated from source with `make gold`; do not hand-edit generated files. If a generated test fails, correct the source transform or registry and regenerate. Do not reset unrelated working-tree changes.

## Interfaces and Dependencies

The shared scorer depends on existing lexical score transforms and `ScoreVectors`. Offline consumers may still compose
`RankVectors` for bounded candidate relations. Request-search vectorization emits a query-ID-keyed vector relation.
`ExactSimilarityCandidates` uses similarity vectorization through `SimilarityQueryEmbedding` and
`VectorizeSimilarityQueries`; caller-owned ANN producers may bypass that exact composition while preserving the ranked
candidate schema. Similarity-only vector scorers live under `scoring/similarity`; vector score rows carry score time and
compatibility identity.

No new runtime dependency is introduced. No model invocation, network client, ANN library, driver-side vector collection, or hidden cache is allowed.
