# Compile Delta table mutations inside transforms

This ExecPlan is a living document maintained under `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current at every stopping point.

## Purpose / Big Picture

A caller who already owns a Delta Lake table can pass its `delta.tables.DeltaTable` object to a Structure transform. The transform compiles typed delete, update, merge, and append helpers, checks the declared schema and native CHECK constraints, and returns the same table object as a named output. Schema changes remain prohibited unless the operation opts into evolution and its method returns the declared new Delta output schema. The caller continues to provision tables and constraints.

The first runtime claim is ordinary PySpark 4.1.0 with Delta Lake 4.1.0. Spark Connect remains unclaimed until separately evidenced. Delta is optional; importing Structure or compiling a transform must not import PySpark or Delta.

## Surprises & Discoveries

- Observation: `Transform.__init__` currently binds only input declarations, and the Core compiler requires at least one input and one output. PySpark steps require a row-schema return and lower to DataFrame-producing recipes. Evidence: `src/structure/core/dsl/model/transforms/Transform.py`, `src/structure/core/compiler/frontend/commands/CompileTransform.py`, and `src/structure/plugin/pyspark/compiler/logic/maps/MapPySparkStep.py`.
- Observation: A compiled, side-effecting SQL operation already exists, so mutation execution within a Transform has a precedent. Delta's Python `delete` and `update` return `None`, which cannot be treated as a DataFrame or reliable metric row. Evidence: `docs/dev/design/TypedSqlExecution.design.md` and Delta's public Python API.
- Observation: Adding a native CHECK validates existing rows and can upgrade the writer protocol. This plan only reads metadata and runs data mutations; it never installs checks. Evidence: Delta Lake constraint documentation.
- Observation: The project virtualenv has no PySpark package (`ModuleNotFoundError`), so Spark-free compiler tests run there. Optional PySpark/Delta packages installed into a separate temporary directory supplied the pinned live lane.
- Observation: PySpark's Core-to-plugin path requires a schema result for ordinary steps. Delta `None` returns are represented as effect steps with a synthetic result lane, while the mutation target remains a caller-bound table handle.
- Observation: The existing Docker store is full; a disposable 4.1 image build failed with `No space left on device`. A temporary host directory held the pinned Python packages without changing project dependencies. Delta Maven jars resolved successfully, and the live tests ran there.
- Observation: Delta 4.1 widened nullability when a table was initially created through a DataFrame write; explicit `NOT NULL` table DDL preserved the Structure shape contract. A native `DeltaTable` handle that had already materialized `toDF()` could keep showing the earlier snapshot after a delete. A freshly opened handle saw the commit.
- Observation: Delta's merge builder has an operation-scoped `withSchemaEvolution()` method, while `mergeSchema` is a DataFrame writer option for append/overwrite rather than a `DeltaTable` method. They need separate typed Structure surfaces and a named post-commit schema contract.
- Observation: Inferring a Delta result from the returned Schema requires analyzer support as well as symbolic capture; otherwise the compiler can capture the mutation yet lower it as a DataFrame projection. The analyzer now resolves a unique matching `delta_output` and marks the step as an effect.

## Decision Log

- Decision: Replace the proposed `DeltaTableWrapper.set_schema()` workflow with `delta_input(Schema)`, `delta_output(Schema)`, and compiler-visible mutation helpers. Rationale: compiling and running a transform is Structure's primary workflow; the caller supplies the native table. Date/Author: 2026-10-04 / user and Codex.
- Decision: Keep `Schema.constraints` and `check(...)` on the existing Schema type. Rationale: one schema can describe ordinary DataFrame rows and Delta table rows; only a Delta binding checks native metadata. Date/Author: 2026-10-04 / user and Codex.
- Decision: Same-schema Delta effect steps may return `None`. Explicit schema transitions return the `delta_output` Schema; this preserves ordinary effect syntax while using normal return-type resolution for the evolved result lane. Date/Author: 2026-10-04 / user and Codex.
- Decision: Support delete, update, append, and all data-mutation clauses of Delta 4.1.0's Python merge builder. Schema evolution requires an explicit `.with_schema_evolution()` and a distinct declared result schema; merge lowers to `withSchemaEvolution()`, append applies `mergeSchema` to one writer. Raw SQL and table administration remain excluded. Date/Author: 2026-10-04 / user and Codex.
- Decision: Verify table shape always. Default CHECK verification parses and compares supported expression trees, ignoring cosmetic SQL differences. `delta_check_match="name"` checks names only; `"off"` skips CHECK verification. Plugin configuration, `@transform`, and `@step` accept the option, with the nearest scope winning and the effective value captured in compiled metadata without a warning. Date/Author: 2026-10-04 / user and Codex.
- Decision: Refresh Structure's internal read frames from a newly opened Delta handle at the table location after each mutation. Return the caller's exact original handle, as promised; callers who previously materialized its DataFrame may need to reopen a handle to read the latest commit. Date/Author: 2026-10-04 / Codex, based on pinned live evidence.

## Context and Orientation

Structure declares row shapes through `src/structure/core/dsl/model/schemas/Schema.py`, transform bindings through `src/structure/core/dsl/model/transforms/`, and compiles methods in `src/structure/core/compiler/frontend/commands/CompileTransform.py`. PySpark symbolic authoring, target recipes, online execution, and generated rendering live under `src/structure/plugin/pyspark/`. A relation parameter is the symbolic row proxy supplied to a step method; it describes fields without loading a Spark DataFrame at compile time. An effect step is a compiled step that runs a side effect and has no row result. Existing steps must retain their current DataFrame behavior.

The old V11 Delta package is recorded in `docs/dev/planning/P08042602.V11-delta-schema-bound-mutations.plan.md`, `docs/dev/design/V11DeltaSchemaBoundMutations.design.md`, and `docs/dev/specifications/V11DeltaSchemaBoundMutations.spec.md`. Revise these documents and the V11 ledger rather than leaving conflicting claims. Do not overwrite unrelated working-tree changes. The Core plugin boundary carries opaque target payloads; Delta implementation belongs to the PySpark plugin, with only the minimal binding/effect distinctions added to Core.

## Plan of Work

First, update the paired V11 design and specification with a runnable-shaped example. Use `delta_input(Order)` for a caller-bound, read-only Delta relation and `delta_output(Order)` for a caller-bound mutable target. The invocation accepts native `DeltaTable` objects under both declaration names. Permit an output to serve as a step relation parameter when explicitly selected. An `@step(input=(changes, orders), output=orders)` method can return `None` after recording a Delta operation; the output records the target handle, not a DataFrame result. Keep ordinary input/output/step contracts unchanged. Require a target table scope for every mutation, and reject attempts to mutate a read-only Delta input or ordinary DataFrame input at compile time.

Next, implement immutable `check(predicate, *, name=None)` declarations in `Schema.constraints`. Resolve symbolic field tokens when Schema finalizes, validate Boolean predicates and referenced fields, and derive anonymous names deterministically from schema identity, the sole referenced field when available, and declaration order. Keep check metadata separate from shape-only Spark `StructType` generation. Reuse physical aliases. The PySpark plugin's Delta binding verifier reads table shape and CHECK properties; it performs no DDL. Parse the supported CHECK expression subset into trees and compare those trees after normalizing SQL keyword/function case, insignificant whitespace, and redundant grouping, while preserving literal values and respecting the session's identifier case policy. Unsupported stored syntax fails with a diagnostic recommending alignment or an explicit weaker comparison setting.

Then add the typed mutation helpers under the PySpark DSL. `delta_delete` and `delta_update` require explicit Boolean predicates; `delta_merge` captures ordered Delta 4.1 clauses; and `delta_append` represents append as a writer effect. Every operation preserves schema by default. `.with_schema_evolution()` explicitly enables only the builder or append writer option associated with that operation. The step returns the schema of a distinct declared `delta_output`, while taking the current `delta_input` as its relation parameter. Validate the post-commit schema and CHECK contract. Do not expose vendor builder objects or raw SQL strings.

Extend the Core binding plan only enough to distinguish DataFrame input, Delta input, and caller-bound Delta output, and to retain `None`-returning effect steps. Extend PySpark recipes with ordered, immutable Delta operations. Protect effect steps from pruning and mark them batch-only. Render generated code and online execution through the same late-bound Delta runtime helpers. Resolve native `DeltaTable` only when executing; reject a missing or incompatible optional runtime with an actionable diagnostic. Before any mutation, validate every Delta binding's shape and CHECK contract using the effective `delta_check_match` option. `"expression"` is the default; `"name"` requires matching names but skips predicates; `"off"` skips checks but still validates shape. Apply method overrides to the bindings used by that method. Preserve step order and execute each native operation once. Reacquire `toDF()` for any read after a table mutation. Return the exact caller-supplied output handle on successful completion; native failures remain catchable and earlier successful steps may have committed.

Finally, synchronize public imports, configuration validation, generated metadata, capabilities, diagnostics, API documentation, V11 milestone text, and the earlier plan's decision log. Keep Spark Connect design-gated until direct evidence exists. Do not add Delta as a core dependency.

## Artifacts and Notes

Expected public shape, subject to the normative specification:

    class SyncOrders(Transform):
        changes = input(OrderChange)
        orders = delta_output(Order)

        @step(input=(changes, orders), output=orders)
        def apply(self, change: OrderChange, order: Order) -> None:
            (delta_merge(order, change, on=order.id == change.id)
                .when_matched_update(set=Order(status=change.status))
                .when_not_matched_insert(values=Order(id=change.id, status=change.status))
                .execute())

    table = DeltaTable.forPath(spark, path)
    result = SyncOrders(changes=changes_df, orders=table).run(session)
    assert result.orders is table

For an intentional schema transition, the method return type selects its declared Delta result. The caller binds the
current table under `current_orders`; `orders` is the result lane and does not need a parameter in the method:

    class EvolveOrders(Transform):
        changes = input(OrderChangeV2)
        current_orders = delta_input(OrderV1)
        orders = delta_output(OrderV2)

        def merge(self, change: OrderChangeV2, order: OrderV1) -> OrderV2:
            return (delta_merge(order, change, on=order.id == change.id)
                    .with_schema_evolution()
                    .when_matched_update_all()
                    .when_not_matched_insert_all()
                    .execute())

Append uses `delta_append(order, change).with_schema_evolution().execute()` with the same return annotation and
post-commit output check. Without the explicit evolution call, mutations retain the current schema.

The example assumes a caller-created table with matching shape and native CHECK metadata. It does not create or alter the table. Relevant upstream sources are `https://docs.delta.io/releases/`, `https://docs.delta.io/delta-constraints/`, and `https://docs.delta.io/api/latest/python/spark/`.
