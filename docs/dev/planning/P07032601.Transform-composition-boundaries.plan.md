## Purpose / Big Picture

Structure supports transform reuse through inheritance, which is best when a child transform specializes one parent
pipeline shape. This plan adds composition for the other common case: run complete transform invocations one after
another and wire declared outputs into declared inputs.

The primary online shape is:

    result = (
        NormalizeOrders(orders=orders_df)
        .to(AddProduct(products=products_df))
        .to(PublishOrders())
        .run(session)
    )

The composed invocation returns the final stage's declared `output(...)` shape. Composition matches only declared
`output(...)` declarations to declared `input(...)` declarations. `lane(...)` remains internal implementation state and
is not a composition boundary. Inheritance keeps its existing exception: child overrides may reference inherited lanes
because they are modifying inherited implementation, not composing external transforms.

Generated execution needs source-time metadata, so generated-capable composition uses a named wrapper transform with one
pipeline field:

    @transform
    class OrderPipeline(Transform):
        orders = input(OrderRaw)
        products = input(Product)

        pipeline = Transform.to(
            NormalizeOrders(orders=orders),
            AddProduct(products=products),
            PublishOrders(),
        )

## Surprises & Discoveries

- Observation: `Transform.to(a, b, c)` can be implemented with the same ordinary instance method as
  `first.to(second, third)`.
  Evidence: In Python, calling an instance method through the class passes the first explicit argument as `self`.

- Observation: Stage hooks cannot be safely flattened in the first slice.
  Evidence: Hooks are methods on each source stage class, while a composed wrapper class or runtime pipeline is a
  different invocation object. The implemented slice rejects hook-bearing stages rather than silently dropping hook
  behavior.

- Observation: Class-field composition can reuse existing constructor binding.
  Evidence: `NormalizeOrders(orders=orders)` stores the wrapper class's `InputDeclaration` object as the stage input
  value; by compile time that declaration has its final class-field name.

## Decision Log

- Decision: Composition is instance-based: `NormalizeOrders(...).to(PublishOrders(...))`.
  Rationale: Users compose invocations with data bindings, not only transform classes.
  Date/Author: 2026-07-03 / Codex and project owner

- Decision: `Transform.to(a, b, c)` is the pipeline starter; do not add `from(...)`, `from_(...)`, `.pipe(...)`, or
  `.as_transform(...)`.
  Rationale: `from` is a Python keyword, `.pipe()` was not the desired vocabulary, and `.as_transform()` is unnecessary
  for online runtime chains.
  Date/Author: 2026-07-03 / Codex and project owner

- Decision: If a downstream input is explicitly bound in the constructor and also matches an upstream output, fail.
  Rationale: There should be no hidden precedence rule for whether the constructor value or upstream pipeline result
  wins.
  Date/Author: 2026-07-03 / Codex and project owner

- Decision: Generated-capable composition uses exactly one wrapper class pipeline field in the first slice.
  Rationale: Generated code needs import-time source metadata and a stable generated class name.
  Date/Author: 2026-07-03 / Codex and project owner

- Decision: Reject hook-bearing stage transforms in this slice.
  Rationale: Hook method ownership and generated/online dispatch need a dedicated design.
  Date/Author: 2026-07-03 / Codex

## Context and Orientation

The implementation touches the transform DSL, compiler frontend, and runtime session.

`Transform.to(...)` creates a `TransformPipeline` from one or more transform invocations. `TransformPipeline` stores
ordered stage invocations and flattens nested pipelines, so `a.to(b.to(c))` has the same stage list as `a.to(b, c)`.
The pipeline object exposes `.run(session)`, which delegates to `StructureSession.run(...)`.

`CompileTransform` now accepts either a normal transform class, a generated-capable wrapper class with one pipeline
field, or a runtime `TransformPipeline` object. The composition path compiles each stage class normally and then rewrites
their IR into one flattened `TransformPlan`.

`StructureSession.run(...)` detects runtime `TransformPipeline` objects and compiles the invocation object rather than
`type(invocation)`. Normal transform classes continue through the existing class-based path.

## Plan of Work

The implemented slice has these key behavior rules:

1. Every downstream stage input must be satisfied by exactly one source: a constructor argument on that stage, or a
   matching output from the immediately incoming stage.
2. Matching uses exact schema identity. If several upstream outputs have the same schema, a same-name output wins. If
   ambiguity remains, compilation fails.
3. Constructor binding plus upstream match is an error. The user must remove the constructor argument or break the
   pipeline.
4. `LaneDeclaration` values are rejected when used as constructor bindings in composed stages.
5. Class-field composition may bind stage constructor inputs to wrapper `input(...)` declarations. Runtime DataFrame
   values are not valid class-body bindings.
6. The final composed output contract is the final stage's declared outputs.

The first implementation intentionally does not support hook-bearing stage transforms, manually interleaving local
subtransforms with class-field pipelines, or exposing earlier-stage outputs as additional final outputs.

## Validation and Acceptance

Acceptance is met when all of these are true:

- `NormalizeOrders(orders=df).to(PublishOrders()).run(session)` returns a `TransformResult` with the final stage's
  output names.
- `a.to(b, c)` and `a.to(b).to(c)` compile to the same ordered flattened plan.
- `Transform.to(a, b, c)` works as the static starter.
- Downstream constructor inputs satisfy missing inputs, while constructor/upstream conflicts fail.
- Missing and ambiguous downstream inputs fail with clear diagnostics.
- `lane(...)` values cannot be used as composition bindings.
- A wrapper class with one `Transform.to(...)` pipeline field compiles and renders generated PySpark as one generated
  class.
- Existing transform inheritance override tests still pass.

## Idempotence and Recovery

All composition work is additive. Re-running tests is safe. The compiler path is deterministic: stage labels are
snake-case transform class names with numeric suffixes for repeats. If a generated rendering regression appears,
inspect the flattened `TransformPlan` first; online and generated execution both consume that shared plan.

If hook composition is needed later, create a follow-up plan that defines how the composed invocation owns or delegates
stage hook methods in both online and generated modes. Do not silently enable hooks without that design.
