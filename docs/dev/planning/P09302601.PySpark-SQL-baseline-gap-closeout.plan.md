# Close the PySpark SQL Baseline Gaps and Boundaries

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` sections as work advances. It follows `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

The public SQL Functions section in `docs/APICatalog.md` currently has several `partial` families. A user can see that
a family is incomplete, but cannot yet tell which missing PySpark functions are straightforward implementation work and
which require a separate design, target profile, provider, or caller-owned boundary.

This plan targets PySpark parity to help users migrate PySpark code. It will reconcile the PySpark 3.5.x/4.0.x baseline
inventory, preserve PySpark semantics where Structure can own a typed transformation, implement the remaining functions
that fit that model, and give every other function an explicit remedy. A completed slice must be observable through a
typed public helper, generated PySpark, online execution, and documented capability evidence; a gated slice must explain
exactly why it is not admitted.

The default baseline is ordinary PySpark `>=3.5,<4.1`. PySpark 4.1 additions, including newer random helpers, remain in
their separate adoption ledger. `expr(...)` and `call_function(...)` are not fallback implementation targets because
arbitrary SQL strings would bypass Structure's typed expression boundary.

## Surprises & Discoveries

- Observation: Ordering descriptors are implemented, but the implementation and consumer contracts are not identical.
  `Expression` exposes all six direction/null-placement variants; typed windows and relation ordering consume them,
  while some ordered aggregates and selected-row helpers intentionally accept narrower forms.
  Evidence: `src/structure/plugin/pyspark/dsl/Expression.py`, `src/structure/plugin/pyspark/dsl/operations_api.py`,
  `docs/api/Windows.api.md`, and the ordered-window rendering tests.

- Observation: The public catalog had omitted supported scalar assertion helpers even though the inventory,
  implementation, API reference, and tests already admitted them.
  Evidence: `functions.assertion` in
  `src/structure/plugin/pyspark/resources/pyspark-transformation-coverage.json` and `docs/api/Expressions.api.md`.

- Observation: The historical SQL-function coverage plan already delivered most deterministic numeric, string,
  collection, JSON/CSV, aggregate, and predicate slices. The remaining work is primarily reconciliation, contract
  closure, and a smaller set of higher-risk families.
  Evidence: completed entries and remaining-work notes in
  `docs/dev/planning/P08222601.PySpark-SQL-function-coverage.plan.md`.

- Observation: PySpark requires `to_binary` and `try_to_binary` format literals to be lowered as `F.lit(...)`; a bare
  Python string is interpreted as a column name.
  Evidence: ordinary PySpark 3.5 and 4.0 live parity tests for the binary slice.

## Decision Log

- Decision: Use `docs/dev/Parity.md` and
  `src/structure/plugin/pyspark/resources/pyspark-transformation-inventory.json` as the detailed baseline authority,
  with `docs/APICatalog.md` as the public family summary and
  `docs/dev/gaps/PySpark-SQL-baseline.gaps.md` as the function-level migration register.
  Rationale: The public catalog is intentionally concise; parity work needs one row per PySpark function with its
  Structure equivalent, evidence path, and caller remedy.
  Date/Author: 2026-09-30 / Codex.

- Decision: Treat PySpark parity as semantic parity, not only name parity. Preserve the PySpark spelling and argument
  behavior when Structure owns the operation; otherwise record the typed equivalent and an explicit migration remedy.
  Rationale: The register exists to help migrate PySpark code without implying that Structure must expose raw SQL or
  arbitrary runtime behavior.
  Date/Author: 2026-09-30 / Codex.

- Decision: Treat a function as an implementation candidate only when its result type, nullability, literal arguments,
  cardinality, determinism, target profile, and streaming classification can be stated without raw SQL or arbitrary
  Python callbacks.
  Rationale: These are the boundaries that make a Structure expression compiler-visible and explainable.
  Date/Author: 2026-09-30 / Codex.

- Decision: Keep XML/URL/provider, Variant mutation, and unresolved partition/generator shapes gated until their missing
  semantics are designed and evidenced. Current-time, AES-GCM, and baseline HLL/Bitmap now have typed designs and
  implementation contracts; live target evidence remains a release gate.
  Rationale: These functions carry time, security, provider, state, schema, or cardinality obligations that cannot be
  inferred safely from a simple scalar function call.
  Date/Author: 2026-09-30 / Codex.

- Decision: Keep `expr`, `call_function`, raw `Column.over`, arbitrary callbacks, UDTFs, and non-scalar UDF forms as
  explicit unsupported or caller-owned boundaries rather than implementation milestones.
  Rationale: They bypass or replace the typed compiler contract instead of extending it.
  Date/Author: 2026-09-30 / Codex.

- Decision: Admit the six default-baseline current-time spellings as typed query-clock candidates. They are
  non-null, query-stable, and nondeterministic; `current_timezone()` is a separate session-configuration read.
  Rationale: This preserves the PySpark migration path while making same-query equality explicit without promising
  equality across executions, retries, or streaming micro-batches.
  Date/Author: 2026-10-01 / Codex and user.

- Decision: Design AES-GCM as a typed Structure equivalent, rather than reproduce every PySpark AES form. Keys are
  symbolic String or Binary expressions, Python key literals are rejected, and an explicit Binary IV emits a warning.
  CBC, ECB, padding selection, and untyped forms remain caller-owned native-PySpark remedies.
  Rationale: The GCM-only API preserves a common secure migration path without treating source-controlled literals or
  weaker cipher modes as ordinary typed transformations.
  Date/Author: 2026-10-01 / Codex and user.

- Decision: Keep runtime JSON schema inference caller-owned. Structure continues to require declared schemas for
  `from_json` and `json_tuple`.
  Rationale: Runtime data cannot add compiler-visible fields or change an output Schema after symbolic compilation.
  Date/Author: 2026-10-01 / Codex and user.

- Decision: Build a shared opaque sketch-type model in stages: HLL and Bitmap on the default baseline; KLL and Theta
  on their PySpark 4.1 profile; and Observation metrics as a later, separate side-channel design. Count-Min remains
  caller-owned until Structure owns a typed consumer.
  Rationale: Branded values preserve migration convenience and prevent opaque serialized state from being confused
  with ordinary Binary while keeping version-specific functionality out of the baseline claim.
  Date/Author: 2026-10-01 / Codex and user.

## Context and Orientation

`docs/APICatalog.md` is the user-facing family summary. `docs/dev/Parity.md` is the detailed parity and boundary
register. `src/structure/plugin/pyspark/resources/pyspark-transformation-inventory.json` lists the reviewed PySpark
surface, while `pyspark-transformation-coverage.json` records Structure support claims. The streaming coverage files
classify whether admitted operations may receive streaming input. The table-based
[baseline gap register](../gaps/PySpark-SQL-baseline.gaps.md) records function-level migration parity.

Row-local SQL functions are normally represented by `Expression(kind="call")` in
`src/structure/plugin/pyspark/dsl/expressions.py` and lowered by `RenderPySparkExpression.py` and
`EvaluatePySparkExpression.py`. Grouped aggregates, windows, relation operations, and row-expanding generators use the
corresponding APIs in `operations_api.py`, `relation_sets.py`, and the generator modules. Public names are re-exported
through `src/structure/plugin/pyspark/__init__.py`.

An implementation candidate is a function that can be validated before Spark runs. Its contract must name accepted
Structure types, result type, nullability, literal-only arguments, row cardinality, deterministic or nondeterministic
behavior, supported PySpark profiles, and streaming status. A design-gated item is not a promise of future support; it
is an explicit hold until those obligations are resolved.

## Current Partial-Family Disposition

The following disposition is the working scope. The first milestone must replace family-level descriptions with exact
function names verified against the baseline inventory.

The working intake is maintained in the table-based
[PySpark SQL baseline gap register](../gaps/PySpark-SQL-baseline.gaps.md). Its implementation-candidate and
design-gated tables are the review surface for migration parity; this plan owns the sequence and acceptance criteria.

Normal, conditional, predicate, and sort functions have no current baseline implementation gap. Ordering descriptors
and scalar assertions are already implemented. `expr` and `call_function` remain unsupported because they erase the
typed expression boundary; ordering still needs uniform operand and consumer validation.

String functions have no remaining default-baseline UTF-8 slice: validation helpers are PySpark 4.0-only and are
target-gated. Random-string helpers belong to the random and target-profile decision. Any helper with version-specific
UTF-8 behavior remains outside the default baseline until a target profile is admitted.

Random and seeded functions have no unclaimed default-baseline slice until the inventory confirms a common 3.5/4.0 API
beyond `rand` and `randn`. `uniform`, `randstr`, UUID-style helpers, and newer random APIs require target/version,
seed, nondeterminism, and streaming contracts; newer-profile items stay in the PySpark 4.1 ledger.

Date and timestamp functions have implemented `from_unixtime` for numeric epoch seconds, `unix_timestamp` for typed
parsing plus its query-time default, typed UTC conversion helpers, and `date_part`/`datepart`. Remaining timezone
conversion, day/name extraction, date/timestamp constructors, and safe `try_*` temporal conversions are
implementation candidates after exact signatures are reconciled. Current-time now has
a typed query-clock contract: `current_date`, `curdate`,
`current_timestamp`, `now`, and `localtimestamp` are query-stable nondeterministic expressions, while
`current_timezone` reads the active session configuration. NTZ/LTZ and interval-sensitive constructors require explicit
target and nullability rules before admission.

Bitwise and binary functions have implemented `to_binary` and `try_to_binary` with literal `hex`, `utf-8`, `utf8`, and
`base64` formats. UTF-8 validation helpers are PySpark 4.0-only and target-gated. AES-GCM is a typed-equivalent
candidate with symbolic keys, optional AAD, and an optional Binary IV that
warns when caller-managed. Other encryption modes, padding selection, and raw key forms remain caller-owned.

JSON and CSV functions have no current implementation candidate beyond the declared-schema `json_tuple` slice delivered
in [P09302602](P09302602.PySpark-json-tuple.plan.md). Dynamic schema inference is caller-owned because it cannot change
a compiled Structure Schema.

String aggregation is PySpark 4.0-only and therefore target-gated for this closeout. If admitted by a versioned target,
its contract must define delimiter, null, order, empty-input, and streaming rules. Baseline HLL/Bitmap aggregates are
implemented; KLL/Theta remain profile-gated.

Windows have no clear baseline gap beyond exact inventory reconciliation; typed window forms already cover the admitted
ranking, selection, and aggregate shapes. Raw `Column.over` and unadmitted window functions remain unsupported.
Ordering variants must follow the consumer matrix below.

Generators and partition transforms have `stack` and equivalent typed generator forms as candidates if output schema and
row cardinality are explicit. Generic generator spellings and `years`/`months`/`days`/`hours`/`bucket` partition
transforms require cardinality, schema, alias, and streaming contracts.

Variant has no default-baseline implementation candidate. `is_valid_variant` is profile-gated; Variant mutation
helpers are reserved for a released target profile and remain design-gated.

XML, URL, and provider/runtime functions have no implementation candidate. XML, URL, geometry-provider, runtime
metadata, reflection, encryption, and sketch/bitmap integrations require separate contracts or remain caller-owned.

The disposition is deliberately conservative. A candidate moves to implementation only after the inventory milestone
verifies that it belongs to the default baseline and that the function has a stable public PySpark spelling in both
target lines.

## Ordering-Descriptor Contract Plan

The six descriptors are `asc()`, `desc()`, `asc_nulls_first()`, `asc_nulls_last()`, `desc_nulls_first()`, and
`desc_nulls_last()`. Each must wrap an orderable scalar expression, preserve the underlying value type and nullability,
record direction and null placement, and render to the corresponding public PySpark Column method.

The consumer matrix is part of the contract. `order_by(...)`, `repartition_by_range(...)`, and typed windows accept
direction and null placement. `collect_list(order_by=...)` currently accepts only `asc()` and `desc()`. Selected-row
helpers and join deduplication helpers choose their own direction and reject pre-decorated descriptors. Relation
ordering
and bounds are batch materialization boundaries; a descriptor inside an admitted row-local or window operation is not
itself a streaming state operation.

Implement validation consistently rather than allowing a pre-decorated `kind="order"` expression to bypass the
orderable-scalar rule. Add focused tests for all six variants, invalid base types, every consumer, generated rendering,
online evaluation, and the intended rejection messages. Update `docs/api/Expressions.api.md`, `docs/api/Windows.api.md`,
`docs/api/Relations.api.md`, the parity register, and both relevant coverage ledgers after the behavior is fixed.

## Plan of Work

### Milestone 1: Produce the exact baseline inventory diff

Read the PySpark 3.5.x and 4.0.x public function inventories represented by the repository policy. For each name in the
intersection, locate its Structure export, implementation, renderer/evaluator branch, API reference, capability row,
streaming row, and tests. Record missing names explicitly instead of inferring them from family prose. Confirm that
`uniform`, `randstr`, newer UTF-8 helpers, and other PySpark 4.1 additions are not silently counted as default-baseline
work.

The result is the table-based [baseline gap register](../gaps/PySpark-SQL-baseline.gaps.md), linked from
`docs/dev/Parity.md`. Every function receives exactly one status: implemented, candidate, design-gated, target-gated,
streaming-ineligible, caller-owned-guided, or unsupported. Each row also records PySpark 3.5.x and 4.0.x presence,
Structure equivalent, evidence, and migration remedy.

### Milestone 2: Close ordering contracts

Update the shared ordering validation so descriptor construction and all consumers agree on the orderable scalar domain.
Preserve existing valid generated source. Decide explicitly whether `collect_list` should remain limited to `asc`/`desc`
or accept null-placement descriptors; retain the narrower behavior if it matches the intended cross-version contract and
document it. Add tests before changing the catalog status again.

### Milestone 3: Implement deterministic temporal and binary candidates

Implement the reconciled timezone, constructors, and safe temporal-conversion functions
through shared typed helpers. Validate formats, units, time zones, component ranges, target-specific timestamp types,
and
nullable results at authoring time where the DSL owns the argument. Then implement `to_binary`, `try_to_binary`, and
common UTF-8 validation/conversion helpers only under a separately admitted target profile with explicit format and
failure semantics.

For each slice, update public exports, symbolic construction, renderer, evaluator, capability registration, API
reference,
ordinary transformation coverage, streaming classification, and focused semantic/rendering tests. Use live PySpark
evidence before making a stronger Connect or streaming claim.

### Milestone 4: Implement aggregate and generator candidates

If the baseline inventory confirms string aggregation, add the smallest typed aggregate slice first. Define delimiter
type, null skipping, empty-input result, ordering, tie behavior, aggregate state, and streaming output-mode constraints.
Add `stack` only through an explicit output Schema or equivalent typed result declaration; test zero rows, null inputs,
row multiplication, output field names, aliases, generated code, and online/generated parity.

Do not add generic raw generator or partition-transform aliases merely to reduce the visible gap. If a typed result
cannot
explain its schema or cardinality before execution, move the item to the design-gated register with a caller remedy.

### Milestone 5: Close design and target boundaries

Move every non-candidate into the table-based [baseline gap register](../gaps/PySpark-SQL-baseline.gaps.md) and link it
from the owning gate or deferred document with the exact missing contract. Current-time, AES-GCM, and baseline HLL/Bitmap
now have typed equivalents; dynamic JSON inference is caller-owned; KLL/Theta remain profile-gated and sketch live
evidence is pending. The unresolved list includes generic generators and partition transforms, Variant
mutation, XML/URL/provider/runtime integrations, and any NTZ/LTZ or interval behavior not proven on the target profile.

Keep `expr`, `call_function`, raw `Column.over`, arbitrary callbacks, UDTFs, pandas UDFs, and custom runtime types
explicitly unsupported or caller-owned where the existing boundary already says so. Target-gated newer functions belong
in
the PySpark 4.1 adoption ledger, not in the default baseline implementation count.

### Milestone 6: Synchronize evidence and close the register

For every status change, update the gap table first, then `docs/APICatalog.md`, `docs/dev/Parity.md`, the relevant table
in `docs/dev/gated/Functions.gates.md` or `docs/dev/deferred/ApiCatalog.deferred.md`, the relevant API reference, the
machine-readable transformation and streaming ledgers, public exports, diagnostics, and tests. Add a consistency test
that rejects missing or duplicate baseline dispositions and detects a catalog row that names a helper absent from the
public API or coverage ledger.

## Validation and Acceptance

The inventory milestone is accepted when every default-baseline PySpark function has exactly one row in the gap
register,
including PySpark 3.5.x/4.0.x presence, Structure equivalent, status, evidence, and migration remedy. The row must
match `docs/dev/Parity.md` and `docs/APICatalog.md`. No PySpark 4.1-only function may increase the default-baseline
implementation count.

The ordering milestone is accepted when all six descriptors render and evaluate consistently for valid scalar keys,
invalid operand types fail before Spark execution, and each consumer either accepts the descriptor or reports its
documented narrower contract.

An admitted function is accepted only when a typed transform compiles without Spark, renders the expected public PySpark
call, executes online with expected values and null behavior, and matches generated execution on every claimed target.
Generators additionally require row-count and schema assertions; aggregates additionally require empty-input, null,
order, state, and output-mode tests; nondeterministic or target-gated functions require explicit seed/profile evidence.

The closeout is accepted when `make build` succeeds, focused compatibility tests pass, available PySpark 3.5/4.0 and
Connect evidence is recorded, and every remaining design-gated or unsupported item has a precise reason and PySpark
migration remedy.

## Idempotence and Recovery

## Interfaces and Dependencies

Use the existing `Expression` model and Structure type classes. Row-local helpers should reuse the existing typed call
representation and shared argument/result-type functions. Aggregates must use the existing aggregate planner. Windows
must use the typed `WindowSpec`. Generators must expose schema and cardinality through the existing typed generator
boundary. Capability checks must use the repository's backend capability registry, and generated code must call public
`pyspark.sql.functions` APIs.

The default support claim remains ordinary PySpark `>=3.5,<4.1`; Spark Connect and Structured Streaming claims are
separate evidence classifications. Do not import private Spark internals or accept arbitrary SQL strings to close a
catalog row.
