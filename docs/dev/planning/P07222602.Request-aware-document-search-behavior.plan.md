# Add Request-Aware Document-Search Behavior Evaluation

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. Maintain this document according to `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

The Search example records individual displayed documents and clicks, but it cannot currently say which documents belonged to the same search request. Consequently, it cannot measure a request with no results, a request with no satisfying click, or the rank of the first satisfying result. After this work, callers will record one `SearchRequest` event for every search attempt, including attempts that return no documents, and every displayed `Impression` will refer to that request.

The new `EvaluateDocumentSearchBehavior` transform will consume a daily request batch with its impressions and clicks. It will produce one behavior row per request and a daily summary for each ranking version. The summary reports observed engagement and propensity-adjusted exposure metrics. It is a fully automated operational monitor, not a substitute for relevance evaluation. The separate plan `docs/dev/planning/P07222601.Judged-document-search-evaluation.plan.md` remains the quality anchor based on explicit relevance judgments.

## Surprises & Discoveries

- Observation: `Impression` identifies one displayed document but not the result list that contained it.
  Evidence: `examples/search/schemas/clicks.py` currently declares `id`, `shown_at`, query, document ID, position, and examination propensity only.

- Observation: `DailyImpressions` and `DailyClicks` intentionally aggregate away the identity needed for request-level behavior metrics.
  Evidence: their grouping keys retain date window, normalized query, document, position, and propensity, rather than an impression or request ID.

- Observation: the example already records an examination propensity on each impression.
  Evidence: `Impression.examination_propensity` is required and existing relevance signals use it to calculate inverse-propensity-weighted evidence. It can therefore support an exposure-level adjusted behavior rate without estimating a new position curve.

## Decision Log

- Decision: Add a required `SearchRequest` event for every search attempt, even when it returns no results.
  Rationale: impressions exist only for displayed documents. Without a request event, zero-result rate and all request-level denominators omit failed searches.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Add required `search_request_id` to `Impression` and required `ranking_version` to `SearchRequest`.
  Rationale: the request ID reconstructs the actual result list, while the version lets daily summaries remain comparable as the live ranking policy changes. The version belongs to the request because all documents displayed for that request came from the same ranking run.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Keep query text on `Impression` even though `SearchRequest` also records it.
  Rationale: the existing streaming feedback transforms consume impressions independently and use their query field as an aggregation key. Keeping it avoids a stream-stream request join and preserves the current feedback boundary. The serving caller must emit the same raw query on both events.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Define satisfaction as one or more attributed clicks with dwell time of at least ten seconds.
  Rationale: this reuses the Search example's current `long_click_count` contract and avoids treating every exploratory click as success.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Publish a daily behavior monitor, not automated relevance scores.
  Rationale: clicks and dwell describe observed interaction with the served result list. They are affected by exposure, presentation, and user intent, so they must not be named Precision, Recall, MRR, or relevance truth.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Defer A/B experiment comparison, interleaving, counterfactual policy evaluation, and session reformulation metrics.
  Rationale: these require experiment-arm or result-ownership logging, randomized exploration probabilities, or session identity. Adding them now would obscure the focused request-behavior contract.
  Date/Author: 2026-07-22 / user and Codex.

## Context and Orientation

The Search example is under `examples/search/`. `examples/search/schemas/clicks.py` defines raw `Impression` and `Click` events plus daily aggregate schemas. `examples/search/transforms/clicks/Impressions.py` and `examples/search/transforms/clicks/Clicks.py` are streaming-compatible transforms that watermark, deduplicate, and aggregate those raw events. `examples/search/transforms/relevance/Signals.py` converts the durable daily aggregates into feedback signals for reranking. Callers own event ingestion, streaming lifecycle, checkpointing, and persistence.

An impression is one document shown in a ranked result list. A click is an engagement event associated with one impression. A search request is the one user attempt that produced the whole list, including an empty list. A long click is an attributed click whose nonnegative dwell time is at least ten seconds. A ranking version is a nonempty caller-owned identifier such as a model or configuration version; all requests reported in one daily behavior summary share a version value.

The public transform facade for the planned evaluation family is `examples/search/transforms/evaluate.py`. Internal implementation belongs under `examples/search/transforms/evaluation/search_docs/behavior/`. Keep the public class in a focused module such as `EvaluateDocumentSearchBehavior.py`, and re-export it from the facade. The existing Search generated-project registries are `tests/integration/pyspark/search/test_search.py` and `tests/helpers/example_projects.py`. Generated files under `examples/structure_generated/search/` are outputs and must never be edited by hand.

## Interfaces and Dependencies

Extend `examples/search/schemas/clicks.py` with this raw event:

- `SearchRequest` has required `id: string`, `requested_at: timestamp`, `query: string`, and `ranking_version: string`. `id` is unique for one serving attempt. `ranking_version` is nonempty and caller-owned. The caller writes one row even if the search returns no documents.

Extend `Impression` with required `search_request_id: string`. Its existing `id`, `shown_at`, query, document ID, one-based position, and `examination_propensity` fields remain. An impression's request ID must reference one `SearchRequest`; the caller emits matching query strings on both events. Do not add ranking version to `Impression`.

Add `search_request_id` and `ranking_version` to `DailyImpressions` and `DailyClicks` only if those durable feedback facts must preserve request/version dimensions after implementation inspection. The preferred design is to leave their aggregate grain unchanged: feedback continues to aggregate repeated query-document evidence across requests, while behavior evaluation consumes raw request-aware events before aggregation. If schema/compiler constraints require reusing daily facts, create new behavior-specific daily fact schemas rather than changing the feedback fact grain.

Create `examples/search/schemas/evaluation.py` if it does not already exist from the judged-evaluation plan. Reuse `EvaluationBatch`, whose one `TimeWindow` selects requests displayed during one UTC-aligned day. Add these behavior output schemas:

- `DocumentSearchRequestBehavior`: batch window, `search_request_id`, `ranking_version`, query, `result_count`, `clicked_result_count`, `long_clicked_result_count`, `has_click`, `has_long_click`, nullable `first_click_rank`, nullable `first_long_click_rank`, and non-null `reciprocal_first_long_click_rank`. The reciprocal field is zero when the request has no long click, including a zero-result request.
- `DailyDocumentSearchBehavior`: batch window and ranking version; request, zero-result-request, resultful-request, clicked-request, long-clicked-request, no-click-request, and no-long-click-request counts; raw click and long-click counts; mean first-click and first-long-click rank among requests that have the respective event; mean reciprocal first-long-click rank across every request; and exposure-level `ips_long_click_rate` plus `ips_dwell_credit_per_impression`.

Implement public `EvaluateDocumentSearchBehavior` with inputs `batch: EvaluationBatch`, `requests: SearchRequest`, `impressions: Impression`, and `clicks: Click`. It outputs `request_behaviors: DocumentSearchRequestBehavior` and `daily_behavior: DailyDocumentSearchBehavior`. Inputs are a batch snapshot: `requests` must include the selected daily request window, and `clicks` must include events through 24 hours after those requests so late-but-attributable clicks can be joined. The transform must use the same attribution rule as `Clicks`: click impression ID equality and click time from impression display through 24 hours after it.

The behavior transform must be batch-only. It must deduplicate raw request, impression, and click IDs before joining. Reject duplicate request IDs with incompatible query or version values; reject an impression whose request does not exist in the selected request batch; and reject nonpositive propensities or positions. Use ordinary Structure/PySpark DSL expressions for joins and metric calculation. If a row-level contract cannot be enforced declaratively, use the narrowest supported validation mechanism and cover its error in tests.

## Plan of Work

### Milestone 1: Introduce request-aware raw events

Add `SearchRequest` and the `Impression.search_request_id` field. Update every Search event fixture, test import, schema registry, and generated schema to provide the new required values. Keep the preexisting Impression query value and document the invariant that it equals its request's query. The current `Impressions`, `Clicks`, and relevance transforms must continue to work without using request ID, demonstrating that behavior instrumentation is additive to feedback aggregation.

Extend `examples/search/Readme.md` event-contract section. Show the serving order: create one request event, produce zero or more impressions that share its ID, then record click events referring to individual impressions. State that no-result requests must be emitted and that a ranking version is immutable for a request.

### Milestone 2: Calculate request behavior

Create the `evaluation/search_docs/behavior/` package and implement `EvaluateDocumentSearchBehavior` in small, traceable stages. First select requests whose `requested_at` falls in `batch.window`; use the request as the outer population so zero-result requests survive. Join valid impressions by `search_request_id`, then join deduplicated clicks by impression ID within the 24-hour attribution interval.

For each request, count distinct displayed documents as `result_count`, distinct clicked impression documents as `clicked_result_count`, and distinct impression documents with at least one long click as `long_clicked_result_count`. `has_click` and `has_long_click` are those counts greater than zero. A request with no impressions has zero counts and false flags.

`first_click_rank` is the least displayed position with an attributed click. `first_long_click_rank` is the least displayed position with an attributed long click. Both are null when absent. `reciprocal_first_long_click_rank` is one divided by the first-long-click rank when present and zero otherwise. It is an observed user-behavior score, not offline relevance MRR.

Calculate exposure-level adjusted values after reducing clicks to one long-click flag per impression. For one displayed impression, its inverse propensity weight is `1 / examination_propensity`. The daily `ips_long_click_rate` is the sum of inverse-propensity weights for long-clicked impressions divided by the sum of weights for all impressions. Its `ips_dwell_credit_per_impression` is the sum of each attributed click's dwell credit, divided by its impression propensity, divided by the sum of all impression weights. Dwell credit is `min(max(dwell_seconds, 0), 60) / 60`, matching the existing click pipeline. Zero impressions produce null IPS exposure metrics, not zero.

### Milestone 3: Summarize behavior daily by ranking version

Group request behaviors by batch window and `ranking_version`. Rates use all requests in that version as their denominator: zero-result, no-click, no-long-click, clicked, and long-clicked request rates are count divided by request count. Retain counts as well as rates. First-click-rank means include only requests with a corresponding click; reciprocal first-long-click rank includes every request, so no-long-click requests contribute zero.

Aggregate the raw click and long-click counts separately from distinct clicked documents. A request may have multiple click events on one impression; the count fields expose that engagement while the boolean satisfaction fields remain request-level. Add output documentation that ranking-version comparisons are descriptive. A change in metric can reflect ranking quality, traffic mix, interface changes, or event-quality changes.

Re-export only `EvaluateDocumentSearchBehavior` from `examples/search/transforms/evaluate.py`. Keep judged evaluation and behavior as sibling public capabilities. Do not add counterfactual, experiment, interleaving, session, or relevance-judgment logic to this transform.

### Milestone 4: Publish and verify

Register all added schemas and transforms in `tests/integration/pyspark/search/test_search.py` and `tests/helpers/example_projects.py`. Regenerate Search PySpark output, traceability, and generated documentation from the source registrations.

Add online/generated parity coverage with one daily batch containing: a request with no impressions, a request with impressions but no clicks, a request with a click below the long-click threshold, a request with multiple clicks on one impression, a request with long clicks at different positions, and at least two ranking versions. Include a click after the 24-hour attribution limit to prove it is excluded. Assert request-level flags/ranks, version-specific daily counts/rates, IPS values using fixed propensities, and parity between direct and generated execution.

## Validation and Acceptance

The feature is accepted when a caller can emit a request event for an empty search and the evaluator returns a request behavior row with `result_count == 0`, false click flags, and zero reciprocal first-long-click rank. A caller can also provide a resultful request with a long click at position three and observe `first_long_click_rank == 3` and reciprocal rank approximately `1 / 3`.

For a fixed daily fixture with two ranking versions, the daily output must contain two summary rows. Each row's request counts and rates must match its per-request rows. The IPS long-click rate must change when only logged propensity changes, while raw request-level satisfaction does not. A late click outside the 24-hour window must not affect any result.

Existing streaming `Impressions`, `Clicks`, and `BuildRelevanceSignals` tests must still pass after the raw-event schema expands. Online and generated behavior outputs must be equal. Search generated schemas, transform docs, PySpark modules, and traceability must be current. Focused tests, generated-output tests, static checks, and `make build` must pass except for separately documented pre-existing failures.

## Idempotence and Recovery

All transformations are pure over caller-provided batch DataFrames. A caller can rerun the same request, impression, and click batch to reproduce the same outputs. Persisted daily behavior summaries should be keyed by batch window and ranking version; persistence and overwrite/upsert semantics remain caller-owned.

The raw schema expansion is intentionally breaking for callers that construct `Impression` rows. Update every fixture and documented producer in one change. If a partial change leaves stale generated files, repair the source schema/registry and rerun the renderer; do not patch generated artifacts. The worktree already contains unrelated active changes, so limit recovery to the behavior feature's files and preserve other modifications.

## Artifacts and Notes

The public invocation should have this shape:

    behavior = EvaluateDocumentSearchBehavior(
        batch=batch,
        requests=search_requests,
        impressions=impressions,
        clicks=clicks,
    ).run(session)

    by_request = behavior.request_behaviors
    daily_by_version = behavior.daily_behavior

The serving caller emits one `SearchRequest` even for a zero-result response. It emits every displayed result as an `Impression` with the same `search_request_id`; later it emits `Click` rows referring to individual impression IDs. It records enough click history to include the 24-hour attribution interval after the selected day.

Future facets remain deliberately out of scope. An experiment or interleaving evaluator needs an experiment arm and ownership of each displayed interleaved result. A counterfactual evaluator additionally needs randomized exposure or policy selection probabilities that provide support for candidate rankings. Session-based reformulation metrics need a stable session identifier. None of those fields are inferred by this request-behavior plan.
