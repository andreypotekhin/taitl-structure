# Admit the Delta table API on Spark Connect 4.1

This ExecPlan is a living document governed by `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as the work proceeds. The repository may contain staged and unstaged Delta work; inspect and preserve it before editing. Do not move this plan to `docs/dev/planning/past/` until the acceptance evidence below is complete.

## Purpose / Big Picture

A Structure user should be able to pass a native Delta Connect table handle to a transform targeted at PySpark `>=4.1,<4.2` with `variant = "spark-connect"`. The same typed Delta helpers that work on ordinary PySpark should compile, run remotely, and produce the same results in online and generated execution. This includes declared generated, identity, and default columns: Structure must verify their actual table metadata before allowing a write to omit them. A Connect client must never need direct access to the Spark server's JVM or storage.

The visible proof is a disposable Connect table with one generated column, one identity column, and one default column. Online and generated transforms bind it, reject a deliberately wrong metadata declaration before writing, then append or merge rows while Delta fills the declared columns. Other tests exercise delete, update, selective overwrite, snapshot/change-feed/history/detail reads, explicit schema evolution, restore, optimize, and vacuum. Unsupported target profiles fail during compilation with a diagnostic naming the helper, profile, variant, and remedy. Delta table creation, constraint installation, and streaming query lifecycle remain caller-managed.

## Surprises & Discoveries

- Observation: `src/structure/plugin/pyspark/delta/runtime.py` already shares most table operations between online execution and generated code, but `validate_delta_table` requires the classic `delta.tables.DeltaTable` class and `_delta_log_field_metadata` calls `spark._jvm` and `spark._jsparkSession`. The latter cannot run in a Connect client.
  Evidence: those functions, `RunOnlinePySparkTransform.py`, and `RenderPySparkTransformModule.py`.
- Observation: The pinned classic 4.1 test finds `delta.generationExpression` and `delta.identity.*` in Delta's log `schemaString`, while `DeltaTable.toDF().schema[field].metadata` is empty for both. The default is available as `CURRENT_DEFAULT` in the DataFrame schema.
  Evidence: `tests/integration/pyspark/v11/test_delta_transform_live.py`, `test_delta_column_feature_metadata_contract`.
- Observation: Spark 4.1's documented `DESCRIBE TABLE EXTENDED ... AS JSON` columns include a default but do not promise generation expression or identity settings. Delta's `detail()` reports table-level properties and location, not the complete log schema. A SQL description alone is therefore not yet an adequate replacement for `DeltaLog`.
  Evidence: Spark 4.1 `DESCRIBE TABLE` reference, https://spark.apache.org/docs/4.1.0/sql-ref-syntax-aux-describe-table.html, and Delta's protocol schema, https://github.com/delta-io/delta/blob/master/PROTOCOL.md.
- Observation: Delta Connect is a separate remote `DeltaTable` implementation in the `delta-spark` Python package, and its server needs Delta Connect relation and command extensions. Delta 4.1.0 publishes Spark 4.1-specific server artifacts.
  Evidence: https://docs.delta.io/delta-spark-connect/ and https://github.com/delta-io/delta/releases.

## Decision Log

- Decision: Admit the exact `>=4.1,<4.2` Connect profile first. Do not infer Connect support from ordinary PySpark or from the broad default profile.
  Rationale: the V11 charter makes Connect a separately evidenced variant and the existing compiler currently grants Delta capability keys to Connect without Connect-specific proof.
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Unsupported Delta calls fail compilation through `BackendCapabilityError`, with actionable profile-specific guidance, rather than emitting code that may fail later.
  Rationale: this follows the existing Structure target-capability contract and the user's selected meaning of “warn.”
  Date/Author: 2026-10-06 / User and Codex.
- Decision: Generated, identity, and default column declarations are required for Connect admission; retain the existing pre-write metadata comparison and assignment rules.
  Rationale: silently trusting a declaration could permit an omitted required value or miss an identity-mode mismatch.
  Date/Author: 2026-10-06 / User clarification.
- Decision: Prefer an existing, structured remote metadata response if a pinned live proof shows exact values for path and named tables. Otherwise add a small server-side Delta metadata bridge that returns the current snapshot's `schemaString`; do not parse transaction-log files in the Python client or depend on client storage access.
  Rationale: the server has the authoritative Delta snapshot and can use Delta's own log reader, including checkpoint and protocol handling. The proof milestone below sets objective acceptance criteria and a fixed fallback.
  Date/Author: 2026-10-06 / Codex.

## Context and Orientation

Structure's source API lives in `src/structure/plugin/pyspark/delta/operations.py` and `schema.py`. Symbolic execution records each Delta action as a `DeltaMutation`; `src/structure/plugin/pyspark/compiler/logic/maps/MapPySparkStep.py` requires a per-operation capability, and `LowerPySparkPlan.py` checks table bindings, CHECKs, and Delta column declarations. `src/structure/plugin/pyspark/capabilities/model/PySparkCapabilities.py` resolves the exact version range and `ordinary` or `spark-connect` variant. Online execution calls `src/structure/plugin/pyspark/delta/runtime.py`; generated modules import that runtime and render equivalent calls. A capability is a compile-time permission, not evidence that the runtime works.

`Schema.delta_columns` declares expectations about an existing table. `delta_generated` checks `delta.generationExpression`; `delta_identity` checks start, step, and explicit-insert mode; `delta_default` checks `CURRENT_DEFAULT`. `validate_delta_table` checks physical fields and nullability, then those declarations and optional native CHECK constraints. The current generated/identity metadata source is the Delta transaction log's current schema. A transaction log is the versioned record from which Delta reconstructs a table snapshot; `schemaString` is the JSON schema attached to that snapshot. Do not substitute an old log action, a data-file schema, or a user declaration for the current snapshot.

The existing Compose matrix has ordinary `pyspark41` and Connect 3.5/4.0, but no `spark-connect41`. The entrypoints are `scripts/run_integration.py`, `infra/compose/docker-compose.yaml`, `infra/compose/images/pyspark/run-integration.sh`, and `tests/integration/pyspark/support/backend_matrix.py`. Ordinary Delta live tests are in `tests/integration/pyspark/v11/test_delta_transform_live.py`. The public contract and status live in `docs/dev/specifications/DeltaTables.spec.md`, `docs/api/DeltaTables.api.md`, and `docs/compatibility/DeltaTables.compat.md`.

## Plan of Work

### Milestone 1: Prove metadata transport before admitting capabilities

Build a disposable Connect 4.1/Delta 4.1 fixture using Delta Connect's required server packages and extension settings. Create both a path table and a named table with generated, always-identity, by-default-identity, and literal-default columns. In a focused prototype test, inspect the remote `DeltaTable`, its DataFrame schema, catalog table schema, `DESCRIBE TABLE EXTENDED ... AS JSON`, and other structured Delta Connect responses. Compare their values with the classic test's authoritative Delta log schema before and after a metadata-changing commit and after a checkpoint. Record the exact observed response and command in `Surprises & Discoveries`.

Use a native remote response only if it exposes generation expression, identity mode/start/step, and default exactly; works for both path and named tables; observes the current committed snapshot; and needs neither client JVM nor client storage. Do not treat human-readable `SHOW CREATE TABLE` text or an empty `StructField.metadata` as proof. If no native response meets every criterion, implement a version-pinned server-side metadata bridge under `infra/connect-delta-metadata/`. Mirror Delta Connect 4.1's custom-relation extension pattern: a Python request sends the table location, and the server relation reads its current `DeltaLog` snapshot and returns one row with `version: long` and `schema_string: string`. Use a small Scala 2.13 artifact with Spark 4.1 and Delta 4.1 dependencies marked as provided; build it through a dedicated Maven descriptor, install the jar on the Connect server, and register its relation class alongside Delta's relation and command plugins. Do not add a Python UDF or SQL scalar UDF that might execute on a worker without a server Spark session. The Python adapter must validate the returned JSON shape and metadata keys, and fail before any mutation if the bridge is unavailable or returns incomplete data. The bridge must use Delta's snapshot reader rather than scan `_delta_log` files itself, so checkpoints, concurrent commits, and future log layout stay Delta's responsibility. Document the jar and server settings for external Connect servers.

This milestone is independently proved by a Connect test that retrieves matching metadata for all four declaration forms, including a deliberate mismatch and a refreshed snapshot. Do not move to capability admission on a partial result. Delta's own current snapshot reader remains the source of truth even if a bridge is necessary.

### Milestone 2: Make the shared Delta runtime Connect-safe

Update `validate_delta_table` in `src/structure/plugin/pyspark/delta/runtime.py` to accept the native classic or native Connect DeltaTable class appropriate to the active session, still rejecting a plain DataFrame and a table from the wrong session. Preserve `require_compatible_delta_runtime`, table shape and CHECK checks, and caller handle identity. Route only the generated/identity metadata fetch through the proven metadata transport; keep the existing default-column comparison against `CURRENT_DEFAULT`. If the transport returns the full log schema, compare all declared column kinds against that same schema where it has the native default key, and check the observed value against the pinned test before replacing the existing default path.

Keep `fresh_delta_frame`, the read helpers, and mutation helpers shared by online and generated execution. Verify remote `DeltaTable.forPath(remote_session, location)` yields a Connect table, and that the native remote methods accept the rendered predicate and assignment types. For every existing helper—delete, update, merge (all current clause forms), append, `replaceWhere`, schema evolution, snapshot, CDF, history, detail, restore, optimize (compaction and Z-order), and vacuum—make the smallest Connect-specific adaptation needed inside the shared runtime or renderer. Do not create an alternate public DSL or bypass existing validation. Check that generated code contains no `_jvm`, `_jdf`, SparkContext, or direct log-file read on the client.

This milestone passes when a wrong generated or identity declaration fails before a commit; correct declarations permit omitted fields and Delta supplies their values; default mismatch also fails before a commit; and online and generated executions leave equivalent table contents and return the caller's same native handle.

### Milestone 3: Gate support by the specified target profile

Split the Delta capability set in `PySparkCapabilities.py` into classic and Connect 4.1 admissions. Preserve existing ordinary-profile behavior. Grant Connect 4.1 binding, CHECKs, Delta columns, and only the operation keys proved in Milestone 2. Deny Delta on Connect 3.5, 4.0, the broad default range, and unadmitted later ranges. Ensure `LowerPySparkPlan.py` and `MapPySparkStep.py` check the binding and each actual mutation kind, including `schema_evolution`, before generation or runtime imports. Add a Delta-specific `CapabilityDecision.unsupported_capability` message whose `problem`, `why`, `use`, and docs identify the helper, profile, variant, supported 4.1 Connect target or ordinary target, and the metadata-bridge setup if applicable. Keep compilation Spark-free.

Spark-free tests must demonstrate that unsupported operations fail during `structure check` or equivalent compiler invocation, that the diagnostic context reports `>=4.0,<4.1` plus `spark-connect` for a denied 4.0 example, and that the same source compiles for `>=4.1,<4.2` plus `spark-connect` after admission. A generated module must never be produced after a failed capability check.

### Milestone 4: Pin live evidence and publish the exact claim

Add `spark-connect41` to Compose, runner selection, backend fixtures, and `infra/compose/README.md`. Reuse the PySpark 4.1 image with `delta-spark==4.1.0`; configure the matching `io.delta:delta-connect-server_4.1_2.13:4.1.0` package, Delta SQL extension/catalog, and Delta Connect relation/command classes on the server. ## Validation and Acceptance

Acceptance requires all existing public Delta helper families, including generated, identity, and default declarations, to have Connect 4.1 online/generated parity or a documented, user-approved scope revision. For metadata, test correct and incorrect generation SQL, identity mode/start/step, and default literal; each incorrect declaration must fail before the first write. Repeat the checks after a metadata change or checkpoint so a stale log action cannot pass. For mutation and maintenance, compare final rows and relevant history/detail observations; test source-order effects, schema evolution, CDF preflight, partition-only optimize filtering, and vacuum retention safeguards. Check returned table identity and native exception propagation. The Connect generated module must import and run without client-only JVM attributes.

Negative compile tests cover Connect 3.5, 4.0, broad default, and 4.2 profiles, while ordinary existing profiles retain their current behavior. The diagnostic must include the exact rejected Delta capability and an actionable target or setup link. `make build` is mandatory at the end of this coding task. The final compatibility cell may say Connect 4.1 supported only for families whose pinned live tests pass; if any required family cannot pass, leave it unclaimed and the plan incomplete rather than weakening validation silently.

## Idempotence and Recovery

Use temporary, uniquely named Delta tables. Never point restore or vacuum tests at a persistent table; use the existing 168-hour default or an isolated table when exercising explicit short retention. A post-commit schema-validation failure does not roll back Delta, so each failure test must use its own disposable table. A failed metadata bridge query must stop before any write. Retry the Connect lane after preserving its Ivy cache; do not delete staged or unstaged project work to get a clean build. If a live lane is unavailable, retain compiler gates and record the infrastructure failure rather than claiming parity from Spark-free tests.

## Interfaces and Dependencies

The public Python helper signatures stay as specified in `docs/dev/specifications/DeltaTables.spec.md`; no new table-creation API is introduced. The internal metadata boundary returns a current snapshot version and the raw Delta schema JSON for a caller-bound table location, independent of whether the source is a native Connect response or a server bridge. `validate_delta_table(table, schema, *, mode="expression")` continues to return the input table object. The capability keys remain `group="delta"` with existing operation names. The integration lane pins PySpark 4.1.0 and Delta 4.1.0 on client and server; any server bridge artifact is a documented deployment dependency for the Connect column-declaration contract, not a dependency of ordinary PySpark or compile-only commands.
