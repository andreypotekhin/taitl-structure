# Complete PySpark VariantType and Variant Helpers in V9

This ExecPlan is a living document. Maintain it according to `docs/dev/auto/Plans.md`; its `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections must describe the actual state whenever work stops.

## Purpose / Big Picture

PySpark 4 introduced a first-class Variant value for semi-structured JSON data. The current V9 implementation already lets a transform declare a `variant(...)` field and use the main Spark 4.0 and 4.2 inspection/conversion helpers. This plan finishes the migration surface without weakening Structure's typed contract: users will have a predictable way to construct Variant literals, compare Variant values, use mutation helpers on the Spark profiles that provide them, and expand Variant arrays/objects into typed row scopes. Unsupported dynamic or profile-incompatible forms will fail with an actionable capability diagnostic instead of compiling to an untyped SQL escape hatch.

The observable result is a transform that compiles to public PySpark APIs on the selected Spark profile, preserves generated/online parity, and is represented consistently in the APICatalog and PySpark coverage ledgers.

## Surprises & Discoveries

- Observation: `variant_explode` is a table-valued function, not an ordinary scalar expression.
  Evidence: the existing `generators.py` and `RenderPySparkStructGenerator.py` model column generators such as `posexplode`; a Variant table-valued function must be represented as a relation-producing operation or a dedicated TVF-capable generator.
- Observation: Variant mutation helpers are split across later Spark profiles.
  Evidence: Spark's in-progress PySpark API documents append/insert/set helpers as 4.3.0 additions and `variant_delete` as a 5.0.0 addition; the capability registry now keeps those profiles separate from 4.0 and 4.2.
- Observation: Variant extraction currently has an intentional explicit result-type requirement.
  Evidence: `variant_get(..., as_type=...)` lowers to a typed cast and avoids silently changing a Variant value into an inferred or untyped Structure expression.
- Observation: The focused Variant suite and repository-wide build are green in the current worktree.
  Evidence: the focused Variant/capability/catalog/streaming suite passes (`292 passed`), and `make build` passes static checks, `1,516 passed, 56 skipped`, and package creation. The broader Docker integration lane still has unrelated search, security, and restart-fixture failures; the new Variant stream test passes independently.
- Observation: Correlated Variant TVFs require Spark's public `Column.outer()` marker when used through `DataFrame.lateralJoin`.
  Evidence: `tests/integration/pyspark/v3/streams/test_file_streams.py::test_variant_explode_runs_online_and_generated_on_pyspark_4_streams` passes for both online and generated execution on PySpark 4.0.

## Decision Log

- Decision: Keep this work as a child ExecPlan of the broader V9 catalog plan.
  Rationale: the parent plan governs all V9 design-gated rows, while Variant has enough profile and type-system detail to require an independently restartable implementation sequence.
  Date/Author: 2026-08-01 / Codex.
- Decision: Use four explicit target profiles for this plan: `>=3.5,<4.0` as the rejection baseline, `>=4.0,<4.1` for the original Variant surface, `>=4.2,<4.3` for `is_valid_variant`, and later `>=4.3,<4.4` plus `>=5.0,<5.1` for mutation helpers whose Spark APIs require those releases.
  Rationale: capability checks must describe the exact runtime contract rather than treating every Spark 4 release as interchangeable.
  Date/Author: 2026-08-01 / Codex.
- Decision: Construct a public Variant literal from a validated JSON text literal and lower it through `parse_json(F.lit(...))`; do not expose PySpark's Python-internal Variant value representation.
  Rationale: JSON text is portable across generated and online execution, can be validated before compilation, and avoids coupling the Structure API to private Python/JVM conversion details.
  Date/Author: 2026-08-01 / Codex.
- Decision: Admit Variant equality through the existing typed equality operators after adding Variant compatibility rules; do not add ordering operators or implicit extraction types.
  Rationale: equality has a clear SQL null contract, while ordering and inferred extraction would require a separate semantic contract for heterogeneous JSON values.
  Date/Author: 2026-08-01 / Codex.
- Decision: Model Variant row expansion separately from scalar expressions because Spark exposes it as a table-valued function.
  Rationale: forcing it through scalar expression rendering would conceal relation cardinality, generated scope fields, and lateral-join requirements.
  Date/Author: 2026-08-01 / Codex.
- Decision: Keep mutation paths literal-only in the initial Structure surface even though Spark also accepts runtime path columns.
  Rationale: the existing typed Variant extraction contract is literal-path based, and literal paths make generated source, diagnostics, and cross-profile behavior deterministic. Dynamic paths remain a later explicit extension rather than an accidental partial API.
  Date/Author: 2026-08-01 / Codex.

## Context and Orientation

Structure is a typed Python-to-PySpark compiler. A `Schema` declares fields, a transform records symbolic operations, and the PySpark plugin renders the same plan for generated source and online execution. A capability profile is a version range selected from global plugin configuration or a compile/session override. A capability requirement is checked during lowering before generated code or runtime execution is allowed.

The main implementation locations are:

- `src/structure/plugin/pyspark/dsl/types/VariantType.py` and `src/structure/plugin/pyspark/dsl/types/Variant.py` for the field/type model.
- `src/structure/plugin/pyspark/dsl/field.py` and `src/structure/plugin/pyspark/dsl/expressions.py` for public fields and scalar helpers.
- `src/structure/plugin/pyspark/capabilities/model/PySparkCapabilities.py` for profile-specific admission.
- `src/structure/plugin/pyspark/compiler/` for capability validation and expression lowering.
- `src/structure/plugin/pyspark/render/` and the online evaluator for generated/online parity.
- `src/structure/plugin/pyspark/dsl/generators.py` and `src/structure/plugin/pyspark/render/logic/steps/RenderPySparkStructGenerator.py` for existing row-expansion patterns.
- `tests/specifications/v9-api-catalog/test_v9_variant_field.py` and the compatibility/coverage tests for no-Spark behavior.
- `docs/dev/specifications/V9ApiCatalogDesignGatedFeatures.md`, `docs/dev/design/V9ApiCatalogDesignGates.md`, `docs/APICatalog.md`, and the three PySpark coverage ledgers for the public status.

## Plan of Work

### Milestone 1: Freeze the profile and capability matrix

Audit every Variant function in the Spark SQL and PySpark public API against the target profiles. Add named capability requirements for the existing 4.0 surface, `is_valid_variant` on 4.2, the mutation family on 4.3, and `variant_delete` on 5.0. Add positive and negative no-Spark tests for each profile. The acceptance result is a table-driven capability test that proves a transform using a helper is admitted only on the profile that owns that helper.

### Milestone 2: Add literals and equality

Add `variant_literal(json_text)` to the public DSL. Require a non-empty string literal, validate its JSON during symbolic capture, and preserve the original JSON text in the expression model. Render it as `F.parse_json(F.lit(<json text>))` for both generated and online paths. Extend typed binary equality compatibility so two Variant expressions compare with Spark's Variant equality and SQL null semantics; reject comparisons between Variant and unrelated Structure types with a diagnostic. Add tests for objects, arrays, scalar JSON, invalid literals, null comparison, generated source, and online/generated expression parity. Do not add ordering, arithmetic, or implicit extraction.

### Milestone 3: Add profile-gated mutation helpers

Implement `variant_array_append`, `try_variant_array_append`, `variant_insert`, `try_variant_insert`, `variant_set`, `try_variant_set`, and `variant_delete` in `expressions.py`. Paths use the same non-empty literal `$`-prefixed rule as extraction, with root deletion rejected. Validate that the input is Variant and that mutation values are Structure expressions Spark can cast to Variant. Attach capability requirements at the function-family boundary. Render the corresponding public `pyspark.sql.functions` calls and mirror them in the online evaluator. Add 4.0/4.2 rejection tests, 4.3 positive tests for append/insert/set, and 5.0 positive/rejection tests for delete. If a target runtime exposes a different signature, update the capability entry and diagnostics rather than silently changing the Structure signature.

### Milestone 4: Design and implement Variant row expansion

The typed generator now records row multiplication, generated scope, output schema, and streaming compatibility. Its declared `pos` field follows the existing Structure long contract; `key` and `value` preserve the nullable outer-row semantics. Rendering uses the public `spark.tvf.variant_explode*` API through `DataFrame.lateralJoin` with `Column.outer()` correlation, never a raw SQL string. Focused no-Spark tests and live PySpark 4.0 streaming evidence cover profile rejection, inner rendering, outer rendering, and online/generated parity.

### Milestone 5: Close intentional exclusions

Document and test that dynamic extraction paths, dynamic extraction result types, implicit Variant-to-Structure extraction, Variant ordering, and provider-specific Python Variant objects are unsupported in V9. Each rejection must name the supported alternative (`parse_json`, a literal path, an explicit `as_type`, or a later design) and must appear in the public API docs. This prevents the coverage ledgers from implying that a helper is complete when only its safest typed subset is supported.

### Milestone 6: Reconcile V9 evidence and close the slice

Update `docs/APICatalog.md`, the V9 design/specification, Sprint 45, `docs/dev/planning/P07302601.V9-api-catalog-design-gates.plan.md`, and the transformation/streaming coverage JSON ledgers. Add focused specification tests for every admitted helper, profile rejection, generated rendering, online parity, and streaming classification. Run live PySpark 4.0 and 4.2 evidence for the current surface; run 4.3/5.0 evidence when those integration images exist. Mark the plan complete only after the focused suites and `make build` pass.

## Validation and Acceptance

The plan is accepted when:

- `variant(...)` fields and the current helper set compile only on their admitted profiles, including global configuration and per-transform overrides;
- `variant_literal(...)` validates JSON and renders identically in generated and online execution;
- Variant equality has tested SQL null behavior, while ordering and implicit extraction fail clearly;
- mutation helpers are present only on their exact Spark profiles and have positive and negative capability tests;
- row expansion is implemented as a typed TVF/generator with `pos`, `key`, and `value` fields and a profile-gated lateral join;
- all admitted helpers are present in the public exports, docs, transformation ledger, streaming ledger, and APICatalog with profile notes;
- focused tests pass and `make build` succeeds.

## Idempotence and Recovery

All changes are additive and can be reapplied safely. If a live Spark probe fails, keep the no-Spark capability tests, record the runtime and exact failure, and leave that helper profile-gated or design-gated. Do not broaden a profile to make a probe pass, do not use raw SQL as a fallback, and do not remove unrelated worktree changes. If a generated artifact changes unexpectedly, rerun the documented generation command and review the diff before accepting it.
