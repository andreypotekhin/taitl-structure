# Embed Raw Hooks in Generated PySpark

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement embedded raw
hooks in generated PySpark without prior conversation history.

## Purpose / Big Picture

Structure currently renders a raw hook by importing the source transform class, constructing it as `self._impl`, and
calling the hook on that object. This is correct for ordinary generated output, but it means a generated transform
with a hook cannot be deployed without also shipping the transform class that generated it.

After this change, a project may set `generated_code_options = ["embed_hooks"]`. Generated PySpark will copy each raw
hook body into its generated transform class, after `run(...)`, under the original hook method name. Generated calls
will use `self.hook_name(...)`; the module will not import or construct the source transform class for hooks. The
default `generated_code_options = []` keeps today’s delegated-hook output unchanged.

The outcome is observable without Spark: render an embedded-hook transform, temporarily make its source transform
module unavailable to imports, then parse and import the generated module successfully. With a Spark-capable test
environment, the same small DataFrame input must produce the same output from online execution and from the generated
class. This feature copies an opaque runtime boundary; it does not make raw PySpark code visible to the Structure
compiler or optimizer.

## Surprises & Discoveries

- Observation: the generated renderer constructs `self._impl` for Python UDFs as well as raw hooks.
  Evidence: `RenderPySparkTransformModule._requires_impl(...)` returns true for either hooks or UDFs, and
  `_udf_initializers(...)` renders `F.udf(self._impl.<function>, ...)` in
  `src/structure/app/target/pyspark/commands/RenderPySparkTransformModule.py`.

- Observation: source transform ownership is already preserved on each lowered hook recipe.
  Evidence: `PySparkHookRecipe.origin` is a `TransformMemberOrigin` with the module, class, method, and in-memory
  owner class. This lets generation extract the exact declaring method rather than relying on late attribute lookup.

- Observation: a generated source unit can contain multiple source transforms.
  Evidence: `RenderConfiguredPySparkProject` groups transforms by `transform.__module__` and invokes
  `RenderPySparkProject.source_unit(...)` once for each group. Rendering must therefore pass per-transform hook source
  information without causing duplicate generated imports or methods.

- Observation: the shared generated-code option vocabulary was extended by the mirrored-layout work before this plan
  was implemented.
  Evidence: `StructureConfigValidator._generated_code_options` admits `mirror_methods`, `embed_exprs`, `embed_hooks`,
  and `embed_udfs`; this implementation preserves those composable choices.

- Observation: the optional PySpark integration command collected 11 tests but found no configured live backend.
  Evidence: `poetry run pytest --run-integration tests/integration/pyspark -q` completed with `11 skipped`.

- Observation: a concurrent change outside this plan introduced a repository lint failure after an earlier successful
  build.
  Evidence: the final `make build` stops at F402 in
  `tests/integration/pyspark/v3/streams/test_file_streams.py:61`; the file is unrelated to embedded hooks and was not
  modified by this plan.

## Decision Log

- Decision: add `generated_code_options` as a list of independently combinable values, not a single generation mode.
  Rationale: generated-code choices will grow independently. An enum-like mode would make unrelated choices mutually
  exclusive and create repeated configuration migrations. The first allowed value is `embed_hooks`; an empty list is
  the stable default.
  Date/Author: 2026-07-13 / project owner and Codex

- Decision: name the first value `embed_hooks`, not `inline_hooks`.
  Rationale: Structure does not compile raw hook code into its expression IR. It copies the author’s Python method
  into generated source and still treats it as an opaque runtime boundary. “Embed” communicates that exact behavior.
  Date/Author: 2026-07-13 / Codex

- Decision: render embedded hook methods after `run(...)` and retain their source method names.
  Rationale: reviewers should see generated execution first and hook implementations immediately afterward. Python
  resolves `self.method(...)` at runtime, so declaration order does not affect calls. Source names improve navigation
  and traceability.
  Date/Author: 2026-07-13 / project owner and Codex

- Decision: `embed_hooks` must fail for a plan that uses a source-backed Python UDF until a later `embed_udfs` option
  is implemented.
  Rationale: otherwise the output would still import the source transform class through `_impl`, contradicting the
  purpose of a self-contained generated transform. A future `generated_code_options = ["embed_hooks", "embed_udfs"]`
  can add UDF source packaging under its own explicit contract.
  Date/Author: 2026-07-13 / Codex

- Decision: the first implementation embeds only hooks whose standalone method bodies can be proven to need no source
  transform state or unresolved module globals.
  Rationale: arbitrary Python methods may depend on `self` state, `super()`, closures, or names imported only by the
  source module. Blind text copying would generate a module that imports successfully but fails later. Local imports,
  parameters, assigned locals, literals, builtins, and `self.spark`/`self.ctx` are safe. Other free references must
  produce a precise generation diagnostic. A later option can explicitly package or declare external dependencies.
  Date/Author: 2026-07-13 / Codex

- Decision: strip `@raw` decorators and render source through Python AST, not by concatenating inspected source text.
  Rationale: the decorator belongs to Structure source declaration and would require source DSL imports or re-register
  generated methods as hooks. AST extraction produces deterministic indentation, avoids decorator execution, and makes
  dependency analysis possible.
  Date/Author: 2026-07-13 / Codex

- Decision: permit `embed_hooks` on a Python-UDF plan only when the already-supported independent `embed_udfs` option
  is also selected.
  Rationale: this retains the plan's source-transform-free boundary while composing with the shared option vocabulary
  introduced by the mirrored generated-method layout. `embed_hooks` alone still fails before generation.
  Date/Author: 2026-07-14 / Codex

## Outcomes & Retrospective

Implementation now embeds AST-normalized raw methods with local imports, parameters, local values, builtins, and
`self.spark`/`self.ctx`. It rejects source globals, closure values, `super()`, and other instance state with `GEN-E0903`.
Default generated output remains delegated and unchanged. Inherited hook calls are bound to generated declaring owners.
The independent `embed_udfs` option remains the required UDF packaging path; general external-dependency packaging is
deferred. Focused configuration, rendering, inheritance, execution, hook, generated-code, and diagnostic tests passed;
feature-scoped lint and static checks also pass. An earlier repository build completed with 842 passed and 11 optional
integration skips, but a final rerun after the live-parity test addition is blocked by an unrelated concurrent F402 lint
error in a user-owned streaming integration test.

## Context and Orientation

A Structure transform is a Python class inheriting from `Transform`. It declares DataFrame inputs and outputs and has
schema-returning step methods. A raw hook is a method decorated with `@raw`. It receives selected DataFrames, the
caller-supplied Spark session, and an optional context object. Because a raw hook contains arbitrary Python and
PySpark, the compiler records its boundary metadata but does not analyze its body.

The existing implementation follows this path:

1. `src/structure/app/compiler/frontend/commands/CompileTransform.py` compiles a source transform into a
   `TransformPlan` and assigns raw hooks a `TransformMemberOrigin` naming the declaring class and method.
2. `src/structure/app/target/pyspark/logic/mapping/PySparkHookMapper.py` copies that metadata into a
   `PySparkHookRecipe`.
3. `src/structure/app/target/pyspark/commands/RenderPySparkTransformModule.py` decides whether the generated module
   needs a source transform import and `self._impl` instance. Today it does so when the plan has hooks or UDFs.
4. `src/structure/app/target/pyspark/commands/RenderPySparkStep.py` renders a hook call. For an ordinary source hook
   it emits `self._impl.<hook>(..., spark=self.spark, ctx=self.ctx)`.
5. `src/structure/app/target/pyspark/commands/RenderPySparkProject.py` renders a single transform or a source unit
   with schemas, runtime support, the generated transform module, and traceability files.

Configuration is resolved from defaults, `structure.toml`, `[tool.structure]` in `pyproject.toml`, and programmatic
overrides. `StructureConfig` is the resolved public configuration model. `CompilerOptions` is its frozen compilation
projection and is part of the compiled-artifact fingerprint. The relevant files are:

- `src/structure/app/configuration/model/StructureConfig.py`
- `src/structure/app/configuration/commands/ResolveStructureConfig.py`
- `src/structure/app/configuration/logic/StructureConfigDefaults.py`
- `src/structure/app/configuration/logic/StructureConfigValidator.py`
- `src/structure/app/configuration/logic/StructureConfigBuilder.py`
- `src/structure/app/compiler/artifacts/model/CompilerOptions.py`
- `src/structure/app/cli/commands/RenderConfiguredPySparkProject.py`
- `src/structure/app/dsl/model/transforms/Transform.py`

Generated source is a reviewable artifact. The default generated class has a public `run(...)` method. Some inherited
transforms also have compiler-owned `_step_...` methods and generated parent classes. The generated class must never
inherit from a source transform class. In embedded-hook output, the raw methods are ordinary generated instance methods
after `run(...)`, with no `@raw` decorator.

“Self-contained” in this plan means the generated transform module does not import its source transform class. It
does not mean that Python or PySpark dependencies used inside an embedded hook are bundled into one file. A local
import in the hook, such as `from pyspark.sql import functions as F`, remains a runtime dependency of the generated
module.

## Plan of Work

### Milestone 1: Add a stable, combinable generation option

Add `generated_code_options: tuple[str, ...]` to `StructureConfig` and `CompilerOptions`. Add the raw list value
`"generated_code_options"` to `ResolveStructureConfig._keys`, default it to `[]` in `StructureConfigDefaults`, copy it
to a tuple in `StructureConfigBuilder`, and validate it in `StructureConfigValidator`. Validation must require a list
of unique, non-empty strings and reject values other than `embed_hooks`. Report `CONF-E0102` with a remedy such as:

    Use generated_code_options = ["embed_hooks"].

Canonicalize the stored tuple by sorted value so option ordering produces byte-identical output and the same compiler
fingerprint. Add the setting to `CompilerOptions.from_config(...)` and `CompilerOptions.fingerprint()`. This makes a
change from `[]` to `["embed_hooks"]` invalidate cached compiled/generated artifacts and makes generated-mode stale
artifact checks compare like with like.

Update `docs/seed/config_seed/pyproject.seed.toml`, `docs/Configuration.md`, and
`docs/dev/specifications/ConfigSchema.spec.md`. Explain that the setting changes generated source only; it does not change
online execution. Document the default and the only initially supported value without promising future values as
implemented behavior.

Add configuration tests beside the existing config-schema tests. They must prove defaults, TOML and programmatic
overrides, stable canonical ordering, unknown-option rejection, duplicate-option rejection, and compiler option
fingerprint changes. Update `res/testing/snapshots/api/public_structure.v1.json` only if the public configuration
constructor snapshot intentionally changes.

### Milestone 2: Capture embeddable hook source deterministically

Create a focused logic component under `src/structure/app/target/pyspark/logic/` with an action-oriented name such as
`RenderEmbeddedHooks`. It receives the lowered hooks in deterministic plan order and their `origin.owner` classes. It
must return rendered method text and the exact set of source-transform imports still required. Keep AST parsing,
dependency validation, and source rendering in small delegates if the action would otherwise become large.

Use `inspect.getsource(...)` on the exact function retrieved from
`hook.origin.owner.__dict__[hook.origin.member_name]`. Dedent and parse it with `ast.parse(...)`; require exactly one
ordinary synchronous `FunctionDef`. Remove decorators. Retain the method name and keyword-only signature used by the
source hook. Do not copy a source docstring unless the renderer’s normal generated-source policy intentionally keeps
it. Render the normalized AST with `ast.unparse(...)`, then indent it as a class member. The output must be
deterministic for unchanged source.

Add one generated-code diagnostic entry, for example `GEN-E0903`, in
`src/structure/lib/cross/errors/registry.py` and document it in `docs/Diagnostics.md`. Use it for an unsupported
embedded-hook body, an embedded hook name collision, or the source-backed Python-UDF conflict. Its context must include
the hook name when a hook is responsible. Add its contract to the existing diagnostic registry tests. Keep invalid
configuration values on the existing `CONF-E0102` path rather than reclassifying them as generation errors.

Perform a conservative scope analysis before rendering. Accept local parameters and assignments, names bound by local
imports inside the method, Python builtins, and `self.spark`/`self.ctx`. Reject `super()`, free closure variables,
unresolved module-global names, and instance attributes other than `spark` and `ctx`. The diagnostic must name the
hook and unsupported reference and explain that `embed_hooks` requires local imports or a standalone hook body. Do not
execute the hook, import PySpark, or import the generated module while generating source.

Keep this analysis limited to dependencies required by the body. It must not claim to prove arbitrary PySpark safety,
streaming compatibility, or security. The existing raw-hook target and streaming declarations remain the semantic
authority.

### Milestone 3: Render embedded calls and remove source-transform coupling

Thread `generated_code_options` from `StructureConfig` and `CompilerOptions` through:

- `RenderConfiguredPySparkProject` to `RenderPySparkProject.source_unit(...)`;
- `Transform.generate(...)` to `RenderPySparkProject.source_unit(...)`;
- `RenderPySparkProject.__call__(...)` and `.source_unit(...)` to `RenderPySparkTransformModule`; and
- `RenderPySparkTransformModule` to `RenderPySparkStep`.

Avoid placing this output-layout choice in `TransformPlan` or `PySparkExecutionPlan`; those objects are the shared
runtime semantics and must remain independent of source layout. The renderer owns this option.

When `embed_hooks` is absent, retain byte-for-byte compatible delegated output: source transform imports, `_impl`, and
the existing hook call spelling remain unchanged. When it is present, make `_source_imports(...)` omit every import
that exists only for hooks, make `_requires_impl(...)` ignore hooks, and have `RenderPySparkStep._hook_call(...)` emit
`self.<original_hook_name>` with no receiver prefix. Append the rendered hook methods after the generated concrete
class’s `run(...)` method. Do this in both legacy inline classes and inherited generated-class output.

The renderer must reserve `run`, generated `_step_...` names, and any other generated class members. Fail generation
when an embedded hook name collides with one. For inherited hooks, preserve owner-qualified semantics already modeled by
`TransformMemberOrigin`: emit methods on generated owner classes when that matches the generated class hierarchy, or
emit deterministic wrappers that bind the correct source body. Do not allow ordinary Python method resolution to call a
child hook when the recipe selects an identically named parent hook. Add a test where a parent and child use the same
hook name and prove the parent recipe still calls the parent body.

Before rendering, reject `embed_hooks` when `_udfs(plan)` is non-empty. The diagnostic must state that a Python UDF
still needs the source transform implementation and recommend removing `embed_hooks` or waiting for `embed_udfs`.
This makes the option’s source-transform-free claim truthful rather than partial.

### Milestone 4: Prove behavior and update maintained artifacts

Add focused tests in `tests/specifications/config-schema/` for configuration resolution and in
`tests/specifications/pyspark-code-generation/` for source rendering. Cover all of the following:

- Default rendering has no behavior or source-text change.
- `embed_hooks` has no source transform import, no `_impl`, original hook names, and hook definitions after `run(...)`.
- All existing `EnrichOrders` hooks render correctly, including a before hook, a multi-input hook, and an output hook
  that uses a local PySpark import.
- Generated source parses with `ast.parse` and imports when the source transform module is unavailable.
- An inherited parent hook remains bound to its declared owner even when the child has the same method name.
- Unsupported `self` state, `super()`, a closure, and a module-global reference each fail with a useful diagnostic.
- A transform containing a Python UDF fails for `embed_hooks` and retains present behavior without that option.
- Rendering the same plan/options twice is byte-identical and option order does not alter output.

Add generated-vs-online parity coverage to `tests/integration/pyspark/` or the established generated-code parity suite.
Use a small transform whose hook body uses only supported embedded dependencies. Exercise both delegated and embedded

Regenerate checked-in generated fixtures only for a fixture deliberately configured with `embed_hooks`; do not change
the default fixtures solely because this option exists. If no committed fixture uses the option, add a small isolated
fixture and its golden output instead of converting public examples. Update generated-code snapshots, traceability
expectations if they include option metadata, public API snapshots where needed, and `docs/dev/Concepts.md` if it maps
generated embedded hooks as a distinct concept.

Update `docs/GeneratedPySpark.md`, `docs/background/Generation.back.md`,
`docs/background/Transform.back.md`, `docs/dev/specifications/PySparkCodeGeneration.spec.md`, and
`docs/dev/specifications/UserStories.spec.md`. Preserve the current delegated-hook statement as the default. Add an explicit

Create a concise design-decision record under `close/archive/decisions/` when implementation begins, documenting the

## Validation and Acceptance

The feature is accepted when a user can set:

    [tool.structure]
    generated_code_options = ["embed_hooks"]

and observe a generated hook-bearing module that has these properties:

- It imports neither the source transform class nor a source hook-owner class.
- It has no `self._impl` field when the transform has no Python UDF.
- Its `run(...)` method calls `self.<source_hook_name>(...)` at the existing hook boundaries.
- The corresponding hook methods occur after `run(...)`, have no `@raw` decorators, and preserve their source names.
- It parses and imports when the original transform module is unavailable.
- It yields the same output as online execution for the covered PySpark fixture.

The default configuration must still emit the existing delegated hook calls and preserve current fixtures. Invalid
option values, unsupported hook dependencies, reserved-name collisions, and plans containing Python UDFs must fail
before writing partial generated output with a user-correctable diagnostic. `make build` must complete successfully.

## Idempotence and Recovery

All edits are additive or controlled renderer changes. Configuration resolution and rendering must be deterministic:
repeating generation with identical source and options must produce identical files. `structure compile --fail-on-diff`
is the safe way to inspect pending generated output before writing it. If a source extraction case fails, remove
`embed_hooks` to restore the existing delegated behavior; do not hand-edit generated files. If a newly added golden
fixture is wrong, fix the source renderer or fixture configuration, regenerate through the normal compiler command,
and review the diff rather than modifying the generated file directly.

## Artifacts and Notes

The intended embedded shape is:

    class EnrichOrdersGenerated:
        def __init__(self, *, spark: SparkSession, ctx=None):
            self.spark = spark
            self.ctx = ctx

        def run(self, *, orders: DataFrame, customers: DataFrame) -> TransformResult:
            ...
            orders = self.remove_negative_totals(orders=orders, spark=self.spark, ctx=self.ctx)
            ...

        def remove_negative_totals(self, *, orders, spark, ctx):
            from pyspark.sql import functions as F
            return orders.where(F.col("net_total") >= 0)

The source hook is copied as a method body. Its decorator is intentionally absent because it is declaration metadata
that has already been compiled into the execution recipe. Validation, projection, hook order, target eligibility, and
streaming declarations continue to come from that recipe, surrounding the ordinary generated method call.

## Interfaces and Dependencies

At completion, these interfaces must exist:

- `StructureConfig.generated_code_options: tuple[str, ...]`, containing only validated canonical values.
- `CompilerOptions.generated_code_options: tuple[str, ...]`, included in `fingerprint()`.
- Renderer entrypoints that accept `generated_code_options: tuple[str, ...] = ()` so direct renderer callers can test
  both layouts without constructing a full project configuration.
- A focused embedded-hook renderer or extractor that accepts `PySparkHookRecipe` data with a live
  `TransformMemberOrigin.owner`, and either returns normalized class-method source or raises a structured generation
  diagnostic.

No new third-party dependency is needed. Use the Python standard library `ast`, `inspect`, and `textwrap`; do not
evaluate user hook code during compilation. Continue using the existing PySpark renderer, compiler artifact builder,
and generated runtime helpers. Do not add a source-text field to backend-neutral IR: source extraction belongs to the
PySpark rendering layer and is intentionally excluded from execution plans.
