# Extend Store with Fulfillment Planning

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. Maintain this document according to `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

The current Store example proves order enrichment, shipment-backed publication, and daily analytics, but it does not show how a Structure application can decide whether an order can be fulfilled, from which warehouse it should ship, what quantity must wait, or when replenishment risk is rising. After this work, a caller will be able to run the Store example in two explicit phases: a planning phase that turns validated order demand plus inventory facts into planned allocations, backorders, and replenishment suggestions, and an execution phase that still turns actual shipment facts into published fulfilled lines.

This keeps Store coherent as one example application while making it substantially richer. A reader will be able to inspect generated code and run tests that prove the example now covers reference lookups, temporal state, allocation decisions, fallback behavior, operational summaries, and the separation between planned fulfillment and actual shipment facts.

  Evidence: `examples/store/transforms/order.py` defines `normalize`, `add_customer`, `add_product`, `add_promotion`, then `add_shipments`, and only `publish` returns `OrderPublished`.

  Evidence: `tests/differential/store/test_store_reference_contract.py` renders `examples.store` source and compares it with an independent Python reference implementation; no Store-specific tests under `res/testing/model/` are involved.

- Observation: The current Store README explicitly says the example does not choose a warehouse layout, which makes warehouse-aware planning an intentional next-step expansion rather than a contradiction.
  Evidence: `examples/store/Readme.md` ends with “The example neither defines a customer-facing storefront nor chooses a warehouse layout.”

- Observation: `select_first_qualified(...)` accepts one orderable expression, not an order-expression tuple.
  Evidence: compiling the first `PlanFulfillment` preferred-option implementation failed with `select_first_qualified(...) order_by requires an orderable scalar expression`; the implementation now assigns a deterministic `option_ordinal` with `row_number(...)` over the exact tie-breaker tuple and keeps ordinal one.

- Observation: Grouped output fields must be grouped keys or aggregate expressions, including placeholder fields.
  Evidence: compiling the first daily summary and reconciliation implementations raised `DSL-E0402` for non-aggregate rate/status fields; the final implementation calculates daily rates in a row-preserving follow-up step and uses aggregate expressions for reconciliation status.

- Observation: Store generated output remains stable after adding fulfillment when deterministic path expectations include the new grouped schema modules and CamelCase transform modules.
  Evidence: `poetry run pytest tests/differential/store/test_store_reference_contract.py tests/metamorphic/test_generation_stability.py -q` passed with `11 passed`, and `poetry run pytest tests/golden/test_examples_generated_output.py -q` passed with `13 passed`.

## Context and Orientation

The public Store example lives under `examples/store/`. `examples/store/transforms/order.py` contains `EnrichOrders`, which currently turns `OrderRaw` into `OrderPublished` by validating identifiers and money fields, enriching customer/product/promotion information, and finally inner-joining to `Shipment`. `examples/store/transforms/analytics.py` contains `OrderAnalytics`, which summarizes actual fulfilled lines. `examples/store/schemas/order.py` defines the current order-line shapes, including `OrderNormalized`, `OrderWithPromotion`, `OrderFulfillment`, and `OrderPublished`.

This plan introduces several plain-language concepts that must remain explicit in the code and docs. A demand line is one validated commercial order line before any warehouse decision has been made. An allocation is the planned quantity to fulfill from one warehouse. Available-to-promise means the quantity that can still be promised to new demand after subtracting already reserved quantity from on-hand inventory and adding eligible inbound quantity that arrives by the promised ship date. A backorder is the part of a demand line that cannot be promised for the planned ship date. A replenishment suggestion is a derived recommendation to move or receive stock because projected available-to-promise falls below a declared safety threshold. These are example-level planning facts, not a hosted warehouse-management product.

Generated source for Store is rendered under `examples/structure_generated/store/` from the example registrations in `tests/helpers/example_projects.py`. Differential coverage for the public example is in `tests/differential/store/test_store_reference_contract.py`. The generated-output guard lives in `tests/golden/test_examples_generated_output.py`. Any new Store transform or schema that is meant to be part of the public example must be added to the example renderer and must regenerate the Store generated package instead of being hand-written under `examples/structure_generated/store/`.

## Interfaces and Dependencies

Add new example schemas under `examples/store/schemas/fulfillment/`. Keep schema modules lowercase and grouped by cohesive domain, following the Search example style. Use these modules and relations:

- `demand/demand.py` contains `OrderDemand`.
- `planning/inventory.py` contains `Warehouse`, `InventoryPosition`, and `InboundInventory`.
- `planning/intermediate.py` contains `InboundInventoryAvailability`, `FulfillmentOption`, and `FulfillmentPreferredOption`.
- `planning/plan.py` contains `FulfillmentAllocation`, `FulfillmentBackorder`, `FulfillmentPlan`, and `ReplenishmentSuggestion`.
- `analytics/summary.py` contains `DailyFulfillmentSummary` and `WarehouseLoadSummary`.
- `reconciliation/reconciliation.py` contains `PlannedActualReconciliation`.

Keep the existing commercial enrichment shapes in `examples/store/schemas/order.py`, but add one new shared boundary there:

- `OrderDemand` should not be added to `order.py`; keep it in `schemas/fulfillment/demand/demand.py` and build it from `OrderWithPromotion`.
- Add a focused helper output if needed, such as `OrderCommercialLine`, only if implementation pressure proves that `OrderWithPromotion` is too tied to the shipment path. Prefer reusing `OrderWithPromotion` directly as the planning input if that keeps the design smaller.

Implement new transforms under cohesive subpackages in `examples/store/transforms/fulfillment/`:

- `demand/PrepareOrderDemand.py` exports `PrepareOrderDemand`.
- `planning/PlanFulfillment.py` exports `PlanFulfillment`.
- `analytics/FulfillmentAnalytics.py` exports `FulfillmentAnalytics`.
- `reconciliation/ReconcileFulfillmentPlan.py` exports `ReconcileFulfillmentPlan`.
- `PrepareOrderDemand` consumes the same business inputs as `EnrichOrders` except `Shipment`. It performs the same normalize/customer/product/promotion stages and outputs `OrderDemand`.
- `PlanFulfillment` consumes `OrderDemand`, `Warehouse`, `InventoryPosition`, and `InboundInventory`. It outputs `allocations`, `backorders`, `plans`, and `replenishment_suggestions`.
- `FulfillmentAnalytics` consumes `FulfillmentPlan`, `FulfillmentAllocation`, and `FulfillmentBackorder`. It outputs `daily_summary` and `warehouse_load_summary`.
- `Fulfillment` lives in `examples/store/transforms/fulfillment/Fulfillment.py` and composes `PrepareOrderDemand`, `PlanFulfillment`, and `FulfillmentAnalytics` into the app-facing fulfillment planning pipeline.

`PlanFulfillment` must remain deterministic. For one demand line, warehouse options are filtered to active warehouses in the same tenant, then ordered by these exact tie-breakers: same customer region first, then lower warehouse priority value, then greater available-to-promise quantity, then warehouse id ascending. The transform may split one demand line across multiple warehouses only after taking the preferred option; the first milestone should keep a simpler rule: allocate from exactly one best warehouse when enough quantity exists there, otherwise allocate the best warehouse’s available quantity and put the remainder on backorder. Do not implement multi-warehouse splitting in the first version.

`FulfillmentPlan` must include both commercial context and planning outcome. At minimum it must carry tenant, order id, customer id, product id, requested quantity, allocated quantity, backordered quantity, selected warehouse id when allocated, planned ship date, `is_fully_allocated`, and a nonempty `plan_status`. Use `allocated`, `partially_allocated`, and `backordered` as the only initial statuses.

`ReplenishmentSuggestion` must stay conservative. Emit it only when `available_to_promise_after_plan` falls below `safety_stock_quantity` and there is either inbound inventory arriving after the planned ship date or no inbound inventory at all. The suggestion is descriptive and must not imply an automated purchase or transfer execution.

### Milestone 1: Create a shared commercial-demand boundary

This milestone makes planning possible without disturbing the current shipment-backed example. The end state is that Store has one explicit relation representing validated order demand after customer, product, and promotion enrichment but before warehouse or shipment decisions.

Edit `examples/store/transforms/order.py` only if the enrichment logic up to `OrderWithPromotion` must be shared directly. The implemented path keeps `EnrichOrders` public and behaviorally unchanged, and adds `examples/store/transforms/fulfillment/demand/PrepareOrderDemand.py` as the planning-demand boundary. It repeats the enrichment stages through promotion so shipment-backed publication and planning demand remain plainly separate.

Create grouped schema modules under `examples/store/schemas/fulfillment/`: `demand/demand.py`, `planning/inventory.py`, `planning/intermediate.py`, `planning/plan.py`, `analytics/summary.py`, and `reconciliation/reconciliation.py`. Keep schema names aligned with the business facts above. Update package exports so the public example package exposes the new schema classes.

Update `tests/helpers/example_projects.py` so the Store generated-project renderer knows about the new schema modules and the new transforms. Do not add any `res/` fixture or source-model dependency.

Acceptance for this milestone is that a caller can run `PrepareOrderDemand` with orders, customers, products, blocked products, and promotions, and get one demand row for a valid order even when no shipment exists. The current `EnrichOrders` differential test must still pass unchanged.

### Milestone 2: Add deterministic fulfillment planning

This milestone adds the main planning behavior. The end state is that Store can decide whether each demand line is allocated, partially allocated, or backordered based on warehouse and inventory facts.

Implement `PlanFulfillment` in `examples/store/transforms/fulfillment/planning/PlanFulfillment.py`. Start by computing available-to-promise per warehouse and product as:

    available_to_promise = max(on_hand_quantity - reserved_quantity, 0)

For the first version, inbound inventory does not increase the quantity available for immediate allocation; it only informs planned ship date and replenishment suggestions. This keeps the first planning contract truthful and simple. If no warehouse has positive available-to-promise, emit a `FulfillmentBackorder` row for the full requested quantity and a `FulfillmentPlan` row with status `backordered`. If the best warehouse has enough quantity, emit one `FulfillmentAllocation` row and a `FulfillmentPlan` row with status `allocated`. If it has some but not enough quantity, emit one allocation row for the available quantity, one backorder row for the remainder, and a plan row with status `partially_allocated`.

Planned ship date should be `order.business.order_date` when the line is fully allocated immediately. For partial or full backorders, use the earliest inbound `expected_at` for the selected warehouse and product when present; otherwise leave planned ship date null. Keep this behavior explicit in docs and tests so no one mistakes it for a guaranteed promise.

Implement `ReplenishmentSuggestion` as a separate output of `PlanFulfillment`. A suggestion should include tenant, warehouse id, product id, `available_to_promise_after_plan`, `safety_stock_quantity`, earliest inbound date if any, and a nonempty `reason` such as `below_safety_stock_after_allocation` or `backorder_without_inbound`.

Acceptance for this milestone is a focused scenario with three orders: one fully allocated, one partially allocated, and one fully backordered. The output rows must show exactly those three statuses and the correct allocated and backordered quantities.

### Milestone 3: Add planning analytics and plan-versus-actual reconciliation

This milestone turns planning facts into operational summaries and preserves the separation between planning and execution. The end state is that Store can summarize service risk daily and compare planned lines with actual shipment-backed fulfillment.

Implement `FulfillmentAnalytics` in `examples/store/transforms/fulfillment/analytics/FulfillmentAnalytics.py`. `DailyFulfillmentSummary` should group by tenant and business date and report demand line count, allocated line count, partially allocated line count, backordered line count, requested units, allocated units, backordered units, fill rate, and backorder rate. `WarehouseLoadSummary` should group by tenant, warehouse, and business date and report planned line count, allocated units, distinct products, and customer count.

Add a focused reconciliation output that compares planning with actual execution without changing `EnrichOrders`. This lives in `examples/store/schemas/fulfillment/reconciliation/reconciliation.py` and `examples/store/transforms/fulfillment/reconciliation/ReconcileFulfillmentPlan.py` as `PlannedActualReconciliation`. It joins `FulfillmentPlan` with `OrderFulfillment` by tenant and order id and reports whether a planned line later shipped or was not observed in shipment facts. Because `Shipment` does not currently carry warehouse identity, the first version intentionally avoids pretending to have warehouse-level actuals.

Acceptance for this milestone is a fixture where one planned line later appears in shipment facts and another does not. The reconciliation output must distinguish those outcomes, and the daily summary must reflect the same allocated/backordered units as the detailed plan rows.

This milestone makes the new capability visible and reviewable as a shipped example. The end state is updated documentation, generated source, differential tests, and repository validation.

## Validation and Acceptance

The feature is accepted when a caller can run the planning path without any shipment facts and observe valid order demand becoming a planning result with explicit allocation or backorder status. A fully stocked case must produce `plan_status == "allocated"` with `allocated_quantity == requested_quantity` and `backordered_quantity == 0`. A low-stock case must produce `plan_status == "partially_allocated"` with positive allocated and backordered quantities. A no-stock case must produce `plan_status == "backordered"` with null selected warehouse only if no warehouse option had stock and no warehouse tie-break winner was selected for future supply.

The example must also preserve the existing actual-fulfillment path. `EnrichOrders` must still require shipment facts to publish fulfilled lines, and its current differential test must keep passing. This proves the planning layer extends Store rather than replacing it.

Generated Store output must remain current. The rendered package under `examples/structure_generated/store/` must include the new fulfillment schemas and transforms. The generated-output golden test must pass, and the planning transform’s generated code must contain schema assertions and deterministic tie-break behavior visible as ordered comparisons or explicit preferred-option selection logic.

The repository build is accepted when the focused Store tests, generated-output checks, static checks, and `make build` pass, except for unrelated pre-existing failures that are documented in this plan.

## Idempotence and Recovery

This plan is additive. New schema and transform files can be created and imported repeatedly without mutating external state. The planning transforms are pure over caller-provided DataFrames, so re-running them with the same rows must yield the same outputs.

If a partial edit breaks Store imports, first restore module exports in `examples/store/schemas/__init__.py` and renderer registrations in `tests/helpers/example_projects.py`, then rerun the import checks before touching generated artifacts. Never hand-edit files under `examples/structure_generated/store/`; regenerate them from source registration. If a new planning schema or transform proves too large, split it into a new Store module rather than broadening the scope of `order.py` further.

Because this work intentionally does not touch `res/`, recovery should never require changing the shared testing model. Keep failures localized to `examples/store`, `tests/differential/store`, `tests/helpers/example_projects.py`, and generated Store outputs.

## Artifacts and Notes

The planning invocation should have this shape:

    demand = PrepareOrderDemand(
        orders=orders,
        customers=customers,
        products=products,
        blocked_products=blocked_products,
        promotions=promotions,
    ).run(session).demand

    plan = PlanFulfillment(
        demand=demand,
        warehouses=warehouses,
        inventory_positions=inventory_positions,
        inbound_inventory=inbound_inventory,
    ).run(session)

    allocations = plan.allocations
    backorders = plan.backorders
    plans = plan.plans
    replenishment_suggestions = plan.replenishment_suggestions

The existing execution path remains separate:

    published = EnrichOrders(
        orders=orders,
        customers=customers,
        products=products,
        blocked_products=blocked_products,
        promotions=promotions,
        shipments=shipments,
    ).run(session).published

The future implementation must keep these meanings distinct in code, docs, and tests:

- `OrderDemand` means “commercially valid line ready for fulfillment planning.”
- `FulfillmentPlan` means “decision about how the line should be fulfilled.”
- `OrderFulfillment` means “actual shipped line observed in shipment facts.”
- `OrderPublished` means “actual fulfilled line exposed by the current Store example.”
