## Purpose / Big Picture

Dedicated model schema files remain Structure's recommended source layout. Some
developers nevertheless want a schema used by one transform only to live beside
that transform. Structure will accept that module-level layout without changing
the established examples that teach dedicated schema modules.

The completed behavior is visible through one focused recipe and through
`structure check` and `structure compile`: a colocated intermediate schema is
discovered, validated, rendered, documented, and traced like any other schema.
A `Schema` class nested inside a `Transform` fails early with an actionable
diagnostic.

## Surprises & Discoveries

- Observation: The accepted module-level form already has the identity and generated-artifact behavior it needs.
  Evidence: `DiscoverStructureProject` scans module dictionaries for locally declared `Schema` and `Transform` classes.
- Observation: Nested schema classes currently fail late and inconsistently.
  Evidence: module discovery omits them, postponed annotations cannot resolve them from a method global namespace, and
  generated rendering expects every schema in the discovered schema-module mapping.
- Observation: The step-call guard scans loaded transform classes as well as the active transform.
  Evidence: an unrelated transform with an unresolved postponed annotation could make a later compilation fail while
  the guard classified its step method. The guard must ignore unresolved annotations outside the active compilation.

## Context and Orientation

A source module is an importable Python file under a configured source root.
Structure recommends separate model schema modules and transform modules. A mixed
module is an accepted alternative that declares both a module-level intermediate
schema and a transform. Discovery records the schema under that source module;
PySpark generation then emits separate `pyspark/schemas/<module>.py` and
`pyspark/transforms/<module>.py` files.

`CompileTransform` reads method annotations. A class-body schema such as
`NormalizeOrders.OrderNormalized` is not a direct module member and cannot
reliably be resolved by postponed annotations. It must be rejected before method
inspection rather than supported with a second ownership and naming model.

## Interfaces and Dependencies

No public callable API, configuration key, or generated naming rule changes.

- Dedicated schema modules remain recommended.
- Module-level schemas beside a transform are accepted and retain normal validation, generation, documentation, and traceability semantics.
- Class-body schemas nested in a transform fail with `DSL-E0402` and a remediation that recommends a model schema file while allowing same-file module scope.
- No recursive nested-schema discovery, owner-qualified generated constants, or compatibility alias is added.

model schema files are recommended, show model input/output schemas imported
into a transform module, and declare only the transitory intermediate schema at
module scope. It must explain that the schema remains in generated artifacts and
that class nesting is unsupported.

Third, add a helper in `CompileTransform`, called after confirming the subject is
a `Transform` and before pipeline or annotation processing. Inspect every
effective transform owner in its MRO. Reject a direct member only when it is a
non-base `Schema` subclass from that owner's module and its qualified name begins
with the owner's qualified name plus a dot. This avoids rejecting an imported
schema merely assigned as a class attribute. Use `DSL-E0402` with a problem that
names the nested schema and a fix that says to move it to module scope, preferably
in a model schema file.

Finally, add a focused source-layout user-story test with model input/output
schemas and a colocated intermediate schema. Prove discovery, check, compile,
generated schema import, generated docs, traceability, and `--fail-on-diff`.
Add negative cases for direct, postponed-annotation, and inherited nested schemas
plus an external-schema class-attribute false-positive guard. Keep the global
step-call guard from resolving unrelated invalid postponed annotations; the
active transform still validates its own annotations normally.
