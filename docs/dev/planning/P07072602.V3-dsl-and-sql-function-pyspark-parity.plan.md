# Implement v3 DSL and SQL Function PySpark Parity

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement the v3 DSL and SQL
function gap-closure slice from this file and the current working tree.

## Purpose / Big Picture

After this plan is complete, Structure users can keep common scalar PySpark Column and SQL function logic inside the
compiler-visible DSL instead of dropping into hooks for ordinary predicates, casts, ordering, string operations,
date/time arithmetic, and numeric helpers. The work closes the `DSL` section of `docs/dev/Gaps.md` for items marked
`planned` while preserving Structure's rule that expressions must remain symbolic, typed, backend-capability checked,
explainable, and readable in generated code.

Users can see the result by compiling an orders-style transform that uses membership predicates, range predicates,
string matching, collection indexing, rich casts, explicit ordering modifiers, substring/split/regexp replacement,
date/time helpers, numeric helpers, and predicate helper functions, then running online/generated parity tests against
PySpark 3.5.x and 4.0.x.

## Context and Orientation

Structure is a Python library that lets users write typed transform classes and run them online with PySpark or emit
generated PySpark source. Compiler-visible expressions are captured during symbolic execution. A symbolic expression is
a Python object that represents a Spark expression without running Spark immediately.

The relevant source areas are:

- `src/structure/app/dsl`: public DSL helpers and user-facing model objects.
- `src/structure/app/compiler/symbolic_execution`: symbolic row and expression capture.
- `src/structure/app/compiler/ir`: intermediate representation models used after source capture.
- `src/structure/app/target/pyspark`: shared online/generated PySpark lowering.
- `src/structure/app/compiler/diagnostics`: structured diagnostics and documentation links.
- `src/structure/app/target/capabilities`: backend capability checks.
- `res/testing/model/v2/orders` and later v3 fixtures: source and generated examples.
- `docs/dev/Gaps.md`: source gap list for this plan.
- `docs/CompatibilityTables.md`: public compatibility table to update when helpers move from planned to implemented.

Terms used in this plan:

- A Column API helper is a method-like operation that PySpark exposes on `Column`, such as `isin(...)` or `between(...)`.
- A SQL function helper is a function-like operation that PySpark exposes under `pyspark.sql.functions`, such as
  `substring(...)` or `date_add(...)`.
- Backend capability means a named feature flag that says whether a configured target profile supports an operation.
- Online execution means Structure directly applies PySpark operations at runtime. Generated execution means Structure
  writes PySpark source that a project can import and run later.

## Plan of Work

Milestone 1 implements planned Column API helpers. Add symbolic support for membership predicates, range predicates,
string predicates, collection indexing, struct field helpers, rich casts, and ordering modifiers with null-ordering
variants. Membership predicates must accept typed literals and compiler-visible expressions. Collection indexing must
infer element type for arrays and nullable value type for maps. Rich casts must distinguish strict casts from
`try_cast(...)` so diagnostics and nullability are honest.

Milestone 2 implements planned SQL function helpers. Add broader string helpers, date/time helpers, numeric/math
helpers, and predicate helper functions. Keep regex behavior explicit: helpers that accept regular expressions must
name that fact in the source API and diagnostics. Date/time helpers must validate that date, timestamp, interval, and
integer operands are sensible before lowering.

Milestone 3 adds shared lowering and capability checks. Every helper must lower through the shared PySpark recipe path
so online and generated execution stay equivalent. Do not add separate ad hoc online and generated implementations.
For any helper whose behavior differs between PySpark 3.5.x, PySpark 4.0.x, classic Spark, and Spark Connect, add a
capability check or explicit diagnostic before runtime.

Milestone 4 updates diagnostics, explain, traceability, and streaming classification. Unsupported Python truthiness,
raw SQL strings, raw aliases, and raw `Column.over(...)` must continue to fail with actionable messages that point to
compiler-visible alternatives. Explain output should show the helper name and relevant operands without becoming a
verbatim expression dump.

Milestone 5 updates public evidence. Add user-story tests, generated PySpark snapshots, online/generated parity tests,
API snapshots, compatibility tables, public reference docs, and v3 fixture examples. The fixture should contain a
compact transform that exercises all admitted helper families in readable source.

## Validation and Acceptance

The plan is accepted when all `planned` DSL gaps in `docs/dev/Gaps.md` are either implemented or explicitly narrowed in
this plan with rationale, and when `make build` passes.

Behavioral acceptance:

- `isin(...)`, `between(...)`, string predicates, collection indexing, struct field helpers, casts, and ordering
  modifiers compile to visible PySpark Column operations.
- String, date/time, numeric, and predicate SQL helpers compile to visible `pyspark.sql.functions` operations.
- Online and generated execution produce equal schemas and rows for every admitted helper family.
- Unsupported raw SQL, raw aliases, raw `Column.over(...)`, raw Python truthiness, and arbitrary Python behavior still
  fail before runtime with diagnostic links.
- Compatibility tables and public references show the admitted v3 helper surface.

## Idempotence and Recovery

The work is additive. Re-running tests, generated snapshots, and API snapshots is safe. If a helper proves ambiguous or
target-specific, keep it behind a backend capability diagnostic rather than rendering partial PySpark. If a public
helper name is exported accidentally, remove the export and restore the snapshot instead of accepting accidental API.

## Interfaces and Dependencies

Use existing Structure expression, IR, backend capability, recipe, explain, and diagnostic infrastructure. Do not add a
runtime dependency that makes compiler commands import PySpark, start Java, or create a SparkSession. New helpers must
be available through the same public import style as existing DSL helpers only after tests and docs are in place.
