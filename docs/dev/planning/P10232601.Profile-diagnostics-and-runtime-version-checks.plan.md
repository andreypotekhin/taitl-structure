# Clarify PySpark profile guidance and validate runtime versions


This ExecPlan follows [Plans.md](../auto/Plans.md). Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` current as implementation proceeds.

Status: implementation complete; live validation in progress, 2026-10-24.

## Purpose / Big Picture


Users targeting a broad PySpark profile should learn exactly which configuration change enables a supported feature.
Users executing against a different Spark version should receive a useful diagnostic before Structure builds Spark
plans or performs effects. Add one configurable runtime check with exception, error-log, and opt-out modes, shared
by online and generated execution.

The project default remains `>=3.5,<4.2`. Features admitted for exact `>=4.1,<4.2` targets retain those gates. This work
does not decide whether the default should instead target the latest validated minor release, add automatic runtime
profile selection, accept arbitrary version ranges, promote feature support, or change state/sink interfaces.

## Surprises & Discoveries


Capability profiles are recognized by specific strings in
`src/structure/plugin/pyspark/capabilities/model/PySparkCapabilities.py`; they are not a general version-range engine.
The current default is `>=3.5,<4.2`, and exact `>=4.1,<4.2` selects the admitted 4.1 feature set.

Direct inspection of `supports(...)` under the default found useful profile remedies for callbacks, scalar helpers,
TIME, Arrow UDFs, and observations. Queries incorrectly say their parity gate has not passed. KLL/Theta, row state,
and Connect checkpointing can fall through to guidance suggesting a hook or waiting for a specification. Apache
spatial guidance is less specific than its structured `required_target`. Provider guidance can incorrectly suggest
switching to ordinary execution when Connect 4.1 is admitted.

`BackendCapabilityError` currently initializes its exception message from `decision.problem`, omitting the actionable
`use` text. `BackendDiagnostic.to_diagnostic()` does not carry its specific `why` into the general diagnostic's
rendered explanation. Correcting decision strings alone therefore does not ensure users see the correction.

`StructureSession.run(...)` compiles and materializes schemas before invoking the PySpark executor. A check placed
only inside `ExecutionAPI.execute(...)` can run too late for version-specific Python type constructors. Generated
classes also have several rendering shapes, including `mirror_methods`, and can be used without `StructureSession`.

There is no general runtime version/profile check. Delta validates Spark/Delta package pairs, some state helpers
check method availability, and integration tests assert runner pins. These checks have different purposes and remain
necessary after the new guard is added.

## Context and Orientation


A profile is the configured set of runtime versions for which a transform is compiled. A capability is an operation
that Structure has admitted for that profile and execution variant. `ordinary` uses local PySpark APIs; `spark-connect`
uses a Python client talking to a remote Spark engine. Being inside the broad default profile does not enable every
operation introduced in one of its later versions.

`PySparkCapabilities.supports(...)` constructs `CapabilityDecision` objects. The core capability models live under
`src/structure/core/target/capabilities/model/`; diagnostic rendering and registration live under
`src/structure/lib/cross/errors/`. Keep `BACKEND-E2402` for unsupported capabilities and preserve structured fields
used by callers and tests.

`src/structure/core/runtime/session/model/StructureSession.py` dispatches actual execution through a selected plugin.
`src/structure/plugin/pyspark/api/ExecutionAPI.py` dispatches online and generated PySpark execution. Its compiler API
already validates plugin-specific options and produces `PySparkExecutionPlan`. Core configuration treats plugin
tables as opaque, so the PySpark plugin must validate the new option's values.

Generated transform classes are rendered in
`src/structure/plugin/pyspark/render/logic/modules/RenderPySparkTransformModule.py`. Their shared runtime source is
`src/structure/plugin/pyspark/resources/runtime.py.template`. Generated schema constants can execute Python type
constructors at import time; keep this distinction visible when documenting standalone generated execution.

## Behavior and Configuration


The supported configuration is:

    [tool.structure.plugin.pyspark]
    profile = ">=4.1,<4.2"
    variant = "ordinary"
    runtime_version_check = "raise"

`raise` raises `StructureRuntimeError` on version mismatch or unavailable/unparseable version information, before
Structure performs the transform's Spark work. It does not additionally log the same failure. `log` emits the same
diagnostic at Python logging level `ERROR` and continues execution. This mode cannot make an incompatible operation
work; native Spark/Python failures can still occur. `off` performs no version discovery, version-related remote
request, comparison, or version-check logging.

Invalid policy values and unsupported configured profiles remain configuration/capability errors in every mode.
Neither `log` nor `off` disables compilation gates, provider validation, schema validation, or native runtime errors.
Use the existing configuration precedence and opaque plugin table merge rules; add no separate environment switch
or top-level legacy alias. Include the explicit default in newly generated and seed configuration.

At runtime read the Python client's `pyspark.__version__` lazily and the supplied session's public `spark.version`.
Do not create or stop a session, run SQL or DataFrame actions, or use SparkContext, private Connect state, JVM handles,
RDDs, or Py4J to discover versions. A Connect metadata request through `spark.version` is permitted; it is not a
query action. Version discovery failures must identify the failing source and respect the selected policy.

Represent the existing supported profiles as explicit inclusive lower/exclusive upper numeric release bounds shared
with the capability profile registry. Do not implement general range syntax in this task. Parse an anchored numeric
major/minor release with an optional patch, using zero for an omitted patch; retain the original version text. Compare
release components, including for vendor/build suffixes after the release. Reject empty, non-string, or nonnumeric
values as unknown versions. A successful membership check does not certify vendor distributions or prerelease
behavior; existing independent evidence gates still apply. Never interpret a Databricks Runtime release number as
the Spark version when the session reports its underlying Spark version.

Register `PYSPARK-E2710` for versions outside the configured profile and `PYSPARK-E2711` for version discovery or
parsing failure; these codes were unused when this plan was written. Include the configured profile, configured
variant, observed client and engine versions, failing component, execution mode, and transform when available.
The remedy must identify `[tool.structure.plugin.pyspark]`, explain how to choose a profile matching the intended
runtime or install/connect to a matching runtime, and describe `log`/`off` as deliberate overrides. Include direct
public diagnostic and troubleshooting links. Do not include connection strings or credentials.

Use the standard-library logger `structure.plugin.pyspark.runtime` without configuring the application's logging
handlers or root level. Cache successful version discovery and completed checks for the runtime object's lifetime,
profile, and policy; use weak references or explicit session-owned state to avoid retaining stopped sessions. Avoid
duplicate error logs when session execution enters a generated class. A different runtime object, profile, or policy
must be evaluated independently. Do not cache transient discovery failures; an unavailable server can recover.

## Plan of Work


### Milestone 1: Actionable capability diagnostics


Replace generic fallbacks for supported target-dependent operations with remedies derived from their actual admitted
profiles and variants. Cover Column callbacks, the five scalar additions, TIME type/helpers, Arrow modes, query
operations, observations, KLL/Theta operations and schema types, row/Pandas state families, spatial operations and
types, materialization, and Connect provider admissions. A profile error must name the configured profile and the
profile that enables the requested operation. A true unsupported operation must retain its real status and remedy.

Use `plugin.pyspark.profile` and `plugin.pyspark.variant` in text and show the `[tool.structure.plugin.pyspark]` TOML
table where configuration is demonstrated. Remove obsolete instructions to set top-level `target_profile` or
`target_variant`. Queries must report the target mismatch rather than falsely saying parity is pending. KLL/Theta
must point to the exact 4.1 target and public aggregation documentation. Arrow guidance must link the UDF reference.
State guidance must distinguish ordinary row 4.1, ordinary Pandas 4.0/4.1, and independent legacy evidence gates.

Do not collapse all remedies into a blanket 4.1 recommendation: Connect checkpointing is admitted on exact 4.0 and
4.1 profiles, native spatial schema constructors have provider/runtime requirements, and Connect Delta/Iceberg have
their own exact 4.1 admissions and dependencies. Retain caller-configured Spark TIME/spatial settings in relevant
secondary guidance; selecting a profile does not enable those flags.

Make the specific reason, code, current target, remedy, and documentation survive decision conversion, Python
exception rendering, CLI text, and machine-readable diagnostic output. Preserve existing structured capability
fields and codes. Test real feature compilation and visible output, including an unknown operation and invalid
variant, rather than checking helper strings alone. This milestone must work with no installed PySpark.

### Milestone 2: Shared runtime guard and policy


Add a focused delegate at
`src/structure/plugin/pyspark/execution/logic/ValidatePySparkRuntime.py` for policy validation, runtime discovery,
profile comparison, structured errors, and logging. Reuse small profile metadata helpers from the capability model
rather than duplicating profile bounds in the executor and renderer. No new third-party dependency is needed for
the existing numeric profile intervals.

Add the option default to the PySpark plugin table in `StructureConfigDefaults`, the CLI config writer, and seed
configuration. Validate it through PySpark's plugin option handling before compilation or execution. Carry the
resolved policy into `PySparkExecutionPlan` with a default of `raise`, and ensure policy changes participate in
artifact fingerprints and cache selection.

With a real supplied Spark runtime, both detected versions must satisfy the profile. Failure to determine either
version is not success. When there is no supplied Spark runtime, retain existing missing-runtime and injected
executor behavior without attempting to import PySpark; a synthetic executor does not establish live compatibility.
Tests using supplied fake Spark runtimes must provide deliberate version probes or explicitly select `off`, rather
than adding a production heuristic that silently exempts mocks.

At the end of this milestone, Spark-free tests with stub sessions prove all three policies, independent client/server
membership, lower/upper boundaries, version suffix handling, unknown versions, log severity, and discovery caching.

### Milestone 3: Execution ordering and generated parity


Introduce an optional executor method `validate_runtime(request: ExecutionRequest) -> None`. Before compilation on
actual execution paths, `StructureSession` calls this method if present, with `payload=None`, its existing runtime
wrapper, invocation, and execution mode. Document that the preflight method must not depend on a lowered payload.
Existing executor plugins without the method remain valid; do not add a mandatory member to the existing executor
protocol. Keep Spark-specific inspection inside PySpark's implementation of the optional method.

Cover normal invocation, source-address execution, alternate plugin routing when it selects PySpark, batch handoff
execution, pipelines/composition, cached artifacts, and parent/child sessions. Perform preflight before compiling or
materializing runtime schemas so a 4.1 target on Spark 4.0 produces the profile diagnostic before a missing TIME type
constructor or generated import error. Keep `StructureSession.compile(...)` and CLI check/compile/docs free of
version discovery. Reuse the guard in the PySpark execution adapter so direct adapter execution cannot bypass it.

Emit the compiled target profile, variant, and runtime policy into generated class metadata and invoke the same
guard before constructor-time Spark work, optional input creation, UDF setup, hooks, step methods, and effects.
Cover legacy, inherited, and `mirror_methods` rendering. Re-export the shared guard through the generated runtime
template instead of copying its implementation. Directly instantiated generated classes follow their compiled policy;
changing generated-mode configuration requires regeneration under the existing stale-artifact rules.

Do not inspect a Spark server during module import. Bare standalone generated imports can still encounter normal
Python dependency errors before a runtime is supplied, because schema constants are imported eagerly. Document
this import ordering explicitly; the early `StructureSession` preflight protects session-driven generated loading,
and the generated class guard protects execution once standalone import succeeds. Do not claim universal protection
for arbitrary user imports or change schema-module initialization as part of this task.

After this milestone, a counter placed in a hook, a DataFrame stub, or a table-effect stub remains zero after a
`raise` failure. Equivalent online and generated executions report the same code and version context; `log` continues
and `off` performs no probing. No generated code accesses classic-only Spark internals.

## Validation and Acceptance


Under the default profile, using a supported exact-4.1 feature must produce `BACKEND-E2402` with a truthful current
profile explanation and a copyable `profile = ">=4.1,<4.2"` remedy under the canonical plugin table. This must be
visible in direct Python exceptions and CLI output and preserved in structured diagnostics. The same feature must
be admitted after changing to an evidenced exact profile and variant. Invalid ranges such as `>=4.0` still receive
supported-profile guidance, rather than being silently narrowed or treated as compatible with future releases.

With profile `>=4.1,<4.2`, client 4.1.0, and engine 4.0.0, `raise` must report `PYSPARK-E2710`, identify the engine
mismatch, and leave all execution counters untouched. Reversing the client/engine versions must identify the client.
Matching 4.1 versions must pass; engine/client 4.2.0 must fail the upper bound; the broad default must accept its
validated 3.5, 4.0, and 4.1 release lines. Unknown or failed version reads use `PYSPARK-E2711` and the same policy.

For the same mismatch, `log` produces an ERROR record containing the diagnostic code and actionable remedy, then
allows a common transform to execute. Duplicate entry through session and generated class validation must not
duplicate the log. `off` must leave throwing version-property stubs untouched and emit no version-check log. Modes
do not suppress normal feature gates or unrelated runtime failures. Missing PySpark versions, unusual suffixes,
policy changes, runtime replacement, and transient discovery recovery require explicit tests.

Compile/check/docs tests must demonstrate zero client imports and zero version reads when performing static work.
Generated-code tests must prove the guard ordering and the documented standalone-import limit. All six live lanes
and admitted provider phases must pass with explained skips, and the final integration-enabled build and diff checks
must succeed. A passing version check must never be presented as managed Databricks parity evidence.

## Idempotence and Recovery


The guard reads metadata and changes no Spark settings or lifecycle state. Tests create disposable artifacts and
capture logs locally. Cache state must not retain runtime objects or mask a changed target/policy. Repeating commands
is safe. Regenerate changed generated-mode artifacts after changing the compiled policy; preserve caller-owned
Spark sessions, streaming checkpoints, and feature work in other chats.

## Interfaces and Dependencies


The public addition is the PySpark plugin option `runtime_version_check: Literal["raise", "log", "off"] = "raise"`.
The optional executor preflight receives an `ExecutionRequest` whose payload is `None` before compilation. Existing
plugins remain compatible. The shared PySpark guard accepts a supplied Spark session plus resolved profile, variant,
policy, transform label, and execution mode; it returns normally or raises `StructureRuntimeError` and owns policy
logging. The implementation uses the existing runtime diagnostic/registry/rendering machinery, Python logging,
numeric profile metadata, and lazy PySpark access. No new Spark service, lifecycle ownership, third-party dependency,
automatic profile inference, or mandatory executor API member is introduced.
