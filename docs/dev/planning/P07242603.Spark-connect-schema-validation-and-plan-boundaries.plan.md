# Make Spark Connect Validation Fast Without Growing Query Plans

This ExecPlan is a living document. Maintain it according to `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` accurate whenever work stops or a design fact changes.

## Purpose / Big Picture

Spark Connect currently spends most of a complex transform's time asking the remote server for intermediate DataFrame schemas. After this change, a Connect user gets strict input and final-output validation by default, far fewer intermediate remote checks, and a safe way to request the existing exhaustive intermediate diagnostics. The implementation must also prevent Connect from receiving an ever-growing serialized logical plan; a logical plan is Spark's deferred description of the query, sent from the Python client to the remote server.

The user-visible proof is a multi-step Connect transform such as `tests/integration/pyspark/search/test_search.py`: it passes without a Java heap error, its input and final result still reject a wrong schema, and its focused Connect duration is substantially below the recorded 283 seconds for the main test on Spark 3.5.

## Surprises & Discoveries

- Observation: 990 `DataFrame.schema` calls consumed 211.7 seconds in the profiled Spark Connect 3.5 lane; 1,027 remote analysis calls consumed 182.1 seconds.
  Evidence: `cProfile` report from the 2026-07-24 integration run.
- Observation: test-level frame persistence consumed only 1.07 seconds and cannot explain the multi-minute result.
  Evidence: 15 `persist()` and 13 `unpersist()` calls in the same profile.
- Observation: disabling every intermediate schema assertion caused Spark Connect 3.5 to fail with `Java heap space` while formatting a large protobuf logical plan.
  Evidence: focused `test_text_fixture_runs_online_and_generated` failed after about 245 seconds; the Connect server stack trace ends in `TextFormat.Printer`.
- Observation: Spark Connect 3.5 exposes no DataFrame checkpoint API.
  Evidence: `pyspark.sql.connect.dataframe.DataFrame` has neither `checkpoint` nor `localCheckpoint`.

## Decision Log

- Decision: Treat schema checking and logical-plan boundaries as independent policies.
  Rationale: a projected DataFrame may be optimizer-collapsible, while a schema inspection is an expensive RPC rather than a reliable materialization boundary.
  Date/Author: 2026-07-24 / project owner and Codex.
- Decision: Keep strict input and final-output validation in every mode.
  Rationale: they are the user-facing contract boundary; intermediate checks are diagnostics and performance trade-offs.
  Date/Author: 2026-07-24 / project owner and Codex.
- Decision: Prototype a session-scoped temporary-view boundary before changing default validation behavior.
  Rationale: creating a temporary view remotely and reading it back through `spark.table(name)` replaces the client-side nested plan with a compact relation reference; unlike a projection, this is a real protocol boundary.
  Date/Author: 2026-07-24 / Codex.

## Context and Orientation

`src/structure/plugin/pyspark/execution/logic/running/RunOnlinePySparkTransform.py` executes online recipes. It calls `ValidatePySparkFrame.validate`, which reads `df.schema`; in Connect that is a remote analysis request. Generated transforms render equivalent `assert_schema(...)` calls from `src/structure/plugin/pyspark/render/logic/modules/RenderPySparkTransformModule.py` and `src/structure/plugin/pyspark/render/logic/steps/RenderPySparkStep.py`.

`PySparkValidationRecipe` records a validation target, schema, schema mode, projection request, and reason. The PySpark compiler lowers transform steps through `LowerPySparkPlan` and `MapPySparkValidation`. A *temporary view* is a name held by one Spark session; creating it sends the accumulated plan once, while reading it later sends only the name. The view must remain alive while lazy output DataFrames reference it and must be removed when the Structure session ends.

The existing public setting `validate_intermediate` means exhaustive intermediate validation. Do not redefine it to mean a plan-boundary policy. Add a distinct PySpark-plugin option for Connect plan boundaries.

## Plan of Work

### Milestone 1: Prove a safe Connect boundary

First remove any incomplete experimental `check` fields or dormant default overrides from the working tree so the baseline remains unchanged. Add an integration-only prototype helper under `tests/integration/pyspark/support` that receives a Connect DataFrame, creates a unique session-scoped temporary view, returns `spark.table(view_name)`, and records the view name for cleanup after the test. Use a UUID-derived name and `spark.catalog.dropTempView` in a `finally` block.

Apply the helper at a small number of high-fan-out search intermediates, never at every step. Run the focused search test on Connect 3.5 and 4.0. Promote this approach only if it passes without heap errors, preserves rows and schemas, and improves the Connect 3.5 first-test time by at least 30 percent. If it fails, retain the evidence and investigate a server-side cache relation rather than changing validation defaults.

### Milestone 2: Make validation policy explicit

Add a PySpark plugin option `connect_plan_boundaries` with values `off`, `auto`, and `strict`; reject other values in the PySpark plugin configuration validator. `auto` is the Spark Connect default and `off` is the ordinary-PySpark default. `strict` means a boundary after every non-final step and is diagnostic-only, not the default.

Keep `validate_intermediate = true` as the exhaustive schema-assertion opt-in. For Connect with the default `validate_intermediate = false`, compiler lowering must preserve step metadata and requested projection, render no intermediate `assert_schema` call, and request an `auto` boundary only at high-fan-out or configured-size threshold candidates. Input and output validation recipes always retain assertions. Both `RunOnlinePySparkTransform` and generated rendering must consume the same lowered policy so parity remains exact.

Extend `StructureSession` with private session-owned temporary-view tracking and an explicit public `close()` method if one does not already exist. `close()` must drop every Structure-created view before stopping or releasing the Spark session; it must be idempotent. Do not drop a view before a returned lazy DataFrame can execute. Document that callers using long-lived sessions should call `close()` when they no longer need Structure results.

### Milestone 3: Diagnostics, docs, and regression tests

Update `docs/Configuration.md` and the Spark Connect troubleshooting section. Explain that input/output checks remain strict, `validate_intermediate = true` restores exhaustive assertions, and `connect_plan_boundaries` controls only Connect plan containment. Include a short TOML example.

Add compiler tests that inspect lowered recipes and generated source: ordinary PySpark retains intermediate assertions; Connect default omits them but emits the boundary helper; explicit intermediate validation restores them. Add fake-frame online-runtime tests proving input/output are validated and intermediate checks follow the policy. Add Connect integration tests proving temporary views are unique, remain available until session close, and are removed afterward.

## Validation and Acceptance

Acceptance requires all of the following:

- Default Connect execution validates malformed inputs and final outputs but does not emit intermediate `assert_schema` calls.
- `validate_intermediate = true` emits and executes every intermediate assertion as it does today.
- Connect plan-boundary tests prove that a returned lazy DataFrame can execute before `StructureSession.close()`, and its temporary views no longer exist afterward.
- The focused Connect 3.5 search test passes without `Java heap space` and is at least 30 percent faster than the recorded 283.23-second unprofiled baseline.
- Ordinary PySpark behavior and generated/online parity remain unchanged.

## Idempotence and Recovery

Temporary view names must include a random session-local prefix so repeated tests cannot collide. Cleanup must tolerate an already-dropped view. If the prototype fails or is slower, remove it completely and leave `connect_plan_boundaries = off`; do not change validation defaults on unproven evidence.

## Artifacts and Notes

The pivotal baseline profile is: 990 schema accesses in 211.7 seconds, 150 collects in 118.5 seconds, and test-frame persistence in 1.07 seconds. This means reducing schema RPCs is worthwhile, but it cannot be used as an implicit plan-management mechanism.

## Interfaces and Dependencies

The final public configuration surface is:

    [tool.structure.plugin.pyspark]
    variant = "spark-connect"
    connect_plan_boundaries = "auto"

    # Optional exhaustive diagnostic mode.
    validate_intermediate = true

Use only the existing PySpark and Spark Connect dependencies. The temporary-view implementation must use the public Spark session methods `DataFrame.createOrReplaceTempView`, `SparkSession.table`, and catalog view deletion; do not access Spark private JVM handles.
