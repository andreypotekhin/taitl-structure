# Raw Pipe Bindings

This ExecPlan is a living document. Maintain it under `docs/dev/auto/Plans.md` as the implementation progresses.

## Purpose / Big Picture

Raw hooks will use the same `input=`, `output=`, and `inout=source | target` vocabulary as step methods. A hook can
request original inputs, current lanes, and materialized outputs by name without `pass_inputs=True` or a special
`inputs` namespace. Its native DataFrame method receives the named frames as keyword-only parameters and returns the
right-side frames in order.

## Surprises & Discoveries

- Observation: current raw hooks reduce their selectors to lane names before runtime, so they cannot distinguish an
  original input from a shadowing current lane.
  Evidence: `HookPlan` contains only `lanes` and `outputs`, while `PySparkHookInvoker` reads every argument from the
  one `frames` map.

## Decision Log

- Decision: `@raw(inout=left | right)` reuses the step-method pipe syntax. Left declarations are hook sources and
  right declarations are hook result destinations.
  Rationale: one public binding vocabulary is easier to learn and preserves the existing role selectors.
  Date/Author: 2026-07-11 / user and Codex.

- Decision: raw methods receive the ordered, de-duplicated union of left and right declaration names. Right-side
  declarations are therefore readable method parameters as well as destinations.
  Rationale: an after-hook must be able to inspect and replace a materialized output such as `output(products)`.
  Date/Author: 2026-07-11 / user and Codex.

- Decision: missing selected frames are compile-time errors at the hook's source-order location.
  Rationale: an output declaration alone does not create a DataFrame, and passing `None` would conceal a pipeline
  error.
  Date/Author: 2026-07-11 / user and Codex.

## Outcomes & Retrospective

Raw hooks now share step-style `input=`, `output=`, and `inout=sources | targets` bindings. The compiler lowers
original inputs to `input:name` runtime sources, retains current-frame sources separately, and passes the ordered,
de-duplicated binding names to the hook as keyword arguments. Generated and online execution use the same recipe.

`make build` completed successfully: mypy reported no issues; the main suite reported 602 passed and 9 skipped; the
additional build suite reported 19 passed; and Poetry built both the source distribution and wheel.

## Context and Orientation

`src/structure/app/dsl/model/transforms/transform_api.py` captures decorator metadata. `CompileTransform` turns that
metadata into a `HookPlan`; its source-order attachment places hooks before or after a compiled step. PySpark lowering
maps the plan to `PySparkHookRecipe`, and both generated code and online execution call the source Transform method.
The former `pass_inputs` flag adds a separate namespace of original inputs; this feature removes that namespace.

## Plan of Work

Update `raw` to accept the step-style binding options and preserve selector intent. Resolve each hook argument to a
runtime frame source during compilation: `input(x)` reads the original input, `lane(x)` reads the current lane, and
bare input declarations retain the normal shadowing rule. The compiler will include right-side targets in the method
argument list and validate that every requested frame exists at the hook boundary. It will retain result destinations
separately for return assignment.

Update the PySpark recipe, generated renderer, and online invoker to pass parameter-name/source pairs. Remove the
`HookInputs` helper and all plan flags that existed only for `pass_inputs`. Migrate hook examples and fixtures to
pipe bindings, then add focused tests for original-input access, right-side output arguments, shadowing selectors,
missing-frame diagnostics, generated calls, and online invocation.

## Validation and Acceptance

The following source must compile and invoke a raw method with `orders`, `customers`, and `products` keyword
arguments, then replace `customers` and `products` from its two returned DataFrames:

    @raw(inout=[orders, lane(customers)] | [lane(customers), output(products)])
    def add_extra_columns(self, *, orders, customers, products, spark, ctx):
        return customers, products

`@raw(inout=input(orders) | output(products))` must receive the original `orders` frame even when a current `orders`
lane exists. Selecting an output before it is materialized must fail with an actionable compiler diagnostic.

## Idempotence and Recovery

The edits are additive and test-driven. Re-running the commands is safe. If a migration leaves a legacy raw form,
the decorator should fail directly rather than silently retaining the removed `pass_inputs` behavior.

## Interfaces and Dependencies

The public interface is `raw(*, input=..., output=..., inout=..., schema_mode=..., project_output=...,
streaming_safe=..., target_backend=..., target_platform=...)`. Hook methods retain `self` followed by a bare `*`,
their declared DataFrame parameters, `spark`, and `ctx`. No new dependency is required.
