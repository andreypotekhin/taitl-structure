# Extend Store with Recommendations and Merchandising

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. Maintain this document according to `docs/dev/auto/Plans.md`.

This plan is intentionally parallel to `docs/dev/planning/P07302602.Extend-store-with-fulfillment-planning.plan.md`. The two efforts must not compete for the same new Store modules. Fulfillment planning owns warehouse, inventory, and fulfillment-planning files. This plan owns merchandising, recommendation, impression-feedback, and merchandising-evaluation files. Shared commercial inputs such as `Customer`, `Product`, `Promotion`, and existing Store order shapes remain in their current files unless both plans are explicitly reconciled in one later follow-up.

## Purpose / Big Picture

The current Store example begins at the order line. It shows how valid orders become fulfilled publication and daily analytics, but it does not show how a Structure application can decide which products to surface to a shopper, which candidates to suppress or boost, how catalog rules and promotions affect ranking, or how product impressions and clicks become reusable recommendation signals. After this work, a caller will be able to run a Store merchandising path that prepares candidate products, applies tenant-owned merchandising policy, ranks product recommendations, records impression and click evidence, and evaluates daily merchandising behavior.

This gives Store a second major branch beside fulfillment planning. Fulfillment planning answers “how do we ship demand?” This plan answers “how do we shape demand before the order exists?” The resulting example will demonstrate candidate preparation, filtering, staged scoring, recommendation output, feedback aggregation, and descriptive operational evaluation, all while preserving the current order-enrichment example and leaving `res/` unchanged.

## Surprises & Discoveries

- Observation: Search already uses the package shape the user wants: focused subpackages plus short public facades such as `transforms/index.py`, `transforms/score.py`, `transforms/search.py`, and `transforms/evaluate.py`.
  Evidence: `examples/search/transforms/` contains small facade modules and domain subpackages such as `chunking/`, `scoring/`, `searching/`, `evaluation/`, and `training/`.

- Observation: Store currently has a flat layout, so the cleanest way to parallelize new work is to add new subpackages for the new domains instead of reshuffling the whole example first.
  Evidence: `examples/store/` currently contains flat `schemas/*.py` and `transforms/*.py` files such as `order.py`, `analytics.py`, and `adv_analytics.py`, while the new fulfillment plan already reserves additional domain-specific files.

- Observation: Recommendations and merchandising fit Store well, but they need new pre-order event contracts that the current Store example does not yet have.
  Evidence: the existing Store schemas focus on orders, products, promotions, shipments, and fulfilled-line analytics; there is no product-impression, click, add-to-cart, or recommendation-run schema today.

- Observation: Store fulfillment work had already moved to grouped subpackages under `examples/store/schemas/fulfillment/`, so the renderer needed to use those current import paths before Store generation could run.
  Evidence: `render_store_example()` initially failed with `ModuleNotFoundError: No module named 'examples.store.schemas.fulfillment.intermediate'`; the current files live under `examples/store/schemas/fulfillment/planning/`.

- Observation: Structure aggregate steps require rate calculations to happen after aggregate totals are materialized.
  Evidence: compiling `BuildRecommendationSignals` and `EvaluateRecommendations` raised `DSL-E0402` for rate fields assigned from aggregate aliases in the same grouped step; splitting totals into `intermediate.py` schemas fixed the compile errors.

## Context and Orientation

The public Store example lives under `examples/store/`. Today it is mostly flat: `examples/store/schemas/order.py`, `product.py`, `promotion.py`, and `shipment.py` define source and enriched shapes, while `examples/store/transforms/order.py`, `analytics.py`, `adv_analytics.py`, and `rowset_join.py` define the current public transforms. Generated Store source is rendered through `tests/helpers/example_projects.py` into `examples/structure_generated/store/`. Public example differential coverage is currently in `tests/differential/store/test_store_reference_contract.py`.

The Search example under `examples/search/` demonstrates the package pattern this plan should follow. Search uses narrow domain folders for both schemas and transforms, plus short public facade modules that export a main pipeline or family entry point. In plain language, a facade here is a small module whose job is to give callers one easy import path, such as `examples.search.transforms.score`, while the detailed implementation stays in subpackages.

This plan introduces several plain-language terms that must be used consistently. A candidate is a product row that is eligible to be considered for recommendation before final ranking. A merchandising policy is a caller-owned set of boosts, suppressions, or caps that affect candidate ranking or eligibility. A recommendation impression is one product shown in one recommendation run at one position. A recommendation click is one click tied to one impression. A recommendation signal is a reusable aggregate derived from those impressions and clicks, such as impression count, click count, or exposure-adjusted click rate. A merchandising evaluator is a batch transform that summarizes how a recommendation run behaved; it is not a relevance-truth evaluator.

This plan must coexist with `docs/dev/planning/P07302602.Extend-store-with-fulfillment-planning.plan.md`. That fulfillment plan owns these new files and concepts: `examples/store/schemas/warehouse.py`, `examples/store/schemas/inventory.py`, `examples/store/schemas/fulfillment.py`, and `examples/store/transforms/fulfillment.py`. This merchandising plan must not create or edit those files as part of its mainline path. If a later consolidation becomes desirable, it belongs in a separate follow-up plan after both branches land.

Do not create a new facade that collides with the fulfillment plan’s proposed `transforms/fulfillment.py`. This plan owns only the merchandising-related package exports above.

The first implementation should use these transform responsibilities:

- `PrepareCatalog` prepares `CatalogProduct` rows from existing `Product`, `BlockedProduct`, and `Promotion` inputs.
- `SelectRecommendationCandidates` takes `RecommendationRequest`, `CatalogProduct`, merchandising policy rows, and suppressions, then emits `RecommendationCandidate` rows after applying tenant-scope eligibility.
- `RankRecommendationCandidates` applies transparent merchandising policy and feedback signals to candidates, delegating scoring formulas to `Ranker`.
- `Recommender` orchestrates candidate selection, ranking, result selection, and run summaries, then emits `RecommendedProduct` and `RecommendationRun`.
- `BuildRecommendationSignals` consumes raw recommendation impressions and clicks and emits daily impression/click facts plus `ProductRecommendationSignal`.
- `EvaluateRecommendations` orchestrates request selection, impression measurement, request measurement, and daily behavior summarization.

The first version must stay deterministic and transparent. Ranking tie-breakers for recommended products should be exactly:

1. higher final score,
2. lower suppression penalty,
3. higher inventory-availability boost when supplied,
4. product id ascending.

The initial final score should be a transparent weighted blend, not a learned model:

- base catalog score from product activity and promotion presence,
- optional merchandising boosts or suppressions from caller policy,
- optional click-feedback signal if sufficient impression support exists.

Do not introduce embeddings, collaborative filtering, or opaque model artifacts in the first version. The point is to demonstrate typed ranking evidence, not ML infrastructure.

### Milestone 1: Establish the parallel-safe package layout

This milestone creates the package structure and public entry points without yet implementing the full recommendation behavior. The end state is that Store contains a Search-like merchandising package family that can evolve independently from fulfillment planning.

Create the schema and transform package directories listed above. Add `__init__.py` files that expose the public schema classes and main transform classes, with CamelCase files reserved for single-component transform implementations.

### Milestone 2: Prepare catalog products and recommendation candidates

This milestone adds the pre-ranking side of merchandising. The end state is that a caller can supply tenant-scoped products, blocked-product rows, promotions, and one recommendation request and get a filtered candidate set.

Implement `PrepareCatalog` in `examples/store/transforms/merchandising/catalog/PrepareCatalog.py`. It should consume existing `Product`, `BlockedProduct`, and `Promotion` relations and emit `CatalogProduct` rows. A product must be tenant-scoped, active, and not blocked to remain eligible. Promotion attachment should remain descriptive and non-destructive: promotion presence can raise a later score but must not force a recommendation by itself.

Implement `SelectRecommendationCandidates` in `examples/store/transforms/merchandising/recommender/admit.py`. It should join `RecommendationRequest` to `CatalogProduct` by tenant, optionally filter by request-owned category or collection criteria if those exist in the request schema, and emit `RecommendationCandidate` rows. Keep request semantics explicit: one request may produce zero candidates, and that outcome must remain visible for later evaluation.

Acceptance for this milestone is a fixed scenario where one product is active and promoted, one is blocked, and one is inactive. The candidate output must retain only the active unblocked product.

### Milestone 3: Rank recommendations with transparent merchandising policy

This milestone adds the main recommendation behavior. The end state is that a caller can run a full recommendation request and inspect ranked recommendation rows with explainable score ingredients.

Implement `Recommender` in `examples/store/transforms/merchandising/recommender/workflow.py`, with ranking in `recommender/rank.py` and formulas in `merchandising/ranking/ranker.py`. The enclosing `Recommender` transform supplies the default `Ranker` parameter to `RankRecommendationCandidates`, allowing subclasses to override the ranker without a constructor. It should consume `RecommendationRequest`, `CatalogProduct`, `MerchandisingPolicy`, optional `MerchandisingBoost` and `MerchandisingSuppression` rows, and optional `ProductRecommendationSignal` rows. It must emit `RecommendedProduct` rows with request id, product id, rank, score components, final score, and one `strategy_id` or `policy_version` field carried from the policy input. It must also emit `RecommendationRun`, a one-row request summary with request id, strategy id, result count, and whether feedback contributed to ranking.

The first scoring contract should be simple and fixed. For example:

- start from `1.0` for every eligible candidate,
- add `0.5` when a valid promotion is present,
- add a caller-owned category or product boost when matched,
- subtract a suppression penalty when a suppression rule matched but did not fully exclude the product,
- add a click-feedback contribution only when the product’s signal has at least 20 impressions.

Every score ingredient must stay in a named field so generated code and result rows remain inspectable. Do not collapse all components into one opaque expression with no decomposition.

Acceptance for this milestone is a fixture where two eligible products differ only by promotion and feedback. The output must rank the promoted-and-supported product first, and the result rows must expose the component fields that explain why.

### Milestone 4: Add merchandising feedback and descriptive evaluation

This milestone adds operational evidence. The end state is that Store can log recommendation impressions and clicks, build reusable recommendation signals, and summarize daily recommendation behavior by strategy version.

Implement `BuildRecommendationSignals` in `examples/store/transforms/merchandising/clicks/build_signals.py`. It should consume `RecommendationImpression` and `RecommendationClick` and emit daily impression and click facts plus `ProductRecommendationSignal`. Use a conservative rule: one click must reference one impression id and fall between impression time and 24 hours later. `ProductRecommendationSignal` should include at least impression count, clicked impression count, raw click count, click-through rate, and optional exposure-adjusted click rate when the impression carries a logged examination propensity.

Implement `EvaluateRecommendations` in `examples/store/transforms/evaluation/recommender/behavior/workflow.py`. It should follow the same spirit as Search’s behavior evaluator, but for recommendation requests rather than document queries. It must retain zero-result requests, requests with impressions but no clicks, and requests with clicks at different positions. `DailyRecommendationBehavior` should summarize request count, zero-result rate, clicked-request rate, mean first-click rank, and exposure-adjusted click rate by strategy version.

Acceptance for this milestone is a fixture with two strategy versions, one zero-result request, and at least one clicked impression. The daily evaluator must produce separate summary rows by strategy version and preserve the zero-result request in the denominator.

### Milestone 5: Publish the Store merchandising branch and verify generated artifacts

This milestone makes the new branch a public shipped example and confirms that it coexists with both the old Store path and the admitted fulfillment-planning path. The end state is updated docs, renderer registrations, differential tests, generated output, and build evidence.

## Original Promise Coverage and Follow-up Gaps

The original promise was: “A recommendation app could combine catalog normalization, taxonomy expansion, session events, impressions, clicks, orders, candidate generation, filtering, ranking, diversification, and experiment evaluation. It would mirror Search’s ‘retrieve, narrow, rerank, evaluate’ structure, but in a commerce setting. It also creates good examples for feature engineering, feedback aggregation, and transparent policy composition.” The completed milestones cover the middle of that flow, not every promised input or decision stage.

Catalog preparation, tenant and activity filtering, candidate generation, policy filtering, named ranking components, impressions, clicks, feedback aggregation, and descriptive strategy-version evaluation are covered. The current `CatalogProduct` is not a complete normalization boundary: it retains raw product category and identifier semantics, and it has no expanded taxonomy. `RecommendationRequest` has request-time category and collection fields, but there is no session-event relation or feature window. Orders exist in the neighboring Store branch, but no recommendation-attributed purchase signal is built. Ranking is deterministic, but there is no post-ranking diversity policy. Strategy and policy versions identify outputs, but there is no experiment assignment, exposure record, variant comparison, or guardrail evaluation. Policy composition is readable through score fields, but no durable decision trace records which stage admitted, excluded, boosted, suppressed, or diversified a product.

### Follow-up milestone 6: Establish normalized catalog, taxonomy, session, and order-feedback boundaries

Add `examples/store/schemas/merchandising/taxonomy.py` with `TaxonomyNode`, `ProductTaxonomy`, and `ExpandedProductTaxonomy`. A taxonomy node is a tenant-scoped category with an optional parent; an expanded product taxonomy is the product’s normalized category plus its ancestor path and stable taxonomy identifiers. Add `examples/store/schemas/merchandising/session.py` with `SessionEvent` and `SessionFeature`, and add `RecommendationPurchase` to the feedback schemas. A session event is a bounded, timestamped customer or anonymous-session action such as a product view, search, category view, or add-to-cart. A purchase is recommendation feedback only after an explicit attribution rule connects it to a prior recommendation exposure.

Add `NormalizeCatalog`, `ExpandProductTaxonomy`, `BuildSessionFeatures`, and `BuildRecommendationPurchaseSignals` under `examples/store/transforms/merchandising/`. Normalization must trim and canonicalize identifiers and category values, preserve the original values only when the schema says they are evidence, and reject cross-tenant joins. Taxonomy expansion must be deterministic and retain the ancestor path rather than flattening away hierarchy. Session features must use bounded event-time windows, deduplicate event ids, and retain recency and event counts. Purchase attribution should consume a dedicated boundary derived from fulfilled order facts, require matching tenant and product, require a known customer or session key, and use a documented attribution window; unattributed orders must remain valid order facts but must not become recommendation conversions.

Acceptance is a fixture where equivalent product/category spellings normalize to the same catalog values, one product expands to two taxonomy ancestors, duplicate and out-of-order session events produce stable bounded features, and one fulfilled order is attributed while a customer-mismatched or late order is not. The feature outputs must expose their source window and attribution status.

### Follow-up milestone 7: Make retrieval, filtering, ranking, and diversification explicit

Extend `RecommendationCandidate` with candidate source and eligibility evidence, or add a closely related `CandidateEvidence` relation if preserving the existing shape is safer. Add `GenerateRecommendationCandidates` and `FilterRecommendationCandidates` as distinct transforms. Candidate generation should combine at least direct category/taxonomy matches, session-interest matches, and a tenant-scoped popularity or purchase signal. Filtering should apply hard eligibility, request constraints, customer or session exclusions, suppression rules, and inventory/service policy in a named order, emitting an exclusion reason for rejected candidates rather than silently dropping every row.

Add `DiversifyRecommendations` after ranking and before final result publication. The first diversity policy should be deliberately small and deterministic: accept no more than a caller-provided number of products from one taxonomy branch, then fill remaining positions in ranked order while preserving the original score and rank evidence. Emit a diversity decision or trace row with the selected branch count and exclusion reason. Diversity must never override a hard suppression or tenant boundary.

Update `Recommender` and `Merchandising` to compose the stages as retrieve, narrow, rerank, diversify, and publish. Preserve `RecommendedProduct` score components, add the candidate source and final decision evidence needed to explain the path, and keep zero-result requests visible. The policy contract must state stage precedence: tenant and catalog validity first, hard suppression second, request and session constraints third, ranking boosts and penalties fourth, and diversity caps last.

Acceptance is a fixture with candidates from three sources, one hard suppression, one request mismatch, and several products in the same taxonomy branch. The output must show which rows were excluded at each stage, must never re-admit a hard-suppressed product, and must select a deterministic diverse result set when the ranked list contains too many products from one branch.

### Follow-up milestone 8: Add top-level evaluation and experiment packages

Model this follow-up on Search. Add `examples/store/schemas/evaluation/` for `EvaluationBatch`, recommendation behavior facts, and experiment metric outputs, and add `examples/store/schemas/experiment.py` for `RecommendationExperiment`, `RecommendationAssignment`, and `RecommendationExposure`. An experiment is a caller-owned definition of variants and measurement window. An assignment records the deterministic variant chosen for one tenant, customer, session, or request. An exposure proves that the assigned variant was actually served. An evaluation is a descriptive comparison of observed metrics; it must not claim causal inference.

Add `examples/store/transforms/evaluate.py` as the public evaluation facade, with recommendation behavior implementation under `examples/store/transforms/evaluation/recommendations/`. Add `examples/store/transforms/experiment.py` as the public experiment facade, with assignment and active-variant selection under `examples/store/transforms/experiments/` and experiment-aware recommendation evaluation under `examples/store/transforms/experiments/evaluation/recommendations/`. Keep `BuildRecommendationSignals` under `merchandising/clicks`; evaluation consumes its facts but does not own feedback attribution. Assignment must be stable for the same key and experiment version, tenant-scoped, and explicit in the request or run output. Evaluation must join only to observed exposures, retain zero-result and no-click requests in denominators, and summarize request count, zero-result rate, impression count, click-through rate, attributed purchase count or conversion rate, and declared guardrails by variant. Missing exposure or missing order attribution must remain missing evidence, not a zero invented by an unsafe join.

A guardrail is a secondary metric with a caller-declared acceptable bound, such as a maximum zero-result rate or minimum service-availability rate. Report the guardrail value and whether the bound was met; do not turn it into an opaque composite experiment score.

Acceptance is a fixture with two variants, stable repeated assignments, one zero-result request, one clicked exposure, one attributed purchase, and one request with no exposure. The evaluator must emit separate variant rows, use the correct denominators, and never count the unexposed request as a served impression.
