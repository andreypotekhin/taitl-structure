# Mirror Generated Transform Methods

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement a mirror-method
generated-code layout without prior conversation history.

## Purpose / Big Picture

Structure currently renders an ordinary generated transform as one `run(...)` method containing every compiled
DataFrame operation. This is executable and optimizer-visible, but code review does not show the source transform's
method boundaries. After this work, projects can select `generated_code_options = ["mirror_methods"]` and receive a
generated class whose compiler-visible step methods have the corresponding source names. `run()` then coordinates
those methods using instance-held DataFrames.

The generated class is one batch invocation. A caller supplies one complete input set to its constructor and invokes
zero-argument `run()`. A batch-processing caller constructs one generated instance per input set. This makes every
input and intermediate DataFrame an instance field without mutable rebinding or accidental cross-batch state. The
default layout remains the current `run(*, inputs)` source shape.

The option set also composes with three member-rendering choices. Expression specials are inline by default;
`embed_exprs` emits named generated methods for `@special(type="expr")` helpers. `embed_hooks` and `embed_udfs` copy
validated source bodies into generated code under
their own explicit contracts; without those options, raw hooks and Python UDFs retain source-backed delegation. These
choices change generated source only, never the compiler's flattened execution semantics.

## Surprises & Discoveries

- Observation: the renderer already has a partial per-step-method path, but only when inherited transform owners are
  present. Its methods use synthetic `_step_<name>_<ordinal>` names and a `frames` dictionary.
  Evidence: `src/structure/app/target/pyspark/commands/RenderPySparkTransformModule.py` selects `_legacy_class(...)`
  for ordinary transforms and `_step_methods(...)` only when `_parent_classes(...)` is non-empty.

- Observation: `@special(type="expr")` helper identity is lost before PySpark rendering. The helper executes during
  symbolic capture and only its expanded expression reaches the PySpark recipe.
  Evidence: `src/structure/app/dsl/model/transforms/SpecialFunction.py` returns
  `literal(self.function(*args, **kwargs))` for an expression special; `PySparkExpressionMapper` maps only the resulting
  expression tree.

- Observation: generated runtime construction currently assumes the default public shape: construct with `spark` and
  `ctx`, then call `run(**bound_inputs)`.
  Evidence: `src/structure/app/runtime/execution/generated/commands/RunGeneratedPySparkTransform.py` constructs
  `generated_class(spark=session.spark, ctx=session.ctx)` and calls `runner.run(**invocation._structure_bound_inputs)`.

- Observation: raw-hook embedding is deliberately being planned as a separate source-extraction feature.
  Evidence: `docs/dev/planning/P07132602.Embedded-generated-hooks.plan.md` specifies AST-based embedding, the
  `embed_hooks` option, and later `embed_udfs` support. This plan must consume that shared option vocabulary rather
  than create a competing generation-mode setting.

## Decision Log

- Decision: express method layout with the `mirror_methods` value in `generated_code_options`.
  Rationale: this follows the established concise option vocabulary such as `embed_hooks`. Absence preserves the
  current generated layout, and the option composes directly with expression, hook, and UDF rendering choices.
  Date/Author: 2026-07-13 / project owner and Codex

- Decision: mirror-mode constructors receive every declared input DataFrame, followed by zero-argument `run()`.
  Rationale: each generated instance represents one complete batch. This makes lifecycle, error handling, and instance
  state obvious, while batch callers create separate instances instead of mutating one runner between input sets.
  Date/Author: 2026-07-13 / project owner and Codex

- Decision: source-named schema step methods are zero-argument state transitions, while raw hooks retain their source
  keyword-only DataFrame, `spark`, and `ctx` signatures.
  Rationale: step methods are generated compiler output and can use instance state naturally. A raw method may be
  embedded verbatim under `embed_hooks`, so preserving its signature makes delegated and embedded forms interchangeable
  and avoids rewriting opaque Python bodies.
  Date/Author: 2026-07-13 / Codex

- Decision: expression specials are inline by default; `embed_exprs` independently emits generated helper methods.
Rationale: expanded expressions are the existing, most locally visible output. A named helper is an opt-in embedding
choice that composes with either method layout.
  Date/Author: 2026-07-13 / project owner and Codex

- Decision: options affect generated-artifact fingerprints even though they do not change the PySpark execution plan.
  Rationale: generated-mode execution must identify source rendered with a different layout or embedding policy as
  stale rather than attempting to run an incompatible public class shape.
  Date/Author: 2026-07-13 / Codex

## Context and Orientation

A Structure transform is a Python class inheriting from `Transform`. It declares named input DataFrames, intermediate
lanes, outputs, expression helpers, raw PySpark hooks, and schema-returning step methods. The compiler symbolically
executes the schema-returning methods and creates a flattened ordered `TransformPlan`. PySpark lowering converts that
plan to a `PySparkExecutionPlan`, which the online runner executes and the PySpark renderer writes as Python source.
The flattened plan, not the generated class layout, defines semantics, validations, hook order, and data flow.

The relevant current path is:

1. `src/structure/app/configuration/commands/ResolveStructureConfig.py` validates configuration keys and builds a
   `StructureConfig` using the defaults, builder, and validator in the neighboring configuration packages.
2. `src/structure/app/compiler/artifacts/model/CompilerOptions.py` projects configuration into cache-keyed compiler
   options. `BuildCompiledTransform` produces a `PySparkExecutionPlan` and semantic fingerprint.
3. `src/structure/app/target/pyspark/commands/RenderPySparkProject.py` and
   `src/structure/app/target/pyspark/commands/RenderPySparkTransformModule.py` emit generated source.
4. `src/structure/app/target/pyspark/commands/RenderPySparkStep.py` renders each recipe into explicit DataFrame,
   Column, hook, validation, join, and caching statements.
5. `src/structure/app/runtime/execution/generated/commands/RunGeneratedPySparkTransform.py` imports the generated
   class, verifies its semantic fingerprint, creates it, invokes it, and normalizes its result.

The expected option combinations are:

    generated_code_options = []
    generated_code_options = ["mirror_methods"]
    generated_code_options = ["mirror_methods", "embed_exprs"]
    generated_code_options = ["mirror_methods", "embed_hooks", "embed_udfs"]

Absence of `mirror_methods` means the current default generated layout. Expression specials are inline by default;
`embed_exprs`, `embed_hooks`, and `embed_udfs` may also be used with that default layout. Unknown values and duplicate
values are configuration errors.

The representative mirror API is:

    first = EnrichOrdersGenerated(
        spark=spark, ctx=ctx, orders=first_orders, customers=customers
    ).run()
    second = EnrichOrdersGenerated(
        spark=spark, ctx=ctx, orders=second_orders, customers=customers
    ).run()

The constructor supplies all original input fields. `run()` copies them into current lane fields, validates them,
executes methods, and returns a `TransformResult`. A generated object is intentionally single-use and rejects a second
`run()` call; a new instance is constructed for the next batch. This also makes concurrent batch processing safe when
each batch uses its own instance.

### Milestone 3: Make hooks and UDFs compose with both generated layouts

Implement the AST-based `embed_hooks` behavior described in
`docs/dev/planning/P07132602.Embedded-generated-hooks.plan.md`, but give its renderer the selected layout. In the
default layout, preserve the present call location and original hook signature. In mirror mode, invoke a raw hook
from the generated step method at the same recipe boundary, passing local DataFrame values plus `self.spark` and
`self.ctx`, and then assign its returned DataFrame(s) to the mapped state field(s).

Without `embed_hooks`, render an original-signature generated wrapper that delegates to the exact owner-qualified
source hook. For example:

    def remove_negative_totals(self, *, orders, spark, ctx):
        return self._impl.remove_negative_totals(orders=orders, spark=spark, ctx=ctx)

With `embed_hooks`, render the validated extracted method body under that same name and signature. Preserve the raw
method's compiler opacity, target metadata, validation placement, and source-owner dispatch in both forms. Do not make
a raw hook a zero-argument state method, because its source-compatible signature is required for safe AST embedding.

Implement `embed_udfs` under the matching source-extraction and dependency-validation policy. A generated UDF
initializer uses the generated embedded method when `embed_udfs` is active and the source implementation only when it
is not. `embed_hooks` without `embed_udfs` must retain the explicit source-backed-UDF diagnostic; both options can omit
`_impl` only when no other source member requires it. Test every combination with no hooks/UDFs, hooks only, UDFs only,
and both, including source imports and `_impl` presence.

### Milestone 4: Preserve special expression calls for `embed_exprs`

Add a frozen compiler-visible special-expression definition model under
`src/structure/app/compiler/ir/model/`. It records the declaring module/class/member, ordered parameter names, the
generic symbolic body, and a deterministic definition key. Add a `special_expr` expression wrapper that contains both
the expanded expression used by normal execution and the actual call arguments. During symbolic capture,
`SpecialFunction` continues evaluating its function to obtain the expanded expression and type/nullability, but also
captures a generic body using symbolic parameters and attaches the definition to the wrapper. The wrapper's normal
rendering is its expanded body, preserving current execution and generated output unless `embed_exprs` is selected.

Carry the wrapper through `PySparkExpressionMapper`. Extend `RenderPySparkExpression` so normal rendering delegates to
the expanded body, while `embed_exprs` rendering emits `self.<helper>(<rendered arguments>)`. Have the transform
module renderer collect used definitions from step, output, join, aggregation, operation, and result expressions;
deduplicate them by deterministic definition key; and render each as a `@staticmethod` after constructor/binding and
before generated steps. Render the generic body with parameter names as lambda-style symbolic references. A source
helper `def clean_id(value)` therefore produces:

    @staticmethod
    def clean_id(value):
        return F.lower(F.trim(value))

Reject an `embed_exprs` definition when source calls for the same helper produce incompatible generic bodies or when
the helper name collides with a generated member. The diagnostic must identify the helper and recommend removing
`embed_exprs` to retain safe expanded output. Ensure source helper owners participate in the existing inheritance
dispatch rules so a parent and child helper of the same name cannot silently render the wrong body.

Add Spark-free expression-rendering tests for direct, nested, repeated, multi-argument, join, filter, projection,
aggregate, higher-order, and inherited special helper calls. Assert that default output remains expanded, `embed_exprs`
renders stable static methods and calls, and both variants parse with `ast.parse`.

## Validation and Acceptance

Acceptance requires all of these observable outcomes:

- No-option generated transforms retain the present public `run(*, inputs)` shape and stable generated fixtures.
- `mirror_methods` creates a class with every declared DataFrame input in its constructor and zero-argument `run()`.
  Source-named schema step methods mutate generated DataFrame fields, while raw hooks retain their source-compatible
  signatures.
- Each generated mirror instance represents one batch and rejects a second `run()` call. Separate instances have no
  shared input or intermediate state, so callers can process batches concurrently without state leakage.
- Generated-mode runtime chooses the correct public invocation shape from the same option set used at rendering.
- `embed_exprs` renders `@special(type="expr")` helpers as deterministic generated static methods; normal output is
  expanded inline by default.
- `embed_hooks` and `embed_udfs` compose with both generated layouts according to their self-contained-source contracts;
  unsupported dependencies fail before files are written.
- Owner-qualified inherited steps, hooks, UDFs, and expression helpers retain the exact source owner selected by the
  compiler plan.
- Generated and online execution produce identical outputs for covered live PySpark scenarios, and `make build`
  completes successfully.

## Idempotence and Recovery

All configuration and rendering changes must be deterministic. Re-rendering unchanged source with the same canonical
option tuple must produce byte-identical files; option ordering must not change output. Use `structure compile
--fail-on-diff` to inspect generated differences before writing them. Removing `mirror_methods`, `embed_exprs`,
`embed_hooks`, or `embed_udfs` restores the default supported representation; do not hand-edit generated files.

If a special expression cannot form a single safe generic generated helper, remove `embed_exprs` and use expanded
generated expressions. If a hook or UDF cannot meet source-embedding restrictions, remove the relevant embed option and
use source-backed delegation. These are safe fallbacks that preserve compiler semantics.

## Artifacts and Notes

The essential mirror output is:

    class EnrichOrdersGenerated:
        def __init__(self, *, spark: SparkSession, ctx=None, orders: DataFrame, customers: DataFrame):
            self.spark = spark
            self.ctx = ctx
            self._input_orders = orders
            self._input_customers = customers
            self._ran = False

        @staticmethod
        def clean_id(value):
            return F.lower(F.trim(value))

        def normalize(self):
            orders = self.orders.alias("order_raw")
            self.orders = orders.select(self.clean_id(F.col("order_raw.id")).alias("id"))

        def remove_negative_totals(self, *, orders, spark, ctx):
            return self._impl.remove_negative_totals(orders=orders, spark=spark, ctx=ctx)

        def run(self):
            if self._ran:
                raise RuntimeError(
                    "Generated transform instances run once; construct a new instance for the next batch."
                )
            self._ran = True
            self.orders = self._input_orders
            self.customers = self._input_customers
            assert_schema(self.orders, ORDER_RAW_SCHEMA, name="OrderRaw", mode="strict")
            self.normalize()
            self.orders = self.remove_negative_totals(orders=self.orders, spark=self.spark, ctx=self.ctx)
            return TransformResult({"published": self.published}, single=True, schema={...})

This excerpt assumes `mirror_methods` and `embed_exprs`, but not `embed_hooks`; therefore its hook is a generated
source-compatible delegate. With `embed_hooks`, the method body is the validated AST-extracted raw body. With no
`embed_exprs`, the `clean_id` declaration and call disappear and its `F.lower(F.trim(...))` expression appears directly
in `normalize()`.

## Interfaces and Dependencies

At completion, these interfaces must exist:

- `StructureConfig.generated_code_options: tuple[str, ...]` and
  `CompilerOptions.generated_code_options: tuple[str, ...]` with canonical, validated values.
- A shared membership helper such as `GeneratedCodeOptions.enabled(options, "mirror_methods")`, used by the renderer
  and generated runtime; it must not duplicate option interpretation in those callers.
- Renderer entry points accepting `generated_code_options: tuple[str, ...] = ()`, preserving existing direct-renderer
  tests and callers.
- Mirror generated classes whose constructor accepts `spark`, optional `ctx`, and every declared DataFrame input, then
  exposes `run() -> TransformResult`.
- Renderer-local deterministic frame-field mapping and explicit source-owner dispatch for generated methods.
- Compiler-visible special-expression definition and call provenance sufficient to render static helper methods under
  `embed_exprs` while preserving expanded expression semantics otherwise.
- The AST-based embedded hook/UDF renderer and diagnostics specified by the embedded-hook work, extended to accept both
  generated layouts.

No third-party dependency is required. Use existing compiler IR, PySpark recipes, renderer, and runtime helpers. Use
the Python standard library `ast`, `inspect`, and `textwrap` only for opted-in source embedding; never execute raw hook
or UDF code during generation.
