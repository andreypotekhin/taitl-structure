# Implement v3 Window PySpark Parity

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement the v3 window
gap-closure slice from this file and the current working tree.

## Purpose / Big Picture

After this plan is complete, Structure users can express the remaining planned window behavior from `docs/dev/Gaps.md`:
null ordering in window order keys, multiple order keys in every window helper, and aggregate expressions over reusable
window specs. The result is a more complete compiler-visible alternative to raw PySpark `Window` usage while retaining
typed frames, explainable ordering, and online/generated parity.

Users can see the result by compiling and running transforms that rank and aggregate over partitioned windows with
multiple order keys, explicit null ordering, and aggregate window metrics such as running sums, averages, minima,
maxima, and counts.

## Surprises & Discoveries

- Observation: v2 supports reusable window specs and explicit frames, but not every helper has normalized multi-key
  ordering or null ordering.
  Evidence: `docs/dev/Gaps.md` lists null ordering, multiple order keys in all helpers, and aggregate windows as
  `planned`.
- Observation: Spark does not allow distinct aggregate functions over a window.
  Evidence: `window_count_distinct(...)` now rejects the combination before generated or online execution.

## Decision Log

- Decision: Keep raw PySpark `WindowSpec` escape hatches unsupported.
  Rationale: Raw `WindowSpec` objects are opaque to Structure's type checks, capability checks, streaming
  classification, and generated-code explanations.
  Date/Author: 2026-07-07 / Codex.
- Decision: Mirror only aggregate helpers already admitted elsewhere in Structure.
  Rationale: Window aggregate parity should not become a back door for unsupported aggregate functions.
  Date/Author: 2026-07-07 / Codex.
- Decision: Admit Boolean, statistical, and collection windows; reject distinct windows.
  Rationale: These helpers use stable PySpark aggregate functions, while Spark rejects distinct aggregates in windows.
  Date/Author: 2026-07-12 / Codex.

## Context and Orientation

A window expression calculates values across related rows while preserving row count. Structure already supports
ranking, lag/lead, rolling helpers, reusable window specs, and explicit row/range frames. This plan finishes the
planned parity gaps needed for practical PySpark window authoring without exposing raw PySpark `WindowSpec`.

Relevant files and documents:

- `docs/dev/Gaps.md`: source gap list for this plan.
- `docs/reference/AdvancedAnalyticalOperations.md`: current public window reference.
- `src/structure/app/dsl`: public window helpers.
- `src/structure/app/compiler/ir`: window expression and operation records.
- `src/structure/app/target/pyspark`: shared window lowering.
- `src/structure/app/compiler/traceability`: window dependency reporting.
- `src/structure/app/compiler/compileability/streaming_compatibility`: batch-only classification for stateful windows.

## Plan of Work

Milestone 1 adds explicit null ordering. Introduce order descriptors that can represent ascending or descending order
with nulls first or nulls last. Reuse the ordering model created for v3 DSL ordering modifiers where possible. Render
to PySpark's null-ordering Column methods when supported by the configured target.

Milestone 2 normalizes multiple order keys. Audit every window helper and ensure it accepts the same order-list shape,
validates all order expressions, preserves deterministic order, and renders a stable `orderBy(...)` sequence in online
and generated execution.

Milestone 3 adds aggregate windows. Mirror admitted aggregate helpers such as count, sum, min, max, avg, Boolean
aggregates, statistical helpers, approximate helpers where already supported, collection helpers where sensible, and
deterministic first/last helpers. Require explicit frames where Spark defaults would be surprising. Reject unsupported
or ambiguous aggregate-window combinations through diagnostics.

Milestone 4 updates explain, traceability, streaming classification, public docs, and compatibility tables. Window
explain output should show partition keys, ordered keys including null ordering, frame, and aggregate helper name.
Stateful or order-sensitive windows remain batch-only for streaming inputs unless a later streaming plan admits them.

## Validation and Acceptance

The plan is accepted when all planned window gaps in `docs/dev/Gaps.md` are implemented or explicitly narrowed, and
when `make build` passes.

Behavioral acceptance:

- Window order keys can specify ascending or descending order with nulls first or nulls last.
- Every window helper accepts and renders multiple order keys consistently.
- Aggregate window helpers run online/generated with parity for admitted aggregate families.
- Invalid frames, missing required order keys, unsupported helper combinations, and raw `WindowSpec` values fail before
  runtime with diagnostic links.
- Explain and traceability show partition, order, null ordering, frame, and dependencies.

## Idempotence and Recovery

The work is additive. Re-running generated snapshots and tests is safe. If target variants differ in null-ordering
method support, use capability diagnostics or equivalent generated expressions only when the resulting PySpark remains
readable and semantically identical.

## Interfaces and Dependencies

Use existing window, expression, aggregate, capability, recipe, traceability, and explain infrastructure. Do not accept
raw PySpark `WindowSpec`. Do not lower unsupported aggregate helpers through string SQL or hidden UDFs.
