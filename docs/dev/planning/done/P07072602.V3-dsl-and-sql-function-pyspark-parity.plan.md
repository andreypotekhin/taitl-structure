# Implement v.3 DSL and SQL Function PySpark Parity

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement the v.3 DSL and SQL
function gap-closure slice from this file and the current working tree.

## Purpose / Big Picture

After this plan is complete, Structure users can keep common scalar PySpark Column and SQL function logic inside the
compiler-visible DSL instead of dropping into hooks for ordinary predicates, casts, ordering, string operations,
date/time arithmetic, and numeric helpers. The work closes the `DSL` section of `docs/dev/Gaps.md` for items marked
`planned` while preserving Structure's rule that expressions must remain symbolic, typed, backend-capability checked,
explainable, and readable in generated code.

Users can see the result by compiling an orders-style transform that uses membership predicates, range predicates,
string matching, collection indexing, rich casts, explicit ordering modifiers, substring/split/regex helpers,
date/time helpers, numeric helpers, and predicate helper functions, then running online/generated parity tests against
PySpark 3.5.x and 4.0.x.

## Surprises & Discoveries

- Observation: The existing DSL already covers the smallest v.1/v.2 expression core but intentionally leaves common
  PySpark conveniences out of the compiler-visible surface.
  Evidence: `docs/dev/Gaps.md` lists Column API and SQL function gaps under the `DSL` section, with `planned`,
  `future`, and `unsupported` status.
- Observation: PySpark's string predicate methods require a Python string argument, rather than a Column literal.
  Evidence: rendering them as `F.col(...).like('new%')` and passing the raw string to the online Column method keeps
  generated and online calls semantically identical.
- Observation: `ArrayType` and `MapType` schemas use public scalar subclasses while literal expressions use their
  base types, so strict dataclass equality rejects equivalent map keys.
  Evidence: a String map key failed until type compatibility compared the stable Structure type name.
- Observation: `Column.try_cast(...)` is PySpark 4.0-only, while Structure's default profile spans PySpark 3.5 and
  4.0.
  Evidence: the PySpark 4 profile admits it explicitly; the default profile rejects it before generating a call
  missing from supported 3.5 environments.
- Observation: the analytical reference already showed `event.sequence.asc()` in a reusable window example, but the
  expression model had no order-descriptor methods.
  Evidence: window lowering only read the legacy `descending=` flag until this slice preserved explicit descriptors.
- Observation: PySpark's 3.5 string helper signatures accept literal positions, lengths, patterns, replacements, and
  capture-group indexes.
  Evidence: retaining those values in expression metadata generates the same direct function calls online and in
  source, without a version-specific Column-argument fallback.
- Observation: `concat_ws(...)` skips null values while retaining a literal separator.
  Evidence: the symbolic helper keeps the separator in metadata and records a non-null String result rather than
  overstating the nullability of its input values.
- Observation: the selected temporal functions accept both Date and Timestamp expressions, but their return types
  differ: `date_add` returns Date, `datediff` returns Integer, and `date_trunc` returns Timestamp.
  Evidence: the symbolic helper records each target type explicitly, so output validation does not rely on Spark's
  implicit coercion.
- Observation: the selected numeric helpers divide into type-preserving operations, Long-producing operations, and
  scale-zero Decimal operations.
  Evidence: Spark's `Ceil` and `Floor` expressions retain scale-zero Decimals while returning Long for their other
  admitted numeric input types.
- Observation: Spark's NaN predicate returns a Boolean even when its input is null.
  Evidence: the public `isnan` contract states that it returns true for NaN and false otherwise, so Structure records
  it as non-nullable alongside the existing null predicates.
- Observation: explicit Struct access needs to recognize both a schema field's Python name and its physical Spark
  alias.
  Evidence: the helper resolves either spelling, then stores the physical name for the generated `getField(...)` call.

## Decision Log

- Decision: Treat this v.3 slice as a planned-gap closure pass, not a wholesale PySpark wrapper.
  Rationale: Structure's public contract is stricter than PySpark's dynamic API. Each admitted helper must be typed,
  symbolic, capability-checked, and renderable without hidden Python UDFs.
  Date/Author: 2026-07-07 / Codex.
- Decision: Keep null/NaN predicates, bitwise methods, struct mutation, raw aliases, raw windows, and raw SQL
  expressions outside this slice unless a later plan changes their status in `docs/dev/Gaps.md`.
  Rationale: The current gap document marks those items as `future` or `unsupported`; silently admitting them would
  blur the v.3 release boundary.
  Date/Author: 2026-07-07 / Codex.
- Decision: Admit string predicates only as String-expression methods with Python string-literal patterns.
  Rationale: This matches PySpark Column method semantics, gives compile-time type diagnostics, and leaves pattern
  syntax visible in generated code rather than admitting opaque SQL fragments.
  Date/Author: 2026-07-12 / Codex.
- Decision: Collection indexing results are always nullable, including non-null arrays and maps with non-null values.
  Rationale: array positions can be absent and map keys can be missing, so a non-null result contract would overstate
  Spark's lookup guarantee.
  Date/Author: 2026-07-12 / Codex.
- Decision: Admit `try_cast(...)` behind the existing PySpark 4-only capability profile.
  Rationale: strict casts work throughout the supported target range, and the isolated 4.0 profile can expose
  permissive casts without generating unavailable methods for 3.5.
  Date/Author: 2026-07-12 / Codex.
- Decision: An explicit order descriptor overrides a window helper's legacy `descending=` option.
  Rationale: the descriptor carries the complete direction and null-placement contract, so applying a second direction
  would either lose null placement or produce invalid nested ordering calls.
  Date/Author: 2026-07-12 / Codex.
- Decision: Admit only literal pattern and replacement arguments for the first regex helper slice.
  Rationale: fixed strings match the full supported PySpark range and make regex behavior reviewable; dynamic pattern
  Columns require a later target-version contract.
  Date/Author: 2026-07-12 / Codex.
- Decision: Keep `concat_ws(...)` narrow: literal separator plus one or more typed String arguments.
  Rationale: this maps directly to the stable PySpark function while avoiding raw column-name strings and unrelated
  numeric, binary, or collection coercion policy.
  Date/Author: 2026-07-12 / Codex.
- Decision: Restrict temporal arguments to typed Date or Timestamp expressions and keep offsets/units literal.
  Rationale: this covers the cross-version scalar contract while making invalid temporal combinations fail during
  symbolic compilation rather than in a Spark job.
  Date/Author: 2026-07-12 / Codex.
- Decision: Admit deterministic numeric helpers only, with a literal integer scale for `round(...)`.
  Rationale: the four helpers are stable across the supported target range and preserve an explicit type contract;
  dynamic scale Columns and broader math functions remain later parity work.
  Date/Author: 2026-07-12 / Codex.
- Decision: Limit `isnan(...)` to Float and Double source expressions.
  Rationale: the narrower type contract prevents meaningless NaN checks on integral, decimal, date, and string values
  while preserving the cross-target floating-point predicate behavior.
  Date/Author: 2026-07-12 / Codex.
- Decision: Keep `get_field(...)` as a separate expression kind rather than reducing it to a dotted field reference.
  Rationale: generated and online execution should visibly use the requested PySpark `getField(...)` API while still
  retaining Structure's exact type and nullability information.
  Date/Author: 2026-07-12 / Codex.

## Context and Orientation

Structure is a Python library that lets users write typed transform classes and run them online with PySpark or emit
generated PySpark source. Compiler-visible expressions are captured during symbolic execution. A symbolic expression is
a Python object that represents a Spark expression without running Spark immediately.

The relevant source areas are:

- `src/structure/app/dsl`: public DSL helpers and user-facing model objects.
- `src/structure/app/compiler/symbolic_execution`: symbolic row and expression capture.
- `src/structure/app/compiler/ir`: intermediate representation models used after source capture.
- `src/structure/app/target/pyspark`: shared online/generated PySpark lowering.
- `src/structure/app/compiler/diagnostics`: structured diagnostics and documentation links.
- `src/structure/app/target/capabilities`: backend capability checks.
- `res/testing/model/v2/orders` and later v.3 fixtures: source and generated examples.
- `docs/dev/Gaps.md`: source gap list for this plan.
- `docs/CompatibilityTables.md`: public compatibility table to update when helpers move from planned to implemented.

Terms used in this plan:

- A Column API helper is a method-like operation that PySpark exposes on `Column`, such as `isin(...)` or `between(...)`.
- A SQL function helper is a function-like operation that PySpark exposes under `pyspark.sql.functions`, such as
  `substring(...)` or `date_add(...)`.
- Backend capability means a named feature flag that says whether a configured target profile supports an operation.
- Online execution means Structure directly applies PySpark operations at runtime. Generated execution means Structure
  writes PySpark source that a project can import and run later.

## Plan of Work

Milestone 1 implements planned Column API helpers. Add symbolic support for membership predicates, range predicates,
string predicates, collection indexing, struct field helpers, rich casts, and ordering modifiers with null-ordering
variants. Membership predicates must accept typed literals and compiler-visible expressions. Collection indexing must
infer element type for arrays and nullable value type for maps. Rich casts must distinguish strict casts from
`try_cast(...)` so diagnostics and nullability are honest.

Milestone 2 implements planned SQL function helpers. Add broader string helpers, date/time helpers, numeric/math
helpers, and predicate helper functions. Keep regex behavior explicit: helpers that accept regular expressions must
name that fact in the source API and diagnostics. Date/time helpers must validate that date, timestamp, interval, and
integer operands are sensible before lowering.

Milestone 3 adds shared lowering and capability checks. Every helper must lower through the shared PySpark recipe path
so online and generated execution stay equivalent. Do not add separate ad hoc online and generated implementations.
For any helper whose behavior differs between PySpark 3.5.x, PySpark 4.0.x, classic Spark, and Spark Connect, add a
capability check or explicit diagnostic before runtime.

Milestone 4 updates diagnostics, explain, traceability, and streaming classification. Unsupported Python truthiness,
raw SQL strings, raw aliases, and raw `Column.over(...)` must continue to fail with actionable messages that point to
compiler-visible alternatives. Explain output should show the helper name and relevant operands without becoming a
verbatim expression dump.

Milestone 5 updates public evidence. Add user-story tests, generated PySpark snapshots, online/generated parity tests,
API snapshots, compatibility tables, public reference docs, and v.3 fixture examples. The fixture should contain a
compact transform that exercises all admitted helper families in readable source.

## Validation and Acceptance

The plan is accepted when all `planned` DSL gaps in `docs/dev/Gaps.md` are either implemented or explicitly narrowed in
this plan with rationale, and when `make build` passes.

Behavioral acceptance:

- `isin(...)`, `between(...)`, string predicates, collection indexing, struct field helpers, casts, and ordering
  modifiers compile to visible PySpark Column operations.
- String, date/time, numeric, and predicate SQL helpers compile to visible `pyspark.sql.functions` operations.
- Online and generated execution produce equal schemas and rows for every admitted helper family.
- Unsupported raw SQL, raw aliases, raw `Column.over(...)`, raw Python truthiness, and arbitrary Python behavior still
  fail before runtime with diagnostic links.
- Compatibility tables and public references show the admitted v.3 helper surface.

## Idempotence and Recovery

The work is additive. Re-running tests, generated snapshots, and API snapshots is safe. If a helper proves ambiguous or
target-specific, keep it behind a backend capability diagnostic rather than rendering partial PySpark. If a public
helper name is exported accidentally, remove the export and restore the snapshot instead of accepting accidental API.

## Interfaces and Dependencies

Use existing Structure expression, IR, backend capability, recipe, explain, and diagnostic infrastructure. Do not add a
runtime dependency that makes compiler commands import PySpark, start Java, or create a SparkSession. New helpers must
be available through the same public import style as existing DSL helpers only after tests and docs are in place.
