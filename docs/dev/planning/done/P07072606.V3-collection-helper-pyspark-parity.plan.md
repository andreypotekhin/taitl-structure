## Purpose / Big Picture

After this plan is complete, Structure users can express common array and map operations that remain planned in
`docs/dev/Gaps.md`: collection size and membership, array construction and set operations, element lookup, and map
concatenation. These helpers keep nested-data transforms Spark-plan-visible and typed, avoiding hooks for ordinary array
and map manipulation.

Users can see the result by compiling and running transforms that calculate collection sizes, test array membership,
build arrays from typed values, repeat and union arrays, look up map values with clear missing-key nullability, and
merge maps with deterministic duplicate-key behavior.

## Surprises & Discoveries

- Observation: v2 already supports many higher-order array/map callbacks, but several simpler collection helpers remain
  planned.
  Evidence: `docs/dev/Gaps.md` lists size, `array_contains`, `map_contains_key`, `array`, `array_repeat`,
  `array_union`, `array_except`, `element_at`, `try_element_at`, and `map_concat` as `planned`.
- Observation: the existing `reserved_v2` expression record is the shared symbolic boundary for generated rendering,
  online evaluation, capability checks, streaming classification, and traceability dependencies.
  Evidence: the new helpers required only additions to that expression family, its PySpark renderer/evaluator, and the
  shared capability rules; generated and online paths consume the same lowered recipe.

## Decision Log

- Decision: Implement non-row-expanding collection helpers before generator helpers such as `explode(...)`.
  Rationale: Row expansion changes transform cardinality and output construction rules. The planned v3 slice can close
  common nested-data parity without taking on generator semantics.
  Date/Author: 2026-07-07 / Codex.
- Decision: Keep arbitrary Python callback control flow unsupported.
  Rationale: Existing higher-order helpers require symbolic callbacks so Spark can optimize the plan. This plan does
  not change that boundary.
  Date/Author: 2026-07-07 / Codex.
- Decision: Expose the PySpark names `size`, `array`, `element_at`, and `try_element_at` directly, with the established
  `array_*` and `map_*` names for the remaining helpers.
  Rationale: These names are concise, discoverable beside the existing `arr_*` callback helpers, and map directly to
  the readable generated PySpark calls.
  Date/Author: 2026-07-12 / Codex.
- Decision: Permit only `map_concat(..., duplicates="error")` and document Spark's `EXCEPTION` map-key policy.
  Rationale: Structure cannot know dynamic map keys during compilation. Rejecting a last-wins choice keeps duplicate
  values from being selected silently; the documented default Spark policy makes conflicts fail at runtime.
  Date/Author: 2026-07-12 / Codex.

## Context and Orientation

Structure supports typed array and map schema fields plus a first set of Spark higher-order helpers. Higher-order
helpers are functions that accept symbolic callbacks over array or map elements. This plan is about simpler collection
helpers and nested-data constructors, not arbitrary Python list or dictionary execution.

Relevant files and documents:

- `docs/dev/Gaps.md`: source gap list for this plan.
- `docs/reference/AdvancedAnalyticalOperations.md`: current public higher-order helper reference.
- `src/structure/app/dsl`: public array and map helpers.
- `src/structure/app/compiler/symbolic_execution`: callback and expression capture.
- `src/structure/app/compiler/ir`: collection expression records.
- `src/structure/app/target/pyspark`: shared collection helper lowering.
- `src/structure/app/compiler/traceability`: collection dependency reporting.

## Plan of Work

Milestone 1 implements collection size and membership. Add helpers for `size(...)`, `array_contains(...)`, and
`map_contains_key(...)` or the project's chosen public names. Validate operand types, nullable elements, map key types,
and Boolean result nullability. Render through PySpark functions in online and generated execution.

Milestone 2 implements array construction and set operations. Add typed `array(...)`, `array_repeat(...)`,
`array_union(...)`, and `array_except(...)` helpers. Type unification must be explicit: compatible element types are
admitted, incompatible element types fail with diagnostics naming the conflicting operands. Array construction from zero
operands should be rejected unless the API requires an explicit element type.

Milestone 3 implements element lookup and map concatenation. Add `element_at(...)` and `try_element_at(...)`, or
Structure-native names for map and array lookup where they are clearer than indexing. Add `map_concat(...)`. Diagnostics
must define missing-key behavior, out-of-range array-index behavior, invalid index/key types, and duplicate-key behavior;
if Spark behavior is target-specific or configuration-sensitive, make that explicit through capabilities or docs.

Milestone 4 updates explain, traceability, docs, compatibility tables, and generated examples. Explain output should
name helpers and operand fields compactly. Streaming compatibility should remain conservative for helpers whose Spark
streaming behavior is not proven by existing first-slice evidence.
