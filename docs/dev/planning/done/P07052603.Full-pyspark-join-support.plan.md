# Implement Full PySpark Join Support

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan follows [docs/dev/auto/Plans.md](../auto/Plans.md). It is self-contained so a contributor can implement the
remaining PySpark join support without relying on prior conversation.

## Purpose / Big Picture

After this work, Structure users can express the PySpark join forms that were left out of the first analytical join
slice: right outer joins, full outer joins, explicit cross joins, non-equi predicates, disjunctive predicates, and join
strategy directives. They can see the feature working by writing a reconciliation transform that keeps matched,
left-only, and right-only rows; running online and generated PySpark parity tests; and reading `structure explain`
output that names the join kind, predicate class, nullable sides, and cardinality.

  Evidence: `docs/dev/project-management/sprints/done/Sprint09_OptimizationExplainDocsTooling.md` includes join strategy
  directives and rich `structure explain` output in scope.

- Observation: PySpark's public DataFrame join API accepts a string, list, Column expression, or list of Columns for
  `on`, and supports inner, cross, outer/full, left, right, semi, and anti join modes.
  Evidence: Apache Spark's PySpark `DataFrame.join` API reference documents `DataFrame.join(other, on=None, how=None)`
  and the supported `how` values.

## Decision Log

- Decision: Add `rowset_join(...)` as the broad rowset join primitive instead of expanding `lookup_join(...)` or
  `inner_join(...)` to cover right, full, and cross joins.
  Rationale: Right and full joins can create rows without a current left row, which breaks the mental model behind
  lookup enrichment and ordinary left-side row multiplication.
  Date/Author: 2026-07-05 / Codex.

- Decision: Require `allow_cartesian=True` for cross joins.
  Rationale: Cross joins are valid PySpark behavior but are often caused by missing predicates. Explicit
  acknowledgement preserves Structure's fail-early posture.
  Date/Author: 2026-07-05 / Codex.

- Decision: Keep automatic join reordering out of this plan.
  Rationale: Reordering affects hooks, filters, validations, traceability, nullability, and output construction. It
  needs a separate optimizer equivalence contract.
  Date/Author: 2026-07-05 / Codex.

- Decision: Treat PySpark string/list `on` support as optional typed shorthand, not as raw string API compatibility.
  Rationale: Structure already resolves fields through typed scopes. Raw strings would reintroduce ambiguity and weak
  diagnostics.
  Date/Author: 2026-07-05 / Codex.

## Context and Orientation

Structure is a Python-to-PySpark compiler. Users write typed schemas and transform methods; Structure symbolically
executes those methods into an intermediate representation, then lowers the representation to online and generated
PySpark through shared recipes. Compiler commands must not import PySpark, start Spark, inspect live DataFrames, or run
user hooks.

## Plan of Work

Milestone 1 adds source capture. Add `rowset_join(...)` with keyword-only parameters `left`, `right`, `how`, optional
`on`, optional `using`, optional `strategy`, and `allow_cartesian=False`. Export it through the public API. Capture a
joined-rowset scope with `.left` and `.right` child scopes. Reject missing `on` except for cross joins, reject `on` for
cross joins, and require `allow_cartesian=True` for cross joins.

Milestone 2 adds IR and static validation. Record method, join type, aliases, predicate, predicate class, cardinality
class, nullable sides, strategy, referenced fields, and source text. Add diagnostics for unsupported predicates, raw
strings, invalid `using`, unsafe base constructors after right/full joins, and cross joins without explicit
acknowledgement.

Milestone 3 adds backend capabilities. Add requirements for `join.rowset_join`, `join.right_join`, `join.full_join`,
`join.cross_join`, `join.non_equi_condition`, `join.disjunctive_condition`, and `join.using_keys` when shorthand is
implemented. Wire unsupported forms through `BACKEND-E2402`.

Milestone 4 lowers PySpark recipes. Generated and online execution must consume the same recipe. Render right joins as
right joins, full joins as full joins, cross joins as `crossJoin(...)` or a target-supported equivalent, and broad
predicates as PySpark Column expressions. Always project final output fields explicitly.

Milestone 5 integrates explain, traceability, and streaming classification. Explain must show join type, predicate
class, cardinality, nullable sides, strategy, and field reads. Streaming classification should mark the new broad forms
batch-only until a separate streaming design admits them.

Milestone 6 adds fixtures, docs, and examples. Update `docs/QuickRef.md`, `docs/reference`, `docs/dev/specifications`,
`docs/dev/specifications/UserStories.md`, `res/testing/model/v2/orders`, and public snapshots as public API symbols
are added.

## Validation and Acceptance

This implementation is accepted when:

- right joins keep right-only rows with nullable left fields;
- full joins keep left-only, right-only, and matched rows;
- cross joins fail without `allow_cartesian=True`;
- acknowledged cross joins multiply rows;
- non-equi range predicates lower to generated and online PySpark;
- disjunctive predicates lower to generated and online PySpark;
- unsafe assignment from nullable sides fails at compile time or validation time with a targeted diagnostic;
- `Output.base(left)` after a right or full join fails with a targeted diagnostic;
- explicit projection after a right or full join succeeds;
- unsupported backend capabilities fail before rendering or runtime;
- explain output reports predicate class, cardinality, nullable sides, field reads, and strategy directives;
- Spark Connect support is either proven or rejected through explicit capability diagnostics;
- `make build` passes.

## Idempotence and Recovery

All listed test commands are safe to rerun. `make build` may format imports; inspect the diff afterward.

If public API snapshot tests fail after adding `rowset_join(...)`, regenerate the snapshot only after confirming the new
exports are intentional. If generated-code snapshots fail, review whether the rendered join type, aliases, and
projection are deterministic before updating expected files.

If a broad predicate proves hard to support in the first implementation, keep the capability unsupported and record the
reason here rather than silently routing through hooks or string SQL.
