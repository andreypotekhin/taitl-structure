## Purpose / Big Picture

Structure already classifies whether generated PySpark transforms are compatible with Spark Structured Streaming. That
classification is useful, but it is not a support claim until online and generated execution are proven with a real
streaming DataFrame. After this plan is complete, a developer can create a streaming source outside Structure, pass the
streaming DataFrame into a compatible Structure transform, and receive a streaming DataFrame plan back from both online
and generated execution.

The user-visible behavior is:

    orders = spark.readStream.table("orders")
    customers = spark.read.table("customers")

    result = EnrichOrdersGenerated(spark=spark, ctx=ctx).run(
        orders=orders,
        customers=customers,
    )

    assert result.isStreaming

The caller still owns `writeStream`, checkpointing, triggers, output modes, and query startup.

## Surprises & Discoveries

- Observation: The repository already had a strong streaming compatibility contract, but it described when generated
  transforms can be used with streaming inputs rather than scheduling live first-slice support evidence.
  Evidence: `docs/dev/specifications/StreamingCompatibility.md` defines compatible operations and severity rules, while
  Sprint 09 previously listed full streaming orchestration as out of scope.

- Observation: Sprint 09 is a better home than v3 for the first slice because it verifies the existing caller-owned
  compatibility boundary; v3 should remain reserved for generated streaming sources, sinks, and lifecycle policy.
  Evidence: `docs/dev/project-management/Roadmap.md` says v1/v2 maintain compatibility when callers pass streaming
  DataFrames and v3 introduces streaming orchestration.

## Decision Log

- Decision: Support caller-owned streaming DataFrames in Sprint 09, not Structure-owned streaming jobs.
  Rationale: This delivers immediate value from the existing transform compiler without taking responsibility for
  source, sink, trigger, checkpoint, output mode, watermark, or query lifecycle decisions.
  Date/Author: 2026-07-05 / Codex

- Decision: Require both online and generated runtime evidence before calling the first slice supported.
  Rationale: Static compatibility can prove Structure is not obviously emitting batch-only operations, but a real Spark
  streaming source proves Spark accepts the DataFrame plan.
  Date/Author: 2026-07-05 / Codex

- Decision: Treat `streaming_safe=True` hooks as trusted boundaries, not analyzed code.
  Rationale: Hook bodies are arbitrary PySpark. Structure can validate signatures and metadata, but it cannot safely
  prove every possible runtime behavior without creating a brittle Python analyzer.
  Date/Author: 2026-07-05 / Codex

- Decision: Keep generated `readStream`, `writeStream`, watermarks, output modes, and state policy deferred to v3.
  Rationale: These features form a streaming job lifecycle contract. Partial ownership would create surprising runtime
  behavior and weak recovery guarantees.
  Date/Author: 2026-07-05 / Codex

## Context and Orientation

Structure is a Python library for schema-driven PySpark transforms. Users write transform classes with typed schema
methods. The compiler builds intermediate representation, then the PySpark target either runs the transform online
through `StructureSession` or emits generated PySpark classes.

Spark Structured Streaming lets a PySpark DataFrame represent an unbounded input. Spark builds a logical plan first;
the user starts a streaming query later with `writeStream`. The first Structure streaming slice works at the DataFrame
plan level only. Structure may return a streaming DataFrame plan, but it must not start or manage the query.

## Plan of Work

Start by extending capability metadata. Add explicit supported capabilities for row-local projection, row-local
filtering, schema-only validation, stream-static left joins, stream-static inner joins, and trusted streaming-safe
hooks. Add explicit unsupported capabilities for source generation, sink generation, trigger policy, checkpoint policy,
output mode, watermarks, state policy, stream-stream joins, stateful aggregation, stateful dedupe, and streaming
actions.

Next make the compatibility checker enforce the first-slice severity rules. A transform marked
`streaming_compatible=True` must fail on `batch_only` or `unknown` operations. A project with checks enabled but no
transform marker may warn instead. Diagnostics must name the operation and explain the runtime-shape assumption: one
streaming current input plus static side inputs.

Then add runtime evidence. Use a small streaming source available in local Spark, such as the rate source, and convert
it into the order schema needed by the fixture. Use a static DataFrame as the lookup side. Exercise row-local
projection, row-local filtering, schema-only validation, and left or inner lookup join. Verify that online execution
and generated execution both return a DataFrame whose `isStreaming` flag is true and whose analyzed plan can be
started by Spark in a short, bounded query if the integration harness supports it.

After runtime evidence, add generated-source scans. A streaming-compatible generated transform body must not contain
`readStream`, `writeStream`, `start()`, `awaitTermination()`, `collect()`, `count()`, `toPandas()`, `show()`, `.rdd`,
`mapInPandas`, or hidden UDF fallback. Keep these scans as guardrails, not as the only proof.

Finally update explain output and public diagnostics. Explain reports should show `compatible`, `batch_only`, or
`unknown`, plus a compact reason. Batch-only analytical operations should point to
`docs/reference/SparkStreamingDeferredFeatures.md`.

## Validation and Acceptance

Acceptance is behavioral:

- A compatible transform marked `streaming_compatible=True` accepts a caller-created streaming current input and static
  lookup side input in online execution, then returns a streaming DataFrame plan.
- The generated class for the same transform returns an equivalent streaming DataFrame plan.
- Stream-static left and inner joins are accepted; stream-stream joins fail before runtime.
- Row-local projection and filtering stay streaming-compatible; grouped aggregation, selected-row helpers, dedupe,
  ranking, lag/lead, rolling windows, right/full/cross joins, non-equi joins, and disjunctive joins remain batch-only
  for streaming inputs.
- Generated streaming-compatible transform bodies contain no streaming lifecycle calls, Spark actions, RDD conversion,
  Pandas conversion, or Python UDF fallback.
- Explain output and diagnostics link to public streaming reference pages.

## Idempotence and Recovery

The work is additive. Re-running static tests, source scans, generated snapshots, and integration tests is safe. If a
live streaming test cannot run in CI, keep the first-slice implementation behind documented manual evidence rather than
weakening the support claim. If Spark rejects an operation previously classified as compatible, change the capability
or compatibility decision to `batch_only` and record the finding here.
