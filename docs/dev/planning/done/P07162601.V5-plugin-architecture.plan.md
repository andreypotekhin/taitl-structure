# Deliver the v5 Core-Orchestrated Plugin Plugin Architecture

This ExecPlan is a living document. Maintain it according to `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises &
Discoveries`, `Decision Log`, and `Outcomes & Retrospective` accurate whenever work stops or a design fact changes.

## Purpose / Big Picture

After v5, Structure can compile and run transforms for an installed target platform without embedding that plugin's
plugin DSL, schema rules, lowering, runtime operations, or generated syntax in Core. Core remains the application: it
discovers source, resolves one target for each transform, owns every workflow by default, stores artifacts, renders
diagnostics, and invokes target-specific `PluginAPI` service facets at explicit points. A selected plugin may
additionally replace an individual private Core engine class for that target when it declares compatibility with the
complete current engine suite. PySpark remains the bundled and supported production plugin. External distributions
can implement the same public Plugin API contract from vendor-owned packages.

Users see the boundary directly. Structure-specific declarations continue to come from `structure`; PySpark field
definitions, expressions, joins, aggregations, and other PySpark plugin DSL APIs come from
`structure.plugin.pyspark`. A transform
declares zero or one target. Different transforms in one project may select different installed targets, but a single
transform or composed pipeline cannot mix them. Structure makes no promise that code written for one plugin compiles
for another.

The release is demonstrably complete when existing PySpark behavior passes through the public Plugin API, a separately
packaged finite-iterable fixture works through real package entry points without Core implementation imports, both API
downgrade directions select the highest mutually supported Plugin API version, a compatible private replacement
engine proves target-local engine injection, and `make build` plus the supported live PySpark lanes pass.

## Surprises & Discoveries

- Observation: Source-mounted Docker integration does not expose Poetry entry-point metadata.
  Evidence: the initial live target selection reported PySpark as unavailable; `PluginRegistry` now supplies a lazy
  bundled-PySpark entry only when the installed `structure` entry point is absent.
- Observation: The existing alternative-backend design promises common-source portability, which conflicts with v5's
  plugin-owned DSL.
  Evidence: `docs/dev/design/AlternativeBackends.md` describes one Structure source lowering to several backends,
  while v5 deliberately allows different plugin DSLs.
- Observation: Installed-plugin discovery can inspect entry-point names and distribution metadata without loading
  the referenced class.
  Evidence: Python's `importlib.metadata.EntryPoint` separates metadata enumeration from `EntryPoint.load()`; v5 must
  preserve that separation in tests.

## Decision Log

- Decision: Core owns every public workflow and supplies the default engine implementation; a selected plugin may
  replace an individual private engine class only through its automatically discovered plugin manifest.
  Rationale: This keeps lifecycle, artifacts, CLI, and the public error surface coherent, while allowing an advanced
  plugin to adapt a workflow that the public Plugin API methods cannot yet express. Replacement is target-local,
  not a
  global application switch, and remains an intentionally undocumented private extension point.
  Date/Author: 2026-07-16 / project owner and Codex.
- Decision: One discovered plugin creates one negotiated `PluginAPI` façade with small service facets.
  Rationale: One entry point gives a plugin one coherent identity and prevents discovery, registration, and version
  negotiation from multiplying across workflow domains. Optional lifecycle facets are absent rather than represented by
  empty plugins.
  Date/Author: 2026-07-16 / project owner and Codex.
- Decision: Use unversioned API definitions and explicit minimum/maximum ranges for versioned Plugin APIs.
  Rationale: Versioned entry-point group names would prevent a newer side from downgrading to the highest version it
  shares with an older side.
  Date/Author: 2026-07-16 / project owner and Codex.
- Decision: A transform may declare only one target; an explicit caller target must match it.
  Rationale: Target APIs and schemas are plugin-owned, so multi-target declarations would imply portability that
  Structure neither validates nor promises.
  Date/Author: 2026-07-16 / project owner and Codex.
- Decision: All installed distributions are eligible by default, short plugin names are allowed, and duplicate names
  fail until
  the user disables conflicting distributions.
  Rationale: This keeps installation convenient without relying on unsafe environment ordering or a Core-owned vendor
  namespace.
  Date/Author: 2026-07-16 / project owner and Codex.
- Decision: Remove target-owned root exports immediately in v5.
  Rationale: Permanent or transitional aliases obscure plugin ownership at the architectural boundary this release
  exists to establish.
  Date/Author: 2026-07-16 / project owner and Codex.
- Decision: Keep the iterable plugin internal and finite.
  Rationale: Its purpose is to prove isolation, packaging, Plugin API use, joins, aggregation, execution, and
  serialization;
  infinite streams would introduce unrelated windowing and termination semantics.
  Date/Author: 2026-07-16 / project owner and Codex.
- Decision: Plugin API version negotiation applies only to the public Plugin API. A plugin that supplies any
  replacement
  engine must declare a compatible Structure version range and the exact current private Core engine-suite revision.
  Rationale: Downgrading one replacement engine while the rest of Core uses newer private engine contracts creates an
  unsafe hybrid system. Core rejects the entire selected target's replacement manifest on either mismatch rather than
  falling back silently to stock engines.
  Date/Author: 2026-07-16 / project owner and Codex.
- Decision: Private engine class injection is disabled unless global Structure configuration sets
  `plugin.plugin_options = "allow_injection"`.
  Rationale: A private engine class runs inside Core's workflow boundary, so enabling it must be an explicit end-user
  trust decision. The option is global in v5; Core names the selected plugin and shows the exact opt-in setting when it
  rejects a replacement.
  Date/Author: 2026-07-17 / project owner and Codex.
- Decision: v5 configuration uses `plugin.default`, `plugin.disabled_distributions`, and isolated
  `plugin.<name>` tables; same-name tables merge by key across normal configuration precedence, while list values
  replace.
  Rationale: Core needs one deterministic selection surface without interpreting target semantics. Replacing lists
  prevents a lower-precedence disablement from being accidentally retained, and isolated tables prevent one plugin from
  observing another plugin's configuration.
  Date/Author: 2026-07-17 / Codex documentation review.
- Decision: Plugin names are exact lowercase ASCII identifiers and must agree among entry-point metadata, plugin
  descriptor, decorator, and configuration.
  Rationale: Exact names keep TOML configuration addressable, eliminate aliases, and make duplicate-provider failures
  deterministic.
  Date/Author: 2026-07-17 / Codex documentation review.

## Context and Orientation

Structure currently compiles `Transform` subclasses by symbolically executing Structure-owned DSL objects into a
`TransformPlan`. `src/structure/core/compiler/artifacts/commands/BuildCompiledTransform.py` resolves PySpark
capabilities, lowers the plan through the PySpark target app, builds runtime schemas, and stores both the supposedly
neutral plan and a concrete `PySparkExecutionPlan` in `CompiledTransform`.

`src/structure/core/runtime/session/model/StructureSession.py` accepts `spark`, chooses online or generated PySpark
execution, and dispatches through PySpark-specific Core endpoints. Online execution code under
`src/structure/core/runtime/execution` interprets PySpark recipes. Generation and schema materialization already live
mostly under `src/structure/core/target/pyspark`, but Core imports their concrete APIs. The public PySpark plugin DSL
is exported
from `src/structure/__init__.py` and `src/structure/core/dsl/api/__init__.py`.

In v5, a "Core workflow" is an application action whose ordering, public interface, lifecycle, error handling, and
resource ownership belong to Structure. A "Callback object" is a target-owned object invoked by a Core workflow at a
documented point. A Callback object may receive and return opaque target values. Opaque means Core can retain,
fingerprint, serialize through service facets, and route the value, but cannot inspect it to decide target semantics.

A "plugin" is an installed plugin factory registered through Python distribution entry-point metadata. A Python
"distribution" is the installed wheel or project metadata name used by package installers; it is not a target-selection
name. A plugin is selected by its short plugin name such as `pyspark`. Each distribution exposes one plugin name. A
"plugin" returns one versioned plugin façade for its plugin name. The façade is complete when it contains required
schema, compiler, and capability service facets; execution, generation, and serialization facets are optional and must
agree with reported lifecycle capabilities.

An "engine" is a Core-owned workflow implementation such as `CompileEngine`, `ExecutionEngine`,
`GenerationEngine`, `SchemaEngine`, or `SerializationEngine`. The public behavior belongs to the workflow, not the
engine class. The default is a Core concrete engine. A replacement engine is an optional, private plugin class injected
for the selected plugin only; it receives the current private `EngineContext`, may subclass the private base or stock
concrete engine, and must preserve all public result and artifact contracts. A nonreplaceable Core router always
resolves the target, negotiates the Plugin API, validates the replacement manifest, constructs engines, and validates
workflow outputs at the public boundary.

Unversioned Plugin API definitions belong under `src/structure/plugin/api`. Versioned Plugin API definitions
belong under `src/structure/plugin/api/v1`. Core discovery and orchestration remain under `src/structure/core`.
Bundled PySpark plugin DSL and Plugin API implementations belong under `src/structure/plugin/pyspark`. External
plugins
use their own import packages and depend only on documented `structure` and `structure.plugin.api` surfaces.

## Interfaces and Dependencies

Introduce immutable unversioned API-definition models equivalent to the following names and meanings. Exact module
decomposition should
follow `docs/dev/Code.md`, but these public concepts and fields are fixed by this plan.

`PluginDescriptor` contains `name`, display name, distribution identity, plugin version, and minimum and maximum
Plugin API versions. `Plugin` is the unversioned plugin base; it reports its supported range and returns one
`PluginAPI` façade for a requested version. `PluginConfiguration` contains the target name, plugin metadata,
negotiated API version, global `plugin_options`, and the plugin's opaque configuration mapping.

The selected plugin may additionally expose a private, optional engine-replacement manifest. Its mapping associates a
stock engine base with a replacement class, conceptually `{CompileEngine: AcmeCompileEngine}`. It contains
`requires_structure`, a compatible Structure release range, and `core_engine_revision`, the exact private engine-suite
token for which the mapping was built. It is detected from the selected plugin with no user configuration. Core checks
`plugin.plugin_options = "allow_injection"` and both compatibility values before resolving or constructing the
replacement classes. A plugin must also declare its ordinary package
dependency on Structure. Core changes `core_engine_revision` only when a private engine contract changes; a normal
Structure release does not force an engine-plugin rebuild when that token remains unchanged.

Replacement engines do not negotiate or downgrade. A replacement manifest with an incompatible Structure range or
engine-suite revision makes the selected target unavailable with a diagnostic that names the plugin name,
distribution,
declared and current requirements, and the remediation: use a matching plugin, disable it, or select another target.
Core must never ignore the mapping and instantiate the stock engine instead. A plugin without a replacement manifest
remains eligible for ordinary Plugin API negotiation.

Use one unversioned entry-point group under the `structure.plugin` prefix and define its name once as a Core constant.
Entry-point names are short plugin names. Do not encode the API version in a group name or create per-service entry
points.

Plugin API v1 defines immutable request/result models, `PluginAPI`, and its small service-facet contracts.
`plugin.schema` validates ownership, interprets plugin field/type declarations, and materializes a target schema.
`plugin.compiler.compile(request)` captures the plugin DSL, performs semantic validation and lowering, and returns
a `PluginCompilation` containing standard artifact metadata plus opaque analysis and lowered payloads.
`plugin.capabilities` returns semantic capability records and target lifecycle conditions. Optional execution,
generation, and serialization facets validate a duck-typed runtime, render target content without writing files, and
encode/decode opaque payloads respectively; Core owns envelopes and storage.

Core diagnostic records retain code, severity, source span, context, problem, remedy, and documentation fields. Plugins
own target diagnostic codes and text but return the Core record type. Core capability records retain id, category,
support status, summary, conditions, and documentation; plugins own semantic entries and Core owns lifecycle entries.

Negotiate one API version between Core and the selected plugin. Let `minimum` be the greater declared minimum and
`effective` the lesser declared maximum. The plugin is compatible when `effective >= minimum`, and Core selects
`effective`. The plugin must then produce a complete `PluginAPI` façade for that version. New compilation selects
the highest common version. Loading a serialized artifact requests its recorded version instead of silently upgrading
it. Missing overlap or a plugin that cannot supply its advertised version raises a plugin compatibility diagnostic
before a workflow begins.

Replace target-wide configuration fields with a Core `target`, a list of disabled distribution names, global
`plugin_options`, lifecycle settings such as execution mode, and opaque per-plugin tables. Preserve ordinary precedence among defaults, config
files, CLI, and programmatic overrides. Target resolution is special: a decorated target
selects itself; an explicit target must match it; an undecorated transform uses the explicit target and then the
configured default. Project compilation resolves each transform independently. Pipeline composition requires every
stage to resolve to the same target.

Keep `Schema`, `Transform`, input/output/lane declarations, and decorators in Core. Keep base field declaration and
definition contracts in Core, but move every public field/type constructor to its plugin package. Field, expression,
and other symbolic objects carry a plugin name. Schema and compiler service facets reject a foreign name before
lowering.
`@raw` inherits the transform target and may carry plugin-understandable string constraints such as `target_profile`
and `target_variant`; those strings narrow but never change the target.

Generalize the runtime boundary to `StructureSession(runtime=..., context=..., config=...)`. Core forwards `runtime`
without target imports or assumptions. PySpark accepts a `SparkSession` directly. The iterable fixture accepts finite
iterables of row mappings. Core still returns `TransformResult`; target outputs remain target-shaped within it.

The Core artifact envelope records plugin name, plugin distribution and plugin version, negotiated API version,
effective plugin configuration, normalized schemas, inputs and outputs, diagnostics, traceability, semantic and cache
fingerprints, and opaque payloads. Include all plugin and negotiation facts in cache keys. Reject execution,
generation, or deserialization through a different plugin or API version. When an engine affects the artifact, also
record the effective engine-suite revision and replacement class identity, and reject an incompatible replay.

## Plan of Work

Sprint 19 establishes the contract without first moving production PySpark behavior. Write the architecture decision,
developer specification, public extension reference, diagnostics, plugin-configuration contract, and target-resolution
rules before implementation.
Add the plugin registry and inject entry-point metadata in unit tests so discovery, disabling, duplicate plugin names,
plugin completeness, and loading failures are deterministic. Add Core v1 façade/facet models and fake plugins.
Refactor compiled artifacts to the Core envelope while temporarily adapting current PySpark lowering behind Plugin API
facets. This temporary
adapter is an implementation bridge, not a public compatibility path.

Add the private engine-selection router in Sprint 19 without exposing it in public authoring documentation. Give the
current private engine suite one `core_engine_revision` token and give every stock engine the same current private
`EngineContext`. After the target is selected, inspect its optional replacement manifest, validate
`requires_structure`, the exact revision, and `plugin.plugin_options = "allow_injection"`, then construct the
declared classes only for that workflow. Test a
replacement of one engine beside stock engines, mismatches in both declarations, absent manifests, and a failed output
boundary validation. The mismatch diagnostic must fail target activation; it must not fall back to the Core class.

Implement negotiation as a focused Core action. Test Core `[1,2]` with plugin `[1,1]`, Core `[1,1]` with plugin `[1,2]`,
partial overlap, no overlap, and a plugin that lies about a supported version. Store the selected version on every
artifact. Build target resolution independently of plugin loading so an unknown, disabled, duplicate, or conflicting
target fails before importing plugin code. Make registry and negotiated façades immutable or session-scoped; do not use
import-time global activation.

Refactor each Core workflow around its Plugin API service facets. Core schema processing discovers classes and
inheritance before asking the schema facet to interpret target fields. Core compilation sequences capture, validation,
lowering, artifact
assembly, diagnostics, traceability, and caching. Core execution validates ownership, runtime, inputs, and results
around the execution facet. Core generation preflights the whole project, asks the generation facet only for content,
and writes
nothing until every target proves generation support. Core serialization owns envelope encoding, checksums, plugin
identity, versions, streams, and recovery around opaque-payload service facets. Core capability tooling merges
lifecycle and
semantic records and renders them through the existing CLI style.

Sprint 20 moves PySpark behind these contracts. Start with field/type ownership and the schema facet, then the PySpark
plugin DSL, semantic checks, capability rules, and lowering. Next move online/generated runtime behavior and
generation
rendering. Preserve shared PySpark recipe parity inside the PySpark package; Core need not know whether PySpark uses one
recipe graph for execution and rendering. Replace `spark=` with `runtime=` only after a working adapter protects tests,
then migrate all callers. Route schema-generation tools through Core and selected-plugin service facets rather than
starting Spark from a generic CLI module.

Keep PySpark compiler commands Spark-free. Callback imports used by check, compile, explain, capability reporting, and
generation must not import the live `pyspark` package, start Java, or create a session. Only execution and live schema
inspection service facets may require the runtime. Verify classic and Connect claims through the existing integration
lanes.

Sprint 21 builds the external contract. Publish how a vendor distribution declares one plugin, supported API ranges,
target configuration, plugin DSL imports, diagnostics, capabilities, optional facets, tests, and compatibility. Add a
conformance kit that accepts a discovered `PluginAPI` plugin and tests manifest consistency, negotiation, schema

## Validation and Acceptance

Discovery acceptance requires an installed fake plugin to appear in plugin listings without its module appearing
in `sys.modules`. Selecting it may import only the required plugin. A disabled distribution must never load. Two
eligible distributions claiming one short plugin name must fail with a diagnostic listing both distribution names and
the exact
configuration remedy.

Negotiation acceptance requires symmetric downgrade evidence. New artifacts use the highest common version shared by
Core and the selected plugin. Serialized artifacts retain their recorded version. No façade may receive a version it
did not advertise, and no workflow may start after negotiation failure.

Target acceptance requires one optional string on `@transform`. A matching explicit target succeeds; a conflicting one
fails. Undecorated transforms use explicit then configured default selection. One project can compile separately
targeted transforms, but `.to(...)` composition across targets fails before semantic Plugin API calls. Foreign
plugin field,
expression, or raw metadata fails with source-located guidance.

Core-ownership acceptance requires plugins to have no file-writing, CLI-registration, global-session, cache, or
diagnostic-rendering responsibility. Generation facets return content; serialization facets return bytes or versioned
data; execution facets return target results. Core owns lifecycle, atomicity, envelopes, routing, and final
presentation.

Private-engine acceptance requires Core to create a replacement only after target selection and manifest validation.
The replacement can coexist with stock engines for that target, but never changes another target's workflow. Core must
first require global `plugin.plugin_options = "allow_injection"`; its default diagnostic names the selected plugin,
states that class injection is disabled, and shows the exact opt-in remedy. Core must
reject a mismatched `requires_structure` or `core_engine_revision` before work begins and render a diagnostic that says
which declaration mismatched. It must validate the replacement's public artifact/result/report/schema boundary instead
of trusting a vendor class. The extension is absent from public plugin-author documentation.

PySpark acceptance is behavioral, not merely structural. Every released schema, expression, join, aggregate, window,
collection, streaming transformation, classic execution, Connect execution, generated-code, traceability, and
diagnostic claim must retain its evidence. Compiler-only commands remain Spark-free. Generated output remains
deterministic and optimizer-visible.

External-plugin acceptance requires the fixture wheel to import no `structure.core` or other implementation package.
Its installed metadata must be sufficient for discovery. The conformance kit must detect missing required plugins,
capability/plugin disagreement, false version claims, wrong-plugin artifacts, weak diagnostics, and unsupported
optional workflows. Iterable results must be repeatable after execution, including when inputs were one-shot finite
generators, and `collect()` must return deterministic row mappings.

Release acceptance requires all Sprint 19-22 criteria, updated public and developer documentation, no target-owned root
exports, no concrete PySpark plan type in Core artifacts, the default build, and required live lanes. Any unmet item
keeps M10 open.

## Idempotence and Recovery

Metadata discovery, negotiation, compilation, fake plugin façades, and documentation checks are safe to rerun.
Registry
tests inject metadata rather than altering the active environment. Fixture-wheel tests build and install only inside a
unique temporary environment and delete only paths they created.

Migrate additively before subtracting. Introduce the Core envelope and PySpark adapters, move one workflow family at a
time, then remove adapters and legacy names in Sprint 22. Keep old and new cache entries distinguishable by plugin and
API version; never reinterpret an old opaque payload as a new version. A failed deserialization leaves the original
artifact untouched and reports whether the remedy is installing the plugin, enabling it, using a compatible version,
or rebuilding the artifact.

Core generation must preflight every selected plugin and rendered file before writing. If rendering fails, write
nothing. Continue using existing generated-file ownership and atomic-write behavior. Never delete generated files for
another plugin merely because one target is disabled.

If PySpark extraction reveals a behavior that cannot fit Plugin API v1 without leaking target semantics into Core,
stop that slice, record the evidence in `Surprises & Discoveries`, and revise the Plugin API specification before
proceeding.
Do not add a private PySpark escape hatch. If API v1 must change before release, update all plugin packages,
conformance tests, and this plan together; after v5 release, follow negotiated versioning instead of changing v1.
