## Purpose / Big Picture

After this plan is complete, Structure users can express the aggregation features that remained planned after v2:
explicit grouping sets and post-aggregate `having(...)` predicates. This closes the `planned` rows in the
`Aggregations` section of `docs/dev/Gaps.md` and establishes the shape for later exact percentile and additional
statistics work without admitting PySpark's dict/list aggregate shorthand.

Users can see the result by compiling and running a transform that produces detail, subtotal, and custom grouping-set
rows, then filters aggregate output rows with a typed `having(...)` predicate while preserving online/generated parity
and readable generated PySpark.

## Surprises & Discoveries

- Observation: v2 implemented rollup/cube and metric-local filters but deliberately deferred arbitrary grouping sets
  and post-aggregate `having(...)`.
  Evidence: `docs/dev/planning/done/P07052601.Advanced-analytical-operations.plan.md` records `grouping_sets(...)` and
  `having(...)` as capability-gated deferrals.
- Observation: PySpark's stable Python DataFrame surface does not expose a portable direct grouping-sets builder across
  supported target variants.
  Evidence: the implementation lowers grouping sets as explicit grouped branches with typed-null omitted keys,
  literal grouping metadata, and `unionByName`.

## Decision Log

- Decision: Treat grouping sets and having predicates as separate milestones.
  Rationale: Grouping sets change grouping-level semantics, while `having(...)` introduces a new aggregate-output
  predicate scope. Keeping them separate makes diagnostics and tests sharper.
  Date/Author: 2026-07-07 / Codex.
- Decision: Keep dict/list aggregate syntax unsupported.
  Rationale: Structure's schema constructors own output names and types. PySpark shorthand hides aliases and weakens
  typed output construction.
  Date/Author: 2026-07-07 / Codex.

## Context and Orientation

Structure aggregation support lets users group rows and produce typed summary schemas. In v2, Structure added typed
`group_by(...)`, rollup, cube, common aggregate helpers, metric-local filters, deterministic first/last helpers,
approximate metrics, and collection metrics. Two common SQL/PySpark concepts remain planned:

- Grouping sets let the user name exact grouping levels, such as `(country, city)`, `(country)`, and `()`.
- Having predicates filter aggregate result rows after metrics are computed, unlike `where(...)`, which filters input
  rows before aggregation.

## Plan of Work

Milestone 1 implements grouping sets. Add a source helper that accepts explicit grouping levels made from typed fields.
Represent the grouping kind and each level in IR. Validate that each level references only fields in the aggregate
input scope, that subtotal output fields are nullable when omitted by a level, and that grouping metadata helpers
continue to identify subtotal rows. Lower through PySpark's grouping-set support when available or fail through a
capability diagnostic when the configured target cannot render it safely.

Milestone 2 implements `having(...)`. Add an aggregate-output predicate scope so users can reference grouped keys and
aggregate metrics, but cannot accidentally reference pre-aggregate row fields that are no longer defined. Lower the
predicate after aggregation. Diagnostics must distinguish pre-aggregate `where(...)`, metric-local filters, and
post-aggregate `having(...)`.

Milestone 3 updates traceability, explain, docs, and compatibility tables. Explain output should show grouping levels
and post-aggregate filter predicates compactly. Traceability should show which input fields define grouping levels and
which aggregate outputs feed the having predicate.

Milestone 4 reviews future aggregation gaps. Exact percentile family, skewness, kurtosis, and mode remain `future` in
`docs/dev/Gaps.md`. Add no public helper unless the gap status is updated in the same change. Backend capability names
may be reserved only if they improve diagnostics for already-documented deferred behavior.

## Validation and Acceptance

The plan is accepted when explicit grouping sets and `having(...)` work in online and generated execution, public docs
and compatibility tables are updated, and `make build` passes.

Behavioral acceptance:

- Grouping sets can express at least detail level, subtotal level, and grand total level in one aggregate transform.
- Output fields omitted by grouping levels are nullable or rejected with a diagnostic that names the field.
- `having(...)` can filter on aggregate metrics and grouped keys.
- `having(...)` rejects references to unavailable pre-aggregate fields.
- Explain and traceability show grouping levels and post-aggregate predicates.

## Idempotence and Recovery

The work is additive. If PySpark target support differs by version or variant, keep grouping sets capability-gated.
Generated fixture updates must be inspected before acceptance. Re-running tests and builds is safe.

## Interfaces and Dependencies

Use existing aggregation DSL, IR, backend capability, shared PySpark recipe, traceability, and explain infrastructure.
Do not implement PySpark dict/list aggregate shorthand. Do not create a second aliasing system outside schema
constructors.
