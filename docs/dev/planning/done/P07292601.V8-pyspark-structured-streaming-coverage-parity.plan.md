# Deliver v8 PySpark Structured Streaming Coverage Parity

This ExecPlan is a living document. Maintain it according to `docs/dev/auto/Plans.md`; its `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections must describe the actual state whenever work stops.

## Purpose / Big Picture

V8 makes Structure's caller-owned PySpark Structured Streaming support catch up to the percentage level of the existing
PySpark batch transformation catalog. A developer should be able to inspect one checked ledger, see which typed
Structure operations can run over caller-supplied streaming DataFrames, and trust that each supported claim has
generated-code, online/runtime, diagnostic, explain, and live restart evidence. Structure still does not own streaming
sources, sinks, checkpoints, triggers, output modes, or query lifecycle.

## Surprises & Discoveries

- Observation: The current catalog already exposes the main v8 measurement gap through `profile` text.
  Evidence: `src/structure/plugin/pyspark/resources/pyspark-transformation-coverage.json` has thirty-four supported
  entries, and four supported entries still say `streaming=batch-only`: `functions.generators`, `dataframe.set`,
  `dataframe.ordering`, and `dataframe.priority-selection`.
- Observation: Spark's own Structured Streaming guide keeps several DataFrame operations unsupported or conditional,
  so v8 cannot honestly mark every batch-supported operation streaming-compatible as a family-level blanket claim.
  Evidence: the Spark 3.5 Structured Streaming guide says limits and distinct operations are unsupported on streaming
  datasets, sorting is supported only after aggregation in Complete output mode, and multiple stateful-operation chains
  are restricted.

## Decision Log

- Decision: Define v8 parity against the existing checked catalog first, then introduce an operation-level streaming
  ledger where family-level accounting hides Spark restrictions.
  Rationale: The user asked for percentage parity with batch coverage, but the current catalog groups safe and unsafe
  streaming operations together in families such as `dataframe.set` and `dataframe.ordering`. Operation-level rows let
  v8 increase real support without overclaiming unsupported Spark shapes.
  Date/Author: 2026-07-29 / Codex.
- Decision: Keep caller-owned lifecycle as a hard boundary in v8.
  Rationale: Source, sink, checkpoint, trigger, output-mode, and query lifecycle ownership are operational concerns. If
  Structure generated them, the feature would stop being transformation coverage and would need a separate streaming
  orchestration contract.
  Date/Author: 2026-07-29 / Codex.
- Decision: Treat Spark-ineligible operations as explicit denominator exclusions only after design evidence, not as
  silent gaps.
  Rationale: Percentage targets invite bad incentives. A family such as arbitrary streaming `limit(...)` should fail
  with a good diagnostic rather than be counted as a missing implementation forever or falsely marked supported.
  Date/Author: 2026-07-29 / Codex.

## Context and Orientation

Structure's bundled PySpark plugin lives under `src/structure/plugin/pyspark`. Users write typed transform classes that
Structure captures as compiler-visible operations, lowers to PySpark execution recipes, runs online through live
PySpark DataFrames, and can render as generated PySpark source. A streaming-compatible transform is still only a
DataFrame transformation: the caller supplies streaming inputs and owns every streaming query lifecycle concern.

The current transformation inventory is `src/structure/plugin/pyspark/resources/pyspark-transformation-inventory.json`.
The current coverage catalog is `src/structure/plugin/pyspark/resources/pyspark-transformation-coverage.json`, and its
guard test is `tests/specifications/compatibility/test_pyspark_transformation_coverage.py`. The normative v8 streaming
specification starts in `docs/dev/specifications/V8StructuredStreamingCoverageParity.md`. Existing streaming behavior is
described in `docs/dev/specifications/SparkStreaming.md`, `docs/dev/specifications/SparkStreamingDeferredFeatures.md`,
`docs/dev/design/V7CallerOwnedStreamingAdoption.md`, and
`docs/dev/specifications/V7CallerOwnedStreamingAdoption.md`.

At kickoff, the same catalog says thirty-four of thirty-six PySpark transformation families are supported for batch.
Thirty streaming-compatible rows are claimed if rows whose profile contains `streaming=batch-only` are excluded from
the numerator. The four supported batch families still marked batch-only for streaming are `functions.generators`,
`dataframe.set`, `dataframe.ordering`, and `dataframe.priority-selection`.

The term `Structured Streaming` means Spark's incremental DataFrame execution model. Structure does not start
Structured Streaming queries; it only returns a transformed streaming DataFrame that the caller may write and manage.
The term `restart evidence` means a test writes input files, runs a query with a caller-owned checkpoint, stops it,
writes more input, restarts with the same checkpoint, and observes correct rows without Structure-owned lifecycle code
inside the generated transform.

## Plan of Work

First, add a checked streaming coverage ledger under `src/structure/plugin/pyspark/resources`, likely named
`pyspark-structured-streaming-coverage.json`. Give it rows for every currently supported batch family. Each row names
the batch catalog id, streaming status, supported operation spellings, rejected operation spellings, state class
(`stateless`, `stateful`, `stateful-composition`, or `ineligible`), output-mode rule, evidence, and notes. Add a guard
test beside `tests/specifications/compatibility/test_pyspark_transformation_coverage.py` that proves every supported
batch catalog id is classified and prints or asserts the parity ratio.

Second, design-gate the four kickoff gaps before changing behavior. For `functions.generators`, evaluate each typed
array-of-struct generator as stateless row expansion. For `dataframe.set`, split union-like operations from distinct,
intersect, subtract, and except operations. For `dataframe.ordering`, split arbitrary order/limit/offset from the
possible narrow post-aggregate complete-mode order case. For `dataframe.priority-selection`, decide whether a bounded
watermarked selected-row contract exists; otherwise keep it streaming-ineligible with a clear diagnostic.

Third, implement the safe stateless candidates. Update compiler streaming classification, explain, traceability,
generated-source scans, and online/generated runners only where live Spark accepts the plan. Each admitted operation
needs a file-stream restart fixture under `tests/integration/pyspark`, generated-source tests proving no lifecycle or
action tokens, static rejection tests for unsafe input modes, and catalog evidence.

Fourth, implement only the stateful or output-mode-sensitive candidates whose design gate proves a narrow safe contract.
Keep one stateful operation per query unless the existing v7 single-stateful-plus-stateless rule explicitly admits the
composition. Do not admit two-stateful chains, arbitrary complete-mode global sorting, selected-row ranking windows, or
priority selection by row-number unless live restart evidence proves the exact PySpark 3.5 and 4.0 behavior and the
diagnostics can state the required output mode.

Finally, close v8 with a hardening sprint. The hardening sprint admits no new streaming surface. It refreshes generated
artifacts, updates API and troubleshooting documentation, runs focused tests, runs live PySpark 3.5 and 4.0 streaming
lanes, and runs `make build`.

## Validation and Acceptance

The first validation gate passes when the new streaming ledger test proves full classification and prints or exposes
the kickoff ratios: batch 34 / 36, streaming 30 / 36, and streaming among batch-supported families 30 / 34.

Each admitted streaming operation is accepted only when a user can run the generated and online forms over a
caller-supplied streaming DataFrame, restart from a caller-owned checkpoint, and observe equivalent output rows on
PySpark 3.5 and PySpark 4.0. The generated transform source must contain no lifecycle, action, RDD, Pandas, or hidden
UDF token.

The v8 release is accepted when the streaming support percentage is no lower than the existing batch support percentage
under the checked measurement rule, all operation-level denominator exclusions are documented with evidence, and
`make build` passes.

## Idempotence and Recovery

The ledger and specification changes are additive. If a live target rejects a candidate, mark only that precise
operation `streaming-ineligible` or `streaming-deferred` and keep the family-level status honest. Do not weaken the
generated-source lifecycle scan to pass a feature. If a candidate behaves differently between PySpark 3.5 and 4.0, gate
it by target or leave it unsupported until both target contracts are explicit.

## Interfaces and Dependencies

Use the existing PySpark plugin architecture. Do not add a new backend or a streaming orchestration package. The new
ledger is a resource file consumed by tests and later by capability/explain tooling. Production behavior changes belong
in the current compiler streaming classification command and focused PySpark streaming logic delegates.

Use only public PySpark DataFrame and Column APIs. Use file-stream integration tests for restart evidence because they
exercise Spark's actual streaming planner while keeping query lifecycle ownership in the test rather than in Structure.
