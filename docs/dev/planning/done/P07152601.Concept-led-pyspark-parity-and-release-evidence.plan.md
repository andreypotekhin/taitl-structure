# Add Concept-Led PySpark Parity and Lightweight Release Evidence

Status: Completed 2026-07-16.

This ExecPlan is a living document. Its `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` sections must be updated as work proceeds. Follow `docs/dev/auto/Plans.md` when changing
this document.

## Purpose / Big Picture

Structure exposes one transform through two public execution modes: online execution of the compiled PySpark recipe and
execution of generated PySpark source. V3 feature slices could pass compiler-only checks while these modes, their type
metadata, and a target PySpark version still disagreed. This work makes a small set of public, end-to-end concept
scenarios the release-admission proof for feature families, while preserving detailed lower-level tests for exhaustive
edges.

A developer can run `make build` without Spark. Before closing a supported PySpark feature, they run the relevant
Compose lanes and see the same public transform produce equal rows, columns, and reliable schema metadata online and
from generated code.

## Surprises & Discoveries

- The Compose runner already invokes the complete `tests/integration` tree and shares a version-aware session, rendered
  project, and row-comparison harness. Concept scenarios can reuse that machinery without another backend harness.
- The default pytest configuration globally loads the integration plugin, so integration-marked concept tests collect
  and skip cleanly in Spark-free development environments.
- Pytest `conftest.py` fixture visibility is directory-scoped. Concept tests outside `tests/integration` import the
  existing shared `spark` fixture and register its wrapped implementation under the same fixture name rather than
  duplicating the Spark session fixture.
- The existing V3 advanced-analytics fixture already supplies representative aggregate, window, and collection output
  lanes. Splitting assertions by output lane gives each public concept a focused failure without duplicating the fixture.
- The V3 scalar and collection fixtures use `try_cast(...)` and `try_element_at(...)`, which Structure correctly
  exposes only through its PySpark 4.0 capability profile. Their live concept scenarios skip narrowly on 3.5 rather
  than weakening that capability boundary.
- The integration renderer and session must compile against the active Compose backend's exact supported profile. A
  broad `>=3.5,<4.1` profile cannot admit a PySpark-4-only operation even while a 4.0 container is running.

## Decision Log

- Decision: Put the live public scenarios in `tests/concepts/live_pyspark/`, not `tests/integration/pyspark/`.
  Rationale: `docs/dev/Concepts.md` defines concept tests as public black-box vocabulary coverage; the integration tree
  remains the owner of infrastructure mechanics and specialized streaming lifecycle tests.
- Decision: Run concept scenarios in both classic `pyspark35` and `pyspark40` Compose lanes. Run Connect lanes only
  when the feature claims Connect support.
  Rationale: the classic versions are Structure's common supported baseline, while Connect is an explicit capability
  profile rather than an implied property of ordinary PySpark behavior.
- Decision: Record release evidence in a hardening plan's `Outcomes & Retrospective` section rather than adding a
  scorecard, owners, or approval workflow.
  Rationale: exact reproducible commands and results are sufficient evidence and preserve the project's lightweight
  development process.

## Plan of Work

### Milestone 1: Establish concept-family parity

Create integration-marked public scenarios for scalar expressions, joins, aggregates, windows, collections, and
source-ordered step/filter flow. Each scenario renders a generated project, constructs its inputs through public
schemas, runs the same transform online and generated, and calls `assert_online_generated_parity`. Assert one visible
family outcome so a parity-only accidental equivalence cannot pass. Keep null, empty, boundary, and invalid-contract
coverage in the narrow suites; each concept scenario selects the representative case that most clearly demonstrates the
family's public behavior.

Reuse `tests/integration/pyspark/support/backend_matrix.py` and V3 analytical fixtures. Do not start queries in these
batch concept scenarios. Stateful streaming restart and checkpoint proof remains in
`tests/integration/pyspark/v3/streams`.

### Milestone 2: Make live concepts part of the existing matrix

Extend `infra/compose/images/pyspark/run-integration.sh` to invoke pytest on both `tests/integration` and
`tests/concepts/live_pyspark`. Preserve `--run-integration`, `--integration-backend`, the existing default skip behavior,
and the single shared backend/session harness. The classic Compose lanes run all supported public concept scenarios.
Tests must use a capability-specific skip only when the current backend cannot support that scenario, and that skip must
name the limitation.

### Milestone 3: Guard consumer completeness and release closure

Extend the transform-expression dispatch catalog test so it proves declared transformation functions have generated
rendering, online evaluation, capability declarations, target mapping, generated-module discovery, and streaming
classifier handling. It must fail when a relevant consumer no longer mentions `transform_expression` or when a declared
collection operation lacks renderer or capability coverage.

Update `docs/dev/Concepts.md`, `docs/dev/Testing.md`, and `docs/dev/specifications/ExecutionSemanticContract.md` so
one live concept scenario is an admission requirement. Update the sprint-planning guide and V4 hardening/coverage plans
to require `make build`, both classic Compose lanes, applicable Connect lanes, generated-artifact freshness, and a
brief evidence record.

## Validation and Acceptance

From the repository root, run:

    poetry run pytest tests/concepts --collect-only -q
    poetry run pytest tests/concepts -q
    poetry run pytest tests/specifications/execution-semantic-contract/test_v3_transform_expression_dispatch.py -q
    make build
    make integration BACKEND=pyspark35
    make integration BACKEND=pyspark40

Run `make integration BACKEND=spark-connect35` and `make integration BACKEND=spark-connect40` only after selecting a
concept with an explicit Connect capability claim.

Acceptance requires six collected live concept scenarios, Spark-free default skipping with the established reason,
passing classic lanes, a passing consumer catalog guard, and a passing default build. Every future V3/V4 hardening
defect receives a focused regression test in the most specific existing suite, categorized in the test or plan as a
missing lowering, lost semantic metadata, invalid static contract, ignored option, or target-version mismatch.
