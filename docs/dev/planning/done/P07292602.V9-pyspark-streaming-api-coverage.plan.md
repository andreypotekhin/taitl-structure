## Purpose / Big Picture

V9 makes Structure's streaming story broader and easier to adopt after v8 closed percentage parity for streaming-compatible transformations. A developer should be able to inspect one checked PySpark streaming API ledger, see which APIs Structure owns as typed DataFrame transformations, which APIs remain caller-owned PySpark lifecycle code, and which APIs are rejected with a concrete reason. The visible outcome is a documented and tested path for using Structure inside real PySpark Structured Streaming applications without Structure silently becoming the streaming job owner.

  Evidence: `docs/dev/specifications/V8StructuredStreamingCoverageParity.md` says generated sources, sinks, checkpoints, triggers, output modes, query names, start/stop behavior, deployment, and recovery are v8 non-goals.

  Evidence: `docs/dev/planning/postponed/P07072607.V3-streaming-orchestration.plan.md` says lifecycle ownership may reopen only with a separate product decision, operational semantics, failure/recovery policy, security review, live evidence, and end-user documentation.

  Evidence: the first v9 guard test treated `startswith` as `start`; the test now checks concrete lifecycle spellings

## Context and Orientation

Structure's bundled PySpark plugin lives under `src/structure/plugin/pyspark`. Users author typed transform classes with schemas and compiler-visible operations. Structure can run those transforms online through `StructureSession` or render generated PySpark classes. A streaming-compatible Structure transform accepts caller-supplied streaming DataFrames and returns a transformed DataFrame plan; the caller still owns PySpark Structured Streaming source construction, sink construction, checkpoints, triggers, output modes, query starts, stops, deployment, and recovery.

The current batch transformation catalog is `src/structure/plugin/pyspark/resources/pyspark-transformation-coverage.json`. V8 added `src/structure/plugin/pyspark/resources/pyspark-structured-streaming-coverage.json`, which classifies batch-supported transformation families for caller-owned streaming. V9 adds a broader ledger for PySpark streaming API families, including lifecycle APIs that Structure must document and guide without necessarily generating.

The governing v9 specification is `docs/dev/specifications/V9PySparkStreamingApiCoverage.md`. Existing streaming contracts are in `docs/dev/specifications/SparkStreaming.md`, `docs/dev/specifications/StreamingCompatibility.md`, `docs/dev/specifications/SparkStreamingDeferredFeatures.md`, `docs/dev/specifications/V7CallerOwnedStreamingAdoption.md`, `docs/dev/specifications/V8StructuredStreamingCoverageParity.md`, and `docs/dev/specifications/V4CallerOwnedStreamingMigration.md`.

The term `Structured Streaming` means Spark's incremental DataFrame execution model. The term `lifecycle API` means PySpark calls that create sources, configure sinks, apply triggers or output modes, start or stop queries, inspect query status, or perform side effects. The term `caller-owned-guided` means Structure does not perform the lifecycle call, but the docs, examples, diagnostics, and tests show how caller PySpark code should surround a Structure transform.

## Plan of Work

First, create a PySpark streaming API inventory and checked ledger. Inspect the PySpark API surface relevant to Structured Streaming and classify each family as `structure-supported`, `caller-owned-guided`, `design-gated`, `streaming-ineligible`, or `out-of-scope`. Seed the ledger from the v8 transformation ledger and extend it with DataStreamReader, DataStreamWriter, StreamingQuery, trigger, checkpoint, output-mode, foreach, listener, state, and Spark Connect streaming families. Add guard tests that require evidence paths and prevent lifecycle APIs from being counted as transformed-DataFrame support.

Second, publish caller-owned adoption recipes. These should be executable examples, not only prose. Add examples that use a caller-created source, pass the streaming DataFrame through online and generated Structure execution, and write through a caller-owned sink with explicit checkpoint and output-mode configuration. Include file-stream restart coverage because it proves that Structure can participate in a real streaming application without owning checkpoint state.

Third, re-evaluate stateful and order-sensitive deferred items from v7 and v8. For each candidate, write or update a concise design/specification note before code changes. Admit only shapes with compiler-visible state, watermark or finite-bound rules, required output modes, explain output, generated-source scans, online/generated parity, and live PySpark 3.5/4.0 evidence. Keep distinct-style set operations, arbitrary global ordering, priority selection, analytic windows, lag/lead, rolling windows, foreach, and two-stateful chains rejected unless the design gate proves a bounded safe contract.

Fourth, improve diagnostics and explain output around streaming adoption. When a transform cannot be used in a streaming application, the diagnostic should say whether the fix belongs in Structure source, caller-owned PySpark lifecycle code, or a batch materialization boundary. Error messages should link to the streaming compatibility and v9 API coverage docs.

Finally, close v9 with a hardening sprint. The hardening sprint admits no new API family. It refreshes generated artifacts and docs, runs focused compatibility and generated-source scan tests, runs live PySpark 3.5 and 4.0 streaming lanes for admitted claims, records skipped or blocked evidence explicitly, and runs `make build`.

## Validation and Acceptance

The first validation gate passes when the new streaming API ledger test proves that every selected PySpark streaming API family has exactly one classification and an existing evidence path. The test should fail if a lifecycle API is silently counted as Structure-owned transformation support.

An adoption recipe is accepted when a user can run it with caller-created streaming sources and sinks, stop the query, restart from a caller-owned checkpoint, and observe equivalent rows for online and generated Structure execution. The generated transform source must remain free of lifecycle and action APIs.

A newly admitted streaming transformation is accepted only when static compatibility tests, explain/traceability tests, generated-source scans, online/generated parity, and live PySpark 3.5/4.0 restart evidence all pass. A rejected shape is accepted only when the diagnostic points to a concrete rewrite, caller-owned lifecycle action, or batch materialization boundary.

V9 is complete when the API ledger, adoption recipes, diagnostics, public docs, target evidence, generated artifacts, and `make build` all pass through the final hardening sprint.

## Idempotence and Recovery

Ledger, specification, and sprint-document changes are additive. If a live target rejects a candidate, leave that precise API row `design-gated` or mark it `streaming-ineligible` with evidence instead of weakening the support rule. If a lifecycle API appears necessary for a user workflow, document it as caller-owned-guided unless the project explicitly approves a lifecycle-owning runtime. Do not remove generated-source lifecycle scans to admit an API.

## Interfaces and Dependencies

Use the existing PySpark plugin architecture and Plugin API boundary. Do not add a second streaming backend. Ledger rows are data resources consumed by tests and later by explain/capability tooling. Production transformation behavior changes belong in the current compiler streaming classification, PySpark lowering, online execution, and generated rendering modules.

Use only public PySpark DataFrame, Column, DataStreamReader, DataStreamWriter, StreamingQuery, and trigger APIs in examples and tests. Any side-effecting API such as `foreachBatch` must remain caller-owned or receive an explicit side-effect/idempotence design before implementation.
