# V3 Step Decorator, Ordered Raw Methods, and Variadic `where`

This ExecPlan is maintained according to `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

V3 separates class decoration from step binding, lets a native PySpark method appear where it runs in a Transform
class, and makes adjacent filters concise without changing their order. A user can write `@step(...)`, place `@raw`
between steps, and write `where(a, b, c)`; compilation, generated code, and online execution retain the existing
PySpark behavior.

## Surprises & Discoveries

- Observation: generated and online PySpark execution already share `HookPlan`, `PySparkHookRecipe`, and the same
  owner-qualified method invocation rules.
  Evidence: `RenderPySparkStep` and `PySparkHookInvoker` both consume the lowered hook recipe.

- Observation: retaining the hook recipe as the raw execution boundary avoids a second native-frame calling protocol
  while still making class-member order the scheduler.
  Evidence: focused raw-boundary and public-API tests pass after source-order attachment.

## Decision Log

- Decision: preserve `HookPlan` as the executable raw boundary rather than introduce a second recipe hierarchy.
  Rationale: raw has precisely the same native DataFrame call, result assignment, validation, projection, input
  namespace, and inherited owner dispatch contract as `@raw`; class-member compilation supplies the new scheduling
  behavior without duplicating generated and online execution logic.

- Decision: retire `@before` and `@after`; `@raw` is the only hook-defining decorator.
  Rationale: V3 hook placement is source-ordered. Keeping target-relative hook decorators, even in compatibility
  imports, would preserve two competing hook-definition models.
