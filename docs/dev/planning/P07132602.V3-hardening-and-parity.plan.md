# V3 Hardening, Contract Integrity, and Live Parity

This ExecPlan is a living document. Keep Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective current as work proceeds.

## Purpose / Big Picture

V3's public transformation surface is complete. This plan turns it into a dependable release boundary: generated PySpark and online execution must agree on results, null handling, and diagnostics; invalid DSL programs must fail before a Spark action whenever the contract can establish that; and generated examples, fixtures, and API snapshots must remain synchronized.

The user-visible result is confidence that a V3 recipe behaves the same whether it is rendered into a module or evaluated immediately. The plan preserves V3's boundary: sources, sinks, query lifecycle, triggers, output modes, checkpoints, and recovery remain the caller's responsibility.

## Surprises & Discoveries

- event_time_between was renderable but could not be evaluated online. This showed that per-backend dispatch is not automatically exhaustive.
- arr_aggregate previously supplied the merged item expression, rather than the accumulator, to its finish callback. The rendered and online forms had different finish lowering.
- arr_sort_by validated its callback but discarded it when rendering and evaluating, silently sorting raw items instead of callback keys.
- A project-level cache decorator shadows the standard-library cache name; internal memoization must import it under an explicit alias.
- The fluent row scope did not expose where(...), while the top-level helper was variadic and secondary input scopes exposed a one-argument form. Both scopes now delegate variadic predicates to the same helper.
- V3-specific PySpark integration currently concentrates in tests/integration/pyspark/v3/streams/test_file_streams.py; several adjacent V3 operations have only renderer, fake-runtime, or inherited V2 integration coverage.
- The current DSL map-entry helpers advertise array<map<string,string>>, whereas Spark's map_entries produces an array of key/value structs. This is an inaccurate typed contract, not merely a missing test.
- Spark `flatten` returns null if any immediate nested array is null. The outer-array nullability alone is not a sound static contract.
- Test modules can use the same `from structure import *` style as end-user recipes when Flake8's F403/F405 exceptions are limited to test paths. Public-module snapshot tests still need an explicit module import to inspect `__all__`.
- Python booleans are integers, so unchecked window controls accepted `True` as offsets, counts, and frame bounds. Approximate aggregate parameters likewise reached Spark without its documented bounds being checked.
- `coalesce(...)` used its first typed argument rather than a common type and unconditionally reported itself non-null. Reversing a documented decimal fallback (`coalesce(0, decimal_value)`) therefore broke output assignability; completed `when(...)` expressions had the same branch-order type issue.
- The renderer/evaluator equality catalog did not establish that a public constructor actually reached either backend or had a capability declaration. A constructor-to-dispatch-and-capability catalog closes that omission for collection and dynamic-window expressions.
- The compiler already owns aggregate type diagnostics and emits stable `DSL-E0402` errors. In contrast, sum/average window helpers had no equivalent guard and accepted non-numeric arguments until Spark analysis.
- Window min/max and rolling min/max likewise bypassed the aggregate validator, allowing collection/map values to reach Spark analysis. Invalid `frame=` values produced incidental attribute errors instead of a DSL diagnostic.
- `lag(...)` and `lead(...)` stored their `default=` values as raw expression data. A field expression or arbitrary object could therefore bypass symbolic validation and render as invalid generated Python.
- Date and timestamp literals correctly rendered as `datetime.date(...)` and `datetime.datetime(...)`, but generated modules omitted the required module import.
- The transform-module expression inventory originally ignored joins, aggregates, selected-row ordering, and several operation-owned expressions. That left import and UDF discovery incomplete outside ordinary projections.
- Scalar helper rendering and online evaluation happened to be complete, but had no constructor-to-backend completeness proof comparable to transform expressions.
- DecimalType admitted precision above Spark's maximum of 38 and non-integral constructor values, allowing invalid schemas and decimal casts to reach backend analysis.
- Arithmetic expressions inherited their left operand's type and nullability. Mixed numeric operations could therefore be modeled as a narrower type than Spark returns, allowing incorrect output assignments.
- Comparisons and Boolean operators did not preserve Spark's three-valued null semantics; `null_safe_eq(...)` also omitted its Boolean type, which only became visible when composing a join predicate.
- `isin(...)` was unconditionally nullable despite non-null inputs, while `event_time_between(...)` unconditionally reported non-null despite nullable timestamps. Ordered helpers also allowed collection sort keys, and aggregate `first_value(...)`/`last_value(...)` silently ignored `ignore_nulls=True`.
- Boolean-annotated direction and null-handling controls accepted arbitrary truthy values, silently changing rendered window and array-sort behavior.
- `grouping_sets(())`, documented as the grand-total level, was rejected before the existing zero-key generated and online lowerings could execute.
- `arr_exists(...)` and `arr_forall(...)` modeled only outer-array nullability, even though Spark's three-valued predicate
  semantics can yield null from a nullable item or callback result.
- `arr_aggregate(...)` omitted nullability from its input array and, without a finish callback, from a nullable initial
  value returned unchanged for an empty array.
- `arr_aggregate(...)` passed `finish=` an accumulator typed only from the initial value. A nullable merge result can
  make the final accumulator null even when the initial value is required.
- `rolling_sum(...)` retained its input type although Spark widens integer, floating-point, and Decimal sums just as it
  does for grouped and reusable-window sums.
- `grouping_sets(())` can produce one aggregate row from empty input, where value aggregates are null even for required
  source fields; their type metadata previously inherited the grouped-input non-null assumption.
- Compiler assignment validation recomputed aggregate and transform-expression nullability from their raw arguments,
  discarding operation-specific outcomes such as empty frames, filters, and absent lookups.
- Reusable window aggregates were conservatively nullable even for an explicit frame that contains the current required
  row; the stronger compiler validation exposed valid non-null output schemas using that common running-frame shape.
- `lower(...)`, `trim(...)`, and `upper(...)` accepted arbitrary input types and preserved them in expression metadata,
  despite Spark's String-only contract and String result.
- Decimal `round(...)` preserved its input type even though Spark derives a bounded result scale and recomputes Decimal
  precision from the integral digits plus that scale.
- `arr_position(...)` was always nullable even though Spark returns the non-null sentinel `0` when a required array
  contains no matching item.
- `bool_and(...)` and `bool_or(...)` were always nullable, needlessly rejecting required output fields for non-null,
  unfiltered grouped values; conversely, the global empty grouping-set branch must remain nullable.
- `event_time_between(...)` interpolated arbitrary non-empty interval text into a backend SQL expression, allowing
  malformed or unsafe interval syntax to reach the renderer and online evaluator.
- `date_trunc(...)` accepted arbitrary non-empty units even though Spark returns null for invalid units, which could
  violate a required output declaration without a compiler diagnostic.
- `to_decimal(...)` inherited source nullability although a present malformed or out-of-range value can cast to null.
- Compiler assignment validation recomputed generic call nullability from children, which discarded the semantic
  nullability of `to_decimal(...)` and `try_cast(...)`; it also incorrectly included a nullable `when(...)` condition
  even though SQL takes the fallback branch for a non-true condition.
- `cache(StorageLevel...)` discarded its level at symbolic construction, so every generated and online path silently
  used PySpark's default persistence level.
- `sum(...)` retained its input type despite Spark's aggregate widening, and filtered non-null aggregates claimed to be
  non-null even when no row qualified.
- Decimal `avg(...)`, `rolling_avg(...)`, and `window_avg(...)` were modeled as Double despite Spark preserving a
  widened Decimal result.
- `collect_list(...)` and `collect_set(...)` propagated source nullability into their element type even though Spark's
  default aggregate form drops null inputs.
- The same collection aggregates were conservatively marked nullable even though Spark returns an empty array for an
  all-null group, a fully filtered group, or an empty window frame.
- `window_min(...)` and `window_max(...)` inherited input nullability despite a valid reusable frame being empty for a
  boundary row.
- `range_between(...)` checked only the number of ordering keys. It allowed non-numeric bounded ranges that Spark
  rejects during analysis, while wrongly rejecting fully unbounded ranges that Spark permits with multiple keys.
- `arr_aggregate(...)` accepted a numerically widened merge result even though Spark requires the merge lambda to
  return the same type as its initial accumulator state.
- `map_zip_with(...)` accepted numerically promoted map-key types even though Spark requires its two maps to have the
  same key type.
- `MapType` accepted a key containing a nested map, and `map_concat(...)` widened distinct map keys or values; both
  forms reach Spark analysis as invalid map operations.
- `first_value(..., where=...)` and `last_value(..., where=...)` recorded their filter but their `min_by`/`max_by`
  lowerings ignored it in generated and online execution.
- PySpark did not accept a Column as `array_position`'s searched item or `map_contains_key`'s key until 4.0, but the supported Structure range starts at PySpark 3.5.
- The initial lag/lead default hardening accidentally excluded date and timestamp literals even though PySpark accepts arbitrary default values and Structure supports those scalar literal types.

## Decision Log

- Decision: Treat the discovered execution mismatches as regression baselines, then use a shared matrix to prevent a renderer-only or evaluator-only implementation from recurring. Rationale: the same semantic operation has multiple lowering consumers.
- Decision: Keep this plan within V3 hardening. Do not introduce V4 API surface merely to improve tests. Rationale: coverage should verify the released contract before extending it.
- Decision: Preserve caller-owned streaming lifecycle. Tests may start, stop, restart, and inspect queries externally, but transformation code must not create or own queries. Rationale: this is a documented V3 architecture boundary.
- Decision: Resolve the map-entry type-model mismatch before changing its public type contract. Rationale: a quick string-map workaround would encode an incorrect abstraction permanently.
- Decision: Represent map entries as a generated internal Struct schema with non-null key and nullable value fields matching the source Map. map_from_entries accepts only non-null Arrays of exactly that key/value struct shape. Rationale: this matches Spark's real map_entries contract and preserves key/value types for safe round-tripping.
- Decision: Require classic-PySpark live semantic parity for supported V3 features. Treat Spark Connect as a separately recorded capability profile, rather than assuming classic behavior transfers. Rationale: availability and lambda/function support can differ by client/runtime.
- Decision: DSL-facing test modules use `from structure import *`, matching end-user code. Keep explicit `import structure` only where the test deliberately inspects the module namespace. Rationale: the wildcard import is the supported public DSL ergonomics, while introspection is necessarily module-oriented.
- Decision: Reject statically invalid approximate-aggregate parameters and integral window controls during recipe construction. Rationale: each has an unambiguous finite/range/type contract, and Python's `bool` must not be treated as a valid count.
- Decision: Make scalar multi-value helpers calculate their common Structure type during symbolic construction. Rationale: type and nullability form part of the expression contract used by output validation, nested expressions, and both execution paths; they cannot depend on argument order.
- Decision: Use a lightweight AST catalog test for constructor-to-backend completeness rather than a duplicated manually maintained operation registry. Rationale: it follows the construction code, catches additions missing a handler or capability, and leaves runtime semantics to focused tests.
- Decision: Apply the compiler's scalar-orderability rule directly to extrema window constructors. Rationale: these expressions do not pass through aggregate validation, but Spark requires the same orderable scalar domain.
- Decision: Restrict lag/lead defaults to compatible Python scalar literals. Rationale: PySpark consumes a raw fallback rather than a Column, and generated code must never serialize arbitrary Python object representations.
- Decision: Treat date and timestamp as supported lag/lead scalar defaults. Rationale: they are typed Structure literals, PySpark's default parameter accepts values, and generated modules now add the required `datetime` import.
- Decision: Make DecimalType enforce Spark's 1..38 integer precision and integral scale domain. Rationale: these are intrinsic type invariants, not execution-time data conditions.
- Decision: Infer the common numeric arithmetic type and nullability during symbolic construction; cast decimal arithmetic to the declared projection type in both backends. Rationale: type metadata must not make an invalid output look assignable, while decimal result precision remains Spark-derived.
- Decision: Model SQL predicate nullability at symbolic construction and compiler validation, while retaining `null_safe_eq(...)` as the explicitly non-null comparison. Rationale: predicate metadata determines projection assignability and must agree with both PySpark execution paths.
- Decision: Restrict Structure ordering contracts to orderable scalar expressions and reject options that no selected backend lowering honors. Rationale: accepting a recipe only to ignore an option or fail Spark analysis violates the DSL's early-diagnostic contract.
- Decision: Enforce Boolean control parameters at symbolic construction, including `descending` and `ignore_nulls`. Rationale: annotations alone do not protect untyped Python callers, and implicit truthiness is not an intentional DSL feature.
- Decision: Admit a single empty grouping-set level as a global aggregate. Rationale: it is explicitly documented, models ordinary global aggregation, and needs no synthetic grouping key.
- Decision: Propagate nullable array elements and nullable higher-order predicate results through `arr_exists(...)` and
  `arr_forall(...)`. Rationale: a nullable Boolean is a real outcome of Spark's three-valued `exists` and `forall`
  semantics, and output assignability must not erase it.
- Decision: Derive `arr_aggregate(...)` nullability from the input array and callback result; also include the initial
  accumulator when no finish callback exists. Rationale: Spark bypasses merge for empty arrays and returns the initial
  accumulator directly.
- Decision: Normalize an explicit PySpark `StorageLevel` into its five constructor settings in the backend-neutral IR,
  while retaining `cache=True` as the default `persist()` spelling. Rationale: symbolic plans cannot carry a backend
  object, but generated and online execution must use exactly the level requested by the source recipe.
- Decision: Model Spark's published sum result widening directly in symbolic expressions and treat filtered value
  aggregates as nullable. Rationale: aggregate metadata governs schema assignability before rendering, so it must not
  conceal a Spark result type or empty-filter null outcome.
- Decision: Use Spark's bounded Decimal average projection (precision and scale plus four) for every Structure average
  helper. Rationale: grouped and window variants share the same Spark aggregate expression and must have one type
  contract.
- Decision: Mark collection-aggregate arrays and their elements non-null regardless of source nullability. Rationale:
  the supported default PySpark collection aggregates skip null input values and return an empty array when none remain;
  Structure does not expose the newer SQL RESPECT NULLS mode.
- Decision: Treat reusable-window extrema as nullable regardless of input nullability. Rationale: callers may choose a
  frame that excludes the current row, leaving an empty boundary frame.
- Decision: Validate bounded range frames at DSL construction, requiring one numeric order expression, while allowing
  a fully unbounded range frame to retain Spark's multi-key/non-numeric ordering flexibility. Rationale: offset-based
  range bounds alter the order value and Spark therefore cannot evaluate them over arbitrary ordering types.
- Decision: Require `arr_aggregate(...)` merge results to exactly match the initial accumulator type rather than merely
  share a common numeric type. Rationale: the merge result becomes the next accumulator state; `finish=` is the
  deliberate separate conversion boundary.
- Decision: Require the two `map_zip_with(...)` map keys to have exactly the same Structure type. Rationale: Spark
  combines keyed map entries, and does not coerce one key domain into another.
- Decision: Reject map-containing map keys as a type invariant, and require `map_concat(...)` inputs to share their key
  and value types. Rationale: Spark rejects nested map key domains and concatenates only same-shaped map values.
- Decision: Lower metric filters for ordered first/last aggregates by nulling their ordering expression. Rationale:
  `min_by` and `max_by` ignore null order values, so this removes excluded rows without changing the selected value
  expression or requiring a separate aggregate relation.
- Decision: Type the `arr_aggregate(...)` finish accumulator from both the initial and merge-result nullability.
  Rationale: every merge result becomes the next accumulator state, so `finish=` must observe its real nullable domain.
- Decision: Reuse the common Spark sum-result type rule for `rolling_sum(...)`. Rationale: rolling and ordinary window
  sums are the same Spark aggregate over different frames, so their numeric widening must not diverge.
- Decision: Mark value aggregates nullable when the active grouping sets include the global empty-key level. Rationale:
  that branch returns a row on empty input, making `sum`, extrema, averages, and ordered first/last values null.
- Decision: Treat aggregate and transform-expression nullability as their operation-level contract during output
  assignment validation. Rationale: these operations have semantics beyond their raw arguments, including filters,
  frames, and missing values; recomputing from child expressions is unsound.
- Decision: Mark non-null input values required for window extrema, sum, average, and Boolean aggregates when the
  explicit frame includes the current row. Rationale: the frame then cannot be empty and necessarily contains one
  required value; frames that can exclude it retain the conservative nullable contract.
- Decision: Construct text normalizers through the shared String helper. Rationale: validation and result typing are
  part of the public DSL contract, so permissive backend coercion must not leak into symbolic schemas.
- Decision: Derive Decimal `round(...)` metadata with Spark's bounded result-scale formula, while retaining the input
  type for integral and floating-point values. Rationale: Decimal result metadata is needed for valid output-schema
  assignment and must match the generated PySpark expression.
- Decision: Propagate only outer-array nullability through `arr_position(...)`. Rationale: a missing match is the
  documented non-null position sentinel `0`, and null elements do not alter that result contract.
- Decision: Treat Boolean aggregates like the other value aggregates: required only for non-null, unfiltered non-empty
  groups, and nullable for a global empty grouping-set branch. Rationale: Spark's Boolean aggregates ignore null input
  and return null only when no qualifying value exists.
- Decision: Restrict event-time bounds to non-negative fixed Spark intervals at DSL construction. Rationale: the bounds
  are interpolated into `INTERVAL` expressions by both lowerings, so a finite grammar provides early diagnostics and a
  safe common contract.
- Decision: Canonicalize and validate `date_trunc(...)` units at DSL construction. Rationale: Spark admits a finite
  documented unit set and invalid units produce null rather than a safe static Timestamp result.
- Decision: Treat `to_decimal(...)` as nullable regardless of source nullability. Rationale: it is a parsing and
  narrowing boundary whose invalid or out-of-range present values produce no Decimal result.
- Decision: Let compiler assignment validation retain semantic nullability for conversion expressions and derive
  `when(...)` nullability solely from its value branches. Rationale: expression construction knows outcomes that a
  generic child-nullability walk cannot safely reconstruct.
- Decision: Require a Python literal searched item/key for `arr_position(...)` and `map_contains_key(...)`. Rationale: that is the common PySpark 3.5/4.0 contract; accepting a Column would make a valid-looking DSL recipe fail on the supported baseline.

## Candidate Inventory

Candidates below are ordered by risk and scope. Confirmed items are already repaired but remain in the permanent regression suite. Investigate items require a focused reproducer before being classified as a defect; implementation follows only after the intended contract is established.

### Confirmed regressions to retain

1. Online event_time_between support and timestamp-only diagnostics.
2. arr_aggregate finish callback receives the accumulator, and online lowering uses Spark's aggregate finish argument.
3. arr_sort_by evaluates callback keys, including ascending/descending nullable-key ordering, rather than sorting raw items.
4. All production imports, expression consumers, generated artifacts, and public API snapshots use operations and transform_expression; V2 names remain only in testing-model/history locations.

### Operation type contracts and collection semantics

5. Investigate whether arr_aggregate validates that the merge callback returns the accumulator type. Spark requires accumulator type stability; finish may intentionally produce a distinct result type.
6. Investigate arr_position item typing. It obtains the array element type but does not currently prove the searched value is compatible with it, unlike array_contains.
7. Investigate arr_sort_by key admissibility. Reject or document non-orderable callback results instead of delegating map/array ordering failures to Spark.
8. Investigate nullable transformed keys and duplicate-key behavior in map_transform_keys; Spark map keys cannot be null and duplicate-key handling may be runtime-configured.
9. Investigate key-type compatibility in map_zip_with; the two input maps should not be silently combined if their key domains differ.
10. Resolve the inaccurate map_entries / map_from_entries typed representation. Choose a schema-aware entry representation or defer the public operation with an explicit diagnostic; do not retain a fabricated map<string,string> result type.
11. Prove literal-versus-column behavior and null/out-of-range semantics for array_contains, array_repeat, element_at, try_element_at, map_contains_key, map_concat, and lookup/set helpers on the supported PySpark versions.
12. Verify try_element_at availability and behavior in the project's supported Spark-version intersection. Add a capability gate or fallback only if the intended contract cannot be supported directly.

### V3 feature-family semantic parity

13. Scalar expressions: nulls and boundary values for string, regular-expression, collection-scalar, numeric, date/time, cast, and predicate helpers.
14. Joins: single and composite using keys, alias disambiguation, explicit Cartesian acknowledgement, strategy hints, forward as-of tolerance and ties, and right/full diagnostics before a Spark action.
15. Aggregations: grouping sets including empty groups, grouping_id, is_grouped, aggregate-only having, and null behavior.
16. Windows: multiple ordering keys, each null-ordering direction, rows/range frames, aggregate-window null semantics, and rejected unsupported/distinct combinations.
17. Collection transformations: empty and null arrays/maps, one-based indexing, duplicate map keys, variable key/count operands, map callbacks, and generated-versus-online results.
18. Source-ordered raw fragments, step, and variadic where: ordering around bindings, multiple outputs, serial-equivalence of predicates, and explain/trace observability.

### Streaming and cross-cutting release evidence

19. File-stream parity for watermarked deduplication, aggregation, bounded stream-stream joins, and correlation in both generated and online paths.
20. Caller-controlled restart and independent-checkpoint scenarios that verify stateful behavior without adding lifecycle ownership to Structure.
21. Stream classifier and diagnostics coverage for every admitted and rejected shape, including watermarked field/lane/order reporting and caller-action guidance.
22. A catalog-based completeness check ensuring every special expression/function has the required renderer, online evaluator, explain/tracing, validator, and stream-classifier handling.
23. Generated fixture/example synchronization, public API snapshots, capability documentation, troubleshooting guidance, and a clean no-production-V2-reference scan.

## Plan of Work

### Milestone 1: Make semantic coverage exhaustive and preserve repaired regressions

Create one authoritative test catalog for expression kinds and special lowerings. It must state which consumers apply to each entry: type validator, generated renderer, online evaluator, explanation/tracing, and stream classifier. Exercise the catalog so adding a new operation cannot silently omit a consumer.

Retain focused regression tests for event_time_between, arr_aggregate, and arr_sort_by using both symbolic/rendered assertions and real Spark rows where relevant. Add type-boundary tests that prove diagnostics occur during recipe construction or validation rather than after a Spark job begins.

### Milestone 2: Close type-contract gaps before expanding behavior
