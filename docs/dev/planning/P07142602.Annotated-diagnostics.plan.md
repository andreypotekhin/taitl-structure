# Add Annotated Source Locations to Diagnostics

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` sections as work proceeds. Maintain this document according to
`docs/dev/auto/Plans.md`.

## Purpose / Big Picture

Structure diagnostics already give users a stable code, named context, a problem, a reason when useful, a shortest
safe action, and a documentation link. They do not yet show the relevant source code: `Diagnostic.source` is only one
unstructured display string. After this work, a compiler diagnostic that has reliable source coordinates will retain
the existing Structure layout and render its `Source:` section as an annotated excerpt with a caret and an explanatory
label. A diagnostic without source text or source coordinates will retain the current plain `Source:` line, so users
see one consistent diagnostic format on every surface.

For example, a nullable assignment should be observable as a single Structure diagnostic, not a second Rust-like
renderer family:

    CompileError SCHEMA-E0301: Nullable expression assigned to non-nullable field

    Context:
      transform: NormalizeOrders
      field: total

    Source:
      --> orders/transforms/normalize.py:24:15
       |
    24 |     total=order.discounted_total(),
       |           ^^^^^^^^^^^^^^^^^^^^^^^ may produce null

    Problem:
      An output assignment may produce null for a non-nullable

    Use:
      Guard the value with where(value.is_not_null()) or provide a non-null default.

    See docs/Diagnostics.md#schema-e0301

The first implementation deliberately makes no edit to user code and no claim that every diagnostic has a precise
expression span. It must make exact, trustworthy spans available where the compiler can prove them, and it must fall
back gracefully everywhere else. This improves correction speed without turning diagnostic rendering into a parser or
requiring a separate terminal format.

## Decision Log

- Decision: keep one `RenderDiagnostic` and enrich its existing `Source:` section when a diagnostic contains an
  annotated span.
  Rationale: all Structure failures should retain the same recognizable order of title, context, source, problem,
  why, action, and docs. A source excerpt is additional evidence, not a different kind of diagnostic.
  Date/Author: 2026-07-14 / Codex and user.

- Decision: preserve `Diagnostic.source` as a logical, string-based fallback and add optional structured source spans
  beside it.
  Rationale: configuration, runtime, generated-output, and compiler diagnostics without readable source must remain
  fully useful and source-compatible with current callers.
  Date/Author: 2026-07-14 / Codex and user.

- Decision: use one primary span and zero or more related spans. A primary span identifies where the user should act;
  a related span explains a declaration, prior use, or other cause.
  Rationale: this gives Structure the useful part of Rust's labelled source diagnostics without collapsing rich named
  context into terminal art.
  Date/Author: 2026-07-14 / Codex and user.

- Decision: define positions as one-based Unicode character columns at the public diagnostic boundary; convert Python
  AST byte offsets before constructing a span.
  Rationale: terminals and IDE users count displayed characters, whereas Python AST `col_offset` values are UTF-8 byte
  offsets. Exposing AST offsets would point at the wrong character in non-ASCII code.
  Date/Author: 2026-07-14 / Codex and user.

- Decision: make source excerpts an immutable part of the span, captured when the compiler can read source, rather
  than having the renderer reopen arbitrary paths.
  Rationale: rendering stays deterministic, supports in-memory source trees, and does not fail or show changed source
  after the diagnostic is constructed.
  Date/Author: 2026-07-14 / Codex and user.

- Decision: this slice renders advice through the existing `Use:` section and does not add automatic code edits or a
  `structure explain` command.
  Rationale: the registry docs link is already the durable deeper explanation. Edit suggestions need a separate
  correctness contract, and a command-line documentation reader is independent of the diagnostic-format improvement.
  Date/Author: 2026-07-14 / Codex and user.

## Outcomes & Retrospective

The implementation adds `SourceExcerpt`, `SourceSpan`, and `BuildSourceSpan` under the shared diagnostics library. The
shared renderer uses a focused source helper, so compiler, configuration, runtime, and CLI diagnostics retain one
format. All frontend errors raised through `CompileTransform._error()` and UDF warnings now receive a declaration-level
span whenever Python source is inspectable; the ambiguous-member collector does too. Schema errors therefore identify
their enclosing method, not an unproven assignment expression. Missing source text retains the previous logical source
line. Expression-level and related declaration spans remain intentionally deferred until the symbolic IR carries a
verified AST origin. Focused pytest and mypy checks pass; add the `make build` outcome here when it completes.

## Context and Orientation

Structure is a Python library that compiles schema-enforced transformation classes into Spark execution plans. A
diagnostic is an immutable, structured value that is rendered for exceptions, the CLI, tests, and future integrations.
The stable code and templates live in `src/structure/lib/cross/errors/registry.py`; the value type is
`src/structure/lib/cross/errors/Diagnostic.py`; and all current human text is produced by
`src/structure/lib/cross/errors/RenderDiagnostic.py`.

The present renderer prints a title, `Severity:`, optional `Context:`, optional one-line `Source:`, `Problem:`, optional
`Why:`, `Use:`, and a docs link. `StructureCompileError` exposes that rendered text from
`src/structure/app/compiler/diagnostics/model/StructureCompileError.py`. Configuration and runtime diagnostics route
through exactly the same renderer, so changes to the model and renderer must preserve their current output where no
span is supplied.

A source span is a source location with a display path, a beginning and ending line/column, an optional label, and a
small immutable excerpt. The display path is project-relative when a known project/source root provides one; it must
otherwise be a stable module-oriented label, never an absolute workstation path. A primary span marks the erroneous
text. A related span marks other text that explains the error, for example a non-nullable field declaration.

`CompileTransform` and `CompilerTransformMemberCollector` are representative compiler producers. They already receive
transform classes and members that Python's `inspect` module can locate in normal filesystem source. Some compiler
errors have no literal user expression to underline yet, because symbolic expressions and plans do not carry Python
AST nodes. This plan first attaches spans only where their location is certain: a named declaration or method. It then
adds a narrowly scoped AST locator for source constructs whose semantic identity is unambiguous. It must not guess at
a line based on matching text.

`docs/background/Diagnostics.back.md` is the published diagnostic contract. It currently requires source file, line,
column, and expression display when available, and requires deterministic, security-conscious rendering. Update it
and the public `docs/Diagnostics.md` index only to document the strengthened source-location behavior; diagnostic
codes and their meanings do not change.

## Plan of Work

### Milestone 1: Extend the model without changing ordinary diagnostics

Create `src/structure/lib/cross/errors/SourceSpan.py` with frozen dataclasses `SourceExcerpt` and `SourceSpan`.
`SourceExcerpt` holds the first one-based line number and an ordered tuple of complete source lines. `SourceSpan` holds
the display path, one-based inclusive start line and column, one-based inclusive end line and exclusive end column,
an optional short label, and an optional excerpt. Validate at construction that paths are nonempty and normalized for
display, lines and columns are positive, the end position is not before the start position, and an excerpt covers the
primary start line when one is supplied. Do not accept absolute display paths.

Extend `Diagnostic` with `primary_span: SourceSpan | None = None` and
`related_spans: tuple[SourceSpan, ...] = ()`, after the existing defaulted fields. Retain `source: str` unchanged. A
diagnostic with a primary span may also retain a logical `source` value, because a transform or expression identity is
still useful to tools and non-terminal consumers. Export the span values through
`src/structure/lib/cross/errors/__init__.py`; do not expose them from the top-level public `structure` package in this
slice.

Add `src/structure/lib/cross/errors/BuildSourceSpan.py`. It is a small standard-library-only action that receives an
inspectable Python object and a display-path policy, safely obtains source file text and the object's first source line,
and returns a declaration-level span with two lines of context before and after it. It must catch `OSError`,
`TypeError`, and unavailable source text and return `None`; diagnostic construction must never fail because source is
unavailable. Its path policy receives the actual path only to read it and returns either a project-relative path or a
stable logical label. Keep source text out of registry entries and never serialize absolute paths into traceability or
generated artifacts.

Add model-focused tests in `tests/lib/diagnostics/`. Prove frozen values reject invalid coordinates, preserve logical
`source`, permit no-span diagnostics, and do not import PySpark. Include an accented identifier test that proves any
AST byte-offset conversion used by the next milestone marks the intended displayed character.

### Milestone 2: Attach trustworthy compiler locations

Create `src/structure/app/compiler/diagnostics/logic/BuildCompilerDiagnosticSource.py`. This orchestration action
receives the transform class, an optional member function or schema class, and the compilation display-path policy. It
delegates to `BuildSourceSpan`; it does not duplicate `inspect` or path logic in compiler checks. Thread the relevant
project root from compiler options to this action where options are available. For direct frontend calls without a
project root, render the module-qualified name as the source label instead of leaking an absolute filename.

First route the representative diagnostics that already know their owner through this action:

- `CompilerTransformMemberCollector._effective()` attaches a primary declaration span to the ambiguous transform
  member diagnostic.
- `CompileTransform` attaches a primary method-declaration span to invalid method structure, missing/invalid schema
  parameter, and hook-signature diagnostics when it has the method or hook member.
- UDF warnings attach the transform or step-method declaration span, rather than claiming the UDF call expression is
  exact.

For schema output compatibility diagnostics, add a source-location seam at the point where the compiler creates the
diagnostic. If the output assignment's AST node and enclosing method have a verified mapping, underline the right-hand
side expression and label it, for example, `may produce null`; otherwise use the enclosing method's declaration span.
The mapping must be based on parsed source plus exact AST line/column attributes and an explicit semantic identifier
carried by the assignment. It must not search source text for a field name, because repeated names, comments, and
formatting make that ambiguous. If the required identity is not currently present in the IR, add the smallest immutable
origin field needed to carry it from symbolic compilation to the check, and test that it does not affect generated code
or plan equality apart from origin metadata.

Related spans are optional in this milestone. Add one only where Structure can name the related declaration exactly;
the nullable assignment diagnostic may point to the schema field declaration with label `declared non-nullable here`.
Do not add a fabricated related span merely to make output look compiler-like.

Use real temporary Python modules in tests, not test functions defined interactively, so `inspect` has source to read.
Also create an in-memory/no-file class fixture and prove it emits the old logical source instead of raising an internal
error. Keep test source paths relative to the temporary project root in asserted output.

### Milestone 3: Render annotations within the existing layout

Refactor `RenderDiagnostic.__call__()` only enough to delegate `Source:` rendering to a focused helper, such as
`RenderDiagnosticSource`. The outer renderer must keep the existing first line and every existing named section in the
same order. When `primary_span is None`, emit exactly the current one-line source behavior. When it is present, render:

    Source:
      --> <display-path>:<start-line>:<start-column>
       |
    <line> | <source text>
       | <spaces>^... <primary label when present>

Render at most five excerpt lines: the marked line plus the nearest context lines supplied by `SourceExcerpt`. Preserve
tabs in the source line but calculate caret alignment with a deterministic tab expansion width of four. A one-character
span renders one caret; longer spans render carets up to the source line end. For a multi-line span, mark the primary
line and append an ellipsis marker rather than drawing a misleading full-file range. Render each related span after a
blank source divider using `::: <display-path>:<line>:<column>` and the same bounded excerpt shape. Related spans must
not replace context, problem, why, use, or documentation.

Terminal color is optional decoration only. The plain returned string is the contract and must contain all meaning.
Do not introduce terminal-width querying, filesystem reads, ANSI escape sequences by default, third-party formatting
dependencies, or a second renderer class selected by diagnostic category.

Update renderer tests with one exact concise annotated transcript, one labelled related-span transcript, a multi-byte
identifier alignment case, and an assertion that a no-span compiler/configuration/runtime diagnostic keeps the existing
layout. Keep broader tests focused on structured values and high-signal text rather than snapshotting all diagnostics.

### Milestone 4: Document, exercise, and finish safely

Update `docs/background/Diagnostics.back.md` to define the optional `primary_span`, `related_spans`, coordinate
convention, display-path rule, excerpt limit, and fallback behavior. Clarify that source annotation augments `Source:`

Add a user-story test under

Run focused tests as each layer lands, then run the project formatter and full build from the repository root. Resolve

## Validation and Acceptance

The change is accepted when a human can verify all of the following.

- A representative compiler error with readable source renders one Structure diagnostic containing its existing
  headline, context, `Problem:`, `Use:`, and docs link, plus an annotated `Source:` excerpt with the right
  project-relative location and a caret label.
- A diagnostic that has a known related declaration renders a labelled second location without losing the original
  problem or action.
- Configuration, runtime, CLI, and compiler diagnostics without a structured span render as they did before; no source
  lookup failure masks the actual diagnostic.
- Absolute local paths, source text outside the bounded excerpt, data samples, secrets, ANSI control codes, and memory
  addresses do not enter rendered diagnostics.
- UTF-8 source with non-ASCII text aligns its caret with the intended displayed character.
- Stable codes, their severity/title/meaning, and every public `docs/Diagnostics.md` anchor remain unchanged.
- `make build` exits successfully.

## Idempotence and Recovery

The changes are additive and safe to repeat. `SourceSpan` construction and rendering do not write files or mutate a
diagnostic. The source helper may read a file only while constructing a compiler diagnostic; it never modifies that
file. If a source file cannot be read, return no span and emit the existing logical source instead.

If AST origin propagation proves more invasive than the milestone permits, ship declaration-level spans only and record
the deferred expression span work in `Surprises & Discoveries` and a focused suggestion. Do not delay the reusable
model, renderer, and trustworthy locations by guessing expression coordinates. If project-root propagation is not
available at a public frontend entry point, use a module-qualified display label rather than an absolute path.

## Artifacts and Notes

The new internal interface at the end of the work is conceptually:

    @dataclass(frozen=True)
    class SourceExcerpt:
        first_line: int
        lines: tuple[str, ...]

    @dataclass(frozen=True)
    class SourceSpan:
        path: str
        start_line: int
        start_column: int
        end_line: int
        end_column: int
        label: str = ""
        excerpt: SourceExcerpt | None = None

    @dataclass(frozen=True)
    class Diagnostic:
        entry: DiagnosticEntry
        problem: str = ""
        use: str = ""
        context: Mapping[str, str] = field(default_factory=dict)
        source: str = ""
        primary_span: SourceSpan | None = None
        related_spans: tuple[SourceSpan, ...] = ()

`RenderDiagnostic(diagnostic, kind="CompileError")` remains the one rendering entry point. Its source helper has two
branches based only on `primary_span` availability, not based on whether a diagnostic is compiler, runtime,
configuration, or CLI output.

## Interfaces and Dependencies

Use only Python's standard library (`dataclasses`, `inspect`, `pathlib`, and `ast` where expression origins are proven)
and existing Structure diagnostic modules. Do not add a third-party diagnostic or terminal-formatting package. The new
`SourceSpan`, `SourceExcerpt`, `BuildSourceSpan`, `BuildCompilerDiagnosticSource`, and rendering helper are internal
implementation interfaces. Their only public effect is the extra structured fields on `Diagnostic` and more helpful
rendered source sections.

`DiagnosticRegistry`, registry entries, diagnostic codes, severity values, and documentation anchor URLs are unchanged.
`SourceSpan` must not import PySpark, compiler packages, Click, or configuration packages; it remains usable by every
diagnostic surface without dependency leakage.
