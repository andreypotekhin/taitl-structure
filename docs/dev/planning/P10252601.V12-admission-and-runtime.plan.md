# Establish the V12 PySpark 4.2 runtime and admission inventory


This ExecPlan follows [Plans](../auto/Plans.md). Maintain Progress, Surprises & Discoveries, Decision Log, and
Outcomes & Retrospective as work proceeds.

Status: ready for Sprint 61 implementation; prepared on 2026-10-25. Runtime implementation has not started.

## Purpose / Big Picture


Give maintainers two reproducible PySpark 4.2 test targets and an explicit account of what happens to every V11
feature on the new runtime. A target is one version/profile and execution variant; ordinary PySpark runs against a
Spark session directly, while Connect submits batch plans to a separate Spark server. Users should be able to run
the same declared-schema projection on both targets, use an admitted retained query, and receive an actionable
diagnostic for a feature whose 4.2 evidence is still pending.

This plan implements Sprint 61 of the twelve-sprint V12 charter. It establishes runtime infrastructure, a pinned
4.1-to-4.2 API/semantic inventory, and capability continuity. It does not implement the new temporal, spatial, sketch,
ranking, Arrow, state, observation, or CDC features assigned to Sprints 62–71. Connect stays batch-only. Sources,
sinks, checkpoints, triggers, query lifecycle, and recovery stay caller-owned.

## Surprises & Discoveries


The resolver already accepts the exact string `>=4.2,<4.3`, but its branch adds the PySpark 4.0 capabilities and
`is_valid_variant`; it omits most exact-4.1 features, provider admission, and materialization operations.
Accepting the profile therefore does not establish continuity.

The ordinary 4.1 runner deliberately selects backend-version checks and V11 tests, while other existing general
selections include integration and live concepts. The launcher partitions broad selections into contracts, examples,
and runtime/concepts, each with a 3,600-second deadline. Preserve these differences and report their selection scope.

The upstream 4.2 Connect generated protocol file states Protobuf Python Version 6.33.5. Reusing the 4.1 image's
6.33.0 runtime pin is unsafe without checking that generated-code requirement. The 4.2 installation guide also
requires Arrow >=18 and Connect gRPC >=1.76.0; Java 17 and Python 3.11 remain suitable baseline choices.

The provider documentation reviewed on 2026-10-25 does not establish a supported Delta/Spark 4.2 pair. Iceberg
1.12.0's published Spark artifacts list 3.5, 4.0, and 4.1. Record these as availability constraints, not a reason
to install mismatched provider jars or block Apache-only runtime preparation.

## Context and Orientation


Structure captures typed Python transforms as a shared intermediate plan. Online execution and generated PySpark
both lower that plan to Spark APIs. Static compilation must work without importing PySpark or starting Java.
A capability is a pair such as `query.exists` that the selected backend must admit before lowering.

`scripts/run_integration.py` enumerates backends, starts required Compose services without recreating them, and runs
one test container at a time. `infra/compose/docker-compose.yaml` defines services and runner environments;
`infra/compose/.env_example` supplies default pins. The mounted launcher is
`infra/compose/images/pyspark/run-integration.sh`; its current provider conditions are explicitly tied to old backends.
`scripts/ensure_compose_env.py` preserves an existing local .env, so new pins must have Compose defaults as well.

`tests/integration/pytest_plugin.py` owns pytest backend choices.
`tests/integration/pyspark/support/backend_matrix.py` owns backend/profile mapping, session construction, worker
Python deployment, and native/online/generated helpers. Add RocksDB configuration for ordinary 4.2 state tests
without configuring providers in its Apache-only session.

`src/structure/plugin/pyspark/capabilities/model/PySparkCapabilities.py` owns exact profile strings, version bounds,
capability sets, and corrective decisions. `tests/specifications/compatibility/test_pyspark_matrix_consistency.py`
checks selections, forwarding, cleanup, failure propagation, and six-target consistency.
The new work must expand those assertions rather than bypass them.

The current API census is
`src/structure/plugin/pyspark/resources/pyspark-4.1-python-api-delta.json`.
It separates documented-index appearance from API origin and runtime support. Use that convention for 4.2.
The transformation and streaming coverage JSON files remain the support ledgers; an API census is not a support claim.

## Plan of Work


### Milestone 1: Reproducible Apache-only 4.2 lanes


Extend the image build with an optional Python base-image argument whose existing default is unchanged. Select
`python:3.11.17-slim-bookworm` for the new lanes and retain Java 17. Resolve the base image to a digest and record
that digest and the installed Java patch version in the evidence report. Pin PySpark/Spark 4.2.0, pandas 2.2.3,
PyArrow 19.0.1, protobuf 6.33.5, grpcio/grpcio-status 1.76.0, googleapis-common-protos 1.71.0, and zstandard 0.25.0
for 4.2. Retain existing click/pytest/rich/toml pins. Freeze other transitive versions in the recorded pip manifest.
Check dependency consistency with `python -m pip check` and import the generated Connect protocol before running Spark.
If a candidate pin cannot resolve or the base tag is unavailable, stop that milestone, record the failed artifact,
and amend this plan with the exact compatible replacement; do not silently select latest.

Make Sedona installation conditional on a non-empty build argument while preserving its existing 1.9.0 default.
Pass an empty argument for 4.2, and leave Delta absent. Do not change old image dependency sets.
Add ordinary Spark 4.2 master/worker services, using default host ports 67077, 68080, and 68081, and two runner
services. Use the existing workspace/read-only plus writable integration-artifact mounts. Give the ordinary runner
the 4.2 master address. Run Connect in the runner-local server using its bundled 4.2 Connect jar, Scala 2.13,
local[2], a 3 GiB driver, UTC, and caller-test checkpoint cleanup. Do not register provider extensions.

Add PYSPARK42_VERSION=4.2.0 and PROTOBUF42_VERSION=6.33.5 to the example environment and provide matching
Compose defaults for existing local .env files. Keep service names explicit:
`spark42-master`, `spark42-worker`, `structure-integration-pyspark42`, and
`structure-integration-spark-connect42`.
Update BACKENDS, SERVICES, pytest choices, profile mapping, expected-runtime assertions, and runner contract tests.
The new Connect backend needs no standalone master service.

Use all three general partitions for both new lanes. Explicitly exclude Delta/Iceberg modules from their general
selection because no provider setup is admitted. Preserve all existing provider phases and the 4.1 general scope.
Update the launcher's Connect checkpoint and cleanup conditions for 4.2. New runtime tests must report client and

## Concrete Steps


Run from the repository root. Begin by confirming a clean baseline and checking the current matrix:

    git status --short
    poetry run pytest -q tests/specifications/compatibility/test_pyspark_matrix_consistency.py
    poetry run pytest -q tests/specifications/runtime-version-checks tests/specifications/backend-capabilities

After adding the inventory and runner changes, run:

    poetry run pytest -q tests/specifications/compatibility/test_v12_python_api_delta.py
    poetry run pytest -q tests/specifications/backend-capabilities/test_v12_continuity.py
    bash -n infra/compose/images/pyspark/run-integration.sh
    make build
    make integration-rebuild BACKEND=pyspark42
    make integration-rebuild BACKEND=spark-connect42

Then run the eight backend selections through `make build INTEGRATION=1`. Preserve sequential execution, existing
services, mounted-source checks, and per-phase deadlines. On macOS use command-scoped idle-sleep prevention,
for example `caffeinate -i make build INTEGRATION=1`. Do not tear down shared services or remove dependency caches.
Record focused selection evidence separately from unfiltered lane results.

## Validation and Acceptance


Both new lanes report PySpark/Spark 4.2.0, import their Connect protocol without a Protobuf version error, and pass
dependency checks. A declared projection and retained typed query produce the same schema and normalized rows
natively, online, and generated; generated Connect paths use no private JVM or SparkContext access.

Exact 4.2 profile selection works without broad-default promotion. A deliberately mismatched client/engine profile
raises the documented runtime diagnostic before execution; log/off behavior retains its tested semantics.
Pending feature diagnostics identify a valid remedy and responsible package. Static check/compile tests import
neither PySpark nor Java. Existing profile/variant behavior and the six old selections retain their regression results.

The pinned API census accounts for every addition/removal and selected semantic change. Each exact-4.1 capability
has a separate per-variant 4.2 row, with either positive evidence or a named sprint and reason. Provider availability
is recorded even when unavailable. All claimed cases pass and every skip has a documented existing or new gate;
do not hide a failure through a blanket 4.2 skip.

## Idempotence and Recovery


Keep old services and pins intact; create separate 4.2 services and image configuration. The environment helper must
not overwrite a developer's existing .env. Retrying a failed phase must use the same recorded pins and command,
and may reuse downloaded artifacts. Test-owned checkpoints and Connect server processes must clean up on success,
failure, and timeout. Preserve evidence from failed attempts with dated filenames.

Do not run multiple Spark test containers concurrently on the shared worker. If a provider cannot be resolved,
retain the Apache-only image and gate that provider. If image dependencies conflict, record and correct the pin
before any support promotion; do not install a different Spark release to satisfy a provider.
