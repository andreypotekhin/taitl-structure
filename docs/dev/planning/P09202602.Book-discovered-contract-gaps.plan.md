the appropriate raw-hook boundary, and copy executable examples from the documentation. After this work, duplicate
identifiers, invalid amounts, missing references, tied selected revisions, and overlapping temporal matches will

rows and schemas. Documentation will distinguish verified behavior, application responsibilities, and deliberate
capability limits without obsolete workarounds for already fixed defects.

## Context and Orientation


The library root is `C:/Taitl/Code/taitl/taitl-structure`; the book root is its sibling
`C:/Taitl/Code/taitl/taitl-structure-book`. Paths without a prefix are relative to the library. The book owns its
manuscripts, prompts, and runnable companions. Library fixes and their durable regression tests belong here.

A transform describes operations on schema-defined relations. Online execution interprets a checked operation
recipe into PySpark DataFrames; generated execution runs emitted PySpark code. Spark normally delays computing
rows until an action such as `collect()` or `count()`. Its optimizer can remove computations whose outputs are
unused. Consequently, seeing an assertion in emitted source is insufficient evidence that Spark evaluates it.

Relation operations are declared in `src/structure/plugin/pyspark/dsl/relation_sets.py` and
`src/structure/plugin/pyspark/dsl/operations_api.py`. Execution and rendering primarily live in
`src/structure/plugin/pyspark/execution/logic/running/RunOnlinePySparkTransform.py` and
`src/structure/plugin/pyspark/render/logic/steps/RenderPySparkStep.py`. Both must implement the same behavior.
In particular, `_require_unique`, `_require_all`, and `_require_reference` currently construct assertion columns,
cross-join them with the data, and drop those columns. `_selected_rows` currently ranks with `row_number` and
keeps rank one without checking ties. These are concrete investigation points, not substitutes for live evidence.

Hooks are ordinary Python methods operating on DataFrames. `InvokePySparkHooks` in
`src/structure/plugin/pyspark/execution/logic/InvokePySparkHooks.py` replaces bound relations with hook returns.
Validation recipes are assembled through
`src/structure/plugin/pyspark/compiler/logic/maps/MapPySparkValidation.py`. The exact boundary behavior is specified
in `docs/dev/specifications/ValidationSemantics.spec.md`: hook-local schema rules apply after the hook, and
schema-only validation must inspect metadata without scanning rows. Inspect how both runners consume those recipes.

Historical evidence is in the book's `docs/dev/planning/P09192601.Aggregation-joins.review.md`,
`P09192602.Collections-relations.review.md`, `P09202601.Extensions-execution.review.md`, and
`docs/dev/Troubleshooting.md`. Those checks used library revision `959149d4` and mostly online Spark 4.0.
They do not establish every current-mode failure. Record the current revision and dirty files before reproducing.

## Scope and Priorities


First fix correctness: assertions that accept invalid data, selection that silently resolves forbidden ties, and
temporal matching that accepts forbidden overlaps. Next settle hook validation and documentation discrepancies.
Cache ownership requires a verified cleanup recipe; a returned projection is not necessarily the internally cached
DataFrame. A new cache-ownership API is not a prerequisite unless the existing documented lifecycle cannot be made
correct. Preserve caller-owned caches and never use application-wide cache clearing as library cleanup.

The earlier summary overlooked ambiguity checks, subtotal flags, cache ownership, and broken reference examples.
This plan includes them. It also corrects the summary's claim that generated execution necessarily needs source
roots: the completed schema fix discovers dependencies from checked plans for an already imported transform.
Source discovery and deployment of Python dependencies remain separate responsibilities.

Do not broaden this repair into automatic third-party dependency installation, generated streaming sources/sinks,
raw WindowSpec support, or all deferred PySpark functions. Sentence segmentation with pySBD is an appropriate UDF
example. Range repartitioning remains batch-only. An explicit early-validation/action API is preserved as a possible
later proposal; the current work must make the already published assertions effective without requiring that API.

### Milestone 2: Make relation assertions enforce their published contracts


Begin with a small prototype using PySpark directly to establish whether assertion predicates survive optimization.
Inspect Spark's optimized plan to confirm or reject the hypothesis that dropping assertion columns removes checks.
Keep the schema and successful row results identical. The error must be causally required for evaluation rather
than placed in a disposable projection. Inspect `exactly_one` and existing hierarchy/priority guards for the same
construction; extend fixes only where a reproduction establishes the shared flaw.

Preserve `require_unique(*keys)`, `require_all(predicate)`, and
`require_reference(value, reference, reference_key=..., nulls=...)` as the user interface. Preserve the respective
`REL-E0702`, `REL-E0703`, and `REL-E0704` diagnostic identities and documentation links. A failed assertion must raise,
not discard offending rows. Keep schema-only validation scan-free and keep ordinary transforms without assertions lazy.

Prefer an optimizer-safe plan-level check. If Spark can still bypass it through empty output, counting, or later
filters, implement an explicit relation-boundary validation action for the authored assertion instead of claiming a
guarantee the lazy plan cannot provide. The source assertion explicitly requests that data check; document its job
cost and timing in the specification, explain output, and public API. Record the prototype evidence and decision
before adopting this fallback. Never silently add eager scans to ordinary schema validation or disable assertions
through a warning-suppression option. Preserve streaming capability restrictions for checks requiring batch actions.

Apply the selected approach to both online and generated paths using small focused delegates where helpful. Extend
`tests/specifications/v6-api-ledger/test_v6_relation_assertions.py` for capture/rendering, and use Milestone 1's live
tests as the enforcement proof. Acceptance requires all invalid cases to fail and valid/empty cases to follow the
documented contract in both modes on Spark 3.5 and 4.0.
