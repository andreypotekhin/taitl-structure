## Purpose / Big Picture

After this change, a PySpark transform author imports every PySpark-specific concept from
`structure.platform.pyspark`: field factories, field types, expressions, joins, aggregation,
streaming helpers, and all other symbolic operations. Core continues to own the Python
declaration model: `Schema` inheritance, `Transform` inheritance, input/output/lane
declarations, decorators, source order, step invocation, override rules, and hook placement.
PySpark owns the meaning and validation of a step body, including concrete and nested field
types. This makes it possible for a future platform to use different field definitions and
symbolic operations without putting its model in Core.

The observable result is a transform such as the following, which compiles and runs with the
same PySpark behavior as today while Core contains no join, expression, concrete field-type,
or PySpark operation plan.

    from structure import Schema, Transform, input, output
    from structure.platform.pyspark import col, field, inner_join

    class Order(Schema):
        id = field.long(nullable=False)
        customer_id = field.long(nullable=False)

    class Customer(Schema):
        id = field.long(nullable=False)
        name = field.string(nullable=False)

    class EnrichedOrder(Schema):
        id = field.long(nullable=False)
        customer_name = field.string(nullable=False)

    class Enrich(Transform):
        orders = input(Order)
        customers = input(Customer)
        result = output(EnrichedOrder)

        def enrich(self, order: Order, customer: Customer) -> EnrichedOrder:
            return EnrichedOrder(
                id=order.id,
                customer_name=inner_join(customer, on=order.customer_id == customer.id).name,
            )

The implementation preserves Core's existing ownership of the method call: Core determines
that `enrich` is a step, resolves its inherited declarations and lane bindings, invokes it once
with platform-supplied symbolic arguments, and records the result's structural placement.
PySpark captures the symbolic operation body and validates it. Core then dispatches the already
captured body to the selected PySpark compiler exactly once.

## Surprises & Discoveries

- Observation: `StepPlan` currently combines Core lifecycle facts with PySpark semantics.
  Evidence: `src/structure/core/compiler/ir/model/StepPlan.py` currently stores source/lane/origin and hooks beside
  `Expression`, `JoinPlan`, `AggregatePlan`, `OperationPlan`, and projections.
- Observation: Core's current frontend invokes user methods while installing `CompileContext`, `RowScope`, and
  `InputScope` from `src/structure/core/compiler/frontend/commands/CompileTransform.py`.
  Evidence: this correctly enforces source order, inherited-step calls, and raw-hook attachment, but makes the
  symbolic execution implementation Core-owned.
- Observation: `Schema` already owns useful target-independent class behavior, but its recursive-type validation is
  currently concrete-PySpark-type aware.
  Evidence: `src/structure/core/dsl/model/schemas/Schema.py` imports `ArrayType`, `MapType`, and `StructType` while
  checking nested schema cycles. That validation must move with the PySpark types; it must not be removed.
- Observation: Platform API test façades construct lightweight schema facets directly.
  Evidence: adding `SchemaAPI.validate()` required those fakes to implement the same no-op method before static
  protocol checking could pass.

## Decision Log

- Decision: Core owns transform structure and invokes every step method; the selected platform supplies symbolic
  arguments and captures the returned body.
  Rationale: Source ordering, inherited overrides, decorators, lane bindings, and hook placement are Structure
  semantics. Letting a plugin invoke methods would duplicate or weaken those guarantees.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: Extend Platform API v1 now with a required authoring facet rather than introduce v2.
  Rationale: v1 is still under active internal development. One explicit, complete v1 contract is preferable to
  preserving a temporary façade that cannot express platform-owned authoring.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: PySpark owns concrete-type and nested-type validation after its types move to the plugin.
  Rationale: Recursive structs, arrays, maps, nullability, aliases, and type compatibility are meaningful only under
  a platform's field model. Removing validation would regress schema safety; moving it preserves the current behavior
  and lets other platforms define their own rules.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: Remove `structure.field` and all root PySpark DSL aliases in this change.
  Rationale: A forwarding alias hides which platform owns the declaration and prevents a second platform from defining
  its own field vocabulary. The migration is intentionally breaking and is completed atomically across examples,
  fixtures, tests, and public documentation.
  Date/Author: 2026-07-18 / project owner and Codex.
- Decision: Core treats every captured platform step body and lowered payload as opaque.
  Rationale: Core may route a value through its workflow, attach the Core structural plan to an artifact, and ask a
  platform to serialize its payload, but it must not inspect target operations to render explain output, decide
  capabilities, or validate a target rule.
  Date/Author: 2026-07-18 / project owner and Codex.

## Context and Orientation

Core compilation begins at `Compiler.frontend.analyze()` and `Compiler.frontend.compile()`. `analyze()` currently uses
`CompileTransform` to create a `TransformPlan`; `compile()` selects a platform and sends that plan as
`CompileRequest.analysis` to `platform.compiler.compile()`. `BuildCompiledTransform` then creates the standard Core
artifact envelope. This workflow ownership remains unchanged.

The problem is the shape of the current plan. The Core compiler's `CompileTransform` imports PySpark-shaped expression
and transform models, symbolically executes methods with Core `RowScope` and `InputScope` objects, and stores the
result in Core `JoinPlan`, `OperationPlan`, aggregate, projection, and expression records. The bundled PySpark
compiler in `src/structure/platform/pyspark/platform_v1/Compiler.py` only lowers that Core-owned target model. Moving
only `JoinDedupe` or `JoinPlan` would leave expressions, aggregation, schema type checks, and method capture in Core.

A structural plan describes facts that are true regardless of data platform: a transform and step name, declaration
origin, input and output schemas, method parameter-to-lane bindings, output lanes, source order, declared options, and
raw-hook placement. A platform step body describes the target language evaluated by the method: for PySpark it is the
expression graph, join sequence, projection, aggregation, streaming operation, and target diagnostics. Core owns the
former and never interprets the latter.

The relevant Core declaration classes are `Schema`, `Transform`, `InputDeclaration`, `OutputDeclaration`,
`LaneDeclaration`, and decorators in `src/structure/core/dsl/model/`. They retain their behavior. Create the public
`structure.dsl` contract package and export `Schema`, `Transform`, the declaration classes, `FieldDeclaration`, and
`FieldDefinition` from it. `Schema` needs those common field containers to merge inherited Python attributes, but their
`type` value is opaque to Core. Only the selected schema facet interprets it. A plugin imports this shared declaration
contract from `structure.dsl`, never from a `structure.core` path.

`structure.platform.api.v1` is the public contract between Core and a selected platform. A public contract here means
that an independently packaged plugin can import the types without importing Core implementation modules. Requests and
results are frozen data classes or protocols. An opaque value is a value whose shape is owned by the plugin: Core may
retain and pass it to the same plugin but may not branch on its fields or type.

## Interfaces and Dependencies

Extend the v1 façade with a required `authoring` field in `PlatformAPI`. Keep the existing optional `analysis` facet
for post-compilation streaming and traceability reports; do not overload it with symbolic authoring. Add the following
public v1 models and protocols under `src/structure/platform/api/v1/` and export them from that package.

`StepAuthoringRequest` is a frozen request containing the selected platform name, plugin configuration mapping, a
stable step identity, the step name and declaration origin, ordered structural input bindings, ordered structural
result bindings, and the step's declared options. Its input and result bindings are public frozen API models containing
only parameter/lane/source names, schema objects, ordinals, and driving/result flags. They replace plugin imports of
Core `StepInputPlan`, `StepResultPlan`, and `TransformMemberOrigin`.

`AuthoringAPI` defines `open_step(request: StepAuthoringRequest) -> StepAuthoringSession`.
`StepAuthoringSession` is a context-manager protocol with these operations:

    arguments() -> tuple[object, ...]
    capture(value: object) -> object

`arguments()` returns exactly one platform symbolic scope for every ordered input binding. Core enters the session,
passes those scopes to the user method, and calls `capture()` exactly once with the returned value. `capture()` returns
one opaque platform body or raises a normal Structure diagnostic for invalid target DSL. The session is responsible for
installing and clearing only plugin-local symbolic state. It must not call Core compiler, frontend, capability,
traceability, schema, or platform-registry services.

Move the structural `TransformPlan`, `StepPlan`, input/output/binding, result, hook, and declaration-origin models to
`src/structure/platform/api/v1/` and export them from that package. Their schema fields are typed as `object` at this
public boundary so the API itself imports no Core implementation module. Core remains their sole constructor.
`Compiler.frontend.analyze()` returns this target-neutral structural plan without evaluating any platform DSL. A
`StepPlan` has a `platform_body: object | None` slot, initially empty. `Compiler.frontend.compile()` selects the
target, asks its schema facet to validate the reachable schemas, then has the Core authoring runner attach one opaque
body to every schema-returning step. The compiler facet receives that completed plan in `CompileRequest.analysis` and
may read only the body values it owns. `PlatformCompilation.analysis` is the same Core-owned completed plan, attached
by Core after a successful compiler return. The compiler must not replace the structural plan.

Make `SchemaAPI.validate(schema: object, configuration: Mapping[str, object]) -> None` a required v1 operation. Core
calls it after target selection and before opening the first authoring session for every input, lane, and output schema
reachable from a transform. PySpark validates that every field declaration was created by the PySpark DSL, that nested
PySpark types are well formed and acyclic, and that aliases, nullability, metadata, and type compatibility satisfy
PySpark's existing rules. A foreign or mixed field definition fails before a user step method executes.

Move the Core concrete models to `src/structure/platform/pyspark/dsl/`, organized by responsibility rather than as one
large compatibility module. This package contains PySpark field factories and field types; expressions and symbolic
row/input scopes; projections; joins and their policy/value classes such as `JoinDedupe`; aggregates, windows,
selection, streaming, and optimization operations; PySpark plan/body records; and their validators. The PySpark
authoring facet owns the replacement for `CompileContext` and captures those records. The PySpark compiler facet
lowers only its own body records with its own capability rules.

Public imports are fixed as follows. `structure.dsl` exports the common declaration contract for plugin authors.
`structure` re-exports only its user-facing platform-neutral declarations: `Schema`, `Transform`, `input`, `output`,
`lane`, `transform`, `step`, `raw`, and `special`. It exports neither `field` nor a PySpark expression, join, type,
streaming, or operation name. `structure.platform.pyspark` re-exports the supported PySpark DSL from its internal
`dsl` package, including `field`, expressions, joins, policies, and type helpers. The plugin package may import
`structure.dsl` and `structure.platform.api.v1`, but no plugin module may import a `structure.core` compiler,
capability, traceability, frontend, registry, or implementation model module.

## Plan of Work

### Milestone 1: Establish a public structural-authoring boundary

First add the public v1 models and `AuthoringAPI` protocol. Update `PlatformAPI` validation, test fakes, the PySpark
plugin façade, and the iterable/conformance fixture so that a façade without `authoring` is rejected before a workflow
starts. Since the project intentionally extends v1, update `docs/specifications/PlatformAPI.md` and
`docs/dev/design/PlatformCallbackArchitecture.md` in the same commit to state that authoring is required and that Core
invokes user methods.

Move the structural plan records from Core IR to the public v1 API package and update Core to import them there. Keep
only structural fields in the records: no expression, join, projection, aggregate, operation, concrete type, or
streaming enum may remain in the Core-owned plan. Add `platform_body` as an opaque field on a completed step. The body
is absent only for a non-symbolic structural step; a schema-returning step must have one before `compile()` calls the
compiler facet.

Refactor `CompileTransform` into two focused collaborators. The structural collector discovers members, inheritance,
declarations, lane bindings, output schemas, options, and raw hooks. The Core authoring runner owns ordered method
invocation, current-step guards, permitted overridden-parent calls, result cardinality checks, lane updates, and hook
attachment. It calls `SchemaAPI.validate()` first, opens exactly one authoring session per schema-returning step, and
uses its arguments/capture operations. Delete Core's symbolic context creation and all Core validation that reads a
target body. Preserve existing diagnostic source context around the Core call so user errors still identify the method.

Keep `Compiler.frontend.analyze()` as the target-neutral structural API. It validates declarations, inheritance,
bindings, output schemas, decorators, and hooks, but it neither selects a platform nor invokes a schema-returning user
method. `Compiler.frontend.compile()` calls it once, resolves the target/configuration, validates every reachable schema
through that platform, and has the Core authoring runner enrich a copy of the structural plan with opaque bodies. It
then calls the selected `compiler.compile()` once with the completed plan in `CompileRequest.analysis`, rejects a
missing/invalid platform result, and attaches that exact completed plan to `PlatformCompilation.analysis`.
`BuildCompiledTransform` continues to own artifact identity, validation, and fingerprints. It stores the completed
structural plan; platform payload serialization remains delegated to the platform serializer.

Add unit contracts before moving PySpark behavior. A recording fake authoring facet must prove that Core supplies the
expected bindings, enters/exits one session, invokes each method exactly once, sends the captured body to the compiler
once, and preserves Core-owned inherited and raw-hook behavior. A failing fake schema validator must prove that no
step method runs after ownership validation fails.

### Milestone 2: Move PySpark authoring, plans, and validation

Create `src/structure/platform/pyspark/dsl/` and move the complete target DSL there. Do not leave forwarding modules
under `src/structure/core/dsl/model/expr`, `.../types`, or target operation/plan modules. Move each consumer with its
owner: PySpark lowering, generated rendering, online execution, explain, streaming classification, traceability, and
diagnostics import PySpark DSL/body records only from the plugin subtree.

Implement `PySparkAuthoringAPI`. Its session creates PySpark symbolic row and relation scopes from the structural
bindings, records joins/filters/projection/aggregate/window/streaming operations in plugin-local state, and validates
the captured return value against the declared result schemas. It returns an immutable `PySparkStepBody`. The body
contains all data previously stored in Core target IR, including source scopes needed by lowering and explain. It may
use PySpark-owned capability rules but must not resolve the platform or invoke a Core service.

Move field factories such as `string`, `long`, `decimal`, `array`, `map`, and `struct` into the PySpark DSL. Their
returned declarations use the shared, backend-neutral declaration container, tagged by the PySpark platform. Move
the concrete scalar, collection, and nested-struct type classes and all checks from `Schema`/Core compiler into a
PySpark schema validator. Preserve current behavior: invalid decimal precision or scale, invalid array/map nested
declarations, forbidden nested nullability configuration, duplicate aliases, recursive nested structs, and incompatible
projection/cast/type use all fail with the current equivalent diagnostic quality. The new validator must traverse
nested arrays, maps, and structs itself; it must not rely on Core class checks.

Refactor `Compiler` in `platform_v1` to accept only a completed structural plan plus `PySparkStepBody` values. It
validates PySpark semantic operation ordering and capabilities, lowers the bodies to its opaque PySpark payload, and
returns schemas/payload data. It does not call a Core compiler, capability, traceability, or frontend endpoint. Explain,
generated traceability, and streaming reports consume the lowered payload or PySpark body through the plugin's own
logic. Keep compiler-only code Spark-free.

Add tests that monkeypatch every former Core symbolic/compiler/capability/traceability entry point to raise. PySpark
compile, explain, generation, static streaming classification, and traceability must still succeed from supplied
bodies and payloads. Add tests for nested type validation entirely through the PySpark schema facet, including a
recursive struct and a mixed-platform field failure before step invocation.

### Milestone 3: Complete the breaking public-import migration

Remove `structure.field`, `structure.types`, root expression exports, root join/policy exports, and all compatibility
aliases that re-export PySpark DSL values. Remove their source modules after every importer is migrated; do not retain
deprecation shims. Update `src/structure/__init__.py`, public API snapshots, schema fixtures, transform fixtures,
generated samples, user stories, specifications, README examples, troubleshooting text, and design documentation.

Use `from structure import Schema, Transform, input, output, lane, transform, step, raw, special` for Core concepts
and `from structure.platform.pyspark import field, ...` for PySpark concepts everywhere. Ensure no Core production
module imports `structure.platform.pyspark` and no plugin production module imports a private `structure.core` module.
Shared public declaration and Platform API imports remain allowed.

Update documentation generation so Core renders only structural transform information. The PySpark documentation and
explain facet render operation, field-type, join, aggregation, and streaming detail from PySpark-owned bodies/payloads.
Preserve existing user-facing PySpark explain text and generated source wherever those outputs remain supported.

### Milestone 4: Prove isolation and preserve released behavior

Run focused contracts after each migration family. Add a static dependency test that rejects imports from
`structure.core.dsl.model.expr`, `structure.core.dsl.model.types`, Core target-plan modules, and all Core compiler

Run the existing compiler, platform API, PySpark generation, explain, traceability, schema, symbolic execution, and

## Validation and Acceptance

Acceptance is behavioral, not only an import reshuffle. The canonical PySpark transform in the Purpose section must
compile through Core, produce the existing PySpark output and generated source, and show its existing explain summary.
Its Core plan must show declaration order, bindings, origin, outputs, and hooks, but Core source must have no class or
branch that understands its join, expression, or concrete type.

A test transform with an inherited step and a `@raw` method must prove that Core still invokes the override under its
existing parent-call restrictions and attaches the hook in the same source-order location. The PySpark authoring session
must only supply symbolic arguments and capture its body. An invalid PySpark `array`, `map`, `struct`, decimal, alias,
or nested recursive schema must fail through `PySparkSchemaAPI.validate()` before any user step body runs. A second
fixture whose field declaration is tagged for a different platform must fail with an ownership diagnostic before
lowering.

Compiler isolation acceptance requires patching former Core symbolic, compiler, capability, and traceability facades to
raise. PySpark compiler, explain, generation, streaming classification, and traceability tests still pass because the
plugin uses its own bodies, validator, capability rules, and report builders. Conversely, static import checks prove
that no Core production module imports a PySpark platform implementation.

The final `make build` must pass. The recorded result must include exact pytest pass/skip counts and each required live
target lane's pass/skip count.

## Idempotence and Recovery

artifacts. Keep the new authoring path additive only while its Core and PySpark contract tests pass. Do not delete a
legacy Core target model until its PySpark replacement is imported by lowering, explain, execution, generation, and

the PySpark package. Do not reintroduce a PySpark model into Core. If an adapter is necessary for one milestone, mark it
as transitional in this plan's Progress section, test both paths, and delete it before the final import-migration
milestone. If a changed generated snapshot differs beyond imports, treat it as a semantic regression: compare the
opaque PySpark body and generated recipe before updating the expected output.
