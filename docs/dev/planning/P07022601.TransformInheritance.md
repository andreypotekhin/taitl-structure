## Purpose / Big Picture

Structure transform classes currently inherit declared inputs, lanes, and outputs, but the compiler only scans the
concrete class body for step method and hook methods. After this change, a developer can factor common pipeline steps
into a parent `Transform` class and extend them in a child class. Parent step methods run before child step methods.
For multiple inheritance, direct parent classes run left to right in the order written in the Python class declaration.

The observable behavior is simple:

    @transform
    class NormalizeBase(Transform):
        rows = input(Raw)
        normalized = lane(Normalized)

        @transform(output=normalized)
        def normalize(self, row: Raw) -> Normalized:
            return Normalized(id=row.id)

    @transform
    class PublishOrders(NormalizeBase):
        published = output(Published)

        def publish(self, row: Normalized) -> Published:
            return Published(id=row.id)

    assert [step.name for step in compile_transform(PublishOrders).steps] == ["normalize", "publish"]

For multiple inheritance:

    @transform
    class PublishOrders(NormalizeBase, AuditBase):
        published = output(Published)

`NormalizeBase` steps run first, then `AuditBase` steps, then local `PublishOrders` steps.

## Surprises & Discoveries

- Observation: `Transform.__init_subclass__` already merges `_structure_inputs`, `_structure_lanes`, and
  `_structure_outputs` from direct bases before local declarations.
  Evidence: `src/structure/app/dsl/model/transforms/Transform.py` updates declaration maps from `cls.__bases__`.

- Observation: inherited step methods are currently invisible to compilation.
  Evidence: `CompileTransform._steps` iterates `transform_class.__dict__.items()`, and `CompilerHookCollector.collect`
  does the same for hooks.

- Observation: generated PySpark classes intentionally do not inherit from the source transform class.
  Evidence: `docs/dev/specifications/PySparkCodeGeneration.md` says generated classes must not inherit from source
  transforms, and `RenderPySparkTransformModule` emits `class {Transform}Generated:` with no base class.

## Decision Log

- Decision: Implement transform inheritance by flattening the effective source transform body into `TransformPlan.steps`.
  Rationale: Online execution and generated execution already consume ordered plan steps. Flattening keeps the target
  runners unchanged and preserves the existing generated-class rule.
  Date/Author: 2026-07-02 / Codex

- Decision: Direct or indirect `Transform` ancestors contribute inherited step methods and hooks even when they are not
  decorated with `@transform`.
  Rationale: Parent transform fragments should be reusable building blocks and may be intentionally incomplete. The
  concrete class being compiled still requires `@transform`.
  Date/Author: 2026-07-02 / Codex

- Decision: Multiple inheritance order is recursive parent-first, direct-base-left-to-right, with diamond bases visited
  once.
  Rationale: This matches the user request for parent transforms to run first and for multiple parents to run in the
  declared order, while avoiding duplicate execution of a shared diamond ancestor.
  Date/Author: 2026-07-02 / Codex

- Decision: A subclass may override an inherited step method or hook method by reusing the method name. The override
  replaces the inherited method at the inherited position. Sibling parents that define the same effective method name
  are ambiguous unless the concrete child overrides that name.
  Rationale: Replacement preserves the parent pipeline skeleton for normal subclass customization. Sibling duplicates
  do not have a clear declared-order meaning and would make hook targeting by method name unsafe.
  Date/Author: 2026-07-02 / Codex

- Decision: An override may call `super().method(row)`, `Base.method(self, row)`, or
  `super(Base, self).method(row)` to schedule the selected parent implementation as a separate step immediately before
  the child step.
  Rationale: This gives parent and child implementations the isolation Python users expect from override composition:
  separate hooks, validation, lane writes, traceability, and generated-code blocks.
  Date/Author: 2026-07-02 / Codex

- Decision: Step-level default options come from the class that declares the effective step method, with
  method-level options still taking precedence.
  Rationale: Parent transform fragments should carry their own `target_backend`, `target_platform`, or `target_profile`
  defaults. The concrete child's plan-level options remain attached to the final `TransformPlan`.
  Date/Author: 2026-07-02 / Codex

## Context and Orientation

A Structure transform is a Python class decorated with `@transform` and inheriting from
`structure.app.dsl.model.transforms.Transform.Transform`. It declares DataFrame inputs with `input(Schema)`,
intermediate lanes with `lane(Schema)`, final results with `output(Schema)`, and public schema-returning instance
methods as step methods.

The current compiler path is:

1. User code calls `compile_transform(SomeTransform)` from `src/structure/app/dsl/api.py`.
2. `src/structure/app/compiler/frontend/commands/CompileTransform.py` validates the transform class and emits a
   backend-neutral `TransformPlan`.
3. `src/structure/app/target/pyspark/commands/LowerPySparkPlan.py` lowers that plan to a `PySparkExecutionPlan`.
4. `src/structure/app/runtime/execution/online/commands/RunOnlinePySparkTransform.py` runs the ordered steps online,
   or `src/structure/app/target/pyspark/commands/RenderPySparkTransformModule.py` renders generated PySpark source.

The important current limitation is local scanning. `CompileTransform._steps` loops over
`transform_class.__dict__.items()`, so it sees only methods declared directly on the concrete class. The hook collector
also loops over `transform_class.__dict__.items()`. This plan changes that one concept: both step discovery and hook
discovery should consume a shared effective member list that includes decorated transform ancestors in the required
order.

The term "effective transform member" means a function that participates in compilation after inheritance and override
rules are applied. It can be a step method, a hook method, or a public helper that will be ignored because it
does not return a `Structure` schema. The collector preserves class-body order inside each contributing class and visits
direct or indirect `Transform` parents even when they are not decorated with `@transform`.

## Plan of Work

Milestone 1 documents the public contract and creates failing tests. Update `docs/dev/specifications/DSL.md` in the
`Transform Classes` and `Step methods` sections to state that direct or indirect `Transform` parents contribute
step methods and hooks even when they are not decorated with `@transform`, parent steps run first, multiple direct
bases run left to right, diamond ancestors run once, subclass overrides replace the inherited method at its inherited
position, explicit parent calls schedule separate parent steps, and ambiguous sibling method names produce a compiler
diagnostic. Add a short example to `docs/QuickRef.md`. Add completed user-story entries to
`docs/dev/specifications/UserStories.md`.

Milestone 2 introduces effective member collection. Add
`src/structure/app/compiler/frontend/logic/CompilerTransformMember.py` with a frozen dataclass containing
`owner: type[Transform]`, `name: str`, and `member: Callable`. Add
`src/structure/app/compiler/frontend/logic/CompilerTransformMemberCollector.py` with a `collect(transform_class)`
method. The collector should recursively visit direct bases left to right, visit parent bases before the child, skip
the root `Transform`, include undecorated `Transform` parents, skip already visited classes for diamonds, and include
the concrete class. It should build an ordered mapping by method name. A method from a subclass of the previous owner
replaces the previous member while keeping the original position. A duplicate method name from a sibling parent raises
a `StructureCompileError` explaining that the concrete child must override the method or rename one parent method.

Milestone 3 wires the collector into compilation. In `CompileTransform.__init__`, create the member collector. In
`_steps`, replace the `transform_class.__dict__.items()` loop with effective members. Use the effective member's
`owner` when resolving step defaults in `_step_options(owner, metadata)`. Keep passing the concrete `transform_class`
to declaration validation so inherited declarations are validated against the concrete effective declaration maps.
When invoking a member, continue calling the function object with the concrete instance:

    result = member.member(instance, *arguments)

This keeps inherited methods able to call `self` helpers and allows generated hook execution to use `Child()` while
calling inherited hook methods through normal Python attribute lookup.

Milestone 4 updates hook collection. Change `CompilerHookCollector.collect` to accept the effective member list, or
give it the same collector dependency. It must group hooks by `(phase, target)` using effective hook methods in effective
order. This preserves parent hooks before child hooks for the same target. Hook signature validation can continue using
`getattr(transform_class, hook.name)` because runtime invocation receives an instance of the concrete transform class.

Milestone 5 hardens diagnostics and traceability. Add tests proving that diagnostics for inherited invalid methods point
to a useful source. If current `_error(transform_class=child, member=name)` is too vague, extend the member dataclass
with a `source` property such as `"{owner.__module__}.{owner.__name__}.{name}"` and teach the duplicate-name diagnostic
to use it. Do not widen traceability models unless tests reveal a user-visible gap; ordered step names are enough for
the feature.

Milestone 6 verifies target behavior. Because lowerers, renderers, online runtime, generated runtime, streaming
compatibility, and traceability all consume ordered plan steps, they should not need structural changes. Add regression
tests that lower and render an inherited transform and assert the generated text contains `# Step method: normalize`
before `# Step method: publish`. Add an online-runtime test using the injected `online_executor` or the fake frame
runtime already used in `tests/user_stories/10_generated_code/shared_pyspark_semantic_contract` to prove the ordered
plan is what execution receives.

## Validation and Acceptance

The feature is accepted when a transform child can inherit and extend parent transform steps, and both compile-time and
target behavior show the parent-first order. A human can verify acceptance by reading the new tests and observing:

    poetry run pytest tests/specifications/transform-inheritance -q

Expected result:

    8 passed

Then run:

    make build

Expected result: the full project build and test suite exits with status 0.

Specific behavior that must be true:

- `compile_transform(Child).steps` includes inherited parent step methods before local child step methods.
- `compile_transform(Child(A, B)).steps` follows direct parent declaration order: A, then B, then Child.
- A diamond ancestor contributes steps once.
- Parent and child hooks attach to inherited steps by target method name.
- Generated PySpark source renders inherited steps in the same order as the compiler plan.
- Online execution receives the same ordered plan.
- Ambiguous sibling method names fail early with a structured compiler error that tells the user to override or rename.

## Idempotence and Recovery

The work is additive and safe to retry. Re-running the tests and build should not mutate source files. If a collector
change breaks existing transform tests, inspect the failing step names first; most failures should be ordering or
override semantics. Keep the old local-only behavior available in the git diff while developing so the implementation
can be narrowed without reverting unrelated user changes.

If the duplicate-name diagnostic is difficult to express through the existing `CompileTransform._error` helper, keep the
initial diagnostic simple and add a follow-up suggestion in `docs/dev/suggestions/`. Do not block the core inheritance
feature on perfect diagnostic provenance.

## Interfaces and Dependencies

New internal model:

    @dataclass(frozen=True)
    class CompilerTransformMember:
        owner: type[Transform]
        name: str
        member: Callable

New internal collector:

    class CompilerTransformMemberCollector:
        def collect(self, transform_class: type[Transform]) -> tuple[CompilerTransformMember, ...]:
            ...

Updated hook collector:

    class CompilerHookCollector:
        def collect(
            self,
            transform_class: type[Transform],
            members: tuple[CompilerTransformMember, ...],
        ) -> dict[tuple[str, str], tuple[HookPlan, ...]]:
            ...

No public runtime API changes are required. The public behavior changes in `@transform` compilation only: inherited
decorated transform members become part of the child transform's compiled plan.
