# Iterable Plugin Authoring and Python Generation

This ExecPlan is a living document. Maintain its `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections as implementation proceeds. It follows `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

Turn `examples/plugins/iterable` from a minimal external-plugin conformance fixture into a realistic, readable example for Structure plugin authors. After this work, an author can see one independently packaged plugin supply a target DSL, accept normal Structure `input` and `output` fields, capture `@step` methods returning schema instances, compile the result into a target-owned recipe, execute that recipe over finite Python rows, and generate equivalent standalone Python with visible `for` loops.

The example is deliberately finite and in-memory. It demonstrates the plugin boundary and generated-code contract; it does not promise a portable distributed, streaming, or arbitrary-Python-control-flow API.

  Evidence: `src/structure/core/compiler/frontend/commands/CompileTransform.py` opens one plugin authoring session per step and passes every binding and result in `StepAuthoringRequest`.

- Observation: Iterable currently refuses step authoring and only compiles exactly one `IterablePlan` class attribute.
  Evidence: `examples/plugins/iterable/src/structure_iterable/authoring/Authoring.py` raises from `open_step`, and its compiler scans class attributes instead of `request.analysis`.

## Context and Orientation

Structure owns transform discovery, field declarations, `@step` binding, source order, and the neutral `TransformPlan`. A selected plugin owns the symbolic values supplied to each step, captures the returned target-specific body, lowers every step into an opaque payload, optionally executes the payload, and optionally generates source.

The Iterable package lives at `examples/plugins/iterable/src/structure_iterable`. It is installed independently through the `structure.plugin` entry point and must continue to import only the public `structure` and `structure.plugin.api` surfaces, never `structure.core`. Its current operations and executor demonstrate finite projection, join, aggregate, and recurrence semantics, but in a class-attribute DSL. The new implementation transfers those capabilities into a step-method DSL and one shared lowered recipe model.

The generated-code boundary currently consists of `GenerationAPI.generate(GenerationRequest) -> Mapping[str, str]` and Core's `GeneratedTransform`. Replace that raw mapping with an API-owned immutable `GenerationResult` carrying `files`, `module_name`, and `classes`. A plugin decides all three values. `Transform.generate()` writes `files` and copies the declared module/class metadata into `GeneratedTransform`; it must not synthesize a target name or package path.

## Plan of Work

### 1. Define the Iterable step language and capture model

Replace `dsl/operations.py` and its public exports with a compact symbolic DSL tailored to finite mapping rows. `Authoring.open_step(request)` must return an Iterable step session whose `arguments()` are one symbolic row per `StepAuthoringInput`; a driving row and a joined/secondary row are distinguishable in the captured body but expose schema field access consistently. `result_arguments()` must return symbolic rows for inherited step calls.

Capture a schema instance returned from a step as a projection recipe: each constructor keyword is a target expression consisting of a field read or supported literal. Capture a returned tuple as one projection per declared result, in declared order. Verify that a returned schema instance has the declared result schema and that the tuple length and schemas match `request.results`.

Provide these public body operations:

- `inner_join(right, on=right.key == left.key)` and `left_join(...)` attach an explicit keyed relation operation to the active step. The first step parameter is always the ordered driving left relation. The secondary relation may only be read after its join operation. Join predicates support one equality between a field from the driving/previously joined side and a field from the secondary side.
- `group_by(*keys).aggregate(result)` marks the step as a finite aggregate. Aggregate expressions support `sum_(field)` and `count()`; key fields and aggregate expressions populate the returned schema instance. Groups retain the order of their first input row.
- `scan(index=..., initial=(...), output=result, next_state=(...))` marks the step as a finite ordered recurrence. The input index must be contiguous from zero, output expressions may read state values and numeric literals, and the next-state tuple must have the same arity as the initial state.

The session must reject unsupported operations, missing joins before secondary-row access, arbitrary function calls, non-equality join predicates, invalid aggregate expressions, and invalid scan shape with precise `TypeError` messages naming the Iterable constraint and the available remedy.

### 2. Lower once and execute the same recipe online

Create immutable Iterable-owned body and recipe dataclasses under `structure_iterable/compiler/model` (or an equally focused model package). A transform recipe contains transform name, named inputs, ordered steps, final outputs, and per-step projection/join/aggregate/scan instructions. It contains no live Schema classes, transform instances, symbolic scopes, or callables, so serializer output and fingerprinting are deterministic.

Change `Compiler.compile` to require `request.analysis` to be `TransformPlan`, verify every `StepPlan.plugin_body` is an Iterable body, lower all steps in source order, and serialize a canonical recipe for the `iterable:` fingerprint. Remove the scan-specific class-field inference and all `IterablePlan` handling.

Refactor `Execution` to interpret that recipe against named finite iterables of mapping rows. Materialize each input exactly once so lists, tuples, and one-shot generators are repeatable. Mapping executes a loop over the driving rows. A keyed join builds a right-side index, then emits one row per inner match or one null-filled row for an unmatched left join. Aggregation groups driving rows in first-seen-key order. Scan carries state through the ordered rows and rejects non-contiguous indices. Each final output returns an `IterableRelation`; multi-output runtime execution returns `TransformResult` with the declared output names.

### 3. Make code generation target-neutral and add Iterable Python generation

Add `GenerationResult` to `structure.plugin.api.v1.model`, export it through the public v1 model API, and update `GenerationAPI` so `generate` returns it. The value has exactly these fields:

    files: Mapping[str, str]
    module_name: str
    classes: tuple[str, ...]

Update `Transform.generate()` to require `GenerationResult`, write its files, and use its module/class metadata in `GeneratedTransform`. There is no mapping-return fallback and no Core-owned `.pyspark` path construction. Update the PySpark generation facet to wrap its existing file map in a result whose module name and class names match its current output, retaining all PySpark generated-code behavior.

Add an Iterable generation facet to the plugin façade. It accepts the mapping of source-transform names to Iterable recipes supplied in `GenerationRequest`, emits package marker modules and one target-owned transform module at `<generated_package>/iterable/transforms/<source-module>.py`, and returns the corresponding `GenerationResult`. Each generated `<Transform>Generated` class exposes `run(**inputs)`: a single final output returns `list[dict[str, object]]`; multiple final outputs return `dict[str, list[dict[str, object]]]` keyed by declared output name. Render each lowered operation as direct standard-library Python. Do not import the Iterable executor or call `execute` from generated source.

### 4. Replace the fixture examples and documentation

Replace the Iterable README's projection attribute and recurrence examples with one realistic multi-step transform. It must declare two inputs and named outputs, project a schema instance, call a keyed left join, produce a grouped aggregate, and run a finite scan. Show the relevant generated Python loop excerpt and state the `run(**inputs)` return contract. Update `docs/dev/PluginAuthoring.md` to identify the fixture as the reference for fields, symbolic authoring, lowering, online execution, generation, and target-owned generation metadata.

Migrate the fixture's school examples and plugin-discovery test transforms to the new step syntax. Preserve unrelated working-tree changes; reconcile any user changes to those files rather than overwriting them.

## Validation and Acceptance

The feature is complete when all of the following are observable:

- An independently installed Iterable plugin compiles a transform with `input`/`output` fields and `@step` methods; no class-owned operation field is required or accepted.
- A method can return `Target(field=source.field)` and a tuple of schema instances for declared multiple outputs.
- A method with two relations must call an explicit keyed join before reading secondary fields; generated code visibly contains the right-side index and driving `for` loop.
- Aggregate and scan helpers produce deterministic online and generated results, including first-seen grouping order and scan index validation.
- Generated source imports and exposes the exact `GenerationResult.module_name` and `GenerationResult.classes`; it has no PySpark dependency and does not delegate to the plugin executor.
- Existing PySpark generation returns the new strict result type and all its generation regressions pass.
- Invalid symbolic bodies fail during compilation with actionable Iterable-specific messages.
- `make build` passes.

## Artifacts and Notes

The central authoring shape is:

    @transform(target="iterable")
    class Enrich(Transform):
        orders = input(Order)
        customers = input(Customer)
        enriched = output(Enriched)

        @step(input=[orders, customers], output=enriched)
        def enrich(self, order: Order, customer: Customer) -> Enriched:
            left_join(customer, on=customer.id == order.customer_id)
            return Enriched(id=order.id, customer_name=customer.name)

The corresponding generated implementation must contain the semantic equivalent of:

    customer_index = index_by(customers, "id")
    enriched = []
    for order in orders:
        matches = customer_index.get(order["customer_id"], ())
        for customer in matches or (null_customer,):
            enriched.append({"id": order["id"], "customer_name": customer["name"]})

The actual renderer may inline the index and null-row mechanics, but must retain the same observable behavior and remain readable as an instructional artifact.
