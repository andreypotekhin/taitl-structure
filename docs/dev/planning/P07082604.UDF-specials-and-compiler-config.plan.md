## Purpose / Big Picture

Structure should let transform authors use Python UDFs when that is the right tool, without hiding the optimizer cost. After this change, users can write `@special(type="udf")` helpers inside a `Transform`, call them from compiled subtransforms, and run the transform in online or generated PySpark mode. By default the compiler warns when UDFs appear; projects can set `warn_on_udfs = false` in Structure config when that opacity is intentional.

This also replaces the unreleased expression-helper decorator with the clearer `@special(type="expr")`. Transparent expression helpers remain optional: ordinary helper methods are allowed when symbolic execution can compile their bodies.

## Surprises & Discoveries

- Observation: The previous expression-helper wrapper simply executed the helper during symbolic compilation and wrapped the result with `literal(...)`; transparent helper support was already mostly present, while true UDF support required explicit expression IR plus PySpark rendering and online evaluation.
  Evidence: the deleted helper wrapper replaced by `src/structure/app/dsl/model/transforms/SpecialFunction.py`.

## Decision Log

  Rationale: UDFs should be allowed, but warning should be configurable because the real concern is optimizer opacity.

## Context and Orientation

The relevant modules are `src/structure/app/dsl/model/transforms/transform_api.py` for public decorators, `src/structure/app/dsl/model/transforms/SpecialFunction.py` for the current helper wrapper, `src/structure/app/compiler/frontend/commands/CompileTransform.py` for symbolic execution, `src/structure/app/configuration` for config, `src/structure/app/target/pyspark` for generated PySpark, `src/structure/app/runtime/execution/online/logic/PySparkExpressionEvaluator.py` for online PySpark execution, and `src/structure/app/compiler/traceability` for dataflow and opaque boundary reporting.

A transparent helper is Python helper code whose body returns Structure expression DSL and remains visible to the compiler. A UDF helper is Python helper code intentionally executed by Spark as a Python UDF; its body is opaque to Spark optimization. An opaque boundary is a point where Structure can no longer inspect field-level behavior, similar to hooks.

## Plan of Work

First add config support. Extend `StructureConfig` with `warn_on_udfs: bool`, default it to `True`, validate it as a boolean, include it in `ResolveStructureConfig._keys`, build it in `StructureConfigBuilder`, and emit it from `WriteStructureConfig` when seed config is requested. Update config tests.

Next change compiler entrypoints. Update `CompileTransform.__call__` and exported `compile_transform(...)` so callers may pass `config`, `project_root`, and config override kwargs, mirroring `StructureSession`. Internal recursive calls for `TransformPipeline` composition must pass the already-resolved config rather than re-resolving. CLI render/generate/docs paths should pass their resolved config into compilation. Direct calls with no arguments should resolve from current working directory.

Then add the special decorator. Implement `special(type=..., **options)` in `transform_api.py` and export it through `structure.app.dsl.api` and `structure.__init__`. Accepted types are `expr`, `udf`, and `opaque`; unknown types fail immediately. Replace current `SpecialFunction` with a small focused model that stores the original callable and metadata. `type="expr"` should preserve the current transparent behavior. `type="udf"` should return a UDF expression only when called while a compile context is active; otherwise it should call the original Python function. `type="opaque"` should fail during symbolic compilation with a diagnostic telling users to use `type="udf"` or a hook.

Add UDF return type resolution. Accept `return_type=` as a Structure type class or instance, such as `String` or `String()`. Also accept PySpark `DataType` instances without importing PySpark at import time; detect by duck-typing on the runtime object/module path once provided. If `return_type` is absent, map simple Python return annotations to Structure types: `str -> String()`, `int -> Integer()`, `float -> Double()`, `bool -> Boolean()`, `datetime.date -> Date()`, and `datetime.datetime -> Timestamp()`. If no supported type is available, raise a registered diagnostic with a docs link and an actionable fix.

Add UDF expression representation. Use `Expression(kind="python_udf", type=..., nullable=..., data=...)` with deterministic fields: function name, defining module/class/member, generated UDF variable name, return type descriptor, and whether the return type is native PySpark. Arguments are normal child expressions. When a UDF expression appears and `config.warn_on_udfs` is true, add one deterministic warning diagnostic per transform/function, explaining that Python UDFs are optimizer-opaque and linking to diagnostics/performance docs.

Add PySpark recipe and rendering support. `PySparkExpressionMapper` should map `python_udf` expressions and require a PySpark UDF capability that is present for ordinary PySpark. `RenderPySparkExpression` should render calls through deterministic generated member names. `RenderPySparkTransformModule` should import source classes when UDFs are present, instantiate source owner classes as needed, and register UDFs in `__init__` with `F.udf(callable, returnType=...)`. For Structure return types, use `RenderPySparkSchema.type(...)`; for native PySpark return types, reference the object safely through the source function metadata or store it as a generated class attribute.

Add online support. Extend `PySparkExpressionEvaluator` to evaluate `python_udf` by creating/caching `functions.udf(...)` callables and applying them to evaluated argument columns. Reuse `materialize_pyspark_schema.type(...)` for Structure return types and pass native PySpark `DataType` objects through as-is.

Update traceability. `CompilerDataflowReads` should recurse into UDF arguments so static dataflow still shows source columns. `BuildCompilerTraceability` should add an opaque boundary or equivalent record for UDF expressions with reason `python UDF body`. `RenderExplainReport` should show UDF warnings through existing diagnostics and include opaque UDF boundaries in traceability output.

Remove the previous expression-helper decorator. Replace imports/usages in examples, tests, README, docs, and generated public API snapshots with `special(type="expr")` or ordinary transparent helpers where clearer. Keep only `SpecialFunction` as the internal implementation model for `special(...)`. Update diagnostic guidance to name `@special(type="expr")`.
