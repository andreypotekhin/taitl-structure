## Context and Orientation


A Spark logical plan is the deferred description of how to compute a DataFrame. Reusing a DataFrame may repeatedly
embed that description; a small row count therefore does not guarantee a small plan. An eager snapshot writes rows
and reads them back, cutting their dependency on the upstream plan. A reliable checkpoint provides another explicit
boundary backed by caller-owned storage. Persisting a frame alone does not provide the same boundary.

The original recommendation 1 was explicit materialization between offline preparation and retrieval, then a
fusion boundary if needed. It is implemented in `tests/integration/pyspark/support/snapshots.py`, its fixture in
`tests/integration/pyspark/conftest.py`, and `examples/search/transforms/searching/search_docs/fuse.py`.
`SearchDocuments.py` in that directory keeps one public component and passes `materialize=~streaming` to
FuseDocuments. Do not introduce a parallel batch component, remove the UDF, or pass streaming state to FuseDocuments.

Recommendation 2 was generating required test artifacts once per backend/configuration while isolating imports.
`tests/integration/pyspark/support/generated_sources.py` implements a module-owned cache keyed by the complete
request, including backend options and stage exposure. Returned source dictionaries are copies; imported generated
modules remain test-local. The `search_sources` fixture in `tests/integration/pyspark/search/test_search.py` uses
this cache. It still generates a broad transform catalog once, except for unsupported Connect 3.5 transforms.
Per-scenario narrowing was a preference, not required for completing the reuse fix; defer it unless measurements
show remaining generation cost justifies added fixture complexity.

Recommendation 3 was measuring exposed stage outputs. These are public outputs of nested transforms, accessible
in addition to final results. Search tests resolve `STRUCTURE_SEARCH_STAGE_OUTPUTS=0|1` once during collection and
pass the same `allow_stage_outputs` value to online sessions, generated compilation, and generated-source caching.
The default is `0`, while library defaults remain true. The cost of true versus false has not been isolated in
recorded live measurements; changing the setting and reporting overall speedup is not that comparison.

Recommendation 4 was shared row collection reuse, bounded runner timeouts, and phase timings.
`tests/integration/pyspark/support/rows.py` now reuses explicitly ordered collections for unordered assertions while
preserving distinct Spark order requests. `infra/compose/images/pyspark/run-integration.sh` bounds pytest to 3600
seconds by default, accepts `STRUCTURE_INTEGRATION_TIMEOUT`, and allows a 15-second kill grace. It prints Connect
server diagnostics on failure. `support/timing.py` supplies `phase(label)`, snapshots log their write/read duration,
generated import setup/cleanup is timed by `generated_project`, snapshot-directory cleanup is timed by the fixture,
and the reranking test logs construction and collection. These timings do not add Spark actions; they only bracket
work already required by the fixture or test.

Existing implementation evidence is recorded in
`docs/dev/planning/past/P09252601.Search-integration-lineage.plan.md`: the complete seven-test Connect 4.0 Search
module passed in 139.34 seconds; isolated reranking passed in 181.41 seconds on classic 3.5 with a 1 GiB driver and
83.59 seconds on Connect 4.0 with 3 GiB. These are different runs, not a controlled comparison. Full document-search
checkpointing remains unsupported on Connect 3.5; this plan does not expand that capability claim.

## Plan of Work


### Milestone 1: Reproducible stage-output selection


Add a test-only environment switch `STRUCTURE_SEARCH_STAGE_OUTPUTS`, accepting exactly `0` or `1`, defaulting to
`0`, and rejecting invalid values before any live work. Put its parser in a focused helper under
`tests/integration/pyspark/support/` and cover it in `tests/app/test_integration_search_options.py`. In
`tests/integration/pyspark/search/test_search.py`, use the same resolved Boolean for the session partial, direct
rendering partial, and `search_sources` request. Do not change production configuration defaults or mutate cached
source dictionaries. Existing source-cache tests already distinguish stage-output configurations; retain them.
The normal test command must continue to select final-output-only behavior. The switch enables measuring the same
test, inputs, materialization boundaries, and assertions with stage exposure enabled.

Preserve `tests/specifications/transform-composition/test_stage_result.py` and stage-related coverage in
`tests/specifications/online-execution/test_v1_structure_session.py`. Do not make lazy stage preparation a prerequisite
or silently weaken stage validation. If exposure reveals a separate correctness failure, record and isolate it;
do not interpret failure or missing outputs as a performance improvement.

### Milestone 2: Complete phase observations


Use the existing `phase(label)` context manager to label source generation, fixture preparation, final-transform
construction, collection, and owned cleanup. Add reusable timing at ownership boundaries in `generated_sources.py`
and `conftest.py`; label generated import cleanup where `generated_project` owns it in `support/backend_matrix.py`.
Complete scenario-level timing in the text-fixture and reranking tests. Keep nested snapshot timings explicitly
labeled as nested: they must not be summed again into their enclosing preparation duration. Source-cache hits and
misses should be distinguishable without retaining Spark objects. Eager checkpoint execution is part of measured
construction, so do not describe that time as pure planning or subtract it without separate evidence.

Add `tests/app/test_integration_timing.py` with a controlled clock to verify start/end messages on success and
exception, propagation of the original exception, and cleanup labels. Measurement must not call count, collect,
explain, or schema solely to get timings. A live failure must still identify the last phase started. Preserve
runner deadlines and resource cleanup, including cleanup on exceptions; test instrumentation must not swallow
errors or change fixture lifetimes.

### Milestone 3: Controlled comparison and handoff


Run the reranking and text-fixture cases with exposure off and on in fresh runners. Keep backend, image, fixture
data, driver heap, partition settings, validation options, and checkpoints fixed within each comparison. Use the
default 1 GiB classic driver and 3 GiB Connect driver; record any actual configuration override. Run three paired
repetitions per backend, alternating which setting runs first. Do not run competing benchmarks concurrently.
Record individual times and medians, not just the best run. Separate cold source generation from cache-hit setup.

Record backend/runtime/image identity, settings, test node, exposure mode, phase times, pytest total, exit status,
and unchanged expected-value/parity results in `docs/dev/issues/I09272601/SearchIntegrationPerformance.bench.md`.
An enabled-stage run that times out or exhausts heap is a bounded result, not a fabricated speed ratio; stop
repeating the same failing configuration after one diagnostic confirmation. Keep library-default changes or lazy
stage preparation out of this plan; recommend them separately only if evidence warrants them.

Run the full default Search module on both measured backends, the focused non-live suites, and `make build`.
Update `docs/dev/Testing.md` with the switch and timing interpretation, and developer troubleshooting if a new
failure/remedy is discovered. Finish by recording limitations and moving this plan to `docs/dev/planning/past/`.

## Validation and Acceptance


Both settings must retain the original expected rankings and online/generated final-row equality in every
successful comparison. The default path must preserve seven passing Search cases on Connect 4.0 and complete the
classic 3.5 Search module without heap exhaustion. New option tests must reject ambiguous values. Source reuse
must remain configuration-sensitive, row reuse must not replace Spark ordering, and cleanup must remove only
owned resources. All phase durations must be nonnegative; exceptions must remain visible and propagate normally.

The report must distinguish observed cost from causal claims: exposure is the only changed variable within a
pair. No absolute speedup is required to finish an honest comparison. A bounded on-mode failure is acceptable
evidence if identified as such and the default lane remains correct. `make build` must pass before completion;
skipped live tests and cached historical logs are not new runtime proof. If Docker is unavailable, keep live
acceptance open rather than mark the plan complete. The preliminary pair is recorded in
`docs/dev/issues/I09272601/SearchIntegrationPerformance.bench.md`; it is not sufficient to close the plan.

## Idempotence and Recovery


Use fresh per-run containers and existing unique shared-volume snapshot/checkpoint directories. Do not delete
another task's containers, storage, or logs. After a timeout, verify that the owned runner and Connect child have
exited before retrying. If cleanup itself hangs, identify that separately from pytest execution; do not claim the
pytest deadline bounds every possible teardown operation. Preserve all preexisting uncommitted changes. Revert
only this plan's instrumentation if it changes behavior; keep the proven materialization/reuse implementation.
