# Modernize Search Similarity and Support Caller-Owned ANN Backends

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date during implementation. It follows `docs/dev/auto/Plans.md` and the repository automation contract in `docs/dev/auto/Automation.md`.

## Purpose / Big Picture

The Search example should show how Structure can express a useful, inspectable similarity-search system without pretending that a distributed DataFrame scan is a production vector database. After this work, a caller will be able to combine lexical and vector neighbor candidates, inspect why each result ranked, and replace the example’s exact vector scorer with an HNSW or other approximate-nearest-neighbor (ANN) provider without changing the hybrid ranking or presentation stages.

HNSW means a hierarchical graph that makes nearest-neighbor lookup faster by visiting a small portion of the vector collection. ANN means approximate nearest-neighbor retrieval: it trades a measured amount of recall for lower search cost. The caller owns building, persisting, refreshing, and querying such an index. Structure owns the typed candidate contract, validation boundary, RRF fusion, deterministic ranking, and generated/online parity.

The existing exact vector path remains the portable reference implementation. It is an example backend and correctness oracle, not a claim that `ScoreVectors` is an industrial-scale ANN implementation.

## Decision Log

- Decision: Treat vector availability as the normal operating assumption, while retaining lexical-only mode as a compatibility and diagnostic path.
  Rationale: The showcase should teach hybrid retrieval first, but existing lexical behavior remains valuable as a baseline and should not require fake vector identity.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: Make the stable swap-in boundary a typed vector-candidate relation, not a Structure-internal HNSW class hierarchy.
  Rationale: A caller or plugin can build and query HNSW, a different ANN service, or an exact scan independently, then supply the same directed ranked candidates to Structure. This avoids adding a backend dependency, driver-side collection, or provider-specific execution model to the Search example.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: Keep the exact vector implementation as the reference backend and correctness oracle.
  Rationale: It is deterministic, dependency-free, and useful for testing alternate providers, but its full cross join must be documented as a bounded example implementation rather than an index-performance claim.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: Separate fusion policy from vector-index policy.
  Rationale: RRF limits and experiment identity govern hybrid ranking, while model, dimension, content revision, and backend identity govern vector compatibility. Combining them forces lexical-only callers to invent vector metadata and couples future backends to the exact implementation.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: Publish hybrid ranking evidence rather than projecting it into the legacy lexical result shape.
  Rationale: The example’s purpose is to showcase transparent Structure transformations. A user must be able to see whether a result was lexical-only, vector-only, or present in both lanes and how RRF ranked it.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: Use RRF as the first fusion rule and do not blend raw BM25 and cosine values.
  Rationale: The two scores have different meanings and scales. RRF combines their ranks while preserving both component scores for inspection.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: Implement document and paragraph hybrid retrieval first; leave section and sentence vector retrieval explicitly deferred.
  Rationale: Documents are the main similarity presentation and paragraphs are the existing passage grain. The smaller scope keeps the provider contract and evaluation tractable.
  Date/Author: 2026-08-10 / User and Codex.

## Context and Orientation

Structure is a typed transformation compiler. Schemas under `examples/search/schemas/` describe DataFrame relations, while transforms under `examples/search/transforms/` declare inputs, intermediate lanes, and outputs. The same transform source is executed online and rendered into generated PySpark, so ordinary logic must remain compiler-visible and must have parity evidence.

The lexical index is built by `examples/search/transforms/indexing/lexical/LexIndex.py`. `CreateSimilarityQueries.py` creates a synthetic query from each target’s normalized vocabulary, and `ReduceSimilarityScores.py` scores same-grain targets, creates reciprocal canonical pairs, and retains up to ten neighbors per source. This lexical path remains the baseline and is not replaced by a hidden vector implementation.

The exact vector path is split into `examples/search/transforms/indexing/vector/VectorIndex.py`, `examples/search/transforms/scoring/vector/ScoreVectors.py`, and `examples/search/transforms/ranking/vector/RankVectors.py`. It validates caller-produced embeddings, computes exact cosine similarity through a DataFrame cross join, ranks deterministically, and emits `DocumentVectorCandidate` and `ParagraphVectorCandidate` relations.

The current document and paragraph hybrid paths are under `examples/search/transforms/searching/search_similarity/`. Adoption transforms normalize lexical and vector candidates, `fusion.py` unions and groups candidates by complete pair identity, and `rerank.py` joins metadata and publishes final results through grain-specific presenters.

RRF, or Reciprocal Rank Fusion, gives a candidate one contribution per retrieval lane: `1 / (rrf_k + rank)`. A candidate present in both lanes receives both contributions; a candidate present in one lane remains eligible with one contribution. RRF is rank-based and does not claim that BM25 and cosine are numerically comparable.

The current worktree contains user-owned staged changes. Every implementation step must begin with `git status --short`, preserve unrelated changes, and review generated diffs before staging or committing anything.

## Plan of Work

### Milestone 1: Establish provider-neutral contracts

Add a `SimilarityFusionPolicy` schema under `examples/search/schemas/` with the RRF constant, independent lexical and vector candidate limits, final result limit, and experiment/run identity. Validate exactly one policy row and positive limits. Remove the need for `SearchSimilarity` to receive `VectorIndexPolicy` merely to fuse candidates. An empty vector-candidate relation remains legal for the lexical regression path, but it must not contain fabricated model or index identity.

Extend the vector candidate schemas with the provenance needed to validate and explain provider substitution: backend identifier, model identity, vector dimension, content revision, experiment identity, source identity, target identity, cosine similarity, and deterministic rank. Use the same contract for exact candidates and caller- or plugin-produced ANN candidates. The backend identifier should distinguish at least `exact_reference` from an external provider such as `hnsw`; it is descriptive provenance, not a dispatch instruction.

Add a validation transform or typed validation steps that reject duplicate source/target rows within a lane, incompatible vector identity, invalid ranks, invalid dimensions, non-finite or zero-norm vectors where vectors are present, and cross-grain candidate keys. Diagnostics must name the relation, source, target, and remedy.

### Milestone 2: Preserve evidence through fusion and presentation

Refactor `examples/search/transforms/searching/search_similarity/fusion.py` so grouping is preceded by a uniqueness contract. It must not silently use `max(...)` to merge multiple rows that should have been one candidate. For a valid pair, preserve the lexical rank, vector rank, BM25, overlap, vector similarity, RRF constant, RRF score, backend identity, and snapshot identity.

Add a hybrid document result schema alongside the legacy lexical result schema. The hybrid result must extend document metadata with source identity, final rank, final RRF score, lexical rank, vector rank, lexical evidence, vector similarity, backend identity, and experiment identity. `RerankSimilarity` must publish this schema instead of dropping hybrid evidence into `IndexedSimilarDocument`.

Keep the legacy lexical presentation behavior available through the lexical path. The new hybrid presentation should have a stable, explicit name and should rank by RRF, then vector similarity, then lexical evidence, then target ID. The final output limit must come from `SimilarityFusionPolicy`, not a hard-coded reducer constant.

### Milestone 3: Harden the exact reference backend and define the ANN swap point

Keep `VectorIndex`, `ScoreVectors`, and `RankVectors` as the exact reference path, but rename documentation and public descriptions so “index” means a validated exact artifact in this example. Add duplicate target-ID validation to `VectorIndex`; a vector index must not count or return multiple embeddings for the same target.

Define the caller integration contract in the Search documentation and tests: an HNSW or other ANN implementation may live outside Structure or in a plugin, may own its graph, persistence, refresh, filtering, and query execution, and must emit the provider-neutral vector-candidate schema. Structure consumes those candidates through the same adoption, fusion, and presentation transforms used by exact retrieval.

Add an alternate-provider test producer using hand-authored candidate rows. It must prove that a candidate relation marked as an alternate backend produces the same fused result shape and ranking semantics as the exact producer. This is a contract test, not an HNSW implementation; no ANN dependency is added in this plan.

Add explicit candidate-limit semantics. The lexical lane and vector lane each receive their own candidate window before fusion, while the final fused limit is applied after RRF. The current lexical fixed-ten behavior must either become the default policy value or be removed from the reducer API; it must not remain an undocumented hidden limit.

### Milestone 4: Complete document and paragraph hybrid surfaces

Update `SearchSimilarity` to consume `SimilarityFusionPolicy` and provider-neutral document candidates. Keep document similarity as the first end-to-end showcase: exact vector candidates are the default example producer, while alternate candidates are accepted without changing the downstream graph.

Add a public paragraph hybrid presenter that composes `AdoptLexicalParagraphs`, `AdoptVectorParagraphs`, `FuseSimilarityParagraphs`, and a paragraph-specific metadata/ranking boundary. It must preserve document, section, and paragraph identity and must not mix paragraph candidates with document candidates.

Define eligibility behavior. Candidate filters that affect correctness, tenancy, access control, or collection scope must be applied by the candidate producer before its per-source limit. The Search transforms may accept a typed eligibility relation where the existing pipeline can apply it before ranking, but they must not advertise post-publication filtering as equivalent to filtered retrieval.

Keep sections and sentences lexical-only in this plan and state that boundary in schemas, documentation, and tests.

### Milestone 5: Add quality, scale, and documentation evidence

Add focused tests for lexical-only, vector-only, hybrid overlap, semantic-only candidates, missing lane contributions, deterministic ties, duplicate rows, self-exclusion, model/revision mismatch, backend provenance, per-lane limits, final limits, and paragraph isolation.

Add similarity judgments or a small deterministic relevance fixture. Report precision at k, recall at k, and nDCG at k for lexical-only, exact-vector-only, and hybrid runs. Do not use clicks as a substitute for judged similarity quality.

Add an exact-backend scaling fixture that records candidate-row growth and runtime for increasing corpus sizes. Treat the results as a documented boundary for the example, not as a performance promise. A later ANN plan may compare HNSW or another backend against exact retrieval using recall-at-k, latency, candidate budget, filter behavior, refresh behavior, and restart behavior.

Update `docs/dev/design/Search.design.md`, `docs/background/Search.back.md`, `examples/search/Readme.md`, `docs/examples/search/searching/SearchSimilarity.back.md`, and the vector-index plan so they consistently describe the exact reference backend, caller-owned ANN boundary, hybrid evidence output, and supported grains. Do not claim that Structure builds or operates a production HNSW service.

Regenerate checked-in Search artifacts through the repository generation workflow. Update user-story coverage and annotated source where required. Keep unrelated worktree changes out of the generated diff.

## Validation and Acceptance

The policy milestone is accepted when lexical-only execution can use an empty vector-candidate relation without a fake vector-index policy, while normal hybrid execution accepts one fusion policy and provider-neutral vector candidates.

The provider milestone is accepted when exact candidates and hand-authored alternate-backend candidates can be substituted at the same relation boundary and produce identical schemas, RRF calculations, deterministic ranks, and explainable lane evidence.

The fusion milestone is accepted when lexical-only, vector-only, and hybrid candidates all survive correctly; candidates found in both lanes receive both RRF contributions; duplicate lane rows fail with an actionable diagnostic; and the public hybrid result exposes the evidence that caused its rank.

The presentation milestone is accepted when document and paragraph hybrid paths are end-to-end, grain-isolated, bounded by explicit per-lane and final limits, and capable of returning a vector-only semantic match.

The quality milestone is accepted when judged metrics compare lexical, exact-vector, and hybrid results, and when documentation clearly labels exact retrieval as the example/reference backend and ANN retrieval as a caller- or plugin-owned replacement.

Generated PySpark and online execution must agree on rows, schemas, ranks, and diagnostics for all focused fixtures. `make build` must pass apart from documented environment-gated skips.

## Interfaces and Dependencies

`SimilarityFusionPolicy` is a one-row typed relation containing positive `rrf_k`, lexical candidate limit, vector candidate limit, final result limit, and experiment identity. It is consumed by fusion and presentation; it does not identify a vector model or backend.

`DocumentVectorCandidate` and `ParagraphVectorCandidate` are the provider-neutral vector retrieval outputs. Each row contains query/source identity, target identity, cosine similarity, deterministic one-based rank, model identity, dimension, content revision, experiment identity, and vector backend identity. The exact scorer and any caller/plugin ANN producer must emit these schemas.

`DocumentFusedSimilarityCandidate` and `ParagraphFusedSimilarityCandidate` are internal fusion rows retaining both lane ranks, both lane scores, RRF metadata, and compatible snapshot/backend identity. Fusion must group only by complete same-grain source/target identity and must reject duplicate lane evidence rather than selecting an arbitrary aggregate.

The public hybrid document and paragraph result schemas retain source identity, target metadata, final rank, RRF score, lane ranks, component scores, backend identity, and experiment identity. The existing lexical-only schemas remain available for compatibility.

No HNSW or other ANN runtime dependency is introduced by this plan. A future provider may be implemented by a caller, plugin, or external service and must satisfy the candidate relation and evidence contract before being accepted as a backend.
