# Move Compiled Artifact Caching to Sessions

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can move compiled-artifact
ownership from transform classes to sessions, add safe artifact sharing and load support, and preserve online and
generated execution parity without needing prior conversation history.

## Purpose / Big Picture

Structure currently caches compiled artifacts in a dictionary owned by every `Transform` subclass. It gives the desired
lazy-once behavior, but it makes artifact lifetime process-global, hides memory use on loaded transform classes, and
makes it awkward to share a deliberate set of already-compiled artifacts among sessions. It also leaves generated code
as a separately imported product rather than a rendering whose identity can be checked against the in-memory plan.

After this work, callers may still compile explicitly or simply run a fresh transform invocation. A session compiles a
transform the first time it needs it, retains the result for the session lifetime, and reuses it for later invocations
with compatible configuration. Applications may pass the same artifact pool to several sessions, bulk-load validated
artifacts at startup, or clear a session pool without mutating transform classes. Generated code is rendered from a
compiled artifact and carries that artifact's semantic fingerprint; generated mode rejects a stale or unrelated module.

The normal user experience remains concise:

    session = StructureSession(spark=spark)
    result = EnrichOrders(orders=orders_df, customers=customers_df).run(session)

The first call compiles and stores the artifact in `session`; later invocations of `EnrichOrders` reuse it. Applications
that want an eager startup failure can use either of these equivalent forms:

    artifact = EnrichOrders.compile(config=session.config)
    session.load(artifact)

    session.compile(EnrichOrders)

`Transform.compile(...)` remains a supported explicit factory. It does not retain a process-global cache entry. The
session or an application-supplied pool owns any retained result.

## Surprises & Discoveries

- Observation: `Transform.compile(...)` already builds a `CompiledTransform` containing checked backend-neutral IR,
  a lowered PySpark execution plan, and materialized schemas. It never stores invocation DataFrames in that object.
  Evidence: `src/structure/app/compiler/artifacts/model/CompiledTransform.py` and the DataFrame-isolation test in
  `tests/specifications/online-execution/test_v1_structure_session.py`.

- Observation: the current cache is class-static, one dictionary and lock per `Transform` subclass, while transform
  pipelines use a second static cache on `TransformPipeline`.
  Evidence: `src/structure/app/dsl/model/transforms/Transform.py` initializes `_structure_compiled` in
  `__init_subclass__`; `src/structure/app/dsl/model/transforms/TransformPipeline.py` declares another static cache.

- Observation: the generated runner compiles the current source to obtain a plan, then imports generated Python by
  module and class name. It does not yet verify that the imported generated class was rendered from that plan.
  Evidence: `src/structure/app/runtime/session/model/StructureSession.py` calls `_compiled(...)` before delegating to
  `RunGeneratedPySparkTransform`, whose module import currently has no semantic-fingerprint check.

- Observation: source hashes currently cover only each root transform class's defining source file. An inherited
  transform, hook, schema, or helper in a different file can change without changing that root-file hash.
  Evidence: `BuildCompiledTransform._classes(...)` returns the root class or pipeline stage classes, and
  `BuildCompiledTransform._source(...)` fingerprints only those classes.

- Observation: the completed plan `docs/dev/planning/P07082603.Compiled-transform-artifacts.plan.md` intentionally
  selected class-static caching. This plan supersedes that ownership decision only; it retains explicit `compile()`,
  lazy-once execution, immutable data-only artifacts, source-unit generation, and memory storage.
  Evidence: the earlier plan's decision log and the resulting implementations listed above.

- Observation: current plan records include source class objects, owner references, arbitrary schema materializations,
  and mapping-proxy-backed result schemas. They cannot yet be persisted safely as a generic JSON artifact without a
  deliberate reversible codec.
  Evidence: `TransformMemberOrigin.owner` is a source class object and `TransformSchemas` accepts materialized runtime
  schema values. The persistent-cache milestone remains gated on a round-trip spike rather than adding pickle.

## Decision Log

- Decision: Preserve both explicit and implicit compilation.
  Rationale: Explicit compilation is valuable for application startup, CI, review, and early diagnostics. Lazy
  compilation is the established convenient form for scripts and notebooks. Removing either would not improve semantic
  correctness; both must obtain the same artifact through the same cache key and builder.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: `StructureSession` owns its default retained artifact pool; transform classes own none.
  Rationale: A session has a clear application-controlled lifetime and already owns resolved execution configuration.
  Transform classes often survive for the whole Python process, so class-static dictionaries can retain artifacts for
  unrelated projects, profiles, and dynamically created classes indefinitely.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: permit intentional cross-session reuse through an explicit `CompiledArtifactPool`, not another hidden
  global cache.
  Rationale: A process may use several sessions with compatible target configuration. Supplying one shared pool makes
  lifetime and sharing visible, while independent sessions stay isolated by default.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: `Transform.compile(...)` remains a standalone explicit artifact factory. `session.compile(Transform)` and
  `session.load(artifact)` are the retained-cache APIs.
  Rationale: A no-session compile must not secretly create a process-global cache. The two session APIs make eager
  compilation concise while preserving the familiar class-level `compile()` spelling for tooling and build code.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: artifact validity is based on a deterministic dependency manifest and content fingerprints, never on
  timestamps alone.
  Rationale: Timestamps can accelerate a probe but are not a correctness boundary. The manifest must cover the root
  transform, effective parent classes, selected hooks and helpers, referenced schemas, pipeline stages, compiler
  options, Structure version, and resolved target capabilities.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: serialized compiled artifacts use a versioned, canonical data format and never Python pickle.
  Rationale: Pickle would execute untrusted data, bind cache compatibility to implementation objects, and hide the
  source-owner resolution needed for hooks. A codec must serialize data-only plans and re-resolve owner classes only
  after validating the manifest.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: generated Python is a rendering of a compiled artifact, not a second semantic authority.
  Rationale: The generator may choose imports, formatting, and file paths, but not transform semantics. Per-transform
  generated metadata must carry the semantic fingerprint of the exact lowered plan it rendered, and generated execution
  must fail closed on mismatch.
  Date/Author: 2026-07-09 / project owner and Codex.

- Decision: name artifact admission `load(...)` and `load_many(...)`, not `preload(...)`.
  Rationale: An artifact is immediately usable once admitted to a pool. `load` matches ordinary cache and storage
  vocabulary without implying a special ahead-of-time-only behavior.
  Date/Author: 2026-07-09 / project owner and Codex.

## Context and Orientation

A transform is a Python class inheriting from `Transform`. Its class declares inputs, lanes, outputs, and
schema-returning step methods. An invocation is a fresh instance such as `EnrichOrders(orders=orders_df)`. It
holds only that call's live input DataFrames. A `StructureSession` holds a caller-supplied Spark session, runtime
context, resolved configuration, and execution-mode choice.

Compilation executes supported step methods with symbolic row objects, creates a backend-neutral
`TransformPlan`, checks it, lowers it into a `PySparkExecutionPlan`, and materializes output schemas. The resulting
`CompiledTransform` is an in-memory data artifact. It must never contain a live DataFrame, a Spark session, a runtime
context, a hook return value, or a generated module object.

An artifact pool is a thread-safe mapping from a compilation identity to a `CompiledTransform`. A session's default
pool is private to that session. An application may construct a pool and pass it to several sessions to make sharing
explicit. A pool is reusable only when its compilation identity matches; it must not share artifacts across different
backend, profile, validation, or schema-materialization settings.

A dependency manifest is an ordered, deterministic description of every compiler-visible source dependency that can
alter an artifact. Every entry includes a stable kind, qualified identity, project-relative source path when present,
and content digest. The manifest additionally includes the Structure version, compiler-options fingerprint, and target
capability fingerprint. An artifact is fresh only if a newly computed manifest is equal to its recorded manifest.

A semantic fingerprint is a digest of the checked artifact's canonical semantic data: its dependency manifest,
backend-neutral plan, target plan, and artifact-format version. It deliberately excludes DataFrames, Spark object
identity, filesystem timestamps, generated text layout, and absolute paths. It identifies the exact behavior that
online and generated consumers must share.

The relevant current implementation is organized as follows:

- `src/structure/app/dsl/model/transforms/Transform.py` binds invocation inputs and provides class-static
  `compile(...)`, `generate(...)`, and `run(session)` behavior.
- `src/structure/app/dsl/model/transforms/TransformPipeline.py` represents a sequence of invocations and has a second
  static compilation cache.
- `src/structure/app/compiler/artifacts/commands/BuildCompiledTransform.py` resolves capabilities, invokes the
  symbolic compiler frontend, lowers the target plan, materializes schemas, and builds a current `CompileKey`.
- `src/structure/app/compiler/artifacts/model/CompiledTransform.py` and `CompileKey.py` define the existing immutable
  artifact and its cache identity.
- `src/structure/app/runtime/session/model/StructureSession.py` currently calls `type(invocation).compile(...)` or
  `pipeline.compile(...)` on every execution request and then chooses online or generated execution.
- `src/structure/app/runtime/execution/online/commands/RunOnlinePySparkTransform.py` interprets the artifact's
  `PySparkExecutionPlan` with live DataFrames.
- `src/structure/app/runtime/execution/generated/commands/RunGeneratedPySparkTransform.py` imports a generated module
  and calls its generated class.
- `src/structure/app/target/pyspark/commands/RenderPySparkProject.py` and
  `RenderPySparkTransformModule.py` render generated Python from PySpark plans.
- `src/structure/app/target/pyspark/storage/MemoryStorage.py` already proves that generated source can be kept and
  imported without disk files.

`docs/dev/specifications/ExecutionSemanticContract.md` requires one shared target plan for online and generated
execution. `docs/dev/specifications/CompilerPerformanceTargets.md` requires deterministic fingerprints and cache
entries that are safe to delete. `docs/dev/planning/P07092601.V4-incremental-compile-cache-diagnostics.plan.md` owns
the later command-line `compile --changed-only` feature; it must reuse, rather than replace, the manifest and codec
introduced here.

### Milestone 1: Define artifact identity and a session-owned in-memory pool

Create data-only models under `src/structure/app/compiler/artifacts/model/` for `ArtifactDependency`,
`ArtifactManifest`, and `ArtifactFingerprint`, or use shorter names that preserve those responsibilities. Add a
compiler command such as `BuildArtifactManifest` that receives a transform class or pipeline plus resolved
`CompilerOptions` and reports the effective compiler-visible dependency closure before a cache lookup. It must walk
the effective transform inheritance graph in the same parent-first order used by the compiler, retain each class once
for diamonds, include pipeline stages in stage order, and include schemas and class-owned special functions and hooks.
It may conservatively fingerprint an entire defining module when a member-level analysis would miss a dependency.

Extend `CompiledTransform` to store its manifest and semantic fingerprint. Keep `TransformPlan`,
`PySparkExecutionPlan`, and schemas as the canonical in-memory semantic content. Do not make the immutable artifact
hold a `StructureSession`, DataFrame, `SparkSession`, or generated source text.

Add a focused `CompiledArtifactPool` component, preferably in `src/structure/app/compiler/artifacts/` or a runtime
session subpackage after checking local package conventions. Its API must be narrow:

    artifact = pool.get_or_compile(subject, options, build)
    pool.load(artifact)
    pool.invalidate(identity)
    pool.clear()
    report = pool.status()

`get_or_compile(...)` uses the current manifest to reject stale entries, performs one build for concurrent identical
misses, and publishes only a fully built artifact. Do not hold the global pool lock while compiling unrelated subjects.
Use an identity based on root transform or ordered pipeline stages plus compiler options to find a candidate, then use
the full manifest to prove freshness. Failed compilation must not poison a slot. The default pool retains artifacts for
its owning session lifetime; expose `clear_compiled()` and an optional entry limit for applications that need a bounded
long-lived pool.

Update `StructureSession.__init__(...)` to accept `artifacts: CompiledArtifactPool | None`. When omitted, construct a
private pool. Add `StructureSession.compile(transform_or_pipeline)`, `load(artifact)`, `clear_compiled()`, and a
read-only cache status method. `run(...)` obtains an artifact through the pool, compiles lazily on a miss, and preserves
the current per-invocation input validation and runner behavior. A session must not stop or reconfigure Spark when its
artifact pool is cleared.

Remove `_structure_compiled` and `_structure_compile_lock` from `Transform` subclasses and the corresponding static
state from `TransformPipeline`. Keep `Transform.compile(...)` as an explicit, uncached artifact factory. Its exact
builder, keys, diagnostics, and output must match `session.compile(...)`; factor the common call through
`BuildCompiledTransform` rather than maintaining two compilation paths.

Add tests in `tests/specifications/online-execution/` and a new matching artifact-cache specification directory that
prove all of these observable behaviors:

- Two fresh invocations of one transform reuse one artifact in one session.
- A second independent session compiles independently by default.
- Two sessions given the same `CompiledArtifactPool` compile once and reuse the same artifact.
- `EnrichOrders.compile(...)` returns a usable artifact but does not retain a global class cache.
- `session.load(artifact)` permits the first matching run to avoid compilation.
- Clearing one session's private pool does not affect another session or the transform class.
- Different target profiles, validation options, or schema-type materializers never reuse an incompatible artifact.
- A failed build leaves no cache entry and a following call retries cleanly.
- A compiled artifact's representation contains no bound-input sentinel, Spark session, or runtime context.

### Milestone 2: Make dependency invalidation complete and explainable

Implement manifest collection before cache reuse. For every root transform, include its own source module, each
effective parent transform module, the exact owner module of every scheduled step and hook, input/lane/output schema

### Milestone 3: Prove and add safe persistent artifact bundles

Before committing a persistent cache format, add a small serialization spike. Build representative artifacts covering
projection, filters, joins, multiple outputs, schema validation, inherited steps, owner-qualified hooks, and a
pipeline. Serialize only data records, deserialize them in a clean Python process, re-resolve source owners by module,

If every required plan shape can round-trip as canonical JSON without loss, add a versioned `CompiledArtifactStorage`
interface with a disk implementation. Its bundle contains a manifest, semantic fingerprint, artifact-format version,
canonical plan data, schema data, and a short diagnostic/report record. It does not store Python class objects,
callables, DataFrames, generated module objects, secrets, or pickled payloads. All writes use a temporary sibling path
followed by atomic replacement. A corrupt bundle is never partially loaded.

If the spike finds a model that cannot round-trip safely, do not use pickle or a partial cache. Record the limitation in

## Validation and Acceptance

The change is complete only when users can observe all of these behaviors:

- Calling `EnrichOrders(...).run(session)` compiles once on the first compatible use and reuses the same artifact for
  later fresh invocations in that session.
- `EnrichOrders.compile(...)` still catches source/compiler errors early without a Spark session. Loading its return
  value into a session prevents another compile.
- Independent sessions do not retain one another's artifacts. Sessions given the same explicit pool reuse compatible
  artifacts and remain safe under concurrent first use.
- Editing a parent transform, a selected parent hook, a referenced schema, a helper owner, a pipeline stage, or a
  relevant option invalidates the dependent artifact. Editing an unrelated module does not.
- Clearing or deleting a cache never changes transform results; it only causes a safe recompilation.
- Valid persistent bundles can be bulk-loaded. Stale, corrupt, unknown-version, or missing-owner bundles are not
  executed and do not prevent fallback compilation.
- A generated module rendered from the current artifact runs with the same observable output semantics as online mode.
  A stale generated module fails with an actionable regeneration-or-online diagnostic.
- Compilation, artifact serialization, and load remain Spark-free. Runtime artifact changes introduce no UDF, RDD,
  collection, or row-wise behavior into compiled plans.
- `make build` passes, and all updated generated fixtures are deterministic.

## Idempotence and Recovery

Session compilation, explicit load, bulk load, generation, and cache clear are safe to repeat. Repeating a
matching load replaces no valid artifact and reports a cache hit. Repeating a compile after a source change builds
one new artifact and never mutates an artifact already executing in another thread.

If a disk bundle is corrupt, delete that bundle or the entire derived artifact directory; the next run recompiles.
If generated code reports a semantic-fingerprint mismatch, regenerate it from the same resolved configuration or use
online execution. Do not edit generated metadata or bypass validation. If serialization cannot preserve a new plan
shape, disable persistent load for that shape and retain correct in-memory lazy compilation until its codec support
is added.

## Artifacts and Notes

The intended runtime ownership and sharing graph is:

    Transform class -- explicit compile --> CompiledTransform
                                           |
                                           +--> session.load(...)
                                           |
    fresh invocation -- session.run --> session private pool -- online interpreter
                                           |
    several sessions -----------------> shared CompiledArtifactPool
                                           |
    validated disk bundles -----------> session.load_many(...)
                                           |
                                           +--> generated renderer --> generated module with fingerprint

The generated module is an output of the `CompiledTransform`; it is never an independent semantic input. An imported
generated module must prove that it was rendered from the same artifact semantic fingerprint before it executes.

The following API names are required at the end of this work; package placement may follow existing local conventions:

    CompiledArtifactPool.get_or_compile(subject, options, build) -> CompiledTransform
    CompiledArtifactPool.load(artifact) -> None
    CompiledArtifactPool.invalidate(identity) -> None
    CompiledArtifactPool.clear() -> None
    CompiledArtifactPool.status() -> ArtifactCacheReport

    Transform.compile(options=None, *, project_root=None, config=None, force=False) -> CompiledTransform

    StructureSession.compile(transform_or_pipeline) -> CompiledTransform
    StructureSession.load(artifact) -> None
    StructureSession.load_many(artifacts) -> ArtifactCacheReport
    StructureSession.clear_compiled() -> None
    StructureSession.cache_status() -> ArtifactCacheReport

`ArtifactCacheReport` is a data-only result that reports counts and deterministic per-artifact reasons. It must not
contain DataFrames, raw source text, Spark sessions, or unbounded exception traces. `CompiledArtifactStorage` is an
optional persistence interface that stores only canonical data bundles and validates them before hydration.

## Interfaces and Dependencies

No third-party dependency is required. Use the existing compiler frontend, IR models, PySpark lowering, schema
materializer, configuration resolver, generated-code renderer, and storage interfaces. The persistent codec may use
the Python standard library JSON and hashing facilities after proving that canonical serialization is sufficient.

The plan must not introduce a dependency from Spark-free compilation to PySpark, Java, a Spark cluster, or generated
module import. It must not use pickle. It must not add a hidden process-global artifact cache. It must preserve the
existing distinction between online mode, which interprets recipes with live DataFrames, and generated mode, which
imports generated code after fingerprint validation.

`P07092601.V4-incremental-compile-cache-diagnostics.plan.md` remains the owner of CLI incremental compilation. Its
future disk cache should consume these artifact manifests and codecs, but a session must work correctly with no disk
cache at all.
