# Schema Composition for Nested Structure Fields

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/dev/auto/Plans.md`. It is self-contained so a contributor can implement nested schema
composition from this file and the current working tree.

## Purpose / Big Picture

Structure already lets users declare nested Spark struct columns with `field(Struct(Address))`, and generated/runtime
schema materialization already handles those nested shapes. What remains incomplete is using nested Structure-derived
classes as ordinary typed values inside compiled transforms: constructing nested struct values, copying them between
schemas, validating nested assignment compatibility, and rendering generated PySpark that Spark can optimize.

After this plan is complete, a user can model reusable value objects such as tenant keys, audit stamps, addresses,
money parts, and source metadata as small `Structure` classes, then place those classes inside larger row schemas as
fields. The observable result is that a transform can read `order.shipping.city`, construct `Address(...)`, assign it
to `shipping=...`, generate `F.struct(...)` rather than opaque Python literals, and validate the nested Spark shape in
online and generated execution.

## Surprises & Discoveries

- Observation: `Struct(SchemaClass)` is already part of the public type model and is exported from `structure`.
  Evidence: `src/structure/__init__.py` exports `Struct`, and `docs/reference/SchemaDeclarationSyntax.md` documents
  `Struct(schema)` for nested schemas.

- Observation: Fixtures already use nested Structure fields in realistic row schemas.
  Evidence: `res/testing/model/v1/orders/schemas/order.py` declares fields such as `tenant = field(Struct(TenantKey),
  nullable=False)` and `shipping = field(Struct(Address), nullable=True)`.

- Observation: Generated and online schema materialization already support nested Spark `StructType` values.
  Evidence: `RenderPySparkSchema.type(...)` returns the nested schema constant for `StructType`, and
  `MaterializePySparkSchema.type(...)` recursively materializes `type.schema`.

- Observation: Symbolic nested reads are partially supported.
  Evidence: `Expression.__getattr__(...)` handles `StructType` expressions by appending nested field columns to a path
  and returning another `Expression(kind="field", ...)`.

- Observation: Nested struct construction is not compiler-visible today.
  Evidence: `CompileTransform._project_assignments(...)` wraps assigned values with `literal(...)`; a nested
  `Address(...)` instance would therefore become a Python literal instead of an expression that can lower to
  `F.struct(...)`.

- Observation: Current field rendering joins nested path segments into a dotted string.
  Evidence: `RenderPySparkExpression._field(...)` renders `F.col("<scope>.<field>")`, while nested access stores field
  paths such as `shipping.city`. This is fragile when any segment has an alias containing a dot, space, or other
  character that Spark treats specially.

- Observation: Struct type compatibility previously allowed any two struct schemas with the same broad `struct` type
  name.
  Evidence: The new negative test assigning `Address(...)` to `Struct(TenantKey)` did not fail until `_same_type(...)`
  was made schema-identity aware for `StructType`.

- Observation: The active worktree had in-progress expression-helper API changes that temporarily removed a fixture
  import target.
  Evidence: `make build` failed on fixture imports until the helper export was restored.

## Decision Log

- Decision: Treat schema composition as nominal nested struct containment.
  Rationale: A `Structure` class is a named row contract. `Struct(Address)` and `Struct(BillingAddress)` should remain
  distinct even if their current fields are identical, because schema names carry domain meaning and diagnostics should
  preserve that meaning.
  Date/Author: 2026-07-08 / Codex.

- Decision: Keep schema composition distinct from inheritance.
  Rationale: Inheritance reuses fields as top-level columns. Composition creates one nested Spark column with its own
  field boundary. Mixing those concepts would make generated projections, validation, and user expectations harder to
  reason about.
  Date/Author: 2026-07-08 / Codex.

- Decision: Use existing `NestedSchema(...)` constructor syntax for nested struct values inside output projections.
  Rationale: Schema constructors already represent compiler-visible output records. Allowing `Address(...)` as the
  value assigned to `shipping` is the least surprising spelling and avoids a second public constructor helper for the
  same concept.
  Date/Author: 2026-07-08 / Codex.

- Decision: Lower nested schema construction to Spark `F.struct(...)`, not Python literals or UDFs.
  Rationale: Structure's core promise is optimizer-visible PySpark. `F.struct(...)` preserves Spark planning,
  generated-code readability, online/generated parity, and nested shape validation.
  Date/Author: 2026-07-08 / Codex.

- Decision: Parent nullability makes nested field reads nullable.
  Rationale: If `shipping` can be null, then `shipping.city` can evaluate to null even when `Address.city` is declared
  non-nullable. This matches Spark behavior and the existing conservative nullability rule in `Expression.__getattr__`.
  Date/Author: 2026-07-08 / Codex.

- Decision: Do not add partial nested updates in this slice.
  Rationale: Syntax such as `shipping.city = ...` or implicit deep merge would add a second assignment model and create
  difficult overwrite/nullability questions. This plan supports constructing or copying whole nested struct values.
  Partial nested updates are tracked as a planned follow-up in `docs/dev/project-management/Backlog.md`.
  Date/Author: 2026-07-08 / Codex.

## Context and Orientation

Structure is a Python DSL and compiler for Spark DataFrame transformations. A schema class is any class inheriting from
`Structure`; it declares fields with `field(type_, ...)`. A field type is a Structure type object such as `String()`,
`Decimal(12, 2)`, `Array(String())`, or `Struct(Address)`. In this plan, "schema composition" means using a
Structure-derived class as the type of a field in another Structure-derived class:

    class Address(Structure):
        city = field(String(), nullable=False)
        postal_code = field(String(), nullable=False)

    class Order(Structure):
        id = field(String(), nullable=False)
        shipping = field(Struct(Address), nullable=True)

Here `shipping` is one Spark column whose data type is a nested `StructType`. It is not two top-level fields named
`city` and `postal_code`. This is different from schema inheritance, where fields from a base schema become top-level
fields on a child schema.

The main files and modules involved are:

- `src/structure/app/dsl/model/types/Struct.py` and `StructType.py`, which define the public nested schema type.
- `src/structure/app/dsl/model/schemas/Structure.py`, which captures schema fields and stores constructor values.
- `src/structure/app/dsl/model/expr/Expression.py` and `RowScope.py`, which create symbolic field references.
- `src/structure/app/compiler/frontend/commands/CompileTransform.py`, which turns returned schema instances into
  projection assignments and validates type/nullability compatibility.
- `src/structure/app/compiler/ir/model/ProjectAssignment.py`, which stores target fields and source expressions.
- `src/structure/app/target/pyspark/commands/RenderPySparkExpression.py`, which renders expression recipes to PySpark.
- `src/structure/app/target/pyspark/commands/RenderPySparkSchema.py` and `MaterializePySparkSchema.py`, which already
  render and materialize nested `StructType` schemas.
- `src/structure/app/tools/logic/maps/MapPySparkSchemaToStructureSource.py`, which generates Structure schema source
  from a PySpark schema and already creates nested Structure classes for nested structs.

The current working tree already supports declaring nested schemas and using nested field references in simple cases.
The missing piece is treating a nested schema constructor as an expression. For example, a transform should be able to
return this:

    return OrderNormalized(
        id=order.id,
        shipping=Address(
            city=trim(order.shipping.city),
            postal_code=order.shipping.postal_code,
        ),
    )

The compiler should turn the `Address(...)` value into a nested struct expression. Generated PySpark should look like:

    F.struct(
        F.trim(F.col("order_raw.shipping.city")).alias("city"),
        F.col("order_raw.shipping.postal_code").alias("postal_code"),
    ).alias("shipping")

The exact scope alias may differ, but the generated expression must be Spark-plan-visible and must preserve the nested
schema field order.

## Plan of Work

Milestone 1 creates executable coverage for the intended behavior. Add focused tests before implementation so the
failure mode is visible. Cover declaration and schema generation already supported by `Struct(Address)`, then add tests
that currently fail for nested construction in a transform. Include a transform that copies a whole nested field from
input to output, a transform that constructs a nested field from nested reads, and a transform that fails when an
`Address(...)` value is assigned to a field typed as `Struct(TenantKey)`. Add tests for parent-nullable nested reads:
`shipping.city` must be nullable when `shipping` is nullable. Add generated PySpark rendering tests that assert
`F.struct(...).alias("shipping")` appears instead of `F.lit(...)`.

Milestone 2 introduces a compiler-visible nested struct expression. Add a new `Expression` kind such as
`"struct"` or `"schema"` to represent a nested Structure constructor. The expression should carry the nested schema
class and ordered field assignments. Update `CompileTransform._project_assignments(...)` so when a constructor value is
a `Structure` instance and the target field is a `StructType`, the compiler converts that value into the new expression
instead of calling `literal(...)`. The conversion must recurse so nested structs inside nested structs work. It must
require every nested schema field to be assigned, reject unknown fields through the existing `Structure.__init__`
behavior, and preserve target nested field order.

Milestone 3 validates nested assignment compatibility. Extend the existing assignment validation in
`CompileTransform._assignment(...)`, `_assignable(...)`, and `_same_type(...)` only as needed to make the new nested
struct expression precise. Assigning a field reference of type `Struct(Address)` to a target field of type
`Struct(Address)` should pass. Assigning a constructed `Address(...)` expression to `Struct(Address)` should pass.
Assigning `Struct(Address)` to `Struct(TenantKey)` should fail with a diagnostic naming the target field, expected
schema, and actual schema. Nullability should follow the existing rule: a nullable expression cannot feed a
non-nullable field unless narrowed or repaired. Nested constructor nullability should be true when any nested assignment
is nullable only if Spark would make the struct itself null; otherwise it can be false because `F.struct(...)` creates a
non-null struct whose child fields may be null. Use tests to lock the chosen behavior.

Milestone 4 lowers nested struct expressions to PySpark. Add support to `PySparkExpressionMapper` if capability checks
need an expression requirement, and add rendering to `RenderPySparkExpression`. The renderer should emit
`F.struct(<child>.alias("<column>"), ...)` where child aliases use the nested schema field's Spark column name
(`FieldDefinition.column`), not necessarily the Python field name. The top-level projection renderer will still add the
outer `.alias("shipping")` when assigning to the output field. If the existing projection renderer already aliases
assignment expressions, avoid double aliasing at the outer level. Render no UDFs and no Python object literals.

Milestone 5 hardens nested field-path rendering. Replace naive dotted path rendering with segment-aware rendering.
For ordinary identifier-safe segments, generated code may remain compact. For aliases or field names containing dots,
spaces, backticks, or punctuation, render a Spark-safe expression that selects each segment without interpreting it as
multiple nested fields. One acceptable approach is to render the root scope with `F.col("<alias>.<top>")` only when all
segments are safe, and otherwise use chained field access such as `F.col("<alias>")[<top>][<child>]` if compatible with
PySpark Column semantics. Add tests for a nested schema where the outer field or inner field uses `alias="postal-code"`
and for a field alias containing a dot.

Milestone 6 rejects recursive nested schemas early. The docs already say self-recursive and mutually recursive
`Struct(...)` cycles are rejected. Add or harden validation during schema class creation or schema compilation so
`class Node(Structure): parent = field(Struct(Node))` cannot silently recurse. Because direct self-reference cannot be
written inside the class body before the class exists, tests can create cycles dynamically or through two classes where
one field definition is patched only if the current DSL permits it. If the current DSL makes direct cycles impossible,
record that discovery in this plan and add tests for the reachable cycle shape instead. The diagnostic should point to
`docs/reference/SchemaSemantics.md` or `docs/reference/SchemaDeclarationSyntax.md`.

Milestone 7 updates schema-generation tooling and public documentation. Confirm that
`MapPySparkSchemaToStructureSource` generates nested classes and imports `Struct` correctly for nested PySpark
`StructType` values. If it already does, add a regression test for generated source that compiles and includes a nested
constructor example in docs. Update `docs/reference/SchemaSemantics.md`, `docs/reference/SchemaDeclarationSyntax.md`,
`docs/reference/SymbolicExecution.md`, `docs/reference/PySparkCodeGeneration.md`, `docs/reference/ValidationSemantics.md`,
`Readme.md`, and `Troubleshooting.md` only where the feature changes user-facing behavior. Keep the documentation
clear that schema composition is nested containment, while inheritance is top-level field reuse.

## Validation and Acceptance

The feature is accepted when this source compiles and runs through Structure:

    class Address(Structure):
        city = field(String(), nullable=False)
        postal_code = field(String(), nullable=False)

    class OrderRaw(Structure):
        id = field(String(), nullable=False)
        shipping = field(Struct(Address), nullable=True)

    class OrderPublished(Structure):
        id = field(String(), nullable=False)
        shipping = field(Struct(Address), nullable=False)

    class PublishOrders(Transform):
        orders = input(OrderRaw)
        published = output(OrderPublished)

        def publish(self, order: OrderRaw) -> OrderPublished:
            where(order.shipping.is_not_null())
            return OrderPublished(
                id=order.id,
                shipping=Address(
                    city=trim(order.shipping.city),
                    postal_code=order.shipping.postal_code,
                ),
            )

A human should observe that generated PySpark uses Spark column expressions and `F.struct(...)`, not `F.lit(Address(...))`
or a Python UDF. The output schema should contain one `shipping` column whose data type is a nested Spark `StructType`
with `city` and `postal_code` children in `Address` declaration order.

Negative acceptance cases:

- Assigning `Address(...)` to a field declared as `Struct(TenantKey)` fails during compilation with a diagnostic that
  names the incompatible schemas.
- Reading `order.shipping.missing` fails as an unknown nested field.
- Assigning nullable `order.shipping` to a non-nullable target without `where(order.shipping.is_not_null())` or an
  explicit non-null construction fails.
- A nested field alias containing a dot is rendered as one field segment, not accidentally split into two nested
  segments.

Documentation acceptance:

- Public docs show `Struct(Address)` as the schema composition form.
- Public docs distinguish nested composition from schema inheritance.
- Troubleshooting explains the remedy for incompatible nested schema assignments and unsupported recursive schemas.

## Artifacts and Notes

The core new IR behavior can be demonstrated with a projection assignment whose expression kind is the nested struct
constructor:

    assignment.field.name == "shipping"
    assignment.expression.kind == "struct"
    assignment.expression.type == Struct(Address)

The rendered PySpark shape should be equivalent to:

    F.struct(
        F.trim(F.col("order_raw.shipping.city")).alias("city"),
        F.col("order_raw.shipping.postal_code").alias("postal_code"),
    )

For nested aliases, prefer tests that assert semantic-safe rendering over exact whitespace. A representative case is:

    class Address(Structure):
        postal_code = field(String(), alias="postal.code")

    class OrderRaw(Structure):
        shipping = field(Struct(Address), nullable=False)

    order.shipping.postal_code

The generated expression must read the single nested field named `postal.code`; it must not read nested field
`postal`.`code`.

## Interfaces and Dependencies

Use existing public APIs: `Structure`, `field`, `Struct`, transform schema constructors, `where(...)`, and existing
expression helpers such as `trim(...)`. Do not add a public `struct(...)` helper unless implementation proves that
schema constructor syntax cannot be made unambiguous.

At the end of the plan, the compiler-visible expression model must support a nested struct expression with these
properties:

- target schema identity: the `Structure` class used by `Struct(schema)`;
- ordered child assignments by nested schema field order;
- child aliases rendered from `FieldDefinition.column`;
- recursive conversion for nested structs inside nested structs;
- no PySpark dependency during schema extraction or frontend compilation.

The PySpark backend must render nested construction with `pyspark.sql.functions.struct`. Online execution and generated
execution must share the same lowering path so they remain semantically identical.
