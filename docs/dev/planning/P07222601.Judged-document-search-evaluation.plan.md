# Add Judged Document-Search Evaluation

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. Maintain this document according to `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

The Search example can rank documents and learn from impression and click data, but it cannot yet tell a user whether a ranked list is genuinely good. After this work, a caller will supply a daily batch of queries, one document-ranking run, and independently assigned relevance judgments. `EvaluateDocumentRankingQuality` will return per-query and daily metrics that make two ranking runs comparable against the same judgments.

The observable outcome is a PySpark transform that reports nDCG, precision, judged recall, success, and mean reciprocal rank at the requested cutoffs. A test fixture with a better-ranked ideal document must produce a higher nDCG and MRR than the same judgments in a worse order. Unknown (unjudged) returned documents must be visible as incomplete coverage, never silently counted as wrong.

## Surprises & Discoveries

- Observation: The existing `DailyClicks` relation is a query-document-position aggregate, not a captured result list.
  Evidence: `examples/search/schemas/clicks.py` groups facts by daily `TimeWindow`, normalized query, document, position, and propensity, but contains no search-request or ranking-run identity.

- Observation: Existing click facts cannot establish corpus relevance or the first satisfying rank in the exact result list a user saw.
  Evidence: `Impression` contains one displayed document and `Click` references that impression, while no schema groups all impressions from one request. The daily aggregate also discards individual impression identities.

- Observation: `SearchDocuments` already exposes a stable, typed ranking result suitable for an offline evaluator.
  Evidence: `examples/search/schemas/search.py` defines `DocumentSearchResult` with `search_query_id`, one-based `rank`, `document_id`, and ranking score fields.

## Decision Log

- Decision: Build judged offline document-search evaluation before click-based behavioral evaluation.
  Rationale: A relevance judgment directly states whether a document answers a query. A click is useful behavioral evidence but is affected by what was displayed and how it was positioned, so it is not a reliable absolute relevance label.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Use four relevance grades: 0 for not relevant, 1 for related, 2 for relevant, and 3 for ideal.
  Rationale: The scale supports both binary measures and graded ranking measures without a future schema migration. Grades 2 and 3 are binary-relevant; grade 1 contributes only to graded ranking value.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Make nDCG the primary quality metric and publish precision, judged recall, success, and MRR. Do not publish Accuracy@N or ERR in this slice.
  Rationale: The chosen rank-position definition of Accuracy@N equals Precision@N. nDCG uses all four grades, while ERR is deferred until a consumer needs its particular cascade-browsing interpretation.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Evaluate one ranking run per transform invocation, with comparisons made by invoking the transform repeatedly against the same persisted judgment pool.
  Rationale: This keeps the public transform focused and avoids adding a run identifier to the Search result schema. The caller can store each daily summary with its own run identity.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Require complete judgment coverage for a metric instead of treating unjudged returned documents as nonrelevant.
  Rationale: The pool intentionally covers a finite candidate set. Treating a new, unjudged document as wrong would bias comparisons against rankers that retrieve novel candidates.
  Date/Author: 2026-07-22 / user and Codex.

- Decision: Penalize short result lists with zero gain at missing ranks.
  Rationale: A ranker that returns fewer than N results should not escape an N-result quality measure. This differs from the earlier click-proxy proposal, where short lists were excluded.
  Date/Author: 2026-07-22 / user and Codex.

## Context and Orientation

The repository is a Python library that captures typed data transformations and renders equivalent PySpark projects. The Search example lives under `examples/search/`. Its schemas describe DataFrame row shapes, and its transforms describe transformations over those shapes. The integration test at `tests/integration/pyspark/search/test_search.py` runs each important transform both directly and through generated PySpark code, then compares the rows.

`examples/search/schemas/search.py` defines `SearchQuery` and `DocumentSearchResult`. `SearchQuery.id` is a caller-local query identifier, and `DocumentSearchResult.search_query_id` refers to it. `DocumentSearchResult.rank` is the one-based rank of a document in that query's result list. The evaluator must neither rerank nor alter these result rows.

`examples/search/schemas/clicks.py`, `examples/search/transforms/clicks/`, and `examples/search/transforms/relevance/` implement impression-backed feedback for live ranking. They remain untouched by this feature. They should not be imported by the judged evaluator: a relevance judgment is caller-supplied data, not an inferred click signal.

The public Search transform facade is `examples/search/transforms/search.py`; it re-exports search-presentation transforms from the internal `searching/` directory. Follow that pattern for the new `examples/search/transforms/evaluate.py` facade and its internal `examples/search/transforms/evaluation/search_docs/` implementation. Register every source schema and transform in both `tests/integration/pyspark/search/test_search.py` and `tests/helpers/example_projects.py`, because those registries drive generated-code and generated-document tests. Generated files under `examples/structure_generated/search/` are outputs; never hand-edit them.

An evaluation batch is one caller-defined UTC-aligned daily `TimeWindow`. A judgment pool is the set of query-document pairs that someone has assigned grades to. The caller builds that pool by combining the top 100 candidate documents from every ranking run being compared, together with any known-answer documents, deduplicating each query-document pair, and assigning it a grade independently of rank. The evaluator scores one run at a time against that shared pool.

## Interfaces and Dependencies

Create `examples/search/schemas/evaluation.py` and register it as `examples.search.schemas.evaluation`. It must declare these schemas using the existing `Schema` and PySpark field factories:

- `EvaluationBatch` has one required `window: struct(TimeWindow)`. The input must contain exactly one row. Its window must be the caller's UTC day and is copied to every output row.
- `DocumentRelevanceJudgment` has required `search_query_id: string`, `document_id: string`, and `relevance_grade: long`. The permitted grade values are 0 through 3. The evaluator assumes the caller provides at most one judgment for each query-document pair. Reject duplicate keys or grades outside this range before aggregation, with an actionable error naming the offending contract.
- `DocumentQueryEvaluation` has the batch window, query ID, `returned_result_count`, `judged_result_count`, `binary_relevant_judgment_count`, and nullable metrics `precision_at_5`, `precision_at_10`, `precision_at_15`, `judged_recall_at_5`, `judged_recall_at_10`, `judged_recall_at_15`, `success_at_5`, `success_at_10`, `success_at_15`, `ndcg_at_5`, `ndcg_at_10`, `ndcg_at_15`, and `reciprocal_rank`. It also has boolean coverage fields for each cutoff and for reciprocal rank so a consumer can distinguish a real zero from an unavailable metric.
- `DocumentEvaluationSummary` has the batch window, total query count, query count with at least one binary-relevant judgment, query count with no binary-relevant judgment, eligible query counts for each cutoff and reciprocal rank, complete-coverage query counts for each cutoff and reciprocal rank, and nullable daily means corresponding to every per-query metric. The reciprocal-rank mean field is named `mean_reciprocal_rank`.

Implement public class `EvaluateDocumentRankingQuality` in `examples/search/transforms/evaluation/search_docs/judged_quality/EvaluateDocumentRankingQuality.py` and re-export it only from `examples/search/transforms/evaluate.py`. Its inputs are `batch: EvaluationBatch`, `queries: SearchQuery`, `results: DocumentSearchResult`, and `judgments: DocumentRelevanceJudgment`; its outputs are `query_evaluations: DocumentQueryEvaluation` and `summary: DocumentEvaluationSummary`. `queries` is the complete evaluation population, so queries with no result rows must still produce an evaluation row.

The transform is batch-only. It has no dependency beyond the existing Structure and PySpark DSL helpers. Use lanes and focused `@step` methods to make the following stages visible in generated traceability: validate batch and judgments, join results to judgments, calculate per-query metrics, and aggregate the daily summary. If the required validation cannot be represented through ordinary Structure expressions, use the narrowest supported validation mechanism and add a direct test for the error; do not use raw PySpark for metric logic.

## Plan of Work

### Milestone 1: Define the evaluation contracts

Add the schema module and include it in the Search example's schema discovery lists. The `EvaluationBatch.window` should use `TimeWindow`, not a date conversion, so it matches the library's existing daily data contract exactly and avoids a Spark-session timezone reinterpretation.

Document the grade scale in each public schema docstring. Define binary relevance as `relevance_grade >= 2`. Grade 1 is related but not sufficient for a binary success claim. Declare metric fields nullable because a metric can be unavailable due to incomplete judgments; do not encode unavailable as zero.

Add an `evaluation` package and its `search_docs/judged_quality` subpackage. Their `__init__.py` files should expose only the internal evaluator types required by import paths. `evaluate.py` is the sole convenient public import surface and must export `EvaluateDocumentRankingQuality`.

### Milestone 2: Calculate coverage and per-query metrics

Implement `EvaluateDocumentRankingQuality` as a composition of small stages. First cross join the single batch row to the query population and retain every query ID. Join result rows by `queries.id == results.search_query_id`; count only actual result rows as returned. Join judgments by both query ID and document ID. A returned document is judged only when that join succeeds.

For each cutoff N in 5, 10, and 15, consider returned results with `rank <= N`. Missing ranks contribute zero gain. Set the cutoff coverage flag only when every actual returned result through N is judged. A short list can therefore have complete coverage, but still has zero gain for its absent ranks.

For completely covered query-cutoff pairs with at least one binary-relevant judgment, calculate:

- `precision_at_N = binary relevant results at ranks 1..N / N`.
- `judged_recall_at_N = binary relevant results at ranks 1..N / all binary-relevant judgments for the query`.
- `success_at_N = 1` when at least one binary-relevant result is at ranks 1..N, otherwise `0`.
- `dcg_at_N = sum((2^grade - 1) / log2(rank + 1))` over ranks 1..N, using zero for missing ranks. `ndcg_at_N` is `dcg_at_N` divided by the ideal DCG obtained by sorting all judgments for that query by grade descending and taking the best N. If ideal DCG is zero, the metric is unavailable.

Set all four cutoff metrics to null when cutoff coverage is incomplete or the query has no binary-relevant judgment. The latter is a no-known-answer query, not a demonstrated ranking failure, and must be counted separately in the summary.

Calculate reciprocal rank from the first returned binary-relevant document. It is `1 / rank`; it is zero when no binary-relevant returned document exists. Its coverage is complete only when every returned document from rank 1 through that first relevant document is judged. When no binary-relevant result is returned, coverage requires every returned document to be judged. Set `reciprocal_rank` to null when this coverage is incomplete or the query has no binary-relevant judgment.

### Milestone 3: Aggregate and publish daily metrics

Aggregate all per-query rows into the sole `DocumentEvaluationSummary` row for the batch. Each daily metric is the average of its non-null per-query values. Its eligible count is the number of non-null values, and its complete-coverage count is the number of query rows whose associated coverage flag is true. Retain both counts so an operational report can reject a misleading score with weak label coverage.

Do not introduce `accuracy_at_N`: it is identical to precision under this contract. Do not introduce ERR, average precision, click-through rate, or propensity-corrected metrics in this transform. nDCG supplies the graded ranking signal, MRR and success describe how early an acceptable answer appears, and precision/recall describe binary result quality within the shared pool.

Update `examples/search/Readme.md` with an Evaluation section after Document Search. Show how a caller constructs a one-row batch DataFrame, passes one ranking run and the persisted judgment pool to `EvaluateDocumentRankingQuality`, and persists the two outputs. Explain that a comparison is made by evaluating each run separately against the same pool. State clearly that the existing click pipeline is engagement feedback for serving, not offline relevance truth.

## Validation and Acceptance

The feature is accepted when a caller can create a batch window, query DataFrame, one ranked document result DataFrame, and a four-grade judgment DataFrame, then run `EvaluateDocumentRankingQuality(...).run(session)` and receive:

- one per-query row for every input query, including queries without results;
- nDCG@5/10/15 that increases when higher grades are moved upward;
- binary metrics that count only grades 2 and 3;
- zero-valued gain for missing result positions;
- null rather than zero metrics when top-rank judgments are incomplete;
- one daily summary whose means, eligible counts, and coverage counts match the per-query rows;
- identical online and generated PySpark outputs.

The Search README must show the complete invocation and explain that the caller owns judgment production and persistence. Generated Search schemas, transform docs, PySpark source, and traceability must contain the evaluator. Focused integration and golden tests, static checks, and `make build` must pass, subject only to separately documented pre-existing failures.

## Idempotence and Recovery

All source edits are additive. Re-running the generation and golden tests is safe because generated files are deterministic outputs of the registered source transforms. If a partial implementation produces stale generated files, restore consistency by completing or reverting only the evaluation source edits, then rerun the generation path; never treat generated files as an independent source of truth.

The evaluator does not mutate caller-owned query, result, or judgment data. A caller may rerun it for the same batch and run identity without changing the input facts. Persisted daily outputs should be overwritten or upserted by the caller using the batch window and caller-owned ranking-run identity; the example does not choose storage technology or sink semantics.

## Artifacts and Notes

The principal public invocation should have this shape (the caller supplies ordinary DataFrames conforming to the schemas):

    evaluation = EvaluateDocumentRankingQuality(
        batch=batch,
        queries=queries,
        results=document_results,
        judgments=document_judgments,
    ).run(session)

    per_query = evaluation.query_evaluations
    daily_summary = evaluation.summary

The caller compares a baseline and a candidate by retaining the same `batch`, `queries`, and `judgments`, then calling the transform once for each run's `results`. The caller records which run produced each persisted summary; the evaluator intentionally does not add a ranker identifier to the general Search result contract.

Future work is intentionally separate. Behavioral evaluation needs request-level impression lists, ranking-policy identity, and experiment-arm logging before it can calculate click satisfaction or counterfactual estimates responsibly. ERR can be added later from the existing four-grade judgment field without changing the input schema.
