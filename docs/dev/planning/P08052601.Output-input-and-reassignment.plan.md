# Allow output branches as step inputs and configurable output reassignment

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date during implementation. It follows the repository guidance in `docs/dev/auto/Plans.md`.

## Purpose / Big Picture

Structure currently treats a declared `output(...)` as a terminal result that cannot be selected as a later step input. This is stricter than ordinary PySpark usage, where a DataFrame branch can be named, reused to derive another DataFrame, and returned alongside that derived result. The restriction makes the Store example carry identity publication steps whose only job is to transfer an internal lane into a public output.

After this change, a previously produced output can participate in the same lazy, immutable dataflow as a lane. A transform author will be able to build a public branch and then derive another public branch from it, while still returning both branches. For example, a `Published` output can feed a later `Summary` output. If the author explicitly chooses to write a later step back to an existing output declaration, that behavior is controlled separately by `allow_to_reassign_output`.

The two semantic options are Core-owned settings whose defaults are supplied by the selected plugin. The bundled PySpark plugin defaults both options to `true`, matching normal PySpark expectations. Projects and programmatic callers can opt into stricter behavior. The result will be observable through Core analysis, online execution, generated PySpark, streaming lineage, diagnostics, and the simplified `BuildProductSignals` graph.

## Surprises & Discoveries

- Observation: PySpark generated code already keeps independent branch DataFrames in a frame mapping; creating a later branch does not consume the earlier branch.
  Evidence: `examples/structure_generated/store/pyspark/transforms/examples/store/transforms/recommender/signals/workflow.py` retains the intermediate and public frame keys and returns several outputs from the same run.

- Observation: The current prohibition is Core-owned, while plugin options are currently passed as opaque mappings to selected plugin facets.
  Evidence: `src/structure/core/compiler/frontend/commands/CompileTransform.py` rejects an output role in `_declared_source`, and `src/structure/core/configuration/model/StructureConfig.py` stores per-plugin option mappings.

- Observation: The compiler already distinguishes a declared output from a lane in its source and write paths, and raw-hook input handling already recognizes output declarations as possible sources within an available-frame map.
  Evidence: `src/structure/core/compiler/frontend/commands/CompileTransform.py` contains separate `_raw_input`, `_raw_output_source`, and `_raw_available` paths.

## Decision Log

- Decision: Use `allow_output_to_input` for the rule that determines whether a produced public output may be selected or inferred as a later step source.
  Rationale: The name describes the directed relationship and does not imply DataFrame mutation.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Use `allow_to_reassign_output` for the independent rule that determines whether a declared output may receive a later assignment after its initial assignment.
  Rationale: Output-to-input reuse and output reassignment are separate authoring choices. The name follows the requested wording; implementation documentation must define reassignment as rebinding the named output frame to a new immutable DataFrame plan, not mutating an existing Spark DataFrame.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Permit bare schema inference to consider produced outputs.
  Rationale: This matches ordinary source-order DataFrame programming and avoids forcing explicit selectors for every branch. An available lane shadows an output, preserving the repository’s existing lane-shadowing rule. Explicit selectors remain authoritative, and unresolved multiple matches remain compile errors.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Preserve source-order availability.
  Rationale: An output declaration exists in the class body before execution, but its DataFrame frame does not exist until a step produces it. A step may consume only an output that has already been materialized by an earlier step.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Keep outputs and inputs as distinct declarations, while allowing a produced output frame to be a source.
  Rationale: The feature models reusable DataFrame branches; it does not turn constructor inputs into outputs or collapse the public result contract into the input contract.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: Treat `@step(input=published, output=published)` as a valid explicit reassignment when `allow_to_reassign_output` is enabled.
  Rationale: The decorator has distinct `input` and `output` keyword arguments, and the same declaration object can be supplied to both. This is the Structure equivalent of rebinding `df = transform(df)` in PySpark; it does not mutate the earlier DataFrame plan.
  Date/Author: 2026-08-05 / User and Codex.

- Decision: The selected plugin supplies defaults, but Core owns option meaning, resolution, source binding, diagnostics, and enforcement.
  Rationale: Whether an output may be a step source or may be reassigned is a transform-graph semantic, not a backend-specific Spark operation. Plugin defaults allow alternative backends to choose a different compatibility posture without moving the rule into opaque backend code.
  Date/Author: 2026-08-05 / User and Codex.

## Context and Orientation

The repository is a typed transformation compiler. A transform class declares constructor `input(...)` relations, private intermediate `lane(...)` relations, and public `output(...)` results. A schema-returning step method reads one or more source relations and writes a result relation. Core analyzes source order and role bindings before the PySpark plugin lowers the plan into online execution or generated PySpark.

The relevant current contract is in `docs/dev/specifications/DSL.md`, especially the “Lanes And Outputs” section. It currently says that lanes are internal funnel streams and that method-level input selection is limited to original inputs or lanes. `tests/specifications/multiple-outputs/test_v1_multiple_transform_outputs.py` currently asserts that selecting an output as a step input is rejected. Those rules and tests must change together.

Configuration is resolved through `StructureConfig` and copied into `CompilerOptions`. Defaults are assembled by `src/structure/core/configuration/logic/StructureConfigDefaults.py`, validated by `StructureConfigValidator.py`, and copied by `StructureConfigBuilder.py`. Selected plugin options are currently stored in `StructureConfig.plugin_options` and included in compiler fingerprints by `CompilerOptions` and `BuildCompiledTransform`.

Core source binding is implemented in `src/structure/core/compiler/frontend/commands/CompileTransform.py`. The relevant methods are `_declared_source`, `_declared_input_source`, `_selected_lane_source`, `_output_lane`, `_outputs`, and `_implicit_output_lane`. `AnalyzeTransform.py` builds the Core `TransformPlan` used by the plugin compiler. The generated and online PySpark paths consume that plan and must retain identical frame and result semantics.

The Store case is `examples/store/transforms/recommender/signals/products.py`. It currently declares `impression_facts` and `click_facts` as lanes, publishes them through identity methods into `daily_impressions` and `daily_clicks`, and independently consumes the private lanes in `summarize_signals`. The intended simplification is to let the summarization steps write the public outputs directly and let `summarize_signals` consume those produced outputs. The composed public outputs are propagated by `examples/store/transforms/recommender/signals/workflow.py`, `recommender/workflow.py`, and `merchandising/workflow.py`.

## Plan of Work

### Milestone 1: Establish the semantic option and plugin-default contract

First inspect the plugin API and configuration lifecycle closely enough to choose a plugin-default mechanism that does not make Core load optional plugin implementations during ordinary configuration inspection. The preferred design is a small negotiated plugin semantic-default facet or equivalent plugin metadata that returns defaults for Core-owned semantic options. The selected plugin must be able to supply `allow_output_to_input=True` and `allow_to_reassign_output=True` for the bundled PySpark plugin. Existing plugins or test fixtures without the new declaration need a documented compatibility fallback, preferably `false`, rather than an accidental permissive behavior.

Add the effective boolean values to `StructureConfig` and `CompilerOptions`, or to the equivalent immutable Core compiler-options value selected by the existing architecture. Configuration precedence must remain built-in/plugin default, project file, and programmatic/CLI override. The selected plugin’s default must be applied before Core analysis. Include both values in `CompilerOptions.fingerprint()` and any artifact manifest or capability identity so changing either option cannot reuse a stale compiled plan.

Expose the settings in the configuration specification with exact names, types, allowed values, default-resolution behavior, and actionable diagnostics. The PySpark plugin’s configuration/default documentation must state that both defaults are `true`. Add config-resolution tests for omitted values, explicit true/false overrides, selected-plugin defaults, invalid types, and compiler-fingerprint differences.

### Milestone 2: Extend Core source resolution for produced outputs

Change Core’s method source resolution so a produced `OutputDeclaration` can be a source when `allow_output_to_input` is true. Preserve the existing explicit role model: `input(...)` selects an original constructor input, `lane(...)` selects a working lane, and an output selector selects a produced public output. The exact selector spelling should be chosen consistently with the existing `BindingSelector` API and documented; do not overload a raw string or introduce backend-specific syntax.

Update the available-frame bookkeeping so each produced output has a source frame with its declared schema, source-order availability, streaming mode, and provenance. A source request must fail if the output has not yet been produced. An explicit output source must fail with a direct configuration diagnostic when `allow_output_to_input` is false.

Extend bare schema inference. At each step, consider only frames available at that source-order position. Preserve the current rule that a matching lane shadows an original input; when a lane and output are both candidates, the lane shadows the output. If no lane is available, a produced output may be selected. If more than one output remains a valid match, fail with an ambiguity diagnostic listing the candidates and recommending an explicit selector. Explicit `input(...)`, `lane(...)`, and output selectors must override inference and continue to validate schemas.

Update the output-write path independently. A first write to a declared output remains valid under both reassignment settings. A later write to an already-produced output is accepted only when `allow_to_reassign_output` is true. When false, report the output name, the original writer, the later writer, and the configuration remedy. When true, preserve source order and make the latest output frame the final value associated with that public output. Reject incompatible schema writes and unresolved branching writers rather than silently choosing a frame.

Add plan metadata or traceability fields as needed to distinguish an output used as a source from an output being written. Explain output should show the source frame and the output frame, so a reader can see whether a step reads a public branch, updates it, or creates a separate result.

### Milestone 3: Prove online and generated PySpark branch semantics

Add focused Core specification tests for the following cases: output-to-input enabled; output-to-input disabled; output read before production; output inferred by schema; lane shadowing an output; explicit original-input selection despite a matching produced output; ambiguous output inference; separate output derivation; same-output reassignment enabled; same-output reassignment disabled; incompatible reassignment; and source-order multiple consumers.

Use small schemas and transforms in `tests/specifications/multiple-outputs/test_v1_multiple_transform_outputs.py` or a new focused specification file. Assert the `TransformPlan` step source, input lane/frame, output lane/frame, result outputs, diagnostics, and output schemas. Preserve the existing test’s intent by changing it from unconditional rejection to strict-mode rejection and enabled-mode acceptance.

Add PySpark rendering tests that prove a public output can be used by a later step and that the generated module keeps the source and derived output variables available. Add online execution tests that run a small DataFrame graph and verify that the first output and derived output both contain their expected rows and schemas. Add parity coverage so generated and online execution return equivalent results.

Extend streaming compatibility tests. A streaming output used by a later step must carry its streaming lineage exactly as a lane would. The feature must not introduce sinks, triggers, checkpoints, or query lifecycle behavior; callers continue to own those concerns. Verify that source-order branching does not bypass watermark, bounded-join, state, or output-mode diagnostics.

Update compiler artifact, explain, traceability, and generated-output tests. Both semantic options must affect relevant fingerprints. Generated source should remain deterministic and should use stable frame names for output-derived branches.

## Validation and Acceptance

The feature is accepted when a transform with two public outputs can produce the first output, use it as a later step source, and return both outputs without a compiler error or runtime mutation. A transform with a matching private lane must use that lane for bare schema inference. An explicit original-input selector must still bypass a produced output. An output read before production, an ambiguous inferred output, a disabled output-to-input setting, and a disabled same-output reassignment must each produce an actionable deterministic diagnostic.

The PySpark plugin must resolve both options to `true` when omitted. A project override of either option to `false` must change analysis behavior and compiler artifact identity. A plugin with different declared defaults must receive those defaults without Core embedding PySpark-specific behavior. The selected plugin must not be required merely to inspect unrelated configuration, consistent with the existing Spark-free configuration contract.

Online and generated PySpark execution must return equivalent rows and schemas for the branch-and-derive scenario. Reusing a public output must not prevent returning it, and creating a derived branch must not mutate or invalidate the original branch. Streaming analysis must retain existing lineage and caller-owned lifecycle boundaries.

The simplified Store `BuildProductSignals` source must no longer need identity publication methods for daily impressions and clicks. Store outputs and product signal values must remain unchanged, aside from generated plan/frame names that directly reflect the simpler graph.

## Interfaces and Dependencies

Core configuration must expose immutable effective boolean values named `allow_output_to_input` and
`allow_to_reassign_output` to source analysis and compilation. The selected plugin must provide semantic defaults for those
names, with bundled PySpark defaults set to `true`. The values must be available to Core before `AnalyzeTransform` resolves
step sources, and they must be included in compiler option fingerprints.

Core source-resolution APIs must accept a produced output as a source only when the effective option permits it. Their
available-frame model must carry declaration name, schema, source-order availability, source kind, streaming lineage, and
provenance. Output writes must distinguish an initial write from a later reassignment and apply the effective
`allow_to_reassign_output` policy.

The PySpark plugin continues to lower ordinary immutable DataFrame operations. No new sink, action, Spark session, query
lifecycle, checkpoint, or external side effect is introduced. Existing PySpark, Spark Connect, and generated-code
capability checks remain in force.

The implementation must preserve the public `TransformResult` contract, schema validation behavior, source-order execution,
lane shadowing, composition output binding, and generated/online semantic parity.
