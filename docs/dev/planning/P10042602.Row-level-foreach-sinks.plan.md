# Add row-level foreach sinks to Structure transforms

This ExecPlan is a living document. Maintain it according to `docs/dev/auto/Plans.md`. Keep `Progress`, `Surprises &
Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as work proceeds. This document is self-contained:
it describes the proposed public behavior, the current implementation seams, the work to perform, and the evidence
needed before claiming support.

## Purpose / Big Picture

An author should be able to declare a row sink beside a transform's inputs and outputs, then write
`foreach(alert, sink)` inside a compiled step. Structure records which final output feeds the sink without executing
Python side effects while compiling or running the transform. The caller receives the ordinary output DataFrame plus a
named sink handoff on the same result object and decides whether and when to run the sink. Adding the sink to an existing
streaming transform must leave the caller's existing output query intact.

The first release covers both batch `DataFrame.foreach` and streaming `DataStreamWriter.foreach`. The callback or writer
body is opaque Python; arbitrary Python in that body does not need symbolic-expression support. Query start, stop,
checkpoints, triggers, retry recovery, credentials, and external sink configuration remain with the caller.

- Observation: Spark worker processes could not import a test module outside their `PYTHONPATH`, even though the driver
  could. The live writer therefore lives in the importable example package `examples.streams.foreach_sinks`.
  Evidence: the initial `ModuleNotFoundError` and subsequent passing 3.5 and 4.0 runs.
- Observation: Core's neutral analysis pass does not carry plugin-authored sink captures. `AuthorTransform` must copy the
  captured sink facts and plans into the structural plan before lowering.
  Evidence: the initial lowered plan had no sinks even though its captured PySpark body did; the final test asserts the
  lowered sink plan and runtime handoff.
- Observation: PySpark batch `DataFrame.foreach(f)` applies a function to each Spark `Row`; it is a shorthand for
  `df.rdd.foreach(f)`. It has no writer `open`/`close` lifecycle.
  Evidence: `https://spark.apache.org/docs/latest/api/python/reference/pyspark.sql/api/pyspark.sql.DataFrame.foreach.html`.
- Observation: PySpark streaming `DataStreamWriter.foreach(f)` first checks whether `f` is callable. A callable object
  takes the simple function branch; a noncallable object with `process(row)` takes the writer branch, where optional
  `open(partition_id, epoch_id)` and `close(error)` are used. Spark serializes a copy for each task.
  Evidence: `https://spark.apache.org/docs/latest/api/python/_modules/pyspark/sql/streaming/readwriter.html`, in
  `_construct_foreach_function` and `foreach`.
- Observation: `src/structure/core/runtime/session/model/TransformResult.py` currently maps only outputs, while
  `StructureSession.run` in `src/structure/core/runtime/session/model/StructureSession.py` receives both online and
  generated `TransformResult` values. A named sink can be added as a read-only result attribute without changing the
  output mapping's iteration and length.
  Evidence: `TransformResult.__getitem__`, `__iter__`, `__getattr__`, and `StructureSession.run`.

## Decision Log

- Decision: Use a class-level `sink(WriterClass)` declaration and a step parameter such as `sink: AlertWriter`, with
  `foreach(alert, sink)` inside the step. Do not add `DataFrame.writeStream` syntax to symbolic rows.
  Rationale: This follows existing declaration and parameter-binding idioms while keeping query lifecycle outside the
  transform. No generic writer annotation is required in the first version.
  Date/Author: 2026-10-04 / user and Codex.
- Decision: Use the already implemented `@special(type="opaque")` on the writer class. Do not introduce a separate
  `@foreach` decorator in the first version.
  Rationale: The marker expresses that Structure must not inspect or execute the writer's Python body during symbolic
  compilation. `foreach(...)` is the explicit consuming operation.
  Date/Author: 2026-10-04 / user and Codex.
- Decision: Keep `process(self, row: Row) -> None` in examples. `Alert` is the Structure output schema, not the actual
  object delivered by PySpark. The declaration's final output binding supplies the schema association.
  Rationale: Spark invokes batch callbacks and streaming writers with `pyspark.sql.Row` values. Annotating the
  parameter `Alert` would promise a conversion that this plan does not provide.
  Date/Author: 2026-10-04 / user and Codex.
- Decision: Expose the sink directly as `result.publish_alerts`. Its immutable handoff has `dataframe` (the exact
  declared final output DataFrame) and `writer` (the authored writer **class**, not an instance). The caller constructs
  the writer with application configuration and runs native PySpark operations.
  Rationale: No writer constructor, network connection, job, or query should run merely because Structure returned a
  transform result. A class handoff permits configured writers without changing an existing transform invocation.
  Date/Author: 2026-10-04 / Codex, implementation choice for this plan.
- Decision: Infer a step's sink parameter by its non-generic writer class when exactly one declaration matches;
  `@step(sink=publish_alerts)` resolves ambiguity. Fail if a declaration name collides with an output name, output
  alias, stage name, or `TransformResult` public member.
  Rationale: This mirrors relation binding without hiding which sink is selected or making result attributes unstable.
  Date/Author: 2026-10-04 / user and Codex.
- Decision: `foreach(row, sink)` initially accepts only rows that resolve to a declared final output after the step's
  return and output binding are known. Multiple calls may target one sink only if they resolve to the same final output;
  duplicate captures of the same pair are rejected until a precise multiplicity contract exists.
  Rationale: A final output has one stable DataFrame for caller attachment. An intermediate row could feed later filters
  or projections and would require a separate branch whose meaning has not been designed.
  Date/Author: 2026-10-04 / user and Codex.
- Decision: A streaming sink writer instance passed to Spark must be noncallable, expose `process(row)`, and may expose
  `open` and `close`. A batch sink uses `DataFrame.foreach(writer.process)` and gets no `open`/`close` calls. For the
  first version, reject `open` or `close` on a writer bound to a batch final output and direct authors to a separate
  batch processor whose `process` is self-contained.
  Rationale: Silently ignoring setup or cleanup methods in batch could cause incorrect writes or leaked resources.
  This deliberately explicit rule can be relaxed later if a batch lifecycle adapter is designed and proven.
  Date/Author: 2026-10-04 / Codex, proposed batch lifecycle rule to review during milestone 1.
- Decision: A streaming sink is an additive second query. Each `.start()` returns its own `StreamingQuery`; neither
  query is started by Structure. The caller gives each query its own checkpoint and manages both handles.
  Rationale: This preserves existing calling code, permits different sinks, and does not claim synchronized progress or
  atomic writes across queries.
  Date/Author: 2026-10-04 / user and Codex.
- Decision: The first implementation rejects sink-bearing composed pipelines and staged transform graphs with
  `DSL-E0406`; a sink attaches only to a direct transform's declared final output.
  Rationale: A composition can rename or hide a child output, and current stage results do not provide a stable
  `TransformResult.sink_name.dataframe` mapping. Failing during compilation avoids silently losing a side effect. A
  future contract can map child sink outputs through stage paths explicitly.
  Date/Author: 2026-10-04 / Codex, implementation boundary.
- Decision: Claim classic PySpark 3.5 and 4.0 only; leave Spark Connect unclaimed.
  Rationale: The callback, writer serialization, separate-query, and online/generated tests run on the classic profiles.
  This test lane does not prove Spark Connect callback serialization.
  Date/Author: 2026-10-04 / Codex, evidence-based target boundary.

## Context and Orientation

A Structure `Schema` describes a row's fields and types for compilation. It is not the `pyspark.sql.Row` object Spark
passes to Python on an executor. A step method runs once under symbolic compilation to create an expression plan; it
does not run once per data row. A sink is a declared destination for rows of one final output. A handoff is a read-only
result value containing the output DataFrame and writer class so the caller can start a real Spark action or query.

The target-neutral public declaration helpers live in
`src/structure/core/dsl/model/transforms/transform_api.py`. `Transform.__init_subclass__` in
`src/structure/core/dsl/model/transforms/Transform.py` collects input, lane, and output declarations. The Core
frontend `src/structure/core/compiler/frontend/commands/CompileTransform.py` resolves step parameters and produces
`StepPlan` and `TransformPlan` values in `src/structure/plugin/api/v1/model/`. The PySpark symbolic context in
`src/structure/plugin/pyspark/symbolic_execution/model/PySparkSymbolicContext.py` captures operations; the PySpark
compiler creates `PySparkExecutionPlan`. Online and generated execution both ultimately return a
`TransformResult`, whose current source is `src/structure/core/runtime/session/model/TransformResult.py`.

The V11 design entry is `docs/dev/design/V11RetainedV9DesignGates.design.md`; its specification counterpart is
`docs/dev/specifications/V11RetainedV9DesignGates.spec.md`. The broader plan
`docs/dev/planning/P08042603.V11-retained-v9-design-gates.plan.md` contains a side-effect milestone. This focused plan
supplies the implementation work for that milestone; reconcile both documents when the feature is admitted. The V9
restriction that transform methods cannot call row-level foreach remains effective until this plan's acceptance gates
pass; do not revise historical V9 claims retroactively.

## Proposed Public Behavior

The following is target API syntax, not code that works today. `AlertWriter` can use arbitrary Python in its body
because Structure only records its class and never calls its methods during symbolic compilation. A direct call to
`AlertWriter.process` from a compiled step still fails under `@special(type="opaque")`.

    from pyspark.sql import Row
    from structure import *
    from structure.plugin.pyspark import *

    class Event(Schema):
        id = string(nullable=False)

    class Alert(Schema):
        id = string(nullable=False)

    @special(type="opaque")
    class AlertWriter:
        def __init__(self, destination: str) -> None:
            self.destination = destination

        def process(self, row: Row) -> None:
            print(f"{self.destination}: {row.id}")

    class PublishAlerts(Transform):
        events = input(Event, streaming=True)
        alerts = output(Alert)
        publish_alerts = sink(AlertWriter)

        @step(output=alerts)
        def publish(self, event: Event, sink: AlertWriter) -> Alert:
            alert = Alert(id=event.id)
            foreach(alert, sink)
            return alert

With one `AlertWriter` sink declaration, the step parameter binds automatically. If the transform declares two
`AlertWriter` sinks, use `@step(output=alerts, sink=publish_alerts)` on this method. The parameter name `sink` is local
to the step; no `self.publish_alerts` reference is needed inside it. The `sink(...)` declaration takes a writer class,
not an instance, and the `foreach(...)` call records only the output-to-sink association.

The caller may continue an existing query without changing it, then opt into the additional sink. The second query
runs independently, can progress at a different rate, and can fail or restart independently. The two checkpoints must
be distinct; Structure makes no cross-query atomicity or exactly-once claim.

    result = session.run(PublishAlerts(events=events_stream))
    primary = result.alerts.writeStream.format("delta").option(
        "checkpointLocation", "/checkpoints/alerts"
    ).start("/tables/alerts")

    alert_sink = result.publish_alerts
    assert alert_sink.dataframe is result.alerts
    secondary = alert_sink.dataframe.writeStream.foreach(
        alert_sink.writer(destination="alerts-service")
    ).option("checkpointLocation", "/checkpoints/publish-alerts").start()

For a batch output, the caller executes an action explicitly:

    batch_sink = result.publish_alerts
    batch_sink.dataframe.foreach(batch_sink.writer(destination="alerts-service").process)

That batch form invokes `process(Row)` on Spark workers. It does not invoke streaming writer lifecycle methods and may
replay rows on task retry. The batch writer must perform its own per-call resource management and idempotence, or the
caller should use another native Spark API outside this feature. A streaming writer should define `open` only when it
needs partition/epoch setup; it may define `close` for cleanup, but must not rely on `close` after a worker crash. The
writer instance has no `__call__` method so Spark selects its `process` object path. The caller supplies a
serializable instance; connection objects should be opened on executors rather than captured in its constructor.

## Validation and Acceptance

The release is acceptable when a transform containing `foreach(alert, sink)` compiles without constructing or
calling the writer; its returned `alerts` DataFrame is unchanged; `result.publish_alerts` exposes that same DataFrame
and the writer class; and the caller can execute a batch action or start an independent streaming foreach query using
ordinary PySpark. Running the transform alone must leave the local test sink empty and must not create a Spark query.

The compiler must reject an intermediate row with a diagnostic that identifies the exact bad `foreach` call and the
final output it could attach to. It must reject ambiguous sink binding, direct calls into opaque writer methods,
result-name collisions, and the batch lifecycle mismatch before execution. A live test must demonstrate a
noncallable streaming writer's `open/process/close` path and show that two queries can advance independently with
separate checkpoints. Online and generated execution must produce equivalent handoffs. A failed/retried task may
replay side effects; the documentation must state that sink idempotence is the caller's responsibility.

## Idempotence and Recovery

The plan's compiler and documentation edits are repeatable. Use temporary local files and test-only checkpoint
directories for live proofs. Stop all test query handles in `finally` blocks and remove only fixtures the test created.
Do not delete a caller's checkpoint to make a test pass; create a fresh test location. If a milestone fails, preserve
its failure output and update `Progress` and `Surprises & Discoveries` before revising the design. The existing
caller-owned `foreachBatch` recipe remains usable throughout implementation.

## Interfaces and Dependencies

The public additions are `sink(writer_type: type) -> SinkDeclaration`, `foreach(row: Schema, sink: object) -> None`,
and `@step(sink=declaration)` alongside automatic sink-parameter binding by unique writer class. `SinkResult` exposes
read-only `dataframe` and `writer: type`, directly under the declared name on `TransformResult`. No writer generics,
automatic writer construction, Structure query manager, or transform-level `.writeStream` proxy are part of this plan.

The PySpark target must validate a writer instance's `process(row)` shape, noncallability for streaming, and optional
streaming `open/close` signatures before it hands the class to the caller. Batch output uses a bound `process` callback and
rejects streaming lifecycle methods in the first version. Structure does not validate external service credentials or
promise exactly-once delivery. Other plugins must receive an explicit unsupported-capability diagnostic until they
implement an equivalent sink handoff; the public declaration must not silently run Python inside their compiler.
