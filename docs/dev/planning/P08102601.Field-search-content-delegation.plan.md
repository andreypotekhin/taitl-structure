# Delegate field-search body clauses to SearchDocuments

This ExecPlan is a living document. Keep its `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections current while implementing it. Follow `docs/dev/auto/Plans.md` when revising the plan.

## Purpose / Big Picture

The Search example currently has two separate query behaviors: `SearchDocuments` searches document content and `SearchFields` searches metadata. This plan makes `SearchFields` the independent entry point for a combined query without making `SearchDocuments` aware of fields.

After this change, a caller can submit one field-aware query and receive one stable field-search result envelope. Explicit field clauses are evaluated by `FieldIndex`; explicit `content:` clauses and ordinary unprefixed text are converted into a normal `SearchQuery` and delegated to the existing `SearchDocuments` funnel. A query containing only metadata clauses remains a metadata-only field search.

Examples:

    aurora beacon
        delegates `aurora beacon` to SearchDocuments.

    content:aurora
        delegates `aurora` to SearchDocuments.

    title:guide aurora
        matches `title:guide`, delegates `aurora`, and returns only delegated results that also match the field clause.

    meta:guide content:upgrade
        matches the generated all-metadata field, delegates `upgrade`, and intersects the two result sets.

    title:guide
        performs a metadata-only field search and does not invoke the content path.

`SearchDocuments` remains field-syntax unaware while accepting an optional query-scoped `document_filter_targets` input. Field delegation uses the same document-search funnel and supplies projected targets as an additional pre-filter; omitted or empty targets preserve the standalone path.

## Surprises & Discoveries

- Observation: unchanged `SearchDocuments` accepts a corpus-wide `Document` relation, while field targets are query-specific.
  Evidence: `RetrieveDocuments` joins `Document` to query-scoped scores but has no field-target input or join on `Document.search_query_id`.

- Consequence: a union of field-matching documents cannot express query-specific admission. A generic query-scoped `document_filter_targets` relation can express it without making canonical `SearchDocuments` field-aware: the field-specific document funnel treats `(delegated_query_id, document_id)` rows only as allowed document IDs.

- Observation: `DocumentFilterScore` is keyed by query and document, but its published value is not purely a pairwise fact. `filter_rank` is calculated across all matching documents and only rows within the 10,000 cap are persisted.
  Evidence: `FilterOverlap.publish_filter_scores` filters by `filter_rank <= maximum_candidates`, and `SelectFilterTargets` applies the same bound to published artifacts.

- Consequence: an unrestricted cached artifact cannot safely serve a restricted query. A document admitted by field search may have ranked beyond the unrestricted cap and therefore have no cached row. Restricted queries must use target-aware filtering unless the cache is redesigned to retain uncapped per-document matches plus a separate scope-aware ranking step.

- Observation: `DocumentScore.score` is also not purely pairwise because `SelectScores` normalizes BM25 by a per-query maximum. Restricting the scoring population changes that maximum and can change the balance between BM25 and overlap components.

- Decision implication: this plan applies `document_filter_targets` through filtering and retrieval, preserving existing full-corpus scoring and score-cache semantics. A later target-aware scoring optimization must define a new normalization/cache contract rather than silently mixing target-normalized online scores with full-corpus cached scores.

- Observation: a generated `meta` string must preserve gaps between source fields or positional phrases can cross field boundaries.
  Evidence: `FieldIndex` derives positions from the token array and removes empty/stop-word tokens without renumbering later positions.

## Decision Log

- Decision: make `SearchFields` the combined-query entry point while keeping canonical `SearchDocuments` unaware of field syntax.
  Rationale: field syntax, metadata matching, body-query extraction, and result-envelope composition belong at the field-aware boundary; the reusable content funnel accepts only a generic optional target relation.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: delegate whenever the parsed query has body content, whether that content came from an explicit `content:` clause or an unprefixed query fragment.
  Rationale: unprefixed text is no longer metadata by default, but it must remain useful as ordinary body search. No caller mode is needed; delegation is determined by the parsed content partition.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: combine explicit `content:` values and unprefixed fragments into one body `SearchQuery` in source order, separated by one space.
  Rationale: `SearchDocuments` already owns free-form content-query normalization. `SearchFields` should route body text to that contract rather than reimplement lexical semantics.
  Date/Author: 2026-08-10 / Codex.

- Decision: reject a boolean `or` that crosses the metadata/body boundary.
  Rationale: delegating one body query and intersecting it with field matches implements conjunction. A mixed union needs an explicit ranking policy for field-only, body-only, and both-lane results.
  Date/Author: 2026-08-10 / Existing design retained.

- Decision: generate a reserved `meta` map entry from all other non-empty metadata values, using deterministic key order and a positional boundary gap.
  Rationale: `meta:` can use one ordinary field-posting lane instead of expanding a query across every field, while phrases remain field-boundary-safe.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: call the generic restriction relation `document_filter_targets` and thread it through the canonical document funnel into document retrieval.
  Rationale: the relation is query-scoped and specifically limits the document-filter universe; `admission_targets` is too broad and suggests a field-specific concept inside `SearchDocuments`. The document funnel remains field-unaware because it only sees query/document keys.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: apply `document_filter_targets` as an additional restriction after canonical filter scores are resolved, and force targeted queries through online filter resolution.
  Rationale: this keeps the canonical cache contract and score normalization unchanged while ensuring that a restricted query does not mistake an unrestricted cached filter group for a complete target-scoped result, without requiring a field-specific `SearchDocuments` subclass.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: preserve existing full-corpus `OnlineScoring` behavior in this plan; do not make `document_filter_targets` change score computation or normalization.
  Rationale: `SelectScores` normalizes BM25 per query before combining it with overlap, so filtering score inputs changes score meaning and makes target-aware online rows incompatible with full-corpus cached rows. Targets still reduce the candidate set entering retrieval and reranking. A future optimization may pass targets into scoring only after introducing a raw-score/global-normalizer or target-scoped cache contract.
  Date/Author: 2026-08-10 / Codex.

- Decision: assign delegated body searches a distinct child query ID.
  Rationale: the delegated `SearchQuery.content` no longer equals the original field-aware query text. Existing filter and score caches, requests, feedback joins, and result rows are keyed by query ID; reusing the parent ID would allow artifacts for different query content to collide. The child ID is deterministic from the parent ID, normalized delegated content, and delegation contract version, while the public `FieldSearchResult.query_id` remains the parent ID after result remapping.
  Date/Author: 2026-08-10 / User and Codex.

- Decision: represent delegated content results as an optional nested `DocumentSearchResult` inside `FieldSearchResult`.
  Rationale: delegated rows retain the complete lexical, feedback, candidate-rank, and final-rank evidence; metadata-only rows do not fabricate a content score or ranking object.
  Date/Author: 2026-08-10 / User and Codex.

## Outcomes & Retrospective

Implementation is complete. The parser now sends unprefixed and explicit `content:` text to document search, while only explicit metadata prefixes produce field clauses. `DocumentFields` generates a deterministic `meta` field with positional boundary gaps. `FieldSearch` in `field_search.py` resolves metadata and selects delegatable queries; `BuildDelegations` creates the internal `FieldSearchDelegation` parent/child mapping, body requests, and `document_filter_targets`; and `PublishFieldSearchResults` in `publish.py` publishes the delegated result as an optional nested `DocumentSearchResult` under the parent query ID. `SearchFields.py` reuses canonical `SearchDocuments` through the optional target input, including target-aware online gap selection, filter-target selection, vectorization, scoring, and retrieval.

Target restrictions are enforced after canonical filter-score resolution and before vectorization, scoring, and retrieval consume the target relation. Ordinary queries retain the unrestricted filter path. `OnlineScoring` remains full-corpus so existing score normalization and cache semantics are unchanged. Focused parser/compiler tests and generated-output parity pass; Spark integration tests remain skipped by the repository environment.

## Context and Orientation

The Search example stores caller-owned documents in `examples/search/schemas/text.py`. `Document.fields` is the authoritative map for searchable string metadata. `ExtractDocumentFields` in `examples/search/transforms/fields/ExtractDocumentFields.py` completes that map and emits flattened `DocumentField` rows. `FieldIndex` in `examples/search/transforms/indexing/fields/FieldIndex.py` converts those rows into positional `FieldTerm` postings.

`parse_field_search_query` in `examples/search/algorithms/field_search.py` currently treats unqualified terms as metadata clauses. This plan changes that behavior: a token with an explicit field prefix becomes a field clause; a token without a prefix becomes body-query text. `content:` is an explicit body prefix. `meta:` is a reserved generated metadata field.

`SearchFields` currently matches field postings and optionally consumes precomputed content scores. It will instead become a staged serving composition. Its field stage resolves metadata matches. Its body stage creates ordinary `SearchQuery` rows and delegates those rows to `SearchDocuments`. Its publication stage joins delegated `DocumentSearchResult` rows to field matches and wraps them in `FieldSearchResult`.

`SearchDocuments` composes canonical online filtering, filter-target selection, online scoring, document retrieval, and feedback reranking. It remains field-unaware and accepts one optional generic `document_filter_targets` relation. The relation narrows target selection and forces target-scoped queries through online filter resolution, while ordinary queries retain the cache-aware path. A delegated query with no field matches is omitted from delegation rather than represented by an ambiguous empty target set.

## Plan of Work

### Milestone 1: Define the query partition and body delegation contract

Update `FieldSearchQuery` and `parse_field_search_query` so the parser emits only explicitly prefixed metadata terms into `FieldSearchTerm`. Preserve the source query text for diagnostics. Build the body `content` value from unprefixed fragments and explicit `content:` values in their original order.

The parser must distinguish three cases:

- A field-prefixed clause such as `title:guide` or `meta:guide` becomes a metadata clause.
- An unprefixed term or phrase such as `aurora` or `"release notes"` becomes body text.
- A `content:` clause becomes body text with the prefix removed.

Boolean operators remain lowercase. Metadata-only `and` and `or` continue to operate in the field lane. A mixed metadata/body `or` is rejected with a diagnostic explaining that combined queries currently use conjunction. Body fragments are passed to `SearchDocuments` as free-form text; `SearchFields` does not assign body phrase or boolean semantics beyond assembling the text.

Rename or replace the old default-metadata fields in `FieldSearchQuery` so the schema no longer claims that unqualified text has a metadata default scope. Retain a field-clause count and an explicit body-content indicator so later stages can decide whether to delegate without reparsing raw text.

### Milestone 2: Add the generated `meta` field

Update `DocumentFields.complete` to construct a base metadata map from typed reserved fields and caller-supplied `Document.fields`, with caller map values winning for existing reserved keys. Remove any caller-supplied `meta` entry before constructing the generated value; `meta` is reserved and derived.

Build `meta` from non-empty base-map values in deterministic ascending field-key order. Join values with a reserved control separator surrounded by whitespace. The separator must normalize to an empty token in the existing metadata tokenizer, leaving a position gap after `FieldIndex` drops it. Replace or escape the reserved separator in source values before aggregation so user data cannot manufacture the boundary marker.

Store the generated value under `fields["meta"]`. Keep body `Document.content` out of the map and out of `FieldIndex`. `meta:` therefore uses the same exact field-name lookup as `title:` but searches one compact aggregate posting lane.

Add tests proving that `meta` includes every searchable metadata value, has stable construction order, cannot be overridden by the caller, and does not allow a phrase to cross from the end of one original field into the beginning of another.

### Milestone 3: Refactor SearchFields into staged delegation

Refactor `SearchFields` into these logical stages. They may be separate transforms or lanes in the same source module, but each stage must have a typed relation boundary.

`ResolveFieldTargets` consumes `FieldSearchTerm` and `FieldTerm`, applies field-local term and phrase matching, resolves metadata boolean logic, and emits query/document target rows. `meta:` is an ordinary `field_name == "meta"` match. No null field name means “all metadata” anymore; only `meta:` has that meaning.

`BuildContentQueries` consumes the parsed `FieldSearchQuery` plus the caller's ordinary `SearchQuery` metadata. For queries with non-empty parsed body content, it projects the ordinary query identity, labels, flags, language, and requested timestamp while replacing `SearchQuery.content` with the parsed body text. It emits no body query for metadata-only requests.

`BuildDelegations` creates child body queries, child requests, the parent/child identity mapping, and field matches projected as `document_filter_targets(query_id=child_query_id, document_id=...)`. It composes canonical `SearchDocuments` using the caller's existing documents, score artifacts, index artifacts, policies, user contexts, and feedback relations. The delegated result is the canonical `DocumentSearchResult`. `SearchFields` must not alter canonical `SearchDocuments` formulas or teach it field syntax.

`PublishFieldSearchResults` handles two paths. For metadata-only queries, it publishes field-only rows in deterministic document-ID order with no nested document result. For delegated queries, it joins delegated `DocumentSearchResult` rows to the resolved field targets when metadata clauses exist; the target restriction should already have been applied inside the document funnel, and this join remains a correctness guard. It then wraps surviving rows in `FieldSearchResult`. Body-only queries pass through all delegated rows with a `content` match scope.

`BuildContentQueries` and `BuildContentRequests` must use the same deterministic child query ID. The child request copies request timing, experiment, user, ranking, and other serving context while replacing `query_id` with the child ID. Keep the original request and parent ID outside the delegated subgraph. After `SearchDocuments` returns, remap `DocumentSearchResult.search_query_id` from the child ID to the parent field-query ID before placing it in `FieldSearchResult.document_result`; internal joins use the child ID, while the public field-search envelope uses the caller's ID.

For a mixed field/body query, emit target rows only for field-matching documents. If no document matches the field clauses, emit no child query/request and therefore no delegated results. For a body-only query, emit the child query/request without target rows, which means ordinary unrestricted `SearchDocuments` behavior.

The result envelope should be:

    FieldSearchResult:
        query_id
        document_id
        match_scope
        document_result: nullable struct<DocumentSearchResult>

`document_result` is non-null only when the content path was delegated. Do not duplicate lexical score, feedback, or rank fields at the outer level; consumers use the nested `DocumentSearchResult` as the authoritative content result. Metadata-only results are constraint matches, not lexical scores.

- Online and generated execution agree for parser-materialized inputs, field-only results, delegated body results, and mixed results.
- Existing direct callers of `SearchDocuments` continue to compile and produce their previous results.
- The focused tests, golden tests, and `make build` pass.

## Interfaces and Dependencies

The parser remains a pure-Python function and must not become a Spark UDF. It produces typed `FieldSearchQuery` and `FieldSearchTerm` rows for the serving transform.

`SearchFields` depends on `FieldTerm`, `FieldSearchQuery`, `FieldSearchTerm`, the caller's ordinary `SearchQuery` metadata, and the same SearchDocuments artifact inputs required for content serving. It owns query partitioning, field matching, body-query projection, delegation, and result-envelope publication.

Canonical `SearchDocuments` accepts its existing `SearchQuery`, document, request, index, score, policy, context, and feedback interfaces plus an optional generic `DocumentSearchTarget` relation. No field schema or field transform is imported into canonical `SearchDocuments`.

`document_filter_targets` has the following contract. If a query has no rows in the optional relation, it is unrestricted. If a query has one or more rows, only those document IDs survive `SelectFilterTargets` and enter vectorization, scoring, and retrieval. The field layer supplies rows keyed by the delegated child query ID. The relation is not a replacement for `DocumentTerm`: `DocumentTerm` remains query-independent lexical index data.

`OnlineFiltering` accepts `document_filter_targets` as an optional additional restriction. Queries with target rows are selected for online filter resolution even when an unrestricted cached filter group is available; after resolution, `SelectFilterTargets` intersects the selected targets with the supplied query-scoped relation. The current `DocumentFilterScore` schema remains global; target restrictions therefore do not claim target-scoped cache completeness.

`OnlineScoring` continues to receive the ordinary body queries and existing score caches without target restriction in this plan. Passing `document_filter_targets` into score matching would change the per-query BM25 maximum used by `SelectScores`; it is therefore reserved for a later target-aware scoring contract.

`FieldSearchResult.document_result` is an optional `struct(DocumentSearchResult)` field. The nested type is authoritative for delegated content ranking. Metadata-only rows carry no content result and must not invent BM25, overlap, feedback, candidate rank, or final rank values.

The `meta` map key is reserved by the Search field model. `DocumentFields` owns its construction; callers may provide arbitrary custom keys but may not override the generated aggregate.
