# Generation

Structure generation turns a checked transform plan into deterministic, reviewable PySpark source and generated
documentation. Discovery, plan validation, artifact identity, and write-if-changed behavior belong to the compiler;
target-specific lowering and rendering belong to the selected plugin.

The [Transform background](Transform.back.md) explains authoring semantics. This background explains source modules,
generated Python, generated schemas, runtime support, documentation, provenance, and performance guardrails.
The normative sources are [PySpark Code Generation](../dev/specifications/PySparkCodeGeneration.spec.md) and the
[PySpark Code Generator design](../dev/design/PySparkCodeGenerator.design.md).

## Source And Artifact Boundary

Compilation and generation are Spark-free. They must not import PySpark, start Java, create a Spark session, connect to
a cluster, or inspect the developer machine's installed Spark runtime.

Source roots are explicit directories containing importable Python modules. Discovery maps each source file to a module
name, validates import-safe structure, preserves deterministic source order, and records source paths and line metadata
for diagnostics.

Generated output is derived from source, configuration, target profile, plugin version, and Structure version. It is not
a second authoring surface and must not be edited by hand. Artifacts may be written to disk, held in memory, or imported
through a caller-selected generated source root.


## Generated Layout

A generated project normally contains:

```text
generated/
  schemas/
    <schema-module>.py
  transforms/
    <transform-module>.py
  runtime/
    <target-runtime>.py
```

The exact package layout is target-owned, but generated modules must have stable names, importable packages,
deterministic file order, and no hidden dependency on the source tree beyond documented runtime helpers.

Generated schemas materialize the checked [Schema](Schema.back.md) model as StructType declarations and result-shape
metadata. Generated transforms expose keyword-only input binding and a run method whose result aliases match declared
outputs. Generated runtime helpers support only the contracts needed by generated code.

Generated headers should identify generator version, selected backend, target profile and variant, and useful source
identity. Users should be able to tell which source and configuration produced a file without executing it.


## Generated Artifact Details

The default artifact tree is:

```text
generated/structure_generated/
  <source-package>/pyspark/schemas/
  <source-package>/pyspark/transforms/
  runtime/
  traceability/
```

Source package paths are mirrored under the generated package. Schema modules may be flattened with the shortest unique
suffix of their dotted source module path. Every generated Python package directory has an `__init__.py` when required
for importability. Paths are stable for source root, module, class, configuration, and target backend.

Every generated Python file begins with a stable ownership header:

```python
# Generated by Structure. Do not edit by hand.
# Source: orders.transforms.order.EnrichOrders
```

Headers contain no timestamps, machine paths, random IDs, or other nondeterministic values. Runtime support files and
traceability files use equivalent stable source identities.


## Generation Configuration

Generation uses the resolved configuration for source roots, generated directory and package, target profile and
variant, validation modes, traceability, formatting, performance, and generated documentation. The generated-only
options are canonicalized before they enter artifact identity:

```toml
generated_code_options = []
generated_code_hard_wrap = 120
format_generated = true
traceability = "none"
strict_performance = true
```

`generated_code_options` changes source packaging without changing online semantics. `embed_hooks` is all-or-error for
eligible hooks and cannot hide a Python UDF dependency. `generated_code_hard_wrap` must be at least `80`; generated
Python should remain within the configured limit. Configuration changes invalidate generated artifacts and their
semantic fingerprints.


## Generated Public API

Generated transforms accept caller-owned runtime objects and declared DataFrame inputs by keyword. They return a
caller-owned DataFrame result or a structured result object containing declared output lanes. Generated code does not
load data, write storage, start streaming queries, or own Spark session lifecycle.

Generated classes may expose schema constants, transform metadata, source identity, explain/traceability data, and
runtime helper references when those are part of the selected public contract. All names must be deterministic and
collision-safe.


## Generation Pipeline

Generation follows one semantic path:

```text
source roots
  -> discovery and import-safe metadata
  -> symbolic capture
  -> checked TransformPlan
  -> selected target capabilities
  -> PySpark execution recipes
  -> schema/runtime/transform source
  -> formatting, provenance, and write-if-changed
```

The emitter renders already-checked recipes. It does not re-infer joins, nullability, literal types, hook order,
validation placement, aliases, or capability support while producing text. Online and generated execution use the same
lowered target semantics described in [Execution](Execution.back.md#semantic-parity-contract).


## Current DataFrame Variable

Generated transforms retain one named DataFrame variable per source-order lane producer. The first step starts from its
selected declared input; each step assigns its result to the destination lane; hooks receive and replace their selected
lane; and joined relations use stable temporary aliases. Multi-result steps share one filter/join frame, then project
each declared result independently. Generated code never relies on implicit carry-through columns or hidden mutation.


## Lowering Rules

Schema declarations lower to explicit StructType fields in effective order. Expressions lower to PySpark functions,
Column operators, typed literals, and explicit casts selected by the target capability profile. Filters lower to
source-ordered where operations. Projections lower to explicit select or equivalent constructors.

Joins lower according to the [Join](Join.back.md) contract: qualified aliases, deterministic repeated-join suffixes,
explicit right-side projection, declared hints, and visible dedupe or temporal policies. Hooks lower as explicit opaque
calls with declared input binding, schema mode, target scope, and order.

Validation lowers at declared input, intermediate, or output boundaries. Schema-only validation remains action-free.
Value-level constraints are explicit and may require Spark work. Streaming restrictions follow
[Streaming](Streaming.back.md).


## Generated Transform and Hook Options

Each concrete source transform maps to one generated public class. The constructor receives keyword-only `spark` and
optional `ctx`; `run(...)` receives keyword-only declared DataFrame inputs and returns the generated `TransformResult`.
Generated classes may preserve inherited source step ownership through compiler-owned generated parents, but users must
not edit or subclass generated classes. A hook-free class omits the source transform import and `_impl`; a hook-bearing
class creates the source implementation instance as required by the selected packaging options.

`generated_code_options = ["mirror_methods"]` can expose source-named generated methods and zero-argument orchestration.
`embed_exprs`, `embed_hooks`, and `embed_udfs` independently control expression-helper, raw-hook, and UDF rendering.
Embedding changes source packaging and artifact identity, not the flattened execution plan. `embed_hooks` is
all-or-error
for a composed artifact and requires every copied hook to satisfy its standalone local-dependency rules.

The generated `HookInputs` namespace is read-only and appears only when a hook requests `pass_inputs=True`. Generated
hooks retain source lane binding, schema mode, validation placement, source order, target scope, traceability, and
streaming classification.


## Generated Documentation And Provenance

Generated documentation should explain effective schemas, field aliases, transform inputs and outputs, step order,
operation families, source locations, artifact identity, and capability profile. It is derived from the same checked
model as generated code so documentation cannot silently describe a different contract.

Compiler provenance maps source nodes to IR nodes and generated PySpark nodes. Static dataflow traceability records
transform, source input, output, and column dependencies inferred from checked IR. Source paths and line numbers are
diagnostic anchors, not semantic identities.


## Rendering and Verification

The emitter consumes resolved configuration, `SchemaDef` values, `TransformPlan` values, target capabilities,
provenance,
and static dataflow records. It must not re-infer aliases, nullability, join order, hook order, validation placement, or
capability support while rendering. Imports are minimal and deterministically grouped; schema projection uses explicit
`select(...)` in effective target-field order.

Generated modules carry a semantic fingerprint of the checked artifact. Generated mode compares that fingerprint with
the
artifact selected by its session and rejects stale output rather than executing a different transform meaning. The CLI
`structure compile --fail-on-diff` generates in a temporary directory, compares added/removed/changed files, and never
modifies the configured generated directory.

Only changed files are formatted and written. Parallel generation may process independent modules concurrently, but
final
file order, aliases, imports, provenance, diagnostics, and conflict handling remain deterministic. Cache keys include
source fingerprints, configuration, target profile, Structure version, and plugin version.


## Generated Documentation

Generated documentation is opt-in and is written below `generated_docs_dir`, relative to `generated_dir` (default
`generated/docs`):

```toml
generated_docs = true
generated_docs_dir = "docs"
generated_docs_formats = ["markdown", "json"]
```

The project index is `index.md` and/or `index.json`; schema pages are placed below
`schemas/<source-module-path>/`, and transform pages use `transforms/<module>.<Transform>.md` or `.json`. Markdown
uses the generated-file ownership header. JSON is valid JSON with `"generated_by": "Structure"`. Schema pages list
field names, Spark names, types, nullability, and bases; transform pages list inputs, outputs, steps, dependencies,
target artifacts, and traceability links. Generated docs describe the checked public contract, not private compiler
internals. When docs are disabled, `--fail-on-diff` ignores existing generated-doc files.

## Determinism And File Writes

Identical source, configuration, target profile, plugin version, and Structure version produce identical generated
content and file order. Determinism includes schema field order, transform step order, alias allocation, imports,
diagnostics, provenance, and generated documentation.

The fail-on-diff mode compares would-be output with committed generated files and fails when regeneration would change
them. Normal generation writes only changed files, preserves project line-ending policy, and does not touch unrelated
files. In-memory generation follows the same artifact identity and content rules.

Parallel generation may process independent modules concurrently, but final output ordering and conflict handling remain
deterministic. Shared caches and artifact stores must be safe for concurrent readers and writers.


## Performance Guardrails

Generation and online execution share compilation work. The compiler should measure discovery, symbolic capture, IR
validation, target lowering, rendering, and file writes separately. Performance targets are regression budgets, not
permission to weaken validation or determinism.

The critical constraints are:

- discovery scales with files and declarations rather than repeatedly importing the same module;
- symbolic capture scales with compiled operations rather than input data size;
- rendering is linear in the lowered plan and emitted text;
- unchanged artifacts are not rewritten;
- caching never changes diagnostics, source order, capability decisions, or generated bytes.

Cache keys include source fingerprints, configuration, target profile, Structure version, and relevant plugin version.
Invalidation must be conservative and observable.


## Diagnostics

Generation diagnostics should identify source transform, target profile, artifact path, and shortest fix. Common
failures include import-unsafe source modules, duplicate generated identities, unsupported target capabilities, stale
generated
output, generated-module import failures, and mismatched source and generated package roots.

```text
CompileError GEN-E0902: Generated transform is not importable

Problem:
  Structure could not import the generated PySpark class for this transform.

Use:
  Run structure compile, ensure the generated source root is importable, or use execution_mode = "online".

See docs/background/Generation.back.md
```


## Provenance and Acceptance

Compiler provenance maps source transforms, methods, expressions, fields, and decorators to IR and generated nodes.
Static dataflow traceability records transform, input, derived relation, schema, field, and artifact dependencies. These
records are metadata, not runtime telemetry, and source paths remain project-relative.

Generation is complete when generated schema constants, transforms, runtime support, provenance, traceability, and
documentation import or validate as configured; online and generated execution pass semantic parity; stale output is
detected without mutation; generated files are deterministic and readable; prohibited operations such as UDFs, Pandas
UDFs, RDDs, `collect`, `toPandas`, and row-wise maps fail or warn according to policy; and compiler commands remain
Spark-free.


## Appendix: Deliberate Non-Goals

Generation does not edit user source, hide unsupported operations behind UDFs or local loops, run Spark actions, own
data or storage lifecycle, generate streaming sources or sinks, or claim compatibility with an unselected backend.
